# 测试约定

## 回归测试与主动脚本分层

- 自动回归断言与人工发起的诊断、基准、冒烟脚本分开存放。Node Web Host 回归测试放在 `apps/web-host/tests/`，Core 回归测试放在 `packages/core/tests/`，前端 Vitest 放在 `apps/ui/tests/`，Playwright 放在 `apps/ui/e2e/`。主动脚本按用途放在对应 Node package 的 `scripts/` 或仓库 `scripts/` 下。
- 主动脚本使用描述动作的名称（如 `probe-*`、`compare-*`、`bench-*` 或 `smoke-*`）；避免使用测试框架会自动收集的 `*.test.*` / `*.spec.*` 命名。自动回归测试继续使用对应框架的标准命名。
- 主动脚本不应成为回归测试的唯一覆盖。发现稳定行为后，应将合成输入、可重复断言沉淀到对应回归套件；真实 Provider/数据探针留在人工脚本目录并明确成本、副作用和授权边界。
- `scripts/tests/` 是测试分层调度和清单治理工具，不是产品测试用例目录。性能报告、临时复现输出和真实数据不得放进回归测试目录。

## 测试目录与命名

- 各端的测试目录先按产品功能归档。功能域较大时，再按路由、存储、调度、执行与投递等职责拆分。
- 文件名使用目录内可区分的职责名，例如 `scheduled-tasks/run/lease.test.ts`。需要说明运行环境时使用 `.postgres.test.ts` 或 `.integration.test.ts`。具体触发条件和预期结果写在用例标题。
- 搬迁与行为合并分开验证。同步更新测试路径清单及元数据，核对移动前后的测试发现范围。Web Host 的递归 glob 交给 Node 展开，命令中的 glob 须加引号，以免 shell 提前展开并漏掉嵌套目录。

## 测试质量与选层

测试的目标是保护产品契约、领域规则和重要边界，不是复述当前实现。针对具体函数编写单测是允许的；关键在于断言函数对调用方承诺的输入、输出、不变量和失败行为，而不是私有变量、调用顺序或当前代码片段。

### 设计测试时

1. 先写清被保护的行为和可能发生的回归，再选能实际经过该行为的最低测试层级：纯逻辑用单测；组件状态、用户操作与请求/持久化联动用组件或集成测试；少量高风险跨系统路径用 E2E。
2. 对领域规则覆盖代表性正常输入、边界输入和非法输入。多组输入共享同一规则时可用表驱动/参数化测试；只有存在真实共用契约时才抽取测试 helper，不为复用而制造含义不清的万能测试框架。
3. 断言结果及可观察副作用，例如返回值、状态变化、请求参数、持久化后重载结果、权限拒绝或可见 UI 状态。避免只断言“某选项/类名/API 字符串出现在源码中”。
4. 每个测试都应能回答：它能拦住什么具体回归？如果采用语义等价的实现方式，测试是否仍应通过？若测试只会因重命名、格式调整、拆分组件或换一种等价选择器而失败，应改为行为断言或静态架构规则。
5. `keyBehavior`、测试名称和必要注释描述关键回归行为，而非只写函数名、实现阶段或泛化的“正常工作”。

### 选择性质测试与状态序列测试

- **性质测试（Property-Based Testing）**：当输入空间较大，且存在明确、可判定的普遍性质时考虑使用，例如规范化幂等、合法数据 round-trip、排序稳定性或边界约束。先确认性质确实属于产品/领域契约；不要为了减少示例用例而机械引入生成式测试，也不要用未经验证的“数学性质”替代具体业务预期。
- **模型/状态序列测试（Model-Based 或 Stateful Testing）**：当风险来自多步操作组合时考虑使用，例如创建、移动、归档、恢复和删除之间的交互。模型应只表达必要的状态和不变量；保留易定位的关键单步回归用例，并确保失败序列可复现、可缩减和易诊断。
- 这两类方法与示例测试互补，不以“抽象程度”决定质量。若性质难以清晰表达、模型成本超过其发现问题的价值，继续使用有针对性的表格测试或集成测试。
- Schema 驱动的 API 测试可用于探索协议形状、参数边界和状态链路，但不能替代业务语义、认证/ownership、数据隔离和副作用断言；接入新工具前先对单个领域做小范围验证，不因方法建议就默认增加依赖。

### 按测试对象处理

- **纯逻辑/具体函数**：保留能说明领域契约的单元测试。若测试仅逐项重复静态枚举、默认值或模板常量，而类型检查/调用方行为已充分保证且没有独立风险，可不新增重复用例。
- **设置与表单**：不要只检查源码含有 A/B 选项。若选项影响运行配置，应验证用户能选值、提交时传出正确值、重新加载后显示已保存值；若选项改变运行策略，再验证对应策略效果。纯展示选项无需为了选项数量机械地创建端到端测试。
- **UI/CSS**：静态源码测试不能证明浏览器中的级联样式和交互结果。视觉/交互缺陷应在具备真实样式计算的浏览器测试中验证关键状态；静态检查只用于 token 使用、选择器归属、禁止规则或其他明确的结构不变量。优先覆盖共享规则和高回归风险场景，不把每个组件都做成截图测试。
- **架构/安全约束**：当约束难以由运行时行为充分表达时，可以使用源码、依赖图或静态扫描测试；断言应聚焦禁止越界、依赖方向、权限隔离等高层不变量，避免锁定完整源码片段或偶然命名。

### 审查与整理

- 发现测试低信号时，优先在修改对应功能时渐进替换；不要以“测试看起来太具体”为由批量删除，也不要仅为提高覆盖率数字增加测试。
- 删除或合并前，确认目标回归已有其他层级的有效覆盖，并遵守下文“测试失败时”的断言保护和数据安全要求。不同责任层的测试即使验证相似结果，也可能分别保护 API 契约、领域规则和用户路径。
- 对高风险规则可抽样做变异验证或手动故障注入，确认行为被破坏时测试确实失败；这属于质量抽查，不改变下文规定的变异测试运行周期，也不自动接入 CI。

## Node 后端回归

- Web Host 测试位于 `apps/web-host/tests/`，由 `@gugu/webui` 的 Node test runner 执行：`corepack pnpm --filter @gugu/webui test`。变更涉及 Core、Gateway 等工作区依赖时按需构建依赖包；Host 测试脚本会执行自身的前置构建。
- Core 测试位于 `packages/core/tests/`，使用 Vitest 与 `tests/suites.json` 分类。常用入口为 `corepack pnpm --filter @gugu/core test:unit`；集成、IPC、PostgreSQL 和 parity 套件按任务所需显式选择。完整分类见 [Node Core 回归对照清单](../../docs/testing/node-core-parity.md)。
- Desktop Host 回归位于 `apps/desktop/tests/`；前端逻辑回归见下节；跨系统关键路径才使用少量 E2E。
- Desktop Host 用例从 `apps/desktop/.tools/agent/runtime.mjs` 取运行时装配，该产物由 `apps/desktop/scripts/build-agent-runtime.mjs` 从 `src/` 打包生成。改动 `apps/desktop/src/main/` 或 `packages/core/src/` 后必须先重建该产物再跑用例；否则测的是上一版代码，会出现与源码无关的假回归或假通过。
- 测试不得读取或写入用户 `.env`、`config.override.json`、真实数据库、真实存储或运行中用户数据。文件与沙盒测试使用临时目录和合成身份；PostgreSQL 集成测试使用专用测试连接、随机 schema，并只清理本次创建的 schema。
- 诊断、基准和冒烟脚本默认拒绝真实数据库、模型或存储副作用；仅在明确授权并提供专用危险开关后运行。只读脚本也应使用合成身份或临时数据。
- Python 后端历史测试不是 Node 后端的常规验收门。只有明确核对旧行为或数据迁移时才可作为只读参考；新行为必须由 Node 测试验证，不以旧 Python 测试通过作为交付条件。
- 测试完成后检查 `git status --short` 和必要的临时存储目录，确保没有生成应被提交的运行时数据；不要清理无法确认归属的用户目录。

## TypeScript 单测（Core 与前端）

Node Core 以 `tests/suites.json` 显式分类，提供 unit/integration/ipc/postgres/parity/all；涉及进程或外部服务的用例应归入慢速层。快速层不启动 Worker、进程或服务；显式选择的 PostgreSQL 集成缺少依赖时应失败，不静默跳过。移动和新增时保留行为断言，同步分类、元数据、清单与 CI；不能把局部切片描述为全量后端功能覆盖。真实制品 smoke 使用新建临时目录。

- 跑法：`corepack pnpm --filter gugu-web run test:run`（一次性）或 `corepack pnpm --filter gugu-web run test`（watch）。
- 所有前端 Vitest 测试统一放在 `apps/ui/tests/<功能域>/`，按产品功能或跨模块领域归档；需要细分时在功能域下建立子目录。`apps/ui/src/` 只放生产代码，禁止在源码旁新建 `*.test.*` / `*.spec.*`；旧的 `apps/ui/test/` 扁平目录不再使用。Vitest 与 `test:fast` 只发现 `apps/ui/tests/`。
- 新测试优先使用 `@/` alias 引用 `src/` 生产模块，避免测试搬迁后相对路径失效；同一测试域的辅助夹具放在 `apps/ui/tests/<功能域>/` 内，不与生产代码混放。文件名使用被保护行为或模块名加 `.test.ts`；浏览器端交互验收仍归 `apps/ui/e2e/`，不混入 Vitest。
- 移动既有测试时保持行为断言不变，只改必要的导入、测试数据路径和质量工具映射；更新 `docs/testing/metadata/` 分片 中对应测试路径，不将纯搬迁误登记为新增测试。
- 改完纯逻辑/composable 之后必须跑。
- 测试失败时先定位实现、夹具和调用链，**不得直接改断言、删除用例、增加 `skip` 或放宽校验来恢复绿色**。
- 只有产品契约明确改变并完成记录后才调整预期。
- 回归用例名称和注释要写明防止的具体回归行为，至少包含触发路径和关键结果。

## CRAP 与变异测试：周期性手动执行

- CRAP 复杂度/覆盖率报告和变异测试不属于自动 CI，不由 push、PR 或发布流水线触发。
- 由维护者每季度手动运行；触及登记范围的重大重构或发布前可额外运行。使用各自文档中的显式范围和命令，并审查报告中的风险项。
- 这些检查是补充性的质量评估，不替代 Node 后端回归、Vitest 或 E2E；现有自动 CI 测试范围保持不变。
- 变异测试范围和源码→测试映射以 `scripts/quality/mutation_scope.json` 为准；该质量报告工具目前由 Python 脚本实现，手动入口为 `python3 scripts/quality/mutation_report.py --language typescript`。仅运行 TypeScript 范围，报告输出到 `docs/reports/`，同日重跑须显式 `--overwrite`。此脚本是维护工具，不代表 Python 后端是开发目标。
- 如需保留同日基线并另存复跑，可传 `--report-dir docs/reports/<run-name>`；只允许写入 `docs/reports/` 内。
- 变异报告必须把 killed、survived、timeout、编译/运行错误、无覆盖、等价和未检查状态分开。未运行、未覆盖或编译失败的变异不得计入 killed；只有完成行为审查后才能登记等价变异。
- CRAP 目标预算为 5 分钟，单种语言的变异测试目标预算为 10 分钟；超预算优先排查环境和显式范围，不接入 CI 或放宽异常统计。
- 报告历史记录长期保留；季度检查只清理确认可再生的临时缓存，不自动删除历史报告。
- 如需改变这一策略，必须先更新对应 PRD 并明确评审，不能顺手把报告或变异任务接入 workflow。

## E2E（Playwright）

配置在 `apps/ui/playwright.config.ts`，用例在 `apps/ui/e2e/*.spec.ts`。

### CI 只接确定性的关键路径

CI 的 Runtime integration workflow 执行 `test:e2e:stable`；当前稳定列表包含 `smoke`、`page-lifecycle`、`calendar`、`chat`、`file-lifecycle`、`file-drag-runtime`、`filesystem-phases`、`mind-canvas-runtime`、`scheduled-task-ui`、`scheduled-task-run`、`theme-divider`。文件系统 E2E 必须创建唯一 fixture，并在每例结束时精确清理，不能依赖测试账号已有文件或项目，也不能因缺少既有数据而跳过。以 `apps/ui/package.json` 的脚本和 workflow 调用为准，调整列表时同步更新本文。

项目文件区 Runtime 拖拽单独由 `test:e2e:experimental` 运行。当前浏览器复现中，项目文件卡片松手后代理没有结束、服务端移动请求也未发出；在修复该交互前不要把这两条用例纳入稳定 CI。

新增用例接 CI 的标准：
- 不依赖测试账号的既有数据（每轮 CI 全新数据库）。
- 不接真实模型；mock LLM 服务位置以对应 workflow 和当前 Node 测试配置为准。断言只验证"收到了 AI 回复"，不抠固定文字。
- 不需要真实设备权限或第三方账号绑定。

新增 CI 用例需同时改 `.spec.ts` 文件、`apps/ui/package.json` 的稳定 E2E 列表，并确认 workflow 调用 `pnpm --filter gugu-web run test:e2e:stable`。

### 选择器约定

- 有 `title`/文本的交互元素：`page.getByRole('button', { name: '登录' })`。
- 没有语义信息的容器：直接用现有 CSS class（如 `.chat-window`），改了要跟着改测试。

### CI 语言与多语言测试

- CI 主 E2E 流程固定使用简体中文 `zh-CN`。Playwright 配置必须显式设置 `use.locale = 'zh-CN'`，测试用户的语言偏好也必须显式初始化，不能依赖 runner 或 devserver 的系统语言。
- 中文是主流程的稳定基线；英文和日文使用独立的 locale matrix 或 smoke 测试，不要让主 CI 同时依赖三套可见文案。
- 选择器优先使用 `data-testid`、ARIA role/name、`aria-label`、表单 `name`、稳定 CSS class 和 URL。可见中文文案不能作为唯一选择器；文案断言也不应承担元素定位职责。
- 必须断言用户可见文案时，主 CI 断言 `zh-CN` 资源；其他语言单独检查翻译缺失、长文本溢出、按钮尺寸和关键路径可用性。
- 测试夹具、seed 数据、快照标题和测试用户可见内容统一使用合成中文数据，不读取真实用户的语言偏好。
- 新增页面或组件时，先补 `zh-CN` 主流程和稳定选择器，再补英文/日文专项；不要为了让多语言测试通过而放宽断言或复制三套业务流程。
