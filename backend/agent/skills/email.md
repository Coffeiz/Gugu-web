# 邮件发送 Skill

## 目标

通过 `send_email` 按邮件用途选择格式。模型负责判断场景、收件人和内容；邮件服务负责模板渲染、纯文本备用正文、HTML 清洗和 SMTP 发送。

## 必须遵守

1. `subject`、`body` 和 `format` 必填。`body` 始终是完整纯文本；模板和自定义 HTML 都必须保留它作为备用正文。
2. 普通邮件交流使用 `format="plain"`，只发送纯文本，不生成 HTML。
3. 定时提醒、周期报告、状态通知和安全通知使用 `format="template"`，按用途选择模板并传语义字段。
4. 只有用户明确要求复杂排版、图表或品牌样式时使用 `format="html"`，并提供受控 `html` 和完整纯文本 `body`。
5. 工具返回 `status=sent` 后才能说“已发送”；这只表示 SMTP 接受，不代表最终送达。
6. 用户未指定收件人时省略 `to`，由服务端发送到当前用户注册邮箱；不要因为看不到邮箱地址而向用户索要。

## 三种模式的适用范围

先判断邮件的用途，再设置 `format`。选择顺序如下：

1. 用户明确指定纯文本、模板或自定义 HTML 时，按用户指定执行。
2. 用户要求复杂视觉排版、邮件图表或品牌样式时，使用 `html`。
3. 邮件属于提醒、周期报告、状态通知、安全通知或批量订阅内容时，使用 `template`。
4. 其他普通邮件交流使用 `plain`。

| 模式 | 适用范围 | 典型请求 | 发送结果 |
| --- | --- | --- | --- |
| `plain` | 一对一的普通交流，内容以自然语言为主，不需要品牌包装 | “帮我告诉客户周五开会”“把这段说明发到我邮箱”“确认收到并感谢对方” | 只发送 `text/plain`；不套 HTML 模板 |
| `template` | 需要稳定结构、反复投递或便于快速浏览的通知类邮件 | 每日/每周报告、定时提醒、任务到期提示、状态变化、安全告警、订阅邮件 | 发送咕咕标准 HTML，并附完整 `body` 纯文本备用正文 |
| `html` | 用户明确要求视觉化、品牌化或复杂布局，标准模板字段无法表达 | 邮件内含定制图表、品牌版式、特殊表格布局 | 发送清洗后的自定义 HTML，并附完整 `body` 纯文本备用正文 |

### 容易混淆的边界

- **是否定时不单独决定格式。** 定时发送的简短原文仍用 `plain`；定时提醒、摘要或周期报告用 `template`。创建定时任务时，应在任务指令中保留该格式选择。
- 普通交流即使包含多段文字，也不因此升级为 `template`；只有确实需要标题区块、摘要、操作按钮或固定通知结构时才用模板。
- 只有用户明确提出图表或视觉布局，或内容确实无法由模板字段表达时才用 `html`。不要仅为了让邮件“更好看”就生成自定义 HTML。
- 邮件客户端不保证运行网页图表。自定义图表使用兼容邮件的表格或文字表达；不要生成 SVG、脚本或外部资源。
- 用户说“发邮件”但未指定样式时，根据内容用途选择；普通说明默认 `plain`，提醒/报告/通知默认 `template`。

## 模板选择

`template` 模式下，所有模板由同一个邮件服务渲染，并自动适配用户的主题和配色：

| 模板 | 使用场景 |
| --- | --- |
| `notification` | 普通通知、结果和消息 |
| `reminder` | 日程提醒、定时任务和待办 |
| `report` | 摘要、统计和进展报告 |
| `security` | 登录、安全告警和账号操作 |
| `test` | 仅 SMTP 连通性或样式测试 |

不要为了改变标题或正文而使用 `test`。

## 内容与排版

- 使用 `title`、`preheader`、`sections`（`heading`/`text`）和 `actions`（`label`/`url`）表达结构化内容。
- `theme` 和 `palette` 默认使用 `auto`，跟随用户偏好；用户明确要求时可指定 `light`/`dark` 和 `mist`/`cafe`/`rose`/`sky`/`sage`。
- 需要间距、分隔线、强调块或按钮时，使用上述语义字段，由标准模板负责表格布局和兼容样式。
- 不要把 HTML 标签塞进 `body`；使用 `html` 时仍必须提供完整的纯文本 `body`。
- `html` 仅允许基础邮件标签：`a`、`b`、`blockquote`、`br`、`code`、`div`、`em`、`h1`-`h3`、`hr`、`i`、`img`、`li`、`ol`、`p`、`pre`、`span`、`strong`、`table`、`tbody`、`td`、`th`、`thead`、`tr`、`u`、`ul`；样式只能使用有限的内联 CSS，不使用自定义 CSS、外部字体、flex/grid、背景图片或复杂定位。
- `html` 最多 40000 个字符；服务端会再次清洗，不要依赖被清洗的标签、属性或样式。
- 邮件客户端不保证支持图表脚本、SVG 或外链资源；需要图表时用邮件兼容的表格或文字表达，不要假定网页图表代码能在邮件里运行。

## 安全边界

- 禁止脚本、事件处理器、表单、iframe、SVG、外部 CSS、外部图片、追踪像素和未经用户要求的敏感信息。图片仅可使用受控的内嵌 PNG；链接只使用完整的 `https`、`http` 或 `mailto` 链接。
- 操作链接只使用完整的 `https`、`http` 或 `mailto` 链接；不要使用 `javascript:`、数据脚本或未验证的重定向。
- 所有动态文案作为文本字段传入，不要把用户输入拼进 HTML 或 URL；服务端会负责转义和安全清洗。
- 不能通过 Skill 绕过服务端 sanitizer；如果排版依赖被清洗的标签或属性，应改用标准模板字段。

## 收件人与 SMTP

- 发送给用户本人：省略 `to`，使用注册邮箱。
- 用户明确指定其他邮箱：传 `to`，发送前确认收件人、主题和正文。
- 发送给客户：先获取当前用户拥有的客户 ID，再传 `client_id`；不要同时传 `to`。
- 客户没有邮箱时如实告知，不能猜测或改发其他地址。
- 优先使用用户设置中启用的个人 SMTP；未配置时回退到 Admin 默认 SMTP。

## 邮件附件

- 只有用户明确要求附上、随邮件发送或转发某个文件时，才添加附件；“发邮件”本身不代表同意附加相关文件。
- `send_email` 使用 `file_ids` 数组指定附件，只能填写当前用户文件库中有效的文件 ID，不能传文件名、逻辑路径或宿主机路径。
- 用户提到的文件没有可用 `file_id` 时，先用 `list_dir` 按文件名或目录定位；多个候选时结合完整路径询问用户选择，不猜测、不因同名而附错文件。若文件尚未进入文件库，说明需要先保存到文件库，再发送。
- 附件最多 5 个，单个最大 10 MB，合计最大 25 MB。超限时告知限制并请用户选择要发送的文件，不要自行压缩、删减或替换附件。
- 发送前的确认内容应包含收件人、主题、正文和附件名称；附件不明确或文件 ID 无法确认时，先澄清，不要发出。
- 发送回执成功后再说明邮件已提交；同时如实列出附件。若附件校验或读取失败，按工具错误说明，不能假称已附上。

## 确认与定时任务

- 交互式发送前确认，不要把“准备发送”说成“已经发送”。
- 用户已授权的定时任务执行邮件时，不要再次请求确认。
- 邮件不可撤回；发送前重点核对外部收件人和敏感内容。

## 失败处理

- 失败时如实报告 SMTP 未配置、连接失败、认证失败或超时，不要声称邮件已发出。
- “已提交给 SMTP”只能表述为 SMTP 已接受，不要承诺收件箱一定收到。
