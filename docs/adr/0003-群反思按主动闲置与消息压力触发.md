# ADR-0003：群反思按主动闲置与消息压力触发

> 状态：已接受
> 创建：2026-10-19
> 最近更新：2026-10-25
> 关联范围：IM 群消息、群组/群友记忆、群内 owner 反思及上下文压缩
> 关联文档：`docs/devlog/2026-10-20-群被动消息反思触发策略.md`

## 0. 决策摘要

| 主题 | 决策 | 边界 |
| --- | --- | --- |
| 被动消息 | 正常持久化、累计条数，不启动或续期闲置反思 | 不取消历史保留与权限开关 |
| 主动交流 | 完成 run 后启动或重置 3 分钟闲置窗口 | 后来的被动消息不延长窗口 |
| 固定条数 | 全群累计 50 条被动消息仍触发群组和群友反思 | 不是每个成员各发 50 条；两个反思游标独立 |
| 上下文压力 | 不足 50 条但被动历史达到 90% 预算时也创建两类反思任务 | 没有新 provider 用量，只能明确采用估算 |
| 压缩 | 反思执行前超预算，先正式压缩、重建上下文，再反思 | 会话忙或无法压缩时持久延后，不带旧超预算快照调用模型 |

## 1. 背景与问题

被动群消息不经过模型 run，但旧逻辑同时更新群游标闲置时间和 owner 群缓冲的闲置队列。零散群聊静默后也会调用反思，增加低收益调用机会。长间隔重建缺少新的主请求前缀，可能低缓存，但不能据此保证减少触发必然提高缓存率。

只移除闲置触发仍有另一边界：少数长被动消息可能在累计 50 条以前就达到上下文预算；现有“反思开始后检查压缩”不能独立启动任务。因此需要由被动消息持久化事件进行无模型预算预检。

## 2. 目标与约束

- 被动记录与反思唤醒分离；不为每次零散聊天登记闲置任务。
- 保留 50 条、任务幂等、失败重试、删除隔离与群记忆开关。
- 上下文压力不能依赖用户下次主动交流才处理。
- 不改变私聊、正常 run 的 provider 实际用量优先原则、压缩算法或缓存标记。
- 不把消息正文、完整快照或凭据写入调度日志；任务只保存已有范围与作用域信息。

## 3. 候选方案

1. 保持所有消息续期闲置：实现简单，但被动聊天持续制造闲置反思。
2. 仅保留 50 条与主动闲置：减少调用，但少数长消息不能提前唤醒预算处理。
3. 主动闲置、50 条与事件驱动预算压力并存：保留原积累规则，覆盖少数长消息；接受被动入库后额外的本地预算检查。

采用第三种。不新增固定频率模型调用，也不把压力检查做成另一条独立摘要算法。

## 4. 决策

### 4.1 触发语义

群消息仅被记录而未进入 run 时，更新历史、水位和被动条数，不开启/重置群闲置。主动 run 完成后，群游标登记主动回合并以完成时间作为闲置起点。后续被动消息可以成为本批反思内容，但不能推迟起点。

全群累计 50 条被动消息继续创建群组与成员批次任务，沿用现有延迟投递、快照复用和补偿机制。压力触发可提前创建两类任务，按各自已反思游标取范围；幂等键不包含触发原因，同范围不因原因不同重复生成任务。在途压力任务按类型去重，同作用域预检串行化，补齐部分入队的另一类型。

群内 owner 被动发言仍进入缓冲，只有主动回合启动闲置。条数/压力触发冲刷和失败后的重试仍有效；重试延迟不是“被动消息续期”。私聊时钟和阈值不变。

### 4.2 压力与压缩

被动入库后，在开启群记忆且未由条数触发的情况下，对当前会话重建历史做 90% 预算预检。使用当前用户模型的上下文大小与共享预算规则；不调用 provider。没有能代表新增被动消息的实际 usage，所以该结果是 `estimate`，不得表述成 provider 实测值。

达到阈值则持久化 `context-pressure` 任务并投递现有队列。执行器不复用旧 run 的低用量或 `provider_compacted` 标志来代表新增消息；以当前持久历史重建反思快照。正式 `compact_for_reflection` 再判定预算：需要压缩时通过既有 baseline 串行入口完成，然后重建再反思；当前会话忙或压缩不能完成则延后任务，不硬发超预算请求。

预检遇到正在运行/有待处理消息的会话，不并发改写 baseline；后续主动 run 完成后的闲置及既有条数任务承担收束。模型与预算检查失败不阻断被动消息持久化，不保证上游故障期间即时反思成功。

### 4.3 数据和升级边界

复用群游标现有字段：`pending_agent_count > 0` 表示尚未闲置收束的主动回合，`active_started_at` 表示最新主动完成时间；`last_message_at/id` 仍表示全部已记录消息。私聊字段语义不变，不新增数据库列。收束时校验版本和活动时间，避免旧扫描清除新 run 的窗口；完成较晚的旧 run 不能把消息水位倒退。

不删除已持久化任务或旧 Redis 重试记录。部署前已预约的闲置/重试可能执行一次，属于旧任务延续；新被动消息不再创建或续期闲置。原反思游标、存储保留及历史上下文读取窗口保持不变，不保证全部旧消息永久进入下一次模型请求。

## 5. 后果与取舍

减少未满条数且没有主动交互的闲置调用；50 条和压力路径仍能沉淀被动群消息。低活跃群长期记忆可能延迟，但历史仍按既有窗口可供下次主动 run 使用。

代价是每次需要预检的被动入库会增加模型配置读取、历史重建和本地估算成本；在途压力任务去重避免重复反思，不代表这些读取完全免费。估算与真实 provider token 可能偏离，后续应观察预检成本和压缩频率；本决策不承诺缓存率或响应时延收益。

## 6. 依据与验证

- `backend/tests/im/test_group_reflection_policy.py` 覆盖被动不启动/续期、主动完成时钟、水位不倒退、90% 边界和不足 50 条的持久任务投递。
- 同文件经过真实任务执行器与预算预检，验证旧 run 用量不能屏蔽被动压力、压缩后重建再反思、无法压缩则延后且不请求反思模型。
- 既有 `test_im_memory_scopes.py` 保留 50 条同时创建两类任务及私聊阈值/闲置覆盖；`test_compaction.py` 保留实际用量优先、缓存输入计入及缺失用量估算覆盖。
- 测试使用隔离数据库、fake Redis、合成消息及模型替身，不连接真实模型或用户数据。不把行为测试结果表述为真实缓存命中率提升。

## 7. 重新评估条件

当被动预算预检耗时显著、压力任务反复积压、实际用量证明估算偏差过大，或产品需要纯记录群禁用长期记忆时，重新评估预检方式与触发范围。新增更多群聊平台、改变历史保留窗口或反思任务幂等语义时同样复审。

## 8. 2026-10-20 时长调整

共享闲置窗口由 4 分 30 秒缩短为 4 分钟，适用于 owner、群及群友反思，不改变各自的条数阈值、触发范围或重试策略。依据是隔离的同前缀模型复放在约 274 秒时缓存读取仍处于冷态，而紧接着的同前缀请求恢复高缓存读取；该观察只支持尽量缩短反思间隔，不足以确定 Provider 的缓存 TTL，也不保证 4 分钟一定命中。后续应以真实反思请求的 provider usage 观察缓存读取率和调度延迟。

## 9. 2026-10-25 时长调整与观察

共享闲置窗口由 4 分钟缩短为 3 分钟，适用于 owner、群及群友闲置收束。提出此变更时引用的三条低缓存 trace 均标记为 `trigger_source=threshold`，即达到条数阈值冲刷，不受闲置窗口控制；因此本次调整不应被视为对这三条低缓存的修复。目标是独立验证更短的闲置窗口是否改善真正由闲置收束触发的反思缓存表现。

本次只调整反思闲置触发窗口；固定条数与上下文压力触发保持原样，暂缓任务的 4 分钟重试延迟保持不变。预计反思更早收束会减少同一会话继续积累的时间，也可能增加小批次反思次数及模型用量。观察期按上线后 7 天统计真实 provider usage：比较 owner `idle` 反思，以及群/群友使用 `in_memory` 或 `in_memory_extended` 快照的闲置任务；记录输入 token 加权缓存率、冷请求占比、输入 token 总量和触发到请求开始的延迟。Owner `threshold` 样本作为不受本次改动影响的对照，按相同 Provider、模型和 API 格式分组。缓存数据只用于判断效果，不承诺所有请求命中。

现有 LoopScope 反思探针没有记录 `knowledge` 分支 usage；因此不能仅凭它评价知识反思的缓存率。若观察期要比较记忆与知识分支，需从已有 provider usage 观测中取得对应样本；缺少配对样本时应明确记录证据不足，不从记忆反思缓存率外推知识分支。
