# ADR-0006：QQ 工具事件不并入流式回复

> 状态：已接受
> 创建：2026-10-20
> 最近更新：2026-10-20
> 关联范围：QQ 私聊中的工具事件与增量文本回复
> 关联文档：`docs/adr/0002-qq媒体使用主动消息发送.md`

## 0. 决策摘要

| 决策主题 | 当前结论 | 主要边界 |
|---|---|---|
| QQ 工具事件 | `tool_call` 和 `tool_done` 使用独立消息，不写入回复流 | 仍按现有工具摘要格式和用户开关展示 |
| QQ 回复正文 | 保留私聊 Markdown 回复的文本流式传输 | 不把工具流式化与正文流式化视为同一能力 |

## 1. 背景与问题

QQ 长任务可能包含大量工具调用。实际使用中出现过 QQ 客户端持续显示消息生成中、回复只收到开头内容，而 Web 中同一轮回复已经完整结束的情况；运行日志也出现过 `QQStreamFinalizationError`，表示流式消息关闭未获确认。

这些现象说明 QQ 长任务的流式交付存在可靠性问题，但目前不足以证明工具事件是每次断流的唯一根因。产品决策是缩小 QQ 流式消息承载范围：工具事件不再与文本回复共用一条长生命周期流。

## 2. 目标与约束

- 降低长任务中 QQ 工具事件与回复正文共享流生命周期带来的交付风险。
- 保留用户查看工具调用进度和结果的能力。
- 保留 QQ 私聊最终文本回复的增量流式体验。
- 不改变飞书的工具卡片行为，也不在本 ADR 中改变 Telegram 的消息策略。

## 3. 候选方案

1. 将工具调用状态和结果持续追加到回复正文流：消息更集中，但会让包含许多工具调用的流保持更久，接受该方式的长任务完整性风险不符合当前需求。
2. 工具事件独立发送，回复正文继续单独流式：增加消息数量，但隔离工具事件与正文流的生命周期，采用此方案。

## 4. 决策

- QQ 的 `tool_call` 与 `tool_done` 不得作为帧写入 QQ 回复文本流。
- 启用工具交互展示时，QQ 按现有摘要格式将工具事件作为独立消息发送；不得因此改为发送不可折叠的完整 JSON。
- QQ 私聊 Markdown 回复正文继续使用现有流式发送与收尾逻辑。此决策不承诺正文流本身不会中断，也不替代对 QQ 流关闭失败的独立诊断和恢复处理。
- Web 继续镜像工具事件；该展示与 QQ 的独立消息策略互不影响。

## 5. 后果与取舍

- 工具状态不再延长 QQ 正文流的事件序列，用户仍能在独立消息中查看工具进度和结果。
- 长任务会产生更多 QQ 消息，且工具摘要与最终回复在视觉上分开。
- 正文仍可能受 QQ 流式接口、网络或客户端行为影响；该 ADR 只决定工具事件的承载方式，不把已有截断问题宣称为已彻底修复。

## 6. 依据与验证

- `backend/agent/im/loop.py` 中 `display_tool_event` 负责将工具事件镜像到 Web，并按平台策略转交 IM 展示；QQ 私聊的文本流由独立路径处理。
- `backend/agent/im/streaming/qq.py` 与 `backend/agent/gateway/qq/outbound.py` 管理 QQ 正文流的发送和收尾；关闭未获确认会报告 `QQStreamFinalizationError`。
- 依据包括 QQ 长任务中出现的用户可见截断现象及上述运行错误。该证据不能单独确定所有截断的底层原因，也不代表线上端到端验证已经完成。
- 本 ADR 记录产品边界；未修改代码，也未运行测试。

## 7. 重新评估条件

只有在 QQ 长任务覆盖多轮工具调用、正文流收尾确认和客户端展示的重复验证均稳定通过，并且用户重新提出合并工具事件的需求时，才重新评估是否将工具事件并入 QQ 流式回复。
