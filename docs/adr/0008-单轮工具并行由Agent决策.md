# ADR-0008：单轮工具并行由 Agent 决策

> 状态：已接受
> 创建：2026-10-23
> 最近更新：2026-10-23
> 关联范围：Agent 单轮工具调度、Shell 执行与工具交互确认
> 关联文档：`docs/prds/【已完成】PRD-LLM-31-单Round并行工具执行.md`

## 0. 决策摘要

| 决策主题 | 当前结论 | 主要边界 |
|---|---|---|
| 同轮多个工具调用 | 将模型在同一响应中提出的有效普通调用视为同轮执行计划，并发调度 | 受全局并行开关与每轮并发上限约束；依赖顺序由 Agent 分轮表达 |
| 服务端冲突预检 | 不通过 `mutates`、`parallel_safe` 或调用间冲突推测，擅自把普通调用整批改为串行 | 每个调用仍独立执行参数、权限、确认及工具自身安全检查 |
| 交互与确认 | 必须等待用户或动态确认的调用保留串行交互路径 | 包括用户提问、管理交互、需要确认的危险操作及当前需动态审批的 MCP 调用 |

## 1. 背景与问题

原调度策略依据工具元数据和整批资格预检决定是否并行。该策略容易把“工具可能有副作用”误当成“同一轮调用必然冲突”，导致模型已经同时提出多项任务，服务端仍将它们排成串行。尤其是多个彼此独立的 Shell 检查，即使各自可独立运行，也会被整批预检阻塞。

工具是否修改状态，并不能单独说明它与同轮其他调用是否存在依赖；反过来，服务端也无法仅靠静态元数据可靠推断模型计划中的语义依赖。若调用之间有先后关系，应由 Agent 先执行前置调用、读取结果，再在后续轮次决定下一步。

## 2. 目标与约束

- 忠实执行 Agent 在同一轮明确提出的多工具计划，减少无依据的串行等待。
- 将并发资源治理与调用间冲突推断分开：运行时可限制并发数量，但不替 Agent 猜测普通调用之间的依赖关系。
- 保留每个工具既有的输入校验、用户归属、权限、安全策略和破坏性操作确认门。
- 保留用户可控的全局串行回退开关、每轮并发上限、取消收尾及工具结果的稳定顺序。
- 不承诺并行写入具备原子性，也不承诺运行时自动检测或修复文件、数据库、进程等资源冲突。

## 3. 候选方案

1. **按整批工具元数据预检后再决定串并行**：可在调度前保守拒绝有副作用或未标记安全的批次，但无法可靠判断真实语义依赖，容易把互不相关的任务一起串行化。
2. **由 Agent 表达顺序，运行时执行同轮计划并施加明确的运行边界**：同轮有效普通调用按有界并发调度；依赖前序结果的工作由 Agent 在下一轮继续。接受调用间真实冲突由 Agent 根据结果处理的风险，并保留各工具自己的安全门。采用此方案。

## 4. 决策

- 模型在同一响应中提出的多个有效普通工具调用，表示 Agent 选择在本轮发起这些调用。并行开关开启时，运行时应将这些调用纳入有界并行调度；不得再以调用是否标记 `mutates`、`parallel_safe`，或服务端推测它们可能冲突为由，将普通调用整批改为串行。
- Agent 需要依赖某项调用的输出时，应先单独调用前置工具，读取结果后再发起依赖调用。运行时按模型声明的轮次执行，不在同轮调用之间创造模型未表达的依赖顺序。
- 并行开关关闭时，多工具调用按原有串行路径执行。并行开启时，每轮实际同时运行的数量不得超过 Admin 配置的并发上限。
- 每个调用仍独立通过工具目标解析、参数校验、权限与用户归属检查，以及工具自身既有的安全策略。破坏性操作需要的确认不得因并行而绕过；需要等待用户、动态审批或恢复交互状态的调用继续走串行交互路径。
- 无效协议调用或无法正常校验的调用可以独立返回错误，不应仅因该错误项而阻塞同轮其他有效普通调用；这些调用不得因此绕过正式 dispatch 的校验流程。
- 并发任务可以按实际完成时间发出进度，但终态、工具结果和 Provider 往返历史必须保持与模型原始调用序列一致。Run 取消时，运行时取消尚未完成的并发任务并完成清理，不得继续请求下一轮模型。
- 本决策不定义跨轮次并行，不授予跨调用共享事务，不提供自动冲突检测、补偿或回滚。部分调用成功、部分失败时，Agent 根据各项结果决定后续处理。

## 5. 后果与取舍

- 独立查询、检查及其他同轮任务可以真正重叠执行，减少不必要的累计等待。
- Agent 的规划质量成为顺序控制的重要部分；模型把有依赖的工作错误地放进同一轮时，运行时不会靠整批串行预检替它恢复语义顺序。
- 对共享文件、外部服务或其他有副作用资源的并发操作可能产生冲突；工具结果应准确呈现成功与失败，后续由 Agent 读取结果并处理。系统不将此风险描述为已解决。
- 并发上限和全局串行回退仍可控制资源压力与诊断影响；单项确认和权限检查仍是安全边界。
- 交互调用需要串行等待，但不应因此让同轮普通调用退回串行；待用户回答或动态审批的调用由交互通道处理，其他交互调用按明确回执延后至 Agent 恢复后再安排。

## 7. 重新评估条件

- 运行数据表明同轮并行造成了超出并发上限可缓解的资源争用、显著错误率上升或不可接受的数据损坏。
- 出现需要运行时强一致保障的共享资源操作，且可提出可验证的事务、锁、幂等或补偿契约；应针对该工具或资源单独设计边界，不因此恢复对所有普通工具调用的整批串行预检。
- 产品要求改变 Agent 对调用顺序的表达方式，或协议明确提供新的依赖语义。
