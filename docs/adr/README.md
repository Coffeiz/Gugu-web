# ADR 撰写规范

本目录存放已接受、会影响产品边界、信任模型、数据语义或跨模块运行方式的架构决策记录（ADR）。本文档只定义 ADR 的撰写与维护规则，不维护具体 ADR 的目录、索引或当前决策列表。新增或更新 ADR 时只修改对应 ADR 文件；新增 ADR 不需要修改本文档。

## 文件命名

使用全局递增编号和简短中文主题：

```text
NNNN-简短主题.md
```

编号按创建顺序递增，不因决策被取代或撤销而重用。主题应准确描述决策对象，不堆叠英文缩写。

## 文档头部

```markdown
# ADR-NNNN：决策主题

> 状态：已接受 | 已取代 | 已撤销 | 提案
> 创建：YYYY-MM-DD
> 最近更新：YYYY-MM-DD
> 关联范围：模块、系统边界或用户行为
> 关联文档：`path/to/doc.md`（如有）
```

状态描述决策当前效力，不描述实现进度。若决策被取代，应在头部和正文指向替代 ADR；保留原文件作为历史记录，不覆盖其历史结论。

## 章节结构

按以下顺序编号。简短决策可以合并不适用的章节，但必须清楚记录决策背景、结论、取舍和重新评估条件。

0. **决策摘要** — 用简短表格列出决策主题、当前结论和主要边界，让读者无需通读即可理解结论。
1. **背景与问题** — 描述触发决策的现状、问题和必要上下文；将事实与假设区分开。
2. **目标与约束** — 写明要解决的问题、适用范围及明确不包含的范围。
3. **候选方案** — 记录实际考虑过的方案及关键取舍。没有实质备选时可省略，不为格式虚构选项。
4. **决策** — 写明被接受的方案和可执行边界。每项规则应能据此判断后续实现是否符合决策。
5. **后果与取舍** — 同时记录收益、成本、接受的风险和对现有行为的影响。
6. **依据与验证** — 列出支持决策的代码行为、测试、实验或数据；说明证据范围和不能推出的结论。没有运行验证时明确注明。
7. **重新评估条件** — 写明哪些产品需求、威胁边界、运行数据或架构变化会触发复审。

ADR 记录决策，不是需求规格或实施计划。不得添加重复的实施 TODO、Phase 清单或维护中的任务状态；若需要实施跟踪，应引用对应 PRD/Issue。实现状态变化不应改写决策，只有决策本身变化时才更新 ADR 状态和结论。

## 语言与证据

- 使用简体中文；代码标识、协议字段和路径使用反引号。
- 区分产品决策、实现现状和验证结果，避免把实现现状误写成不可变约束。
- 数据应说明测试环境、比较对象和适用范围；不得把局部基准表述为生产承诺。
- 引用仓库文件时使用相对路径；不得写入本机或服务器的绝对路径、真实地址、用户名或凭据。
