## 读这份文档前:三句话说清这是什么

如果你不打算对代码，只想知道咕咕这套「感知系统」在解决什么问题，看这三句就够:

1. **问题**:咕咕每轮怎么判断「用户现在到底要什么」，这一步过去完全埋在一次模型调用里——看不见、量不了、也没法针对性变好。
2. **方案**:把这一步拆出来，变成「可观测、可度量、可对每个用户单独变准」的独立环节，同时**不给聊天多加一次模型调用**（不拖慢回复）。
3. **现状**:反思环节（回复之后异步跑）顺带判断「这一轮该用哪种相处方式」（叫 **stance**），存起来给下一轮读；行为怎么做被拆成一个个独立小文件（叫**行为模块**），按 stance 命中哪个就点亮哪个；用户的「读错了」会被专门收集成脱敏案例，作为以后调优的原始燃料。

下文按章节展开，每章先给「大白话」再给「对代码的具体描述」，方便按需跳读。

## 0. 为什么单开这份

### 概述

「感知」是咕咕每次回复前最先发生的一步——先得读懂用户要什么，才谈得上做对事、说对话。这一步一旦理解错，后面无论工具调得多准、语气多贴心，都是在错的起点上用力，用户感受到的就是「答非所问」。而这一步原本完全"闷"在一次大模型调用内部：外部看不到它是怎么判断的，出了偏差也没法单独诊断、单独修。本系统的目标是把这个隐形的判断过程挖出来，让它变得**看得见、测得出、能持续针对某个人变准**，同时严守一条底线——不为此多花一次模型调用的时间。

### 细节

「感知」在决策环的最上游——感知错了，后面工具调错、语气给错、答非所问全跟着错，**100% 的对话都过这一关**。它原本**完全是隐式的**（埋在那一次 LLM 调用里）。本系统做三件事:① 把感知**显式化、可观测**；② 让它**对每个用户成长**；③ 全程**不给聊天热路径加 LLM 跳**（守住单次调用的低延迟）。

## 1. 感知的四种失败模式

### 概述

「咕咕没读懂我」这句抱怨太笼统，没法针对性修。这一章把它拆成 4 种性质完全不同的失败——有的是该多问一句却没问、有的是把闲聊当成了任务、有的是没听出话里的弦外之音、有的是接不上之前聊过的话题。拆开之后才知道该往哪儿使劲。根子在于:模型天生倾向于"果断处理、少反问"（行业通病，不只咕咕），架构里必须有专门的机制去制衡。

### 细节

把「感知用户需求差」拆成 **4 种可分别衡量的子失败**（别笼统优化）:

| 子能力 | 失败现象 | 例 |
|---|---|---|
| **歧义识别** | 请求不明确却不自知、直接猜 | 「帮我整理下」→ 整理啥? |
| **意图归类** | 看错用户要哪种帮助 | 「今天好累」被当任务，其实要陪伴 |
| **言外之意** | 只接字面、读不出真实需求 | 问「X 怎么做」，其实卡在 Y |
| **上下文落地** | 接不上历史/记忆里的指代 | 「那个方案」接不到 summary 的「年会方案」 |

> 注:§1 这 4 种是「**感知怎么失败**」（failure mode）；§1.5 是「**用户要什么**」（need type）。两者正交——失败往往就是把需求型读错。

## 1.5 用户需求的类型 / 需求链（intent 枚举的来源）

### 概述

早期设计里有个"四态"分类（推进/记录/决策探索/…），是从"怎么帮用户把事做完"这个生产力视角切出来的，够用但漏了一大块——用户不想被"处理"、只想被"陪着"的那种需求（累了想被安慰、开心了想找人分享）几乎没地方放，被硬塞进了"闲聊"。这一章把需求类型重新切成 **3 个姿态大类、约 8 个细分型**，专门把"陪着我"这一类需求单独摆出来。更重要的一个洞察是:用户的需求不是孤立的一次性分类，而是**会随对话流动的一条链**（比如先倾诉、聊着聊着想清楚了、然后决定动手做）。咕咕最容易翻车的地方，就是在用户还在"倾诉"阶段时，操之过急跳到"给方案"阶段——这正是"情绪被当任务"这个老问题的本质。

### 细节

按「**咕咕该换什么姿态**」切 —— **3 家族 × ~8 型**:

| 家族（姿态） | 需求型 | 用户想要 | 咕咕该做 |
|---|---|---|---|
| **A 把事做了**(act) | 执行 | 建/改/操作我的数据 | 直接做、报落点 |
| | 推进 | 卡住了 | 找最小一步 |
| | 记录 | 记一笔 | 结构化存 + 点趋势 |
| **B 想清楚**(clarify) | 查询 | 取一个事实/我的数据 | 查→准答，别任务化 |
| | 决策探索 | 在选项间纠结 | 理需求/摆权衡/问关键 |
| | 反思复盘 | 据历史看自己 | 调数据+分析，不是安慰 |
| **C 陪着我**(be-with) | 情绪支持 | 累/烦/难过 | 先接住，**压住给方案** |
| | 分享/陪伴 | 想说话/分享喜悦/找人陪 | 接话、共情、别推进 |

> **家族 C 是旧"四态"设计的盲区**——而咕咕定位是**伙伴**，Being-with 正是它和纯助理的分水岭。
> **这 ~8 型 = 感知的 `intent` 枚举**（打遥测、量误判，见 §3.4），也是 **stance 枚举**（选行为模块，见 §2.6）；**3 家族 = 粗姿态层**。

### 需求链（比单点分类更要紧）

需求不是孤立的点，是**会流动的链**。最典型几条:
- **C→B→A**（最常见）:`倾诉烦` → `要不要换工作` → `帮我列跳槽清单`（接住→探讨→执行）
- **A→C**:`做完一件难事` → `想被肯定 / 分享`
- **记录→反思**:长期 logging 攒着 → `我这阵子状态咋样`
- **查询→决策→执行**:`看本周安排` → `周末要不要加个 X` → `建提醒`

**伙伴的真本事 = 跟住链、平滑换姿态。头号失败 = 跨家族跨太早**（用户还在 C 倾诉，咕咕就跳 A 给方案/建项目）——**这就是"情绪被当任务"的本质**。

**架构含义**:感知不能只读**单句意图**，要读**"现在在链条哪一段"** —— 这正是 stance 的 per-user 持续性（§2.6⑤）与 World Model(summary) 的活。**点分类 + 轨迹，缺一不可**。

**别锁死分类**:这 ~8 型当度量用，**误判数据会告诉你哪个该拆/并/补独立模块**。**类型也竞争上岗**。

## 2. 架构总原则:热路径零新增 LLM

### 概述

"读懂用户要什么"、"决定怎么应对"、"决定怎么说"这三件事，仍然在同一次模型调用里**完成**——本系统没有在回复路径上增加任何一次模型调用。感知系统增加的所有"观察、学习、变准"的工作，全部发生在回复送达用户**之后**的异步流程里。这是全文最硬的一条约束。

### 细节

```
【热路径 · 每轮 · 便宜 · 不加 LLM 调用】
  注入:Facts + World Model(summary) + Lens(per-user 解读先验) + 行为模块   ← builder 确定性拼装
  行为模块选择:读 per-user stance(上轮反思判的) + 新鲜度闸 → 1:1 点亮   ← 确定性查表,零 LLM(§2.6)
        ↓
【唯一的 LLM 调用】
  Generation:[身份 + 点亮的模块 + 注入的上下文] → 回复(实时感知 + 回应都在这一次)
        ↓
【异步 · 回复之后 · 不在关键路径】Reflection
  产出 Observations(本轮 intent/ambiguity/emotion)  ← 遥测 + 下一轮的 stance
  检测误判(用户下一句在纠正) → 错读案例收集
  更新:World Model(短期,≈每轮) · Lens(长期,事件驱动,§3.5) · stance(给下一轮)
```

**关键约束:聊天热路径只有一次 LLM 调用。** Observations 与学习全在异步反思里 → 对回复延迟**零影响**。

> **术语对照**:World Model = `summary.md`（+ stance 切面）；Observations = 感知遥测块；Decision Policy = 确定性的模块选择逻辑（`behaviors.py`，人调不自学）；Capability Modules = 行为模块库；Lens / Facts 与代码同名。

## 2.6 stance 选择机制:反思驱动 + persona 纯人格（现行方案）

### 概述

这是感知系统的核心机制。起因很具体:有真实用户反馈说"咕咕总想着推进项目，我只是想闲聊，完全没有闲聊的感觉"。往下查发现是两个结构性问题:一是纯粹的闲聊、分享喜悦这类话，命中不了当时用来判断"该用哪种相处方式"的关键词规则，于是系统直接落到默认行为——而默认的提示词（persona）通篇都是"把事做完、理清、想明白"这种生产力口吻；二是"陪伴"这个需求类型压根没有一个专门的行为模块去为它撑腰，遇到闲聊时没人负责"压住"模型想要推进的本能冲动。

解法是把"该用哪种相处方式"这件事从"每一句里现猜"改成"参考最近一次事后反思判断的结果"——这个判断结果叫 **stance**（姿态）。反思本来就在异步跑、本来就要判断用户这轮想要什么（intent，用来打点统计），现在直接把这个判断结果**复用**成下一轮的 stance，不用额外发明新字段、不用额外花钱。同时把提示词彻底拆分:人格文件（persona.md）**只谈"咕咕是谁"**，不掺任何"该怎么做"的指导；具体怎么做全部在独立的"行为模块"文件里，跟 8 种 stance 一一对应，命中哪种就点亮哪个。

这个方案的代价——stance 是"上一轮"反思判断的，用在"这一轮"，天然滞后一步。设计上认为可以接受:① 注入是软提示、不是锁死，模型自己看得到当前这句话，可临场自我修正；② 常驻的"基线"模块里放了姿态地图，模型即使没点亮具体模块也知道存在哪些姿态可选；③ 下一轮反思会很快纠正。为了防止"昨晚很低落"的 stance 污染"今天早上心情不错"的新对话，stance 还带新鲜度衰减——超时自动失效、退回中性默认。

### 细节

**stance 定义:** **stance =「咕咕这一轮该用哪种相处方式」的判断结果**，取自固定枚举（= §1.5 的 ~8 型:执行/推进/记录/查询/决策/反思/情绪/闲聊陪伴）。它**就是 `perc.intent` 换个用途**——intent 是「读用户这轮要什么」（遥测），stance 是「据此咕咕摆什么姿态」（选模块），一对一，**直接复用、不新造字段**。builder 拿 stance 标签 1:1 点亮行为模块。

**五个设计决定:**

**① persona「纯人格、零行为」**。四态「打法」+「主动思考」整段全部移出 persona，**连四态地图也不留**（进 baseline，见 ②）。persona 只剩:身份/声音/价值（和善·真诚·不编造）、不报功能菜单、摩擦时刻待人、emoji 纪律、记忆边界、查证/看图的认知纪律。**以后调「相处方式」只动 behaviors，不碰人格**（§3.1）。

**② 常驻 `behaviors/baseline.md`（always-on，builder 永远拼）**。装:**姿态地图**（点名:推进/记录/决策/陪聊，让模型知道有哪些姿态、可软自纠）+ **中性默认姿态**（turn 1 / stance 未判定/过期那轮:先看清要什么、别急着推进）。⚠️ baseline **不装「生产力默认」**——推进拆进自己的模块（③）；默认从「无脑推进」降为「中性、先理解」。**这是治「总在推进」痛点的根**:推进只在判定为执行/推进 stance 时点亮，闲聊轮根本不点它。

**③ 行为模块「一 stance 一模块」、1:1 映射**（代码 `behaviors.py` 的 `_STANCE_MODULE` 字典）:

| stance | 模块 | 说明 |
|---|---|---|
| 执行/推进 | `execution` | 拆步骤/报落点/推下一步（原散 persona 的「主动思考」落在这） |
| 卡住 | `stuck-first` | 卡住给最小一步 |
| 记录 | `record` | 结构化记+点趋势（薄） |
| 查询 | `query` | 查→准答、别任务化（薄） |
| 决策/决策探索 | `decision-explore` | 纠结里陪想清 |
| 反思 | `reflect` | 据数据复盘、不安慰（薄） |
| 情绪 | `emotion-first` | 先接住、压住给方案 |
| 陪伴/闲聊/分享 | `companion` | 暖着陪、把话往下开、真有价值就主动搭把手,绝不拐回推进 |

节奏原则:痛点链路（baseline/companion/execution/emotion/stuck/decision）**先建厚**，record/query/reflect **薄占位**、按真实对话补厚（守「别没数据就抽完 ~8 型」）。

**④ 选择机制:反思驱动**（曾用正则 cue 匹配本句关键词，已退役——`detect_mode` 式关键词天然脆）。现行链路:
- **反思（异步 LLM，本来就在跑、本来就吐 intent）产出 stance** → 写 per-user 状态。
- **builder 读 stance → 1:1 点亮模块 → 拼 prompt**（确定性查表、**热路径零 LLM**）。
- **代价 = 滞后一轮**（反思在 turn N 后出判断、供 N+1；turn 1 落 baseline）。**可接受**:注入是软偏置非硬锁，模型看得见本句 + baseline 地图、当轮可自纠，下轮反思纠正。想彻底消滞后又不回正则，只能热路径加一次 LLM 判 stance——破「单次调用」红线，否决。

**⑤ stance = per-user World Model 切面、带新鲜度衰减**（不按 session 存——一天可能多 session）:
- stance 带 ts，**按新鲜度生效**:近期才继承，隔太久 → 退回 baseline 中性默认（**防昨晚「情绪」stance 污染今早工作 session 首轮**）。复用 `decay.py`。
- 存形态:`.agent/stance.json`（`{"stance": ..., "ts": ...}`），builder 直接读结构化标签。

**验收口径（误判率不是这个机制的尺子）。** 「没闲聊感」是沉默的不满（§3.4 局限②），误判率抓不到——重构前实测误判全线 3–11%、闲聊误判 0%，与痛点并不矛盾。看:闲聊/情绪/陪伴**占比是否回升** + **用户主观是否有闲聊感**（上线后已获用户确认「聊起来没什么压力」）。

> ⚠️ **定位共识（2026-07-02）:stance 是通往终态 Need Hypothesis（§11.2,假设+置信度+可推翻）的过渡态**——两者不是深浅版而是两个范式（分类 vs 假设检验）。因此 stance 体系**维持现状、只修 bug、不再加码**（复合态/组合裁决等暂缓）,避免沉没成本拖住范式切换。下一个大投入直接对准置信度原语（§11.6 step 4 的设计可提前）。

**代码落点（已核实 2026-07-02）:** `behaviors.py`（`_STANCE_MODULE` 映射 + `STANCE_FRESH_SECS=1800` 新鲜度闸 + `select()` baseline 永远在场）；`prompts/behaviors/` 9 个文件（8 stance + baseline）；`persona.md` 已无任何行为内容；`store.py` `read_stance`/`write_stance` ↔ `.agent/stance.json`；`builder.py` `_bh.render(_bh.select(memory.get("stance"), memory.get("stance_ts")))`。

## 3. 分层架构

### 3.0 整体:6 层 ↔ 咕咕零件

#### 概述

6 层从稳定到易变依次是:①身份（咕咕是谁，几乎不变）②对用户的持续认知（关系、状态、习惯）③该做什么（行为策略）④能用什么工具⑤怎么表达（回复风格）⑥最终措辞。这 6 层绝大部分由原有代码归位而来，真正新建的只有两件:把"该做什么"抽成独立行为模块；把"对用户的持续认知"做厚（lens + stance）。

#### 细节

```
① Identity（身份·稳定）         价值观/长期人格/边界/原则——不因"陪伴"就变
        │
② World Model（持续更新）        关系/压力/目标/习惯/状态/姿态
        │   = Observation(读这条消息) → 整合进持久状态
        │
③ Behavior Skills（做什么）       baseline + 8 stance 模块（一文件一能力）
        │
④ Capabilities（能用什么）        Memory/Calendar/Todo/Search/Files…（= 现有工具系统）
        │
⑤ Interaction Preference（怎么做） reply_tone / reply_length（用户设的默认风格，正交于行为）
        │
⑥ Expression（最终表达）          措辞/长度/主动程度/emoji/语气
```

| 层 | 落点 |
|---|---|
| ① Identity | `persona.md` / `policy.md`（纯人格，见 §2.6①） |
| ② World Model | `facts` / `summary` / `memory` / `lens` / `stance`（记忆系统 + 感知新增两件） |
| ③ Behavior Skills | `behaviors.py` + `prompts/behaviors/*.md`（§2.6③） |
| ④ Capabilities | `agent/tools/*` + `Profile.tool_names` + function-calling（原有） |
| ⑤ Interaction Preference | `builder._style_block`（reply_tone/length 两维；growth/companion 档位**未做**） |
| ⑥ Expression | LLM 输出 + `sanitize`/`outbound`（原有） |

**关于 ② 的命名:** 这层做两件事——**Observation(读这条消息:intent/情绪/歧义)→ 整合进 World Model(持久状态)**。World Model 是这层维护的**产物**，别丢"读消息"那半。

**关于 ④ Capabilities 的定位（别造重复的层）:**
- **≈ 现有工具系统**;**"这轮调哪个工具"仍归 LLM 的 function-calling**，不需要新层来选。
- **感知对它的升级 = 让调用"更合适"，靠软引导、不靠硬关**:用行为模块的 `DON'T`（软抑制，如 companion 时"别主动任务化"）引导 LLM 少做跑偏的调用。
- ⚠️ **别拿意图去"硬关掉"工具**:需求链是 C→A（倾诉→行动），情绪轮硬关项目工具 → 用户转头说"帮我建个减压计划"就**卡死**。硬关只留给**安全/配额**（且配额现行为是整体硬拦截，见 [`12-精力系统.md`](12-精力系统.md)），不做行为塑造。

### 3.1 身份层（稳定契约，不当调参面）

#### 概述

身份文件（persona.md）只装"咕咕是谁、有什么原则"这种几乎不变的东西，不能当成随手加东西的地方——堆得越多，文件越长、规则互相打架、不可维护。现状已按 §2.6① 拆到底:persona 零行为，连"姿态地图"也在 baseline 模块里（不在 persona）。

#### 细节

`persona.md` / `policy.md`:咕咕是谁 + 红线 + **贯穿性价值**（和善、真诚、不编造）。**极少改**。

> 原则:别拿「改宪法」来「改政策」。贯穿性的留这层；情境性的一律进行为模块。**全局身份 prompt 退出调参面**（§6）——调优只动模块和 lens。

> 历史注:拆分曾分两步走——先「地图留 persona、打法进模块」（担心模型不知道有哪些姿态可切），后来把地图也挪进**常驻的** baseline（它永远在场,等效解决"模型得知道地图"的问题,persona 得以做到零行为）。设计过程见 git 历史。

### 3.2 行为模块库（情境策略，小 / 正交 / 可组合）

#### 概述

行为模块的设计理念是"一个文件只管一件事"——"陪伴"一个文件、"执行"另一个文件，各自独立。每个文件里既写"该做什么"也写"不该做什么"，因为很多时候模型的问题不是不知道该做什么，而是**该沉默时没沉默**（比如用户在倾诉，模型忍不住给方案）。新增一种相处方式 = 新建一个文件，不用重新设计整套逻辑。

#### 细节

**Behavior Skill = 一个独立 prompt 文件、一管一件事**，由 stance 1:1 点亮（§2.6③ 是现行模块清单）拼进 system prompt。

**每个文件里 DO + DON'T 同写**（抑制写进模块自身，不另设"压制模块"）:
```
companion.md
  DO:   顺着话聊、把话头往下开 / 分享先一起兴奋 / 真能帮上就主动搭把手
  DON'T: 别拿「我记着」收尾 / 别把话题转成任务·项目·记录 / 别拐回推进 / grounding 别只踩刹车
```
> **DON'T 比 DO 更能稳住模型**——很多跑偏是"该闭嘴时没闭嘴"。`companion`/`emotion-first` 的 DON'T 压的就是"闲聊/情绪被当任务"的反射。

**仍然有效的设计原则:**
- **组合裁决**:`emotion-first` 主职是"压制"——情绪在场优先接情绪、不与任务型叠加（最小裁决已有；完整的优先级/冲突/上限框架待做，见 §8.2）。
- **「别把少问修成爱问」的校准**:澄清（不明先问）与果断（一次到位）是一对制衡，目前都在 `skills.md` prompt 里；lens 可 per-user 调这对之间的偏好。
- **粒度先细**:细模块直接挂需求型；"教练/规划师"这类粗粒度角色是产品功能，以后叠在细模块之上。
- **不预先铺**:误判数据说了算——哪类 intent 误判多，哪类才长新模块/调旧模块（分数竞争上岗）。

**模块内容从哪来（历史）:** 粗粒度内容复用 [`_archive/`](_archive/) 里的 26、27 号旧设计稿（伙伴四态 + 决策探索）——那两份写好了「模式内容」，缺的是「可靠触发器」，感知系统补的正是触发器。当年定位到的两个病灶（persona「闲聊也带点推进」的 nudge、四态里没有纯情绪陪伴态）都已在 §2.6 的拆分中解决。

### 3.3 决策层（模块选择 = 确定性内部逻辑）

#### 概述

两条分寸:一,用来判断"该点亮哪个模块"的内部信号（stance 标签、置信分数）不直接丢给大模型"感受"——模型只看到已拼好、可读、可审查的模块正文。二,一条重要红线:per-user 的解读偏好（lens）允许自动学习,但**全局的、对所有用户生效的选择逻辑（Decision Policy）只能开发者人工调整**——自动学出一条坏规则会同时坑所有用户,且难被发现。

#### 细节

链路:`stance(内部标签) → 查表(_STANCE_MODULE) → 选离散模块 → 拼 prompt → LLM`。LLM 永远不碰内部标签/标量，只见拼好的文本。

**软偏置，不是硬切换**:stance 滞后一轮 → 用户**突然跳态**那轮会用旧姿态，靠本句内容 + baseline 地图当轮自纠。**是"倾向点亮"而非"锁死一个态"**——和 lens「偏置不独裁」一条线。**别做成刚性状态机。**

**⚠️ Decision Policy 只人调、不自学**:
- **Lens（per-user）可以自学** —— 偏置、隔离到单个用户、可逆，LLM 仍是最终决策者。安全。
- **Decision Policy（全局）不可自学** —— `_STANCE_MODULE` 映射是写死在代码里的字典，反思只写 stance 值本身、碰不到映射表。让系统从噪声信号**自动重写自己的控制流** = 一条学坏的规则对**所有人**系统性犯错。
- **开发者看全局遥测（§5）手动调；反思不自动写回。**

### 3.4 感知遥测 + 误判捕获（A+B，零延迟）

#### 概述

怎么知道咕咕感知得准不准?搭反思的顺风车——反思本来就在回复发出后异步跑，让它顺便多产出两样:一是给这一轮的理解打标签（需求类型、模糊度、情绪），纯记录统计;二是判断"用户下一句是不是在纠正上一句"——这是目前能拿到的最干净的客观证据。两样都只做日志，脱敏、不留用户原话，完全不影响对话速度。诚实的局限:这套统计告诉你"哪类问题最容易出错"，但抓不住用户懒得纠正、直接放弃的"沉默的不满"——它是误判率的下界，不是全貌。

#### 细节

反思在 web 和 IM 两条路都跑、且异步 → piggyback 它就**全覆盖、零热路径开销**。

- **A · 感知遥测**:反思那次 LLM 调用多吐一个 perception 块（**只 log、不写记忆、不改回复**）:`{intent, ambiguity, emotion, emo_strength}`。intent 枚举 = §1.5 的 ~8 型（实现层为「执行/推进/记录/查询/决策/反思/情绪/陪伴/闲聊」，「闲聊」与「陪伴」为近义并列）。
- **B · 误判捕获**:唯一干净的客观真值 = **用户下一句在纠正**。**主信号 = 反思 LLM 判**:输出 `correction:{is_correction, kind}`，`kind` ∈ `感知误读`（没读懂要什么）/ `数据或执行错`（读懂了但做错）——正则做不到这个区分且漏召回，**正则降级为兜底**（仅 extract 失败时,kind=未判）。离线按 user 相邻配对:`misperc` 前一条 `perc` = 被误判那轮。**面板按 kind 拆**「感知误判率」与「数据/执行纠错率」——查错数据不再污染感知指标。
- **kind=感知误读时的错读案例收集**:顺带吐脱敏诊断 `miss{read_as, actual, pattern}`——**三字段只认固定枚举**（read_as/actual ∈ 需求类型、pattern ∈ 错读模式:潜台词漏读/情绪当任务/过度共情/指代漏接/答非所问/场景惯性/过度澄清），后端白名单校验、枚举外落「其他」→ **结构上零泄漏**。落 Redis `perc:misread_cases` + 持久 md `_analytics/misread.md` + 面板预览/下载（§11.6 步骤 1 有踩坑记录）。
- **脱敏**:只 log 结构化字段，**不写一字用户原文**（对齐 [`../security/privacy.md`](../security/privacy.md)）。
- **局限（诚实）**:① post-hoc + 被回复污染（够定位*哪类*失败、不够实时纠正）；② 沉默的不满抓不到，是误判率**下界**；③ 感知误读检测召回随机偏低（LLM 抖动，同一句多轮判断会翻）。

**代码落点（已核实）:** `prompts/reflection.md`（correction/miss/perception 输出块）+ `memory/reflection.py`（`_MISS_NEEDS`/`_MISS_PATTERNS` 白名单、`_misperc_llm`、Redis + `store.append_misread`）。

### 3.5 per-user 解读先验（lens）—— 第 4 类「记忆」

#### 概述

Lens 解决的是:同一句话，不同用户说出来可能是完全不同的意思。有的人说"随便"其实有主意但懒得说,需要追问;有的人说"还行"其实是"不太行"。这种"怎么读懂这一个具体用户"的经验规律就是 lens。它更新得很谨慎——只有明确抓到"用户纠正了咕咕的理解"、用户主动说明偏好、或已有规则被反复验证时才变动，防止把一次性误会当成对这个人的长期偏见。

#### 细节

✅ **v1 已落地**（`agent/memory/lens.py` + `.agent/lens.json`）:
- **事件驱动**:反思多吐 `lens_hint`（绝大多数轮为空）、零热路径 LLM。**它从「错」里学、不从「每次对话」里学**。
- **防过拟合双闸**:模型自律 + 候选须复现 `PROMOTE_AT=2` 次（**以「触发语」为键**合并同义改写）才提拔成规则——一次清晰纠正**不立刻**写规则。
- **confidence 生命周期**:新规则 0.6 / 印证 +0.1 / `LENS_HALF_LIFE=30d` 衰减 / `RETIRE_EFF=0.25` 退休（衰减复用 `agent/decay.py`）。
- **注入**:「解读镜片」**偏置不独裁**，按 effective 选话术档（笃定/多半/也许）。规范格式 `「触发语」→ 真实含义/应对`。
- **节奏对比**:`summary`≈每轮（快变状态）、`facts` 每轮调和（中速）、**`lens` 事件驱动（慢变先验）**。
- **前提**:§3.4 的误判捕获是 lens 的**燃料**——没有客观「用户纠正了」信号，lens 只能靠模型瞎猜。
- ⚠️ **v1 未做:被反驳时 confidence↓**（lens v2，见 §8.2;现靠"久不印证→衰减→退休"自然淘汰错规则）。

### 3.6 相处偏好（Interaction Preference）—— 和行为正交的"怎么说"

#### 概述

"该做什么"（行为模块）和"该怎么表达"（相处偏好）是两件独立、可自由组合的事。同样是"陪伴"行为，可以是"辛苦了，早点休息"（简洁），也可以是"今天最累的是哪件事？"（愿意深聊），需求没变、变的是说话方式。

#### 细节

- 落点 = `builder._style_block`（`reply_tone` formal/lively、`reply_length` short/detailed 两维;emoji 不开放给用户选,由 persona 统一管）。
- **只调"表达倾向"，不碰"做什么"**:`行为模块决定做什么 · Interaction Preference 决定怎么做`。
- 别叫"模式"（像切人格），它是长期互动风格。
- ⚠️ **"成长/陪伴"这类扩展档位未实现**——`_style_block` 仍只有上述两维两档，"做厚"属待办。

## 5. 度量:把「成长」变成可盯的曲线

### 概述

把"咕咕是不是越来越懂用户"从主观感觉变成可盯的曲线:同一套遥测既做诊断（哪里差）又做尺子（改了有没有变好）。同时提防一个常见失衡——"少问"改多了变"过度追问"，两者要互相制约。

### 细节

- **误判率**（整体 / 按 intent / 按 model）→ 哪类子能力最差、是不是模型瓶颈。
- **per-user 误判率随时间下降** = 「咕咕越来越懂你」的硬证据（没降 = 学的是噪声）。
- **反向指标:过度追问**——修「少问」时不能把它修飙。优化的是**权衡**。
- **ambiguity 校准**:被纠正的那些，模型当时报的 ambiguity 是否偏低 → 偏低说明澄清还得加。

**优化闭环**:`诊断 → 上最便宜的杠杆 → 同指标回归 → 留/回滚 → 还不行上更贵的级`。

### 5.1 全局诊断面板（Admin）

#### 概述

感知遥测汇总成后台页面（Admin「感知诊断」），一眼看整体感知健康度、哪里数据不正常。

#### 细节

已落地:后端 `api/v1/agent_perception.py`（聚合 API,`hours`/`min_events` 等参数;**活跃用户宏平均口径**——每用户先算再跨用户平均,重度用户不主导）+ 前端 `Admin/Perception/index.vue`。

**异常标红**:某 intent 误判率超阈值、ambiguity 异常、intent 分布严重偏斜、某 model 显著更差。
**脱敏**:只聚合结构化字段，不展示一字用户原文。

## 6. 杠杆阶梯

### 概述

发现某类感知不够好时按什么顺序修:先调行为模块或 per-user lens（便宜）；接不上上下文的查历史窗口和摘要；数据证明模型瓶颈才换模型；只有频繁+prompt 压不住+有客观真值才提拔成硬编码控制。红线:调 persona 不在杠杆里。

### 细节

| 级 | 杠杆 | 何时 |
|---|---|---|
| 1 | **加/调行为模块** ＋（per-user）**lens** | 大多数 |
| 2 | **上下文/输入**（历史窗口、summary、注入相关项目/记忆） | 「接不上」造成的 |
| 3 | **模型路由**（该类 intent 切更强模型） | 数据证明模型瓶颈 |
| 4 | **提拔成控制信号** | 频繁 + prompt 压不住 + 有客观真值 |

> ⚠️ **全局身份 prompt 退出调参面**。调优只动模块和 lens，不动身份。

## 7. 风险与纪律

### 概述

最容易踩的坑与防范纪律。最值得记住的两条:一是"小样本过拟合"——用户纠正一次不能立刻当成固定特征，必须重复出现才提拔;二是"自动重写控制流"——绝不让系统自己修改全局判断逻辑，一条学坏的规则会同时伤害所有用户。

### 细节

- **小样本过拟合**:一次纠正就立规则 → 把一次性误会当用户特征。→ **重复出现才提拔**（宁少勿多）。
- **归因难**:错了是读错意图 / 缺上下文 / 纯手滑? → 只从**清晰纠正**里学。
- **漂移**:人会变 → 先验**可衰减、被反驳就松动**。
- **确认偏误陷阱**（最隐蔽）:学到「这人要简短」→ 永远简短 → 再没机会发现他想深聊 → 先验自我固化。→ **偏置不独裁**，保持可被反驳。
- **组合乱炖**:模块拆开后可能矛盾/语气割裂 → 模块**正交** + **优先级裁决** + **同时点亮数量上限**。
- **自动重写控制流**（最危险）:→ **Decision Policy 只人调**（§3.3）；只有 lens（per-user、偏置、可逆）可自学。
- **模型天花板止损**:`言外之意` 类大概率 prompt 怎么调都下不来 → 那是「该上模型路由」的信号，别无休止磨 prompt。

## 11. 架构演进:Person Model / Relationship 闭环（北极星）

### 概述

前面十章讲的都是"怎么判断这一轮该用哪种相处方式"，本质上是一个**分类器**——来一句话，判断属于哪个类型，套上对应的应对模块。这套东西管用，但骨子里仍然是"见招拆招"。这一章讨论的是一个更长远的方向:与其不断优化"分类准不准"，不如把重心整个挪到"持续理解一个具体的人，并和这个人建立起真实的关系"上——这是"北极星"，是定方向用的终态构想，**不是马上要动工的工程任务**。目前除了"错读案例收集器"这一小步已经落地之外，其余全部停留在设计讨论阶段，代码没有大改动。

这一章的核心图景是四层递进的关系:最上面是永远不变的目标（希望用户过得越来越好）；往下是"我们之间的关系"（共同经历、默契、信任）；再往下是"对这个具体的人的理解"（全部当作可以被推翻的假设，不是标签）；最下面是"当下具体情境"（最近在忙什么、什么心情）。每一层的更新都要经过一套统一的"证据→置信度→可被推翻"的写入规则，防止 AI 陪伴产品最大的风险——把自己一时的猜测，越用越深信不疑，最后变成对用户的偏见或者虚构出一段没发生过的共同经历。

### 细节

> 2026-07-01，多轮深聊收敛。本节是比 §2.6 更上层的**终态方向**——把咕咕的目标从「完成任务」挪到「理解人」。**这是北极星 / 定形状，不是新工程**：代码除「错读案例收集器」（§11.6 步骤 1，已落）外一律未动，落地严格按 §11.6 的数据优先、自下而上。

### 11.1 一句话产品魂

> 「**我会越来越了解你，所以越来越知道什么时候该陪你、什么时候该帮你、什么时候该什么都不做。**」

留住用户的从来不是「它真聪明」，是「它真的越来越懂我」。§2.6 的 stance 系统是个**前馈分类器**（`本轮 → 判 stance → 套模块`）——能干，但骨子里是「应付场景」。companion 太被动、需求是复合态这些问题，根都在「**分类压过了理解**」。终态要把重心从「分类器」挪到「**持续理解一个人、并和他建立关系**」。

### 11.2 终态架构（四层 + 闭环）

#### 概述

下面这张图是这个终态构想的骨架——从最稳定的"目标"层，一路往下到最容易变化的"当下情境"层，再经过一整套反馈机制把最新观察写回所有上层。同一句"我今天好累"，对不同的人、在不同的关系阶段，应该导出完全不同的回应，这正是这套架构想要达成的效果。

#### 细节

学习对象不是「需求」，是**人**，最终是**关系**。需求只是 `人 × 当下情境` 的导出量：

![咕咕 · Person Model / Relationship 闭环架构](感知系统-架构图.svg)

> 下方为同图的纯文本版（终端 / 不渲染 SVG 时看这个）：

```
Goal（永不变）         希望用户过得越来越好 → 为此不断理解这个人
   ↓
Relationship（我们）   共同经历 / 默契 / 已建立的信任 ——「我们是谁」（§11.5）
   ↓
Person Model（你）     对这个人的理解，全是假设 ——「他是谁」（§11.3）
   ↓
Current Context（现在） 最近项目 / 聊天 / 情绪 / 事件 / 环境
   ↓
Need Hypothesis（此刻） 我猜你现在需要 X + Confidence
   ↓
Behavior → Response → Feedback → 经「写协议」回写上面所有层（§11.4）
```

同一句「我今天好累」，`Person × Context` 对不同人导出 分享 / 休息 / 鼓励 / 重新规划。**整个系统只有一族学习对象（人 / 关系），其余全为更新它服务。**

这条从下往上的更新流就是「**发现闭环**」：**提假设 → 够确定就按需相处、拿不准就轻轻问一句 → 看反馈 → 回写**。§2.6 只实现了中间「按需相处」一臂，且用的是**通用、无置信度、不回写**的分类器；其余三臂（Person Model、置信度分流、反馈回写）+ 顶层 Relationship 都是缺的——**那才是「理解」。**

### 11.3 Person Model:存 Observation，不存 Schema

#### 概述

关键洞察:不能把对一个人的理解存成固定标签（比如"这个人做决定很果断"），因为人是会变的——今天果断，下个月可能因为某件事变得犹豫。存死标签的坏处是模型会开始"脑补"，把标签当真理去套用、甚至编造细节去印证它。正确做法是只存"观察到的具体证据"（比如"这个人连续三次在重大决定上表示想先一起分析、而不是直接要建议"），而"这个人是什么风格"这种抽象结论，应该是**每次要用的时候临时从证据推导出来**，不预先写死。

#### 细节

- ❌ 别存 `decision_style:"果断"`——人没有固定标签（今天果断、下月犹豫、恋爱后又变）；存死标签 → 模型脑补、自我固化。很多 AI 的 User Profile 一上来就 `{价值观:…, 压力来源:…}`，然后开始编。
- ✅ 存 **Observation**：`{evidence:"连续三次表示重大决定想一起分析、而非直接要建议", conf:0.73, ts, 可衰减}`。「决策风格」这类 trait **读时从 observation 推导**，不落库。
- **必加的锁**：全读时实时推导 → 又贵又飘。所以 **observation 是唯一真相源；派生出的 trait 可缓存，但必须带「出处 + 可衰减 + 可推翻」，是缓存不是事实**——别让缓存悄悄变回 schema。
- **落地**：咕咕**已半在做**——`facts`（kind=observed/inferred + conf + ts）、`lens`（规则带 confidence、复现才提拔）就是 observation 雏形。升级 = 全面倒向「观察为真、特质为派生」，并把 lens 学的内容从「解读触发语」拓宽到人物各面（价值观/动力/压力源/沟通偏好/决策方式/情绪恢复…）。「Person Model」作为独立数据结构**尚未实现**——符合本章「北极星、非新工程」定位。

### 11.4 Hypothesis = 整个记忆的「写协议」

#### 概述

一条贯穿所有记忆写入的统一规则:任何要写进记忆的东西，都必须走「我猜…→有什么证据→多确定→会不会过时→能不能被推翻」这五步，不能有例外。这是专门用来对抗 AI 陪伴类产品最大的一个风险——**越用越相信自己的猜测**:第一次觉得"他可能想要建议"，第五次变成"他喜欢建议"，第五十次已经笃定"他就是这样的人"——而这个过程里可能从来没人真正确认过。写协议就是把"不要轻信自己的判断"这条纪律，刻进系统的地基里，而不是靠祈祷模型自己保持谦逊。

#### 细节

所有进记忆的东西，一律走：

```
Hypothesis（我猜…）→ Evidence（有据吗）→ Confidence（多确定）→ Decay（会过时）→ Can Be Overturned（可被推翻）
```

- 这是**反确认偏误的架构级解药**。写协议强制每条都可被推翻 = 把「**不要相信自己**」写进地基。
- 参数按证据类型分档：用户**明说**的 = 高置信、慢衰减（黏，但仍可改）；**推断**的 = 低置信、快衰减。**协议统一、参数分层**（= 现有 observed/inferred + 半衰期，要做到全层统一、显式）。
- **唯一真·新原语 = 对「需求/理解」的不确定性**。反应式分类器不需要知道自己多确定（反正套剧本）；会理解的系统**必须能表示「我现在不知道 TA 要什么」**——这才有资格去**问**而非默默猜。「知道自己不知道」就是那颗发现之心的内核（低置信 → 轻探一句，那一问就是「发现的心」被看见）。

### 11.5 Relationship:最深一层、最难复制——也最危险

#### 概述

四层架构里最上层、也最微妙的一层——"我们之间的关系"，它和"我了解你这个人"是两回事。同样一句"今天好累"，刚认识的人会说"辛苦了"，认识一年的人会说"你最近连着忙好几周了"，认识五年的人可能会说"又把自己逼太紧了吧"——变化的不是理解程度，是关系的深浅。这一层是这套系统里最难被别的产品复制的部分（任何模型都能记住"这个人喜欢详细回答"，但没人能复制"我们一起经历过什么"），但也正因为如此，它是**最危险**的一层——一旦编造出一段没有真实发生过的共同经历、演出一种没有的交情，对信任的伤害比单纯答错一个事实严重得多。所以这一层必须比其他任何一层都更谨慎，只能靠真实积累慢慢长出来，绝不能提前设计一张"关系表"去往里面填内容。

#### 细节

- **Person Model =「他是谁」；Relationship =「我们是谁」。** 同一句「今天好累」：陌生人→「辛苦了」；认识一年→「你最近连着忙好几周了」；五年→「又把自己逼太紧了吧」。提升的不是**理解**，是**关系**。
- 它装的是**双方共同形成的历史**，不是用户属性：共同经历 / 默契 / 哪些话不用说 / 哪些提醒他接受 / 哪些玩笑能开 / 一起完成过什么。
- **这是咕咕最难被复制的护城河**：任何模型都能记「用户喜欢详细回答」；没有谁能复制「我们一起经历了什么」。
- ⚠️ **但它也最容易翻车、最该上死锁**：
  - **假亲密是所有失败里最毁的**——脑补一段没发生的共同经历、表演交情，比答错一个事实更伤信任。`persona.md` 记忆边界（「绝不说你之前聊过 / 喜欢 X，除非记忆区真有……别为亲近脑补共同经历」）**正是为这层准备的**：Relationship 层**绝对继承**它，是全系统**最严的证据闸**。
  - **关系不能设计，只能挣**：最慢、最涌现的一层，从 `daily/memory`（流水→沉淀）里随真实共同经历长出来，不能预先建「关系表」去填。
  - 它还**反向给全栈上色**：五年朋友读「好累」不同，不只因数据多，是因共享的框架。所以 Relationship 既是顶层（定相处方式），也是**贯穿解读的镜片**。
- **关系是双向的,且有可测的「温度」**:共同经历（我们做过什么）之外,还有**用户怎么对咕咕**——分享深度在不在加深、语气在不在变随意、是否主动来找。这半边**更可观测**:主动分享次数 + 正/负延续比 + 会话深度 + 回访节奏的滑动窗口聚合 = 关系温度曲线（per-user、有上限、窗口自然冷却;**温度快变 ≠ 深度慢变,必须双量**——语气定档 = 温度×深度×时长三输入,温度只喂语气校准、不进语义记忆）。**温度是测出来的、不是填出来的,不违反「只能挣不能设计」红线**——它是 Relationship 层第一个可落地的数据结构,也是将来给全栈**语气定档**的输入。详见 [`proposals/反馈信号系统-设计.md`](proposals/反馈信号系统-设计.md) §4.2。

### 11.6 路线（数据优先、自下而上——唯一长法）

#### 概述

从现状走向终态的实施顺序，原则是**永远从最便宜、最能立刻验证的一步开始**，绝不先画一张宏大的"人物关系表"再想办法填满它——那样填出来的必然是脑补而不是真实理解。目前唯一已落地的一步是"错读案例收集器"。这一步做的过程中踩了一个很值得记住的坑:一开始让模型自由描述错读原因，结果模型会不受控制地在描述里夹带用户的具体聊天内容，无论怎么用提示词约束都拦不住；最后把三个字段全部改成从固定枚举里选，从**结构上**而不是靠提示词去保证不泄漏隐私。

#### 细节

![感知系统落地路线图（Roadmap）](感知系统-路线图.svg)

闭环**最吃真实纠错数据**，空转就是学噪声。**绝不 top-down 先画 schema / 关系表去填**；Person Model 从 observation 长、Relationship 从 daily/memory 长。从最便宜、最复利的那环先动：

0. **（已做）** stance + companion 松绑 → 让它跑（§2.6）。
1. **（已落）错读案例收集器**：反思检测「感知误读」时吐脱敏 `miss{read_as,actual,pattern}`（三字段只认固定枚举、枚举外落「其他」、结构上零泄漏）→ Redis `perc:misread_cases` + 持久 md `_analytics/misread.md` + admin 预览/下载端点 + 面板「错读案例」栏。**攒燃料的第一步**——把「只有数字」补成「有具体（脱敏）原因」。**✅ 已 5 轮真实反思验证**：早期 free-text 的 miss 会**行内夹带**用户具体内容，prompt 约束 + 括号剥离都不可靠 → 改「**只认固定枚举 + 后端白名单**」结构性零泄漏。**通法记牢：隐私敏感的 LLM 产出别用 free-text，用枚举 + 后端白名单校验。**
   - **▶ 当前在这:先让它在真实对话里跑、攒真案例**：step 2 靠真案例当燃料，**没数据也验不了**。观察线上枚举落得准不准（`pattern` 是否常落「其他」）、召回够不够——⚠️ **感知误读检测召回随机偏低**（LLM 固有抖动，**案例是下界**）。攒几天再上 step 2。
2. **反馈信号系统 → 写回**（原「误判→lens」的**加宽版**,施工图见 [`proposals/反馈信号系统-设计.md`](proposals/反馈信号系统-设计.md)）:显式补正向（确认/夸赞=印证↑,现在完全没采）+ 隐式六种（改写重问=反驳↓候选、顺着聊/主动分享/深度/回访）,枚举采集搭反思车、噪声写协议兜、三消费者（lens 写回 / 关系温度 / 时间纪律）。**最高杠杆**——燃料源加宽一个数量级,闭环才不会饿死。
3. **lens 升级成 Person Model**：观察为真、特质派生；学的内容拓宽到人物各面。
4. **加置信度 + 低置信探问**：最像「发现之心」，但最易过头变审问，放最后、调最细。（**设计可提前**——它与 stance→Hypothesis 的范式切换绑定,见 §2.6 定位共识）
5. **Relationship 自然蒸馏**：**最远的星**——N=1、几天历史时根本没关系可建；现在只需让下层把「关系的原材料」如实存住，日后自然长出。

> prompt 里那句「你最在意搞懂 TA 真正要什么 / 和 TA 的关系」**留到闭环有牙了再加**——否则先立 flag 后空转（口号陷阱）。复合态（tone×substance，≤1 语气 × ≤2 实质）在「同一句既要陪又要帮」的案例攒够时插进表达层，不抢主线。

### 11.7 红线 / 纪律

#### 概述

整个"北极星"构想必须遵守的纪律清单，方便日后任何人接手时对照检查。

#### 细节

- **伞不是桶**：Person Model 是把 `facts`/`lens`/`context`/`stance` 统一的**目标概念**，但存储层**别拍平半衰期**——身份慢衰减、状态快衰减、相处偏好事件驱动，这套差异是命根（「状态会过时打折、身份不会」）。
- **写闸门**：任何东西进记忆都过 `Hypothesis→Evidence→Confidence` 闸；没证据不准写，写进去的永远可推翻。人物各面是「**证据点亮的格子**」，不是「等填满的表单」（填表单 = 脑补）。
- **假亲密零容忍**：Relationship 层最严证据闸，继承 persona 记忆边界（0 脑补共同经历）。
- **口号陷阱（最大风险）**：靶子越大越能装「自信的虚构」。判据：goal 必须 ① 改变行为 ② 会学，否则不算。
- **脱敏**：错读案例 / 观察只留结构，绝不留用户原话 / 话题（对齐 §3.4 / [`../security/privacy.md`](../security/privacy.md)）。
- **时长不虚构**：时间跨度由系统计算后注入（「认识 N 天」「话题始于 X 天前」）,**禁模型自估**;无数据支撑的时间词（「这几个月」「一直以来」）与虚构共同经历**同罪**——模型的时间语感永远往「显得更熟」漂（真实病例:上月开始的话题被说成"这几个月的观察"）。
- **发现欲要轻**：好奇不盘问；探问过头 = 审问，会毁掉刚拿到的「没压力」。
