# 飞书机器人接入指南（从零到跑通）

> ⚠️ **架构已重写（2026-07 前后）**：早期版本是"管理员在飞书后台手动建一个共享应用，所有用户 OAuth 扫码绑定到同一个 bot"；现在改成了 **BYO（每个用户自己扫码创建并拥有一个飞书机器人）**，不再有 Admin 共享频道面板、不再有独立的 OAuth 绑定步骤（bot 归属即用户归属，天然不用绑）。本次改写已对照 `agent/adapters/feishu.py`、`app/api/v1/feishu_connect.py`、`agent/adapters/supervisor.py`、`app/models/UserBot`、`views`/`ProfileModal.vue` 逐一核实。旧版依赖的 `app/api/v1/feishu_event.py`（Webhook 事件入口）、`app/api/v1/feishu_bind.py`（OAuth 绑定）、`agent_admin.py` 的频道 CRUD **均已被删除**，本文不再收录，如需查历史做法翻 git 记录。
> 架构与决策见 [`20-IM接入架构.md`](20-IM接入架构.md)、[`00-总览.md`](00-总览.md) Phase 4。

## 易读概述

咕咕支持"住进"飞书：用户在飞书里私聊一个机器人，就能像在网页上一样跟咕咕对话、让它管项目/文件/日程。

现在的接入方式很轻——**用户自己在咕咕的"个人设置"里点一下"接入咕咕 → 飞书"，手机飞书扫个码，飞书那边会自动帮你创建一个专属机器人并完成授权，扫完就直接能用了**，不需要用户去飞书开发者后台手动创建应用、配权限、发布版本。这背后是飞书官方提供的"设备授权流程"（一种和登录扫码类似的授权机制），咕咕的后端替用户跑完这套流程,把生成的机器人凭据存起来。

因为机器人是"每个用户自己的"（术语叫 BYO，Bring Your Own），所以消息一进来天然知道是哪个用户发的，不需要再额外做一层"飞书账号绑定咕咕账号"的手续——这也是相比更早期"大家共用一个机器人、还要各自 OAuth 绑定"方案的简化。

对于要读懂或维护这块代码的人，下面"专业细节"部分给了完整的组件清单、启动方式和排错表；对纯粹想知道"接入飞书大致要经过哪几步"的人，记住这句就够：**用户扫码 → 飞书自动建机器人并把凭据交给咕咕 → 咕咕后台自动为这个机器人起一条常驻连接 → 私聊机器人就能跟咕咕对话。**

## 专业细节

### 0. 前置

- 后端能正常起（`backend/`，`.venv`，从 `backend/` 目录跑以加载 `.env`）
- Redis 可达（`settings.redis`，扫码授权任务的临时状态存在 Redis）
- 一个飞书账号（用来扫码；不需要企业管理员权限、不需要预先在开发者后台建应用——这步已被扫码自动化取代，见 §1）

---

### 1. 用户侧：扫码自动创建机器人

用户在咕咕「个人设置 → 咕咕设置 → 接入咕咕」页面选「飞书」→ 点击后前端渲染出二维码 → 用户拿手机飞书扫码、在授权页确认。

整个过程走的是飞书 `accounts.feishu.cn` 的 **OAuth 2.0 设备授权流程（Device Authorization Flow，RFC 8628）**，全程不需要开发者资质或预先注册应用，参考了 QwenPaw 的做法、实测可用。分四步（代码 `app/api/v1/feishu_connect.py`）：

```
1. POST accounts.feishu.cn/oauth/v1/app/registration action=init
     → 返回 supported_auth_methods（确认支持 client_secret 方式）
2. POST … action=begin (archetype=PersonalAgent, auth_method=client_secret, request_user_info=open_id)
     → 返回 device_code + verification_uri_complete（即扫码授权页地址）
3. 前端把 verification_uri_complete 拼上 source=Gugu 参数，渲染成二维码
4. 用户手机飞书扫码 → 在授权页确认 → 飞书为其创建一个 PersonalAgent 类型应用
5. 前端轮询 GET /me/feishu/connect/{poll_id}（后端内部再轮询飞书 action=poll {device_code}）
     → 拿到 client_id / client_secret（即 App ID / App Secret）
     → 后端写入该用户的 UserBot 记录（platform=feishu），并发布 im:supervisor:reload 通知 supervisor 去接这个新机器人
```

几个实现细节：
- `device_code` 只存服务端 Redis（按 `poll_id` 存取，TTL 1 小时），不下发给前端，防止泄漏。
- 轮询等待中飞书按标准协议返回 `400 {"error":"authorization_pending"}`，这个响应不能当异常抛出，要正常继续等。
- 若用户拒绝授权（`access_denied`）或 device_code 过期（`expired_token`/`invalid_grant`），接口分别返回 `status: fail` / `status: expired`，前端据此提示重新扫码。
- 授权时若拿到用户的 `open_id`，会顺便存一份"可触达地址"（`scheduled_tasks.save_imreach`），使咕咕能在用户还没主动私聊过机器人的情况下也可以主动推送消息（如定时任务提醒）。
- 国内飞书的接口域名是 `accounts.feishu.cn`；国际版 Lark 是 `accounts.larksuite.com`（如需支持得再加 domain 判断，当前未做，标注**待核实**是否已有计划支持）。

> 这一步产出的凭据（App ID/App Secret）就是该用户专属机器人的身份，直接对应用户，**不需要再额外做绑定**——这点和早期方案的本质区别。

### 2. 凭据存哪：`user_bots` 表

- 表结构：`app/models/__init__.py` 的 `UserBot`，字段 `user_id / platform / name / app_id / app_secret / sandbox / enabled`。
- 一个用户可以有多个 bot（不同平台各一条，理论上同平台也可以有多条，代码按 `(user_id, platform, app_id)` 做 upsert 防重复）。
- 用户在设置页可以看到自己名下的机器人列表、启停、删除（`GET /me/bots` 等，`app/api/v1/user_bots.py`）。
- **不再有 Admin 后台的共享频道配置面板**——早期文档里的「Admin → Agent 配置 → 频道 tab」已经不存在，`agent_admin.py` 里这段职责已被显式注释掉并说明改为走 `/me/bots`、`/me/feishu/connect`、`/me/qq/connect`。

### 3. 跑两个进程（管家 + worker）

和早期方案一样，仍然需要两个常驻进程，但**管家现在读的是数据库 `user_bots` 表，不是配置文件**：

都从 `backend/` 目录、用 `.venv`：

```bash
# 频道管家：轮询 user_bots 里 enabled=true 的记录，为每条起一个网关子进程（增删启停约 5s 内生效）
.venv/bin/python -m agent.adapters.supervisor

# worker：消费队列 → 跑咕咕大脑 → 发回飞书
.venv/bin/python -m worker
```

后台跑法示例：
```bash
.venv/bin/python -m agent.adapters.supervisor > /tmp/gugu_sv.log     2>&1 &
.venv/bin/python -m worker                    > /tmp/gugu_worker.log 2>&1 &
```

**连上的标志**（管家日志 `/tmp/gugu_sv.log`）：
```
[supervisor] ▶ 启动 feishu:<bot_id>
[feishu:<bot_id>] 网关启动（owner=<user_id>），WebSocket 长连接中…
[Lark] ... connected to wss://msg-frontier.feishu.cn/ws/v2 ...
```

> 单个机器人的凭据由 supervisor 通过**环境变量**（`FEISHU_BOT_ID` / `FEISHU_APP_ID` / `FEISHU_APP_SECRET` / `FEISHU_OWNER`）注入子进程，不走命令行参数，避免 `ps` 命令泄漏密钥。子进程是 `agent/adapters/feishu.py` 的 `serve()`，调试单个机器人也可以直接手动跑这个模块并手动设好上述环境变量，但正式环境一律用 supervisor（支持多用户多机器人 + 动态起停 + 崩溃退避重启）。

### 3.5 管家原理

> 详见 `00-总览.md` Phase 4「频道面板与动态网关」。此前的"配置文件驱动"描述已过时，以下按当前代码（`agent/adapters/supervisor.py`）重写。

**为什么要管家**：lark `ws.Client` 只有 `start()`、**没有 `stop()`**——单个连接在进程内断不掉。所以用**进程级管理**：

```
用户扫码 / 在设置里启停删除自己的机器人
   → 写/改 user_bots 表（enabled 字段）
   → supervisor 每 5s 轮询 DB 里 enabled=true 的 user_bots（_fetch_userbots）
   → reconcile：新增/启用 → spawn 网关子进程；停用/删除 → kill 子进程；崩溃 → 按退避策略自动重启
```

- **一个机器人 = 一个子进程**：`python -m agent.adapters.feishu`（凭据由环境变量注入，非命令行参数），kill = 断开。
- **多机器人并存**：可同时挂任意多个用户各自的飞书机器人，消息 payload 带 `owner_user_id`（BYO 模型下机器人收到的消息天然归属其 owner，worker 无需再查绑定表）。
- **崩溃退避**：进程存活不足 5 秒判定为「秒崩」（多半是凭据错误等必现问题），按指数退避（10s 起、封顶 5 分钟）重试，避免用错凭据的机器人反复疯狂重启拖垮进程；跑了一阵子才挂的（多半网络抖动）立即重启不退避。
- **面板改即生效**：约 5s 内连接起/停，不用手动重启 supervisor 本身。

### 3.6 关于 Webhook 模式

早期文档里的「模式 B：请求地址 (Webhook)」——即通过公网回调地址 `POST /api/v1/feishu/event/<频道id>` 接收事件——**对应的代码 `app/api/v1/feishu_event.py` 已不存在**，`app/main.py` 目前只注册了 `feishu_connect_router`（扫码连接），没有 Webhook 事件路由。现在收消息**只走 WebSocket 长连接**（§3 的管家 + 网关子进程），不再支持也不需要公网回调收消息。

> 如果之后确有必要重新支持 Webhook 模式（比如未来要做无需常驻进程的部署），需要重新实现事件入口，当前代码库里没有可用的这部分逻辑——**待核实**是否已有相关计划。

### 4. 测试

飞书里**私聊你自己刚创建的那个机器人**发一句（如「你是谁」）。预期：

- 网关日志：`[feishu:<bot_id>] 收到 <open_id> @ <chat_id> (text): text='你是谁' att=0 trace=<trace_id>`
- worker 日志能看到处理与回复过程
- 飞书里收到咕咕的回复

整条链：`飞书消息 → 网关(WSS) → Redis队列(im:inbound) → worker → run_collect(人格+记忆+工具) → feishu.send_text 发回`。

网关收到消息后还会做两个轻量的"秒回"动作（不经过大模型，纯关键词判断，零网络开销）：给消息加一个表情回应（如"在看"👀、"哈哈"😄），并可能在任务进行中时对"还在吗/算了"这类短语直接短路处理，不占大模型的一轮。

### 5. 排错

| 现象 | 原因 / 解法 |
|------|------------|
| 网关连不上 / 报鉴权错 | 该用户的 App ID/Secret 有问题，多半是扫码授权没走完整或飞书那边把 PersonalAgent 应用撤销了，需要用户重新走一遍扫码流程（§1） |
| 收不到消息 | 检查该机器人在 `user_bots` 表里 `enabled` 是否为真；看 supervisor 是否已经为它 spawn 了子进程 |
| 收到但回不出 | 看网关/发送侧日志的 `code`/`msg`，多半是 lark SDK 报的具体错误；确认该机器人凭据仍然有效 |
| worker 反复 `TimeoutError: Timeout reading from ...:6379` | redis 阻塞读 `XREADGROUP block` 时读超时太短。已修：`app/core/redis.py` 的 `get_redis` 设 `socket_timeout=None` |
| 同一个机器人跑出两条连接冲突 | 别对同一个用户的机器人凭据同时手动跑 `feishu` 网关又跑 supervisor；也别拿这套凭据同时接到 OpenClaw 等其它网关 |
| 用户扫码后设置页显示的机器人没连上 | 等约 5s（管家轮询周期）；看管家日志 `/tmp/gugu_sv.log` 有没有 `▶ 启动 feishu:<bot_id>`；确认该记录 `enabled=true` |
| 扫码卡在等待 / 一直 `waiting` | 用户还没在手机上完成飞书那边的授权确认；device_code 过期（超过 1 小时）需要重新发起 |

---

### 6. 为什么不再需要单独的"用户绑定"步骤

早期方案是"所有用户共用一个飞书应用"，所以必须再做一层 OAuth 绑定，把"飞书里的这个人（open_id）"和"咕咕账号（user_id）"对应起来。

现在每个用户扫码创建的是**自己独有**的机器人（`UserBot.user_id` 直接记录归属），机器人收到的每条消息天然就是"发给这个用户自己的机器人"，所以入队时直接带上 `owner_user_id`，worker 不需要再查一张绑定表去反解身份。这也是 BYO 模型相比"共享 bot + 绑定表"更简单的地方——少了一个可能出错的中间环节。

> 唯一还依赖"公网可达"的场景，是扫码授权页把飞书导回咕咕前端的重定向（标准 OAuth 重定向，属于飞书 `accounts.feishu.cn` 授权流程本身，不是咕咕自己另开的回调端口）；收消息的 WebSocket 长连接依然不需要公网。
