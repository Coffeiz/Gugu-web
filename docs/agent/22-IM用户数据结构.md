# IM 用户数据结构

> 本文记录咕咕在 IM 平台上的身份、Bot、会话、群组成员和权限数据结构。它是 QQ 群聊权限、C2C 按钮绑定和群聊记忆的基础设计；当前未实现的部分会明确标记。群组/member 记忆的实际文件与异步执行细节以 PRD-IM-3 为准。
> 相关：[[20-IM接入架构.md]]、[[21-群聊消息架构.md]]、[[../product/PRD/PRD-IM-1-im接入稳定性与qq自建websocket.md]]、[[../product/PRD/PRD-IM-3-群组与成员记忆.md]]。

## 易读概述

咕咕需要区分三种对象：

1. **Gugu 用户**：登录咕咕网页的账户，拥有项目、文件和记忆。
2. **平台身份**：某个平台上的具体用户，例如 QQ 的 `user_openid`、飞书的 `open_id`。
3. **IM 会话**：Bot 所在的私聊、群聊或频道，例如 QQ 的 `group_openid`。

当前 `UserBot.user_id` 解决的是“哪个 Gugu 用户拥有这个 Bot”，还没有解决“群里发言的 QQ 用户是谁、是否是 Bot 所有者”。两者不能混成一张表。

`users.id` 是咕咕账号自身的全局用户 ID，可跨该账号绑定的多个 Bot 和平台复用。QQ 的 `user_openid/member_openid` 不是全局用户 ID，只在对应 Bot/App 作用域内参与身份绑定；本方案不做跨 Bot 的 QQ 身份自动合并。

## 专业细节

### 1. 身份层级

| 对象 | 示例 | 作用域 |
|---|---|---|
| Gugu 用户 | `users.id` | 咕咕系统 |
| Bot 应用 | `UserBot.app_id` | 平台应用 |
| 平台用户身份 | QQ `user_openid` | 通常受 Bot/App 作用域限制 |
| 平台会话 | QQ `group_openid` | 某个群 |

QQ 消息字段对应关系：

```text
C2C_MESSAGE_CREATE.author.user_openid  -> platform_user_id
GROUP_* .author.member_openid          -> platform_user_id
GROUP_* .group_openid                  -> platform_chat_id
```

`platform_user_id` 是咕咕内部的通用字段；QQ 的 `user_openid` 是平台原始值。不要把 `group_openid` 写入用户身份字段。

### 1.1 平台身份 ID 与显示名

IM 消息同时保留两类字段，但职责不能混用：

| 字段 | 用途 | 是否参与身份判断 |
|---|---|---|
| `platform_user_id` | QQ 的 `user_openid/member_openid` 等稳定平台身份 | 是，权限、会话归属和“是否同一人”比较只使用它 |
| `platform_user_name` | QQ `author.username`/可用昵称，作为当前发言人的显示名 | 否，只用于自然称呼；不能用于绑定、权限或身份合并 |

QQ raw event 当前可以提供 `author.username`。网关将它作为显示元数据传入 Agent，并与消息一起保存；显示名缺失或变化不影响身份识别。群名仍不从正文或昵称猜测，若平台 API 没有提供就不填。

特别注意：同一个 Bot 下不同 QQ 号可能共享同一个 `owner_user_id`（因为 Bot 属于同一个 Gugu 账号），但只要 `platform_user_id` 不同，就必须视为不同平台发言人；不能因为 Gugu 账号相同、群会话相同或历史称呼相同而合并。

2026-08-03 在 devserver 实测：主号的群聊 `member_openid` 与私聊 `user_openid` 指纹一致（`e1592494`），小号群聊指纹不同（`e44e746c`），说明 QQ 已正确区分两个发言人；两类消息的 `owner_user_id` 指纹却相同，因为当前 BYO 网关把 Bot 所属的 Gugu 用户直接写入 payload。结论是：`platform_user_id` 能区分发言人，但当前 worker 仍会优先按 `owner_user_id` 解析，尚未完成群成员与 Bot owner 的权限隔离。`union_openid` 在本次样本中为空，不能作为当前实现的依赖。

### 2. 目标数据结构

#### 2.1 `platform_identities`

记录“哪个平台身份对应哪个 Gugu 用户”：

```text
id                         主键
gugu_user_id               users.id
platform                   qq / feishu / wechat
platform_user_id           平台用户 ID；QQ 为 user_openid/member_openid
scope_type                 bot / app / tenant
scope_key                  UserBot.id、app_id 或平台租户标识
status                     pending / active / revoked
verified_at                验证完成时间
verified_by                c2c / group_code / keyboard / admin
created_at / updated_at    UTC 时间
```

推荐唯一约束：`(platform, scope_type, scope_key, platform_user_id)`。QQ 的 `user_openid` 不应被假设为跨 Bot、跨应用全局唯一。

#### 2.2 `im_chats`

记录 Bot 所连接的会话：

```text
id                         主键
bot_id                     UserBot.id
platform                   平台
platform_chat_id           QQ group_openid / 飞书 chat_id
chat_type                  c2c / group / channel
display_name               可选展示名
enabled                    是否启用
group_requires_at          是否要求 @ 后才回复
group_read_enabled         是否记录未 @ 的普通群消息
tool_policy                群聊工具白名单配置
created_at / updated_at    UTC 时间
```

同一个 Bot 可以拥有多个 `im_chats`。群聊配置必须按会话保存，不能只挂在 `UserBot` 上。

#### 2.3 `im_chat_members`

记录平台身份在某个会话中的成员状态；owner 不在这里重复绑定，而是由 Bot 的全局所有者身份推导：

```text
id                         主键
chat_id                    im_chats.id
identity_id                platform_identities.id，可为空
platform_user_id           收到消息时的原始身份快照
role                       member / unknown
permissions                JSON 或独立权限表
first_seen_at / last_seen_at
```

`identity_id` 用于绑定后的稳定权限判断；`platform_user_id` 用于处理尚未完成绑定的群成员和审计。

#### 2.4 IM 记忆作用域

群组和 platform user 使用独立的轻量记忆，完整设计、实际文件格式和实施计划见 [`PRD-IM-3-群组与成员记忆.md`](../product/PRD/PRD-IM-3-群组与成员记忆.md)。本文只固定数据结构边界：

```python
MemoryScope(
    owner_user_id="...",
    platform="qq",
    bot_id="...",
    scope_type="platform-user",  # or group
    scope_id="...",
)
```

作用域必须包含 `owner_user_id + platform + bot_id + scope_type + scope_id`。逻辑文件格式为：

```text
.agent/im/{platform}/{bot_id}/
├── groups/{group_id}/profile.json, summary.json, daily.md, memory.md
└── platform-users/{platform_user_id}/profile.json, pattern.json, summary.json
```

群组 summary 是当前状态快照，daily 是近期流水，memory 是压缩后的稳定知识；平台用户只保留轻量 profile、pattern、summary。成员记忆不能跨群合并，群内公开信息不能反向写入 owner memory。

### 3. 当前实现与目标的差距

当前已实现：

- `UserBot.user_id` 记录 Bot 所属的 Gugu 用户。
- QQ 适配器读取 C2C 的 `author.user_openid`。
- QQ 群消息读取 `member_openid`，并通过 `platform_user_id` 传入 Agent Loop。
- 群聊开关目前主要保存在 `UserBot` 上。
- 当前 Bot owner 的身份比较、member/unknown 降权和工具白名单已在 IM Loop、runner 与 dispatch 层接入。

当前仍未实现或不在本阶段范围内：

- 持久化 `platform_identities`、`im_chats`、`im_chat_members`。
- 持久化 `owner_platform_user_id` 或等价绑定关系。
- 按群覆盖工具白名单和成员状态。

群组/member 记忆的作用域、反思、压缩和删除屏障已按 PRD-IM-3 实现，不使用 owner memory namespace；真实多平台人工验收仍以 PRD-IM-3 的清单为准。

在这些表落地前，不能把消息 payload 中的 `platform_user_id` 当成永久绑定身份，也不能仅凭 `UserBot.user_id` 判断群内发言者拥有 Gugu 内容的 CUD 权限。

### 4. QQ 身份绑定

QQ 身份绑定不依赖群消息、验证码或 `@咕咕`。网页用户需要确认 QQ 身份时，咕咕直接向已知的候选 `user_openid` 发送一条 C2C 确认消息，用户点击按钮后完成平台身份绑定；owner 身份是 Bot 级别的全局关系，不在每个群重新绑定：

```text
网页发起“绑定 QQ 身份”请求，生成一次性 pending action
  ↓ QQ 通过候选 user_openid 发送 C2C“确认 / 取消”按钮
  ↓ 用户点击按钮，QQ 回传 interaction event
  ↓ 校验 Bot、咕咕用户、pending action 和点击者 user_openid
  ↓ 确认后写入 platform_identities，建立该 Bot 的 owner 绑定
```

按钮数据只放不可猜测的一次性 pending action ID，不放 Gugu 用户 ID、QQ 身份或密钥。pending action 必须绑定网页用户、Bot 和候选 `platform_user_id`，并在成功、取消或过期后失效。按钮回调必须再次校验点击者的 `user_openid`，不能因为按钮被转发就允许其他成员确认。

这条流程发生在 C2C 通道，不要求用户先在群里发消息，也不要求用户 `@咕咕`。它只负责建立平台身份，不改变任何群开关；在确认按钮回调完成前，不进入 Agent Loop、不读取群上下文、不开放任何工具。

如果数据库里完全没有该用户的 QQ `user_openid`，机器人无法凭空发现或主动发送 C2C 消息。此情况应在网页上明确提示“需要先完成一次 QQ 身份绑定”，另行走平台允许的身份采集流程；不能把群内普通消息或 `@咕咕` 当作本次绑定流程的隐式前提。

### 4.1 身份认证策略

#### 4.1.1 QQ 身份获取策略

QQ 身份按用户生命周期分三种情况获取：

1. **新用户接入 QQ：直接获取**
   - 新用户完成 QQ 接入或首次与 Bot 建立 C2C 会话时，立即读取并持久化 `user_openid`。
   - 这一步只建立平台身份与咕咕用户的关联，不自动开启群聊，也不自动授予群 owner 权限。

2. **老用户再次聊天：自动补采集**
   - 老用户发送 C2C 消息，或在群里产生可读取的消息时，从 payload 中读取 `user_openid/member_openid`。
   - 当前 QQ Bot 实测：同一个账号的 C2C `user_openid` 与群聊 `member_openid` 一致，不同账号的群聊 `member_openid` 不同；服务端应将它们按 Bot 作用域幂等 upsert 到 `platform_identities`，但不能因为 `UserBot.user_id` 相同就把不同发言人当成 owner。

3. **老用户没有聊天：Keyboard 确认**
   - 网页用户需要绑定 QQ 身份时，如果数据库已有候选 `user_openid`，后端直接发送 C2C“确认 / 取消”Keyboard。
   - 用户点击“确认”后，完成 `platform_identities` 绑定，成为该 Bot 的 owner；点击“取消”或超时则不建立绑定。
   - 这一步是确认 `platform_user_id` 属于哪个咕咕用户，不是开启某个群，也不是通过 Keyboard 反向发现未知 QQ 身份。

如果老用户既没有历史 C2C/群消息记录，数据库也没有 `user_openid`，后端就没有 C2C 消息的发送目标，不能直接发送 Keyboard。此时必须先走平台允许的身份采集流程，不能假设能通过群消息或 `@咕咕` 完成发现。

#### 4.1.2 从身份到权限

身份认证分为四个阶段，不能把它们合并成“收到 QQ ID 就拥有权限”：

1. **身份采集**：从 QQ C2C 的 `user_openid` 或群消息的 `member_openid` 建立 `platform_identities`，只证明“这个平台身份被观察到”。
2. **用户关联**：将已知 QQ 身份关联到咕咕网页用户，但仍不代表它拥有某个群的管理权限。
3. **Bot 作用域所有者认证**：咕咕账号的 `users.id` 是全局身份，但每个 Bot 都要单独确认一个 QQ 平台身份作为 owner。同一个已绑定 `platform_id` 在该 Bot 接入的所有群中都拥有完整 CUD 权限，不需要逐群认证；其他平台身份即使通过同一个 Bot 发言，也不能继承 `UserBot.user_id` 的 owner 权限。多个 Bot 不自动合并 QQ 身份。
4. **会话授权**：每次群消息进入 Agent Loop 前，根据 `chat_id`、`platform_user_id` 和 `im_chat_member` 解析 `owner`、`member` 或 `unknown`，再决定工具和数据范围。

认证时必须同时校验：

- pending action 尚未过期、取消或使用过；
- Bot、发起的网页用户和 pending action 一致；
- 按钮点击者的 QQ `user_openid` 与初始绑定身份一致；
- 同一 Bot 下的身份绑定关系尚未被其他有效 action 覆盖。

`platform_identities` 是跨群、但不跨 Bot 的身份关系：同一个 QQ 用户的 `user_openid/member_openid` 在当前 Bot 作用域内统一为一个 `platform_user_id`。该 Bot 的 owner 必须由 `UserBot.user_id` 与已确认的平台身份关联确定，不能仅凭 payload 中的 `owner_user_id` 推导。`im_chat_members` 记录其他群成员的 `member` / `unknown` 状态和审计信息；群内其他成员即使已经被采集到 `member_openid`，也不能执行该用户的内容 CUD。

### 5. 权限、消息与记忆

权限判断顺序：`平台和 Bot → im_chat → platform_user_id → platform_identity → im_chat_member → role/permissions → 工具和数据范围`。

默认策略：`owner` 允许 CUD；`member` 允许聊天，CUD 禁止；`unknown` 默认禁止 CUD 和用户内容搜索。当前实现通过 `user_bots.group_allowed_tools` 配置群成员白名单，默认只开放 `web_search`；`group_context_search` 开启后只查询当前群 `chat_id` 的短期消息。权限必须在 runner 工具集和工具 dispatch 前都执行，不能只依赖提示词限制模型。

消息表应引用 `chat_id` 和 `identity_id`，短期上下文只拼接当前群最近消息，不混入其他群。当前产品决策是每个群保留最近 50 条原始群消息；群组和 platform user 的轻量记忆已使用独立 namespace、异步反思和删除屏障实现，具体执行状态见 PRD-IM-3。

### 6. 实施顺序

权限实施按以下顺序推进，前一步完成并验证后再进入下一步：

#### Phase 5：身份采集与 Bot owner 绑定（🔲 未做）

1. **身份采集**：持久化 QQ C2C 的 `user_openid` 和群消息的 `member_openid`，只记录身份，不改变权限。
2. **用户关联与 Bot owner 确认**：每个 Gugu 账号只绑定一个 Bot；新用户首次 C2C 消息可作为候选 owner 身份，老用户通过 C2C Keyboard 确认后写入 `platform_identities` 或 `user_bots.owner_platform_user_id`。群消息不能自动抢占 owner，不同 Bot 不做跨 Bot 自动识别。

#### Phase 6：群成员权限隔离与工具白名单（✅ 已完成）

#### 2.3 WebChat 与 IM 身份隔离

`users.id` 是 Gugu 账号自身的身份；`platform_user_id` 是某个 IM 平台上的当前发言人身份。两者不是同一个概念，不能互相替代。

| 会话来源 | 使用的身份 | 是否注入平台身份上下文 |
|---|---|---|
| WebChat | `users.id`、`user_name` | 否 |
| QQ / 飞书 / 微信私聊 | `users.id` + 当前平台用户身份 | 是 |
| QQ / 飞书 / 微信群聊 | `users.id` + 当前平台用户身份 + `chat_type` + `chat_id` + `im_role` | 是，仅限当前 IM 会话 |

约束：

- WebChat 不设置、不读取 `platform_user_id`、`chat_type` 和 `im_role`。
- IM 才保存并使用 `platform_user_id`、`chat_type`；群聊身份比较只在当前 Bot 作用域内进行。
- Agent 不能把 Gugu 用户名当成 QQ 昵称，也不能根据语气或历史印象猜测平台身份。
- 平台身份上下文只用于内部核对、会话隔离和权限判断，不主动向用户展示原始平台 ID。
- `platform_user_name` 只用于当前发言人的自然称呼，不参与绑定、权限判断或“是否同一个人”的比较。
- 同一个 Bot 下不同 QQ 号即使共享 `owner_user_id`，只要 `platform_user_id` 不同，就必须视为不同平台发言人。
- WebChat 与 IM 使用不同的身份语义，即使属于同一个 Gugu 账号，也不能用 WebChat 的历史内容推断 QQ 发言人身份。
- QQ raw WebSocket 当前可从 `author.username` 获取发言人显示名，并映射为 `platform_user_name`；该字段随消息保存，仅用于称呼。群名不从正文或昵称猜测，查询不到时不填。

#### 当前已知边界：群聊共享会话与用户资料隔离

群聊短期上下文按 `chat_id=group_openid` 共享，这是为了让咕咕理解群内连续对话；但 Bot 的 `owner_user_id` 是 Gugu 账号归属，不等于当前 QQ 发言人身份。当前实现已经用 `platform_user_id` 做 owner/member 权限判断，也会把当前 username 注入称呼上下文；非 owner 的 owner profile、记忆、项目和文件读取已在 Loop/context loader 边界阻止，长期 group/member 记忆则由独立 scope 管理。

1. **权限解析器 ✅**：按当前 Bot 的 `owner_platform_user_id` 与消息 `platform_user_id` 比较，得到 `owner`、`member` 或 `unknown`，不做跨 Bot 身份合并。
2. **权限规则 ✅**：`owner` 使用完整工具集；`member` 和 `unknown` 仍可聊天，但只能使用白名单工具。runner 与 dispatch 双层校验，不能只依赖提示词。
3. **工具白名单 ✅**：默认只开放 `web_search`，可在个人设置中按 Bot 切换；`group_context_search` 可选且只查询当前群，其余用户内容和 CUD 工具保持 owner-only。
4. **群级配置暂不纳入本阶段**：当前所有群共用该 Bot 的 owner 和工具白名单，不为每个群重复绑定 owner。若未来需要群聊开关、成员状态或群级工具策略，再单独增加 `im_chats` / `im_chat_members`。

#### Phase 7：群聊记忆隔离与压缩（🟡 代码完成，待人工验收）

1. **记忆隔离**：消息和短期上下文按 `chat_id` 隔离，保持每群最近 50 条原始消息上限。
2. **平台用户记忆**：按 `platform + bot_id + platform_user_id` 保存轻量 `profile`、`pattern` 和 `summary`，不保存 owner 同等规模的 daily/完整事件记忆。
3. **群组记忆**：按 `platform + bot_id + group_id` 保存 `profile`、`daily` 和 `memory`，分别包括群资料、近期群聊和压缩后的稳定群知识。群 profile 使用 `name/nature/rule/role/project/preference/note` 类型，只记录公开稳定事实。
4. **复用组件**：调用现有 memory 的提取、压缩和检索组件，但使用独立 namespace、权限策略和异步 reflection。
5. **隐私治理**：补充成员记忆的可见范围、删除、过期、群解散清理和跨群不合并测试。

当前已完成：`MemoryScope` 隔离、group/member 专用 prompt、异步 `memory:reflection` worker、1 小时活跃窗口、15 分钟空闲收束（worker 每 30 秒扫描）、group daily 压缩、tombstone 删除屏障，以及不泄露 scope 标识的 Admin 整体预览和批量维护入口。仍需在 devserver 验证真实多平台消息、压缩失败补偿和删除后重建 scope。

每一步都要兼容当前 `UserBot.user_id` 的 Bot 所属关系，不把 Bot 所有权迁移成平台用户身份。

平台用户 profile 的固定格式：`profile.json` 保存 `[ {"type": "...", "text": "..."} ]`，`type` 取 `name`、`address`、`pronoun`、`background`、`preference`、`note`；不保存机器 `id`、时间戳或置信度。owner 的 profile 使用同样的类型集合，但保存 `{type,text,ts}`，其中 `ts` 仅用于审计。旧格式会按 `note` 兼容，并在下一次写回时规范化。
