# 咕咕 提示词优化指南

> 怎么写、怎么改咕咕的提示词。综合 OpenAI 两篇官方指南里**真正适用于「长期陪伴 agent + 弱模型混用」**这个场景的原则，加上咕咕的现状评估与可执行清单。改提示词前先读这份。

---

## 易读概述

咕咕的"人设"和"行为准则"不是写死在代码里的固定台词，而是几份 Markdown 提示词文件（人格、工具使用准则、内容红线等），每一轮对话咕咕开口之前都会重新拼一遍交给大模型。这份文档讲的是**怎么写这些提示词才管用**。

背后有个不轻松的现实：咕咕同时要在好几个不同强弱的大模型上跑（贵的强模型、便宜的弱模型都要能用），而弱模型对提示词的"服从度"会打折扣——你说得越绕、越依赖它自己判断，它越容易漏做或做错。所以这份指南不是空谈写作技巧，而是围绕两个问题展开：**怎么把话说清楚让模型真听懂**，以及**弱模型和强模型该分别怎么伺候**。

指南参考了 OpenAI 官方的两篇提示词工程材料，取了其中真正适用于"长期陪伴、多步骤、工具调用"这类场景的部分，同时对照咕咕现有提示词做了一遍评估——哪些已经做对了、哪些还能再改进、哪些是刻意不改的（比如为了不削弱红线的显著性）。文档还记录了一次内容复核：原以为提示词里有不少重复啰嗦的地方，逐条核对后发现大多数"重复"其实是从不同角度讲同一件事，删了反而会丢意思，所以最后没有大动。

## 专业细节

### 0. 适用范围与一句话原则

- **管什么**：`backend/agent/prompts/`（`persona.md` 人格、`skills.md` 常驻工具行为协议、`policy.md` 红线/对外口径、`reflection.md` 记忆提炼、`default.md` 数据模板、`compress*.md`）；以及 `backend/agent/skills/*.md`（`use_skill` 渐进式披露的技能正文，见 §3.1）。
- **不管**：模型选择、temperature、API 参数——那些在 `llm_select.py` / `config`，不在这份。
- **一句话**：**说清「要到哪、什么算到了、什么时候停」，而不是堆「绝不做什么」**。红线该硬的硬，但别让绝对令淹没判断力。

### 2. 适用原则（筛过的，按重要性）

#### 2.1 结构：人格 / 目标 / 完成判据 / 约束 / 输出 / 停止条件
GPT-5.x 指南推荐的系统提示骨架：

```
Role（1-2 句）→ Personality（语气 + 协作风格）→ Goal（用户可见的产出）
→ Success criteria（什么算做完）→ Constraints（红线/安全/证据）
→ Output（分段/长度/语气）→ Stop rules（何时重试/兜底/收手）
```

咕咕已有 Role/Personality（persona）、Constraints（policy）、任务准则（skills），**缺 Success criteria 和 Stop rules**——见 §4。

#### 2.2 outcome-first，少用绝对令
- 描述**目的地**，让模型自己选路径，别一步步规定流程。
- **避免 ALWAYS / NEVER（绝不/必须/铁律）——除非真的不可变**。绝对令过密会压掉模型的判断力。
- 例：把「绝不长篇大论」→「默认 2-4 句话说清，复杂事才展开」（给了可执行的度，而非一刀切禁令）。

#### 2.3 人格与任务分离，且都要短
- **人格**（语气、温度、直接程度）和**协作风格**（何时发问、多主动）分开写、各自简短。
- 咕咕已分（persona vs skills）✅，但 persona 偏长，可精简（§4）。

#### 2.4 完成判据 + 停止条件（agent 关键，咕咕最缺）
- 给**显式停止条件**：「每拿到一个结果就问——现在能不能用足够证据回答用户的核心诉求了？能就收尾。」
- **完成契约**：把任务当作「未完成」直到所有要求项都覆盖、或显式标记 `[卡住]`；心里存一份交付清单。
- 没有这些，多步任务只能靠 `MAX_ROUNDS` 硬截，容易早停或空转。

#### 2.5 检索预算（搜索别没完）
- **先做一次宽搜**；只有在「结果不够 / 关键事实缺失 / 要求穷尽 / 要某份具体文档」时才再搜。
- **别为措辞优化反复搜**。空结果先试 1-2 个兜底策略，再如实说「没查到」。

#### 2.6 证据与引用：只引本轮检索到的
- 具体事实（产品/人物/价格/数据/赛果）只用检索到或上下文给的，**绝不编**。
- 这条咕咕已有（policy 的「不虚构联网信息 + 交叉验证」），保持。

#### 2.7 删水词、长度给确切值
- 「简短点、别太多」→「2-4 句」；「分几段」→「最多 3 段」。
- 默认正文用**平实段落**，对比/清单/用户要才上 bullet。

#### 2.8 正面表述优先（第一篇 #7）
- 「不要做 X」尽量补「改为做 Y」。咕咕 policy 已有大量 `❌… → ✅…`（很好），但 persona/skills 里很多裸「别/绝不」可补正面替代。

### 3. 咕咕提示词现状速览

拼装顺序（`agent/context/builder.py`，`\n\n---\n\n` 分隔）：

```
persona（人格）→ 本轮行为模块（stance，见感知系统文档）→ 解读镜片（per-user lens）
→ skills（工具使用准则）→ policy（红线/对外口径）→ 风格偏好 → 技能索引
┃ 记忆块（summary→facts→memory→daily）→ 当前来源/渠道 → default（实时数据：今天/项目/日历/文件）
```
（┃ 为 prompt 缓存断点，见 [[24-LLM支持与适配.md]] §3；上面拼装顺序已对照 `builder.py` 逐段核实，比早期版本多了「行为模块」「解读镜片」两段，来自相处方式系统，见 [[gugu-companion-system]]）

| 文件 | 行数 | 角色 |
|---|---|---|
| `persona.md` | ~29 | 咕咕是谁、能做什么、记忆边界、风格、摩擦处理、表情红线 |
| `skills.md` | ~50 | 常驻工具行为协议 + 少量高优先级路由例外；技能目录由注册表生成 |
| `policy.md` | ~52 | 内容红线、对外口径（不报工具名/不泄身份） |
| `reflection.md` | ~69 | 记忆提炼（facts/daily/summary，JSON 输出） |
| `default.md` | ~15 | 实时数据模板（占位符） |

行数按当前代码核实（早期版本记录的 persona ~43 行 / skills ~75 行已随迭代变化，改动较大，下方 §4 的具体行号引用已相应失效，仅保留结论性描述）。

#### 3.1 `skills.md` 与 `agent/skills/*.md` 的关系（渐进式披露）

咕咕有两层"技能"概念，容易混：

- **`agent/prompts/skills.md`**：**常驻**提示词的一部分，每轮都会注入完整正文。内容是通用的「工具使用准则」（先判断要不要动手、检索预算、真实性铁律、不可逆操作两步确认等）。
- **`agent/skills/*.md`**（当前由注册表自动扫描）：**按需**加载的技能正文，每轮只把注册 metadata 的短描述索引注入 system prompt，模型判断命中后主动调 `use_skill` 工具才把正文拉进上下文——这是渐进式披露（progressive disclosure），避免所有技能细节常驻占 token。加载逻辑见 `agent/skills/__init__.py`。

**这两层怎么衔接**：`builder._skills_index_block()` 从注册表生成技能名称和短描述；命中后由模型调用 `use_skill` 延迟加载正文。因此新增 Skill 不再需要同步修改 `skills.md`。`skills.md` 只保留所有场景都必须遵守的工具行为协议，以及图片识别等少数不能依赖普通索引显著性的高优先级例外。

这样可以避免短描述、主动指针、Skill 索引三处重复描述同一能力；具体工具步骤和场景规则归对应 Skill 正文，注册 metadata 只负责目录发现与关联校验。

### 4. 现状评估（对照 §2）

#### ✅ 已经做得好的（别动）
- **人格 / 任务分离**（persona vs skills）——符合 2.3。
- **指令在前、数据在后、`---` 分隔**——符合第一篇 #2、2.1 结构感。
- **`❌… → ✅…` 示例**（policy 里对外口径一节）——符合 2.8、第一篇「show, not tell」。
- **不虚构事实 + 交叉验证**（policy「不虚构联网/实时信息」）——符合 2.6。
- **不可逆操作两步确认、需求不明先问 vs 事实去查**（skills 对应段落）——符合 default follow-through。
- **真实性铁律「没真调工具就别说做了」**（skills「真实性铁律」段）——这是「完成判据」的雏形，保留。

> 注：早期版本此处按行号引用（如「skills 11-14、54-57」），但 `skills.md` 迭代后行号已不对应，故改为按段落标题引用，更耐版本变动。

#### ⚠️ 可优化的（按优先级）

| # | 问题 | 位置 | 对应原则 |
|---|---|---|---|
| 1 | **缺「完成判据 / 停止条件」**——只有「怎么做」没有「何时算完、可以停」 | skills 整体 | 2.4 |
| 2 | **缺「检索预算」**——有工具选择，没「搜几次、何时停」 | skills「工具该用就用」段 | 2.5 |
| 3 | **「绝不/铁律/禁止」密度过高**——非红线的偏好也用绝对令 | persona/skills/policy | 2.2 / 2.8 |
| 4 | ~~同一规则跨文件重复~~ **经复核多为互补侧面、非纯重复**（见下），不宜激进去重 | 多处 | 已复核 |
| 5 | **persona 偏长**，摩擦处理那段很细 | persona「摩擦时刻」段 | 2.3 |
| 6 | 个别长度用模糊词（「别长篇大论」） | persona「风格」段 | 2.7 |

**#4「跨文件重复」复核结论（2026-06-28 逐字核对后修正）**：原以为是冗余，核完发现**多数是互补的不同侧面，删了会丢语义**，故**不做激进去重**：
- 「联网相关」三处各讲一件事：persona「不确定就去查证」= 不确定就**去查证**（态度）/ policy「不虚构联网信息」= **不虚构**搜索外结果（红线）/ skills「工具该用就用」= **事实去查 vs 需求要问**（工具选择）——保留。
- 「不编共同历史」：persona「关于记忆」段（带「两类不确定」区分）+ policy「不虚构与用户的共同历史」（红线本体）——有重叠但 persona 那段有独有价值，保留。
- 「别假装调工具」「别报工具名」：属 token 级红线、是 mimo 的兜底，**靠重复提显著性**，保留（见 §5）。
- 「没建成定时任务别承诺」：skills 的泛未来任务 + 日历提醒是**两类场景的平行规则**，非重复，保留。
- 结论：**真正能安全删的「水词」很少**；勿为「去重」牺牲语义或 mimo 显著性。

### 5. 弱模型（mimo）专项 ⚠️ 最重要的取舍

咕咕模型池含 **mimo**（弱模型，对 prompt 遵从打折）。GPT-5.x 指南的 small-model 专章直接适用：

**指南的小模型原则：**
- 关键规则放最前；给**完整执行顺序** + 决策规则 + **一个正确流程示例**（不只给输出格式）。
- **把「做动作」和「报告结果」明确分开**。
- **显式定义「遇到模糊怎么办」**。
- **窄、边界清晰的任务**才交小模型；**模糊 / 多步 / 规划类路由到更强模型**。

**对咕咕的两条结论：**
1. **重复不是纯浪费**——对 mimo，关键红线多处重复 = 提高显著性。所以 §4 #4 的「去重」**不能一把梭**：
   - **高层语义红线**（联网不虚构、不编历史）：强模型听得住 → 可收敛到一处权威表述，别处一句话指引（省 token）。
   - **token 级习惯红线**（别假装调工具、别报工具名、emoji）：弱模型靠重复兜 + 输出层 strip 兜底 → **保留重复**，只压缩明显啰嗦的行文（删水词不删红线）。
2. **路由**：现在是「带媒体强切 mimo」；建议**反向**也加「多步规划 / 模糊澄清类避开 mimo、走强模型」——这正是指南说的「把模糊/多步路由到更强模型」，也印证你们「mimo 不适合可靠多步工具 agent」的既有结论。

> 红线本质分两类，决定了能不能用 prompt 治：**① 高层语义**（prompt 可治，强模型尤其听）；**② 低层 token 习惯**（prompt 软、弱模型打折，最终靠输出层兜底）。改任何红线前先判断它属于哪类。

### 6. 优化清单（可执行，按性价比）

**第一档（纯增量、不动红线、对 mimo 安全）—— ✅ 已落地（2026-06-28）：**
1. ✅ **「完成判据 + 停止条件」**（skills.md）：每步自检「核心诉求答得上了吗？答得上就收尾」；多步任务列内部清单，全勾或标 `[卡住]` 才算完。
2. ✅ **「检索预算」**（skills.md）：先一次宽搜；只在结果不够/缺关键事实/要穷尽时再搜；别为措辞反复搜；空了先换搜法再说没查到。

**第二档（涉及红线/风格取舍）—— 复核后大多不做：**
3. ✅ **长度给确切值**（persona.md）：「不长篇大论」→「默认 2-4 句、复杂才展开」。已落地。
4. ⏸️ **绝对令软化** —— **暂不做**：大多是真红线或已配正面例（❌→✅），安全空间小。
5. ⏸️ **高层语义红线去重** —— **不做**：见 §4 复核，多为互补、非冗余。
6. ⏸️ **persona 摩擦处理精简** —— **不做**：那段带 ❌→✅ 具体例，正是指南推荐给小模型的「示范正确流程」，删了伤 mimo。

**先别碰（确认保留）：** token 级红线的重复（别假装调工具、别报工具名、emoji）——mimo 的兜底，去了掉可靠性。

### 8. 改提示词的操作守则

- **热更新**：`prompts/*.md` 和 `agent/skills/*.md` 由 `builder.build` / `agent/skills/__init__.py` **每轮现读**（`read_text`），改完**无需重启**、下一轮生效（开发/生产都是）。代码侧改了 builder 逻辑，开发可用 `make dev-worker` 自动重载，生产才需重启对应进程（见 [deploy.md](../ops/deploy.md) §6.1）。
- **改前先判类**：这条是 §5 的「高层语义」还是「token 习惯」红线？强模型听 vs 弱模型打折，决定改 prompt 还是改输出层。
- **小步验证**：改完用「网页 + 一个 IM + 一次定时任务」三路各测一遍（口径共用，别只测网页）；弱模型问题尤其要在 mimo 路实测。
- **别让风格块盖红线**：风格偏好块（语气/长度）注入在 policy 之后——确认它不会软化掉前面的红线（既有踩坑：风格块盖过抽象红线）。
- **改 reflection.md 注意**：它的输出是严格 JSON，改提示别破坏 `{"facts":[...],"daily":"...","summary":"..."}` 契约。
- **新增技能只需补齐注册 metadata**：在 `agent/skills/*.md` 写好 `name`、`description_short`、`description_long`、类别和关联工具；注册表会自动扫描并生成索引，不要再把技能目录或普通触发指针复制到 `skills.md`。
