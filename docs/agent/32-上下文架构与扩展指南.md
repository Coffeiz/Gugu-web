# 咕咕上下文架构与扩展指南

本文面向维护后端 Agent、工具、Skill、provider adapter 和观测系统的开发者。内容以当前 `dev` 工作区代码为准；历史 PRD 中未落地的目标不能当作现状。

## 1. 当前组装模型

一次请求的逻辑结构可以概括为：

```text
稳定 system
  + 会话 snapshot 固定注入
  + 已持久化的 canonical history
  + 当前 user message
  + 动态尾部
      - 当前消息 sent_at reminder
      - 本轮临时上下文 / IM 身份与桥接信息
      - stance / summary
      - 当前时间
```

不同 provider 的外层 wire format 可能不同，但内部组装边界应保持一致。Anthropic 使用独立 `system` 参数；OpenAI-compatible provider 通常把稳定 system 作为第一条 system message。不要因为 provider 表面格式不同，在 Web、IM 和定时任务中各自发明一套历史组装规则。

主要入口：

- `backend/agent/context/builder.py`：生成稳定 system 与 snapshot dynamic context。
- `backend/agent/context/session_snapshot.py`：snapshot 生命周期、TTL、hash 和时间 reminder。
- `backend/agent/context/message_assembly.py`：固定部分、conversation、动态尾部的顺序管理。
- `backend/agent/context/history.py`：持久化历史到 provider history 的统一转换。
- `backend/agent/runner.py`：请求编排、快照读取、工具轮次、持久化和用量记录。
- `backend/agent/gateway/web.py`：Web 流式入口；IM/其他入口应复用同一 runner 约定。

## 2. 静态规则与 snapshot

`builder.build_split()` 返回 `(static_text, snapshot_context, now_str)`。

### 稳定 system

稳定 system 主要包含：

- persona/profile policy；
- lens、style preferences、policy；
- Skill 索引和简短能力目录；
- 不依赖当前消息内容的行为约束。

profile 文件只取第一个 `---` 之前的静态 policy。项目、日历、文件等业务数据不得通过旧模板再次拼入 system，避免形成双轨上下文。

### snapshot context

当前 snapshot 记录：

- `system_prompt`；
- `snapshot_context`；
- `session_info`；
- `user_tz`；
- `im_channels`；
- `im_memory`；
- `context_revision`；
- `context_epoch`、`snapshot_hash` 和过期时间等元数据。

快照默认闲置 TTL 为 30 分钟（`DEFAULT_IDLE_TTL`）。当前 `ensure_snapshot()` 的可复用判断主要看快照存在、必要字段完整且未过期；业务 revision 会被写入快照并在重建时读取，但不能把它误解为当前代码已经对每种业务变更都即时重建。明确失效通过 `invalidate_snapshot()`，压缩完成后会调用该路径。

业务 revision 的来源包括 projects、calendar、files、memory、preferences、timezone 和 im_channels。revision 的事件与前端 SSE 通知是两个概念：某项变化可以影响 Agent snapshot，却不一定需要刷新整个前端。

### 当前已知边界

- `snapshot_hash()` 当前组合的是 system hash、session info hash 和 covered message hash，没有把完整 `snapshot_context` 与 revision 纳入 hash；它更适合作为 checkpoint/trace 身份，而不是完整业务快照内容的密码学身份。
- `checkpoint_snapshot()` 会把本轮新增 user/assistant 消息纳入 hash 并刷新 idle TTL，但不会把最新业务背景重新读入已有 snapshot。
- 需要把业务变更“立即反映到当前 session”时，应显式失效快照，而不是在每轮把同一批业务数据追加到动态尾部。

## 3. History 与时间

`session_history.load_session_history()` 以 `baseline_message_id` 为追加水位读取历史，并保留 summary。未压缩时不按最近 N 条滑动，压缩后从 baseline 继续追加。

`build_history_parts()` 负责：

- 保留普通 user/assistant 历史；
- 从 `content_json` 读取结构化工具历史；
- 将 Anthropic/OpenAI 的工具 wire format 转换到统一内部语义；
- 在完整 user turn 后追加 `sent_at` reminder；
- 对旧数据和附件引用执行必要的规范化。

时间 reminder 是独立消息，不塞进 user 正文，也不作为数据库正文的替代字段。当前消息时间和当前时间都属于动态区域；前者来自消息 `sent_at`，后者每轮重新生成。

## 4. Canonical 工具历史

`backend/agent/context/canonical_tool_history.py` 是 provider-neutral 的内部协议：

- `ToolCall(id, name, input)`；
- `ToolResult(tool_call_id, content, is_error, tool_name)`；
- `ToolSchemaEvent`、`SkillSchemaEvent`、`ToolDiscoveryEvent`。

持久化历史使用 canonical block。provider 适配器在发送边界转换：

```text
canonical tool_call
  -> Anthropic: assistant content.tool_use
  -> OpenAI: assistant.tool_calls

canonical tool_result
  -> Anthropic: user content.tool_result
  -> OpenAI: role=tool + tool_call_id
```

因此不能把某个 provider 的 wire JSON 当作跨 provider 的长期 canonical 数据，也不能在 Web/IM 中分别把工具历史文本化。`render_events_for_provider()` 只负责把 schema/skill/discovery 事件渲染成当前 provider 可理解的文本；原始 canonical 事件仍应保持可恢复。

新增工具或 Skill 时：

1. 在 registry 中定义工具 schema、权限和 destructive/confirm 语义；
2. 在 Skill 索引中保留短描述，详细 schema 按 Skill 注入；
3. 通过 canonical event 保存 schema/discovery 事件，不能把 provider-specific schema 直接写进 session history；
4. 为 Anthropic、OpenAI-compatible、Web、IM 至少补一条共同历史转换测试；
5. 验证 LoopScope 只记录工具数量、digest、adapter 调用统计等脱敏字段。

## 5. 工具与 Skill 注入

当前固定 Adapter 路径向模型暴露稳定入口：`call_tool`、`use_skill`、`ask_user`。首轮能力目录保持轻量；Skill 首次使用后，关联工具 schema 通过 canonical event 进入历史，后续 provider 请求由 adapter 重新渲染为合法 schema/消息。

扩展时要区分三层：

- **业务工具**：真正执行项目、文件、搜索等动作；
- **Skill**：决定何时加载一组工具及其工作流；
- **Adapter**：把内部 canonical 事件和工具调用转换成 provider wire format。

不要在 core 中用正则猜测工具调用，也不要把 provider schema 的差异散落到 gateway。守卫、权限和 destructive 确认仍在工具注册/dispatch 层完成。

## 6. 压缩

`compress_conv.py` 负责显式 `/compact` 和实际预算触发的对话整理：

- summary 作为一条 `role="summary"` 记录保存；
- runner/web 在发送前用 `pop_summary()` 取出，再放入固定上下文，而不是把 role=summary 直接发给 provider；
- 压缩完成后更新 `baseline_message_id`，并让下一轮刷新 snapshot；
- 工具调用和结果应视为一个原子 turn，不允许生成孤儿 `tool_result` 或孤立 OpenAI `role=tool`；
- 摘要生成失败必须让压缩失败，不得把“没有摘要”伪装成成功测试。

压缩只处理旧 conversation；snapshot 自己有独立生命周期。不要为了压缩而把项目、日历、文件重新复制到摘要中。

## 7. 图片与缓存边界

附件历史优先保存稳定引用/元数据。首次视觉消费可能使用 base64 或 provider 可接受的图片块；`strip_vision_for_history()` 会在持久化或后续历史组装时去除不应长期重复发送的视觉载荷。

`loop_drivers.py` 会识别 volatile base64 image，把缓存断点放在图片之前，并在首次消费后把同一轮内部的图片消息收敛为稳定文本/占位，避免下一 round/run 在同一历史位置出现“base64 → 占位文本”的结构断裂。图片能力的实际格式仍由 `chat_attach.build_user_content()` 和 provider adapter 决定。

缓存规则：

- 固定 system 可按 provider 能力加主动 cache 标记；
- conversation checkpoint 才能成为历史缓存断点；
- 每轮变化的动态尾部不加 cache 标记；
- Anthropic/OpenAI-compatible 的 cache_control、anchor 和 usage 字段必须由 adapter 处理；
- 不要依据单个 provider 的 cache_read 统计推断所有模型都支持同一种缓存语义。

## 8. LoopScope 与日志边界

LoopScope 记录上下文组装、snapshot 命中/重建、provider round、canonical event 数量、schema digest、adapter 调用次数、输入输出与缓存统计。诊断字段必须脱敏：

- 不记录聊天正文；
- 不记录完整附件、base64、签名 URL；
- 不记录完整工具 schema payload；
- 可记录数量、长度、digest、provider、api format、状态和耗时。

可观测性失败不能阻断上下文组装。业务错误需经过统一 redaction；原始异常只进入诊断日志。

## 9. 修改检查清单

修改上下文相关代码前：

- 先确认内容属于稳定 system、snapshot、history 还是动态尾部；
- 确认 Web、IM、scheduled 是否复用相同 runner/adapter；
- 确认 provider wire format 没有泄漏到 canonical history；
- 确认新增字段不会改变稳定缓存前缀；
- 确认图片、工具结果和 schema 事件没有进入可见日志；
- 补充至少一条历史转换、压缩边界或缓存边界回归测试。

建议验证命令：

```bash
cd backend
.venv/bin/pytest -q

cd ../frontend
npm run typecheck
npm run test:run
```

## 10. 当前待改进项

以下不是本文声称已经完成的功能，而是当前实现的明确边界：

1. `snapshot_hash` 尚未覆盖完整 snapshot context 与 context revision；
2. snapshot revision 已有记录和业务 bump，但即时失效策略仍需继续收敛，不能默认所有业务 mutation 都会让活跃 session 立刻重建；
3. provider cache 能力和 TTL 由各 adapter/厂商决定，LoopScope 的本地 token 估算不能替代厂商 usage；
4. provider 工具 schema payload 目前不进入 LoopScope 诊断详情，这是隐私与体积上的有意取舍。
