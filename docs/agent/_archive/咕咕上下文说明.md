# 咕咕上下文说明

这份说明面向使用咕咕的用户，解释咕咕如何在一段持续对话中记住信息、使用工具和处理附件。它不描述模型厂商的内部实现，也不保证模型每次都会记住所有细节。

## 一次回复会看到什么

咕咕处理一条消息时，通常会综合以下几类信息：

1. **稳定规则**：咕咕的角色、回答方式、基本安全规则，以及当前启用能力的简短目录。
2. **会话快照**：会话开始时读取的项目、日历、文件概览、记忆、来源和可用渠道等背景信息。
3. **对话历史**：当前会话中已经发送和收到的消息，包括工具调用及其结果。
4. **当前消息**：你刚刚发送的文字、附件和引用内容。
5. **动态信息**：消息发送时间、当前时间、最近的相处方式/摘要，以及当前这轮临时上下文。

这些信息不是混成一大段文本。稳定部分尽量保持不变，变化频繁的部分放在对话尾部或最新消息附近，这样既能减少重复处理，也能让咕咕更准确地知道“现在发生了什么”。

## 记忆、项目和文件什么时候更新

项目、日历、文件和长期记忆属于会话背景。它们会在会话建立或快照刷新时重新读取；当前实现使用约 **30 分钟的闲置快照有效期**。会话期间新产生的消息、工具结果和你的明确说明仍会进入对话历史，因此不必把每次变化都重新复制成完整背景。

如果你刚刚修改了项目、偏好或连接设置，而咕咕暂时没有反映，继续发送一条消息或重新开始/刷新会话通常会触发新的上下文读取。快照刷新与前端页面刷新不是同一件事。

## 工具和技能

咕咕不会在每轮都把所有工具的完整说明塞进上下文。开始时通常只提供简短的能力目录；当任务需要某项技能时，咕咕先加载对应技能，再使用该技能关联的工具。

工具调用和工具结果会作为对话过程的一部分保留。这样后续轮次可以知道刚才做过什么，也能在需要时继续使用结果。工具成功或失败的状态属于过程信息，不等于咕咕已经完成了你的最终目标，咕咕仍需要根据结果组织回复。

## 图片和附件

附件会先以附件引用和元数据进入消息。需要视觉理解时，咕咕可以读取附件；需要找同款或相似图时，会把附件交给相似图搜索工具。

图片的原始视觉数据有时只在首次消费图片的那一轮临时发送。后续历史会尽量使用稳定的附件引用或占位信息，避免每轮重复携带很大的图片数据。图片搜索结果中的网络图片也可能需要单独读取，具体取决于来源是否可访问。

如果咕咕无法读取图片，通常可以尝试：

- 重新发送为 JPG 或 PNG；
- 让咕咕读取你刚发送的附件；
- 提供角色名、作品名或图片来源作为补充线索。

## 对话太长时会怎样

当历史接近上下文限制，咕咕会把较早的一部分对话整理成摘要，并保留较新的原文。工具调用和工具结果会尽量作为一个完整过程处理，不把调用和对应结果拆开。

摘要不是逐字记录，适合保留决定、事实、偏好和未完成事项；需要精确原文时，建议重新提供相关内容。也可以使用 `/compact` 主动整理旧对话；如果当前没有足够的旧内容可整理，咕咕会告诉你这一点。

## 时间信息

消息发送时间和当前时间会作为上下文中的独立提示提供给咕咕。消息时间使用你的用户时区格式化，当前时间会随每轮更新。时间提示不属于长期记忆，也不应被理解为你说过的正文。

## 隐私与诊断

会话背景按用户和会话隔离。性能监控和 LoopScope 主要记录耗时、用量、缓存统计、事件数量和脱敏摘要，不应把聊天正文、附件内容或完整工具参数当作诊断数据展示。

咕咕仍可能因模型限制、网络失败、附件过期或上下文过长而遗漏信息。遇到重要事实，直接在当前消息中重申通常最可靠。
