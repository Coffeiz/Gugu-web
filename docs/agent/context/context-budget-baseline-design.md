# 上下文预算与 Baseline 设计

## 1. 背景

当前 Web 和 IM 共用会话历史，但不同模型、不同入口的上下文上限可能不同。历史中还可能包含大型工具结果、图片或视频数据。若首次请求直接加载完整会话，服务商可能在 Agent Loop 开始前返回 `413 request_too_large`，导致用户只看到“调用中出错”，也没有机会进入正常压缩流程。

本设计将“运行中上下文保护”、“run 完成后的后台 checkpoint”和“正常记忆维护”分开：

- 正常维护可以使用 LLM 做摘要和长期压缩。
- Agent Loop 运行中达到模型硬上限时，只压缩当前 run 之前的历史，保护当前 run 的消息链并继续执行。
- run 完成后按 90% 软阈值启动后台压缩；下一条消息消费这个 checkpoint，不让压缩与新消息并发写同一 session。
- 供应商异常或压缩失败时，执行确定性的分级兜底，不把“开小差”作为第一次预算处理手段。

## 2. 目标

- 在请求发出前估算完整上下文，避免用服务商错误作为常规截断机制。
- 保留当前合法的历史基线，例如已有 150k 上下文且仍低于有效预算时继续累积。
- 超量时按消息边界快速截断，保证请求可以重新发送。
- 使用 `baseline_message_id` 标记已经被处理的历史水位，后续请求和 TTL 都从新基线继续。
- 对 Web、私聊、群聊和定时任务使用同一套预算策略。
- 让视觉附件和工具结果不会把原始二进制反复注入上下文。

## 3. 核心概念

### 3.1 有效预算

```text
effective_budget = min(
    模型配置的上下文上限,
    已知的服务商上限,
    本地安全预算,
)
```

本地安全预算应留出 system prompt、工具定义、当前消息、输出空间和估算误差，不能把模型标称上限全部用于历史。

### 3.2 Baseline

`baseline_message_id` 是上下文历史水位，不是“最近 N 条消息”。

- baseline 之前的内容已经被摘要、归档或明确丢弃。
- 普通请求只加载 baseline 之后的消息。
- 每次强制截断或正常 LLM 压缩完成后，baseline 推进到最后一个已处理的完整消息。
- 工具调用和对应工具结果视为不可拆分的消息组；不能只保留其中一半。

### 3.3 两种压缩

| 类型 | 触发时机 | 是否允许调用 LLM | 目的 |
| --- | --- | --- | --- |
| 正常维护压缩 | 空闲、定时、累计达到阈值 | 可以 | 生成可读的 daily/summary/memory |
| 运行中硬预算压缩 | 工具结果追加后、准备进入下一轮时达到模型硬上限 | 可以，但只压缩当前 run 之前的历史 | 保护当前 run，继续完成多步骤任务 |
| 请求自救截断 | 预检超量、413、单条结果超限、压缩失败 | 不可以 | 立即把请求压到安全预算内 |

请求自救流程不是记忆压缩：先保留当前用户消息和完整工具链；若摘要不可用，先保留最近 20 条完整消息，仍超预算时才做本地确定性截断。

### 3.4 当前 run 保护范围

当前 run 从本轮用户消息开始，到最终 assistant 输出结束。运行中的压缩只允许处理保护边界之前的历史：

```text
旧历史                         可压缩
当前 run 之前的历史             可压缩
当前 run 的用户消息             保留
当前 run 的 assistant/tool call  保留
当前 run 的 tool result         保留
当前 run 的最终 assistant 输出  保留
```

当前 run 的所有消息仍须正常持久化。若当前 run 自身的单条工具结果已经超过模型上限，不能只压缩旧历史，必须对该结果执行字段级截断或摘要化。

## 4. 请求流程

```text
加载 baseline 之后的历史
        ↓
递归清理不可直接注入的附件/工具结果
        ↓
组装 system、工具定义、动态上下文、当前消息
        ↓
估算请求大小
        ↓
未超预算 ─────────────→ 正常调用 Agent Loop
        │
        └─ 超预算
             ↓
       运行中硬预算检查
       ↓ 只压缩 run 之前的历史
       LLM 压缩
       ↓ 失败/仍超预算
       最近 20 条消息
       ↓ 仍超预算
       确定性强制截断
             ↓
       重新估算
             ↓
       在预算内 → 调用 Agent Loop
       仍超量 → 丢弃更旧历史/大型结果，或返回明确错误
```

run 完成后的后台流程独立于上面的同步自救流程：

```text
run 输出完成
    ↓
估算 session 上下文
    ↓
低于 90% → 保持当前 baseline
达到 90% → 后台创建压缩 checkpoint
    ↓
下一条消息到来时等待 checkpoint
    ↓
使用新 baseline 组装上下文
```

### 4.1 预检

预检必须发生在第一次 provider 请求之前，不能先发送一次完整请求再等待 413。估算内容至少包括：

- system prompt 和当前时间等动态提示词；
- 工具定义；
- baseline 之后的会话消息；
- 当前用户消息和附件描述；
- 预留输出预算。

预算口径必须覆盖 `PromptMessages` 的完整请求：固定前缀、可压缩 conversation 和动态尾部都要计入。RAG 召回、提醒、当前时间等动态尾部不属于可压缩历史，但不能因为它们位于 conversation 之外而被估算遗漏。压缩或确定性截断时，应先为动态尾部预留 token，再只处理可压缩 conversation，并在替换 conversation 后原样保留动态尾部；预检、压缩结果校验和最终截断必须使用同一套总量口径。

### 4.2 强制截断规则

强制截断必须是本地、同步、可预测的操作：

1. 先移除已经不应进入模型的原始图片、视频、base64 和重复工具输出，仅保留类型、摘要、引用或文件标识。
2. 保留当前用户消息、最近一组完整的工具调用链和必要的系统上下文。
3. 从最旧历史开始按完整消息组删除，直到估算值低于安全预算。
4. 如果仍然超量，继续删除较旧的工具结果和附件描述。
5. 如果单条当前消息或单个工具结果本身超限，按字段级规则截断；不能通过无限重试解决。
6. 推进 `baseline_message_id`，记录本次被截断的范围和原因。

默认目标是把历史压到有效上下文预算的约 20%，但这个 20% 是“确定性截断后的安全目标”，不是要求调用 LLM 生成 20% 摘要。

### 4.3 413 兜底

如果本地估算没有命中，但 provider 仍返回 413：

- 只允许执行一次更激进的确定性截断并重试；
- 重试仍失败则停止当前请求并返回明确错误；
- 不在异常路径启动 LLM 摘要，不进行无限 retry；
- 记录请求大小、预算、截断阶段和重试次数，不记录聊天正文。

### 4.4 运行中硬预算与后台 checkpoint

工具调用完成后、进入下一轮 provider 请求前必须再次计算预算，不能只在整个 run 的第一轮预检一次。

- 达到模型硬上限：立即压缩当前 run 之前的历史，然后继续当前 run。
- 当前 run 的用户消息、工具调用、工具结果和最终输出不得被后台 checkpoint 删除。
- run 完成后，90% 只作为后台压缩阈值，不作为当前请求的失败阈值。
- 后台压缩必须以 session 为粒度加锁，并携带覆盖消息水位；新消息到来时若发现 checkpoint 正在运行，应等待同一任务，而不是并发启动第二个压缩。
- 后台压缩失败不阻塞当前已完成的 run；下一条消息仍需执行硬预算预检和确定性兜底。
- 压缩结果提交前校验消息水位，避免旧任务覆盖新消息产生的 baseline。

## 5. 正常 LLM 压缩

正常记忆压缩由现有异步记忆维护流程负责；对话上下文 checkpoint 则在 run 完成后按 90% 阈值异步启动。两者可以共用摘要契约，但必须使用独立的 session checkpoint 锁和消息水位，避免后台任务、运行中硬预算压缩和手动 `/compact` 覆盖彼此的 baseline。

正常压缩完成后：

- 摘要写入对应 scope 的记忆文件或数据库记录；
- `baseline_message_id` 推进到摘要覆盖的最后一条消息；
- 下一次请求只读取新 baseline 之后的内容；
- 如果 LLM 压缩失败，仍保留确定性截断能力，不阻塞对话。
- run 完成后的 checkpoint 不得阻塞已经发送给用户的回复；下一条消息才等待其完成。

## 6. TTL、模型切换与 Scope

### 6.1 TTL

TTL 从当前 baseline 之后的未整理消息计算，不重新扫描已经归档或丢弃的旧历史。空闲整理完成后更新 baseline 和整理时间。

### 6.2 模型切换

每次请求根据当前激活模型重新计算 `effective_budget`：

- 切换到更小上下文模型时，先预检并确定性截断；
- 切换到更大模型时，不自动恢复已经丢弃的历史；
- baseline 是单向水位，避免模型切换造成历史来回膨胀。

### 6.3 Scope

owner、member、group、私聊和群聊可以有不同的动态上下文，但使用相同的 baseline、预算、截断和重试规则。不同 scope 不能共享 baseline。

## 7. 附件和工具结果清理

清理必须递归处理嵌套结构，尤其是 `tool_result.content`：

- 图片、视频和音频只保留可供模型使用的引用、尺寸、媒体类型或短描述；
- 禁止把原始 base64 写入后续历史上下文；
- 读取旧数据时也要清理，不能只依赖新消息写入时清理；
- 单个工具结果设置字段级大小上限，超出部分使用截断标记；
- 清理日志只记录大小、类型和 fingerprint，不记录正文、附件名或用户输入。

## 8. 状态与可观测性

每次请求可以记录以下结构化字段：

```json
{
  "event": "context-budget",
  "scope": "group",
  "baseline_message_id": 0,
  "history_messages": 533,
  "estimated_tokens": 0,
  "effective_budget": 0,
  "preflight_over_budget": false,
  "run_hard_budget": false,
  "protected_run_messages": 0,
  "post_run_checkpoint": false,
  "checkpoint_status": "idle",
  "forced_truncate": false,
  "provider_413": false,
  "retry_count": 0,
  "dropped_message_count": 0,
  "oversized_item": false
}
```

实际实现中不写入估算之外的正文内容；敏感标识按现有日志安全规范处理。

## 10. 验收标准

- 合法的 150k 上下文不会被无条件压缩或截断。
- 预检发现超量时，不发生第一次必然失败的 provider 请求。
- 异常路径不调用 LLM 压缩，不因压缩失败继续重试。
- 工具轮次达到硬上限时，当前 run 消息不被丢弃，且能在压缩历史后继续下一轮。
- run 完成后达到 90% 会创建后台 checkpoint，低于 90% 不重复压缩。
- 413 最多触发一次确定性截断重试。
- 新 baseline 后的请求不会重复加载已处理历史。
- 旧历史中的嵌套 base64 不会再次进入模型请求。
- Web 和 IM 对同一 scope 使用一致的预算与 baseline 语义。

## 11. 待确认参数

- 各 provider 的真实上下文上限由配置提供，还是维护一份能力表。
- 本地安全预算预留比例，建议先按模型上限的 80%～90% 评估。
- 强制截断后的 20% 目标是否按 token 预算，还是按消息组上限兜底。
- 截断后的历史是否只推进数据库 baseline，还是同时写入一条可审计的系统事件。
