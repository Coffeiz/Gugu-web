## 这篇在讨论什么（速读）

**要解决的问题**：IM（飞书/QQ/微信）现在走的是**非流式**回复——用户发一句话，如果咕咕这轮要跑多步工具调用（比如联网搜索+读网页+回答），用户在整个过程里**完全看不到任何中间反馈**，只能干等最终一条消息，长的能等到几十秒。网页端有 SSE 流式输出兜着，IM 没有，这是 IM 体验相对网页明显偏差的一块。

**核心结论**：给 IM 加一层「慢工具开始执行时发一条自然语声明」的机制，但**声明内容必须来自代码/工具自身登记的固定文案，绝不能是模型现场生成的话**——这是全文最重要的约束，直接对应咕咕一直在做的「真实性守卫」（`03-可靠性.md`）：如果放开让模型自己决定说什么再去调工具，一旦模型说了却没真调用（哪怕概率很低），这句话已经作为真实 IM 消息发出去、用户看到了、撤不回，比现在「沉默等待」体验更差、还多出一种新的失信场景。

**方案取舍过程**（详见下文 §2）：讨论过三版——① 模型自己先说一句再调工具（否决，可靠性风险）；② 纯系统状态提示如"🔍 正在搜索…"（可行但没有聊天感）；③ **最终版**：Runtime 在工具真正要派发的那一刻，读取该工具自己登记的 `start_message` 模板发出去（自然语气 + 100% 确定性保证）。

**还没做的部分**：代码完全没动；「接入咕咕」（IM 绑定设置）那边需要加一个开关，让用户自己决定要不要开这个功能——这个开关的具体位置/交互还没设计，是本文档留的一个待定项（见 §6）。

## 1. 背景

- IM 走 `agent/runner.py` 的非流式路径（对照网页走 `adapters/web.py` 的 SSE 流式，见 [`../02-决策环.md`](../02-决策环.md) 「① 入口编排」）。多步工具循环（`core.py` 的 `LLMRunner`，最多 6 轮）跑起来的这段时间里，IM 用户只能等最终结果。
- 现有的「秒回」机制（`agent/adapters/*.py` 的 `_on_message` 收到即发表情反应）已经解决了「消息有没有被收到」这个最基本的确认，但没有解决「处理过程中在干什么」这个更细的反馈缺口。
- `agent/runtime_state.py` 已有 IDLE/THINKING/SEARCHING/GENERATING 状态机（带 TTL 防卡死），目前只用来给网关短路"还在吗/算了"这类用户追问，没有被用来主动推送进度。

## 2. 方案取舍（讨论过程）

### 2.1 否决：模型自己先说一句声明，再调用工具

```
LLM: "让我看看。"
（这里本该紧跟工具调用）
——结果模型这轮因为各种原因没真的发出工具调用
IM 用户看到：🤖 让我看看。
然后什么都没发生。
```

这正好撞上咕咕最花力气在防的失败模式（`agent/core.py` 的 `_announces_intent`/`_NARRATION_NUDGE`、`31-多步执行与防停顿.md`）——「说了要做却没做」。声明一旦发到 IM 就是真实消息、撤不回，比现在的沉默更糟：从「用户等得久」变成「用户等得久 + 被骗了一句」。**这条路径直接否决，不因为体验好就妥协可靠性。**

### 2.2 可行但体验有限：纯系统状态提示

```
Tool Dispatch → 系统："🔍 正在搜索..."
```

可靠（Runtime 生成、不是模型话），但没有「聊天感」——IM 里会变成程序在报状态，不像人在做事。

### 2.3 最终版：Runtime 在 dispatch 时读取工具自带的自然语声明

关键分离：**"要不要说话"和"说什么话"分开**——说话的时机和触发条件由 Runtime 严格把控（工具真正要执行时才说），但话术内容可以是自然语气的（"我去查一下最新资料"），只要这句话本身不是模型现场决定的、而是工具注册时就写死/模板化好的。

**声明来源的边界**（本文档最重要的一条纪律）：**只有 Runtime 在 dispatch 那一刻已经确定知道的信息，才能拿来生成声明；不能是任何形式的推测。**

- ✅ `browser.click(target=...)` → 声明可以带上 `target`，因为这是调用参数，dispatch 时已知。
- ✅ `web_search(query=...)` → 声明可以是固定文案"我去查一下"，或带上 `query` 变量。
- ❌ `http_get(url=...)` → **不能**细分成"读网页"/"下载PDF"/"调用API"，因为这几种的区别要看**响应的 Content-Type**，dispatch 那一刻请求还没发出去，根本不知道对方会返回什么。这种工具只能用统一的粗粒度文案（"我去看看这个链接"），不能装出一个它自己都不知道的判断。

## 3. 架构

```
用户消息进 IM
   ↓
① 秒回表情（已有机制，网关收到即发，独立于下面这套，不受影响）
   ↓
② Runtime 进入 Busy Session
   （复用现有 runtime_state.py 的 THINKING 状态，不新建概念——
    一个 Busy Session ≈ 一轮「用户消息 → 最终回复」之间的处理周期）
   ↓
③ 模型开始跑决策循环，触发第一个工具调用
   ↓
   走到 agent/tools/base.py 的 dispatch（全系统唯一的工具派发入口）
   ↓
   ┌─ 这个 Busy Session 还没发过声明？
   │  ├─ 是 → 看这个 Tool 有没有注册 start_message
   │  │       ├─ 有 → 立刻发一条真实 IM 消息（内容来自 Tool 自己的
   │  │       │        metadata，不是模型现场生成），标记「本 session 已声明」
   │  │       └─ 没有 → 不发（工具自认为够快，不用提醒——天然免去
   │  │                  「哪些工具算慢」这个额外判断，纯本地查询类
   │  │                  工具如 list_files/get_calendar 不用挂这个字段）
   │  └─ 否（已经声明过）→ 跳过，直接执行
   ↓
④ 真正派发工具执行
   ↓
⑤ 同一个 Busy Session 内后续随便调几个工具、循环几轮
   ——都不再重复发声明（③ 的「已声明」标记保证只触发一次）
   ↓
⑥ 模型收尾，最终回复发出
   ↓
⑦ Busy Session 结束（runtime_state 清掉 THINKING）
   ——下次用户再发消息、再触发慢工具，回到 ② 重新走一遍
```

**改动点集中在两处**（架构上不新增系统，全部挂在两个已有的东西上）：

1. `agent/tools/base.py` 的 `Tool` 注册结构加一个可选字段 `start_message`（静态字符串，或 `lambda(args) -> str` 按调用参数变化措辞——只能读 dispatch 时已知的参数，绝不能猜返回结果，见 §2.3 的边界）。
2. dispatch 函数本身加一段「本 Busy Session 是否已声明」的判断 + 发送逻辑，挂在 `runtime_state.py` 现有的状态生命周期上（进入 THINKING 时重置「未声明」标记，清除时一并清掉）。

## 4. 约束条件

- **只在 IM 生效，网页不接入**：网页本来就是 SSE 流式输出，用户已经能看到生成中的动效，再插一条系统声明反而可能显得多余、割裂对话流。这是专门补 IM「非流式、长时间沉默」这个特定痛点的，不是要改网页的体验。
- **声明内容 100% 来自 Tool 自己登记的 metadata，模型不参与生成这句话**——这是贯穿全文的核心纪律，不是实现细节，是可靠性边界。
- **一个 Busy Session 最多发一条声明**，不管中间调了几个工具、循环几轮——避免多工具连续调用时刷屏。
- **没注册 `start_message` 的工具完全不触发这套机制**——工具自己决定要不要用这个功能，Runtime 不维护一张「哪些工具算慢」的额外名单。
- **声明的细分粒度受限于 dispatch 时刻已知的信息**——响应到达之后才能确定的东西（如 `http_get` 的资源类型）不能提前细分，只能用粗粒度的通用文案。

---

## 5. 与「所有对用户可见的状态必须来自已确认事实」这条项目原则的一致性

这个设计遵守的其实是咕咕一直以来的调性——不可逆操作要走确认门（`agent/confirm.py`）、跨用户访问统一走 `get_owned` 把"不存在"和"越权"一起返回避免探测、聊天内容不落原文只留指纹（`agent/logsafe.py`）——都是同一种"宁可少说、不说错"的克制。这次的声明机制只是把这条原则用到了一个新的界面（IM 进度反馈）上：**所有拟人感必须建立在系统已确定发生的事实之上，不能建立在任何形式的预测或模型自由发挥上。**

## 6. 待定项（评审后才能定）

- ⬜ **「接入咕咕」（IM 绑定设置）要加一个开关**，让用户自己决定要不要开这个功能——具体加在哪个设置面板、默认开/关、是否分平台（飞书/QQ/微信）单独控制，都还没设计。这是本文档明确留下的第一个待办，实现之前必须先定。
- ⬜ 首批哪些工具该挂 `start_message`（`web_search`/`deep_research`/`image_search`/`http_get` 这几个网络型工具是明显候选，具体列表待定）。
- ⬜ `start_message` 的具体文案、要不要多个候选随机挑一个避免机械重复，留给实现阶段按 persona 语气打磨。
- ⬜ 是否需要给已有的 `runtime_state.py` 加一个「本 session 是否已声明」的字段，还是用一个独立的轻量标记（如 Redis 里挂一个 TTL 键）——具体存储位置待实现时定。
