## 这篇在讨论什么（速读）

**要解决的问题**：咕咕现在完全没有「主动触达」能力——不会在用户没开口时主动想起 TA。这是产品层面唯一还空着的大块。本文讨论的是：要不要、以及怎么把「咕咕该不该行动、行动什么、怎么表达」从一个大 Prompt 里抽成一条可观测、可演进的决策管线。

**核心立场（全文最重要的一条）**：不主张把聊天和主动触达一刀切地统一成同一套"厚"决策流程。聊天路 LLM 当场在场、判断力够，决策层保持**薄**；主动触达路 LLM 不在场（没有用户消息触发），必须显式打分、显式过闸门，决策层做**厚**。两路共享的是管线的"形状"和可观测性，不是决策的"逻辑量"。

**想清楚了但还没做的部分**：评分体系怎么分层、主动触达管线的候选生成/打分/闸门/LLM 把关/反馈五步怎么串、分期路线怎么排。这些都还停在设计阶段，§9 也留了一批需要继续拍板的待定项。

如果只想知道"现在咕咕会不会主动找我"——答案是不会，本文只是在讨论要不要做、怎么做。

## 0. 一句话

把「咕咕要不要行动、行动什么、怎么表达」从**一个万能 Prompt** 里抽出来，变成一条**可观测、可演进的决策管线**——但**按当前 LLM 现状校准厚薄**：对话路保持薄（让模型当场判），主动触达路做厚（模型不在场，必须显式决策）。

## 1. 背景与目标

- **差异点**:伙伴 vs 助理的核心是「在你开口前就记挂着你」。咕咕现在**完全没有主动触达**——这是产品层面唯一还空着的大块（见 [`../02-决策环.md`](../02-决策环.md) 未做项 / [`../../product/wishlist.md`](../../product/wishlist.md)）。
- **长期野心**:若以后接语音/邮件/桌面/车机，输入来源会变，但「理解→决策→执行→表达→反馈」这条链不该每接一端重写一遍。事件驱动能让 Trigger 可扩、中间链复用。
- **本草案目标**:① 定下决策层的**哲学与边界**；② 给**主动触达**一个可落地的第一版设计；③ 留下**待定决策**供继续讨论。

## 2. 北极星 vs 现状校准（核心立场）

**北极星**(GPT 提的，认同方向):
> *Everything is an Event, everything goes through Decision.* 用户的「你好」和系统发现的「连续三天没完成项目」走同一条决策引擎，由它决定要不要行动、行动什么、怎么表达。薄 Prompt、厚 Decision、可追踪、增量长评分。

**为什么不照搬到聊天路**(校准，贴合当前 LLM):
1. **LLM 在场时判断已足够好**:实时对话里「该多温柔 / 多长 / 要不要追问」，强模型结合全上下文当场判得很细。抽成 `warmth=90 → 换 prompt` 是把高维语境判断**压成标量再还原 → 降级**。
2. **LLM 吐的分数没校准**:同句话这次 78、下次 85，用 `if score>80` 当**硬控制流**会比现在更不稳。咕咕的「守卫」层正是因为模型不可靠才存在——别再往控制流里塞模型吐的噪声数字。
3. **多一跳 = 已修过的回退**:`core.py` 现为**单次流式调用**（早期"探测→再流式"双调用敷衍已修）。给聊天加 Perception 前置 LLM 等于把延迟请回来；聊天是 95% 路径、对响应最敏感。

**关键不对称**(本草案最重要的一条):

| | 聊天路 | 主动触达路 |
|---|---|---|
| 决策时刻 LLM 在不在场 | **在**（参与者，可实时判） | **不在**（无用户消息触发） |
| Decision 层厚薄 | **薄**——大部分让给 LLM | **厚**——必须显式分数+闸门 |
| 外化判断划不划算 | 多数是降级 | 必需 |

> GPT 说「聊天和主动触达只有 Trigger 不一样、其它全一样」——**最漂亮也最误导**。正确说法:两路共享**同一套管线形状 + 遥测**，但 Decision 层**厚薄相反**。统一在「形状和可观测性」，不在「逻辑量」。

**三条落地原则**:
- **该厚则厚、该薄则薄**:决策外化只推到「确定性比 LLM 强 / LLM 缺席」为止，一步不多。
- **分数先当信号、后当控制**:先只 log、观察校准，确认稳了再升级成控制流。**且能毕业进控制流的，多是有「客观真值」的分**(调没调成、用户回没回、答案对不对);主观分(Warmth/Humor/Verbosity)没真值可校准，大概率永远停在遥测——这正常，留给 LLM。
- **从两端往中间长**:别一上来把聊天推平成厚 Decision；理解层的信号**凭观察到的真实失败逐个挤进聊天**，不预先铺。

**⚠️ v0.2 修订:聊天不是一律薄。**「聊天默认薄」的前提是「LLM 在场判断够好」;一旦观察到**某项判断 LLM 确实不可靠**，它就该进决策层——哪怕在聊天里。**第一个被观察出来的就是「该不该先问清需求」**:模型爱直接下判断 / 替用户做决定，不去澄清真实需求(系统性毛病，非咕咕独有)。详见 §5「Clarification Need」。

## 3. 咕咕已有的「决策层雏形」

不是从零起——「提示词软、守卫硬」其实已经是**外科手术式的 Decision 层**，分布在两端:

- **前端 · `router.py`（⓪ IM 前置路由）**:确定性预路由，「嗯/算了/还在吗」据状态机短路。新增的 `awaiting` 标志也属此层。
- **后端 · `core.py` 真实性守卫（④′）**:确定性后检，「说了没做/该做不做/改了没核对」逼纠偏。

本草案是同一哲学的**延伸**:把决策层从两端，向「模型缺席」的场景（主动触达）扩；而不是推平到聊天的控制流里。

## 4. 统一管线（形状）

所有行为走同一形状，**只有 Trigger 不同、Decision 层厚薄不同**:

```
Trigger（事件）
  · 用户消息  · Cron 定时  · 系统事件(任务完成/deadline 临近/连续行为)
        │
        ▼
Context Builder   收集相关信息（不思考）：会话/项目/日历/记忆(summary/facts/daily)/时间/last_active
        │
        ▼
State Analyzer    理解「现在发生了什么」（intent/emotion/topic/是否需外部信息）——只描述，不决策
        │
        ▼
Decision Engine   产出少量 Score（见 §5）
        │            · 聊天路：薄，多数交给下游 LLM
        │            · Push 路：厚，分数+确定性闸门定夺
        ▼
Action Planner    确定性规则把分数落成动作（要不要调工具 / 要不要 Push / 给多少 token / 换哪套语气）
        │
        ▼
Tool Executor     （需要时）执行工具，回灌结果
        │
        ▼
Response Generator  LLM 拿着已定好的约束写话
        │
        ▼
出口：Chat（流式回） / Push（IM+站内通知） / Silent（决定不打扰）
        │
        ▼
Feedback          记录结果（开没开/回没回/多久回）→ 反哺 Decision（见 §7）
```

> **现状映射**:聊天路今天已是 `Context(builder) → (隐式理解) → core.py 单次流式(LLM 自己决策+执行+表达)`。本草案**不拆聊天的这一跳**，只让它**额外吐遥测**（§5），并把完整管线**先建在 Push 路**。

## 5. 评分体系（起步 ~10，三层，带定义）

**原则**:起步只要 ~10 个核心分；每个**写一句定义 + 单一职责**；**先遥测、后控制**；以后增量长（Novelty/Surprise/Growth/Interruption Cost/Trust Risk/Long-term Value… 都后话）。

分三层（职责清晰、便于扩展）:

### 第一层 · 理解（Understanding）「用户现在需要什么」
| Score | 定义（一句话） | 起步用途 |
|---|---|---|
| **Clarification Need** | **需求/意图有多不明、现在猜错代价多大 → 该先问还是直接做** | **聊天:prompt 已上 + 遥测**（首个进场聊天的信号） |
| Tool Need | 是否值得调工具，而非靠模型直接答 | 聊天:遥测（LLM 已自主调）；Push:控制 |
| Confidence | 当前答案的可信程度（低→去查，更低→认不知道） | 遥测（减少编造，先观察） |
| Emotional Support | 是否应优先回应情绪而非给方案 | 遥测 → 后续喂 prompt |
| Reflection Need | 是否应调历史数据做分析，而非直接安慰 | 遥测 |

> **Clarification Need · 第一个进场聊天的理解层信号**（v0.2）
> - **失败现象**:咕咕爱直接下判断 / 替用户做决定，不去问清真实需求 → 答非所问。模型通病(被训得果断、少问)。
> - **关键区分**:① 事实/信息未知 → **去查**(别问用户)；② 用户**意图/需求**不明(多种合理解读、缺关键参数)→ **先问一句最关键的澄清**。旧 prompt 把两者混成「别问、去查、果断做」，是主因。
> - **双胞胎坑**:过度追问一样烦人。所以目标不是「多问」，是**校准**——歧义高、猜错代价大才问；能合理默认的别问。
> - **做不成硬守卫**:「本该问却没问」是主观判断、无当场真值。唯一干净的真值是**事后**——用户下一句若是纠正(「不是，我是说…」)，就是「刚才该问」的铁证 → 可作遥测的 ground truth + 反哺。
> - **已落地(prompt 层)**:`skills.md` 加「需求不明先问一句」+ 区分两种不确定 + 配平原「一次到位/别推回用户」；热生效。
> - **闭环现成**:咕咕一问就进 `awaiting` 状态，用户的「嗯/是A/不是B」由路由正确放行回 agent（见 [`../02-决策环.md`](../02-决策环.md) 等回话标志）。
> - **后续**:emit Clarification Need 分只 log，用「下一句是否纠正」统计「该问没问」命中率；够稳再谈是否软控制。

### 第二层 · 决策（Decision）「系统该怎么行动」
| Score | 定义 | 起步用途 |
|---|---|---|
| Initiative | 答完要不要主动再推一句 | 遥测 → 谨慎转控制 |
| **Interrupt Value** | **是否值得主动联系用户**（Push 核心） | **Push:控制** |
| **Silence Value** | **保持安静是否比发消息更有价值**（与 Interrupt 独立） | **Push:控制** |

### 第三层 · 表达（Expression）「决定怎么说」
| Score | 定义 | 起步用途 |
|---|---|---|
| Verbosity | 该简短还是详细 | 聊天:遥测（先别硬卡 max_tokens）；可软提示 |
| Warmth | 语气温暖程度 | 遥测 → 软提示（不做硬 prompt 切换） |
| （Humor 等） | 后续再加 | — |

> **为什么大多先"遥测"**:见 §2——LLM 吐的分数没校准，先 log 几周看准不准、稳不稳，**确认某个分数确实校准、且确定性决策确实优于让 LLM 判，才升级成控制流**。`Interrupt/Silence Value` 例外——它们服务的 Push 路本就没有 LLM 当场判，必须一上来就当控制。

## 6. 主动触达（第一个落地战场）

**为什么从这开始**:Push 路是这套架构**唯一无可争议**的战场——决策时刻 LLM 不在场、要跨全用户廉价筛、要审计、要频率预算。小、闭环、风险隔离，正好把「分数→决策→动作→生成→反馈」整圈先跑通。

### 6.1 关键 reframe
**「沉默」本身是弱理由，「沉默 + 一个具体由头」才是强理由。** 按"开口后像不像朋友"排序，优先做**带由头**的:

| 由头 | 信号源 | 像朋友 | 风险 |
|---|---|---|---|
| 追问当下重心 | `summary.md` | ★★★ | 低（有据） |
| 情绪回访 | `daily`/`summary` 情绪线索 | ★★★ | 高（说不准就冒犯） |
| 承诺兑现 | 咕咕说过「回头帮你看X」 | ★★★ | 中（需先捕获承诺） |
| 截止提醒 | 项目/日历 deadline | ★★ 偏助理 | 低（定时任务已覆盖一半） |
| 纯沉默问候 | `last_active_at` | ★ 易空泛 | 高 |

> v1 建议先做 **summary 追问 + 情绪回访** 两类（最像伙伴、summary 现成）；承诺兑现/纯沉默放后面。

### 6.2 管线（候选 → 打分 → 闸门 → LLM 把关 → 投递 → 反馈）
```
Cron 每天 1–2 次扫「近 30 天活跃用户」（控成本，只扫活跃）：
 ① 候选生成（确定性，零 LLM）：从信号扒由头 → {reason, 上下文, 分数, 新鲜窗口}
 ② 打分 + 闸门（确定性）：
    · 冷却：距上次主动触达 < X 小时 → 砍
    · 静默时段：23:00–08:00 不开口（真·紧急 deadline 例外）
    · 距上次对话太近（刚聊完）→ 不"问候"
    · 频率预算：≤1/天、≤3/周；最近被忽略 → 预算腰斩（忽略退避）
    · 相关性门槛：Interrupt Value 低于线、或 Silence Value 高于线 → 不发
 ③ LLM 把关（只对闯过闸门的极少数，1 次调用）：
    "给你由头+上下文：现在是好时机吗？是→写一句自然的话；否→弃权"
    —— 给模型最后一道"算了这会儿没必要"的否决权 + 润色
 ④ 投递：复用现有 通知/IM 出口；默认站内通知，重要的（deadline）才进 IM
 ⑤ 反馈：记 {reason, 时间, 渠道, X 小时内有没有回} → 反哺 ②
```
> **成本**:确定性闸门先筛掉 99%，只给"真有由头"的少数花 1 次 LLM。成本 ≈ 真有事可说的用户数，不是总用户数。

### 6.3 两个核心分
- **Interrupt Value**:这个由头此刻值不值得打断用户（deadline 95 / 连续坚持 65 / 没事 10）。
- **Silence Value**:此刻闭嘴是不是更好（今天用户已经聊很多 → 95「今天别说了」）。**与 Interrupt 独立**:可能既"有点值得说"又"但今天该安静"。最终 `发不发 = Interrupt 高 且 Silence 低 且 过闸门`。

### 6.4 复用现有件（别重造）
- `app/scheduled_tasks.py` + APScheduler:Cron sweep 的执行器。
- `run_ephemeral`（[`../00-总览.md`](../00-总览.md)「提醒工作流」）:静默后台跑 + 不进对话历史，主动触达天然就该这样。
- 通知/IM 出口:`events.publish(notification=…)` 站内弹窗 + `_deliver_im` 按渠道 DM。
- `summary.md` / `daily.md` / `last_active_at` / 项目 deadline:候选生成的信号源。
- `runtime_state.py`:存冷却/预算/退避状态（Redis，仿 awaiting 标志）。

## 7. Feedback 闭环（最该投入、最难抄）

大多数 agent 都没闭这个环。每次主动触达后记:`{event, reason, channel, opened, replied, dismissed, delay}`。用回应率反哺每人的**打扰预算**:
- 连续 K 次没回应 → 预算指数衰减甚至**休眠**，只有高价值由头（真 deadline）能唤醒。
- 被搭理 → 缓慢回升。
- 本质是个**老虎机/置信度**问题:用最少的打扰探出"这人吃不吃这套"。

> 仅对 Push 有意义（聊天有隐式反馈）。无论上层架构怎么演化，这块都值得做。

## 8. 分期路线

1. **P1 · 只建 Push 的决策管线**（不碰聊天）。`Event→Context→{Interrupt,Silence}→确定性闸门→1 次 LLM 写/否决→投递→Feedback`。由头先做 summary 追问 + 情绪回访。
2. **P2 · 聊天开始吐遥测**。反思/收尾步额外吐几个结构化信号（emotion/companionship 等），**只 log 不控制**，观察校准。
3. **P3 · 分数择优升级为控制**。某分数确认校准、且确定性决策确实优于 LLM，才从遥测转控制（从两端往中间长）。
4. **P4 · Feedback 调参成熟**:打扰预算/退避自适应；可选学习用户活跃时段择时。

## 9. 待定决策（继续讨论）

1. **统一 vs 务实**:要「统一决策引擎」(哲学优先，聊天也走厚 Decision) 还是「该厚则厚该薄则薄」(务实优先)？本草案站务实——统一只落在*遥测和管线形状*，不落到聊天的*控制流*。
2. **侵入性**:Push 默认只站内通知，还是也进 IM DM？倾向分级（默认站内，deadline 才进 IM）。
3. **默认开关**:主动触达默认开（极低频）还是默认关用户自开？伙伴感要默认开，但必须给关/调频设置。
4. **v1 由头范围**:先做哪几类？倾向 summary 追问 + 情绪回访。
5. **分数由谁产**:Push 路的分数走规则还是小 LLM？（关系成本与 §10 校准风险）
6. **择时精度**:v1 固定活跃窗口，还是从历史消息时间戳学个人活跃时段？

## 10. 风险与反模式

- **恐怖谷/过界**:提到的事不准、或方式像被监视 → 比沉默更糟。情绪回访尤其要**有据**（基于 summary/daily 实写，不脑补），宁可不发。
- **分数当控制流太早**:LLM 吐的数字没校准，硬阈值 = 抛硬币。→ 先遥测后控制。
- **为对称给聊天加跳**:别为「统一」在 95% 路径付延迟税。
- **过早优化记忆/评分**:起步 ~10 分就够，别一上来铺一百多个。
- **频率失控**:没有硬预算 + 退避，主动触达=骚扰。预算和 Feedback 是防线。
- **推倒重写**:咕咕现在能跑且精简。从两端增量长，别整体重构。
