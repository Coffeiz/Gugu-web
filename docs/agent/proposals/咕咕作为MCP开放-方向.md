# 咕咕作为 MCP 对外开放 · 方向探讨

> **状态:方向探讨（2026-07-04），未拍板、未实现。** 本文记录「把咕咕的能力做成 MCP 给其他 agent 用」这个想法的分析与取舍，作为**未来开发方向**存档，到时再选择做不做、做哪半。不含实现。
>
> **区分两个 MCP 方向（别混）**:
> - **client 方向**（咕咕**消费**外部 MCP 工具）:已有占位 `agent/mcp/`（`client.py` + `registry.py`，把外部 tool 注册成 skill），**Phase 3、未做**，见 [`../00-总览.md`](../00-总览.md) §mcp/。
> - **server 方向**（咕咕**开放自己**给别的 agent 用）:**本文**。文档此前没有。

---

## 0. 一句话

**咕咕的「手」（动作/数据）适合开成 MCP，咕咕的「记忆和人格」不适合。** 前者可做、有清晰价值；后者是护城河 + 隐私雷区，真要开也只开授权过的派生切片。

---

## 1. 关键前提:咕咕是两层叠在一起

| 层 | 是什么 | 做 MCP server 的性质 |
|---|---|---|
| **动作/数据层** | 项目、日历、文件、任务的增删改查 | **本来就是工具形状**（`agent/tools/` 注册表），做 MCP 主要是接管道 |
| **陪伴/记忆层** | 对这个用户的记忆、人格、关系、主动性 | 不是「工具」，是**体验 + 护城河**，开放 = 隐私雷区 |

问「把咕咕功能做成 MCP」，先问**哪一半**——两半难度与风险天差地别。

---

## 2. 动作层:可做、合理（但有三件必须的活）

咕咕内部已有 `agent/tools/` 工具注册表 + `dispatch`（`create_project`/`add_event`/`list_files`/`search`/`send_file`…），**这些已经是「工具」**。包成 MCP server ≈ 把同一批 tool schema 用 MCP 协议暴露、复用度高。真正要做的:

1. **身份/鉴权**（核心设计点）:咕咕工具全是 per-user（`get_owned` 按 user_id 隔离）。MCP server 必须知道「替哪个用户操作」→ 发一个**每用户的 MCP token**，把所有调用 scope 到那个 Gugu 用户。与咕咕已有 token 体系（user/stream token）一脉。
2. **挑安全子集**（不是整个注册表抛出去）:① 有些工具绑咕咕对话上下文（`attach_id`、聊天暂存），给外部 agent 未必顺;② **destructive 工具的确认门**绑在咕咕对话流里，外部 MCP 没有「对话」可确认 → 要么只暴露非破坏性工具，要么要求调用方显式传 `confirm=true`。
3. **安全面**:对外开后端 = 新攻击面 → scope + 限频 + 审计（同[安全审计报告](../../security/安全审计报告-2026-07-03.md)的口径:require_admin 之外还要 per-token 授权、越权告警、ownership 隔离照旧）。

**价值**:另一个 agent（如用户自己的编码 agent）能读项目状态、加日历提醒、查文件——把咕咕当「个人数据 + 日程中枢」。合理、可做。

---

## 3. 记忆/陪伴层:技术能做，但慎——这是雷区

「把咕咕对用户的记忆 / Person Model 开成 MCP 给别的 agent 查」——听着最有价值（咕咕最懂这个人），但撞整套设计红线:

- **隐私**:咕咕记忆最私密（健康/情绪/工作机密）。整套设计一直做**数据最小化、脱敏、per-user 隔离**;把原始 Person Model 管道给外部 agent = 一次性把隐私面放大一个数量级，违背自己立的所有红线。
- **护城河**:咕咕的价值是**关系 + 陪伴体验**，不是「可查询的记忆 API」。做成 API 就把护城河商品化，还触**假亲密/信任**红线——用户信咕咕记着，不代表信它把这些喂给随便哪个 agent。
- **真要做的边界**:只能**用户显式授权 + 派生/粗粒度切片**（如「最近在忙什么」的 summary），**绝不是原始 facts/observation 直出**;且要 per-consumer 授权闸 + 审计。

---

## 4. 方向提醒:反过来（client）可能更该先做

MCP 双向。**client 方向**（给咕咕接外部 MCP 工具）比 **server 方向**（把咕咕开放出去）**风险小得多、也更自然**——而且 `agent/mcp/` 占位就是 client 方向。要投 MCP，先做 client（给咕咕更多手）比先做 server（把咕咕的手借出去）安全。

---

## 5. 结论与建议（到时选择）

- **动作层 server MCP**:✅ 可做、合理。真做就先做一个**窄的、scoped**（如日历 + 项目 读/建）、per-user token 鉴权、curated 安全子集、处理确认门。
- **记忆层 server MCP**:⚠️ 先别。护城河 + 隐私雷区;真要开只开授权过的派生切片，不是原始记忆。
- **client 方向**:是更安全的第一步（占位已在，Phase 3）。
- **动手前先想目的**:是「让我别的 agent 管我的 Gugu 数据」（→ 动作层 server，scope by user token），还是「让别的 agent 借咕咕对我的理解」（→ 记忆层，慎之又慎）。前者支持先做窄的，后者要拦一道。

---

## 6. 待拍板（真启动时）

1. 目的到底是「操作我的数据」还是「借用理解」——决定做哪半。
2. 动作层子集范围:先只读 + 建（日历/项目），还是也放改/删（要确认门方案）。
3. 鉴权:per-user MCP token 怎么发/吊销/scope（复用现有 token 体系到什么程度）。
4. 记忆层若碰:授权模型 + 只暴露哪些派生切片 + 脱敏口径。
5. 先 client 还是先 server:资源有限时的顺序。
