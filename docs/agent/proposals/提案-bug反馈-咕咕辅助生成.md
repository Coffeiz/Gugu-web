# 提案：用户报 bug 时，咕咕辅助生成结构化报告

> **状态**：功能提案，**未实现**。供日后做时参照。
> 相关：现有反馈系统（`api/v1/feedback.py` + `models.Feedback` + `Admin/Feedback`）、[[安全-工具错误信息脱敏]]、[[gugu-privacy-redaction]]、[[wishlist.md]]。

---

## 1. 背景

本会话里咕咕遇到文件移动失败，**自己临时写了份 bug 报告**——结果暴露了两个问题：① 报告里**泄露了内部路径/UUID**（`uploads/<uuid>/…`，已促成"工具错误脱敏"那次修复）；② 咕咕**自信地误诊**（说"token 只有 read 权限"，实为 OS 文件权限）。这两点正好定义了本功能"该怎么做、不该怎么做"。

## 2. 一句话

用户在聊天里自然描述 bug → 咕咕**就着已发生的上下文分析推测**（不复现）→ 生成**结构化报告**（用户原话原样保留 + 咕咕的观察/推测分区标注）→ 存进**现有反馈系统**、后台渲染成 md。

## 3. 核心原则（红线）

1. **用户原话是圣域**：逐字、独立、不可变字段存储；咕咕的任何分析**只能追加、绝不改写覆盖**它。（防"咕咕的总结/误判替换了真实症状"——本会话的教训。）
2. **咕咕只分析推测、不复现** ⭐（本次新增）：
   - **不重跑任何操作**（尤其刚失败的、破坏性的）——复现会有副作用、可能越查越坏、或制造新错误；
   - 只基于**已发生的上下文**（这轮对话、它已经拿到的错误、它自己刚才的动作/推理）做分析；
   - **对咕咕自身的 bug 特别有效**：咕咕回看自己刚才的行为就能定位（"我把 media 变量覆盖了"这类自省），不需要复现就能指出问题。
3. **事实 vs 推测三分**：用户原话 / 咕咕观察到的事实（工具X→错误Y，可靠，基于回执）/ 咕咕的推测（根因猜测，**明确标"⚠️ agent 视角、可能不准"**，不冒充事实）。
4. **必过脱敏**：报告存储前过 `sanitize_error` 那套（密钥/连接串永远抹；路径/UUID 按去向定）；**别让"自动生成报告"成新泄露口**。
5. **显式同意 + 数据最小化**："转述到后台"跨隐私边界——用户点头才发，只带相关片段、不是整段对话/用户文件。

## 4. 报告结构模板

```
# Bug 报告 #<id>
<session_id · model · 时间 · 触发来源 web/QQ/飞书>

## 用户原述（原样，未改动）
> <用户原文，逐字；仅抹真·密钥，其余保留措辞>

## 咕咕观察到的事实
- 触发工具：move_items → 返回错误：Permission denied ‹路径已隐藏›
- 本轮还调过：read_file(成功) / …
- （都是工具回执级、可靠）

## 咕咕的检查与推测（⚠️ agent 视角，可能不准）
- 推测原因：目标文件夹写权限问题
- 注意：咕咕看不到服务端日志/OS 权限/DB 内部，基础设施类问题它注定查不准

## 复现/上下文线索
- （从对话里能提取的步骤，不主动复现）
```

## 5. 数据与落地（扩现有反馈系统）

- `models.Feedback` **已有** `category`（bug/suggestion/other）+ `content`——`bug` 类别现成。
- **扩字段**（建议）：`user_raw`（用户原话，圣域）、`agent_report`（咕咕生成的 md，含观察+推测分区）、可选 `context`（session_id/model/触发工具等结构化元数据）。`content` 可留作兼容。
- **后台**：`Admin/Feedback` 面板把 `agent_report` 渲染成 md 展示；用户原话单独高亮、标"原文未改"。
- **`.md` 是渲染格式、不是存储形态**：存数据库行，别往磁盘散落 `.md` 文件（loose 文件难管理 + 多一份用户内容落盘的隐私/清理负担）。

## 6. 流程

1. **触发**（显式）：聊天里「报个 bug」/ 反馈按钮；或咕咕检测到反复报错时**主动问**「要不要帮你报给开发?」；
2. 咕咕**就地分析**（不复现）：回看本轮错误 + 自己的动作 → 填"观察到的事实 + 推测"；
3. **确认**：把将提交的报告给用户看一眼（含它的推测）→ 用户点头；
4. **脱敏 + 存**：过 redaction → 写 `feedbacks`（kind=bug + user_raw + agent_report）；
5. 后台 Admin/Feedback 可见。

## 7. 明确不做

- ❌ **不复现/不重跑操作**（副作用 + 可能恶化）；
- ❌ **不静默上报**（必须用户同意）；
- ❌ **不往磁盘写散落 .md**（数据库行 + 后台渲染）；
- ❌ **不让咕咕的推测覆盖/污染用户原话**；
- ❌ **不把咕咕推测当事实**（必须标注）。

## 8. 实现要点

- 复用 `agent/tools/base.sanitize_error`（或抽成通用 redactor）做存储前脱敏；
- 给咕咕一段 skill/prompt：「报 bug 时——①逐字保留用户原话；②只基于已发生上下文分析、**不要复现**；③区分『你确认的事实(工具回执)』与『你的推测』，推测标注;④对自己的 bug 重点自省刚才的动作」；
- `Feedback` 加 `user_raw`/`agent_report`/`context` 列（alembic 迁移）；
- 一个 `submit_bug_report` 工具或在反馈端点上扩 `kind=bug` 的结构化提交。

## 9. 价值

- 把用户的模糊抱怨变成**结构化、带技术上下文**的报告，开发可直接动手；
- **咕咕自身的 bug 尤其好找**——它自省刚才的行为往往一眼定位（不复现、零副作用）；
- 不污染用户原话 + 标注推测 → 既拿到分析、又不被咕咕的自信误判带偏排查方向。
