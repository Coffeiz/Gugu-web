## 0. 总纲:借什么 / 不借什么 / 已经更好的别退

| MaiBot 的东西 | 判断 | 理由(一句话) |
|---|---|---|
| **分层记忆(高命中自动注入 / 低命中按需检索)** | ✅ **借(改写)** | 咕咕记忆随量增长会稀释注意力+撑爆预算;这是既定方向(检索系统),不是新坑 |
| **确定性读回(读取端零 LLM 打分选择)** | ✅ 已有,别退 | 咕咕 stance 就是"异步学、build 时零 LLM 点亮",同一哲学 |
| **闭环强化(点亮→回看接住没→强化)** | ✅ **借(换心脏)** | 骨架对,但奖励信号要换成咕咕自己的反馈信号,不是 MaiBot 的 LLM 自评 |
| **学用户不学自己(Expression 排除 SELF)** | ✅ 借(护栏) | 语气镜像/相处镜片若做,"绝不学自己的回声"是硬约束 |
| **纠正级联失效(源事实被推翻→派生内容失效)** | ✅ **借(轻量版)** | 已核实是用户反馈驱动、非时间老化;咕咕缺"源→派生"依赖,只借这一下、砍掉重实现 |
| `reply_effect_judge`(回复后模型自评) | ❌ **不借** | 撞「不要相信自己」;咕咕的"测用户真实反应"是更硬的版本 |
| 多轮 Planner + 选工具与吐正文分两次调用 | ❌ 不借 | 撞「单次调用打完一轮」红线;是咕咕主动选的分歧,不是缺口 |
| `person_profile` 六桶固定 schema | ❌ 不借(可改写) | 撞「Observation 不存 Schema、不 top-down 画表」;至多当读时派生视图 |
| 插件进程隔离 RPC | ⏸ 搁置 | 当前规模过度设计;未来若支持第三方插件再当范式参考 |
| "要不要回复"纯规则门 + idle 退避 | ⏸ 搁置 | 为群聊常驻角色服务;咕咕 1:1 响应式用不上,除非 IM 走群聊 |

下面展开三件:**改进一(记忆分层)**、**改进三(纠正级联,记忆侧的小补丁)**、**改进二(相处镜片,主体)**。

## 改进一:分层记忆检索(记忆侧)

### 结论:不是重构,是升级 `render_facts` 那一步 + 配套 embedding 基建

实读确认咕咕的注入系统**已经具备检索雏形**,不需要推倒:

- `facts.json` 已是结构化存储(每条 `kind/conf/imp/ts`),不是一坨 markdown;
- 已有衰减过滤(`effective = 置信×衰减`,退休低分);
- 已有分层(`facts / daily / memory(长期压缩) / summary`,各自生命周期);
- **`render_facts(facts, query)` 已经在按 query 做相关性挑选**——超 `FACTS_INJECT_MAX=40` 就"重要度保底 + 相关性填充 + 补齐",代码注释自己写着「词法相关性是 v1(无 embedding),后续可换向量」。

### 两处增量(骨架不动)

1. **挑选从词法→语义**:现在相关性用字 bigram Jaccard(词法重叠),"我压力好大"匹配不到"TA 是设计师、赶稿易焦虑"。换成 embedding 向量检索,才能按语义挑对那 40 条。**这是真正的工作量(embedding 管线 + 向量库),但只插进 `render_facts` 的挑选那步,`read_memory`/`_memory_block` 不动。**
2. **按命中率分档**:身份/关系/温度(高命中)继续恒注入;历史情节(低命中)只在语义命中时进。

### 守住的红线

- **不做成 `search_memory` 工具让模型按需调**——那是多一次往返,撞单次调用红线。咕咕的分层是**"更聪明的自动注入"(语义挑对该上桌的)**,不是"按需检索工具"。除非某天愿意为深挖记忆专门破例多一次调用,否则别往工具化走。

### 落地:v1 范围 + embedding 配置解耦 + 重建 job

**现状基线(实查)**:后台**目前零 embedding**——config 无 EmbeddingSettings 段、后端无任何 embedding/cosine 调用,`store.py:177` 只是句占位注释「词法相关性是 v1,后续可换向量」。所以这是**从零新增**,不是改现有。

**规模真相——不需要向量数据库**:咕咕记忆 per-user 隔离,一个用户几十~几百条 facts。几百个向量做相似度 = **Python 里暴力点积排序,微秒级**。**不需要 pgvector / Qdrant / 任何新服务**(需要向量库的前提是跨用户检索或百万级向量,咕咕都不沾)。向量存在每条 fact 旁边即可。所以"embedding 基建"其实是"接个 API + 缓存向量 + 一个 cosine 函数",天数级、非项目级。

**v1 最小范围(4 件就够跑)**:
1. **config pin 一个 embedding 模型**:独立 `EmbeddingSettings` 段(照 `VoiceSettings` 那种"独立模型"写法)+ 连通测试按钮(测通 + 记维度)。⚠️ 加嵌套 config 段要**三处同步**(`apply_override`),否则段静默变 dict/不加载(smtp/voice 踩过)。
2. **反思写 fact 时顺手 embed 并缓存**——在**异步反思里**做,off 热路径;向量随 fact 存。
3. **`render_facts` 里 embed query + 暴力 cosine**,替/补现在的 bigram 词法相关性。
4. **只在 facts 超注入上限(`FACTS_INJECT_MAX=40`)时才启用检索**;轻用户继续全量注入、零成本、零改动。
- 热路径提醒:query 要在 context-build 前 embed 一次(**热路径新增一个快 API 调用**,~几十 ms,远小于 LLM 调用),用"只对超 40 条用户做"兜住。

**embedding 模型必须和聊天模型解耦、单独 pin(最重要,因聊天模型天天切)**:
- `EmbeddingSettings` 独立、稳定、**不进 `pick_model` 路由**——聊天模型怎么 churn(qwen⇄deepseek⇄mimo)都碰不到向量;
- 甚至不用同 provider,按"稳定 + 中文语义好 + 长期有 access"选(`qwen text-embedding-v3` / OpenAI `text-embedding-3`),**pin 死基本一辈子不换**;
- 向量存 `embedding_model + 版本`,能检测过期。**聊天切换 ≠ 触发重建**,两条不相干的线。

**换模型语义 + 重建 job**:向量是模型专属的,换 embedding 模型 = 旧向量**彻底不可比**(不是漂移;同模型内确定性、不漂)。但 **facts 存的是文本 → 向量是可重建缓存、非主数据** → 换模型 = 拿文本重 embed、重建索引,**记忆一条不丢**。重建入口做成后台 job(不是同步清空重灌),四要点:
- **批量、可续跑**(半路挂了别从头/别重复计费);
- **原子切换**:旧索引服务到新索引建好验证再切,别边建边删;
- **版本戳 + 自动检测**:配置一改自动标"stale/需重建"并告警,别指望人记得点;
- **重建期优雅降级**:退回现有 bigram 词法(白捡的安全网),检索不空窗。
- 重建是**罕见应急阀**(只在主动升级 pinned 模型时),不是日常运维。

### 附:facts 内容怎么分类——向量语义位置,不加硬 category 字段

自然会问"facts 能不能按个人习惯/工作/生活分类"。**结论:分类不做成存进 facts 的字段,做成向量之上的读时视图。**

- **别加硬 category**:预定义"个人习惯/工作/生活"桶 = MaiBot 六桶 schema 的缩小版,撞「不存 Schema」红线;且边界糊(健身算习惯还是生活?)、僵(改桶要回炉重分)、有损。
- **向量当底料**:每条 fact 存 embedding,"分类"被"语义相邻/检索"取代——问"工作上怎么样"按语义拉出工作类 facts,不需要谁贴标签;一条"赶稿压力大"可同时靠近"工作"和"情绪",硬分类做不到。
- **要人能读的标签就读时派生**:后台面板/给用户看"咕咕对你的了解 · 工作/生活"时,读的那一刻现聚类 + 现打标,**临时视图不落库**(= 咕咕已有的 trait 读时派生)。
- facts 存储仍是扁平 `{text,kind,conf,imp,ts}` + 向量,`kind/imp/ts` 是认知性质轴,话题分类交给向量语义位置,不新增字段。

### 状态

方向已定,落地路径已清(见上);是**唯一够格现在就排期**的一块——不依赖反馈数据、不依赖改进二三、从零新增但天数级工作量。

**决策(2026-07-03):提前做,定位为「共享 embedding 地基」而非单纯 facts 优化。** 实查 facts 尚未有人超 40 条(facts 检索的收益暂时潜伏),但决定仍先建——因为向量是一层**多消费者的公共基建**:记忆检索(改进一)只是第一个头,相处镜片的"引用哪些记忆更合适"、未来的检索排序/跨记忆语义关联都要靠它。先把原语(config + embed 服务 + cosine 缓存)建好、facts 接第一个头。

承重点 = 选定并 pin 一个**专用 embedding 模型**(与聊天 provider 解耦——当前只配了 minimax 且它在聊天轮换里,不宜复用)+ `EmbeddingSettings` 段(三处同步)+ embed 服务/cosine 通用件 + `render_facts` 暴力 cosine 改造。

## 改进三:纠正级联失效(记忆写协议的小补丁)

> MaiBot 的用户画像有一个咕咕没有的东西:**源事实被推翻 → 建在它上面的派生内容自动失效**。这条**已实读核实**信号来源(见文末调研),值得借,但只借思路、砍掉重实现。

### 核实结论:是用户反馈驱动,不是时间老化

追 MaiBot `is_inactive` 的唯一写入点 + 9 个调用点,给"画像段落打 stale mark → 级联隐藏"的**只有两条路,都是用户驱动**:① 用户对话里说"你记错了/应该是 X" → 12h 异步观察窗 + 关键词预筛 + LLM 纠错分类器 → 自动 forget 那条 relation → 依赖它的画像段落打 `feedback_correction` mark → 级联隐藏(可回滚、留审计);② 用户 WebUI 显式改记忆(`memory_correction`)。**时间老化只改 relation 状态、不打 mark,不发起级联。**

### 咕咕的空缺 = 缺"源→派生"的依赖连接,不是缺检测

咕咕**已有纠错的一半**:`reflection._misperc_llm` 已判"这句是不是纠正",`apply_facts_ops` 已能按纠正 remove/降 conf(facts 带 conf/衰减/可推翻)。**缺的是级联**——咕咕 facts 扁平独立,没有"派生内容依赖哪条源事实"的连接:

- 派生层 = `summary`(World Model)、`daily→memory`(压缩长期叙述)、未来"读时派生的 trait",全是从底层 facts LLM 归纳出来的;
- **纠正一条 fact,facts.json 下轮就对,但 summary/memory 里那句建在旧 fact 上的叙述还在**——要等下次反思重写 summary / compress 重压 memory 才消失,甚至一直留着。

### 借法:轻量版(砍掉 90% 复杂度,拿 80% 价值)

- **别抄重实现**:MaiBot 那套是 9000 行 kernel + relation 图 + stale-mark 表 + 回滚日志,咕咕不需要。
- **轻量做法**:检测到某条 fact 被纠正/删除(misperc 已有) → **把 summary/memory 标脏 → 下次异步反思定向重派生**(而非等自然周期)。在已有异步反思里做,**不碰单次调用红线**。
- **不借它的异步纠错窗 + 关键词预筛**:那是省"每轮跑 LLM"成本的,咕咕反思本就对话后异步跑、`_misperc` 内联判,没在付那笔成本。

### 状态与优先级

**低于改进一、二。** 咕咕派生层本就时间衰减 + 周期重派生,所以这是"纠正后到重派生之间的**延迟**里带旧内容",是弱化版问题、非永久错。定位 = 给记忆写协议加的一块"纠正级联到派生层"补丁,归 [`../11-记忆系统.md`](../11-记忆系统.md) 而非感知。承重点 = 派生层怎么标脏 + 定向重派生的触发粒度(整段重写 vs 只补差)。

## 改进二:相处镜片(⑤ Interaction Preference,行为侧)

> 这是本方案的主体,也是"A(固定应对模式)+ B(每用户学习修改)结合"这个设计意图的落点。

### 2.1 定位:lens 的行为侧孪生 = 固定底座 + 每用户学习叠加

咕咕的 `lens`(解读镜片)已经是"**模块固定、每用户学出叠加层、带置信度/衰减/可推翻**"这个结构——只不过它偏置"怎么**读懂** TA"(感知侧)。**相处镜片 = 把同一机制复制到"怎么**回应** TA"(行为侧)。**

```
固定行为模块(companion.md 等,人人一样,= 底座/全体先验)
        +
每用户相处镜片(学出来的小幅校准,= 偏移/个人后验)
        ↓
   注入时:模块打底,镜片微调(零额外 LLM 调用)
```

- **底座不变** → 咕咕永远是咕咕,身份不漂移;
- **镜片只 nudge** → "对这个用户,companion 里的'先共情'要克制,他爱直接要方案"。

它正好填 [`../10-感知系统.md`](../10-感知系统.md) §3.6 里标着"**growth/companion 档位未做**"的坑:把 ⑤ Interaction Preference 从现在的**手动两维**(`_style_block` 的 reply_tone/reply_length)**进化成学习版**。

### 2.2 结构:因子化 contextual bandit + 全体先验兜底

> **修订(取代早前的 MCTS/分支树设想)**:相处镜片是**单步决策**——`context → 一组 knob 值 → 近即时反馈`,每轮 knob 当轮重新挑、不改变约束下轮的持久状态、奖励基本落在下一轮反馈上。这是 **contextual bandit,不是 MDP**,不需要树搜索的 lookahead。早前把"由粗到细的分支"形式化成 MCTS 是**过度设计**——MCTS 属于 Planner 层(见 §5),不属于 Lens 层。

但"用 contextual bandit"这句还漏一件事:5 个维度铺在**联合动作空间**上是组合爆炸(5 维×3 档 = 243 臂),单用户样本喂不动。解药恰好被"维度间近似独立"这个判断解锁——**用因子化 bandit:每个维度一个小 bandit**(tone-bandit / length-bandit / 举例-bandit…),从同一反馈信号并行更新,各自只 3 个臂。

- **动作空间 = 有界维度**(一组 knob 值,各在 band 内),**不是自由文本策略**——守住"易漂移的 LLM 产出别用 free-text,用枚举"的教训。
- **因子化解样本饥饿**:15 臂 vs 243 臂,天差地别;这才真正接住了最初"分支/省样本"的诉求(要的是省样本,不是树)。
- **不归因**:反馈来了,把当轮**所有激活的维度 bandit** 一起朝奖励更新,让统计在探索里把功劳分匀(= 之前定的 OKR 视角,不做单轮因果归因)。
- **UCB / Thompson 当"比例控制器"**:探索/利用配比不手拍,从每臂"抽过几次、赢面多大"自动导出;探索随置信度收窄、但永不归零(偏好会漂)。
- **全体先验兜底(partial pooling)**:每个维度 bandit 用"大多数用户适用的档位"当先验起点,新用户不从零探索 → **同时解决样本效率和冷启动**(避开纯 B 的鸡生蛋 + 簇碎片)。
- **contextual 保持粗粒度**:context(模块/温度档/工作模式)分桶别太细,否则每桶样本又碎;早期粗桶、以后再上能跨 context 泛化的线性/神经 bandit。

### 2.3 奖励:双时间尺度(快代理驱动生长 / 慢 goal 审计校正)

bandit 要**密集快反馈**才学得动,而真实目标是**稀疏慢信号**——两者冲突,调和点落在咕咕现成的 **温度(快)× 深度(慢)** 分层上:

- **快信号 = 稠密代理**:每轮反馈枚举(顺着聊/改写重问/主动分享…,`reflection._FEEDBACK_ENUM`),喂 bandit 去探索、更新;
- **慢信号 = 审计员**:长程 goal(误读率在不在降 / 我对他的 facts 在被印证还是被推翻 / 主动分享在不在真涨 / **他自己的项目在不在推进**),定期把"快代理赢了但真实目标输了"的配置降权。

**一句话:快信号让镜片学得动,慢信号让镜片不学歪。** 谄媚配置在快信号上刷得再高,一到慢审计就被摁下去——这比单纯"抗刷加权"更根本地治谄媚。**这条"快代理 + 慢 goal 审计"不止属于镜片,应提成跨模块的通用学习框架(见 §5)。**

### 2.4 目标定义:goal = 用户自己声明的目标(抗谄媚 + 抗家长式)

奖励绑长程 goal 才是抗谄媚真解(只盯即时好评必然长成马屁精)。但 goal 里"让用户成为更好的人"**只能 = 用户自己声明的目标,绝不是咕咕的家长式判断**,否则是打着为你好旗号的操纵。

咕咕的产品形态天生有这把尺子:**用户自己定的项目有没有推进、说要做的有没有跟进、回来时是带着进展还是还卡在原地**——这是难以靠拍马屁刷出来的"真变好"信号,也和"更懂用户"(误读率/印证率)一起构成慢 goal。

### 2.5 上限:处处设界

"上限一定要做"这条贯穿全设计,不止一处:

- **维度 band**:每个 knob 只能在底座默认值 ±band 内浮动,镜片**只能 nudge、永不覆盖底座**;
- **探索幅度**:陪伴 agent"故意试个差回应"是拿真实关系当试验田 → 探索只在 band 内小扰动,不大摆(band 一石二鸟:既挡"用力讨好"、又框住探索幅度);
- **每维臂数少 + 最小样本门**:每个维度 bandit 只 2–3 档、够样本才敢偏离先验,防在几条噪声反馈上过拟合;
- **探索永不归零**:用户偏好会漂(心情/阶段),目标是移动的 → 永远留一点轻探索 + 镜片带衰减(老配置淡出)。

### 2.6 与检索耦合

相处镜片不只调语气——它可当**检索排序的一路信号**:"引用哪些记忆更合适"本身就是 read-time 的每用户策略,和改进一的语义检索同层。例:镜片学到"这人爱具体例子" → 检索时该类情节记忆加权。两者共用一个每用户读时策略,不分家。

### 2.7 红线守卫(逐条对账)

| 红线 | 本设计怎么守 |
|---|---|
| 单次调用打完一轮 | 镜片是注入(自动拼进 prompt),零额外调用;不做成按需检索工具 |
| Observation 不存 Schema / 不 top-down 画表 | 镜片只学 **Response Policy**(解释长度/共情程度/主动提问频率/先给方案 vs 先倾听/是否引用旧记忆),**绝不学 Observation**(喜欢猫/容易焦虑/是设计师)。**硬边界**:是关于用户的事实 → 进 facts/Person Model;是"怎么回应"的旋钮 → 进镜片,两边不许串。这条边界就是"不存 Schema"红线在行为侧的具体化,也是保持全系统层不乱的命根子 |
| 假亲密 / 不能设计只能挣 | 镜片是**测出来的**(反馈驱动),不是填的;band + 慢 goal 双重防"用力讨好" |
| 不要相信自己 | 奖励用观测到的用户反应 + 项目进展,不用 LLM 自评 |
| 学用户不学自己 | 反馈只算用户侧反应,绝不把咕咕自己的输出学成偏好 |

## 跨模块:算法归位 + 快慢奖励框架

> 这一节是比"具体用 Bandit 还是 MCTS"更高一层的抽象,是本方案讨论到最后最有长期价值的部分。

### A. 算法归位——每个问题用它最擅长的算法,别为了用某算法把问题复杂化

| 模块 | 更适合的算法 | 前置门槛 |
|---|---|---|
| **相处镜片(回复风格)** | 因子化 contextual bandit(UCB / Thompson) | 反馈信号数据 |
| **记忆检索排序** | embedding 检索 + 学习排序 | embedding 基建 |
| **主动触达策略** | 规划算法(MCTS / tree search) | **用户响应世界模型**(见 C) |
| **长期任务/关系规划** | 规划算法(MCTS / tree search) | 世界模型 + 长程 goal |
| **单次回复生成** | LLM | — |

**判据**:要不要 lookahead/规划,看这个问题是不是"**动作会改变约束未来的状态、且奖励延迟到未来**"。相处镜片不是(当轮重挑、奖励近即时)→ bandit;主动触达是(今天发了改变明天的耐心、奖励在 7 天留存)→ 规划。

### B. 快奖励 + 慢 goal:提成通用学习框架

"快代理让它学得动、慢 goal 让它不学歪"不止属于镜片——**检索排序 / 工具调用 / 项目提醒 / 主动触达 / 长期规划,全都可以套 `Fast Reward + Slow Goal`**。这是比任何具体算法都可复用的抽象。两条让它在每处都安全的纪律:

- **慢 goal 必须锚"用户自己声明的目标"**(项目推进 / 是否越来越依赖工具而非被骚扰),**不是咕咕的家长式判断**——这是全系统抗刷的总闸;
- 它对上咕咕**已有的 温度(快)× 深度(慢)** 双量,不是新引入的哲学,是把已有分层提炼成通用件。

### C. MCTS 的真正归宿 = 主动触达(未来,且卡在一道门上)

主动触达是真序列决策(连发三天烦不烦、今天不打扰是否换来后天主动回来),优化的是"未来 7 天满意度 + 项目推进 + 留存",不是"这条消息有没有回复"。**MCTS 搜"做什么"(今天主动吗/主动什么/何时发/带不带项目/要不要等),LLM 负责"说什么"**——责任分层干净,绝不搜索 token 级话术。

**但有一道必须先过的门:MCTS 需要一个"用户响应世界模型" `P(下个状态 | 状态, 动作)`。** AlphaGo 的模拟器是棋规(白送、完美);触达没有棋规,得从**稀疏、非平稳的单用户数据**里学"提醒一次→他烦的概率"。没有它,MCTS 就是在搜一棵**脑补的未来树**(= MaiBot"奖励靠脑补"那个病搬到转移模型上,更隐蔽)。所以:

- **触达 v1 不直接上 MCTS**:先用"**带触达历史状态(距上次几天/最近发过啥)的 contextual bandit + 硬冷却启发式**",廉价吃下大部分序列性;
- 等攒出**被验证过的用户响应模型**,再把 MCTS 放到 **Planner 层**跑真规划;
- **触达的探索成本全系统最高**(回复风格试错顶多一轮尴尬,触达试错 = 静音/卸载)→ population 先验 + 保守探索 + 慢目标(留存)审计在这里是承重墙,不是可选项。"天天发→回复率涨→模型觉得成功→一周后被静音"就是慢目标审计存在的全部理由。

## 3. 待拍板的决策点(定了才升级成正式 proposal)

承重点已从"归因怎么算"(讨论中溶掉了——用优化视角,不需单轮因果归因)转移到下面这些:

1. **奖励函数**:快代理具体收哪些信号、抗刷权重(建议"主动分享/顺着聊" > "确认夸赞",因夸赞易刷);慢 goal 具体由哪几个量合成、审计怎么给分支降权。**这是现在最承重的一格。**
2. **维度清单 + 每维 band**:⑤ 现在只有 reply_tone/reply_length 两维;要加哪些(共情浓度 / 给方案 vs 倾听 / 话痨度 / 正式度…),各自 band 多宽。
3. **bandit 算法参数**:UCB 常数 / Thompson 先验、每维臂数与档位、最小样本门、探索衰减曲线、先验(全体)怎么估。
4. **四方优先级**:`lens` / `温度定档` / **手动 reply_tone** / `相处镜片` 冲突时谁盖谁——这是唯一还没拍、又必须先拍的点(手动设置该不该永远压过学习结果?)。
5. **contextual 粒度**:每模块一棵树,还是几个模块共享。
