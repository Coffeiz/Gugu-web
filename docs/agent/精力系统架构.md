# 精力系统架构

> 「精力」是咕咕对用户暴露的说法，内部实质是 **Token 用量配额**。每个用户有 **6 小时**和**每周**两道固定窗口的 Token 上限，窗口内累计用量达到上限即 **硬拦**——直接回一句「咕咕累了，休息会儿再来」，不再启动本轮生成。

---

## 易读概述

**解决什么问题**：咕咕每次回复都要调用大模型，而大模型是要花钱的（按 Token 计费）。如果不设上限，单个用户理论上可以无限制地聊、无限制地消耗成本。「精力系统」就是给每个用户设一个用量天花板，防止成本失控，也让"资源分配"这件事对用户可感知——用户在 App 里看到的是一根「精力条」，而不是冷冰冰的用量数字。

**大致怎么运作**：
- 每个用户有两道配额："6 小时内能用多少"和"这一周能用多少"，两者独立计算，任一道顶到线都会被拦下来。
- 这两道配额不是"用了之后慢慢回血"的滑动条，而是**整点清零**的固定窗口——比如 6 小时窗口是每天 0 点、6 点、12 点、18 点这几个整点重置；一到点，之前用了多少全部清零重新开始。
- 用户在网页/App 上能看到自己的精力条：用了多少、上限多少、大概什么时候恢复。
- 一旦某个窗口的额度用完，咕咕不会含糊其辞地"变笨"或者"部分功能不可用"，而是干脆利落地告诉用户"我累了，休息一下"，不会再启动这一轮的思考和回复——避免那种「限额好像生效了又好像没生效」的模糊体验（这套系统历史上确实有过这样一版"软降级"设计，后来被推翻，详见后文）。
- 目前配额判定对**网页对话**和 **IM 渠道（飞书/QQ/微信等）** 都会生效，两边走同一套判定逻辑，口径一致。

**不懂代码的读者可以先记住三件事**：① 精力条清零是"整点重置"，不是"歇会儿就回血"；② 精力耗尽后聊天/问问题也会被拦，不是只挡"重操作"；③ 单个用户可以被单独设置更高或更低的上限，管理员在后台能调。

## 专业细节

### 〇 一图速览

```
对话请求 → stream()              生成结束 → 记账
  │                                │
  ├─ 查 User.token_limit_6h/weekly ├─ core 拿 usage（_usage 事件）
  ├─ 算固定窗口起点（6h 整点/周一） ├─ web 累计 usage_tokens
  ├─ Σ(AgentUsage 窗口内 in+out)   └─ cap_usage 按剩余封顶后写（顶过线只记填满；满则跳过）
  └─ used ≥ limit ?
        ├─ 是 → 硬拦：回「咕咕累了，休息会儿再来」+ 持久化 + return（不生成）
        └─ 否 → 正常启动 _generate
```

闭环：**用量记账**（写 `AgentUsage`）↔ **配额判定**（读 `AgentUsage` 求和）。两端都按「固定窗口起点之后的累计」算，非滑动窗口。

---

### 一 数据模型

**`User`**（`backend/app/models/__init__.py`）
| 字段 | 含义 |
|---|---|
| `token_limit_6h` | 该用户 6 小时窗口 Token 上限。`None` = 不单独限制（回退全局默认） |
| `token_limit_weekly` | 每周窗口上限，同上 |
| `token_limit_monthly` | **预留字段，当前判定逻辑未接入**（既不参与判定也无默认值） |

`None`/未设 → 回退到全局默认值；判定时 `limit = user.token_limit_6h or default_6h`（注意 `0` 会被 `or` 当成"未设"而回退默认，要"完全禁用"应给极小正数如 `1`）。

**`AgentUsage`**（每轮对话一条计费记录）
`user_id` · `session_id`（会话被删则置 `None` 保账） · `tokens_in` · `tokens_out` · `model` · `provider` · `tools_used` · `created_at`

用量 = 某窗口起点之后所有记录的 `Σ(tokens_in + tokens_out)`。

**全局默认**（`QuotaSettings` @ `backend/app/core/config.py`）
| 字段 | 默认 | 说明 |
|---|---|---|
| `default_token_limit_6h` | `None` | 全局 6h 上限，`None` = 不限制 |
| `default_token_limit_weekly` | `None` | 全局每周上限，`None` = 不限制 |

可被运行时 override 覆盖（`AppSettings` 的 `quota` 段，`config.py` 合并逻辑）。

---

### 二 用量记账（写入链路）

1. **拿 usage**（`backend/agent/core.py`，双 API 路径各一处）：
   - Anthropic 路径：累计 `final.usage.input_tokens / output_tokens`（含 `cache_read_input_tokens`）。
   - OpenAI 兼容路径：请求带 `stream_options={"include_usage": True}`，累计 `chunk.usage.prompt_tokens / completion_tokens`。
   - 生成收尾 `yield {'type': '_usage', 'input': ..., 'output': ...}`。
2. **累计**（`web.py` `_generate`）：消费 `_usage` 事件，写入本轮 `usage_tokens`。
3. **落库**（`web.py` 持久化段）：`if usage_tokens["input"] or usage_tokens["output"]` → `db.add(AgentUsage(...))`。会话在生成期间被删 → `session_id=None` 仍记账（与 FK `SET NULL` 一致）。

> ⚠️ 若某模型流式不返回 usage（OpenAI 兼容端点未开 `include_usage` 等），`usage_tokens` 恒 0 → `AgentUsage` 不记 → 用量永远算 0 → **配额永不触发**。这是排查"限额不生效"的第一嫌疑点。

---

### 三 配额判定与硬拦（核心）

判定逻辑集中在 `backend/agent/quota.py`：`is_exhausted()`（是否耗尽，供硬拦判定）+ `cap_usage()`（记账时封顶/冻结）。两个入口共用它：
- **网页对话**：`backend/agent/adapters/web.py` 的 `stream()`，在创建会话、存用户消息**之后**、启动 `_generate` **之前**判定（`quota.is_exhausted`）。
- **非流式路径（IM / 定时任务）**：`backend/agent/runner.py`，同样在用户消息落库之后、真正生成之前调用 `quota.is_exhausted`，耗尽则直接返回「咕咕累了，休息会儿再来～」，不启动生成。**这一点是本次核实时更新的**——历史上（见 §七）IM 渠道不经过此判定，现在 `runner.py` 已经接入同一套 `quota` 模块，两条路径口径一致（详见 §七"作用范围"的更正）。

### 固定窗口（非滑动，本地时区整点）

窗口计算在 `agent/quota.py` 的 `six_h_window_start()` / `_week_start()`：
- **6h 窗口**：每天 `00:00 / 06:00 / 12:00 / 18:00` **本地时区**（`app.core.tz.LOCAL_TZ`）整点为起点，内部换算成 UTC naive datetime 存取。
  `win_local = now_local.replace(hour=(now_local.hour // 6) * 6, minute=0, second=0)`
- **周窗口**：本周一 `00:00` **本地时区**起点，同样换算成 UTC naive 存取。
  `wl = (nl - timedelta(days=nl.weekday())).replace(hour=0, ...)`

> **核实更正**：旧版文档在此处写的是「UTC 整点」，但代码实际按 `LOCAL_TZ`（本地时区）取整点、再转换成 UTC naive 存取比较。窗口的“换日/换周边界”是按本地时间算的，不是 UTC 时间——这会影响“几点重置”的直觉判断，容易被文档误导为国际标准时的整点。

### 判定
```
limit_6h = user.token_limit_6h or default_6h
if limit_6h is not None and used(win_6h) >= limit_6h:
    quota_exceeded, reset_at = True, win_6h + 6h
# 6h 没超才看周窗口；任一超即拦，reset 取先耗尽那档
if not quota_exceeded and limit_week is not None and used(week_start) >= limit_week:
    quota_exceeded, reset_at = True, week_start + 7d
```

### 硬拦行为（2026-06-27 起）
`quota_exceeded` → **不启动生成**，直接：
1. 持久化一条 assistant 消息「咕咕累了，休息会儿再来～」；
2. 经 `genstream.typed_stream(msg)` **逐字** yield `token` 事件 → 复用前端对 token 流的现成渲染，做出咕咕「打字」的 SSE 动画；末尾 `done`、`return`。

> `typed_stream` 是放在 `agent/genstream.py` 的**全局可复用** helper——任何系统侧"主动让咕咕逐字说一句"的场景都能 `async for line in genstream.typed_stream(text): yield line`，统一动画口径。

**聊天、查询一律不放行**——这是与旧"软降级"的根本区别（见 §七）。

### 封顶 + 满额冻结记账（`agent/quota.py` 的 `cap_usage`）
记账前用 `quota.cap_usage(db, user_id, settings, tin, tout)` 按 **6h 剩余额度封顶**本轮用量：
- **顶过线**（单轮对话很长、会把 6h 用量推过上限）→ 只记「填满到上限」的部分，**超出（对话后半段）的 token 丢弃**，精力条最多 100%、不越线；
- **已满**（剩余 ≤ 0）→ 返回 `(0, 0)`，本轮不写 `AgentUsage`（冻结）；
- **无上限** → 原样记。

被封顶 / 冻结掉的 token **既不计 6h 也不计周**（周同按 `AgentUsage` 求和）。两处记账都接：
- **网页流式** `web.py _generate`；
- **非流式** `runner.py`（IM、定时任务等路径）——满额后同样封顶 / 冻结，**不污染周精力**。

窗口整点重置后 `used` 归零，自动恢复满额记账。

**踩坑记录**（`cap_usage` 的取舍理由）：封顶不按比例缩放，而是"tin 优先、余量给 tout"精确填满剩余额度。原因：比例缩的 `int()` 在 `remaining` 很小、token 很大时会截断到 0（如 `limit=1`），导致 `used` 永远是 0、cap 永远填不满，硬拦的 `used>=limit` 永不触发——精力条显示 100% 却能一直聊下去的 bug 根因。

---

### 四 恢复机制

固定窗口、**整点清零**，不是"用掉后等 N 小时滑动恢复"：

- 6h 配额在下一个 6 小时整点（本地时区 00/06/12/18）归零；
- 周配额在下周一 00:00（本地时区）归零。

恢复 = 到下一个窗口整点（而非固定 6 小时）；整点一到，配额归零、记账解冻同时发生。

### 五 前端展示

- **接口**：`GET /api/v1/auth/quota`（`backend/app/api/v1/auth.py`）返回
  `used_6h / limit_6h / reset_6h_at / used_weekly / limit_weekly`，`reset_6h_at` 即下次清零时刻。
- **UI**：`frontend/src/components/common/ProfileModal.vue` 的「精力」区——进度条 `used_6h / limit_6h`、百分比、`limit_6h` 为空时显示「不限」，并据 `reset_6h_at` 文案化「X 后恢复精力 / 精力充沛」。
- 展示是**只读**的；改限额不在此处（见 §六）。

### 六 配置与运维

- **给单个用户限额**：改其 `User.token_limit_6h / token_limit_weekly`（DB 或后台用户管理）。单位是 **Token 数**。要近乎"立即触发"可设很小的正数（如 `1`）；设 `None` = 用全局默认；注意别设 `0`（会被回退成默认）。
- **改全局默认**：`config.py` 的 `QuotaSettings` 或运行时 `quota` override。
- **重启**：网页判定逻辑在 `web.py`，IM/定时任务判定逻辑在 `runner.py`；`agent/quota.py` 改了两边都要重启对应服务（`gugu-backend` / `gugu-worker`，参见 [`agent-im接入架构.md`](agent-im接入架构.md) §10）。dev 下 scp 即热重载生效。

### 七 边界与历史

- **历史变更（2026-06-27）**：原先是**软降级**——配额耗尽设 `degraded=True`，只把工具砍到只读（`light_tool_names`）并让咕咕婉拒「创建/修改/删除/整理文件/生成文档/联网搜索」等重操作，**聊天/查询照常**。表现为"限额好像没生效（其实只挡重活）"+ 重操作时偶发空气泡。现已整体替换为 **硬拦**，`degraded` / `light_tool_names` / `READ_ONLY_TOOLS` 一并移除。
- **作用范围（本次核实已更正）**：旧版文档在此处写的是"该配额只在网页对话路径生效，IM 渠道（飞书/QQ，走 `gugu-worker`）不经过此判定"——**这个说法已经过时**。核实代码（`agent/runner.py` 第 224 行）发现 `runner.py` 现在同样调用 `quota.is_exhausted` 做硬拦判定，`web.py` 和 `runner.py` 两处的判定注释也互相印证（均写明"与 IM/定时任务 runner 同口径"）。也就是说，**目前网页对话和 IM/定时任务共用同一套精力判定，口径一致**，耗尽后两边都会被硬拦、都不再生成。此前的"IM 不受限"是历史状态，已被后续改动取代，若仍看到旧描述属于文档滞后，本次已修正。
- **跨线那条封顶**：判定基于**已落库**的 `AgentUsage`，本轮 Token 等生成结束才记账。把额度顶过线的那一轮仍会放行生成，但记账时由 `cap_usage` **封顶到填满上限**（超出丢弃），精力条停在 100% 不越线；下一轮起被硬拦、记账冻结（§三）。
- **`token_limit_monthly`**：模型里有字段，判定与默认值都未接入，属预留。
- **空 usage 即失效**：见 §二末的警告——用量统计断了，配额形同虚设。
