# 时区与统一时钟迁移方案

> 日期:2026-07-11 · 对应 [代码审查-GPT复审核实版-2026-07-10.md](../security/代码审查-GPT复审核实版-2026-07-10.md) 的 **P1-c**。
> 状态:方案(未执行)。这是一次跨切迁移,不是快改——本文把它拆成可分批、可回滚的阶段。

## 0. 一句话

**存储一律 aware UTC;"展示"与"日期归属"在边界按用户时区换算;`utcnow()` 收敛成单一时钟出口。**
当前离这个目标有三道坎,按下面阶段推进,**新代码即刻走统一时钟先止血**。

## 1. 现状核实(2026-07-11)

| 事实 | 数据 | 影响 |
|------|------|------|
| DateTime 列**全是 naive** | `app/models/__init__.py` 42 列,`timezone=True` 0 列 | 迁 aware 要改列类型 + 迁移 + 修所有 aware/naive 比较点 |
| **无用户时区字段** | `User` 上搜不到 timezone/tz/utc_offset | "展示按用户时区"**当前做不了**,是前置条件 |
| `datetime.utcnow()` 散落 | 后端 55 处,业务路由直调(如 `mind.py` captured_at) | 无单一时钟出口,迁移时要逐处找 |
| 前端不用 dayjs | `dayjs` 0 处引用,日期逻辑散在组件(原生 Date) | 日期归属无纯函数出口,难测、难统一 |

**这个 bug 长什么样**:naive-UTC 算出来的"今天"边界是 UTC 零点,不是用户本地零点。UTC+8 的用户在本地 0:00–8:00 之间,"今天/明天/本周"会整体错一天——截止日、日历归属、"未来日期"判断在午夜附近全飘。

## 2. 目标模型

- **存储**:所有时间列 `DateTime(timezone=True)`(Postgres `timestamptz`),值为 aware UTC。现有 naive 值**本就是 UTC**,迁移时贴上 UTC tzinfo 即可,无数据语义变化。
- **运算**:后端一律在 UTC 下比较/加减,用统一时钟 `now_utc()`(aware)。
- **边界换算**:只有两处碰用户时区——① **展示**(给前端的可读时间/相对时间);② **日期归属**("这条属于哪一天""是不是今天/本周""截止日")。这两处走**单一出口**,不散落。
- **用户时区来源**:`User.timezone`(IANA,如 `Asia/Shanghai`);首次登录用浏览器 `Intl.DateTimeFormat().resolvedOptions().timeZone` 探测并写入,设置页可改;缺失回退服务端默认(记一条,别静默当 UTC)。

## 4. 风险与回滚

- **最大坑:aware/naive 混比 TypeError**。缓解:Phase 1 先收敛出口(过渡返 naive)、Phase 2 一把翻 aware + 全量测试;别在中间态零散引入 aware。
- **列迁移**:`timestamp → timestamptz` 在 Postgres 是安全的(带 `USING ... AT TIME ZONE 'UTC'`),可逆(反向 `AT TIME ZONE 'UTC'` 回 naive)。上线前本地 + devserver 各 `alembic upgrade head` 跑一遍。
- **无用户时区的老用户**:Phase 0 前 / 探测失败时,回退服务端默认时区并**记一条 warning**,不静默当 UTC(否则又是隐性错一天)。
- **分批可停**:Phase 0/1 落地后即便不继续,也已"止血"(单一时钟出口 + 用户时区就位);Phase 2/3 才是真正修好归属。

## 5. 建议执行顺序

Phase 0(用户时区字段)→ Phase 1(统一时钟出口,过渡 naive)→ Phase 2(列迁 aware + 翻真时钟)→ Phase 3(日期归属出口 + 接敏感点,先协调并发改动)→ Phase 4(收口)。
Phase 3 的前端 `dateAttribution.ts` 纯函数可**提前独立落地 + 测试**(不依赖后端迁移),作为 P1-a 测试的延伸。
