# 全仓变异测试分阶段执行计划

- 日期：2026-10-12
- 状态：计划待执行
- 目标：在一个质量周期内，对仓库第一方 Python 与 TypeScript/Vue 生产源码完成一次可追溯的全范围变异测试。
- 执行约束：devserver 测试进程最多使用 2 核、2 GiB 内存，不使用 swap；分批、低优先级运行，不因排期而跳过未完成的变异。
- 自动化边界：仅手动运行，不接入 CI，不改变现有 CI 门禁。

## 1. 已知基线与估时

- 最新全量 CRAP 扫描报告识别 4,583 个函数，其中高风险 467 个、中风险 372 个。高风险项集中于 Agent loop/gateway/IM、文件预览与同步、终端、画布批操作和 RAG。详见 [`2026-10-12-CRAP-AND-MUTATION-ANALYSIS.md`](../reports/2026-10-12-CRAP-AND-MUTATION-ANALYSIS.md)。
- 前端 Vitest 最近一次完整运行 754/754 通过。后端完整 pytest 曾有 4,396 项通过、20 项失败；修正测试隔离后，原失败的 20 项定向复测通过，但完整后端套件还需在正式变异前重跑。
- 全前端 Stryker 曾扫描到约 68,712 个候选变异；该次在启动检查阶段因 devserver 负载而中止，没有变异得分。
- 受限资源 Python 试跑覆盖登记的 7 个目标：60 个变异全部 killed，耗时约 132 秒，最大内存设限为 2 GiB。结果见 [`2026-10-12-DEVSERVER-MUTATION-2C2G-SMALL.md`](../reports/2026-10-12-DEVSERVER-MUTATION-2C2G-SMALL.md)。
- 预计需要 4–7 个日历日的分阶段执行时间；这是粗略估计，不是截止时间。前端候选数量明确，后端全范围变异数尚未测量。第一阶段先测量实际候选数和每批吞吐，再更新剩余时间估计。

## 2. 范围

覆盖 `backend/agent`、`backend/app` 和 `frontend/src` 中仓库维护的第一方可执行生产代码。每个变异必须关联到能验证其行为的测试；对跨模块契约保留少量集成测试。

排除编译产物、打包输出、第三方/vendor 代码、静态图片/字体、生成代码和纯数据文件。依赖真实模型、第三方 IM、网络或容器的代码仍纳入范围，但用 mock/fake 隔离外部副作用；不得访问真实账号、用户数据、生产数据库或真实外部服务。任何排除项都要在最终清单中写明理由。

全仓范围超出现有 `scripts/quality/mutation_scope.json` 的登记范围。正式执行前需要：

1. 更新 PRD-TEST-2，注明这是一次周期性的全范围审查，不改变“手动运行、不接 CI”的策略。
2. 建立按阶段可单独调用的 scope/config 和报告目录，保持源码到测试的映射明确；不覆盖或混淆既有 Phase 2 基线报告。
3. 对新增执行配置做独立检查，确认候选范围、测试过滤、超时分类和报告汇总没有漏计。

## 3. 阶段与顺序

阶段按依赖顺序单批执行，同一时间不并发启动多个变异器。首日阶段 0 完成后，以实际候选数细化各阶段耗时。

| 阶段 | 功能区与主要源码范围 | 优先行为 | 完成产物 |
|---|---|---|---|
| 0. 基线与范围校准 | 全部登记源码；完整 pytest、Vitest；每个阶段的模块—测试映射 | 确认普通测试基线、扫描目标数、工具 dry-run、资源限制与报告拆分 | 基线报告、纳入/排除清单、各阶段候选数与时间预估 |
| 1. 核心状态与安全 | `backend/app/core`、`app/security`、`agent/security`、`agent/interactions`、对话 pending queue；`frontend/src/utils`、`stores`、`services` | ownership、授权、确认门、脱敏、租约、缓存与更新结算 | Python/前端核心阶段报告 |
| 2. 文件、存储与同步 | `backend/agent/tools/files`、`agent/rag`、`app/services/storage`、`files`、`filesync`、文件预览；前端 Files、files/filesync composables 与组件 | 上传/覆盖/删除、配额、预览、路径归属、同步对账、索引更新 | 文件与同步阶段报告 |
| 3. Agent 与对话运行时 | `backend/agent/context`、`loop`、`gateway`、`run`、`conversation`、`app/services/agent`、流式与会话相关模块 | 输入组装、状态机、取消/续接、队列、工具调用和流结束语义 | Agent/Chat 阶段报告；重点审查最高 CRAP 项 |
| 4. IM、记忆与计划任务 | `backend/agent/im`、`memory`、`backend/app/scheduled_tasks.py` 及提醒/任务服务；前端 Schedules、Calendar 相关功能 | 消息确认与重试、平台适配、记忆读写、重复任务、时间边界 | IM/任务阶段报告；外部平台只用 mock |
| 5. 项目、画布与协作 | `backend/app/services/canvas`、项目和数据迁移服务；前端 Projects、Mind、Calendar 中未覆盖页面与交互 | 批量画布操作、项目状态、拖拽/排序、导入导出和状态回调 | 项目与 Mind 阶段报告 |
| 6. 终端、沙盒与管理能力 | `backend/app/api/v1/terminals.py`、`agent/terminal`、`agent/sandbox`、配置/opsmetrics、Admin/MCP/Skills；前端 Terminals、Admin、MCP、Skills | PTY/WebSocket 生命周期、输出队列、权限边界、配置校验、管理接口 | 系统边界阶段报告；不启动真实沙盒或终端服务 |
| 7. 汇总与复核 | 各阶段输出 | surviving、timeout、error、no coverage、not checked 分类；确认等价变异；抽样复跑 | 全量汇总报告、风险与修复建议、资源使用记录 |

如果阶段 0 显示单一阶段仍过大，可按子目录/模块拆批，但保持上表功能边界及每批独立报告。每次只推进一个阶段，允许跨日暂停；下次从最近一个已完成报告继续。

## 4. 资源与隔离

- 每个测试/变异进程放入独立 cgroup v2 scope：`CPUQuota=200%`、`MemoryHigh=1792 MiB`、`MemoryMax=2048 MiB`、`MemorySwapMax=0`。资源属性无法验证时不启动该批。
- Mutmut 子进程最多 2 个；Stryker concurrency 最多 2。若测试阶段内存持续逼近 `MemoryHigh`，先降为 1 个 worker；超过 `MemoryMax` 时保留 OOM/退出分类，缩小该批后再重跑，不提升上限。
- 使用独立临时副本，不在 Mutagen 实时同步目录运行变异，也不将 devserver Git 元数据当作代码基线。副本只复制当前阶段必要源码、测试和质量配置。
- 排除 `.env`、配置覆盖文件、锁文件、数据库、用户数据、上传目录、容器卷和服务日志。不得清理运行配置或持久化数据来腾空间。
- 开始每批前记录负载、可用内存、swap、根分区空间与活动服务；运行中记录 CPU/内存峰值、耗时、退出码。不得为测试停止业务服务或无关进程。
- 阶段完成后保存 JSON/Markdown 报告，再清理该阶段的临时副本和工具缓存；保留历史报告。确认服务仍健康、没有残留测试进程。

## 5. 报告与分类

每个阶段使用独立目录，至少记录：日期、工作文件快照说明、源码范围、测试范围、候选数量、killed、survived、timeout、compile/runtime error、no coverage、equivalent、not checked、运行时间、资源峰值和限制原因。

mutation score 只以 `killed + survived` 为分母。编译错误、运行错误、超时、无覆盖、等价和未检查项分开列出，不得计成 killed。仅在维护者检查行为并记录理由后登记 equivalent。汇总时保留每阶段原始数据，并核对全局总数与阶段合计一致。

## 6. 完成标准

1. 全部纳入范围的生产源码都有变异结果，或有经过审查的排除说明。
2. 所有目标均处于已分类状态；没有把工具未执行、超时或测试基线失败伪装为通过。
3. 完整 pytest 与 Vitest 基线在变异前通过；外部集成使用 mock/fake，未访问真实用户或生产服务。
4. 各阶段与总报告可复核、候选数对账一致，记录资源限制实际生效。
5. surviving 变异按用户风险和 CRAP 排序给出行为测试补强建议；不为提高分数机械改实现。
6. devserver 服务仍健康，临时副本及无用测试进程已清理；不触发 CI，不提交、不推送，除非之后另行要求。

## 7. 主要风险

- 全前端候选规模约 68,712，完整执行可能持续数十小时；后端全量候选数未知，4–7 天估时可能需要上调。
- 2 GiB 上限下，Stryker 全量初始化/编译阶段可能超过内存高水位或被 cgroup 终止。若连续两批在启动阶段 OOM，应缩小模块批次并记录，不绕过硬上限。
- 大型模块的测试发现可能不完整或依赖静态源码检查；正式变异前需验证 runner 的 test filtering。过滤测试必须保证相关测试能运行，不能为缩时而静默跳过边界行为。
- 多阶段报告增加汇总和状态追踪成本；以统一 JSON schema、固定阶段 ID 和候选对账避免重复/漏算。
