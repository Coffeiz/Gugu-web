# QQ 与飞书流式功能误删恢复

## 现象

QQ 个人设置中没有“私聊流式回复”开关，QQ 私聊不再实时输出；飞书也从流式卡片退化为等待完整回复后发送。检查后发现这不是单一 UI 回归，而是一次功能整理时删除了整条能力链路。

## 根因

历史提交 `745b2b09d` 删除了飞书 `CardKit` 流式实现、QQ `QQPrivateTextStream`、`runner.run_stream` 以及相关出站适配代码。随后 IM 主循环统一改成 `run_collect`，所有平台都等待完整响应。

QQ 私聊流式开关还被迁移 `20260829000001_remove_qq_private_streaming` 从数据库删除，同时个人设置 API、前端字段和 `message_format` 的读取函数也被移除。结果是：即使恢复发送器，运行时仍没有可配置的开关，且读取路径会引用不存在的函数。

## 修复

- 恢复 QQ `stream_messages` 发送器和飞书 CardKit 流式卡片。
- 恢复 `runner.run_stream` 和 IM Loop 的平台流式分支。
- 增加 `round_end` 流事件：QQ 每个工具 round 结束当前消息，再创建下一条继续流式输出。
- 恢复 QQ 私聊流式开关的数据库模型、API 读写和个人设置 UI。
- 新增迁移 `20260831000003_restore_qq_private_streaming`，默认关闭，不修改旧迁移历史。
- 保留交互确认场景的非流式降级，避免流消息未结束时按钮无法展示。
- 修复恢复代码中残留的 `meta` 死引用，并清理恢复过程中误带入的重复出站函数。

## 验证

- Python 语法检查通过。
- 前端 `vue-tsc --noEmit` 通过。
- QQ、飞书、IM 出站定向测试通过，最终为 `44 passed`。
- 重复顶层函数/类定义检查通过。

## 经验与约束

删除或合并疑似冲突功能前，必须先列出受影响的完整链路：数据库字段与迁移、API schema、前端设置、运行时读取、出站适配器、测试和文档。必须明确告知用户“会删除什么、会保留什么、是否影响已有配置和数据”，得到确认后再删除；如果只是职责冲突，应优先统一入口而不是删除能力实现。
