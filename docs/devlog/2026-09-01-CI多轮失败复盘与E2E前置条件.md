# CI 多轮失败复盘与 E2E 前置条件

## 背景

2026-09-01，`dev` 分支连续多轮 CI 失败。问题不是单一回归，而是构建链、测试环境和测试用例与当前实现依次暴露出来。最后在 `e905483e7` 后 CI 全部通过。

这次排查的关键原则是：每次只处理当前已被日志证明的问题，不把环境失败、代码失败和测试失配混为一谈。

## 失败演化

### 1. 生产前端镜像仍解析本地 Runtime

生产 Docker 构建使用 `frontend/Dockerfile.prod`，镜像上下文没有 sibling Runtime，但 Vite 仍解析到 `../../gugu-interaction-runtime`。生产路径最终固定使用 npm 包，只有 `VITE_USE_LOCAL_RUNTIME=1` 的集成测试才启用本地 Runtime alias。

### 2. LoopScope package build 把测试源码编进去了

`loopscope/packages/storage` 的构建配置包含 `src/**/*.ts`，同时收集了测试文件，导致测试 fixture 路径缺失时 package build 失败。构建配置排除 `*.test.ts` 和 `*.spec.ts` 后恢复正常。

### 3. Runtime checkout 与 RAG worker

Runtime checkout 曾因私有仓库认证失败；Runtime 公开后移除不必要的 token 依赖。随后后端测试暴露 RAG worker 的 native 依赖解析问题，补充 worker 可运行依赖路径并让完整 pytest 通过。

以后构建 worker 后应增加独立 smoke gate：启动 worker，发送最小 tokenize/BM25 请求，确认 worker 真正可用后再进入完整 pytest。

### 4. 前端语言环境与登录引导

E2E runner 默认语言曾使页面渲染为英文，而用例使用中文选择器，导致大量用例在登录后页面阶段失败。Playwright 固定使用 `zh-CN`，登录 setup 等待 onboarding 状态请求完成并关闭首次设置引导后，主要路径恢复。

### 5. 测试与当前组件实现失配

后续日志显示，部分测试本身已经落后于实现：

- GuguChat 输入框已由 `textarea` 改为 Tiptap 的 `.chat-input-editor .ProseMirror`；
- 文件删除已接入统一确认弹窗，测试需要明确点击确认；
- 日历编辑弹窗类名已由 `.eem-floating` 改为 `.eem-popup`；
- 终端测试在页面导航前读取 `localStorage`，在 `about:blank` 上触发 SecurityError。

这些属于测试边界问题，不能通过放宽断言或增加等待时间掩盖。

### 6. 二分阶段暴露的严格类型与日历时序问题

在回到二分基准 head 后，Frontend strict check 暴露 `auth.ts` 中异步赋值后的可空类型问题，改为先解析并保存局部 `nextUser` 再写入 store。

日历用例依赖月格的即时布局判断活动是否可见。活动数据加载和“更多”布局存在时序变化，因此改用活动加载后始终存在的侧栏活动项作为编辑入口。

### 7. 终端 E2E 的 Sandbox 前置条件

交互式终端创建会经过 `page_access()`，要求 Shell 开启且 Docker sandbox runtime ready。CI 的 Runtime integration 只启动 PostgreSQL、Redis 和应用，没有提供 sandboxd、Rootless Docker 及固定沙盒镜像，因此接口返回 403 是符合权限策略的结果，不是终端 API 回归。

在 CI 具备完整 Sandbox 基础设施前，终端用例不应放在 stable E2E 清单中；完整 `playwright test` 仍保留该用例，供已配置 Sandbox 的环境运行。

## 最终改动

- 修复前端严格类型错误。
- 稳定日历活动编辑 E2E 入口。
- 使 stable E2E 只包含当前 CI 能提供基础设施并且可确定运行的路径。
- 保留完整 E2E 对终端能力的覆盖，避免把未具备环境条件误判为产品通过。

## 排查清单

以后遇到 CI 红灯，按以下顺序检查：

1. 先确认失败 workflow、job、head SHA 和失败步骤，避免看旧 run。
2. 区分构建、类型检查、后端测试、E2E 和基础设施失败。
3. 对 E2E 先读取 error context 和 screenshot，再检查 selector 是否仍存在于当前组件。
4. 对页面内 `evaluate` 检查是否已经导航到同源页面，尤其是 `localStorage` 和 `fetch`。
5. 对 Sandbox、Runtime、LoopScope 等外部依赖确认服务、权限、固定镜像和 socket 是否真的存在。
6. 构建产物通过不代表运行时可用；worker、Runtime 和 Sandbox 都需要最小启动 smoke gate。
7. 修复后同时运行对应本地 typecheck、测试收集或可执行测试，并记录无法本地复现的环境条件。

## 验证结果

最终远端 CI 在 `e905483e7` 后通过：Docker release、Backend、Frontend、Runtime、LoopScope 和 stable E2E 均为绿色。前端本地 `typecheck`、`typecheck:strict`、Playwright 用例收集和 `git diff --check` 也通过。
