# 咕咕邮件设计标准 Phase 3：定时任务与可观测性

日期：2026-09-02

## 结果

- 定时任务新增 `email` 投递渠道，收件人固定解析为当前用户注册邮箱。
- 定时邮件使用服务端 `reminder` 模板，并读取用户已保存的主题模式和配色；模板传入 `title`、`preheader` 和 `sections`，正文仍保留纯文本 fallback。
- 页面创建并授权的定时任务沿用 `authorized_tools` 规则，不在执行阶段重复触发邮件确认门。
- SMTP 发送结果按日汇总到 `ops:email:YYYYMMDD`，只记录调用数、成功/失败数、耗时和错误码。Admin 的 `/admin/ops/summary` 通过 `email_delivery` 返回这些数据，不记录邮箱、主题或正文。

## 失败与重试边界

SMTP 发送不是本实现可以安全假设幂等的操作，因此定时投递层不自动重试。一次性任务发送失败会保留任务并标记失败，用户可以从任务面板手动再次执行；周期任务本轮失败后等待下一次计划触发。Agent 执行阶段已有的无副作用 schema 重试仍属于模型执行重试，不会重发已进入 SMTP 投递的邮件。

## 验证

- 定时投递成功时只调用一次邮件发送入口，并报告 `邮件：已发送`。
- SMTP 超时或失败时返回脱敏错误码，`_delivery_succeeded()` 不会把一次性任务误判为成功。
- 后端相关测试覆盖邮件渠道成功、失败和不重试边界；模板与邮件工具测试继续覆盖既有 Phase 1～2 行为。
