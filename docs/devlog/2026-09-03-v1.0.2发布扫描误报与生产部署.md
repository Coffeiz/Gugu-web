## 弹窗进场动画修复

问题：所有 BaseModal 弹窗（含 bm-card 双栏弹窗）打开时第一帧就出现实心底色块，内容再淡入；离场是整卡 opacity 淡出所以正常。

排查：浏览器逐帧探针（MutationObserver + rAF 采样 computed style）显示两种弹窗第一帧 `.bm-card::after` 遮罩（veil，`background: var(--panel-bg)`）都是 opacity 1 实心，玻璃 ramp（blur/背景色渐变）只是内部机制，整体从未淡入。

修复：进场照搬离场——`.bm-enter-from .bm-card { opacity: 0 }` 整卡淡入。两个关键点：

1. opacity 加在 `.bm-card` 自身而不是 `.bm-center`：元素自身的 opacity 不影响它自己的 backdrop-filter，卡片毛玻璃全程仍采样页面；被隔离的只有卡内面板，由仍在进行的玻璃 ramp 盖住。
2. `transition` 简写必须把 `background-color`/`backdrop-filter` 一起写全，否则会覆盖 global.css 给 `.bm-card` 的 blur ramp 过渡，blur 第一帧直接跳满值。

验证：探针逐帧 opacity 0→1 平滑（240ms），veil 1→0、blur 0→20px 同步；`test:css-glass`、`test:ui-dialogs` 回归通过。

## 发布扫描四连败复盘

v1.0.2 tag 的「Publish GHCR and Docker Hub release」连续失败四次，前三次都报同样的两个 HIGH：msgpack 1.1.2（GHSA-6v7p-g79w-8964）与 setuptools 70.3.0（CVE-2025-47273）。而镜像真实安装版本是 1.2.2/84.0.0（requirements 固定 + Dockerfile 内 force-reinstall + importlib.metadata 构建断言，任何一处不符构建直接失败）。

前两轮修复方向错误：

- PR #38：去掉 buildx `sbom: true`（怀疑 gha cache 缓存了过期 SBOM attestation）——无效。
- PR #39：安全门前移到 build job，`load: true` 扫本地镜像——**本地镜像扫描仍报旧版本**，排除 registry referrer/SBOM 关联理论。

第三轮在 devserver 从源码现场构建同版本镜像（完全脱离 gha cache），逐层检查文件系统：全盘只有 `msgpack-1.2.2.dist-info` 和 `setuptools-84.0.0.dist-info`，没有任何文件声明旧版本。但 trivy 日志里有三个此前被忽略的特征：

- `Number of language-specific files num=1`（语言专用清单文件，不是 dist-info）
- 漏洞目标名是裸的 "Python"（不是某个 METADATA 路径）
- 警告 "Third-party SBOM may lead to inaccurate vulnerability detection"

最终定位：**pip 包自带的 vendored CycloneDX SBOM `/usr/local/lib/python3.14/site-packages/pip/_vendor/bom.cdx.json`**。解析该文件确认里面记录的是 pip 内部依赖 msgpack 1.1.2、setuptools 70.3.0——与 trivy 漏洞表的 installed version 逐字一致。trivy 扫镜像时把它当应用依赖清单解析成 python-pkg 目标，pip 自己的 vendored 版本被报成应用漏洞。

修复（PR #41）：trivy 扫描步骤加 `skip-files` 跳过该文件。第四次发布全绿。

教训：

1. trivy 报的 installed version 与镜像 dist-info 不一致时，优先怀疑语言清单类文件（CycloneDX/SPDX/lockfile），而不是缓存或 registry 元数据。
2. 静态推理连续三轮全错（缓存、attestation、referrer），最后靠「现场构建 + 直接看文件系统」一步实锤——早该这么干。
3. devserver 是现成的排障环境：架构与生产一致（amd64）、无需装任何工具（trivy 用 `aquasec/trivy` 容器跑）、源码由 Mutagen 同步。

## 基础镜像钉版本

`python:latest` 钉为 `python:3.14-trixie`。中途先试了 bookworm，构建失败：Debian 12 仓库没有 `docker-cli`（backend 容器内需要 docker CLI），trixie 才有——与原 latest 同底，只钉版本不换发行版。

## 生产部署与验证

流程：Docker Hub 拉 `coffeiz/gugu-web-{backend,frontend}:v1.0.2`（注意 tag 带 v）→ 重新 tag 为 `.env` 引用的 `gugu-web-backend/prod` → `docker compose -p gugu-web-main up -d`。

两个坑：

- sandboxd 与 backend 引用同一个镜像 tag，compose 按 tag 比较检测不到底层镜像变化，需要单独 `--force-recreate sandboxd`。
- worker/gateway 显示 unhealthy 是已知的 healthcheck 配错（容器内无 `/health` 路由），判断实际健康要看日志：worker 正常启动（consumer + 5 个内置定时任务），gateway 的 QQ 双 bot 和飞书 WebSocket 全部连接成功。

验证：backend healthy；容器内 LibreOffice 25.2.3.2 存在，`soffice --headless --convert-to pdf` txt→Writer→PDF 实测转换成功；容器内 `importlib.metadata` 读到 msgpack 1.2.2。
