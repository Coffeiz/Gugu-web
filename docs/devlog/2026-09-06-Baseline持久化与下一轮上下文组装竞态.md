# 开发记录 · 2026-09-06 · Baseline 持久化与下一轮上下文组装竞态

## 2026-09-06 · Baseline 持久化与下一轮上下文组装竞态

### 现象

- 上一轮 LoopScope 显示请求输入约 36k，但下一轮 round1 重新加载了约 254k 上下文。
- round1 的 `cache_read` 约 248k，容易被误判为“输入已经复用”或“缓存异常”。
- round1 之后的 inline compaction 能把后续 round 降到约 30k，但不能改变已经发出的 round1。

### 根因

- 请求 input usage 是单次 Provider 请求的统计，不是会话持久化 baseline；上一轮结束时的 36k 不能直接作为下一轮 baseline。
- 当时 session 仍使用旧 baseline `29366`，并加载了约 498 条历史消息。此前多次后台摘要失败（摘要为空或包含外层包裹标记），因此 baseline 没有推进。
- baseline 更新原本是异步调度的。若下一轮在持久化完成前开始组装上下文，就可能继续读取旧 baseline。
- `cache_read` 表示 Provider 命中了稳定前缀，不表示整个 prompt 与上一轮相同，也不会降低 LoopScope 的 `input` 总量或用户 token 上限计算。

### 处理与验证

- 修复后的服务重启后，baseline 更新任务已成功执行，并将 session baseline 从 `29366` 推进到 `29844`、再推进到 `29870`。
- 后续 run 的 round1 已恢复正常，说明此前异常样本产生于修复部署前、且摘要任务持续失败的时间窗口。

### 规范

- 读取会话上下文时必须使用最新的已持久化 baseline；不能用上一请求的 input usage、输出长度或临时 inline 截断位置冒充 baseline。
- 每次压缩只在摘要完整、非空、格式校验通过且 CAS 水位未变化时推进 baseline；失败必须保留旧 History 和旧 baseline。
- 异步 baseline 更新与下一轮 context assembly 必须按 Session 串行。下一轮不能在上一轮的 baseline 更新尚未完成时无条件读取旧边界；应等待更新完成，或读取带版本校验的最新持久化状态。
- LoopScope 至少同时记录 `baseline_message_id`、`history_selected_count`、`provider_input`、`fresh_input` 和 `cache_read`，排查时先区分“上下文组装过大”和“Provider 前缀缓存命中”。
- 看到高 `cache_read` 不能推断输入相同；必须结合 Prefix Diff、baseline revision 和实际消息序列判断缓存边界是否正确。

### 后续检查项

- 为“baseline 更新进行中时启动下一轮”补充串行化回归测试。
- 验证 baseline 更新失败后下一轮仍能稳定使用旧 baseline，且不会重复叠加旧摘要或原始历史。
- 将 baseline 更新状态、等待时间和失败原因纳入 LoopScope 的可观测字段，但不得记录聊天正文或用户输入。
