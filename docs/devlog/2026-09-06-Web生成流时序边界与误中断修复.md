# 开发记录 · 2026-09-06 · Web 生成流时序边界与误中断修复

## 现象

后台生成实际仍在继续，甚至已经正常调用模型和工具，但 Web 聊天在发送消息后或
刷新续接时出现“这次生成被中断了，请重试”。该提示与后台 Run 的真实结果不一致。

## 根因

Web 生成同时存在三套状态判断：

1. 后台 Run 通过生成快照和最终 `done/error` 表达业务生命周期；
2. Redis lease 表达后台任务的进程归属和并发控制；
3. SSE 转发层根据连接是否收到消息、快照是否存在、lease 是否存在推断生成是否中断。

其中第 2、3 项被错误地当成业务状态使用：后台任务刚创建时快照已经存在，但 lease
尚未建立，流转发层把它判成 inactive；SSE 连接在正常结束或刷新时也可能先看到 EOF，
前端再自行合成“生成中断”事件。后台 Run 并没有失败，却被展示层误报。

## 处理

- `genstream.is_active()` 只依据快照是否存在且尚未进入终态判断；lease 不再参与业务状态。
- `genstream.subscribe()` 只处理明确终态：
  - 快照为 `done`：补发 replayed `done`；
  - 没有快照：返回 `idle done`，表示没有可续接的生成，不表示失败；
  - 活跃快照：继续发送 keepalive，等待后台 Run 的显式事件。
- 快照在发布 `done/error` 前先写入终态，再广播事件；`end()` 短暂保留终态快照，覆盖
  广播与迟到续接之间的窗口。
- 前端不再把 SSE EOF 推断为生成失败，也不再合成 `generationInterrupted` 消息；
  失败只接受后台发布的 `error` 事件。
- 删除临时流式 probe、`streamKind` 参数和对应的启动宽限测试，避免诊断逻辑成为第二套
  生命周期实现。
- lease 仍保留在压缩和后台任务的归属控制中，但不参与 SSE 展示、刷新续接或用户可见
  成功/失败判断。

## 固化的生命周期顺序

```text
POST /chat
  建立 Redis subscription
  初始化生成快照
  启动后台 Run
  转发 SSE

后台 Run
  更新快照 -> 广播 token/tool 事件
  持久化业务结果
  写入终态快照 -> 广播 done/error
  释放 lease，短暂保留终态快照

刷新 / GET stream
  先建立 subscription
  读取快照
  活跃：回放快照并等待后续事件
  已完成：补发 done
  不存在：返回 idle done，由前端重新读取数据库
```

## 不变量

- Run/数据库终态是唯一业务事实来源。
- SSE、Redis channel 和快照只负责展示、回放和传输续接，不负责推断失败。
- transport disconnect、EOF、keepalive 超时和 lease 缺失都不能单独生成用户可见错误。
- `done/error` 必须先更新快照再广播；前端刷新不能因为错过广播而丢失终态。
- lease 只表示后台任务所有权，不表示 Run 成功、失败或是否应该展示中断。
