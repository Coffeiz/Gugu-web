# 用户沙箱授权 Phase 4

## 本次完成

- 增加 `sandbox.filesystem_authorization_enabled` 灰度开关，默认关闭；关闭时授权入口拒绝申请，已存在的 grant 也不会提升执行策略。
- 会话和定时任务的授权申请、授予、撤销写入脱敏 `SecurityEvent`，grant 与生命周期审计在同一数据库事务内提交。
- Redis 仅聚合 `requested/granted/revoked/denied` 和主体类型指标，不保存路径、正文、文件名或凭据。
- GuguChat 会话标题栏和定时任务表单都使用公共 `FilesystemAuthorizationDialog`，流程由可注入 API 的 `useFilesystemAuthorization` 统一维护。
- 会话列表、任务列表和工作区状态接口均返回后端真实开关/有效授权状态，避免前端状态与后端权限漂移。
- 定时任务新建后的授权流程使用保存响应中的任务 ID；Agent 工具在开关关闭时直接拒绝授权参数，避免先创建确认请求后失败。
- GuguChat 挂载时就加载会话授权摘要，小窗无需先展开即可显示当前权限入口。

## 审计结论

- grant 与 policy 的唯一事实源仍是 `backend/app/services/filesystem_authorization.py`。
- Shell、PTY、Docker sandbox、scheduler、文件工具、回收站和 `web_download` 没有新增第二套路径授权判断。
- 会话授予/撤销会同步 `filesystem_authorization_grant_id`；撤销后列表不会继续显示已授权。
- 审计元数据只允许固定键和值类型，主体、结果和来源均使用固定枚举；没有新增可见正文日志。
- 未删除与本阶段无关的工作区修改，也未改写运行配置。
