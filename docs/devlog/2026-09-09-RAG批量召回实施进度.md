# RAG Phase 0/1 实施进度（2026-09-09）

## 已实现

- 自动召回开始时创建 LoopScope span，成功、超时、容量上限、取消和内部错误在等待边界结束；迟到后台结果不能创建第二条成功记录或改写注入状态。
- 来源进度记录索引准备、sidecar 查询、数量统计与完成/失败状态；修正 sidecar 时间包含 DB 统计的问题，补齐 source_diagnostics 传递。
- snapshot 缓存锁内复查命中，区分 transient-only 条目与已经加载持久化来源的条目。
- TS `batch_search` 一次分词和 BM25 计分，按来源/scope 独立截断；Python 保留最终权限复核和 conversation 水位。
- Memory 并入一次总查询：worker 新增 `replace_transient` 瞬态语料槽（只驻内存不落盘），`batch_search` 的 search 项可声明 `corpus: "transient"`；两个语料槽各自计算 BM25 统计边界，不合并文档。瞬态槽按快照指纹驻留，指纹未变时零额外 IPC；Python 记录进程代数，worker 重启后自动重传。
- `BatchUnifiedRetriever`：一次索引准备 + 一次 `batch_search` 同时取回持久化与 Memory 候选；`search_knowledge` 按 `search.rag_query_mode` 选择 legacy / `batch` / `batch_shadow`。
- `ShadowUnifiedRetriever`：交付 legacy 结果，影子批量结果只记录候选差异（`shadow_equal`、`shadow_first_diff_index`、`shadow_batch_count`、`shadow_total_ms`）进 source_diagnostics；影子失败只记 `shadow_error`，永不影响交付。
- 构建类 op（`replace`/`patch`/`build_and_index`/`replace_transient`）使用独立的 30s 构建超时；500ms 搜索超时只约束搜索类请求。此前全量索引装载超过 500ms 会被误判为 worker 不可用（batch 模式冷启动必现）。
- worker JSONL 流上限放宽到 32MB：批量查询响应聚合多来源候选原文，单行超过 asyncio 默认 64KB 时 readline 抛 "chunk is longer than limit"，现在会以 `TsSidecarUnavailable` 显式关闭重连而不是留下半行错位。
- 配置默认 `legacy`，未变更运行配置，未自动切换用户查询。

## devserver 全链路验收（真实账号，4063 chunk / 7 来源）

`scripts/bench_rag_recall_modes.py`（新增）驱动 `search_knowledge` 主链（准备、排队、检索、排序、注入组装），不含 LLM 意图路由与重排；每模式独立进程保证冷口径一致；30 轮热 + 6 并发 × 4 轮突发：

| 指标 | legacy | batch |
|---|---:|---:|
| 冷启动 | 2115ms | 1384ms |
| 热 P50 / P95 | 157ms / 236ms | **38ms / 59ms** |
| 并发 P50 / P95 | 1214ms / 1636ms | **169ms / 369ms** |

batch 模式全部来源共享一次索引准备（P50 22ms）和一次 sidecar 查询（P50 6ms，排队 0ms）；legacy 每来源独立排队 32–89ms 且冷启动并行重建互相踩踏（canvas 单项构建 598ms）。热路径端到端 P95 59ms，远低于 500ms 验收线；3 秒总预算下的真实超时大头确认为 legacy 的每来源串行排队与索引重建叠加，而不是单次 IPC。

等价验证（`batch_shadow` 同帧对比，3 轮 × 6 查询）：

- 持久化来源 canvas/conversation/file/knowledge/note/project：候选 ID 与分数（6 位小数）18/18 完全一致，无权限扩大。
- Memory 来源 shadow 不一致（18/18），根因在 legacy 侧：legacy 的 Memory 走 `replace` 覆盖 worker 唯一持久槽（replace-churn），shadow 流程中持久槽被其他来源/全量语料占据时，Memory 候选是对错误语料计算的 BM25（分数随语料漂移）。batch 侧 Memory 固定查独立瞬态槽（455 文档），协议测试证明与隔离索引一致，属确定性正确侧。分进程跑 legacy/batch 对比时，legacy 进程最终注入几乎只剩 memory 结果、batch 进程各来源均衡，同样是该缺陷的表现。
- 诊断口径注意：batch 的 `document_counts.memory` 是持久槽 + 瞬态槽合并计数（870 个已索引 memory chunk + 455 瞬态文档 = 1325），Memory spec 实际只查瞬态语料。
- legacy 并发 replace 与批量复用检查交错时可触发 `TsSidecarUnavailable`（批量查询索引版本不一致）；shadow 模式正确隔离为 `shadow_error`，交付不受影响。生产 batch 模式无 legacy 腿，并发召回 24 样本 0 错误。

# Phase 2/3 追加（2026-09-09）

## Phase 2：TS 统一候选排序

- 契约审计确认 TS `rank_candidates`（confidence-v1）已是唯一评分实现，Python 正常路径只做映射与回填；清理 contracts 里从未传输的 `rank` 字段。
- `TsSidecarClient.rank_candidates_with_cache` 增加 scoring_version 守卫：worker 返回版本 ≠ `confidence-v1` 时抛 `TsSidecarUnavailable`，评分器代际漂移响亮失败而不是静默换口径。
- 冻结测试钉住 tie-break 真实契约：SOURCE_PRIORITY 只影响 confidence 入选顺序，最终输出按 fused 降序 + id 升序重排（首个测试按臆想顺序断言失败后修正为真实行为）。
- `batch_shadow` 增加 rank 影子：batch/legacy 两侧候选分别送 TS 评分器，记录 `rank_scoring_version`、`rank_equal`、`rank_first_diff_index`。
- 排查记录：诊断模式冷启动偶发 rank 影子全空的根因是 legacy 单一 owner 级 revision 设计（各来源共享 max(indexed_at)，后建来源跳过重建、瞬态 replace 劫持持久槽），属 legacy 已知结构缺陷，batch 为确定性正确侧；shadow_error 隔离不影响交付。

## Phase 3：TS 接管 hybrid 融合

- worker 新增 `hybrid_fuse` op，与 Python `hybrid_results` 逐位对齐：RRF 浮点顺序 `weight * ((K+1)/(K+rank))`、cosine 含 sqrt、维度不匹配/零向量记 0.0 但保留向量名次、vector_map 非空而命中均无可用向量时按纯词法 RRF 重打分（不是透传原始分——首版漏了这条，靠等价测试逼出）。
- `TsSidecarClient.hybrid_fuse`：退化输入（无查询向量/空缓存/命中均无可用向量）本地走 `hybrid_results`，语义逐位一致且避免空载 IPC；正常输入只传候选子集向量（整份向量表约几十 MB，不进 IPC）。
- `_memory_finalize` 增加 `fuse` 注入点：batch 主链传 TS 融合闭包，legacy 保持 Python 融合作为回滚；worker 融合失败显式记 `ts_hybrid_error` 后回滚 Python 实现，不静默兜底。
- 向量仍由 Python 生成与加载（provider/密钥/配置边界不变）。

## 测试

- TS：hybrid_fuse 手工 RRF 冻结值（1e-12）+ 透传契约测试；全量 43 通过，typecheck 通过。
- Python：真 worker 等价测试（全量/部分缺失/脏向量/命中均无向量/空缓存/无查询向量六种情形，9 位小数对齐候选身份、排序与 fallback）；后端全量 2308 通过。

# Phase 4 追加（2026-09-09）

## 索引生命周期收口与可观测

- worker 恢复磁盘索引时区分三种结局：无索引文件（首次冷启，非损坏）、version_mismatch、corrupt；后两者经 ping 的 `restore_error` 显式上报，Python 侧存为 `restore_error` 属性并透传进查询诊断 `index_restore_error`。损坏索引不再无声跳过；全量重建成功后 worker 与 Python 双侧清空。
- 新增测试：损坏报告与重建恢复（TS + Python 双侧，含 owner_hash 子目录真实布局）；并发 patch/replace/search 管线化请求下 revision 单调推进、每个检索响应与其声明 revision 严格一致（首版断言用错删除键 `d0:1:0`——worker patch 的 deletes 是裸文档 id，测试失败逼出正确契约）。

## Phase 4 遗留的决策

- 「TS 统一处理 source adapter 与分块」的写路径移交未实施：worker 统一 builder 已就绪但其文本方言与 Python 投影不一致（TS file 适配器拼 relative_path，Python 拼「文件：/类型：/空间：/阶段：」头部），切换会改写已入库 chunk 文本与版本；且 KnowledgeIndexEntry 表是跨进程持久 chunk 事实源，分块必须发生在写库前。移交需三步（方言对齐 → 双实现投影等价 → shadow 投影），列为后续独立阶段。Phase 5 查询主链不受影响：worker 语料本来就是 Python 投影后经 replace/patch 提交的文档。
