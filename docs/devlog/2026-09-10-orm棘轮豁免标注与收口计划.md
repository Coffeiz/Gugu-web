# 2026-09-10 ORM 棘轮豁免标注与收口计划

## 背景

PR #53（v1.1.2 发版准备）合并门要求两个 workflow 全绿。Runtime integration 自本周期起红在
「ORM boundary ratchet」（阶段 1 棘轮）：基线取 merge-base(HEAD, origin/main) = v1.1.1
（6030690e6），检查 `backend/app/api/v1/` 与 `backend/agent/tools/` 相对基线**新增**的
高风险 ORM 行。当前清单 35 行、分布在 8 个 api/v1 文件：

| 文件 | 行数 | 内容 |
|------|------|------|
| trash.py | 11 | 回收站枚举 5 + 清理写入 5 + 模型 import 1 |
| projects.py | 9 | 项目关联读取（folders/files/events/tasks）×2 个处理器 + import |
| mind.py | 7 | 画布读取 5 + 概览聚合 2 |
| agent_admin.py | 2 | 用量场景统计读取（1.1.2 新增特性） |
| files.py | 2 | 批量操作前/后行读取 |
| search.py | 2 | 全局搜索项目/日历域 |
| events.py | 1 | 定时任务读取 |
| folders.py | 1 | 模型 import |

这些行全部是 1.1.2 周期内各特性会话直接写进 API 层的（本分支 conf-v4 相关提交未触碰
api/v1）；棘轮按 merge-base 整周期比对，所以在合并门前全部计入。标注前完整清单见
CI run 34432522620 失败日志。

## 决策：行内豁免标注，迁移留作发版后独立 PR

两个候选路径：

1. **立即迁移 Service 层**：8 个领域、约 15-20 个查询点的真实重构，需要逐域设计
   Service 接口并保持归属校验（`user_id` 过滤）与测试覆盖。压在已就绪的发版分支上
   风险与收益不匹配。
2. **采用脚本预留的 `orm-exempt:` 行内标注**（`check_orm_boundaries.py` 自身注释要求
   「豁免必须写在新增代码行上并说明原因，便于审查和后续收口」）：35/35 全部逐行标注，
   原因写明待收口的 Service 与来源（1.1.2 遗留/新增）。

选择 2。豁免是**逐行、带原因、随代码走**的，收口时删一行标记即兑现；阶段 0 基线
报告（`scan()`）不受影响，存量规模仍然可观测。

## 落地

- 8 个文件 35 行追加 `# orm-exempt: <原因>`（`rstrip + 两空格 + 注释`，不改任何代码逻辑）。
- `py_compile` 8 文件全部通过；标注后本地验证
  `python backend/scripts/check_orm_boundaries.py --diff-base 6030690e6` → ✅ 通过。

## 收口计划（发版后按域拆独立 PR，迁一个域摘一批标记）

1. trash.py（11 行）→ 新建 TrashService：回收站枚举 + 清理写入 + import。
2. projects.py（9 行）→ 项目关联读取下沉 Service（两个处理器复用同一批量接口）。
3. mind.py（7 行）→ MindService 承接画布读取与概览聚合。
4. agent_admin.py（2 行）→ 用量场景统计并入 admin usage Service（**新增代码，优先收口**）。
5. files.py（2 行）→ files Service 批量行读取。
6. search.py（2 行）→ 各域 Service 提供搜索查询。
7. events.py（1 行）+ folders.py import（1 行）随相邻域迁移一并处理。

每迁完一个域，对应 `orm-exempt:` 标记必须同 PR 摘除；全部摘除后棘轮恢复零豁免状态。
