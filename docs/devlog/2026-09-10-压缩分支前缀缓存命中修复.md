# 会话压缩缓存命中率排查：分支前缀修复

## 现象

Admin 用量页按场景统计，`compaction` 场景长期贴着 0.1% 缓存命中率（样本 364.7K 输入）。当天已经把 run 内溢出压缩改成「追加式」（复用主会话 canonical 序列、末尾追加压缩指令），预期应该吃到 MiniMax 的会话内前缀缓存，实际没有。

## 排查过程

用 devserver 真实链路逐层验证，而不是只看单测：

1. **对照主 run 与压缩分支的 wire 帧**：同一次 run 里主对话帧 `cache_read=71950`，而紧随其后的压缩分支 `cache_read=128`。说明分支请求与主 run 刚发过的请求**从第一个 token 起就不一致**，前缀缓存整段落空。
2. 逐项定位不一致的来源（provider 层探针 + 真实链路复现）：
   - **分支只发中段**：追加式分支当时把「待压缩的中间片段」当作消息序列发出，第一条消息就是对话中段，与主 run 的请求序列根本不同前缀。
   - **anthropic 路由的角色投影缺失**：`render_history` 之后主 run 还会把「消息级 system」投影成 user（`loop_drivers.AnthropicDriver.run_round`），分支没做这一步；同一前缀只换角色，实测 `cache_read` 3840 → 384。
   - **工具声明缺失（决定性）**：provider 把 `tools` 一并算进可缓存前缀。生产规模（101 个常驻工具、anthropic schema 约 5.5 万字符）下，带工具命中率接近 100%，不带掉到约 15%；`tool_choice` 一旦设置同样会毁掉命中（100% → 15%）。

## 修复

- `compaction._branch_prefix_history`（新增）：分支改发「固定前缀 + 待压缩区间之前的完整历史」，与主 run 请求逐 token 同前缀；渲染复用主 run 的 `render_history`，anthropic 路由再补 `render_anthropic_message_roles`。切片严格按 `message_history` 的位置计算——`_drop_orphan_tool_results` 会浅拷贝并可能丢消息，两个列表长度不一定相等，跨列表用下标会切偏，身份匹配只在 `message_history` 内成立。
- `BranchInput.tools` + `ContextBranch.run` + `provider_runner.complete_messages/_anthropic/_openai`：把本 run 的工具声明贯通到分支。anthropic 路径只发 `tools`、**不设** `tool_choice`；OpenAI 兼容路径复用主 run 的 `build_tool_params`。
- `core.compact_context_now` 传 `branch_tools=getattr(ctx, "tools", None)`；追加指令尾部补一句「也不要调用任何工具」，替代 `tool_choice` 的约束作用。

## 验证（devserver 真实 web run，2026-09-11 00:07 CST）

同一会话连续四轮，分支每次调用直接读 `usage`（插桩 `provider_runner._record_usage`，不靠数据库行号猜）：

| 轮次 | 分支调用 | 输入 | cache_read | 命中率 | 同轮主对话 |
|------|---------|------|-----------|--------|-----------|
| 1 | 第 1 块 | 1009 | 30233 | 96.8% | cr=30233 / 99.2% |
| 1 | 第 2 块 | 3748 | 128 | 3.3% | — |
| 3（强制去掉 tools） | 第 1 块 | 16755 | 13392 | 44.4% | cr=29540 / 98.3% |
| 4（仍去掉 tools） | 第 1 块 | 2157 | 29392 | 93.2% | cr=30053 / 95.5% |

修复前该场景是 `compaction cr=128` 对 `chat cr=71950`（约 0.2%）。现在分支读到的 `cache_read` 与同轮主对话帧一致，说明两者确实共享同一份可缓存前缀；把工具声明去掉后首轮即跌到 44.4%，要到下一轮才靠同形前缀重新热起来，佐证工具声明确实参与前缀。

## 仍然冷的来源（本次未改）

1. **run 结束后的 baseline 压缩**（`compress_conv._call_llm`）走的是 `BranchInput(stable_system=..., delta=...)`，没有 `history_messages` → 落到旧的重编译路径（把历史摊平成一段文本），结构上不可能与主 run 共享前缀，每次约 3 万输入、`cache_read=0/128`。它也打 `scenario=compaction`，所以 Admin 场景表里的聚合命中率仍会被它拉低。
2. **分块滚动摘要的第 2 块**必然冷：它的前缀包含第 1 块刚生成的摘要，与主 run 无同形前缀。

要把 `compaction` 场景的聚合命中率提上去，需要评估给 baseline 压缩也换成追加式（DB 重放历史 + 与主 run 同口径渲染，成本与风险都更高），本次不在范围内。

## 续：baseline 不再重放生成，直接复用 run 内摘要（2026-09-11）

上节第 1 条后来处理掉了，但方案不是「给重放换追加式」——重放路径在 worker/收尾阶段从 DB 重建 provider 帧，与主 run 的 system/工具/渲染逐字节对齐成本高且脆；而 baseline 触发的时机（`run_finalize` 里 `compaction_applied=True` 时）**本 run 刚在 provider 边界生成过同一批历史的摘要**，那段摘要生成请求就是已经命中缓存的追加式调用。于是改成：

- `run_finalize`：从本 run 收尾帧里提取 `<compacted-summary>` 正文，连同本轮用户消息 id 一起传给 `compress_conv.compress_if_needed`（`reuse_summary` / `reuse_before_message_id`）。
- `compress_conv`：复用路径不再调用摘要 LLM，只按原有保留窗口规则重算 baseline 水位并落库；可压缩范围被限制在 `id < 本轮用户消息 id` 之内——run 内压缩把本轮消息整体保护、不写进摘要，水位若推进到它们之上会丢上下文。手动 `/compact` 等无 run 摘要可复用的场景仍走原重放路径。

**水位安全性论证**（为什么直接复用不会丢历史）：baseline 的保留窗口按内容字符算（每条 ≤ 内容字符数 ≤ 渲染字符数），run 内保留窗口按渲染字符算，同样的字符预算下 run 保留的消息只少不多——即 baseline 想压缩的消息集是 run 内摘要覆盖集的子集；再加上复用时把范围限制在本轮消息之前，两个方向都不会出现「水位越过了摘要没覆盖的消息」。

**验证**（devserver 真实 run，预置大历史 + 连续两轮触发 run 内压缩）：两轮都是 `_call_llm` 重放调用 0 次、审计行 `trigger=run_reuse`、summary 落库；水位停在保留窗口边界且恒小于本轮用户消息 id（第 1 轮 0 → 38078，压缩 171 条；第 2 轮 38078 → 38088，压缩 10 条，并把上一版摘要滚动合并成新摘要 186 → 614 字符）。之前每轮压缩后必然出现的那条「in≈3 万、cr=0/128」baseline 重放用量行不再出现。全量后端测试 2480 passed（新增 baseline 复用回归 3 项）。

探针为压低成本把 `context_tokens` 调到 24000，于是 run 内追加式摘要自身被输入预算切成多块（一次压缩 7 次分支调用，首块之外都是对话中段切片，只共享 system+工具那段前缀）——这是探针配置的产物：生产预设 120k 的触发点约 108k（含工具声明），消息部分约 75k < 输入预算约 110k，单块即可装下。该现象与「分块滚动第 2 块必然冷」同源，属既定结构，不在本次范围。

**剩余的冷调用**：分块滚动摘要第 2 块（设计使然）与手动 `/compact` 的重放路径（低频，暂保留）。

## 续 2：生产规模复测发现分支仍整段 miss——thinking 参数不对齐（2026-09-11）

baseline 复用上线后用生产预设复测：合成填充触发 90% 线，分支仍然 0.1%；暖前缀对照更矛盾——主请求 30 秒前刚写过缓存、本轮 `cr=105932`（99.9%），紧随其后的分支 `cr=128`。逐参数受控实验（小请求手工构造）定位到：**请求参数参与 MiniMax 的缓存键**，`thinking` 一变整段 miss（`max_tokens` 不参与；连续第二条 user 消息会被服务端合并进前一条、同样导致 miss）。

而预设 `thinking="adaptive"` 时，主循环经 `adapter.build_anthropic_thinking_params(ai)` 得到 `{}`（MiniMax 不发 thinking），分支却在 `provider_runner._anthropic` 手拼 `{"type": "adaptive"}`——就差这一个参数（分支与主请求的 messages 逐元素、tools、system 均逐字节一致）。修复：`complete_messages` 传 `align_with_main_run=True`，与主循环用同一个 adapter 构造 thinking/generation 参数。修复后同条件复测：分支单次调用 `in=758 cr=94009`，**命中 99.2%**（修复前同位置 0.1%）。

两个补充事实：会话闲置约 40 分钟后首轮 `cr=0`，MiniMax 缓存 TTL 以十分钟计；手动 `/compact` 仍是摊平重放、与主对话请求零共享前缀（预热后实测 1.2%），是剩余的冷路径。
