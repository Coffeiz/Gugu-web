# 2026-09-10 本地测试偶发失败：测试连了共享 Redis

## 背景

v1.1.3 发版预检时本地全量 pytest 报过一次 `1 failed, 2445 passed, 7 errors`
（test_folder_storage_relocation、test_mind_api 等），但**单跑这些文件全绿**，换个时机
再跑全量也是 2453 全绿。当时的推测是「随机序插件导致用例相互污染」，但复查发现本机
`backend/.venv` 里根本没有安装 `pytest-randomly`（requirements-dev.txt 里也没有），
顺序是固定的——推测不成立，必须换个方向定位。

## 定位

复发实验：同时起两个 pytest 进程跑全量，立刻稳定复现一条失败：

```
FAILED tests/test_scheduled_delivery_targets.py::test_execute_task_passes_structured_target_to_delivery
AssertionError: assert {'错误': '任务正在执行，请稍后再试'} == {'QQ': '已发送'}
```

`app/scheduled_tasks.py:execute_task` 用 `scheduled:lock:{task_id}` 这把 Redis 锁做
「同一任务同一时刻只跑一处」的互斥（试运行与正式触发共用）。测试库里 task id 从 1 开始，
两个进程拿到同一个 id，就抢同一把锁。

接着确认「测试到底连的是哪个 Redis」：把 Redis 指向不可达地址再跑全量，得到
`10 failed, 2443 passed`——失败全部落在 `test_scheduled_task_execution.py` 与
`test_scheduled_delivery_targets.py` 里那些**没有自行 mock** `get_redis` 的用例。

根因链：

1. `tests/conftest.py` 的 `_isolate_local_configuration` 只把 `OVERRIDE_FILE` 换成了
   临时空路径，**没有隔离 `.env`**（`SettingsConfigDict.env_file` 跟随
   `GUGU_ENV_FILE`，默认读工作区 `.env`）；
2. 开发机 `.env` 里的 `REDIS__HOST` 指向共享地址（本机没有本地 Redis，`redis-cli ping`
   直接 Connection refused）；
3. Redis 相关链路只有确认门被 `_fake_confirm_redis` 换成了进程内假客户端，其余
   （定时任务锁、`im:seen` 去重、租约、各类 GC 锁）一律用真实客户端。

所以本地一次「全绿」的测试其实是在读写共享 Redis 的：低 task id 与共享环境里的真实任务
同键，既会让并发/相邻的两次测试互相抢锁（表现为顺序、时序相关的假失败），也可能替真实
任务抢锁；授权、去重等键还会跨测试残留。CI 里 Redis 是 workflow 提供的独立 service，
而且只有单个 pytest 进程，所以一直没暴露这个问题。

## 处置

`tests/conftest.py` 新增 autouse fixture `_hermetic_redis`：用 `fakeredis`（`FakeServer`
+ `fakeredis.aioredis`）给每个测试一份进程内 Redis，async 与 sync 共用同一个 server，
语义等同「同一个 Redis」，测试之间零残留。替换点是 `app.core.redis` 的模块级单例
`_client` / `_sync_client` 而不是各调用处的 `get_redis` 名字——懒加载函数读的就是这两个
全局，因此 `from app.core.redis import get_redis` 与 `R.get_redis()` 两种写法都覆盖。
原先只为确认门准备的 `_fake_confirm_redis` 手写假客户端随之删除，由它统一承担。

`fakeredis[lua]` 进 `backend/requirements-dev.txt`：`Lock.release()/extend()` 走 Lua 脚本，
没有 `lupa` 时 fakeredis 会报 `unknown command 'evalsha'`。需要真连 Redis 做集成验证时，
设 `GUGU_TEST_REAL_REDIS=1` 显式退出替身（已验证：置该变量并让 Redis 不可达，相关用例
重新变红，说明确实切回了真实客户端）。

## 验证

| 场景 | 处置前 | 处置后 |
|------|--------|--------|
| 全量（顺序，Redis 可达） | 2453 passed | 2453 passed |
| 全量（`REDIS__HOST=127.0.0.1 REDIS__PORT=1`） | 10 failed | **2453 passed** |
| 两个进程并发跑全量 | 1 failed | 2453 passed（两进程） |
| 三个进程并发跑全量 | — | 2453 passed（三进程） |

并发跑耗时约 3 分钟（比单跑慢，因为三份全量争 CPU），但结果稳定全绿。
