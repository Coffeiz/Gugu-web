# 完整沙箱授权不进 Shell 动态提示词：授权后模型仍以为 /personal、/project 只读

日期：2026-09-11
关联：`backend/agent/security/shell_policy.py`、`backend/agent/prompts/shell.md`、`backend/tests/test_shell_policy.py`

## 现象

用户在会话里给了「完整用户沙箱授权」后，模型仍然不知道 `/personal`、`/project` 已经可写：要么继续声明只读、要么顺着用户的话复述「沙盒已开通 shell、文件库读写」。用户的实际疑问是「给权限之后 session 状态提示词会变化没」——答案是**不会**。

## 排查

用 devserver 上真实会话（session 388，绑定 workspace 30）分别按「真实策略」和「已授权策略」两次调用 `build_dynamic_prompt`，输出**逐字节相同**。

代码层原因：

- `evaluate()` 已经算出了授权结果，放在 `ShellDecision.full_user_sandbox_write`（`shell_policy.py:265/284`）；`agent/tools/shell.py:315-316` 也确实用它把 sandboxd 的 `personal_read_only` / `project_read_only` 翻掉，所以授权对**执行**是生效的。
- 但 `build_dynamic_prompt` 从不读这个字段。它生成的动态块只包含：Shell 是否注册、复合命令规则、`/workspace` 的 cwd 映射、全部 Shell 命令开关、Autopilot、直跑运行时、OSS 模式。
- 与此同时静态 `shell.md` 明确写着「`/personal` 和 `/project` ……两者默认只读；只有完整用户沙盒授权才允许写入」，并要求「每轮都必须以该状态为准」。协议让模型去查一个从不声明这件事的动态块。

结果：模型没有任何提示词依据判断自己的 `/personal`、`/project` 写权限，只能靠用户的话猜。这也解释了为什么「完整沙箱权限当时没解开文件工具」的体验——一部分来自已删除的位置写权限围栏，另一部分来自模型根本没有渠道得知授权生效。

## 修复

在 `build_dynamic_prompt` 里按 `safe.full_user_sandbox_write` 追加一行（非 OSS 模式）：

- 未授权：`- /personal、/project：本轮以只读方式挂载。要写入（新建、修改、删除）需先获得本轮完整用户沙箱授权；未授权时不要反复重试同一写入命令，也不要换路径或换工具绕过只读。`
- 已授权：`- /personal、/project：本轮已按可读写挂载（完整用户沙箱授权生效），可直接在其中创建、修改和删除文件。`

用 `safe`（`pwd` 探测）而不是 `dangerous` 的决策：`pwd` 是 SAFE 风险，不会命中 `ShellRisk.DANGEROUS` 分支里那几个**漏传** `full_user_sandbox_write` 的提前返回，因此只有它这个字段可信。

## 缓存代价（已知取舍）

这段动态块由 `agent/runner.py:407-412` 追加在 **system prompt 末尾**，而 system prompt 位于整条消息序列的最前面。因此它的内容一变，下一轮整段前缀缓存会 miss 一次。授权/撤销是低频的用户主动动作，代价可接受；而且该块本来就存在「evaluate 不通过则整块消失、同时摘掉 shell/run_script 工具」的跳变，新增一行没有引入新的跳变类别。若要彻底规避，需要把整块挪到消息序列末尾（与既有「时间放末尾」同思路），属于另一个改动。

## 验证

- devserver 真实数据（只读探针，未改数据）：session 388 现有 `grant_id=14`、`full_user_sandbox=True`，动态块输出「已按可读写挂载」；把策略模拟成未授权后，同一会话输出「以只读方式挂载」，两个分支都命中。
- `tests/test_shell_policy.py::test_dynamic_shell_prompt_reports_personal_project_write_state` 覆盖两个分支。
- 后端全量 `2504 passed`。
