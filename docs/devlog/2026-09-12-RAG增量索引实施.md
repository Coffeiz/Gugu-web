## Phase 1（2026-09-12）：Knowledge 文档级增量

### 已落地

- 单条读取：`KnowledgeStore.get(entry_id)`（按 ID 直读单个 .md，不遍历全库）；
  `KnowledgeAdapter.build_source_record_for(source_id)` 出单条 canonical record。
- 单文档增量写库：`persistent_store.apply_document_patch`——**父文档作用域 replace**：
  该 parent 下不属于 upsert 键集的行一律删除（版本推进/chunk 收缩/正文改写都不残留旧 chunk），
  然后整来源 bump `indexed_at`（owner revision 取 max(indexed_at)，纯删除时必须显式推进，
  否则其他进程查询侧检测不到变化）。
- 向量增量：`agent/knowledge/vector_cache.apply_vector_delta(upserts, delete_keys)`——
  只 upsert 变更 chunk、删指定 key，不做整表 prune（sync_vectors 的 prune 语义在
  增量路径会误删其他文档向量）。删除键来自旧 chunk 的 `cache_key`（含 version，
  不能用 slot key）。
- TS worker patch：`pipeline.update_knowledge_document` 在 DB 提交后主动把单文档增量
  patch 给 worker（整表持久向量搭载），这样下次查询 `reuse_if_current` 直接命中；
  worker 报 `revision_mismatch` → 用 DB 全量投影做 worker 侧来源级 replace 回退；
  worker 不可用（未启动等）只记 `status=worker_unavailable`，DB revision 已推进，
  查询侧懒同步自愈。
- 事件路由：`handle_rag_index_event` 中 knowledge 事件带 `source_id` 走文档级增量，
  否则保持来源级重建。`save/update/delete_knowledge` 工具本来带 source_id；
  自动反思（reflect_if_candidate）改为返回保存条目 id 列表并逐条发事件
  （原来发空 source_id 触发全量重建）。
- 测试：新增 `test_rag_knowledge_delta_index.py` 8 例（单条读取 spy、单条投影、
  正文变更无残留、删除保兄弟、no_change 不打 worker、mismatch 回退、worker 不可用自愈、
  事件路由）；全量后端 2553 例全绿。

### 关键决策

- **DB 侧用「父文档作用域 replace」而不是按 delete 列表删**：chunk slot 键不含 version，
  正文改写时 delta 的 deletes 为空（同槽位由 upsert 覆盖），只有 slot 消失才有 deletes；
  version 推进换行键，必须靠键集差删旧行。
- no_change（digest 全等）不推进 revision、不打 worker——重复事件天然幂等且零成本。
- 测试驱动管线需绕过内存 SQLite 短路：抽成 `pipeline._in_memory_sqlite()` 供
  monkeypatch；且必须同步 monkeypatch `db_session._engine_loop`，否则 ensure_engine
  跨 loop 误判会连回真实数据库（conftest 里踩过的同一个坑）。

### 受影响集合定案（PRD 要求明确）

- file record 只含 folder_id/stage_name 等 id 与自身元数据，**不含 folder 名**：
  文件夹改名不改变任何 file record → 受影响集合恒为文件自身。
- project record 只拼接项目自身事实，不依赖文件正文：文件增删改不影响项目 doc。
- 因此移动/重命名/覆盖的受影响集合 = 单对象；旧 scope 残留由 digest 的 scope
  字段变化触发 upsert 兜住（Phase 0 补的 scope 进 digest 在这里兑现）。

## Phase 4（2026-09-12）：性能对比与收尾

### 单文档变更：文档级增量 vs 来源级全量（devserver 实测，5 轮）

| 规模 | document_patch P50/P95 | source_replace P50/P95 | 加速比 |
|------|------------------------|------------------------|--------|
| 1000 条 | 54ms / 93ms | 418ms / 494ms | ~7.7× |
| 3000 条 | 161ms / 197ms | 1268ms / 1361ms | ~7.9× |

（来源级耗时与 Phase 0 基线一致量级：1000 条全量 ≈ 550ms 含 TS 投影与写库。）

测量脚本 `scripts/bench_rag_delta_compare.py`。文档级耗时里还包含
KnowledgeStore.save 的 O(n) 全库 list（业务写入自身成本），纯索引增量部分
（单条读取 + 单条投影 + patch 写库）只有几十毫秒——增量收益随库规模线性放大。

### 批量事件合并窗口定案

- 当前 bus 没有显式时间窗，按 owner/source 合并 pending；但它只保存单个最后事件，
  因而多个 `source_id` 的事件可能覆盖，不能据此认定批量更新无丢失。
- 发布层会把 `entity_ids` 展开为多条文档事件；进入 pipeline 后按
  (user, source, doc) 加锁。该锁只保证已到达 pipeline 的同文档更新串行，不能弥补上游
  pending/outbox 覆盖不同 ID 的问题。
- 是否需要批量合并窗口暂不作为结论；Phase 5 先保证 ID 集合不丢，再测量重复 patch 与延迟后决定。

### 默认增量覆盖确认

- knowledge/file/project/calendar/note/canvas：事件带 source_id 即走文档级；
  文件库 API 的 remove/批量删除已带 file_op id/ids（files.py 5 处）。
- 无 id 的事件（老调用方、管理端触发）自动回退来源级重建，行为不变。
- 定期校准入口：依赖 Admin 新面板，按目标约定跳过（见 Phase 3 记录）。
- 上述为代码路由范围记录，不代表所有来源的端到端一致性已验收；Conversation/Memory
  保留专用语义，事件多 ID 合并和各来源召回一致性以 Phase 5 回归为准。

### 旧路径清理

- 契约无重复实现：`_worker_document_key`/`_index_document_digest` 全部委托
  `agent.rag.delta`（index_cache、ts_sidecar、batch_retriever 共用一份）。
- shadow 路径：rag_query_mode 早已 unified 单档（RAG-7 收口），无遗留。
- chunk diff 唯一入口 `compute_chunk_delta`；查询侧 index_cache 与写侧
  update_document 共用。

### §11 首轮测试覆盖记录（2026-09-13 审计修正）

下列测试执行数量仍是 2026-09-12 的真实运行结果；此前把部分行为测试、通用测试或代码接线检查等同于 PRD 验收，覆盖结论过宽。具体边界如下：

- `test_rag_delta` 覆盖稳定槽位、digest、chunk 增减/删除、no-op 和输入顺序确定性。
- Knowledge 专项覆盖单条读取 spy、正文变化、删除、no-op、revision mismatch 来源级回退、worker unavailable 状态和事件路由；关键词独立变化、删除后恢复尚无专项测试，现有修改 helper 始终写相同关键词。
- file/project 专项覆盖文件正文覆盖与删除、项目字段/阶段变化、删除和 entity IDs 事件发布；文件“移动”用例改的是 `stage_name`，没有验证真实 `folder_id` 变化、旧 scope 不可召回或 UI/RAG 一致性。
- Calendar 有 patch 与删除调用；Note/Canvas 专项目前主要验证单条 record 构建，Canvas 关系变化时多个端点的事件投影、Note 变更/删除的完整 patch 链尚未验证。
- 事件总线测试覆盖同一 owner/source 的 operation 合并，但没有传入多个不同 `source_id`。当前 pending 与 outbox 都按 owner/source 保存单个最后事件；文档级事件存在不同 ID 被覆盖的风险，不能据现有测试宣称“无丢更新”。
- `test_rag_index_jobs` 覆盖持久任务合并、失败退避和到期状态推进；durable recovery 测试只检查应用启动源码包含恢复器调用，没有模拟进程重启后多 ID 重放并核对最终索引。
- TS worker 测试覆盖本地索引文件恢复/损坏状态和请求序列原子性；尚未覆盖 Python 在 worker 重启且 DB/worker revision 不一致时执行 replace 并清除错误状态的完整闭环。worker-unavailable 用例只断言 DB 投影已写入，没有真正发起后续查询验证自愈。
- 未找到 RAG 写路径专属的 projection 事务失败、向量部分失败、owner/folder/group-member scope 隔离及诊断日志脱敏回归；不能用相邻模块的通用测试代替这些验收。
- 性能实测记录的是 1000/3000 条下单文档修改相对来源全量替换的 P50/P95；单文档删除、连续 10 次同源多 ID 变更、worker 重启恢复耗时和 chunk-diff/TS-patch 分段耗时未测。

### Phase 5 责任对齐

Phase 5 的范围、阶段责任模块和退出条件以 PRD §10 的“阶段责任边界”与“Phase 5”为准。实施责任按模块划分：事件合并/outbox 由 `agent/events/bus.py`、`agent/rag/index_jobs.py` 负责；单文档 patch/revision 由 `agent/rag/pipeline.py` 与 TS RAG worker 联合负责；来源受影响集合由各 adapter、事件发布层和对应来源测试负责；覆盖矩阵、阶段状态与性能证据由本 PRD 和本 devlog 同步维护。人员负责人不在此处臆造。

### 结论

Phase 0–4 的代码与首轮性能/测试结果已记录，但 PRD 的全部验收标准尚未闭环。Phase 5 已开启，优先修复或验证同源多 `source_id` 事件合并，再完成来源 scope、durable recovery、特殊来源边界和性能场景的补测；在此之前不得将 PRD 标记为整体完成。
