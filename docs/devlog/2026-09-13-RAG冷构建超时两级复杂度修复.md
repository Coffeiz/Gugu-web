# RAG 对话查询全超时：冷重建两级 O(n²) 与 30s 构建预算

> 日期：2026-09-13
> 环境：devserver（192.168.110.51，systemd 系统级 gugu-rag-sidecar / gugu-backend / gugu-worker）
> 结论先行：当天下午的 RAG 更新触发了 20237 条文档的全量冷重建，`patchInMemory` 逐条处理的 O(n²) 让 install 耗时 68s，超过 30s 构建预算 → 操作被取消、persist 永不执行 → 索引快照永不落盘 → 每次查询都全量冷重建 → 全部超时。修复分两级（标记-清扫 + 新增侧词项倒排预聚合），全量重灌 68s → 0.78s。

## 现象

下午更新 RAG 相关代码后，devserver 上所有对话的 RAG 召回超时；同日早些时候发布的 v1.2.1（生产）无此问题。RAG_PROBE 诊断显示三件套同时出现：

- `cache_miss` 原因为 `empty_or_expired`；
- `worker_revision_reused: false`（每次都在重建）；
- 卡在 `index_install_start` 之后没有 `index_install_done`。

## 成因链

1. **触发条件**：下午的更新使索引快照 revision 失效，下一次查询触发 sync_index_from_database → 全量补丁（20237 条 upsert 一把进 `patch` op）。
2. **热点 ①（O(n²) 第一层）**：`patchInMemory` 逐条调 removeDocument/addDocument——每条 upsert 触发一次 `documents` 数组全量 filter 拷贝，每个词项 posting 一次 `indexOf` + `splice` 线性搬移。2 万条文档 × 2 万条数组 = 4 亿次元素搬移，install 实测 68s。
3. **热点 ②（30s 预算放大成死循环）**：`ts_sidecar.py` 的 `BUILD_TIMEOUT_SECONDS = 30` 把整个构建 op 在 30s 处取消。取消发生在 install 之后、persist 之前 → **落盘永远不发生** → 下一次查询 revision 仍 miss → 再来一次 68s 冷重建 → 再被取消。单次慢被放大成永久性超时。
4. **热点 ③（O(n²) 第二层，第一版修复漏掉）**：见下文。

## 修复过程

### 第一级：构建预算 30s → 120s（commit d86e8c52）

治标兜底：给冷重建留出足够时间让 persist 跑完。实测全链路 ~70s，120s 留了余量；搜索路径的超时（`_timeout_seconds()`，cap 30s）不受影响。

### 第二级：patchInMemory 标记-清扫（commit bf2808a1b）

把「每条一次全量操作」改为三段式：账目（docFreq/lengths/documentsById）先全部处理完并收集脏词项集合 → 对脏词项 posting 一次性重建（旧条目过滤移除 id、补上新增词频）→ `documents` 数组单次 filter。同 id 多条 upsert 保留最后一条，与原「后者胜」语义一致。

修完后基准测试（事故同规模 20237 条）发现问题**没修完**：全量重灌仍 71.6s。原因：posting 重建阶段对每个脏词项都线性扫一遍 `added` 全表找该词项的贡献者——全量重灌时几乎所有词项都脏，O(脏词项数 × 文档数) 退化回原点。第一版只优化了小补丁场景，恰好事故路径是全量重灌。

### 第三级：新增侧按词项倒排预聚合（commit ca54a6908）

入账阶段在遍历 `added` 时顺手按词项预聚合 `[docId, count]` 列表（`addsByTerm`），重建阶段每个脏词项只取自己的条目。总工作量正比于总变更词项出现数，达到理论线性。

中间还踩过一个实现坑：第一稿清扫阶段解构 `for (const [docId, frequency] of added)`，但 value 是 `{document, frequency}` 包装对象，`frequency.get` 直接炸——改为 `entry.frequency.get(term)` 后 62/62 通过。

### 最终基准（详见 [INVEST 报告](../reports/2026-09-13-INVEST-RAG冷构建超时基准.md)）

| 操作 | 事故时 | 最终 |
|---|---|---|
| 全量重灌 patch（事故热点） | 68s | 0.78s |
| 冷构建 20237 条 | ~70s | 0.73s |
| search 验证 | — | candidates=20237，正常 |

## 教训

1. **修复杂度必须用事故规模做基准验收**。第一版标记-清扫在小规模测试全绿，事故规模下仍是 71.6s——如果当时直接部署，超时事故不会好。「优化后跑一下单测」不等于「优化生效」。
2. **超时预算指向的操作要检查「取消后状态是否可恢复」**。本例超时取消发生在 persist 前，慢不是问题，慢 + 永不落盘才是死循环。设计上更优的方向是「install 完成即允许 persist（哪怕操作超时已取消）」，本次未做，靠复杂度修复让耗时远低于预算。
3. **minify bundle 不能用标识符 grep 验证内容**，变量名会被改写，必须行为级（协议基准）验证。
4. devserver 的 sidecar 是**系统级** unit（`sudo systemctl restart gugu-rag-sidecar`），不在 `systemctl --user` 里。
5. 生产 v1.2.0 仍带 30s 预算 + O(n²) 旧代码，生产后端重启/索引失效会复现本事故，v1.2.1 需携带修复。
