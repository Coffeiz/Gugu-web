# ask_user 无选项提问在网页端没有任何回答入口

- 日期：2026-09-13
- 相关提交：`de3113c49`（兜底按钮 + 文本消费侧「真实选项」口径）

## 现象

咕咕问开放性问题时（ask_user `kind="question"`、不带 options），网页端
交互气泡只有文案没有按钮；用户在输入框打字回复，消息直接进入排队
（「排队中」），不会被当作提问的回答。

## 根因

回答通路依赖「随选项生成的 action token」：

- `create_prompt` 里自定义回复按钮的追加条件是
  `allow_custom_reply and rendered_options`——0 选项时连兜底按钮都没有，
  `rendered=[]`，prompt 没有任何 action，也就没有 token；
- 网页端回答走 `/interactions/{id}/resume-text`，两步式（点自定义回复 →
  `/respond` 激活 → 打字 → `/resume-text`），入口钥匙就是按钮的 token；
- 网页发送路径（`gateway/web.py stream()`）没有交互消费层：run 活跃
  （ask_user 挂起也算活跃）→ 消息进 pending queue。IM 链路则不同，
  `agent/im/interaction_text.py` 在收到文字时先调
  `consume_custom_text` 尝试消费活跃提问——这就是 QQ 打字能直答而
  网页不能的结构性差异。

## 修复

- `create_prompt`：agent 来源即使 0 选项也追加自定义回复兜底按钮，
  网页端复用现成两步式；
- `consume_text` / `consume_custom_text`：兜底按钮不计入「真实选项」。
  这一步是防回归的关键——兜底让 `options` 从空变非空后，原守卫
  `if options and not custom_input_active` 会把 IM 直接打字回答开放
  问题的老通路判成「请先选择自定义回答」而拒绝。以
  `id != CUSTOM_REPLY_OPTION_ID` 过滤后再判空，choice 的两步式要求
  与 IM 直答通路都保持原状；
- 前端：空 options 的存量提问不渲染空按钮区（悬空分隔线）。

## 验证

- 后端交互 38 测试全绿（新增：question 0 选项建 prompt 断言兜底、
  IM 直打消费、两步式消费），全量 2595 passed 零失败；
- 前端 typecheck + 组件测试通过；用户 devserver 实测正常。

## 边界（未做）

网页发送路径仍是「排队优先」：提问挂着时直接打字会进队列（不丢失，
提问过期 run 收尾后作为新消息开新 run）。若要网页也像 QQ 一样
consume-first（打字直接算回答），需动发送协议前后端两头，另立任务。
