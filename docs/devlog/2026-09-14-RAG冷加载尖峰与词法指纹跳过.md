# RAG 冷加载尖峰三连：从 6.6s 盲区到词法指纹跳过

> 日期：2026-09-14
> 关联：[RAG 冷构建超时两级 O(n²) 修复](./2026-09-13-RAG冷构建超时两级复杂度修复.md)（前情）
> 提交：`ad2f65a7`（install 分段探针）、`2210eec6`（宿主侧分段计时）、`78cc138c`（词法指纹跳过）、`52102276`（白名单）、`04b6cecd0`（死代码清理 + 超时进度留存）

## 现象

用户报三个 run（约 02:01–02:06）自动召回全部 ~15s 超时。RAG_PROBE 的 late completion 三条全中。此前 01:39 也有一单（15.10s）。

## 排查链

### 第一层：账面只有 8.5s，还有 ~6.6s 盲区

01:39 那单的探针：`index_cache_get` 8.0s（冷加载）+ memory 0.4s + 检索 0.1s ≈ 8.5s，但预算打满 15.1s。剩余 ~6.6s 无处安放——已知诊断盲区：`queue_wait_ms` 只测 Python 连接端锁，**宿主内每 owner 锁等待不可见**。

### 第二层：给盲区装探针

两级补齐（`ad2f65a7`、`2210eec6`）：

- worker install 内部拆 `install_tokenize_ms` / `install_structure_ms`（此前 `index_install_build` 是一个黑盒数）；
- 宿主 `handle_request` 向成功响应注入 `host_queue_ms`（到达→派发）与 `host_upstream_ms`（client._request 全程，含每 owner 锁等待）。

### 第三层：真实案例推翻了盲区假设

用户聊天几轮后再看日志：三个 run 全部对上 late completion，且新探针**当场洗清了宿主的嫌疑**——`host_queue_ms=0`、worker 全程 115–128ms。真正的模式在别处：

- 02:01 与 02:04 各自做了**整表增量重灌**（16,866 / 20,316 条，install 5.7s / 6.8s）；
- `forced_resync: true`，即 snapshot baseline revision 每轮都被业务写入（file refresh、memory upsert）推着变，revision 一变就走 `revision_resync_forced_index_get`（force=True）；
- 于此同时每轮的来源级重建把整来源 chunk 行的 `indexed_at` 全部推新——**水位增量读出来的 delta 本身就近全表**。

### 关键认知：水位复用救不了

最初设想「让 forced resync 保留水位做增量」。但数据说明行是真的变了——变的只是时间戳，正文没动。水位机制按 `indexed_at > cursor` 判变更，无法区分「内容重写」和「时间戳重写」。**所以修法从「复用水位」变形为「install 指纹跳过」**：在 install 入口对每条 upsert 算词法指纹（对齐 Python `delta.py` 契约：版本号/时间戳不参与 digest），与现存条目一致的直接保留，不分词不动账目。

### 手滑插曲

指纹函数第一版把 Python 的 `"\x1f".join(...)` 语法直接搬进了 TS——worker 起不来，基准脚本当场抓住（`"\u001f".join is not a function`）。基准/协议测试先行的好处又兑现了一次。

## 结果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 5000 条整表重写（仅时间戳变） | 全量重新分词 | **48ms** |
| 2 万条 install（事故同规模） | 5.7–6.8s | 仅真实变更文档分词 + 全表指纹哈希（亚秒级） |
| 探针计数 | — | `install_skipped_documents` 直接报告空转重写量 |

协议套件 62/62；跳过语义显式验证（重写后搜索结果逐条一致、真实变更可见）。

## 续章：指纹生效后的「最后一个 15s」（run-a3c681261435）

指纹上线后用户再报一单冷启动超时。探针显示已知病理全部消失——delta 只扫 3,447 行（不再是全表）、install 253ms、宿主零排队、检索 152ms，索引段合计 ~2.5s，但预算仍打满 15s，且超时后 1.4s 才收尾完成。

### 又一次误诊与更正

最初怀疑「Python 侧 `load_index_documents` 全量装载 8s」。完整读控制流后证伪：`_selected_backend` 恒返回 `typescript`，`get()` 的 TS 分支**无条件早返回**，Python 全量装载那段代码**根本不可达**；01:39 探针里 8s 的 `index_ts_document_load` 是包在 worker sync 外层的标签（install 6s 主导），不是 Python 装载。由此，之前对「为什么 install 这么快还需要 15s」的怀疑对象（Python 全量装载）并不存在。

### 两项落地

1. **删除不可达的 legacy 块**（`04b6cecd0`，-48 行）：`load_index_documents` 全量装载 + 来源合并 + 带 documents 的 `_build_index` 调用——Python 后端时代的路径，TS 迁移后成为死代码。`force` 语义不受影响（只作用于缓存捷径跳过）。
2. **超时进度留存**：这 15s 里 ~12s 无法归因的根因是——超时取消会拆掉 observation 上下文，per-source `progress` 数据随之蒸发（这就是本次探针 stage_ms 为空的直接原因）。`_search_with_timeout` 超时分支现在会在上下文销毁前把 `source_progress` / `pending_sources` 快照打进 WARNING 日志。

### 当前状态

- 已知病理全部修完：O(n²) install、指纹跳过空转重写、合并丢 ID、诊断空转、死代码；
- run-a3c681261435 的 ~12s 是最后一个未归因盲区——下次复现时，超时进度快照 + 三段探针（Python → 宿主 → worker）可以直接点名卡在哪个来源的哪个阶段。

## 终章：4.7s 冷启动的完整账本与 10s 窗口定案

指纹跳过上线后，用户复测报「4.69s，没超时但偏慢」。LoopScope span 首次给出完整分段：`index_worker_restore_check` 4,085ms（磁盘快照恢复，`disk_index_reused: true`，不再触发分词）+ memory 准备 356ms + 检索 250ms。

### C 基准：解析不是大头

用 C（mmap + 手写 JSON 扫描器 + FNV 哈希表）与 Node 同机同文件对照：

| 实现 | 读文件 | 解析 + 建表 | 合计 |
|---|---|---|---|
| C（-O2，3 轮） | ~0ms | 193ms | ~0.2s |
| Node（readFileSync + JSON.parse + Map） | 364ms | 262–307ms | ~0.63s |

C 仅快 3 倍——V8 的 `JSON.parse` 本就是优化的 C++。**由此发现 4.1s 的外层探针数值是嵌套括号**（restore_check / database_load / cache_get 三者同为 4085），「纯恢复」实际只有 ~0.7s（读 370ms + parse 260ms + 建表 50ms），其余是 worker 启动税（~320ms，bundle + jieba 原生绑定）、增量同步（~1s）、九来源调度与 IPC 零碎。**「恢复 4.1s」是外层括号，不是单段成本。**

顺带证伪了 mmap 设想：mmap 的「0ms 读」是把 IO 藏进了扫描缺页；Node 路径里省不掉的是 UTF-8→UTF-16 解码，mmap 化收益上限 ~300ms，真正的零拷贝恢复需要二进制格式 + native addon，不值得。

### 定案：窗口 5s → 10s（commit b7055d802）

预热方案被内存账否决：实测每个热 owner worker 常驻 **358MB** RSS，按「前 20 活跃 owner」预热即 ~7GB，不收敛；缩小到 K=3 又只剩边际收益。用户拍板：**把自动召回超时窗口从 5s 放宽到 10s**——冷启动 ~4.7s 首轮稳稳完成（此前 5s 窗口压线、随时误判），后续查询毫秒级，代价仅「隔了很久的第一句多等几秒」。

三轮 devserver 回放验证冷启动稳定性：4,116 / 4,141 / 4,156ms（±20ms，纯物理成本），warm 7ms。

## 教训

1. **盲区要靠探针显形，不能靠推断填数**——「6.6s 大概率是宿主排队」的推断是错的，装上探针后宿主 15 分钟就洗清了嫌疑，真凶在 install 的重复分词。
2. **增量机制的成本模型要看「行的什么变了」**：`indexed_at` 水位判的是「行动过」，不是「内容变了」。来源级重建整表推时间戳的设计，会把增量退化成全量。指纹（内容 digest）和水位（时间戳）是互补的两层，缺一不可。
3. **修方向要允许被数据改写**：开工前认定的方案 1（水位复用）在深挖后被证伪，真正的杠杆在 install 指纹。如果硬按原方案做，6.8s 一秒都省不下来。
4. 探针常驻化是对的：`install_skipped_documents` 让「空转重写量」成为每次冷加载的常设观测项，下次抖动一眼定位。

## 教训（续）

5. **探针标签的命名会骗人**：`index_ts_document_load` 听起来像「TS 的文档装载」，实际是 worker sync 的外层计时——据此误判出一段「8s 的 Python 装载」。归因前要读标签的产生代码，不能只读标签名。
6. **不可达代码的认定要靠「常量推导」**：`_selected_backend` 硬编码返回 typescript，是判定那段分支永不可达的硬证据；单看调用形态会觉得它「随时可能被走到」。
7. **诊断数据要活过它自己的取消**：超时取消 = 上下文拆除 = 进度蒸发的连环坑，在取消点显式留存快照，比事后加更细的探针更管用。
8. **外层探针是括号不是分段**：`restore_check` / `database_load` / `cache_get` 三个数值完全相同即嵌套关系的信号——把外层括号当成单段成本，会得出「解析很贵」的错误结论（实际纯恢复仅 0.7s）。
9. **内存换时间的方案要先量 RSS 再定 K**：预热直觉上是「小改动」，实测 360MB/owner 后才发现「前 20 活跃 owner」≈7GB 不收敛。任何常驻类方案先测单实例占用，再谈规模。
