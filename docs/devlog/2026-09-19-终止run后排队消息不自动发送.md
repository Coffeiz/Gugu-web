# 终止 run 后排队消息不自动发送：claim 竞态窗口 + 排水无重试，以及取消标记的代际泄漏

日期：2026-09-19
关联：`frontend/src/components/common/gugu-chat/composables/useChatStream.ts`、
`backend/app/api/v1/agent.py`、`backend/agent/llm/genstream.py`、`backend/agent/gateway/web.py`

## 现象

用户点「停止」终止正在跑的 run 后，终止前排在输入框上方排队条里的 pending 消息不再
自动发送，永远停在「Queued」状态。时灵时不灵——有时停止后排队消息立刻正常接续发送，
有时卡死。伴随场景：页面刷新后续看（resumeStream）中排队再停止，失败率明显更高。

## 排查过程与弯路

这个 bug 排了两天，中途推翻了三次自己：

1. **第一嫌疑：后端排队 run 静默死亡**。用测试账号 + 纯 API 复现出「排队消息落库但
   永远没有回复、`active:false`」后，一度以为是后端把排队的生成任务杀了。加了从
   `_generate` 入口到 runner 首事件的全链路 PQPROBE 探针 + SIGUSR1 任务栈转储，结果
   复现越来越不可控：有时任务跑完所有探针却没回复，有时正常。浪费了大量轮次后才意识到
   **API 复现的时序根本不对**——模型太快，终止到达时原 run 经常已经自己跑完，排队 run
   已接管会话，此时「终止」打在接管者上是**正确行为**，不是 bug。
2. **第二嫌疑：取消标记误杀接管者**。终止端点读快照（拿 owner_run_id）与写取消标记之间，
   排队 run 可能已经 `begin` 接管会话；会话级标记（`genstream:cancel:{sid}`="1"）会把这个
   刚接管的 run 一起杀掉。这条是真实存在的竞态，顺手修了（见下），但不是用户报告的主因。
3. **真凶（前端探针定位）**：浏览器完整流程 + `__pqLogs` 排水探针，看到
   `drain: dispatch result=false stillInQueue=true` 且 `send()` 从未被调用——失败发生在
   `dispatchPendingQueueItem` 的 **claim** 环节。手动 curl claim 端点复现
   `{"claim_token":null}`，对照代码：

```python
# agent.py claim_session_pending_queue_item
if await genstream.is_active(session.id):
    return {"claim_token": None, "reason": "session_active"}
```

## 根因

点「停止」后前端立即排水（`drainPendingQueue`），但后端 cancel 的收口有最长约 5 秒的
窗口：跨 worker 时终止端点只能写 Redis 取消标记，由 run 心跳在 5s 周期内发现并自杀，
之后才发布 done、快照才变非 active。在这个窗口内 claim 一律返回 `session_active`。

旧排水的处理是：

```ts
if (!dispatched) {
  if (!drainViewIsCurrent()) return
  if (!pendingQueue.value.some(...)) continue
  return          // ← 放弃，且没有任何重试调度
}
```

第一次 claim 撞上收口窗口 → 排水整体 return → 此后再没有事件触发新的排水 → 队列
永远无人消费。窗口是竞态，所以时灵时不灵；刷新续看场景失败率更高，因为 resume 流的
abort/cancel 与排水几乎同时发生。

## 修复

### 前端：session_active 等待重试（主修）

`useChatStream.ts` 排水循环：claim 闭包记下 `response.reason`；`!dispatched` 且条目
仍在队列时，若 `claimReason === 'session_active'` 则等 2s 重试同一条（上限 8 次 ≈ 16s，
足以覆盖跨 worker 心跳窗口），重试期间保持视图校验（切走/开始流式即退出）。重试耗尽
才维持旧的放弃语义，避免不可派发的条目无限循环。

### 后端：取消标记按 owner run 归属化（附带加固）

`genstream.request_cancel(session_id, owner_run_id)` 把快照 owner 写进标记值；
`is_cancelled(session_id, owner_run_id=None)` 的新语义：

- 带 run 归属的调用方精确比对；
- 不带的（loop 安全边界等）与当前快照 owner 比对——标记指向的 run 已不是活跃 owner
  即为过期标记，顺手删除，不再误杀接管会话的排队 run；
- 旧版万能值 `"1"` 与快照 owner 为空的中间态保持 fail-safe（认账）。

这封掉了「终止端点读快照与写标记之间，排队 run 接管后被误杀」的另一条丢失路径。

## 验证

- 浏览器完整流程：发长消息 → 流式中刷新 → 续看 → 排队 → 点停止 → 排队消息在
  ~20s 内自动发送并收到回复，排队条清空（修复前 15s+ 仍卡在 Queued）。
- devserver：后端 `pytest -k 'pending_queue or genstream or cancel'` 41 passed；
  前端 chatPendingQueueDispatch/Storage vitest 9 passed。

## 教训

- **API 复现必须钉住时序前提**：复现「终止对排队的影响」前先确认 `active:true` 且
  快照 owner 仍是原 run，否则测的是另一个（正确的）行为。模型太快就换长输出保窗口。
- **mutagen 双向同步会吃掉本地 revert**：本地 `git checkout` 清掉的探针文件会被
  devserver 侧旧版本覆盖回来，清探针后必须核对 diff 再 flush。
- 前端探针（`window.__pqLogs` 环形日志）比后端日志更快定位「UI 没调到」类问题——
  这次三天的排查里，真正一锤定音的是 5 行前端 dbg。
