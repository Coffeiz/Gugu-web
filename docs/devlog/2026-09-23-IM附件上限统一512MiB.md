# IM 附件上限统一至 512 MiB 并流式暂存

- 日期：2026-09-23

## 背景

QQ 入站附件仍保留单附件 50 MiB、单消息 100 MiB 两层限制；这与聊天附件已经
使用分块暂存、由 Nginx 统一限制请求体至 512 MiB 的策略不一致。此前 IM 下载还
把全部网络块放在列表里再 `join`，提高上限会让大 FLAC 等媒体产生数倍于文件的
短时内存占用。

## 改动

- IM 入站移除重复的单附件 50 MiB 门槛，统一使用单消息附件总量 512 MiB；有
  `Content-Length` 时按剩余额度提前拒绝，无长度时按实际流量累计拦截。
- 附件下载改用 `SpooledTemporaryFile`：8 MiB 内存阈值以上自动滚到临时磁盘；
  大于音频整字节处理门的文件复用 `chat_attach.stage_stream`，不整包读入内存。
- 将 64 MiB 音频 materialize 门集中在 `chat_attach`，Web 与 IM 共用该策略。它
  只控制转码等需要整字节的处理，不是上传拒绝上限；大音频原样流式暂存。
- 超限作为结构化入站结果传给 IM 主流程，用户会收到文件大小提示；仅有超限附件
  的消息在 Agent 调用前结束，避免空文本被模型回复成空消息。混合消息仍继续处理
  已接收附件和文字。

## 验证

- IM 附件有无 `Content-Length` 时均按同一消息总量限制拒绝超限流量。
- 验证大附件进入流式暂存，内容和来源消息元数据保持一致。
- 验证超限提示可见，且附件-only 超限消息不会继续进入 Agent。
- `tests/test_im_media_ingress.py` 与 `tests/test_chat_attachments_ownership.py`：
  47 passed。
