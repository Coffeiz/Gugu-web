# 单容器内置 Rootless Shell：方案收敛、实施与 fnOS 验收

## 结论

单个 `gugu-web` 镜像现可在 NAS 单容器部署中运行 Shell 沙盒：外层应用容器在 fnOS 中启用“使用最高权限执行容器”（Docker privileged），容器内部由专用非 root 用户运行 Rootless Docker 和 `sandboxd`；Shell 命令仍在临时的 `gugu-sandbox-*` 子容器执行。无需 Compose、宿主 Docker Socket 映射、独立 `sandboxd` 常驻容器或手动导入沙盒镜像。

用户最初查看了旧的 `gugu-web` 容器，Admin 因此显示 Rootless 未启用、执行镜像不可用；后来确认测试运行的是新建且启用了高权限的 `gugu-web2` 容器，Shell 沙盒已成功运行。这个过程说明 NAS 上核对端口和容器实例是验收的一部分，不能把旧容器状态当成新镜像的结果。

这是一种面向可信个人单用户的便捷部署方式，不代表外层应用具备多租户级隔离。privileged 外层容器被攻破仍有较高宿主机风险；内部 Rootless 主要约束其创建的执行容器，不能消除外层风险。

## 背景：目标为什么从“单镜像”逐步收敛到“容器内 Rootless”

目标是让普通 NAS 用户导入一个镜像、配置数据目录和端口后即可使用 Shell。此前的分体部署把沙盒管理器放在独立服务中；把 `sandboxd`、代理和多个执行镜像都改成 NAS Compose 项目，虽然可行，但没有满足“只部署一个镜像”的产品目标。

早期的一体化实现已经将 manager 和执行 runtime 纳入 app 镜像，并补齐 bundle 校验、候选 app 组装、离线包和 release digest 传递。但 C9（`c9e9d6a21`）的 embedded manager 仍需要访问宿主 Docker daemon。对 NAS 单容器用户而言，这通常意味着手动找到并映射 `/var/run/docker.sock`；fnOS 面板的存储映射选择器并没有把 socket 作为普通目录映射选项呈现。Docker Socket 还会把宿主 Docker 控制权交给 app，与“少配置、个人快速开箱”的目标不符。

因此最终目标不是恢复 Compose，也不是把命令直接放到 Web 进程执行，而是：保留已有逐命令容器执行边界，把 Docker daemon 移入 `gugu-web` 容器，使用 Rootless Docker；外层 privileged 只作为该内层 Rootless daemon 所需的运行前置条件。

## 过程时间线

### 1. C9：内置 manager 与 bundle 的代码基线

2026-09-28，分支逐步完成一体化沙盒的第一轮实现：

- 明确 `embedded`、`external`、`disabled` 管理模式，embedded app 可以托管 `sandboxd`；
- 在 app 镜像中校验并导入固定 digest 的 runtime bundle；候选 app 必须来自同一轮构建与验证；
- 收敛默认、离线、开发与生产 Compose 的 manager 职责，避免默认部署重复启动 `sandboxd`；
- 增加 bundle 归档完整性、离线 Shell smoke、发布候选 digest、执行超时清理和部署模式回归。

这一阶段解决了“镜像中包含什么、发布时是否能保证 app 和执行镜像匹配”的问题，但没有解决单容器不依赖宿主 Docker Socket 的核心障碍。C9 的内置 manager 仍通过宿主 daemon 创建执行容器。

对应的阶段记录包括 `DEPLOY2 Phase 1.5.3/1.5.4、1.6、1.7、1.8.1–1.8.3`。其中旧阶段日志里的宿主 socket 拓扑是当时的架构记录，不是本次最终单容器方案。

### 2. 回退后探索 Bubblewrap，随后澄清目标

2026-09-29，用户要求撤回分支上的沙盒/部署改动，检查实现状态，并提出“单容器 Bubblewrap 可运行”的方案方向。分支先记录了 Bubblewrap Phase 0 的 fnOS 可行性探索。

这段探索暴露了关键歧义：Bubblewrap 是否是用户最终希望采用的沙盒技术，还是只是在确认单容器是否能摆脱 Docker Socket。随后用户澄清，期望回到 C9 的内置 Docker 沙盒基础上，给外层容器 privileged 能力，并在其中运行 Rootless Docker；不继续 Bubblewrap。Bubblewrap 因而不是最终实现，也不应作为部署文档或后续架构依赖。

### 3. 以 C9 为基础改成容器内 Rootless Docker

用户确认可以接受外层 privileged 的信任边界，且单用户单镜像部署不把 cgroup 作为前置条件后，PRD-DEPLOY-2 从“embedded app 调用宿主 Docker Socket”改为“embedded app 内部运行 Rootless Docker”。决策要点：

- 继续复用 `SandboxdClient`、`SandboxdServer`、`DockerSandboxExecutor` 和逐命令临时容器；
- app 容器不探测、不挂载、不连接宿主 Docker Socket；
- 内部 Rootless daemon 使用专用非 root UID、固定 subordinate UID/GID、私有 data-root 和仅容器内 Unix socket；
- manager 仅访问内部 daemon；执行容器只挂载经过所有权和路径策略校验的用户工作区；
- daemon、镜像或必要内核能力不可用时 Shell fail-closed，不回退到宿主 Rootful daemon 或 app 本机执行；
- 默认一体化 Compose 的 app 也改用内置 runtime；Compose 额外保留 SearXNG 与受限 updater，但不再需要单独沙盒服务或执行镜像；
- `docker-compose.prod.yml` 的分体业务部署继续保留 external Rootless manager 边界；
- 不要求 cgroup v1/v2。缺少 cgroup 时不提供内核级 CPU、内存、PID 硬限制，只保留实际有效的应用层并发、超时、输出限制、取消与回收。

### 4. 打包与 devserver 容器验证

Rootless daemon 及其用户态网络、overlay 和 UID 映射依赖随 app 镜像构建，最终镜像还需携带同次构建产生并经过摘要校验的执行 bundle。固定运行时来源为 Debian Trixie 仓库签名包，包含 `docker.io`、`docker-cli`、`rootlesskit`、`slirp4netns`、`fuse-overlayfs`、`uidmap` 及所需运行库；不从浮动 tag 的第三方镜像复制未经固定的二进制。

devserver 冒烟验证记录：

- 外层 app 容器以 `--privileged` 启动，只挂临时 `/data`、`/config`，没有宿主 Docker Socket，也没有额外 sandboxd 容器；
- 内部 Docker API 位于 `/run/user/1000/docker.sock`，daemon 的 `SecurityOptions` 报告 `rootless`；RootlessKit 使用 `slirp4netns`；
- bundle manifest 校验并导入后，内置执行镜像可用；真实 `sandboxd execute` RPC 与 `network=none` Shell smoke 成功；
- 执行容器以 UID/GID 65532 运行，在 `/data/users` 下授权的临时工作区完成 bind mount 读写；外层容器重启后 daemon、manager 健康恢复，bundle 镜像仍可使用；
- 测试内核为 Linux `7.0.0-31-generic`，Docker 报告 cgroup v2、`CgroupDriver=none`。这证明 cgroup 不是本方案启动的硬前置条件，但不代表具备 cgroup 硬资源限额，也不能代替 fnOS 内核验证。

开发过程中曾遇到 Docker Hub 的 Dockerfile frontend、基础镜像 metadata/layer 请求超时；在网络请求未完成时没有把不完整镜像当成候选交付。构建和包导出转到 devserver 执行。fnOS 导入只接受普通 `.tar`，因此最终交付未压缩 tar，而不是 `.tar.gz`。

### 5. fnOS 真机确认及一次误判

首次看到 Admin 显示“当前 Docker 不是 Rootless”“执行镜像不可用”时，后来发现检查的是旧的 `gugu-web` 实例，而不是新导入并以最高权限启动的 `gugu-web2`。新容器还可能使用不同宿主端口；打开旧端口就会继续看到旧实例状态。

切换到正确的新容器后，用户确认 Shell 沙盒成功运行。这验证了该 fnOS 机器在 privileged 外层容器条件下允许本方案所需的内部 Rootless Docker；也证明最初那次“不工作”是实例/端口选错，不是新镜像 Rootless sandbox 实现失败。

## 主要阻碍与处理

| 阻碍 | 影响 | 处理与结论 |
|---|---|---|
| 单容器面板不便映射宿主 Docker Socket | 普通用户难以配置；Socket 等同宿主 Docker 高权限入口 | 不再依赖宿主 Socket；在外层容器内运行专用 Rootless daemon |
| 单个 app image 可能只是基础层，不含 runtime bundle | CLI 存在也不代表 daemon 或执行镜像存在，Shell 会显示不可用 | 把 daemon 和同次构建的 bundle 纳入最终一体化镜像；候选检查摘要、image ID 与归档完整性 |
| Rootless 需要 user namespace、subuid/subgid、rootlesskit、slirp4netns 和 overlay 支持 | 不同 NAS 内核、Docker 面板安全限制会导致启动失败 | 外层 privileged，内部 daemon 仍以非 root 运行；检测失败就报告原因并 fail-closed |
| NAS 侧状态核对可能连错容器或端口 | 旧容器状态被误认作新镜像故障 | 验收必须核对实例名、实际映射端口与 Admin runtime 状态；本次更换到 `gugu-web2` 后确认成功 |
| runtime 与执行 bundle 增大镜像并让发布链更复杂 | 镜像构建、候选验证和离线导入成本上升 | 同提交构建、固定来源、校验 manifest/digest/image ID；当前候选约 1.49 GB |
| fnOS 导入文件格式限制 | `.tar.gz` 不能直接用于该面板导入 | 交付普通 `.tar`，记录 SHA-256、镜像 ID 和大小 |
| 无 cgroup 控制器 | 不能承诺内核级 CPU、内存与 PID 硬上限 | 不把 cgroup 作为运行条件；如实报告限额能力，仅保留有效的应用层限制 |
| privileged 外层容器权限较高 | app 被攻破可能带来宿主机风险 | 用户接受个人单用户快速部署的信任取舍；明确不面向多租户、公网和业务服务器 |
| Bubblewrap 与 Docker 内置沙盒目标混淆 | 可能继续开发不符合最终产品目标的技术路线 | Bubblewrap POC 仅作短暂探索；最终选择内部 Rootless Docker，不把 Bubblewrap 纳入产品方案 |

## 本轮验证边界

**已由自动化/容器测试验证：**Rootless daemon 与 socket 边界、bundle 导入和校验、embedded 管理器生命周期、路径/UID 映射、容器内授权目录读写、`network=none` Shell smoke、失败时不回退、超时清理及默认/离线/分体 Compose 契约。2026-09-28 阶段记录的定向 pytest 集合分别覆盖 106、114、153、189 项；这些是不同阶段和不同范围的测试数量，不应相加当成一次完整套件结果。release 脚本、workflow YAML 和 Compose YAML 也有对应定向校验。

**已由用户在 fnOS 确认：**正确的高权限单容器实例可启动并运行 Shell 沙盒。

**仍需独立验收，不因 Shell 冒烟通过而推定完成：**完整 PTY 与 MCP stdio 链路、受控 egress 全流程、并发/取消/超时/输出限制在 NAS 上的组合行为、重启和升级持久性，以及实际 fnOS 内核下执行容器可见性与其他用户路径隔离。详见当前 [PRD-DEPLOY-2](../prds/PRD-DEPLOY-2-一体化镜像内置沙箱管理.md) 验收清单。

## 架构决策记录

- **选择：**外层 privileged `gugu-web` + 容器内部 Rootless Docker + embedded `sandboxd` + 逐命令临时执行容器。
- **不选择：**宿主 Docker Socket 作为单容器 Shell 依赖；Bubblewrap；app/worker 进程直接执行用户命令；Rootless 不可用时降级 Rootful 或本机执行。
- **默认 Compose：**仍是 integrated app，并加 SearXNG 与受限 updater；updater 单独持有宿主 Docker Socket 做更新 RPC。该 socket 不传给 app 的沙盒管理器。
- **分体部署：**继续使用 external Rootless manager 的独立部署边界，不将单容器内部 daemon 责任扩展给业务 app。
- **信任边界：**面向用户自行管理的个人单用户 NAS；不声称具备多租户安全等级。
- **资源策略：**cgroup 不作为单容器运行前置；没有内核控制器就不宣传内核硬限额。
