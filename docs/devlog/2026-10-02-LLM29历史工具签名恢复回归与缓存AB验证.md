# LLM-29 历史工具签名恢复回归与缓存 A/B 验证

## 问题

用户在 LLM-29 迁移后继续观察到下一 run round1 的缓存读取量低于上一 run 最后 round。逻辑消息面板显示前缀相同，因此本次排查同时比较实际 SDK 请求结构、数据库恢复后的 Area 和加密 Provider 状态。

## 根因

迁移后的实时消息与持久恢复消息形状不同：实时工具块在 `content`，恢复的中性 row envelope 在 `content_json`。Anthropic 驱动仍直接读取 `content` 来确定有效历史工具 ID，使恢复路径返回空集合，过滤掉历史 thinking/signature。

因此同一个 run 内缓存正常，跨 run 恢复却改变请求前缀。续接标志为 true 也不能证明历史签名全部保留。旧路径还会将过滤结果重新持久化，已有会话丢失的签名不能靠重启恢复。

## 修复

工具 ID 改为从实际 Provider 历史投影读取，不新增另一套 content/content_json 兼容解析。保留签名只修复出站副本，不改变 canonical 消息区域或普通消息持久化边界。

新增行为回归测试覆盖数据库提交与恢复、两轮工具签名续接、已裁剪工具状态排除以及 canonical 摘要不变。该测试在旧代码下失败，修复后通过。

## 真实调用验证

在 devserver 使用会话 BYOK 进行两轮独立缓存命名空间的 A/B。复用导出上下文生成真实签名工具轮，执行只读 schema 工具，并通过临时 SQLite 恢复中性消息。旧组模拟原读取器，新组使用修复驱动；充分预热上一请求后发送下一轮。

两轮旧组都在索引 5（从 0 计数）的历史消息发生变化，cache_read 分别从 33,189 降至 31,464、从 33,188 降至 31,463。修复组无历史前缀差异，分别完整保留 33,189、33,191 个缓存 token。

修复后比例仍低于预热请求约 100% 的比例，原因是新增最终回复和问题扩大输入，不代表旧前缀损坏。排查须同时报告 cache_read、fresh、总 input 和实际请求差异，不能只比较比例。

原导出缺少完整签名字节，持久状态已被覆盖，因此未声称逐字节重放历史故障请求。完整方法与数据见 [缓存验证报告](../reports/OPT-Cache-Strategy-2026-10-02.md)。

代码已同步到 devserver；确认无运行中的会话后按运维白名单重启服务，四个单元均为 active，后端 `/health` 返回正常。修改保留在工作区，未提交。
