# 非聊天 LLM 协议路由与推理输出收口

## 问题与根因

Responses 配置下，问候仍调用 Chat Completions，且只有 180 token 输出预算。MiniMax 的兼容 Chat 返回可包含 `<think>` 内容；预算耗尽时可能只有推理、没有问候正文。会话标题和摘要也存在同类协议误选，40/80 token 预算会使标题退回原输入、摘要为空。

进一步检查发现，压缩/反思的文本与 JSON 入口、邮件翻译、管理员能力检测和多模态检测也未全部按配置选择 Responses。问候不读取对话持久化推理状态，本次故障不是历史 reasoning item 注入导致。

## 修复范围

- 新增轻量 `agent.providers.standalone`，统一问候、标题/摘要和邮件翻译的协议路由、客户端关闭及可见正文提取，不载入或写入主对话推理状态。
- 支持推理的模型在有限输出预算下至少预留 4096 token，业务层继续约束标题、摘要和邮件结构；不支持推理的模型保持原预算，分支的 `None` 预算保持原语义。
- `provider_runner` 文本、JSON 和历史追加入口共用非 Anthropic 路由，Responses 继续使用现有分支投影；保留历史、工具、缓存及用量采集，显式思考覆盖仅修改请求副本。
- Responses 正文优先提取结构化 `message` 项，忽略 `reasoning` 项；仅在结构化 output 缺失时读取兼容聚合字段。Chat 正文及 JSON 提取剥离 `<think>`，避免解析推理中的 JSON。
- 问候缓存版本更新，避免继续展示旧的错误缓存；锁超时覆盖模型请求窗口，错误只记录异常类型，原始异常进入受限诊断日志。
- Admin 能力检测发送原生 Responses 请求，图片检测使用 `input_image`。Responses 音频/视频尚无已验证的探测格式，明确返回无法判定，不再误调用 Chat 后推断其能力。

## 验证

devserver 上 158 项相关 pytest 全部通过，覆盖问候缓存与协议、标题/摘要、分支投影与缓存、压缩/反思、邮件、能力探测、定时任务及推理策略。

真实模型探针只使用合成输入，显式允许真实 LLM 调用，只读模型配置，不保存请求正文或凭据。MiniMax-M3 与 M3.1 的标题、摘要、JSON 和反思共八个目标用例均完成且无推理混入；其中一次 M3 反思遇到上游 529，单独复测成功。另验证共享入口的 Chat、Anthropic 以及 Responses 邮件翻译，正文非空、邮件结构有效。

缓存测试的 adapter 夹具改为继承完整适配器契约，Responses 夹具改为提供实际 message output；原行为断言保留，没有增加生产 fallback 来迁就不完整夹具。

本次不修改主聊天流的历史回放或推理持久化策略，不修改用户运行配置，也不自动提交、推送或触发 CI。
