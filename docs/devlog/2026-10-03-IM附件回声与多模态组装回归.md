# IM 附件回声与多模态组装回归

## 现象与根因

- 私聊用户发送图片及问题后，网页展示一条只有相同附件的助手消息，没有实际回答。
- 群聊未触发 Agent 的图片消息也出现相同助手附件气泡。
- devserver 只读查询确认：用户附件已持久化，但没有对应助手消息。消息接口为所有角色补附件时间线，错误地把用户附件包装成助手事件；旧助手消息没有时间线时也会被重复展示。
- 私聊真实 run 在模型调用前失败：`Canonical batch 不支持 block 类型：image`。当前媒体由附件入口构造，但重构后的 batch 校验未接受媒体块。音频和视频也受相同边界影响。
- 媒体与引用资料混合时，canonical 工具/事件提取还可能仅保留引用和文字，丢弃媒体。

## 修复

- 仅为已有展示时间线的助手消息补齐附件；用户附件和无时间线的旧助手附件仍由原消息展示。
- 复用统一媒体类型集合，允许当前请求内存 batch 承载媒体，继续拒绝 Provider 工具 wire。
- 引用/上下文事件与媒体混合时保持媒体原位置；不改变数据库附件引用和已持久消息的写入策略。

## 验证

- 修复前新增 46 个行为用例全部失败；修复后通过。
- devserver 相关 9 个测试文件共 148 项通过，包含消息 API、上下文组装与投影、引用上下文、IM 媒体入口、飞书媒体和 runner。
- 消息展示矩阵覆盖 Web、QQ、飞书、微信私聊/群聊及图片、音频、视频、PDF、文本附件；同时验证增量拉取与旧助手附件不重复。
- 多模态组装覆盖 Anthropic 图片/视频、OpenAI 图片/音频/视频，分别验证有无引用资料、文字和媒体保留、已存用户消息不重复写入媒体。
- 真实故障 trace 无模型调用，故复现采用隔离数据库和组装行为测试，没有向真实会话发送测试消息，也没有改动用户运行配置。

## 部署边界

代码同步后，常驻后端/worker 需要重启才能载入修复；单纯刷新网页不更新 Python 服务。
