# 压缩与反思分支缓存前缀回归

## 现象与调查

当天用量账本确认：一次会话压缩输入 244,076 token，缓存读取 55,936，命中率 22.9%；最初八次记忆反思合计约 44%。同会话普通对话大多接近 99%，反思有的仅命中 128 token，有的超过 90%。这不是面板漏算缓存输入。

反思低命中同时出现在 Responses 与 Anthropic，不能简单归因于 Responses 推理续接。部分反思等待统一闲置窗口 270 秒，供应商缓存时效是额外变量；但立即执行的反思也曾仅命中 16%，压缩在同一 run 中也由主请求约 87% 降至 22.9%。

## 确认的根因

1. Area 重构把冻结 snapshot 与 ledger entries 分离。反思快照只捕获 `entries`，漏掉 `request_prefix`。反思因此不是主请求的完整前缀；后续 Knowledge 分支可能复用已经预热的反思前缀，从而出现高命中，并不能证明与主对话对齐。
2. `compact_context` 已取得 provider projection，`_branch_prefix_history` 又把它转成裸列表交给 canonical renderer。真实只读 trace 重放发现索引 33 起结构被改写，364 条变成 359 条。合成 wire 工具轮同样能复现二次渲染丢失 `tool_use`。
3. 反思缓存探针把 ProviderConversation 当普通对象估算，且对象估算走 trace 展示裁剪。长前缀被低估至不足 32K，低命中未触发告警。展示 token 账本不受此问题影响。

## 修复契约

- 同进程 ReflectionSnapshot.history 改为不可变 ProviderConversation，含冻结前缀与末尾 assistant，排除 dynamic tail；revision 对具体消息计算。
- `render_branch_prefix` 区分 canonical、Area 与已有 wire 投影，后者不得重复渲染。
- Owner、群/成员、Knowledge 反思保留 wire 类型；DB 历史重建的 `build_history_parts` 结果也明确包成 wire 投影。
- 压缩保留 wire 消息与准确前缀范围；持久历史校验后的截取仍保留不可变类型。
- 探针基于完整 JSON 估算前缀并计算指纹，但只返回结构化计数/指纹，绝不返回正文。
- 不增加推理续接开关或 provider 特例，不改主会话推理状态，不改后台闲置窗口、压缩阈值、摘要落库 CAS 或权限。

## 测试与结果

修复前新增三条行为回归全部失败；修复后通过。Anthropic/Responses 捕获均验证冻结前缀与动态尾部隔离。详细真实模型三组 A/B 数据见 [缓存报告](../reports/OPT-Cache-Strategy-2026-10-03.md)：反思约 0.66% → 99.46%–99.90%，压缩约 20.34% → 99.51%–99.52%。

核心压缩、反思、分支及 LoopScope 回归 172 项，Knowledge/Provider/主 loop/持久化边界 99 项，IM 与其他上下文调用链 136 项，共 407 项通过。确认门和相关模块编译通过。三条旧 IM 夹具把正式 wire 渲染 mock 成裸列表，与原有媒体清理契约已不一致；改为真实投影类型并去掉该 mock，保持原来的正文去重和媒体隔离断言。持久化接管测试改为检查 wire 内的消息正文，而不是绑定旧 tuple 容器类型。

ripwire 捕获/渲染入口的参数契约未变；质量检查报告捕获快照近期频繁修改的 churn 警告，不能称为全绿，根因修复与上述回归作为本次改动依据。
