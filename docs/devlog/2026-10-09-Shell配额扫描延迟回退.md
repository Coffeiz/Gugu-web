# Shell 全量容量扫描导致命令延迟

## 现象

默认沙盒 Shell 执行简单的目录查看命令也耗时约 80–90 秒。用户确认命令使用默认范围，没有切换到 system/宿主范围。

## 根因

本地存储后端的 Shell 路径在执行前调用配额监控准备逻辑。该逻辑会递归测量 Workspace、个人文件和项目文件根目录，并核对数据库中的文件记录；即使本轮只监控 Workspace，也会先测量全部根目录。执行期间的容量 watcher 又同步递归遍历受监控目录，执行结束后还会等待一次完整用量校准。

因此，全量对账一旦遇到文件数量多或磁盘较慢的用户目录，就会进入每次 Shell 命令的关键路径；扫描时间直接叠加到命令启动/返回时间，并可能阻塞 sandboxd 的事件循环。全量对账适合独立校准，不适合在每条 Shell 命令上同步执行。

## 处理与产品取舍

- 本地 Shell 恢复为执行前只读取 `StorageQuotaLedger`，不准备物理扫描目录，也不在命令结束前等待完整校准。
- 移除本地 Shell 运行期的全目录轮询；执行请求不再携带配额扫描根目录。
- 采用软配额：允许当前命令将用量推过上限；账本记录超额后，后续 Shell 命令在执行前被拒绝。物理容量全量校准留给独立对账/周期任务。
- 不触及同一提交中的文件同步、Telegram、回收站和前端修复。

这项取舍不承诺越限后立即同步拦截下一条命令：阻止逻辑以账本数据为准，Shell 写入须先经文件同步或后续校准反映到账本。它避免把全量遍历放回 Shell 热路径，同时保留明确的超额拒绝规则。

## 验证

- `tests/storage/test_shell_policy.py` 与 `tests/storage/test_storage_quota_ledger.py`：64 项通过。
- Python `compileall` 与 `git diff --check` 通过。
- 相关测试已在 devserver 复跑：64 项通过。
- 回归测试验证本地 Shell 热路径不会触发全量对账，且账本已超额时不会启动命令。

## 后续约束

不要在单次 Shell 调用中重新接入 `get_local_storage_quota_watch()`、同步目录测量或收尾 `reconcile_user_storage()`。如果未来需要更强的即时容量上限，应采用不阻塞命令热路径的计量/文件系统配额方案，并单独验证准确性与延迟，不能通过恢复每次全量扫描实现。
