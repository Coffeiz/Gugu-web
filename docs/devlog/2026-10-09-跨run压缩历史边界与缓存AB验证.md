# 跨 run 压缩历史边界与缓存 A/B 验证

## 问题

一个 run 压缩后，下一 run 的 Round 1 没有沿用上一 run 最后一轮的压缩前缀。压缩器在 run 内得到的历史边界与数据库持久化重建历史的边界不一致：前者可能将上一 run 的保留轮次折叠进摘要，后者仍恢复其原文，造成下一次请求前缀变化。

## 修复

调用 `compact_context()` 时传入 `messages.protected_history_start` 作为 `protected_previous_from`。压缩和后续持久历史重建由此共享上一 run 历史的保护边界。

## A/B 验证

使用真实 MiniMax provider 和合成摘要、合成对话历史做前缀 A/B；只读模型配置，不写入 Gugu 用量账本或业务数据表。旧路径第二轮 `fresh_input=14578`、`cache_ratio=0.87%`；修复路径第二轮 `fresh_input=24`、`cache_read=14683`、`cache_ratio=99.84%`。两组总输入 token 数基本相同，变化来自前缀缓存复用。

devserver 上运行现有压缩行为用例 `tests/agent/context/test_compaction.py`，结果为 60 passed。通用缓存对比诊断也已运行，统计和运行边界见 [A/B 报告](../reports/2026-10-09-OPT-跨run压缩前缀连续性.md)。
