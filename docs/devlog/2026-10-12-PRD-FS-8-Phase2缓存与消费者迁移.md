# PRD-FS-8 Phase 2：缓存边界与消费者迁移

## 结论

文件库主路径已由全量列表切换为服务端 keyset 分页。全局缓存只保留有界目录页与按 ID 详情；文件库、项目文件区、回收站、上传路径选择、音频、Mind 引用、Markdown 引用及搜索跳转不再依赖整库缓存。分页 API 已成为正式 `/files`、`/folders` 路径；旧全量列表、版本水位和数组回收站接口已移除。

缓存上限为最多 8 个目录、合计 2,000 个目录实体，ID 详情缓存最多 600 项。文件库当前目录、回收站、已删除目录内容及上传目录选择均有 2,000 项客户端硬上限，项目文件目录也按相同上限停止继续累积。排序由服务端分页参数执行；缓存键包含 scope、排序和 cursor 维度。事件能定位旧/新 scope 时只失效相关目录页，无法定位或发生重连时不再全库刷新。

## 计数决策

没有新增精确统计投影。代码审查未能证明 File/Folder 的全部 ORM、批量 SQL、同步及恢复写入都处于同一个可维护投影的事务边界；为维持精确总数而加投影会扩大正确性风险。依据 PRD §3.4，移除了文件库摘要、项目卡片和回收站的精确计数热查询/展示。项目删除确认改为明确告知项目内文件和文件夹会一起移入回收站，不再依赖可能不可用的文件计数。文件夹卡片直属文件数仍只对当前分页中的文件夹查询。

## 主要审查点

- 页面切换及账号 epoch 变化会阻止迟到响应写入新缓存；失效相关 scope 后从首屏重新取数。
- 搜索、Mind 引用和 Markdown 相对路径使用 owner-scoped ID/路径解析，冷缓存不请求全局文件缓存。
- 文件和回收站的继续加载保持各自 cursor；达到客户端上限时停止继续累积并保留提示状态。
- 上传只批量解析本次相对路径节点；音频恢复仅查有限页并保留当前曲目。
- 项目删除语义由服务端核对：项目、项目文件夹和项目文件统一软删除/进入回收站；确认提示保留该影响说明。

## 验证

- 后端：文件、文件夹、分页、回收站、项目删除及定时任务回归共 80 项通过。
- 前端：filesCache、目录分页、导航、回收站、上传、项目文件区、Mind 引用和项目文件计数共 8 个测试文件、21 项通过。
- `npm run typecheck` 通过。
- 静态搜索确认前后端运行时代码没有旧全量列表、版本刷新、全空间文件夹清单或数组回收站消费者；同时删除了已无调用者的整库/旧回收站查询 helper 和全量目录缓存接口。类型文件保留仍需的项目删除路由。
- Phase 3 百万级 PostgreSQL 基准、全量回归与 E2E 仍待执行，本记录不把上述定向测试当作发布验收。
