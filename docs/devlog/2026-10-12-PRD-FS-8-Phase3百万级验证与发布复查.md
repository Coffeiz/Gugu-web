# PRD-FS-8 Phase 3：百万级验证与发布复查

## 验证范围

在独立临时 PostgreSQL 中装载 1,025,000 个 File 与 170,001 个 Folder，共 1,195,001 个实体。数据覆盖 400,000 个文件的平面目录、深页 cursor、30,000 个同级目录、项目文件及回收站。所有标识与内容均为合成数据；未访问或修改 devserver 的数据库、用户数据和运行配置。

基准以服务端真实分页 service、100 项页大小执行；每组先预热，再测 25 次，报告 p50/p95。深页由 keyset 边界构造，运行查询不使用 OFFSET。应用层 p95 与 `EXPLAIN (ANALYZE, BUFFERS)` 均在 1.195m 数据集验证。

所有分页响应每类不超过 100 项，低于 200 项硬上限；首屏/深页 p95 均低于 500ms。最大单页深页查询为 100 个实体；回收站目录内容分别分页文件和文件夹。

对六种文件排序的首屏与深页运行 `EXPLAIN (ANALYZE, BUFFERS)`：均使用对应的 `ix_files_page_*_scope` 索引，返回 101 行（含判断 `has_more` 的一行）；首屏 shared buffers hit/read 合计约 4–107，深页约 3–15。深页比较条件下推至索引扫描，无随页数增长的 OFFSET。类型排序对应 CASE 表达式索引；`size` 的缓冲区数略高，仍远低于整目录扫描。

### 压测中发现并修复的查询计划回归

首次压测时，文件详情第二次查询重复应用了目录过滤。PostgreSQL generic prepared plan 将 `folder_id = ?` 与 `coalesce(folder_id, 0) = ?` 当作独立过滤，选中 `ix_files_page_id_scope` 和 `ix_files_folder_id` 的 BitmapAnd，实际读取平面目录 400,000 行，再对 name 排序；第 6 次执行后名称首屏 p95 超过 1 秒。

目录作用域已经由 `coalesce(folder_id, 0)` 复合索引键完整表达。移除重复 `folder_id` 条件，并让详情查询只按已授权的页内 ID、owner 和活动状态读取。复测确认 generic plan 继续使用排序 scope 索引；名称页稳定在约 2–4ms，其他文件排序和深页也全部低于 10ms p95。此修复保留 owner 和活动状态校验，页内 ID 来源仍受用户、空间和目录约束。

## 发布链路与回归

- 在隔离 PostgreSQL 上实际执行 Alembic `upgrade` 与 `downgrade`，并重复升降级循环；每轮确认 12 个新增索引创建和移除。为采集最终计划再次升级后，停止并删除整个临时数据库。生产/devserver 未执行迁移。
- 后端 `tests/storage/files`：275 项通过。
- 前端 filesCache、目录分页、回收站和项目文件同步：4 个测试文件、13 项通过；`npm run typecheck` 通过。
- 新增只读 Playwright E2E：进入个人文件目录，确认使用有界分页响应、单页不超过 hard limit、旧 `/files/all` 未被请求；有下一页时滚动并验证带 cursor 的续页请求。E2E 通过；未写入或删除用户文件。
- 对发布边界进行代码级复查：分页 API 与消费者同一分支；`/files/all`、`/folders/all`、`all_in_scope` 无运行时消费者；回滚不得恢复无界列表 API。此次未部署或推送，因此没有对线上服务做版本回滚演练。
- 失败用例中，第一次 E2E 运行因测试断言误认为前端必须显式传 `limit` 而失败；按服务端默认 100 修正断言后复跑通过。该失败未暴露产品行为缺陷。

## 结论与边界

PRD §4.2 的隔离 PostgreSQL 规模、分页 hard limit、查询 p95、索引计划与前端有界读取验收通过。未对路径解析、上传、媒体内容或 SSE 做百万级吞吐压测；这些调用链由 Phase 1/2 行为测试与本阶段全文件回归覆盖，且不再调用全量列表接口。索引 benchmark 是合成单用户数据的可复现形状验证，不代表生产硬件的绝对耗时。发布需以前后端同版本为单位执行；本阶段只完成代码级发布/回滚边界复查，没有替用户部署或推送。
