# 文件库 grep 算法性能实验

## 结论

当前改动将授权 owner 的真实只读扫描从 25.50 秒降到 19.97 秒，约快 21.7%，但仍未达到 10 秒目标。剩余时间主要用于读取并扫描正文，线程数继续增加没有稳定收益。针对两字中文短词，`pg_trgm` 仍走顺序扫描；普通全文检索和 RAG 召回不符合逐字匹配契约。

更有希望的算法是按文件保存一个基于 Python `casefold()` 文本构建的紧凑 n-gram Bloom 筛选器：先用筛选器排除绝大多数文件，再用当前逐行扫描器读取候选正文并精确核验。它允许假阳性但不能产生假阴性，因此可保留行号、上下文、大小写折叠和权限语义。本轮仅在完全合成数据上验证了筛选算法；没有在真实数据库建索引或改 schema，因此尚未在 devserver 验证它能把真实查询降到 10 秒内。

## 已核实现状与真实只读测量

- `backend/agent/tools/files/grep.py` 对每个候选文件读取正文，UTF-8 解码后逐行按字面量检查；大文件走分块读取以控制单文件内存，但仍需读取全部候选字节。没有正文倒排索引或 RAG 召回路径；`backend/agent/rag/README.md` 也明确说明文件库不参与自动 RAG。
- `backend/app/services/files/corpus.py` 按 owner、删除状态和文件空间读取元数据，逻辑路径解析后用于权限范围校验。基线工作区扫描 87,676 条元数据，筛出 48,115 个正文候选，读取 48,115 个对象，共 344,274,221 字节；最终命中 1 个文件、10 行。正文和路径值没有写入报告。
- 仅在用户授权的 owner 范围内进行低频只读测量。未在真实数据库创建索引、修改 schema/数据或配置；没有记录用户标识、正文、文件名、路径或搜索词。

| 阶段 | 优化前基线 | 已提交优化 | 当前轻量投影 | 基线到当前 |
|---|---:|---:|---:|---:|
| 总耗时 | 25,495 ms | 23,761 ms | 19,973 ms | -21.7% |
| 元数据读取 | 3,336 ms | 3,711 ms | 1,400 ms | -58.0% |
| 路径解析 | 984 ms | 992 ms | 856 ms | -13.0% |
| 候选整理 | 120 ms | 120 ms | 64 ms | -46.7% |
| 正文读取与扫描 | 20,904 ms | 18,765 ms | 17,629 ms | -15.7% |
| 进程峰值 RSS | 未采集 | 419,756 KiB | 290,884 KiB | 较已提交优化 -30.7% |

每组为单次低频真实扫描，阶段耗时按同一追踪方式采集；未用 `tracemalloc` 追踪结果作延迟比较，因为它会显著扰动耗时。正文读取量和命中统计保持相同。轻量投影主要降低了 ORM 元数据成本和内存，正文扫描仍是总耗时的主要部分。

### 原生批量字面匹配算法对照

在相同 owner 范围、相同 48,115 个正文候选上，额外验证了“操作系统原生批量固定字符串扫描 → 当前 Python 精确扫描器复核命中文件”的算法。候选路径只从 owner 过滤后的 File 元数据构造，原生扫描输出仅在进程内消费，不输出文件路径；精确复核仍使用应用存储接口和既有行语义。结果聚合为 1 个精确命中文件、10 行，与此前只读基线一致。

本次单次测量：元数据 4,310 ms、路径/候选准备 1,215 ms、原生批量正文扫描 11,601 ms、命中文件精确复核 1.3 ms，总计 26,333 ms；峰值 RSS 431,444 KiB。原生扫描阶段比此前 Python 正文阶段 17,629 ms 快约 34%，但单次数据库阶段波动较大，且端到端总耗时未低于当前 19,973 ms 基线，更未达到 10 秒。它证明底层批量扫描可减少解释器/任务调度成本，但仍必须读取全部 344 MB 正文；也不能把 `grep` 子进程作为后端正式依赖。因此不选作最终方案。

要继续把端到端耗时压到 10 秒内，必须在正文读取之前有可用的持久候选索引。更可行的下一个算法实验是数据库内执行每文件 Bloom 位图检查、只向应用返回候选 ID，再对候选正文做原精确核验；位图不应经应用层整批传输。其收益、数据库内过滤成本和生命周期维护尚待隔离数据库实测，未在真实数据库中建索引。

## `pg_trgm` 隔离 Compose 对比

测试在本任务独立的 PostgreSQL Compose 项目、临时数据库和卷中完成，没有端口发布或真实目录挂载。语料为 48,115 条合成记录，逻辑正文 360,262,863 字节；每种查询 5 次，数据库缓存已预热。结果只比较数据库内 `LIKE` 的候选性能，不等价于当前对象存储读取端到端延迟。

| 查询类别 | 无索引 p50/p95 | `pg_trgm` p50/p95 | 命中数一致 | 计划结果 |
|---|---:|---:|---|---|
| 两字中文 | 580/603 ms | 582/600 ms | 是 | 顺序扫描，无收益 |
| 三字中文 | 557/608 ms | 0.161/0.482 ms | 是 | GIN Bitmap Index Scan |
| 单字中文 | 583/720 ms | 574/639 ms | 是 | 顺序扫描，无收益 |
| 无命中长词 | 585/638 ms | 0.213/0.394 ms | 是 | GIN Bitmap Index Scan |

GIN 索引构建耗时 8,771 ms，占用 118,841,344 字节，约为逻辑正文体积的 33%。16 行写入对照中，正文插入 p50 从 0.083 ms 升到 1.069 ms，正文更新 p50 从 1.320 ms 升到 20.721 ms；删除 p50 为 0.217/0.226 ms。路径移动不改变正文索引，本次独立样本中 p50 为 49.177/35.548 ms（无索引/有索引），波动较大，不能据此宣称移动更快。

`pg_trgm` 对三字及更长的高选择性查询很有效，但目标短词只有两个汉字时无法提取有效 trigram。单字也无法有效剪枝。另一个语义边界是 PostgreSQL `ILIKE` 不等价于 Python Unicode `casefold()`；隔离语料中的扩展折叠探针出现 Python 命中、`ILIKE` 零候选。因此不能把 `ILIKE` 直接当作当前大小写不敏感匹配的候选筛选器，否则会漏结果。

## Bloom 二元组候选筛选实验

使用确定种子的随机中文合成语料，12,000 个文件、24,624,030 字节，平均 2,052 字节/文件。每文件预加载 2 KiB Bloom 位图，按 casefold 后的单字与相邻二元组构建，使用现有逐行匹配逻辑复核候选。重复 7 次，`p95` 为最大样本值。

| 查询类别 | 完整扫描 p50/p95 | Bloom 候选阶段 p50/p95 | 候选文件 / 精确命中 | 语义一致 |
|---|---:|---:|---:|---|
| 稀有两字中文 | 51.568/53.748 ms | 4.693/6.046 ms | 12/2 | 是 |
| Unicode 折叠扩展 | 50.058/53.329 ms | 6.479/8.005 ms | 1/1 | 是 |
| 跨行边界假候选 | 53.484/56.050 ms | 5.865/6.083 ms | 16/0 | 是 |
| 无命中 | 50.652/51.534 ms | 5.470/5.698 ms | 1/0 | 是 |

过滤器总量 24,576,000 字节，初次构建耗时 25.279 秒；另一个 1 KiB/文件实验产生 714/12,000 个候选，而 2 KiB/文件降至 12/12,000，说明位图大小明显影响假阳性率。16 个约 2 KiB 文件的过滤器重建 p50/p95 为 28.805/29.968 ms。上述候选查询延迟假定过滤器已在内存，不含数据库传输 24.6 MB 位图的时间，也不含索引表的空间、事务和回填开销；不能外推成真实 devserver 的延迟。

### 接近当前平均文件大小的补充实验

另用固定种子的中文合成语料测量 6,000 个文件、34,200,009 字节（平均 5,700 字节/文件），每文件 2 KiB Bloom，查询重复 7 次。构建耗时 32.455 秒；单个真实命中查询产生 914/6,000 个候选（15.23%），估算候选正文 5,209,801 字节，完整扫描与 Bloom+精确复核命中数一致。过滤阶段 p50/p95 为 11.022/13.441 ms，但过滤器已驻留内存，**没有计入**从数据库传输 12,288,000 字节过滤器的时间。若将过滤器和候选正文简单相加，本实验需读取约 17.5 MB，低于 34.2 MB 全量正文；这是数据量估算而非端到端延迟收益，且 15.23% 候选率表明在较大文件上固定 2 KiB 仍有不少假阳性。

这支持“先做轻量候选过滤、再保留原精确扫描”的算法方向，但不支持立即部署固定大小 Bloom。下一次合成实验应比较按 distinct n-gram 数量配置位图的方案，并计入过滤器数据库读取/传输、候选正文读取和峰值内存；只有端到端结果稳定优于全扫描，才考虑实现。

### Bloom 位图留在数据库内部的隔离实验

在两次独立的 PostgreSQL 18 Compose 运行中测试 SQL `get_bit(bytea, …)` 候选过滤；应用侧只收到候选文件 ID，再取正文做逐行精确核验。基础语料为固定种子的随机中文，6,000 个文件、34,308,000 字节、平均 5,718 字节/文件；随后将这些合成行复制扩展为 48,000 行，逻辑正文共 274,464,000 字节。扩展语料保留了同一随机文档分布和候选比率，但不是 48,000 份独立正文。每文件 2 KiB 位图，另含跨 owner、deleted、索引缺失和 DIRTY 样本。每次运行、每种方案重复 7 次，p95 使用最近秩法。

| 合成行数 | 路径 | 第 1 次 p50/p95 | 第 2 次 p50/p95 | 候选文件/总数 | 正文传输 | 精确命中 | 语义等价 |
|---:|---|---:|---:|---:|---:|---:|---|
| 6,000 | 全量正文取回并逐行扫描 | 477.97/570.87 ms | 486.66/567.21 ms | 6,000/6,000 | 34,308,000 B | 1 | 基线 |
| 6,000 | DB 内 Bloom + 候选精确复核 | 298.60/337.57 ms | 280.19/294.76 ms | 78/6,000 | 446,004 B | 1 | 是 |
| 48,000 | 全量正文取回并逐行扫描 | 4,171.81/4,699.38 ms | 7,185.12/9,510.69 ms | 48,000/48,000 | 274,464,000 B | 8 | 基线 |
| 48,000 | DB 内 Bloom + 候选精确复核 | 2,444.87/2,579.48 ms | 3,189.15/6,448.28 ms | 624/48,000 | 3,568,032 B | 8 | 是 |

48,000 行样本候选率为 1.3%，应用层正文传输减少 98.7%。两次 Bloom p95 都低于 10 秒，但波动较大（2.58 至 6.45 秒）；位图留在数据库内，缺失索引和 DIRTY 显式回退为候选，跨 owner 与 deleted 样本被排除，精确命中集合相同。9 个额外性质样例覆盖中文、大小写敏感复核、casefold 扩展、跨行、无正规化、单字符/无效编码回退。结果支持 DB 内过滤比把位图整批传到应用层更可行；这只覆盖隔离数据库取候选和合成正文，不包含真实应用元数据路径解析及真实对象存储往返，不能当作真实 grep 端到端 p95。

为测量应用正文扫描段，又将预先计算的 Bloom 候选 ID 交给产品现有 `_scan_candidates` 和 `LocalStorageBackend`。临时目录含 48,000 个合成路径（6,000 份固定种子随机正文以硬链接扩容），每路重复 7 次：全扫描 p50/p95 12,505/13,056 ms，读 48,000 个文件、274,464,000 B；候选扫描 p50/p95 173.64/210.19 ms，读 616 个文件、3,522,288 B；完整 grep 结果签名相同。此分段不计 SQL Bloom 检查时间，也未加入 DB 测试中的 missing/DIRTY 安全回退候选（DB 路径的候选数为 624），不能将本地硬链接存储数据当作 OSS 延迟或真实请求总耗时。

基础语料构建 6,000 份位图耗时 42.54/42.07 秒，两次进程峰值 RSS 为 65,636/65,528 KiB；初始数据库装载耗时 1.88/3.32 秒。将行扩展至 48,000 用时 22.98/14.55 秒，复制的是合成数据和位图，不计入真实索引构建成本。16 文件维护操作的 p50/p95：新增两次为 58.44/88.82 ms、100.40/4,812 ms；编辑为 51.99/56.80 ms、78.62/2,295.50 ms；移动为 2.31/7.38 ms、3.53/48.01 ms；删除为 3.46/3.82 ms、3.82/7.47 ms。第二次运行的维护尾延迟明显受环境波动影响，不能按首轮低值估计 SLA。若按基础构建速度线性外推，48,115 个独立现有文件约需 5.7 分钟，这是估算不是测量，应作为后台回填而非同步查询成本。

综合目前候选方案，优先继续验证**owner/file 关联、DB 内判定的 Bloom n-gram 筛选 + 原逐行精确复核**。生产可用性仍需解决初始回填、内容更新时的失效协议、活动 filesync 的竞态绕过，以及索引缺失回退；没有在真实数据库建表或写索引。原型尚未接入应用；后续的进程内预热测试证明热查询低于 10 秒，但当前产品请求和冷查询仍未达标。

### 真实 owner 数据的进程内预热可行性检查

最后用临时只读进程载入当前 worktree 的 grep/corpus 模块，连接 devserver owner 范围数据库和 storage。全量读取正文时同时构建 casefold Bloom 位图和逐行精确基线，然后重查元数据/路径，以位图过滤并用当前分支扫描器复核。结果只输出聚合值：87,676 条元数据、48,115 个正文候选；预热读取 344,266,029 B，耗时 1,202,149.89 ms，位图占 98,535,424 B，峰值 RSS 473,372 KiB。热查询包含元数据、路径、过滤与精确复核，耗时 3,957.52 ms，只读 33 个候选、1,599,316 B；全量和候选结果逐项相同，均为 1 个文件、10 条匹配，元数据复查稳定。

该实验说明算法在当前真实数据和 worktree 扫描器上可以把**预热后的查询**压到 10 秒内，但约 20 分钟的预热成本和约 462 MiB 峰值 RSS 不适合请求内同步构建。位图只存在实验进程内，未写入数据库、磁盘或服务配置，服务未重启；因此当前产品请求仍是全量扫描，不能据此声称已上线或冷查询达标。若继续实现，应做后台可恢复回填、持久索引及内容更新失效协议；真实数据库索引仍受本任务禁止修改 schema/data 的约束。

作为另一实现对照，纯 Python 集合倒排表在 12,000 文件、22,490,437 字节合成语料上的构建峰值约 202.5 MiB，1,049,449 个 posting；短词候选虽可缩至 1 个文件，但构建内存不适合直接放入服务进程。这使定长/按文档大小配置的 Bloom 位图更值得继续验证。实验使用进程内哈希只比较算法形状；生产实现必须采用跨进程、跨版本稳定的哈希和显式索引版本，不能持久化 Python `hash()` 的结果。

## 综合选择与边界

1. **本轮可验证并保留的方案**：SQL 路径候选下推、只读取 grep 所需的轻量元数据投影、CJK 原始 UTF-8 字节预筛，以及大文件流式扫描。它们保持原有逐行精确核验和 owner 隔离；适合索引尚未部署或候选范围已较窄的场景。线程继续维持 64，不再加大。
2. **下一阶段最值得实现的算法**：owner/file 关联的 casefold n-gram Bloom 筛选器，先筛文件 ID，再复用原扫描器核验。索引缺失、版本不匹配或文件内容不可解码时必须安全回退；文件变更先使索引无效，写入成功后再发布新索引，避免旧索引造成假阴性。查询结果必须继续经过现有 owner、space、deleted、逻辑路径条件；索引不能授权或返回正文。
3. **不选 `pg_trgm` 作为本轮方案**：实际目标短查询没有收益；三字查询的收益无法覆盖目标流量，且 Python `casefold()` 的差异需要额外规范化索引和维护。
4. **不选纯 Python 倒排表**：候选很少，但构建峰值内存过高。普通全文检索、分词/RAG 召回均不能代替逐字匹配。

本轮没有把 Bloom schema 或维护钩子接入应用，因为真实数据库禁止改 schema，且单靠内存合成测试无法验证对象存储与数据库间的索引一致性、所有创建/编辑/复制/导入/恢复路径以及 owner 隔离。仅凭候选算法微基准还不足以宣布综合方案已经上线或已达到 10 秒目标。

生命周期只读审查进一步确认，正文变更分散在普通新建/覆盖、API 编辑、Agent 编辑、复制、undo/redo、压缩包解压、数据可携带导入、filesync 和存储对账重建等路径；单独依赖通用 `File.version` 不足以证明内容索引新鲜。严格无假阴性需要独立内容 revision 与 COMPLETE/DIRTY 状态，写入期间失效、完成后才发布；缺失/过期一律回退扫描。filesync 目录在 watcher 更新数据库前可能已改变正文，因此严格方案还需对活动同步根绕过索引，或先改成同步失效协议。索引候选仍必须从当前用户授权的 File 查询出发，并重新应用 space、deleted、逻辑路径过滤。
