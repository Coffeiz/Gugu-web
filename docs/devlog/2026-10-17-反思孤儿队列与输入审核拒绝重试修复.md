# 反思孤儿队列与输入审核拒绝重试修复

## 问题与边界

- owner 反思缓冲保存在 Redis，会话删除后不会随数据库外键清理。历史重建没有会话时无法得到快照，`False` 被统一转换为失败，缓冲每五分钟回队。
- IM 反思遇到 MiniMax 兼容协议的 `input new_sensitive (1026)` 时，上游使用 HTTP 500。原任务按普通错误退避五轮，最终只保留 `RuntimeError`，丢失审核拒绝分类。
- 两者是独立链路。原始请求内容没有完整留存，不能仅凭错误推断具体敏感文本或媒体；也不能将大量队列失败日志等同为模型调用次数。

## 修复

1. 会话删除的数据库事务提交后，清理该用户、该会话的私聊和群聊 owner 缓冲及闲置队列成员。Redis 清理失败只进入受限诊断，不回滚已经提交的删除。
2. 闲置消费者在持有既有锁、取走缓冲后，检查会话归属是否仍然存在。不存在则终止并清理残留，不调用模型、不重新入队；运行中或有待处理消息的现存会话不能据此被判为已删除。
3. 查库异常仍恢复原缓冲并延期。检查放在取走缓冲之后，防止原列表尚在 Redis 时又回填一份。
4. 仅按结构化上游 HTTP 错误中的精确 `1026` 消息识别输入拒绝，不搜索异常正文或用户输入中的相似字串。
5. 公共分支结果增加可选、固定值的 `provider_error_code`。审核拒绝不在分支内重打；IM 执行器将其转换为固定异常，任务首次失败即进入 `dead`，保存 `input_sensitive`，不推进成功游标、不自动换模型。
6. 普通 500、网络超时等仍沿用原任务退避。此次不扩展为所有供应商错误码的本地映射，也不改变 owner 分支其他暂时失败的恢复协议。

## 回归覆盖

使用临时 SQLite、进程内 Redis 和模拟 provider，覆盖：

- 精确审核错误、包装异常、普通 500、相似但不是错误码的正文。
- 带多次重试预算的分支只调用一次；经过真实 IM 执行器落库后，死信重投不再调用模型。
- 普通上游故障仍进入重试，审核拒绝保存明确终态标签。
- 私聊和群聊孤儿缓冲重复扫描不回队，不触及其他用户的缓冲。
- 会话删除清理两套队列但保留其他会话；数据库提交失败保留原缓冲。
- 查库和反思暂时失败时，原内容恰好恢复一份并延期。

本地扩展回归覆盖 context 目录、provider 错误分类、IM 记忆和终端删除生命周期，425 项通过；依赖图补充的附件归属、IM 会话与媒体、运行生命周期和实时流式回归另有 161 项通过，共 586 项。归属守卫、确认门守卫、语法检查与 `git diff --check` 通过。未调用真实模型，也未变更生产队列或运行配置。

devserver 验证受既有缓存/日志同步冲突限制，未清理冲突或覆盖远端文件。自动质量检查发现消费函数复杂度由 15 增至 17，来自闲置接管和会话存在性两个必要判断；保留清晰 guard，不为压低指标拆分已有状态机。相关函数参数契约保持不变。
