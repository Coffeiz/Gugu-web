# QQ 流式收尾与 LoopScope 终态隔离回放

## 现场与证据边界

QQ 一条回复结尾出现 `_STATE`，用户同时观察到 QQ 流消息仍显示生成中，LoopScope run 也长期停在 `running`。

只读核对确认：

- LLM 第二轮 span 的 `draft` 已包含 `_STATE`；数据库正文同样包含它。来源模型为 MiniMax-M3.1-Flash-Preview。这足以排除 QQ 发送器首次拼入该字面量，但不能仅凭 draft 判断是模型本身还是上游兼容服务造成的。
- Worker 记录了回复完成；Collector 最后收到的快照仍无 `ended_at`，没有 `Final response` span。
- Collector 的 `raw_json` 已经是 QQ 来源，查询列 `session_key` 却仍属于 Web；这是存储更新遗漏，不能据此断言 IM Context 丢失。
- 现场没有保留终态 POST 的失败诊断，因此无法证明当时一定发生了 Collector 超时；后续故障注入验证的是可导致相同表现的代码路径。

本次未调用真实模型重新生成历史答案，未发送消息到真实 QQ，也未改写原始故障 run、用户业务数据或运行配置。

## 复现与修复

1. **QQ 中间刷新失败后跳过关闭**：已建立的流发生一次中间帧超时，`error` 和失败任务继续阻止最终 `input_state=10` 帧。修复后，在记录受限诊断后，使用已知 `stream_msg_id` 和完整正文尝试关闭；没有首帧回执时仍报告原错误。关闭请求本身失败以专用异常传回 IM 编排层，不能因已有可见前缀而算作成功；模型事件仍继续消费至最终响应以完成持久化。
2. **在途回执提前确认新文字**：HTTP 请求期间累计的新 token 被一并写入 `last_sent_text`，导致回执超出实际发送内容。现在回执只保存该帧捕获的正文。
3. **IM 镜像覆盖 trace 来源**：`genstream.begin` 不再把已经绑定的 IM 来源重设为 Web；普通未绑定的 Web 路径继续初始化为 Web。
4. **Collector 保留旧归属**：重复上报同一个 run 时同步更新 `sessionKey` 和 `traceId`，使查询列表与原始快照一致。
5. **终态上报永久丢失**：运行中快照继续单次 best-effort；终态对网络错误、408、429、5xx 最多发送三次，间隔 0.1/0.2 秒，全部在独立上报任务中完成。无效请求不重试，最终失败进入受限诊断，不新增空闲心跳。成功收尾从 LLM draft 恢复正文时，也补齐 run 顶层输出。

没有新增“删除 `_STATE`”的文本规则，正常生成内容不因这个字面量被修改。

真实故障快照约 2.2 MB，只读载入内存后在临时 SQLite 中重放，能从 `running` 更新为 `success`，完整保留 1384 字符正文及其 `_STATE` 尾巴。两次入库约 235/245 ms；这是单次隔离回放耗时，不是性能提升测量。临时数据库随实验结束清理，完整正文未写入报告或测试夹具。
