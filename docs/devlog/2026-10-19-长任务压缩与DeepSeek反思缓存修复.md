# 长任务压缩与 DeepSeek 反思缓存修复

用户发现真实对话连续出现十万以上输入、仅三万左右缓存读取。经授权对 devserver 的完整 trace 进行只读调查，定位到两个独立原因：十轮保护窗口让大段工具结果在压缩后继续留在当前任务；DeepSeek 的追加式 JSON 分支因 `response_format` 无法复用主对话大段历史缓存。

运行中实际输入达到 90% 后，压缩器可以处理本 run 较早的完整执行轮，始终单独保留本次用户最后原文和最近一个完整执行轮。普通历史恢复的十轮窗口保持原策略。同步修复压缩后的保护位置更新、Area 索引与 wire 清理后的消息坐标混用，并阻止仅达到 90% 时误用溢出硬裁切。

DeepSeek 的追加 JSON 参数策略归入其 Provider 模块：追加历史时使用任务中的 JSON 指令和统一解析/业务校验；独立 JSON 调用、其他 Provider 的请求保持现有行为。无效 JSON 仍然不能成为可应用的反思结果。

真实回放中，三次后续主请求的未命中输入减少 64.25%，后两次命中率均约 99.5%；完全相同 JSON 任务的反思分支命中率由 29.94% 提升至 99.89%。794 项相关回归通过。实验没有执行历史工具、写业务数据库或修改用户配置；原始内容仅在受控 Collector，仓库只记录统计。

详见 [A/B 报告与复现命令](../reports/OPT-Cache-Strategy-2026-10-19.md)。诊断脚本默认不读取真实 trace 或调用真实模型，必须显式授权开关；没有新增常驻探针。

修复已同步到 devserver 并重启后台服务；四个服务均为 active，`/health` 返回正常。没有修改数据库结构或用户运行配置。

## MiniMax Chat API 补充验证

对已配置 MiniMax 模型回放相同历史及 JSON 任务，显式切换上游 JSON 参数：A/B 均为 110,623 输入 Token、110,592 缓存命中、31 未命中，命中率 99.97%，JSON 校验通过。未复现 DeepSeek 的参数切换退化，保留 Provider 差异；公共运行中压缩修复继续覆盖所有 Provider。详细边界与受控诊断标识见缓存策略报告。

## 统一追加 JSON 分支策略

按用户确认，将有历史的 Chat JSON 分支策略统一放入公共适配器，删除 DeepSeek 重复覆盖。独立 JSON 请求保留各 Provider 原参数，继续解析和业务校验。六个 Provider 的请求参数和无效输出回归共 32 项通过。该统一不代表所有模型均复现缓存问题，实际输出可靠性仍受模型指令遵循能力影响。
