# 日历跨端原子版本更新

## 问题

Agent 的 `update_event` 修改事件但不递增版本，旧 Web 草稿携带原版本仍能提交。Web PATCH 虽然在 Python 中比较版本并递增，但最终 SQL 没有版本条件，读取完成到写入之间仍可被另一端更新后静默覆盖。

## 修复

- 在 `app/services/calendar.py` 增加共享 `update_event_atomic`，使用事件 ID、用户归属、未删除状态及预期版本作为同一条 UPDATE 的条件；数据库递增版本，仅 `rowcount == 1` 成功。
- Web PATCH 与 Agent 工具均在修改 ORM 字段前执行原子更新；成功后刷新 ORM 对象，再使用新活动状态同步提醒。
- Web 保留原 409 提示。Agent 使用本次在服务端读出的版本，冲突返回“事件刚被其他端修改，请重试”；不自动读取最新版本后覆盖重试。
- 只修改提醒也会推进事件版本。共享入口拒绝通过业务字段覆盖归属、版本或删除状态。
- 事件更新和提醒同步仍处于原调用方事务中：Web 的 `get_db` 异常清理及工具 dispatch 的 error 回滚负责撤销失败操作；共享入口不提交事务。
- 成功后原有撤销记录与实时广播保持不变；冲突者不修改提醒、不记录成功撤销操作、不广播成功。

没有给模型增加 version 参数，没有强制旧 Web 调用提供 version；省略时使用本次服务端读取的版本做原子比较。没有增加数据库列或迁移，不涉及创建幂等键、跨端长期 base-version 协议、删除路径或独立提醒接口的并发协议。

## 验证

[新增回归测试](../../backend/tests/scheduling/events/test_event_atomic_update.py) 使用合成事件、内存 SQLite 和独立 AsyncSession。四种 Web/Agent 组合在失败者完成读取后，先让另一个 Session 提交，再继续失败者更新，验证 CAS，而非只断言 Python 提前比较。

覆盖旧 Web 草稿被 Agent 写入失效、同版本至多成功一次、仅改提醒递增、提醒校验失败时活动及版本回滚、提醒不被失败者修改、越权/已删除/缺失资源拒绝、禁止覆盖保护字段及不传 version 的旧接口兼容。提醒时间使用带时区的完整时间比较，避免把数据库 UTC 小时误当作活动本地小时。

## 后续补齐：旧草稿与删除路径（2026-10-20）

按后续审查补齐三个相邻缺口：

- Dashboard 快捷编辑在打开时固定记录事件版本并随 PATCH 提交。收到 409 时明确提示旧草稿未保存，回滚乐观更新并刷新月视图与即将到来的事件缓存，避免静默吞掉用户输入。
- Web PATCH 的 `version` 改为必填；DELETE 也要求版本，并通过共享条件 UPDATE 做可撤销软删除。Agent 删除保持原来的硬删除语义，但 DELETE 使用事件读取时的版本条件；失败者不会删除事件或提醒。两条路径均保留原有确认、撤销及任务处理行为。
- Web PATCH 只有版本、没有业务字段时作为无操作返回，不递增版本、不记录撤销、不广播；Agent 的提醒专用更新仍递增事件版本。

新增确定性交错覆盖：Web 删除读后被 Agent 更新、Agent 删除读后被 Web 更新时均返回冲突且不删事件/提醒；Dashboard 旧草稿遇到 409 后提示并刷新缓存。测试使用合成数据与隔离数据库，不连接真实用户数据或模型服务。

本地验证：调度与撤销回归 **177 项通过**；Dashboard 快捷编辑组件测试 **1 项通过**；前端 TypeScript 检查通过。归属与确认门检查、测试元数据校验（新增 2 个测试文件）、Python 编译及 `git diff --check` 均通过。质量差异检查 `gating=0`；少量新增测试/共享 CAS 结构提示均为新符号或轻微项。未触发远端 CI，未提交、推送或重启服务。
