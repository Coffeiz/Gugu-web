# 群反思复用主 run 原始前缀

## 问题

群闲置反思通常由独立 worker 执行，只能从数据库重建历史，拿不到主 run 的进程内 `ReflectionSnapshot`。当被动群消息成为本批最后一条消息时，旧逻辑还会直接丢弃候选快照。于是群反思虽然带着完整历史，却经常无法复用主请求的原始 Provider 前缀和工具声明。

## 修改

- 主 run 结束后，持有快照的进程预约群闲置 drain；Redis 只保存短期协调标记，worker 在标记有效期间避让，进程退出后由 TTL 到期交给 worker 接管。
- 群任务含被动消息时，数据库历史只作为尾部核对来源。仅当重建消息逐条以原始 Provider wire 前缀开头时，沿用主 run system、工具声明和 wire 历史，再追加被动消息；不匹配时继续使用数据库重建。
- LoopScope `snapshot_source` 标记 `in_memory`、`in_memory_extended` 或 `persisted_history`，不包含对话正文。

## 验证

devserver 真实 DeepSeek `deepseek-flash` / Chat Completions 隔离 A/B：持久历史重建缓存率均为 0%；原始前缀追加为 90.59% 与 91.09%。第二轮经正式 `ContextBranch` 记录到隔离 LoopScope trace，来源与 usage 一致。后续真实 MiniMax `MiniMax-M3.1-Flash-Preview` / Anthropic Messages 隔离 A/B 三轮：历史投影重建缓存率为 2.05%–2.25%，原始前缀追加为 99.57%–99.65%。MiniMax 测试直接走生产 Anthropic client，没有经过正式 `ContextBranch` / LoopScope。两组实验均使用合成内容，不写业务记忆、不调用真实群消息或工具。详细 usage 和限制见[真实模型 A/B 报告](../reports/2026-10-20-INVEST-群反思原始前缀复用真实模型AB.md)。

报告只证明合成历史通过严格对齐时可复用真实 Provider 缓存；真实 QQ 消息历史仍需观察 `snapshot_source` 和缓存率，不能据此保证所有消息都能对齐。
