# 长视频理解超时与 LLM 重试风暴调查

> 2026-10-22 · 只做现场调查与复现，未改代码、未改运行配置。修复方向待拍板。

## 1. 现象

QQ 侧用户让 Agent「看下刚发的视频」。Agent 第一轮正常调 `read_file`（15.4s，读文件库视频并上传 Files API），
工具卡片也正常渲染；随后**第二轮 LLM 调用连续 6 次读超时**，12.5 分钟后才判定失败，给用户发了一条 56 字的
通用失败提示（「请求处理失败，未识别到上游 HTTP 错误（诊断编号 …）」）。

用户侧观感：工具卡片之后长时间没有正文，最后只看到一句没有原因的失败提示。

线上事故是 15:11:27 → 15:23:53 = **746s**，复现是 **749s**，差 3 秒，形状完全一致。

## 4. 根因

三个数字对不上：

1. **应用侧不设视频时长上限**：`backend/agent/providers/minimax/media.py` 的 `M3_MEDIA_LIMITS` 里
   `max_duration_s=None`、`transcode_video=False`，10.5 分钟视频原样上传（不转码、不截断）。
   这是 2026-10-22「原文件直传」方向的结果，见 `docs/reports/2026-08-05-TEST-LLM-MINIMAX-M3-VIDEO-MM-FILE.md` 第 10.6 节。
   共享默认策略（`backend/agent/providers/media.py`）本来有 `max_duration_s=120` + 转码兜底，M3 这条策略把它整个绕开了。
2. **上游处理这条视频要 130s+ 才吐第一个字节**：631 秒视频按 `fps=1` 抽帧约 631 帧，上游要先抽帧再起流。
3. **客户端读超时写死 120s**：`backend/agent/loop_drivers.py:296` 的 `httpx.Timeout(connect=10, read=120, write=10, pool=5)`。

于是：每次尝试必然超时 → `backend/app/core/retry.py` 的 `LLM_RETRY`（最多 5 次、间隔 5s、预算 900s）
把它放大成 **6 × 125s ≈ 12.5 分钟静默** → 最后才落一条通用失败提示。
真正的杀手是「**视频太长 + 读超时太短**」，重试策略只是把 2 分钟的失败变成 12.5 分钟的失败。

## 5. 顺带发现的次要缺陷

1. **视频块被放进 `tool_result`**：`backend/agent/loop_drivers.py:486` 的 `AnthropicDriver.build_tool_round`
   把工具返回的媒体块原样塞进 `tool_result.content`。Anthropic 协议里 `tool_result` 只允许 text/image；
   MiniMax 宽容（实测 200 且能正常返回），但真 Anthropic 端点会 400。
   OpenAI/Responses 驱动有 `_openai_tool_result`（`backend/agent/providers/message_utils.py:627`）把媒体块摘出来
   单独成一条 user 消息，Anthropic 驱动缺这一层。
2. **失败提示文案误导**：`APITimeoutError` 落到 `describe_llm_error`（`backend/agent/errors.py:188`）最后的兜底分支，
   显示「未识别到上游 HTTP 错误」，与真实原因（等首字节超时）不符。
3. **Files API 上的 mm_file 没有回收路径**：`backend/app/core/chat_attach.py:1087` 的 `_upload_video_mmfile`
   上传后从不删除，本次事故在 MiniMax 侧留下 1 个孤儿文件（调查期间已清理）。

## 6. 结论

- 触发条件：MiniMax M3 协议 + 文件库视频 + 视频时长导致上游首字节延迟 > 客户端读超时（120s）。
- 放大条件：`read_file` 的视频请求走**第二轮**（工具续轮），此时上下文已含长历史，上游首字节更慢。
- 与「视频块放在 tool_result」无关：两种位置的首字节延迟实测一致（130.4s vs 132.8s）。

## 8. 第二次故障：上游视频时长硬限 1800 秒（2026-10-22 16:32）

同一场调查里出现的**另一种失败模式**，与读超时无关：上游直接 400。

- 输入：用户第二条视频，**4119.1 秒（68.7 分钟）、235 MB**。
- 咕咕的处理：用沙箱 `ffmpeg -f segment -segment_time 1800 -c copy` 切成三段再读——
  `part00=1801.815s/111MB`、`part01=1799.140s/89MB`、`part02=518.174s/23MB`；前两段以 `mm_file` 引用进入请求（请求体 33.8MB）。
- 上游拒绝（诊断编号 `DBB3D699FAEB1D0F`）：
  `invalid params, messages[167]'s content[1] video's duration is bigger than 1800 seconds, please check your input (2013)`

**结论：MiniMax 单条视频的硬上限是 1800 秒**，超过即 400（不是降级、不是超时）。`-segment_time 1800` 按关键帧切会溢出 1.8 秒，1801.8 秒那段照样被拒。

由此确定的两条边界：

1. 应用侧至今**没有任何视频时长闸门**：`M3_MEDIA_LIMITS.max_duration_s=None` 且 `transcode_video=False` → 连 ffprobe 都不跑，应用根本不知道视频多长，只能等上游拒。
2. 上游 2013 的原始说明（「视频时长超 1800 秒」）在错误呈现层被压成「请求参数错误，请检查模型名称、接口格式和请求参数」，真正可用的信息丢了。

## 9. 决策拆分（2026-10-22 16:55–16:58）

长视频这件事拆成**两个互不相干的维度**，处理方式不同：

| 维度 | 含义 | 决定 |
|---|---|---|
| **A. 超出 provider 规格** | 视频时长超过该 provider 的上游硬限（如 MiniMax 1800 秒） | **本轮实施**：应用侧先判定，直接返回**失败的 tool result**，不让上游去拒 |
| **B. 规格之内但等不起** | 视频没超规格，但上游首字节慢到超过客户端读超时（如 300s），用户白等十几分钟 | **暂缓**：等真实再发生再设计。设计它需要实测"视频时长 → 上游首字节延迟"的曲线，成本高于当前收益 |

维度 B 的设计要素（**留档，未来再设计时直接用，不必重查**）：

| 结论 | 依据 |
|---|---|
| 闸门值应取 min(上游硬限, 该 provider 自己等得起的上限) | 上游硬限来自 provider 规格；"等得起"是各 provider 自身管线速度的属性 |
| **不能用 MiniMax 的数套到别的 provider** | 每 provider 的"每视频秒延迟"不同；把一个 provider 的实测套到另一个是拿别人的尺子量别人 |
| 延迟观测点（仅 MiniMax） | 631s 视频 → 首事件 126–133s（隔离请求）、138.8s（生产 run `run-fdc92046339d`）、首个正文 token 197.6s（隔离复跑） |
| 改时长闸门时必须一并处理的两个坑 | ① ffprobe 触发条件应改成「要处理视频就探测」，否则 provider 侧声明"无限制"时没有时长可判；② 错误文案「当前 Provider 不支持这种视频格式，**未进行转码**」里的 provider 行为假设对 `transcode_video=True` 的 provider 是错的 |

## 10. 维度 A 落地（2026-10-22 17:10–17:30）

### 10.1 机制已在通用媒体层就位

通用媒体层（`backend/agent/media/video.py`）已经具备维度 A 的全部机制：

- `prepare_video_media()` 在**上传之前**按 Provider 规格判定时长，超限抛 `ValueError`；
- 两条入口共用这一处判定——`read_file` 路径（`agent/tools/media_reader.py`）把
  `ValueError` 转成 `{"error": …}`，由 `agent/context/canonical_tool_history.py`
  的 `_tool_result_is_error()` 判为**失败的 tool result**；聊天附件路径
  （`agent/chat/attachments.py`）把同一句话退化成文字提示；
- ffprobe 触发条件是「要转码 **或** 有时长上限才探测」，探测失败 fail-closed
  （确认不了时长 ≠ 没超限）；
- 拒绝文案统一成「……，未发送给 Provider」，跟"已发送"的口径区分开。

机制在工具层、数值在 Provider 规格，所以**新 Provider 只要声明自己的上限就自动
获得这个闸门**，不需要为 MiniMax 特设任何分支。

### 10.2 缺的最后一环：闸门数值（本次补上）

机制齐了，但闸门当时是**关着的**：`M3_MEDIA_LIMITS.max_duration_s=None` 且
`transcode_video=False` → 既不探测也没有上限可判 → 68 分钟视频仍原样上传、
仍由上游 400 拒绝。补上的是**一个数值**：

```python
# backend/agent/providers/minimax/media.py
max_duration_s=1800,            # MiniMax 单条视频官方硬限
duration_limit_inclusive=False,  # 上游拒的是 "bigger than 1800"（严格大于）
```

边界取**非包含**语义是有依据的：上游 400 原文是
`video's duration is bigger than 1800 seconds`，判的是严格大于，正好 1800 秒
上游能收——应用侧用包含边界会误拒上游收得下的视频。实测被拒的那段是
1801.815 秒（`ffmpeg -f segment -segment_time 1800 -c copy` 按关键帧切必然溢出），
与上游口径一致。

副作用（已知且可接受）：M3 视频从此会跑 ffprobe 探测时长。旧实现（HEAD）对
**所有** Provider 都无条件探测并 fail-closed，所以这是把 M3 拉回旧口径，不是
新增依赖；代价是每次读视频多一次 ffprobe 与一份临时文件写入。

维度 A 的实施要点见下节。当前未修、已知会复现的症状：① 超过 1800 秒的视频仍被上游 400；② 该 400 对用户显示为「请求参数错误」；③ 永远等不到首字节的超长视频仍会白等最长 910 秒（300s 读超时 × 3 次尝试）后才失败（属维度 B，暂缓）。

## 11. 时长闸门前置 + 按路径探测（2026-10-22 18:00–19:20）

### 11.1 问题：闸门开在字节读完之后

维度 A 把时长上限挡住了，但**闸门的位置不对**。两条消费路径的顺序都是：

```
stat / meta → 大小闸门（读前拦 ✓）→ get() 读全部字节 → prepare_video_media
                                                       → 探测时长 → 时长闸门
```

时长探测发生在**读完字节之后**，而探测的实现（`probe_video(raw)`）必须把整份字节
**落成临时文件**才能喂给 ffprobe。于是拒绝一个 235MB 的超长视频，代价是：

- 从存储读 235,392,959 字节进内存；
- 再写 235,392,959 字节的临时文件，再读一遍；
- 才换来一句「这条视频时长 4119.1 秒，超过 Provider 的 1800 秒上限」。

**同一个函数里的大小闸门是在读字节之前拦的，时长闸门却做不到**——原因不是
"时长必须读文件才知道"，而是没人把"读之前就知道时长"这条路接上。

### 11.2 改动

| 改动 | 位置 | 作用 |
|---|---|---|
| `probe_video_at(storage_key)` | `agent/media/video.py` | 按**存储路径**探测：ffprobe 对文件按需 seek（IO 量 KB 级），不落临时文件、不把视频读进内存 |
| `check_video_duration(duration, model_cfg)` | `agent/media/video.py` | 时长闸门抽成独立函数——读前拦截与读后校验共用同一份规则和文案，不留两套 |
| `prepare_video_media(..., duration=, probe=)` | `agent/media/video.py` | 调用方已知时长/探测结果时直接复用，不再重复探测 |
| `probe_video_for(raw, storage_key)` | `agent/media/video.py` | 探测入口：优先按路径，没有本地路径（对象存储）回退字节探测 |
| `StorageBackend.local_path(key)` | `app/services/storage/__init__.py` | 本地后端返回可读路径；对象存储返回 None（`None` 就是"没有本地路径"的显式表达） |
| 读前拦截 | `agent/tools/media_reader.py`（read_file）、`agent/chat/attachments.py`（聊天附件） | 两条消费路径都在**读字节之前**按时长闸门拒 |

对象存储没有本地路径 → `probe_video_at` 返回 None → 不做读前拦截 → 退回字节探测，
**行为与优化前完全一致**（只是没有提速）。这条回退路径有用例锁定。

### 11.3 效果

**A/B 设计**：同一进程、同一批文件、同一台机器，用 monkeypatch 切换两条路径——

- `before`：把 `probe_video_at` 打成永远返回 None → 强制走旧路径（读字节 → 落临时
  文件探测 → 读完之后才判时长）；
- `after`：真实实现（按路径探测 → 读字节之前就判时长）。

before/after 交替跑 5 轮取中位数，消除冷热缓存与顺序偏差。取数时 devserver 空闲
（1 分钟 load ≈ 6）。样本按体积区间钉死（235MB / 58.8MB / 16MB 三档），不打印
文件名。

| 场景 | before p50 | after p50 | 从存储读出的字节 | 探测产生的临时盘峰值 |
|---|---:|---:|---:|---:|
| 超限视频（235MB / 4119 秒） | 39,853.7ms | **204.8ms** | 235,392,959 → **0** | 235,392,959 → **0** |
| 合格视频（58.8MB / 631 秒，走 mm_file） | 184.8ms | 153.1ms | 58,820,613 → 58,820,613 | 58,820,613 → **0** |
| 合格视频（16MB，走 base64） | 159.4ms | 177.4ms | 15,974,223 → 15,974,223 | 15,974,223 → **0** |

**并发压力**（样本 = 超限视频 + 合格视频轮转，N 路同时读）：

| 并发 | before 墙钟 | after 墙钟 | before 读字节 | after 读字节 | before 临时盘峰值 | after 临时盘峰值 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1,371ms（冷启 33.8s） | **131ms** | 235MB | **0** | 235MB | **0** |
| 4 | 9,741–16,973ms | **650–740ms** | 588MB | **118MB** | 530–588MB | **0** |
| 8 | 35,302–47,327ms | **1,012–1,560ms** | 1,177MB | **235MB** | 1,059–1,174MB | **0** |
| 16 | 73,562ms | **2,155ms** | 2,354MB | **471MB** | 2,354MB | **0** |

三件事值得单独说：

1. **超限视频的成本从"读一遍 + 落一遍"变成"零"**：拒绝一个 235MB 的视频，现在
   连一个字节都不读——闸门前置到读字节之前，跟大小闸门对齐了。
2. **并发下的差距是量级差**：旧路径每路并发都要写一份等体积的临时文件，16 路时
   临时盘峰值 2.3GB、墙钟 73.6 秒；新路径临时盘恒为 0、墙钟 2.2 秒。
3. **after 的读字节正好是"只读合格视频"的那部分**：4 路并发里有 2 路是超限视频，
   after 只读 2 份合格视频（118MB），before 全读（588MB）。省下来的不是"更快"，
   是"本来就不该读的字节"。

> 取数说明：首轮取数时 devserver 上并行跑着漏洞扫描（4 核机器 load 50~94），时间
> 数字不可信，已全部作废重取；上表是机器空闲时重跑的结果。首轮数据还暴露出基准
> 脚本自身的两个 bug（并发计数被 `zip` 截断、计数包装嵌套导致字节数恒为 0），
> 修正后才取到上表——两次离群值（并发 4 的 after 8.5s）也是因此复跑确认的。
