# IM 重启恢复与视频内存调查

## 现场结论

用户实际发送两条消息；Redis 入站流也只有两条。第一次 Worker 重启后把未确认的原请求和后续消息合并；后一次 Worker 被内核 OOM killer 终止，再次回收同两条消息，产生相反顺序的合并请求。新 run 的存在不能作为用户重复发送或并发执行的证据。

OOM 时 Worker 常驻匿名内存约 3.66 GiB；内核此前还终止了沙盒关联进程。第一次重启的触发原因未确认，不能一并归因为 OOM。中间回复已发至 QQ，但旧 run 未收尾、展示时间线未落库；后来 run 完成不会补回旧进程丢失的内存内容。

## 消息修复

- Worker 在进入业务处理前给批次的所有原始 stream ID 保存同一执行收据，未确认期间不过期。
- 请求落库时用收据绑定唯一执行身份。租约失效后重领到已开始的请求，只标记中断并确认，不自动重跑工具，不把该消息重新放入防抖缓冲与后续消息拼接。准备阶段尚未落库的请求仍允许恢复。
- Redis 无法确认处理租约时保留待重领，不无保护地执行。
- 已完成正文轮次和工具事件在渠道展示前保存检查点；媒体块替换成历史占位，检查点不作为模型正文。
- 正常完成时更新同一展示行，避免检查点与最终回复重复。最终提交后 ACK 前退出的恢复只确认，不改成中断。
- 优雅停止的取消路径同样不 ACK 未完成请求。进程重启不承诺恢复 Python 执行栈或实现外部副作用的 exactly-once。

当前修复从启用后的新批次开始生效；旧版本已生成的重复用户行和已经丢失的回复不会自动改写。

## 视频内存：已证实与未证实

两段源视频约 43.8 MB / 40.4 MB，当前 MiniMax 策略的 inline 阈值为 45 MiB，因此会选择 Base64。仅编码正文就约 112 MB，尚未计入原始字节、JSON 字符串、UTF-8 请求缓冲和重试副本。

代码中另有全量放大路径：canonical digest 用完整 JSON 字符串再编码；LoopScope 每轮保存输入，整 run 快照再序列化提交。Collector 的入口上限为 24 MiB。真实 trace 最后保存的轮次仍在大视频读取之前，已保存输入总计约 7.9–17.4 MiB，不能用这些已保存行的体积断言实际内存峰值，也不能断言某一次 JSON 分配就是 OOM 的唯一原因。需要隔离的分阶段 RSS 测量进一步归因。

## 优化方案与实施范围

1. 大视频优先走现有 Files API 引用，保留原视频质量；新增按路径流式上传，避免先 read_bytes 再上传。inline 阈值依据隔离测试决定，不能将传输策略阈值误当作文件能力上限。
2. 上传结果按用户、Provider 配置身份和源文件内容身份缓存，限制生命周期并回收远端文件。避免不同用户共享私有上传引用。
3. LoopScope 完整正文继续保留；二进制媒体采用受控 artifact 存一份、各轮引用，取回时仍可查看。不能直接截断 Prompt 或删掉正文来掩盖问题。增量提交 span，避免累计整个 run 越传越大。
4. canonical digest 在保持字节与排序契约不变的前提下改成流式哈希；不要改变缓存前缀或 wire 内容。检查 tokenizer 是否误对 Base64 做文本编码。
5. 媒体读取、编码和请求体组装共用按字节加权的并发预算；当前 ffmpeg semaphore 只控制转码，不能约束直传视频。等待期间继续维护 run 活跃状态。

隔离 A/B：使用合成、合法视频，覆盖单个约 40 MiB、两段组合、四个并发任务；旧 inline 与上传引用交替执行。分别测读取、编码、context/digest、trace、SDK 序列化和发送阶段的进程峰值 RSS、墙钟、发送字节、重试次数、成功率；在受限子进程里测试，避免再次压垮运行服务。以峰值 RSS 显著下降、正常正文/工具历史可恢复、视频内容可理解和无新增重试为验收，实际数据出来前不承诺降幅。

已实施：本地大视频路径流式上传、4 MiB 内联策略、按用户/配置/内容隔离的六小时引用缓存、媒体准备阶段加权预算、canonical JSON 流式摘要、LoopScope 编码移出事件循环。上传前后核验源文件身份，失败不回退大 Base64；缓存命中不续期，避免引用超出远端寿命。512 MB / 1800 秒的 Provider 能力边界不变。

三轮隔离内存 A/B 已完成：两段 84 MiB 场景峰值 RSS 中位数由 385.67 MiB 降到 50.88 MiB，四段由 721.63 MiB 降到 50.98 MiB。最大上传块 64 KiB，原件不变。测试仅测合成传输、摘要和 JSON 编码，不含真实模型理解。完整方法、取舍与未完成项见[视频文件引用内存 A/B](../reports/2026-10-23-OPT-视频文件引用内存AB.md)。通用 artifact 存储、span 增量上报和远端主动回收尚未实施，不把本轮局部改善写成全链路完成。

## 同日重复最终回复补充

第二次现场不同于上面的 OOM：网关入站只有一条原始请求，服务端生成两条相同用户行、两份措辞不同的最终回复，两个 run 共用同一入站 trace，期间没有 Worker 重启。这是重复执行，不是同一正文发送了两遍。

长任务完成后、ACK 前失去租约的分支会保留 PEL，后续重领原本会再次执行。已用持久化完成记录、原 Redis 租约不存在的状态复现：修复后重领只确认，不创建新用户行或再次调用处理器。原现场没有记录租约丢失的确切时点，故不能把这条分支说成已经逐步证实的现场唯一原因。续期返回零现在会记录无正文的所有权丢失诊断，不再静默忽略。

第一轮结束同时有受限诊断 `agent.loopscope.final_snapshot` 的 `Broken pipe`。终态走独立轻量接口，全量快照失败时，LoopScope 会显示已完成但只保留之前上传成功的 span；因此不能用“没看到视频工具卡”证明未调用。源代码存在大视频内联导致快照超过入口上限的路径，但该次失败没有保存被拒请求体，不能仅凭 Broken pipe 将其精确归因为 413。

## 验证

devserver 串行运行消息恢复、Worker 准入、run 收尾、生命周期、collect、核心循环和聊天历史 API 回归：174 项通过。使用临时数据库与 fake Redis，不操作真实用户数据或调用真实模型。

补充媒体、Provider、附件、trace 和 canonical context 后，综合回归 325 项通过；随后新增租约丢失诊断与快照编码不阻塞事件循环的行为用例，相关专项回归 32 项通过（与综合集合有重叠）。综合运行有一条异步连接清理警告，未将其描述为无警告全绿。视频附件测试补齐独立语音配置替身，避免因环境 BYOK 开关查询实际配置。

定向 diff 空白检查与 Python 语法检查通过。静态结构检查仍提示预算初始化与测试 helper 的通用形状重复，以及新增路径准备函数的复杂度；没有为清除分数而合并不同责任模块，也未把该结构检查说成已通过完整合并门禁。未提交、推送或触发 CI。

源码已同步。后续检查时入站队列仍有未确认消息，为避免再次中断任务，没有主动重启运行服务；最新源码不等于所有运行进程已加载最新版本。
