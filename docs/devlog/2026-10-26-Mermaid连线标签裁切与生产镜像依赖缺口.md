# Mermaid 曲线连线标签被裁切与生产镜像依赖缺口

## 现象

QQ / IM 里带曲线连线的 Mermaid 图表，连线标签的文字底色被切掉一半，标签里的连线从
文字底下穿出来。另一条线上的问题是：图表在开发环境正常，部署到容器后整张图渲染失败。

## 根因

### 标签被裁切：viewBox 没容下越界的标签底色

Mermaid 在长曲线连线上会把标签底色放到 SVG 的 viewBox 之外。Resvg 按 viewBox 裁剪，
越界部分直接被切掉——于是标签底色缺一块，底下的连线就露了出来。

修复方式是把越界的标签底色纳入 viewBox：新增 `expandViewBoxForEdgeLabelBackgrounds()`
扫描 `edgeLabel` 组里的 `background` / `labelBkg` 矩形，按累计的 `translate` 偏移算出
它们的实际位置，必要时扩展 viewBox，并同步根节点内联的 `max-width`。

尺寸预算另抽成独立模块 `raster-dimensions.mjs`，由 `calculateMermaidRasterDimensions()`
统一算，避免尺寸规则散在渲染与栅格化两处。

### 生产镜像缺依赖

`worker.mjs` 新增了 `import { calculateMermaidRasterDimensions } from './raster-dimensions.mjs'`，
但两个生产 Dockerfile 的复制清单里没有这个文件：

- 根 `Dockerfile` 的 `./bin/` 复制清单
- `backend/Dockerfile.prod` 的 `./bin/` 复制清单

镜像里的 `gugu-mermaid-worker.mjs` 启动时会 `ERR_MODULE_NOT_FOUND`，直接导致
QQ / IM 的 Mermaid 图片渲染全部失败。源码目录里的 Worker 测试是在源码树上跑的，
发现不了这种打包遗漏；真正拦住它的是部署契约测试
`tests/platform/deployment/test_embedded_deps_contract.py`——它会扫描 `worker.mjs`
与前端渲染器的相对导入，逐个要求 Dockerfile 把这些模块复制进对应目录。

## 一个容易漏掉的连带影响：Web 端也走这条共用函数

`expandViewBoxForEdgeLabelBackgrounds()` 是在共用的 `normalizeMermaidEdgeLabelBounds()`
末尾调用的，而 Web 端 `frontend/src/utils/mermaidRenderer.ts` 也调用这个共用函数。
所以「只改 IM 栅格化路径」的说法不准确——Web 端的 SVG 同样会被扩展 viewBox。

实际影响需要分两种情况看：

- **标签底色在 viewBox 内**：扩展函数是恒等变换。`minX` / `maxX` 等只在标签真的越界
  时才会被 Math.min / Math.max 改写，viewBox 与内联 `max-width` 都保持原值，
  Web 端图表尺寸不变。
- **标签底色越出 viewBox**：viewBox 变大、内联 `max-width` 同步变大。浏览器同样按
  viewBox 裁剪，所以不扩展的话 Web 端也会切掉标签——扩展是对 Web 端的**修复**，
  代价是这类图表在 Web 上会略微变大（内联 `max-width` 优先级高于样式表里的
  `max-width: 100%`）。

两条行为已写进前端契约测试，锁成可回归的约定，而不是靠约定俗成。

## 修复

- `backend/ts/workers/mermaid-renderer/svg-style.mjs`：新增 viewBox 扩展；尺寸预算
  抽到 `raster-dimensions.mjs`。
- 根 `Dockerfile` 与 `backend/Dockerfile.prod`：复制清单补上 `raster-dimensions.mjs`。
- `frontend/tests/markdown/mermaidRenderer.test.ts`：新增两条 Web 路径契约测试
  （越界时扩展画布、界内时尺寸不变）。

### 再加一道构建期闸：镜像里冒烟启动 Worker

部署契约测试能发现「复制清单漏了某个模块」，但它依赖有人去改那条清单。一旦漏了，
缺文件只会在镜像运行时炸（`ERR_MODULE_NOT_FOUND`），线上表现为 QQ / IM 的 Mermaid
整张图渲染失败。

所以在两个镜像的构建里加一步冒烟：

```dockerfile
RUN printf '{"sources":[]}' | node bin/gugu-mermaid-worker.mjs
```

空 source 列表会让 Worker 走完模块加载但不渲染任何图表，于是这一步同时校验：

- Worker 的全部同级依赖都能解析（`svg-style.mjs` / `diagram-source.mjs` /
  `theme.mjs` / `raster-dimensions.mjs`）；
- CJK 字体文件在镜像里存在（Worker 在模块级就校验字体路径，缺了抛
  `cjk_font_unavailable`）。

任一环节缺失都会让**镜像构建失败**，而不是等到线上渲染时才暴露。实测：把
`raster-dimensions.mjs` 从运行目录拿走，这条命令立刻以 `ERR_MODULE_NOT_FOUND` 失败，
与线上缺文件的表现一致。

## 验证

- 前端契约测试：`tests/markdown/mermaidRenderer.test.ts` 10 passed。
- 后端 Worker 测试：`backend/ts` 的 mermaid renderer 用例 10 passed
  （这组用例会真的 spawn Worker 进程渲染图表，跑满机时可能因 20 秒上限超时，
  空载复跑通过）。
- 部署契约测试：`tests/platform/deployment/` 242 passed, 3 skipped。
- 镜像布局模拟：按 `./bin/` 的镜像目录结构复刻后，冒烟命令通过。
- CI：`docker-release.yml` 与 `runtime-integration.yml` 在 `dev` 分支手动触发后全绿。

## 经验与约束

- **新增 Worker 依赖时，Dockerfile 的复制清单必须同步**。JS/TS 的 import 在构建期
  不校验，缺文件只会在镜像里运行时炸。部署契约测试会扫描相对导入并逐个核对复制
  清单——它是这类遗漏的唯一 CI 闸门，加依赖时要把清单当成代码的一部分维护。
  清单之外的第二道闸是镜像构建期的 Worker 冒烟：让缺依赖在构建期就失败。
- **共用函数的调用方不止一个**。给 IM 栅格化路径加行为时，要先确认 Web 端是否
  也走同一个函数；「只影响 IM」需要用调用点而不是提交说明来证明。
- **viewBox 扩展对界内标签必须是恒等变换**。否则所有常规图表的尺寸都会平白变化，
  这类回归很难靠肉眼看图发现，适合直接写成契约测试。
