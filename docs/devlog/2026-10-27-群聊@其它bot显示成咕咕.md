# 群聊里 @ 其它 bot 一律显示成「咕咕」

## 现象

同一个 QQ 群里同时有多个 bot（自有 bot + 别人的 bot）。用户在群里 `@` 某个 bot 时，
网页端的气泡里显示的是 `@咕咕`，而不是被 @ 的那个 bot 自己的名字；有时候又直接露出
一串平台原始 ID（如 `<@D3C3AC11…>`）。

## 根因：展示层把「被 @ 的 bot」一律写成「咕咕」

`backend/app/api/v1/agent_routes/sessions.py` 的会话消息接口里，展示名映射是这样拼的：

```python
mention_names = {
    str(message.platform_user_id): message.platform_user_name
    for message in msgs
    if message.platform_user_id and message.platform_user_name
}
for message in msgs:
    if message.platform_bot_user_id:
        mention_names[message.platform_bot_user_id] = "咕咕"
...
if bot_platform_user_id:
    mention_names[bot_platform_user_id] = "咕咕"
```

两处赋值都把「被 @ 的 bot」直接映射成常量 `咕咕`，跟这个 bot 到底是谁没有关系。
这写法来自只有「一个咕咕」时的假设（#104 引入），同群多 bot 的场景下就指错了对象：
`@` 别人家的 bot 也显示成 `@咕咕`。

另一半现象（露出原始 ID）是同一段逻辑的另一面：`mention_names` 只装了「当前这一页
消息里当过发言人」的 ID，而被 @ 的 bot 如果这一页没说过话，映射里就没有它，
`replace_mention_ids()` 按设计保留原始 ID 不替换。

## 名字其实已经在库里：bot 发言时 QQ 会带昵称

QQ 的 mention 事件只给 ID 不给名字：

```json
"mentions": [{"id": "D3C3AC11...", "bot": true, "is_you": true}]
```

但同一条消息的 `author` 字段是带昵称的（`username` / `nickname`），群成员和机器人
都算。所以只要那个 bot 在群里开过口，它的真实昵称就已经落在
`conversation_messages.platform_user_name` 里了——问题不在「拿不到名字」，而在
「展示层没去查」。

实测（自有 bot 群 + 第三方 bot 群各一条）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `@` 第三方 bot（它在群里说过话） | `@咕咕 测试测试` | `@小咕助手 测试测试` |
| `@` 第三方 bot（它没说过话） | `<@D3C3AC11…> 看看天气` | 同左（仍无名字来源） |
| `@` 自己这个会话的 bot | `@咕咕 看看天气` | `@咕咕 看看天气`（不变） |

## 一个必须知道的细节：自有 bot 的两套 ID 不是同一个

QQ 对同一个 bot 给了两种 ID：

- mention 事件里的 `mentions[].id`、以及绑定时存进 `user_bots.bot_platform_user_id`
  的，是 **app 级 openid**；
- bot 自己在群里发言、事件回传时的 `author.id`，是 **群级 member openid**。

所以「bot 的发言记录」和「@ 它的那个 ID」对不上号，靠 ID join 拿不到自有 bot 的
昵称。第三方 bot 没有这个断层（它的发言记录 ID 与 mention ID 一致），能直接 join 上。
这解释了为什么修复后自有 bot 仍走产品名兜底，而第三方 bot 能显示真实昵称。

## 修法：按可信度分层解析展示名

新增 `agent/im/models.py::extract_mention_ids()`，从正文里抽出显式 mention
（只认 `<@ID>` 尖括号形态，裸 `@xxx` 可能是邮箱，不猜）；再由
`app/services/conversations.py` 的两个查询提供名字来源：

- `get_session_display_names()`：查这些平台 ID 在本会话里最近一次发言时的昵称
  （取最新，改名后不会被旧昵称冻结，与 events 侧「展示层按会话内最新 username
  解析」的既有约定一致）；
- `get_user_bot_display_names()`：查用户自有机器人的「平台 ID → 配置名」。

展示层 `_group_mention_names()` 按下面顺序取值：

1. 会话内真实发言记录里的昵称（成员和机器人通用）——`@` 到别的 bot 显示它自己的名字；
2. 当前会话自己的 bot → `咕咕`（产品自称，和群里看到的昵称一致）；
3. 用户在同一平台的其它 bot → 它在 IM 配置里起的名字；
4. 解析不到 → 不放进映射，原始平台 ID 保持原样（不猜名字）。

第 4 条是刻意保留的：`@` 一个从没说过话的 bot 时，系统手上确实没有它的名字，
写死一个标签反而会指错对象。

候选 ID 从**正文和引用原文**两处收集（引用框里的 `@` 同样会被渲染）；漏掉引用原文
那一处会让引用框重新露出原始 ID——这是写测试时被抓出来的。

## 验证

- 定向测试：`tests/agent/test_agent_api_messages.py` + `tests/im/test_im_protocol.py`
  + `tests/im/qq/test_qq_raw_ws.py` 共 109 passed（新增 7 条：@ 其它 bot 显示其昵称、
  @ 自己 bot 显示咕咕、@ 自己的另一个 bot 显示配置名、未知 ID 保持原样、改名后取最新
  昵称、mention ID 提取只认尖括号形态、引用原文里的 @ 同样解析）。
- 全量 `tests/agent`：2438 passed, 1 skipped。
- 用真实群数据跑渲染探针：第三方 bot 的两条 @ 消息分别渲染成 `@小咕助手 测试测试`、
  `@小咕助手 看看天气`；自己 bot 的 @ 仍是 `@咕咕`；人多群里成员 @ 仍解析成昵称，
  无残留原始 ID。探针跑完已清理。

## 顺带确认但没改的两处

- **会话标题**：IM 新会话的标题最初是消息原文切片，会短暂带 `<@ID>`；但 LLM 标题
  生成随后会覆盖它，实际只在生成失败时才残留，属瞬时现象，不单独立项。
- **前端**：`resolveSpeaker()` 给群成员气泡标发言人、给 AI 侧标"咕咕"的逻辑本来就
  正确，这次不需要动前端。

## 遗留

从没在群里说过话的 bot 没有名字来源，@ 它仍显示平台原始 ID。要补齐需要新增
QQ 群成员昵称查询（当前网关只调发送类接口，没拉过群成员名册），属于独立的一步。
