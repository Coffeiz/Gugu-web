# 群聊自动回复抢答：@ 别的 bot 也回、命令式短句也回

## 现象

群里同时有多个 bot 时，咕咕会抢答两类消息：

1. `@` 的是**别的 bot** 的消息——群里 @ 别人家的机器人，咕咕也插一句；
2. 明显是下给某个机器人的**命令式短句**（"测试个功能"）——也当成对自己的。

抢答之后，咕咕还会在群里解释自己为什么收到这条消息（"我这边收到的群消息里……我
没法只按'没 @ 我'来判断，就当成给我的了。以后这种带别的 bot @ 的，我尽量不抢话"）。
这类元解释比抢答本身更让人困扰：群里突然出现一段关于机器人路由的自言自语。

## 根因一：@ 别的 bot 这件事，模型根本看不到

QQ 的 mention 事件里，每个提及带三个字段：`id`、`bot`、`is_you`。网关只把
"@ 是不是咕咕"折成布尔量 `group_mentioned` 传下去，**别的 bot 被 @ 这件事
在下游完全不可见**。

于是到了回复选择门（`group_reply_decision`）面前，模型看到的是一条带
`<@D3C3AC11…>` 的正文——一串它无法解释的 ID。它不知道那是另一个机器人，
更不知道咕咕自己的 ID 长什么样。于是它的判断只剩"这条看起来像在问我"，然后
就回了；回复内容里那段"我没法判断"的元解释，正是模型在解释自己看到的矛盾。

**这不是提示词能单独解决的问题**：光靠提示词，模型无法区分"@ 的是我"和"@ 的是
别人"。判断必须由网关用平台的结构化字段做出来。

## 根因二：提示词的默认方向是"尽量参与"

原来的回复选择提示词这么写：

> 只有消息直接向咕咕提问、延续与咕咕的交流，**或确实能为群成员提供帮助**时才回复

后半句是个敞开的口子：任何看起来"我能帮上忙"的短句都能被算成该回，包括
"测试个功能"。同时提示词没有给"沉默"任何优先级，也没有禁止把路由判断写进
正文——所以模型一边过度参与，一边还把判断过程解释给全群看。

## 修法

### 一、确定性拦截：@ 别的 bot 的消息完全不进回复链路

网关侧新增 `_qq_message_mentions_other_bot()`：mention 条目里 `bot=True` 且
`is_you` 不为 True，就是"@ 别人家的机器人"。这个事实通过 payload 字段
`mentions_other_bot` 传下去。

下游两处"这条要不要只记录不回复"的判断同时加上这条规则：

- `agent/im/conversation.py::should_record_passive_group()`
- `worker.py::_is_passive_group_payload()`（worker 侧镜像，用于被动消息实时落库）

结果是：@ 别的 bot 的消息**只落库、不进任何 run**——不抢答，也省掉一次 LLM 调用。
这条规则不看群的回应方式，`回复全部` 模式下同样成立。

### 二、提示词重写：沉默优先、只认明确叫咕咕

`agent/im/auto_reply/prompts/group_reply_decision.md` 重写成三层结构：

1. **前提**：能走到这个选择门，说明这条消息没有 @ 咕咕——消息里的 @ 都不是在叫它。
2. **默认**：群里绝大多数消息不需要咕咕参与，默认沉默；拿不准就沉默。
3. **该回的**：明确叫了咕咕的名字、明确延续与咕咕的对话、或明确抛给全群且咕咕
   能给出确定答案的求助。
4. **该沉默的**：@ 指向别人/别的 bot、看起来是下给某个机器人的命令式短句、
   成员之间的对话、被制止（"没叫你"）、闲聊与表情。
5. **回复内容约束**：不要在正文里解释自己为什么收到这条消息，也不要承诺"以后尽量
   不抢话"这类自我约束——要么给出答案，要么彻底沉默。

## 验证：拿真实模型跑真实选择门

为了不动用户正在用的 bot，临时建了一个假 bot（群回应方式=回复全部），把合成消息
推进 `im:inbound` 队列，让 worker 用**真实模型 + 新提示词**跑完整流程，看模型的选择。

第一轮（只改提示词，未加"命令式短句"规则）：

| 群消息 | 模型选择 | 是否符合预期 |
| --- | --- | --- |
| 测试个功能 | `should_reply=true` | ✗ 仍然抢答 |
| 没人问她 | `false` | ✓ 沉默 |
| 没叫你 | `false` | ✓ 沉默 |
| 咕咕，GPT-6.1 Terra 是什么 | `true` | ✓ 正常回答 |

补上"看起来是下给某个机器人的命令式短句"这条规则后第二轮：

| 群消息 | 模型选择 | 结果 |
| --- | --- | --- |
| 测试个功能 | `false` | ✓ 沉默 |
| 帮我看看这个 | `false` | ✓ 沉默 |
| 咕咕，你觉得呢 | `true` | ✓ 回复（"？说啥呢，都没说是什么事"） |
| 有人知道手冲水温多少合适吗 | `true` | ✓ 正常作答（给出浅/中/深烘水温） |

第三轮后又发现真实群里 12:05 那条"测试个功能"是在另一个 bot 也在的群里发的，
但**咕咕自己的会话里看不到别的 bot**（每个 bot 一个会话），所以提示词只能按
"没有明确叫咕咕的命令式短句"来兜底——这正是上面那条规则的由来。

探针用完即清理：假 bot、8 个探针会话、26 条消息、Redis 去重键、探针脚本全部删除。

### 确定性拦截的端到端验证

再用一次假 bot 走完整链路（同样的临时 bot + 合成消息），验证"@ 别的 bot 的消息
**一次模型调用都不发生**"：

| 合成消息 | `mentions_other_bot` | 模型调用 | 结果 |
| --- | --- | --- | --- |
| `<@OTHERBOTID> terra什么性能` | true | **0 轮** | 只落库，worker 日志记"群聊普通消息已记录" |
| `<@OTHERBOTID> 对照组消息` | false | 1 轮，`should_reply=false` | 走选择门，模型看到 @ 判沉默 |

第一行说明拦截发生在模型之前（省掉整轮调用）；第二行说明没有拦截时同样会沉默
（提示词那一层也生效）。

清理：假 bot、探针会话、消息、Redis 键、脚本全部删除；另外删会话会让已排队的
群反思任务在 `load_messages` 阶段报错（worker 日志里的 `memory-reflection-failed`），
这是探针删除动作的残留，只影响已不存在的探针群，真实群不受影响。

回归：`tests/im` 659 passed；`tests/agent` 2438 passed, 1 skipped；新增用例覆盖
"@ 别的 bot 只记录不回复"（dispatch 侧与 worker 侧各一条）与 QQ 网关的
`mentions_other_bot` 标记。

## 追加：提示词重写导致的静默回归，与「选择门」的工具调用合规率

### 现象

群里咕咕出现「明明在生成回复，但群里什么都看不到」。用户在群里直接问
「怎么不说话了这回」。

### 定位

LoopScope 里能看到 `LLM round 1` 有完整正文、`Final response` span 也有文本，
但 `conversation_messages` 里**没有对应的 assistant 行**，worker 日志也没有
`[im-loop] qq 回复`。

对照 `backend/agent/im/dispatch_finalization.py`：选择门开着时，只有
`gate.choice is ReplyChoice.REPLY` 才允许把正文发进群；否则整轮按「未选择」
静默收尾（PRD-IM-16 §6 的规定：模型直接输出正文、无效调用或未选择，都不得
发送正文）。

所以「模型没调用 `group_reply_decision` 工具」＝「这一轮正文被整段丢弃」。

### 触发原因（本轮提示词重写）

把 20:11 与 21:04 两次 run 的 provider 输入逐项对比：

- `selected_tool_digest` 两次完全相同（`8fecb57124afb0fa`），工具集合没变；
- `Tool schemas injected` 两次都是 `tool_count=1`、`schema_bytes=294`，
  `group_reply_decision` 都在 `selected_tool_names` 里。

**唯一的变量是 system prompt**：本轮重写把判定标准放在协议前面，并且用
「要么给出答案，要么彻底沉默」收尾，模型据此直接开始写正文、跳过了强制工具
调用。21:10:03 把协议重排到最前（「第一步：先调用工具，不要先说话」）后上线，
但**合规率并没有实质改善**。

### 实测合规率（真实群，近 60 分钟）

| 项目 | 数量 |
| --- | --- |
| run 总数 | 51 |
| 门工具被调用 → 判定「回」 | 12 |
| 门工具被调用 → 判定「沉默」 | 16 |
| **门工具被跳过 → 正文被丢弃** | **24** |

也就是说：模型**打算回复**的 36 轮里，只有 12 轮真的发进群，**约 2/3 丢失**。
工具每次都被正确注入，所以这不是注入缺陷，而是模型工具调用合规性的抖动，
叠加「不调用即丢弃」这个设计把抖动放大成了整轮静默。

### 结论

- 选择门把「模型没调用协议工具」直接等同于「模型主动沉默」，等于用一次
  模型服从性去赌一整条消息是否送达。协议不完整时应该有兜底，而不是
  静默吞掉。
- 「群聊不抢答」的正确解法是把判定从主模型里拿出来做成一次**独立、上下文很小
  的判定**（判定为不回复就不进主 run），而不是要求主模型先调工具再回答——
  后者既贵（每条消息都在完整上下文上跑）又不稳。

## 追加二：门开后重复调用选择工具 —— 整轮报废

### 现象

新群 2652（「奇怪」）22:04:46 的 run `run-4da8b94715aa-b7e0bf` 以 error 终态结束，
群里一个字都没有（成员那头还正好吐槽「刚才那轮卡住没回」）。同一晚群 386 还有
两次同款失败。

### 根因：不是漏调门，是多调了门

- round 1：模型调 `group_reply_decision(should_reply=true)` → 门开
  （`{"selected": "reply"}`）→ `Continue after tool round` → round 2；
- round 2：门工具此时**已从 provider 的 schema 里移除**（runner 在 REPLY 状态会把
  它过滤掉），但**工具名还留在对话历史里**，系统提示词也还写着「必须先且仅调用
  一次」——模型据此复读了该工具名；
- `tool_batch_allowed` 在 REPLY 状态下要求批次里不含门工具 → 违反 →
  `group_reply_protocol` 错误终态。

两轮模型的 token 全部白烧（input 81.5k、其中未缓存 21.6k、output 84），群里零
输出。20:12、20:13 那两次里模型还把 `should_reply` 写成了字符串 `"true"`
（schema 声明的是 boolean + `additionalProperties: false`），说明它是在凭历史
记忆调一个已经不在列表里的工具。

这与「漏调门」是相反的失败方向：漏调门有协议纠错轮兜底，多调门此前没有任何
兜底，直接判死。

### 修复

1. `agent/im/auto_reply/decision.py` —— `ReplyGate.choose()` 对「已经做过选择」
   的重复调用改为**幂等**：既有选择权威，重复调用不改写它；与既有选择一致的
   （含模型写成字符串 `"true"` 的情形）静默放过，冲突的仍然报错，但只让这一次
   工具调用失败，不牵连整轮。
2. `agent/im/auto_reply/decision.py` —— `tool_batch_allowed()` 允许 REPLY 状态下
   「只调门」的批次（夹带业务调用仍算越权），并用 `MAX_DUPLICATE_CHOICES = 2`
   封顶，避免模型卡在复读里无限烧 token（普通 run 没有全局轮次上限）。
3. `agent/im/auto_reply/prompts/group_reply_decision.md` —— 补一句「这个工具只
   在你还没做出选择时可用；调用过一次、拿到结果之后不要再调用它」，消除
   「提示词要求调 / 工具已不在列表」的矛盾。
4. `agent/im/auto_reply/decision.py` —— 给选择工具补 `description_short`：

   ```python
   # backend/agent/tools/base.py
   self.description_short = description_short or label or name
   self.provider_description = self.description_short
   ```

   **provider 看到的工具描述来自 `description_short`，不是 `description`**；不设
   就回落成 `label`（选择工具的 label 是「群聊回复选择」）。所以只改
   `description` 对模型毫无影响——第一版修复就踩了这个坑：改完重启，provider
   的 schema 字节数纹丝不动（294），才把这条链路查出来。补上
   `description_short` 后同一份 schema 变成 444 字节，模型这才真的看到
   「拿到结果后不要再调用它」。

第一轮的严格校验不变：`should_reply` 必须是布尔，否则工具报错、让模型重选
（`test_invalid_selection_does_not_open_gate` 仍然保护这条）。

### 验证

- 新增 `backend/tests/im/auto_reply/test_duplicate_decision.py`：幂等重复、字符串
  写法、冲突重复仍然报错、次数上限、以及一条端到端复现线上故障的用例
  （开门 → 复读一次 → 正常跑完，不再产生 error 事件）；
- 更新 `backend/tests/im/auto_reply/test_decision.py`：原来把「REPLY 状态下重复
  调门判为不允许」写成预期的那条断言，改为允许（并补了「夹带业务调用仍越权」）；
- `tests/im/auto_reply` 57 passed；`tests/im` + `tests/agent` 全量
  **3140 passed, 1 skipped**（975s，devserver 串行）；
- 22:44 重启四个服务部署，部署后 8 个 run **零 error 终态**；门工具的 provider
  schema 字节数从 294 变成 444，可作为「新描述已进 provider」的部署标记。
  「复读」这个场景本身频率低（当晚三小时才出现 3 次），部署后暂未自然复现，
  该路径由上面的端到端用例覆盖。

## 遗留

- 自有 bot 的两套 openid（app 级 vs 群级）仍然对不上，模型看到的 `@ID` 永远不是
  咕咕自己的 ID。要让模型能"认人"，得把 ID 渲染成名字再喂给它——那需要把展示层
  的名字解析下沉到入站链路，本次没做。
- 飞书 / Telegram 还没接 `mentions_other_bot`：这两个平台的 mention 事件不提供
  "被提及者是不是机器人"的标记，要等各自平台给出等价信号才能照搬这条规则。
- **选择门本身很吃 token**：实测一次「判定是否回复」的 LLM 轮，输入约 19.4k
  token（其中约 14.7k 命中缓存，真正未缓存约 4.6k），输出几十到几百。也就是说
  群里每来一条消息，都要在完整上下文上跑一轮模型，即使结论是沉默。上面那条
  确定性拦截已经让"@ 别的 bot"的消息完全不用跑模型；再往下省，得把判定前移成
  一个只带最近几条消息的轻量判定调用，沉默就不进主 run——这是下一步的优化方向。
