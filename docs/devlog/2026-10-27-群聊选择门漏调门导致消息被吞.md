# 群聊选择门「漏调门」导致群消息被吞

> 日期：2026-10-27
> 涉及：`backend/agent/im/auto_reply/`、`backend/agent/loop/runner.py`、
> `backend/agent/loop/round_runtime.py`、`backend/agent/loop_drivers.py`
> 关联：[群聊自动回复抢答与提示词重写](./2026-10-27-群聊自动回复抢答与提示词重写.md)

## 现象

群 2652 里，模型明明已经写好了回复正文，群里却一个字都没有。run 以
`group_reply_protocol` 错误终态结束，对外文案是「这条咕咕没接上 😅 稍后再看看。」
——但群里成员并没有对咕咕说过话，这条提示本身就误导。

第一例是 23:00:36 的 `run-c66a36c604bc-da85e9`：

| 轮次 | 发生了什么 |
| --- | --- |
| round 1 | provider 只暴露了 1 个工具（`group_reply_decision`，schema 444 字节），模型**没调**，直接写正文（45 output tokens） |
| 纠错轮 | `Continue after tool round` → next_round=2，纠错指令以「对话中段的 system 消息」送达 |
| round 2 | 模型**完全无视**纠错指令，又写了 325 tokens 正文（草稿里毫无协议意识，就是自然继续聊天） |
| 终态 | `MAX_PROTOCOL_RETRIES=1` 用尽 → error 终态 → 群里零输出 |

代价：input 104830 / fresh 23294 / output 370 全烧，一条群消息丢失。

## 当晚全部协议错误分类

| 时间 | 群 | 轮数 | 门调用 | 各轮工具 | 形态 |
| --- | --- | --- | --- | --- | --- |
| 20:12:29 | 386 | 2 | 1 | 门, 门 | 多调门（已在前一条 devlog 修掉） |
| 20:13:08 | 386 | 3 | 1 | 门, call_tool, 门 | 多调门 |
| 22:04:46 | 2652 | 2 | 1 | 门, 门 | 多调门 |
| 22:27:07 | 2652 | 1 | 0 | call_tool | 元工具绕过 |
| 22:42:30 | 2652 | 1 | 0 | call_tool | 元工具绕过 |
| 22:42:45 | 2652 | 2 | 0 | —, — | 直接写正文 |
| 23:00:36 | 2652 | 2 | 0 | —, — | 直接写正文 |

22:04 之后**再没有多调门**，全是绕过。

## 根因：两套工具约定在打架

- PENDING（还没做选择）阶段，provider 只暴露 `group_reply_decision` 一个工具；
- 但 system prompt（28k~62k 字符）里的 capability catalog 明确列着
  `call_tool` / `get_tool_schema` / `use_skill` / `ask_user` 和 170 个已授权工具；
- 模型被教会的是「任何工具都通过 `call_tool(tool_name=..., arguments=...)` 走」，
  于是照惯例发 `call_tool`——**provider 不校验工具名**，调用原样送达服务端，
  被门禁判越权。

两种绕过方式：

1. **元工具绕过**：发 `call_tool(list_workspaces)`、`call_tool(shell)` 这类调用
   （22:27、22:42:30）。这类调用**有工具调用可以拦截**。
2. **直接写正文**：一个工具都不调，自顾自输出正文（22:42:45、23:00:36 等）。
   这类**没有任何工具调用可以拦截**，协议只写在 system prompt 里是拦不住的。

而 `tool_choice` 恒为 `auto`（`agent/providers/base.py`），协议层零强制。

### 影响面比「7 条错误」大得多

群 2652 走选择门的 154 个 run 里：

- 119 个正常调门（77%）；
- 29 个「成功但没调门」——21:41~22:31 那段旧代码窗口（并行 agent 22:33 之前
  那版还没有协议检查），模型写好正文、门没开、dispatch 静默丢弃，**群里零输出
  且不报错**；
- 6 个协议硬失败。

22:33 换成有协议检查的代码之后，静默丢弃归零，但同两件事变成了硬失败：
**22:33 之后 52 个走门 run → 47 正常、5 次协议硬失败（9.6%）**；22:44 部署之后
28 个走门 run → 25 正常、3 次硬失败（10.7%），最近一次 23:11:29。
**约 23% 的群消息被选择门吞掉，而且都是在模型已经写好答案的情况下被丢的。**

## 修复一：越权调用降级成工具级错误，不再整轮判死

原先 `runner.py` 在批次层面判定越权后直接 `yield error` 收尾：整条消息连同已经
算好的 token 一起报废。改成逐调用判定、逐调用隔离：

- `agent/im/auto_reply/decision.py`
  - 新增 `gate_call_violation_reason(gate, resolved_name)`：按**最终业务工具名**
    逐调用判定（`call_tool` 这层包装要先解开，否则元工具绕过检测不出来）；
  - 新增 `MAX_TOOL_VIOLATIONS = 2` 与 `ReplyGate.note_tool_violation()`：单次违规
    只是把这次调用隔离成工具级错误回灌给模型，连续超限才把整轮判死；
  - `tool_batch_allowed()` 语义随之调整：门开了之后业务工具照常执行，重复调门
    按幂等放行。
- `agent/loop/runner.py`
  - 越权调用不再整轮判死，而是按轮初的门状态算出越权名单，并行批次走
    `protocol_errors` 隔离、串行批次走 `resolve_tool_call` 的协议错误分支——
    两条路径都会把错误当成工具结果回灌给模型，模型下一轮补调门后能继续跑完；
  - 连续违规超上限才落原来的 error 终态。

**判定必须基于轮初状态**：选择工具一旦被执行，门就开了，同一批里后面的业务调用
会看起来「合法」。这一点在第一版实现里踩过——串行路径在执行到选择工具后才
判定，结果同批的 `read_file` 被放了过去（`test_violating_business_tool_never_runs`
抓到的）。

## 修复二：PENDING 轮用 provider 原生强制工具选择

「直接写正文」这种绕过没有工具调用可以拦截，只能让 provider 保证这一轮只产出
选择工具的调用。实测（`backend/scripts/diagnostics/probe_gate_forced_tool_choice.py`，
deepseek/openai 兼容端，正是群 bot 在用的 provider）：

| 组合 | 结果 | 前缀缓存命中 |
| --- | --- | --- |
| thinking=adaptive + 强制 tool_choice | **400** `Thinking mode does not support this tool_choice` | — |
| thinking=adaptive + `required` | **400** 同上 | — |
| **显式 thinking=disabled + 强制 tool_choice** | **200，且确实产出 `group_reply_decision`** | **0.9878**（基线 0.9864） |
| 之后恢复 thinking + auto | 200 ✓ | 0.9864 |

两个关键结论：

1. **关思考必须显式发参数**。省略思考字段等于沿用 provider 默认——DeepSeek 默认
   开着思考，照样拒收强制 tool_choice。走适配器自己的开关
   （`adapter.build_openai_thinking_kwargs(ai, thinking="disabled")`）。
2. **关思考、开强制都不打崩前缀缓存**：整条序列（预热 → 门轮强制 → 业务轮恢复
   思考）每一步的 `cache_read` 都是 13824。

实现：

- `agent/loop_drivers.py`：`_OpenAICtx` 增加 `forced_tool_choice` /
  `base_think_kwargs` / `disabled_think_kwargs`；`prepare()` 同时算出显式关闭
  思考的参数；`run_round()` 在强制时覆盖 `tool_choice`（OpenAI 兼容协议的嵌套
  形状 `{"type":"function","function":{"name":...}}`）。
- `agent/loop/round_runtime.py`：PENDING 轮设置强制 + 显式关思考，门开之后还原
  用户配置的思考并撤掉强制。
- provider 拒收强制 tool_choice 时（4xx 且正文提到 tool_choice）自动退回普通
  `tool_choice` 重发同一轮，本 run 不再强求（`gate.tool_choice_supported`）。
- **Anthropic 协议不强制**：实测强制 tool_choice 会打崩前缀缓存（命中从 ~100%
  掉到 ~15%），所以只对 openai 格式生效。

## 遗留

- Anthropic 格式的 provider 仍然只能靠提示词约束模型不绕过选择门（强制会打崩
  缓存）。这类 provider 的群消息仍可能整条丢失。
- 强制 tool_choice 要求这一轮显式关思考。群 bot 当前用的 deepseek 支持这套开关；
  遇到不支持的 provider 会走 400 降级路径，退回软协议。
- 选择门本身很吃 token（判定一轮约 19.4k 输入，见上一条 devlog）：把判定前移成
  只带最近几条消息的轻量调用，仍是下一步的优化方向。
