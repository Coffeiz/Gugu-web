# QQ 长流式消息约 15 KB 分段调查

## 问题

长回复在 QQ C2C 私聊中显示为多条连续消息。初步怀疑是 QQ 的单条长度限制，也需要区分平台侧拆分和应用主动开启多个流。

## 查证方法

- 在 devserver 对两次真实 C2C 长回复记录流帧元数据：帧序号、`input_state`、匿名化流 ID 指纹、正文字符数/UTF-8 字节数和 HTTP 结果；不记录正文或用户标识。
- 对用户提供的 QQ 消息导出按消息时间边界统计正文字符数和 UTF-8 字节数，不将聊天正文写入本记录。
- 对照 `backend/agent/gateway/qq/text.py`、`backend/agent/gateway/qq/outbound.py` 的流帧构造及收尾逻辑。
- 查阅腾讯 QQ Bot Node.js SDK 的 `stream_messages` 用法和社区项目的文本分片配置。

## 结果

| 导出样本 | 各条机器人消息正文大小（字符 / UTF-8 字节） |
| --- | --- |
| A | 5,020 / 14,662；2,299 / 6,695 |
| B | 4,859 / 14,071；6,257 / 14,601；1,169 / 2,729 |
| C | 5,120 / 14,926；1,417 / 4,159 |

两次帧探针都只观察到一个流 ID，帧序号连续递增，所有 HTTP 请求均返回 200，结束帧 `input_state=10` 也成功。第一条探针记录了 34 帧（index 0–33），最后一帧正文为 12,370 字符、31,486 UTF-8 字节；第二条记录了 32 帧（index 0–31），最后一帧正文为 6,620 字符、19,168 UTF-8 字节。尽管 HTTP 层各自只呈现一条成功的流，聊天导出分别记录为三条和两条独立消息。

多个导出消息边界落在约 14–15 KB UTF-8，折合约 4,800–5,100 个常见中文字符。这与公开实现采用约 4,500 字符的保守单条分片配置相符；它是兼容性配置，不是 QQ 官方公布的精确限制。

代码检查未发现按字符数或字节数主动拆分 QQ 气泡的阈值。`complete_qq_lines()` 仅将未完成的末行留在缓冲区；`QQPrivateTextStream` 以 `input_mode=replace`、同一 `stream_msg_id` 和递增 index 更新当前流。它不会自行创建新的消息流。因而“HTTP 200 且流 ID 未变”并不保证 QQ 客户端/消息历史仍只有一个气泡；现有证据将拆分定位到 QQ 流式链路的下游行为。

## 结论与决策

- 现场表现高度支持 QQ C2C 流式消息存在约 15 KB UTF-8 的实际单气泡边界；这是基于消息导出与帧探针的经验结论。本次查阅的腾讯 SDK 使用指南未列出该数字，因此不将其称为已确认的协议硬限制。
- 保留现有换行安全刷新。它防止尚未完成的 Markdown/URI 行进入不可修改的流前缀；最终 Markdown DONE 帧也需要换行，相关逻辑由 `backend/tests/im/qq/test_qq_reply_sequences.py` 覆盖。
- 若要让分段边界稳定且不截断 Markdown，应另行设计保守的长度上限，并优先在完整段落/行边界关闭当前流、开启下一流。该策略会产生多条消息，只能让分段可控，不能消除平台单气泡限制。本次仅查证和记录，未修改发送策略。
