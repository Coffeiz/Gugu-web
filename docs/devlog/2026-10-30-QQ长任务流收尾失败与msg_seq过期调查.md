# QQ 长任务流收尾失败与 `msg_seq` 过期调查

> 排查日期：2026-10-30
> 排查环境：devserver 受限诊断记录、本地合成协议模拟
> 排查对象：QQ C2C 长任务的被动流式回复
> 排查目的：记录长任务只有工具通知、最终文本未送达的现场；判断它是否可能与同一入站 `msg_id` 的序号重用有关

---

## 现象

一次约 35 分钟的长任务中，QQ 收到了多条工具完成通知，但用户没有收到最终文本。任务最后阶段出现 `QQStreamFinalizationError`。用户确认 QQ 端没有看到最终文本流；Web 端的 Run 已经完成。

devserver 的受限诊断记录显示该收尾异常下层包含 `QQAPIError`，HTTP 状态为 400。事故发生时的诊断没有保存上游数字错误码，因此无法直接确认 400 的具体原因。

## 协议约束

- QQ 官方消息概览列出：C2C 被动回复的有效期为 60 分钟，每条入站消息最多可回复 4 次。相同 `msg_id + msg_seq` 重复发送会失败；多次回复同一消息需要递增 `msg_seq`。
- QQ 官方流式接口示例要求同一流的分片复用 `stream_msg_id` 和 `msg_seq`，`index` 从 0 递增；最终分片使用 `input_state=10`。
- 官方流式接口列出 `50001` 服务错误和 `50002` 频率限制，但没有在该页公布单条流的最大存续时间。

官方资料：

- [消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)
- [流式发送单聊消息](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_stream_messages.post.html)

**边界说明：**官方资料说明每条消息的被动回复次数，但没有明确解释不同 `stream_msg_id` 是否在所有情况下都按独立回复计数。本记录不把“每个内部模型 round 必然消耗一次额度”当作已证实事实。

## 代码路径

1. `backend/agent/gateway/qq/outbound.py::_next_seq()` 为携带同一 `msg_id` 的回复分配递增序号。
2. 当前 Redis 计数器 TTL 是 600 秒，且只在首次 `INCR` 时设置；超过 10 分钟后，键可能过期，后续序号从 1 重新开始。
3. `backend/agent/im/streaming/qq.py::finish_round()` 收束一轮文本后，默认创建下一条 QQ 流。新流会再次按原入站 `msg_id` 分配 `msg_seq`。
4. `backend/agent/im/streaming/qq.py::_finish_qq_stream_run()` 对 `QQStreamFinalizationError` 直接向上抛出，不执行普通消息恢复。worker 会延迟重领失败消息段，因此错误没有被立即改发为主动消息。

这给出一个与现场吻合的候选链路：较早的文本流使用 `msg_seq=1`，序号键 10 分钟后过期；长任务后续的新流再次拿到 `msg_seq=1`；QQ 按重复对拒绝请求；最终流收尾报错。工具通知是独立发送的，所以它们成功并不能证明最终文本流已送达。

## 合成复现

使用可推进逻辑时间的 Redis 替身和只实现去重规则的 QQ 假端点完成本地序号分配与收尾路径复现；该场景已收敛为 `backend/tests/im/qq/test_qq_reply_sequences.py` 的回归用例。

模拟在逻辑时间推进 35 分钟后观察到序号从 1 重置为 1，假端点按 `msg_id + msg_seq` 去重并返回合成错误码 `40054005`，本地最终得到 `QQStreamFinalizationError`。这证明当前代码存在可导致该失败签名的路径；它**不是**真实 QQ 服务端复现，也不能单独证明事故的上游错误码就是 `40054005`。

探针只使用合成消息 ID、内存 Redis 替身和假 QQ 传输，不连接真实 QQ、数据库或模型。

## 已确认与待确认

### 已确认

- 当前序号键 600 秒 TTL 短于官方 C2C 被动回复有效期 60 分钟。
- 序号键过期后，代码可以为同一逻辑消息重新分配 `msg_seq=1`。
- 合成协议模拟能从重复序号走到 HTTP 400 和 `QQStreamFinalizationError`。
- QQ 流收尾异常当前不会立即回退主动消息；异常会交给 worker 的重领路径。

### 尚未证实

- 事故 HTTP 400 是否确为重复序号错误。历史诊断没有保留上游错误码。
- 事故中更早的 QQ 回复是否已使用相同 `msg_id + msg_seq`，以及序号键当时是否已过期。
- 事故是否还受到被动回复次数、消息内容校验或其他 QQ 400 错误影响。
- 一条跨多个工具 round 的长流是否会触发 QQ 未公开的流存续限制。

## 修复方案与验证

- 将同一入站 `msg_id` 的序号状态保留 70 分钟，覆盖官方 60 分钟被动回复窗口并留出 10 分钟余量。键从首次分配序号时起算，首次分配不会早于该入站消息，因此覆盖完整窗口。
- 通过 Redis Lua 原子完成 `INCR` 与首次 `EXPIRE`，避免并发初始化期间留下无 TTL 的序号键。
- Redis 不可用时不再以本机时间戳生成序号；该路径无法保证跨进程单调性，应明确失败并交给现有发送错误处理。
- 回归测试推进合成时钟 35 分钟，验证同一条流的多帧复用 `msg_seq` 且 `index` 递增，之后新流获得下一个序号，不触发重复序号拒绝。
- 此修复不改变流式分段、工具通知气泡或文本与工具消息的排列方式。

修复后，回归用例推进逻辑时钟 35 分钟并断言序号保持单调，覆盖旧序号过期后再次从 1 开始的真实用户可见风险。

## 后续方案讨论边界

- 若保留工具通知独立气泡，工具边界前后的文本应分成不同流，以保持消息时间顺序；每个新流都必须分配可靠的新 `msg_seq`。
- 若把工具摘要写入一条长流，时间顺序可以保持在同一气泡内，也能减少新流和新序号；代价是工具通知不再是独立气泡，而且整次 Run 依赖一条长生命周期流。此前的长任务断流现象尚未通过真实 QQ 长任务验证消除。
- 不论选择哪种呈现，序号键都必须覆盖消息仍可能被动回复的时间范围，并避免在 60 分钟有效期内重置。序号与过期时间应原子维护。
- 主动消息回退应按错误是否确定未送达区分；不能对已确认部分送达或结果不明的超时盲目重发完整文本。主动发送仍受用户设置与平台频控约束。

## 原调查中的诊断改动

本地工作区在 `backend/agent/gateway/qq/outbound.py` 的收尾失败诊断中新增安全字段：HTTP 状态、上游数字错误码、`msg_seq`、帧序号及流/入站 ID 是否存在；不记录正文、URL 或平台 ID。此诊断尚未部署，后续事故需在更新运行环境后才能采集到这些字段。

调查阶段只增加了安全诊断字段，没有修改序号策略；后续生命周期修复也未改流式结构或主动消息回退逻辑。本轮只使用合成数据，没有发送真实 QQ 消息。
