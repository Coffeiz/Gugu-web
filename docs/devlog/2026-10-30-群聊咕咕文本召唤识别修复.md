# 群聊“咕咕回答下”未触发：收据变量覆盖与称呼别名缺失

> 排查日期：2026-10-30
> 排查环境：devserver 受限诊断记录、真实群 Session
> 排查对象：QQ 群消息“咕咕回答下”未启动 Agent Run

## 现象

群里连续发送“pyx是什么文件”“pyx是什么文件？”和“咕咕回答下”，最后一条没有召唤咕咕。第一次排查发现评分器在注意力评估阶段抛错；修复后重发仍未进入 Run。

## 根因

首次失败来自 `runtime.py::load_attention_snapshot`：局部状态变量 `latest_accepted_final` 初始为 `None`，随后从 delivery 模块导入同名函数。当没有可用 ACCEPTED 收据时，快照把函数对象作为最近回复事实传给评分器；`attention_algorithm.py::_last` 读取 `.accepted` 时抛出 `AttributeError`。dispatch 对带有有效入站消息的评估异常按 fail-closed 处理，因此没有启动 Run。

修复将查询函数显式命名为 `fetch_latest_accepted_final`，保留事实变量在“无收据”时为 `None`。

第二次失败已经正常完成评分，但所有关系分为零。真实 Bot 配置名是通用标签“我的 QQ 机器人”，而生产 alias resolver 只传入这个配置名，没有把产品当前统一称呼“咕咕”纳入别名。因而“咕咕回答下”里的“咕咕”没有匹配对象，不能触发高置信名称呼叫。

## 修复

- Alias resolver 始终提供标准称呼“咕咕”，并保留已配置 Bot 名及 payload 别名。
- 标准称呼仍必须满足名称与请求动作/召唤关系的词法约束；孤立提及不因此成为 DIRECT。
- PRD 更新为“当前所有已接入 Bot 统一识别咕咕，暂不支持自定义称呼”，并保留 Bot 名作为附加别名。

## 验证与边界

- 受限诊断记录确认：首次事件在 scorer 中异常并落为 PASSIVE；快照收据变量修复后，第二次事件进入正常 scorer，但因名称关系分为零而落为 PASSIVE。
- 代码已同步到 devserver，后台服务已重启。诊断时间线里第二次评分记录早于标准别名修复；新代码部署后尚未收到一条新消息用于端到端确认。
- 本次未运行测试。需要通过一条新的群消息确认“咕咕回答下”进入 Run；已经记录为 PASSIVE 的旧消息不会自动重放。
