# 延迟群聊 ASK 恢复错用旧候选与过时推理状态

> 排查日期：2026-11-02
> 排查对象：群聊 ASK 等待静默窗口后恢复时的评分主体和 Run 上下文

## 现象

在一批群消息中，较早的“@其他成员”问题与较新的开放问题一起进入延迟 ASK 状态。恢复时重新扫描原始批次，可能让较早消息重新成为评分主体。即使评分主体正确，恢复 Run 还可能把原问题追加到较新的会话历史末尾，或延续前一 Run 的 provider reasoning state，令模型误以为旧话题仍是当前话题。

## 根因

- 待处理状态保存整批消息，到期时注意力运行时会重新构造并遍历整批候选，而非绑定登记时通过评分的确切 ASK 事件。
- 恢复时把较晚的群消息和出站事实放入 ASK 的历史快照，使原问题的历史评分受到未来信息影响。
- 恢复 Run 的当前入站消息实际上早于会话中已落库的后续群消息；上下文缺少这一时间关系说明，模型可能将旧问题视为最新消息。
- 新恢复 Run 允许沿用旧的跨 Run provider reasoning state，旧的推理主题可能覆盖新的会话文本上下文。

## 修复

- Redis 待办只保留选中的 ASK 事件及其事件 ID、平台消息 ID、发送者；等待期间的新 ASK 可更新触发锚点，其他消息只更新静默时钟。
- 到期只对确切触发事件评分。历史快照按该事件到达时点裁切，较晚群消息和 Bot 出站不参与原问题分数。
- 其他成员通过平台原生回复关系直接回复待处理 ASK 时，原子取消待办；提问者后续发言及其他普通群消息保留为后续上下文，并重置静默时间。
- 恢复 Run 的系统提示明确区分旧 ASK 与较新的会话历史，要求模型检查问题是否已解决、转题或过时，并在不需要回复时调用 `choose_no_reply`。
- 延迟恢复 Run 禁用跨 Run provider reasoning state；正常 Run 的推理续接策略不变。
- 注意力版本更新到 `attention-v3.0.7`；评分公式和门槛保持不变。

## 验证

- 针对性后端回归：`20 passed`，覆盖待办锚点、原始时间评分、后续历史隔离、provider reasoning state 隔离及相关注意力路径。
- pytest 输出包含两个来自 `pypinyin` 的 `codecs.open()` 弃用告警，与本次改动无关。
- 本次没有连接真实群聊或执行预发布端到端验收；测试验证的是运行时边界，不代表线上行为已验收。
