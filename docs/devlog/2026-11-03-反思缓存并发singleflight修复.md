# 反思缓存并发 singleflight 修复

## 背景

devserver 上的 MiniMax 反思复现显示：两条拥有相同稳定前缀的请求近乎同时发出时，都只读取到约 0.1% 的缓存；等其中一条完成后再发第三条，则缓存读取接近 100%。这说明冷缓存阶段的同前缀并发会互相竞争。请求此前已有缓存探针，但无法直接判断两次请求的最终稳定前缀是否相同。

## 修改

- Provider 最终请求探针新增稳定缓存前缀摘要指纹。摘要覆盖缓存锚点前的实际请求内容、工具 schema、模型及生成参数；动态尾消息被排除。LoopScope 只保存 SHA-256 指纹和 singleflight 状态，不保存新增的请求正文或凭据。
- 仅对带历史的后台反思分支启用 Redis 跨 Worker singleflight。Anthropic、OpenAI Chat 和 Responses 请求分别按最终投影生成协调键；命名空间包含 Provider 与协议格式。
- Redis 租约为 90 秒，每 30 秒续租；等待上限为 360 秒。Provider 失败、任务取消或正常完成都会释放锁。Redis 不可用、等待超时或锁无法获得时记录诊断状态并继续原 Provider 请求，避免 Redis 故障阻断反思。
- 压缩分支、知识分支和普通对话不启用该协调。

## 验证

新增回归覆盖：动态尾消息不改变缓存前缀指纹、稳定历史/工具 schema 改变指纹、同前缀请求串行、不同前缀并行、Provider 异常与任务取消后的锁释放、租约续期、Redis 故障放行，以及 LoopScope 只暴露指纹和状态字段。

本地定向测试结果：`60 passed`。此记录不代表 devserver 已部署或已进行补丁后的真实 Provider 缓存复测。
