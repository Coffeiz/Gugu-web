# N2 BYOK 向量重建状态读取

## 基线及范围

`GET /api/v1/byok/embedding-rebuild/status` 基线为 `backend/app/api/v1/byok.py:rebuild_my_vectors_status`；真实生产写入方为同文件 `_rebuild_my_vectors_worker`，键为 `emb:rebuild:user:<用户UUID>`，TTL一小时。前端已有 `rebuildVectorsStatus` 调用。该GET只有用户认证，没有BYOK gate，不迁移POST启动与向量计算服务。

Worker running状态为status/ts；正常终态包含status、done、total、with_patterns、pattern_vectors、memory_vectors、failed_users、message、ts；异常终态为status/error message/ts。读取不改正常完成和进度文案，不代替Worker生成状态。

Core `byok/embedding-rebuild-status.ts` 使用可信owner调用读取端口，缺失和损坏JSON保持Python idle语义；Redis错误向上抛出，由HTTP错误出口脱敏，不能伪装idle。错误终态message复用现有 `agent/core.ts:redactToolError`，其规则与Python `app.core.redaction.redact`一致。与旧GET直接回显原始异常不同，Node必须遵守可见错误脱敏边界；不把正常进度改为泛化文案。

Host `modules/byok/embedding-rebuild-status.ts` 仅负责认证、可信owner和HTTP。Redis键属于Host注入，不从请求路径、query或body接收用户标识。

## 验证进度

先编写失败测试，devserver首次因Core模块不存在而失败；实现后首次复测撞到并行Core构建期间dist入口暂时缺失，该次不计功能绿灯。

Python既有 `test_byok_user_embedding_rebuild.py::test_status_idle` 定向1/1。Node测试包括正常/缺失/损坏状态、错误脱敏、认证/owner、Redis故障500及真实隔离Redis旧Worker键读取。统一Core构建完成后，Node契约3/3与生产Host集成1/1合计4/4，无skip。生产集成使用真实用户token及隔离Redis：缺失idle、完整正常终态结构、query不能改变owner、错误message脱敏、未认证401均通过；随后新增不配置Redis的真实Host回归，发现main虽抛503，统一错误出口却强制改成500；保留503预期断言，通过Host路由注入available检查直接发送503通用错误，不修改共享错误映射。修复后同批4/4再次通过，无Redis不伪装idle，正常Redis执行故障仍统一500脱敏。实际Worker未启动，测试直接向相同协议键写入合成状态，不声称向量计算消费者已经迁移。

## 边界

读取真实Redis键不代表向量计算或POST启动迁移完成，测试不会调用付费Embedding。数据库不在此GET直接调用链，不能作为PG/SQLite迁移证据。真实部署、正常前端轮询至完成、实际生产Worker任务均尚未验收。保留其他会话修改，不修改Python后端或用户运行配置。
