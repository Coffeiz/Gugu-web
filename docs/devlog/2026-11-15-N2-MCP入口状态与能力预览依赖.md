# N2 MCP入口状态与能力预览依赖

## MCP入口状态

`GET /api/v1/mcp/status` 以 `backend/app/api/v1/mcp_settings.py:mcp_status` 为基线。它只返回平台mcp.enabled，不连接MCP server，也不发现工具；前端router实际使用它控制MCP入口。不能从状态可读推断MCP配置CRUD或工具调用已经完成。

Core `mcp/status.ts` 组合可信设置读取；Host `modules/mcp/status.ts` 负责认证、只读配置及HTTP。配置优先级为默认 < 环境JSON < 嵌套环境 < override，每次读取响应热更新。Python override通过model_construct保留原值，Node不擅自把字符串转换为另一种开关语义；损坏配置明确拒绝，不写回运行配置。

测试先因Core模块缺失失败，实施后Node 2/2。覆盖优先级、热更新、认证及错误脱敏。`compat/tests/test_mcp_status.py` 使用真实Python handler和AppSettings、独立临时配置，1/1。生产Host已接线；串行Core构建通过后，真实用户token/生产认证读取默认开启、临时override关闭及重新开启均通过，未认证401。与契约合计3/3，无skip。MCP状态本身不访问数据库或Redis，生产认证使用隔离PG；同一个Host集成中的其他API另使用隔离Redis。所有执行在devserver，不连接外部MCP，不读取用户配置或改动参考后端。

## BYOK能力预览阻塞

核实 `POST /api/v1/byok/capabilities` 只需静态Provider声明，无网络/凭据；已有Core `capabilitySnapshot` 可复用。新增Core与Host原型及严格Python实际handler对照，但保留失败，不接生产。

六类代表输入中，openai、qwen、minimax、local快照完全一致；两个共享Provider差异阻塞：

- Ollama native：Node selected_api_format为ollama，并返回disabled/adaptive及low/medium/high/max；Python实际handler为openai，reasoning modes/efforts均为空。
- custom/unknown：Node default_base_url及default_base_urls.openai使用OpenAI默认地址，Python均为空。

`apps/web-host/tests/byok/capabilities-preview.test.ts` 全字段严格比较，未删除或放宽失败断言。按子测试计5通过、3失败（包含失败父测试），HTTP认证/gate/DTO/额外凭据字段隔离通过。未修改共享Provider实现；该API不得标完成，也不能把其他四类通过当作全Provider接通。

原型文件：Core `byok/capabilities-preview.ts`、Host `modules/byok/capabilities-preview.ts`。需要共享Provider契约先明确上述差异，再决定兼容策略；此任务不扩大为Provider领域重构。
