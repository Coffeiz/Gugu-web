# N2 QQ 扫码连接

## 接口和真实消费者

- `POST /api/v1/me/qq/connect` 创建扫码挑战。
- `GET /api/v1/me/qq/connect/{task_id}` 轮询授权；该 GET 会在授权成功时解密、写入/更新 Bot、清理挑战并发出通知，不能只当状态查询迁移。
- 前端真实消费者为 `apps/web/src/services/api.ts` 的 QQ connect start/poll；保存后的 Bot 由 Python 正式 gateway `_fetch_userbots` 消费。

基线：`backend/app/api/v1/qq_connect.py` 的 `start/poll/_decrypt_secret`；pytest `tests/im/qq/test_qq_connect_scan_url.py`，邻近 `tests/im/test_user_bot_message_format.py`。旧扫码 URL 历史回归必须保留 `/qqbot/openclaw/connect.html`，不能误用内部平台名 `/qq/`。

## 目标调用链

Host `modules/im/qq-connect.ts` 负责认证、HTTP 错误映射及可信门户配置；Core `im/qq-connect.ts` 完成挑战 owner/过期语义、门户 JSON 协议、AES-256-GCM 解密、owner 锁内 upsert 和提交后清理/通知。

门户请求通过已有 `NodeProviderTransport` 的 URL/DNS 校验、固定目标、超时、响应大小上限和不跟随重定向。默认官方门户；自定义门户只来自可信 Host 环境，显式允许本地目标供原有自托管门户及隔离测试使用，请求体不能改变目标或授权本地网络。Host 生命周期关闭该 transport。

Redis 使用通用短期状态存储，协议键仍为 `qqconnect:<task_id>`，值只含 uid/key，TTL 600 秒；AES key 只存服务器。成功响应不泄漏 challenge key 或 AppSecret。

正式模型没有 owner/platform 唯一键，事务内锁 owner 行串行化 Node 并发写入。与既有手动 QQ 创建直接共享 `insertQqBot` 的完整正式默认列；原手动创建的事务、加密及通知顺序保留。

- 同 app_id 再扫码更新密钥并重新启用，不重复创建。
- 不同 app_id 且 owner 已有 QQ Bot，返回业务失败并清理挑战。
- 密文损坏/缺少字段保留挑战，不写入 Bot。
- owner 不匹配 403，并且不请求上游。
- 提交成功后清 Redis 挑战，再 best-effort 失效 owner 四种 IM 来源快照并通知；不影响其他 owner/Web 来源。
- 事务失败保留挑战且无快照/通知副作用。提交后 Redis 删除失败返回脱敏 503，凭据已经持久化，不能声称回滚。

## 有意安全差异

1. 未配置 Redis 时，认证后直接 503，不先创建上游任务；Python 是请求上游后才访问 Redis。
2. 挑战写入使用 NX，防止上游重复 task_id 覆盖其他 owner 的密钥；Python 无条件覆盖。
3. Node owner 行锁避免并发创建重复 Bot；不声称解决 Python 自身的并发竞态。
4. 门户错误/Redis 故障返回固定安全文案，不回显上游正文、原始异常、凭据或连接地址；不自动跟随重定向。
