# N2：QQ 机器人创建与快照失效

## API 与真实消费者

新增 `POST /api/v1/me/bots`（生产路由允许尾斜杠），前端 `botsApi.create` 已调用该地址。Core `im/user-bot-create.ts` 承担平台授权、业务校验、事务创建和提交后副作用；Host `modules/im/user-bot-create.ts` 承担认证 owner、BotIn DTO 及 400/409/503 映射。主会话接入 package/app/main，复用现有目标 Host 的 EncryptedString AES-GCM 适配及动态 IM 平台设置读取。

真实 Python `agent.gateway.gateway._fetch_userbots` 从同一正式表读取启用 Bot，经过 ORM 解密并生成 gateway spec。本轮验证实际读取结果和凭据 SHA，不启动 QQ 连接或外部进程；不把实际 QQ 网关运行、消息往返或部署算完成。

## Python 基线与保留行为

基线为 `backend/app/api/v1/user_bots.py::create_my_bot/BotIn/_out`、`app/core/crypto.py`、`app/core/events.py::publish/bump_context_revision` 和 `agent/context/session_snapshot.py::invalidate_user_im_snapshots`。

- QQ 平台关闭先返回 503，再检查凭据。空串 400，已存在 QQ Bot 409。保留 Python 的细节：name 不 trim，纯空白 AppID/Secret 在校验后 trim 成空值；没有自行添加前置非空校验。
- 正式 UserBot 没有 owner/platform 唯一约束；Node 使用 owner 用户行锁串行创建，两个 Node 请求只有一个成功。**此锁不能保证未采用同一锁的旧 Python 并发创建也唯一**，未宣称跨运行时唯一性已修复。
- AppSecret 用与 Python HKDF-SHA256/AES-256-GCM 相同格式持久化，响应只返回掩码。显式填写完整 ORM 默认值，避免依赖精简表或缺失 server default。
- 保留 commit → refresh → 通知顺序。提交后记录丢失时返回错误，不把 undefined 当创建成功，也不触发快照或事件。数据库创建失败没有后续副作用。

## 最小共享依赖与解绑接线

新增直接依赖 `invalidateOwnerImSnapshots(db, ownerId)`：独立提交，限定 owner 和 `feishu/qq/wechat/telegram`，仅设置过期时间、context_epoch+1，保留旧快照正文和两个 hash，Web 及其他 owner 不受影响。Python 的 snapshot 旁路 trace 在没有 active run 的 HTTP API 内本来跳过；本切片没有迁移 trace 或 IM 执行器。

创建提交后先 best-effort 失效快照，再发布真实 `im_channels` refresh；任何一个副作用失败都不撤销已持久化创建，失效失败也不阻断资源事件。主会话还在既有 QQ 解绑生产回调中复用该能力，先尝试失效，再继续原 Redis 发布；没有改写已有 IM 业务或迁移旧目录。
