# N2 Telegram 接入安全边界

本轮只核对 `POST /api/v1/me/telegram/connect` 和 `PUT /api/v1/me/telegram/connect/{bot_id}`，没有新增实现或测试，不将可复用的 Bot 持久化能力算成这两条 API 已完成。

Python `app/api/v1/telegram_connect.py` 的 `_verify` 必须依次调用 getMe/getWebhookInfo，拒绝非法 ID、已有 Webhook 和无效 Token；创建还要求 owner 单 Bot 与跨 owner 平台 ID 唯一锁；换到不同 Bot 时清除旧 owner 私聊绑定。对应 pytest 为 `tests/im/telegram/test_telegram_connect.py`。

实际协议由 `app/services/telegram_bot_api.py` 构造：Telegram 官方要求 Token 位于进程内 HTTPS 请求路径中，该文件为其明确声明了固定官方主机/禁重定向/不记录完整 URL 或正文的旧实现例外。当前用户 AGENTS 规则禁止凭据写入 URL；不能从旧 Python 注释自行扩大为新 Node 例外。父会话确认保留此阻塞，因此未构造携带 Token 的 Node URL、未调用真实 Telegram、未开始伪客户端测试。

另一个需要明确接线的契约是 safe-egress：Python `call` 在有效 `safe_egress.enabled` 时使用 `build_httpx_proxy` 且关闭环境代理，配置异常也返回安全错误。Node 已有 `createSafeEgressSettingsReader`、安全凭据加解密及 `NodeProviderTransport` 的显式 proxy/authorization 能力；目前生产该 reader 仅接管理员配置读取，尚未形成 Telegram 每次验证时的动态有效代理和认证装配。不能直接采用默认环境 transport 并声称与 Python 专用代理规则一致，也不需要据此重做整个代理领域。

QQ/飞书已具备加密 Bot 写入、快照失效和真实 Python 消费证据，但这些能力不能消除 Telegram 的上述协议安全冲突。待用户明确该协议边界之后，才能开展新 Node 受控适配的 TDD；正式 SQLite、Telegram 真实服务与部署均未验证。没有改 Python、运行配置、共享入口或清单；没有提交/推送/CI。
