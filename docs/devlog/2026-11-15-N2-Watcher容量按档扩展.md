# N2 Watcher 容量按档扩展

完成 `POST /api/v1/admin/filesync/watcher-capacity/expand` 的目标结构和生产接线。真实调用方为 `apps/web/src/components/filesync/FileSyncAdminPanel.vue` 的“立即扩容一档”，请求封装在 `apps/web/src/api/filesync.ts:expandWatchLimit`。

生产链路为管理员 guard → `modules/filesync/watcher-capacity` → Core `filesync/watcher-capacity` → Host `adapters/inotify-limit-client` → 已有正式 Unix helper。Core 决定扩展成功或已到硬上限；Host 只做认证、HTTP 错误映射和 Unix 单行 JSON 协议，不搬入整个 filesync Worker 或新建 daemon。

## Python 实际合同

基线是 `filesync_admin.expand_watcher_capacity`、`app/services/filesync/inotify_limit_client.py:request_limit_agent` 与 `scripts/runtime/inotify_limitd.py`。

- 客户端只发 `{"operation":"expand"}`，不接受 API 调用者提供 socket 路径、操作、目标 sysctl 值或硬上限。
- socket 路径实际来自 Python 模块的 `os.getenv('FILESYNC__WATCH_LIMIT_SOCKET',默认正式路径)`；AppSettings/FilesyncSettings 没有 watch_limit_socket 字段，`config.override.json` 不覆盖 socket。Node 复用同名环境变量和正式默认值，不发明额外来源。
- 真正动态配置由 **helper** 的 `configured_hard_limit` 每次读取其挂载策略中的 `filesync.watch_hard_limit`；helper 根据 socket peer UID 统计监听数、按当前值扩一档、上限夹取，并以锁串行化。Node 不复制或绕过这套特权规则。
- 连接超时 2 秒、读取超时 3 秒；响应按换行或 EOF 分帧、最多 4096 字节，必须 JSON object 且 `ok is True`。客户端销毁每个 socket 和定时器，不能把拒绝响应里的原始内容或路径带到 API。
- 成功原样返回正式 helper 数据；没有 expanded 返回 409 `当前容量已达到配置硬上限`；服务不可用/拒绝/协议错误返回 503 `宿主机 watcher 管理服务不可用`。

## 完成和未完成边界

本接口的业务、生产入口和正式 helper 协议已接通。**整个文件同步管理页仍未闭环**：按钮可见条件是尚未迁移的 `GET /admin/filesync/status` 返回 watcherCapacity.available；没有用假状态显示按钮，也没有修改前端绕过条件。

当前平台是支持 Unix socket/peer UID 的服务端；桌面、正式宿主机 socket 挂载/权限、真实 sysctl、完整部署和 Worker 的自动扩展未验收。本接口无业务数据库读写，隔离 PG 只用于既有生产 Host 初始化；不能据此声称双库 filesync、特权宿主部署或整页前端验收完成。

所有新增业务直接位于目标 Core/Host 目录。未改旧 domains、Python 参考实现、共享清单或其他会话实现；导出和组合根由主会话增量处理。未提交、推送、fetch 或触发 CI。

## 本轮剩余类别的具体缺口

继续逐项核对以下尚未覆盖项，未改变其完成状态：

- `GET /admin/filesync/status`：`get_admin_sync_status` 先解析真实 workspace/local binding root、`cleanup_stale_conflicts` 并可能 commit，然后聚合 journals/conflicts/outbox 和 watcher helper 状态。当前 Core 只有 run read/cancel/dry-run，不能简化为 DB counts 或固定 unsupported。
- `POST /admin/filesync/bindings/{id}/initialize`、`/{id}/reconcile`、`/{id}/missing-preview`、`/{id}/missing-apply`、`POST /admin/filesync/reconcile-issues`：依赖真实绑定 root identity、磁盘投影、共享排他对账/计划及执行消费者；Node dry-run job API 不代表这些 Worker 行为已具备。
- `POST /admin/filesync/conflicts/{id}/resolve`：`admin_resolve_conflict → resolve_sync_conflict` 还需实际文件冲突解决、outbox/提交/发送事件的双事务语义，不能仅把 conflict 状态改 resolved。
- `GET /admin/folder-doctor/scan` 和 `POST /admin/folder-doctor/repair`：实际依赖旧 DB folder/project/workspace 期望目录、key strategy、空骨架判定、misplaced cap/冲突和全盘目录观测；repair 重新扫描，只补缺失目录，禁止删孤儿或搬文件。当前目标无同源目录映射合同，不为了旧目录领域扩展迁移；本轮未做文件操作。
- `GET /files/{fid}/thumb`、`/{fid}/xlsx-preview`、`/{fid}/xlsx-preview-image/{image_id}`：需要 owner/软删检查后完整共享预览服务，含大小限制、缓存失效、实际图像/表格解析及 XLSX 内嵌图关联与格式错误。当前 generic file bytes reader 不等于这些服务；避开并行 perception 工作，不接原文件冒充缩略图/预览。
- `POST /admin/storage-quota/reconcile`：Python先取得真实 Redis lock，保存 queued 后在同进程 create_task 启动 `_run_full_reconcile`，续锁并处理实际全用户用量重算；Node只读状态已接通，不把写入 queued 算后台消费者完成。
- `POST /onboarding/dev/reseed`：仅开发账号，重播种还需清旧引导物理对象、projects/files/calendar 事务和随机新 key；现 Core reset-guide 只复位引导状态，不是 reseed。不得把 resetGuide 代替重建数据；当前不做破坏性清理测试。

以上均找到具体调用链或平台依赖，未宣称永久不能实施；对应共享能力具备后可继续按有效红灯推进。
