# N2 定时任务文件授权申请与确认

## 迁移范围

- `POST /api/v1/scheduled-tasks/{task_id}/filesystem-authorization/request`
- `POST /api/v1/scheduled-tasks/{task_id}/filesystem-authorization`

Python基线为 `scheduled_tasks.py` 的两个同名handler、`filesystem_authorization.py:grant_scheduled_task_filesystem_access` 与实际确认Store；前端已有对应调用。Core新增 `scheduled-tasks/task-filesystem-authorize.ts`，Host同名模块负责HTTP、确认码DTO及只读热策略；生产根复用已有Redis确认Store、HMAC及授权指标适配。不迁移任务创建/调度/执行器。

## 行为与事务

先按owner读取任务，再判断平台是否local存储且完整用户沙箱授权已开启；停用任务400，跨owner/缺失404，开关关闭409。申请不创建grant；按用户、任务摘要和任务identity撤旧确认并生成10分钟一次性确认码，requested审计同事务。确认码缺失、重复消费、过期或任务绑定不匹配均失败；持久grant及任务引用与granted安全审计同事务。锁定任务行避免两个Node请求创建重复grant；redeem后再次读取热策略，关闭时不能落grant。

保持Python的正常返回和失败副作用：Redis确认不可用时申请返回200的confirmation_unavailable结构，不假装authorized；错误绑定可建立正确任务的新待确认记录；确认码一旦兑换，不随后续DB失败恢复。事件绑定提醒可申请确认，但确认时service语义返回409；此时码已消费。复用当前未撤销指针与按主体/范围/未过期条件查active grant的历史差异也保留；Node额外限定指向grant必须同owner。

全局配置优先级为默认 < 环境JSON < 嵌套环境 < override，实时读取 `storage.backend` 和 `sandbox.full_user_sandbox_authorization_enabled`。不复用只看启动环境的旧开关，不写用户配置。requested/granted指标使用原UTC日键、固定field与14天TTL，不包含任务正文。
