# N2 定时任务、管理员更新与外部连接剩余盘点

范围为本轮尚未逐项证明的 18 个接口。这里只做代码、调用方和 pytest 核对，不修改实现、共享入口或 API 清单；没有执行 Docker、更新器、真实扫码/外网连接、真实通知或破坏性文件操作。

## 定时任务 4 个接口

真实前端消费者为 `apps/web/src/services/api.ts` 的 scheduled-tasks API；日历与定时任务界面使用该 service。

| API | Python 行为与未具备的链路 |
| --- | --- |
| `POST /api/v1/scheduled-tasks/` | `scheduled_tasks.create_task` 除了归属、时间窗口、附件/投递目标和授权校验，还包括日历提醒重复处理、Undo 合并与提交后发布。现 Node `modules/scheduled-tasks/task-create.ts`、`persistence/task-writes-postgres.ts` 为未装配原型；业务与查询仍在 Host，并非目标 Core 完整用例。生产 `main/app` 没有调用 `registerScheduledTaskWrites/createPostgresTaskWrites/createPostgresTaskResolver/createPostgresTaskExternal`，也未组装真实调度执行消费者；不能只注册路由写入没有目标执行器的任务。 |
| `PATCH /api/v1/scheduled-tasks/{task_id}` | `scheduled_tasks.update_task` 有改类型重置旧 schedule 字段、日历提醒冲突 409、编辑内容撤销持久工具授权、停用撤销文件系统授权、保持未传字段及投递目标解析语义。现 Host 原型有部分事务逻辑，但同样未装配；需先证明事务内确认码撤销/授权审计、完整投递解析及真实调度消费。不能把已完成的独立授权接口当作所有写入路径已消费授权。 |
| `POST /api/v1/scheduled-tasks/test-notify` | `scheduled_tasks.test_notify → _resolve_web_delivery_targets → app.scheduled_tasks.deliver_to_channels`，认证 DB 会话在外部投递前关闭；不创建任务，返回各选定渠道的实际结果。Node 的 delivery-target 查询仅提供目标，未找到生产同等多渠道投递服务。仅实现 web 或把发布事件当作 IM 已送达会改变用户可观察结果。 |
| `POST /api/v1/scheduled-tasks/{task_id}/run` | `scheduled_tasks.run_now → execute_task`；普通任务走 trial，不写运行状态；失败过的一次性任务走正式重试，成功必须收尾。HTTP 超时只结束等待，shield 保留实际执行且最终投递。Node `once-task-poller.ts` 的 `execute(taskId)` 和 `repeating-dispatch.ts` 的 `execute()` 仍为注入端口，生产 main 无对应实例或实际执行注入；不能以假 runner 或返回 pending 代替执行。 |

已阅读对应 Python `test_scheduled_task_schedule_rules.py`、`test_scheduled_task_execution.py`、`test_scheduled_delivery_units.py` 的场景，并核对 task workspace/delivery targets 文件。覆盖规则包括活动提醒幂等、试运行/失败重试、owner 限定群目标、IM reach 回退、邮件无收件人等。Core `agent/tools/scheduled-tasks.ts` 目前提供只读 `createListScheduledTasksTool`，并不是上述创建、执行或投递能力。

本轮未做这些接口的红灯或实现，未宣称现有原型可生产使用；后续需要完成对应共享用例与真实执行/投递消费者，或先把已具备的依赖明确提供给独立切片。

## 管理员更新 6 个接口

真实消费者为 `apps/web/src/services/adminUpdate.ts`。Python `backend/app/api/v1/admin_update.py` 调用 `updater.client.call_updater`，不是通用 RPC 或静态版本信息：

| API | 必要行为 |
| --- | --- |
| `GET /api/v1/admin/update/status` | 检测真实部署类型；enabled 时读取进程内应用包执行器状态。终态 succeeded/failed/rollback_required 还会按 task id、状态、版本幂等写结果审计。仅 disabled 平台状态不是全部实现。 |
| `POST /api/v1/admin/update/check` | 调用实际更新源检查 candidate，随后写检查审计。 |
| `POST /api/v1/admin/update/preflight` | operator 传给真实预检，返回 readiness/challenge；审计记录通过与否及版本。 |
| `POST /api/v1/admin/update/start` | 校验 manifest 摘要，**先提交审计，再**向真实执行器传 challenge、manifest、operator；涉及当前容器/进程被替换后的继续执行。 |
| `POST /api/v1/admin/update/rollback/preflight` | 调用真实 rollback_preflight 并审计。 |
| `POST /api/v1/admin/update/rollback` | 先审计，再传 challenge/operator 给回滚执行器。 |

`updater/client.py` 继续调用 deployment detector、self_update_enabled 和实际 AppBundleExecutor，并把 busy、challenge_expired/invalid、preflight_failed、update_source_unavailable 等错误映射为具体 HTTP 状态。当前目标 Node/Core 未找到对应 updater/应用包验证、确认挑战及生命周期执行实现。没有把 Python reference 后端当作 Node 隐式代理，也不在禁止 Docker 验收的当前范围补整个部署更新领域。

已核对 `tests/platform/admin/test_admin_update_routes.py`：它只验证 6 路由存在与 bearer 安全声明，不能证明更新行为。真实行为基线位于 `tests/platform/deployment/test_updater_app_bundle.py`、`test_updater_deployment.py`、`test_updater_standalone.py` 等，后续迁移需按部署平台单独验收。

## 外部连接 8 个接口

前端真实消费者为 `apps/web/src/services/api.ts` 的 qqConnect/feishuConnect/wechatConnect/telegram 接入调用。

| API | 必要行为与缺口 |
| --- | --- |
| `POST /api/v1/me/qq/connect/` | 调官方 create_bind_task，随机 AES key 只保存 Redis `qqconnect:{task_id}`，TTL 600；返回官方 `/qqbot/openclaw/connect.html` 扫码地址。单独 start 不具备完整 Node 连接消费流程。 |
| `GET /api/v1/me/qq/connect/{task_id}` | owner 限定任务、过期/等待/失败语义、AES-GCM 解密；同用户同 app_id 更新，另一个 QQ Bot 冲突拒绝，提交 Bot 后通知失效。缺完整目标 Bot 连接用例及共享 IM 失效链。 |
| `POST /api/v1/me/feishu/connect/` | 官方注册 begin，Redis 保存 owner/device_code，TTL，并构造带 source 的验证地址；Node 无对应注册协议端口和完成消费者。 |
| `GET /api/v1/me/feishu/connect/{poll_id}` | pending/slow_down/expired/access_denied 分支；成功 upsert Bot，还保存 owner open_id、时间及 `save_imreach`，发布 IM refresh 并删除 Redis challenge。上述成功副作用未具备完整目标实现。 |
| `POST /api/v1/me/wechat/connect/` | 依赖 WechatClient 创建二维码与 Redis owner/qrcode 状态；Node 未具备同等客户端。 |
| `GET /api/v1/me/wechat/connect/{task_id}` | 通过 WechatClient 轮询，finally 必须 stop；成功更新该用户微信 Bot token/baseurl、提交后清 Redis 并发布 refresh。不能只返回 waiting/expired。 |
| `POST /api/v1/me/telegram/connect/` | `telegram_connect._verify` 校验 token、getMe 身份及 getWebhookInfo（已有 webhook 要拒绝，不能擅自删除）；PG 唯一键锁保护平台 ID 与 owner 单 Bot约束，创建加密凭据、提交后 `_touch`。Node 已有 binding-code API 并不覆盖 token 验证或唯一性写入。 |
| `PUT /api/v1/me/telegram/connect/{bot_id}` | owner 验证、getMe、平台ID唯一锁；改绑到不同 Bot 必须清空旧 owner 私聊绑定，不同用户同平台 ID 冲突 409。提交后同样调用 `_touch`，不是一般字段更新。 |

共同具体依赖为 Python `app/core/events.py:bump_context_revision` 在 `im_channels` 改变时调用 `_invalidate_im_session_snapshots → agent.context.session_snapshot.invalidate_user_im_snapshots`；该链会失效四种 IM source 的已存在会话快照。现 Node 发布者只有 Redis context revision/live 事件，尚无同等数据库快照失效消费者。此前 QQ 解绑已记录同一缺口；本轮没有扩展整个快照领域，也不把新 Bot 写入和 Redis 成功当作完整连接完成。

已阅读 `tests/im/qq/test_qq_connect_scan_url.py`（锁定官方 qqbot 路径，避免二维码白屏）及 `tests/im/telegram/test_telegram_connect.py`（token验证、owner/平台唯一、换 Bot 清绑定等）。现有 QQ 测试仅 start+mock HTTP/Redis，不证明 poll 成功副作用或真实外部服务。

## 本轮结论

18 个接口均找到了真实消费者和具体生产缺口；本轮没有证明其中某个具备完整依赖、可直接独立接入的业务切片。没有编写新失败测试或实现，也未新增路由数量、修改清单完成状态。以上是当前目标结构与调用链的核对结果，不表示这些接口永久不可迁移。
