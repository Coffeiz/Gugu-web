# N2 导入确认、回滚与恢复：部分实现及写门禁阻塞

本轮根据真实消费者和现有正式 Python Worker，先后实现三个目标结构用例及 Host 路由：

- `POST /api/v1/data-portability/imports/{job_id}/apply`
- `POST /api/v1/data-portability/imports/{job_id}/rollback`
- `POST /api/v1/data-portability/imports/{job_id}/recover`

**当前均不能计为生产完成。** 检查恢复权限时发现缺失跨 API 的账号替换写入门禁。主会话已撤下三个用例的生产 main 注入，仅保留目标模块、包导出、可选路由装配及定向测试；没有让不安全的替换能力继续暴露。没有扩展全局认证/所有业务写入口的共享迁移。

## 与清单三行对应的明确阻塞

| method/path | 已验证 | 阻塞与当前生产状态 |
| --- | --- | --- |
| `POST /api/v1/data-portability/imports/{job_id}/apply` | Core事务；曾通过的生产Host+真实Python incremental/replace消费 | Node普通用户写入口尚无替换维护门禁。两模式单跑不证明replace并发安全；整个API的main注入已撤下，不标已完成。 |
| `POST /api/v1/data-portability/imports/{job_id}/rollback` | owner/快照/幂等/互斥事务；缺能力红灯后实现 | 回滚也进入替换维护窗口，需要相同跨API门禁。生产main注入撤下；真实快照恢复新增批次未验收，不能借apply的Worker绿灯宣称回滚完成。 |
| `POST /api/v1/data-portability/imports/{job_id}/recover` | owner、needs_recovery、双归档引用、旧租约/error清除和并发事务 | needs_recovery必须持续阻止普通写入，而迁移控制面必须可访问。该共享权限合同缺失，main注入撤下；真实故障后重试未验收。 |

重新接入前，需要可信owner维度的共享门禁覆盖普通写入口，按Python的三种维护状态返回423及Retry-After=5，并豁免安全方法与迁移控制面；随后验证普通业务拒写、控制面可恢复及真实Worker终态后恢复写入。不是在三个route本身加一个if或固定拒绝即可解决。本记录不修改共享清单，也不把部分实现升为完成。

## 已有代码与基线

Core `packages/core/src/data-portability/apply-import.ts` 集中三个同领域用例，复用已有任务读取 DTO 和 PostgreSQL transaction/query 端口。Host 路由分别在 `modules/data-portability/{apply,rollback,recover}-import.ts`；不依赖旧 domains 原型。真实消费者是 `ProfileDataPortabilityPane.vue` 和 `services/api.ts` 的数据迁移 API。

Python 基线为 `data_portability.py` 的对应 handler 和 `app/services/data_portability/api_jobs.py`：

- `apply_import_job`：用户行锁、owner 任务行锁、queued 同模式/幂等键重试、预检/有效期、一致时间比较、一次性 SHA256 确认能力、replace 完整归档和 incremental 唯一冲突规则、跨导出/导入互斥、状态更新与能力消费同一事务。
- `create_rollback_job`：owner/来源行锁；成功 replace 且快照未过期；同幂等键必须指向同来源，重试优先于后来的过期校验；创建新的 rollback 任务并继承来源归档和快照有效期。
- `recover_import_job`：仅所属 replace/rollback 的 needs_recovery，且暂存和快照引用完整；重排 queued，保留 stage=needs_recovery，原子清除旧 lease owner/until 和 error_code，不自行改归档/快照。

Host 建立认证与 DTO、403 确认能力错误及 202/no-store 协议。临时生产 main 曾使用 SHA256 和 timingSafeEqual，非法 hash 拒绝；不能用普通字符串比较作为正式密码学适配。

## 直接阻塞：跨 API 写门禁

Python `app/core/security.py:get_current_user` 在身份/停用/版本检查后调用 `ensure_data_replacement_allows_write`：

- GET 等安全方法与 `/api/v1/data-portability/` 控制面豁免。
- 普通用户写入若存在所属 `DataImportJob.status IN ('applying','rolling_back','needs_recovery')`，返回 **423**、固定提示及 **`Retry-After: 5`**。
- 正式 replace Worker 先将 job 设为 applying 并提交，再排空已有会话、获取快照、切换文件和数据库；失败恢复未完成时保留 needs_recovery，继续阻止普通写入。

当前 Node `src` 未找到等价任务状态查询/写入门禁。仅有普通账号 active/security_version 检查不够；Worker 成功单跑也不能证明与 Node 并发写入安全。该能力横跨全部用户写入口、会话与文件/DB 维护窗口，不应在本切片重建整套共享认证层。

因此 apply（尤其 replace）、rollback、recover 的 API 业务和定向实现保留，生产入口撤下，**未标记完成**。正式 SQLite、完整 Alembic、真实部署、门禁下并发写入、故障恢复 Worker、完整 rollback 消费均仍待验收。不能因为 incremental 成功或 Python Worker 存在就隐藏这些限制。

## 本轮其余逐项核对

- `GET /admin/agent/llm-presets`：会在首次缺 ai_presets 时持锁迁入旧 ai 配置，并为每条返回 declared_capabilities；已有 Core Provider registry 与 Python 同输入不一致，不能只遮蔽 key 后返回旧原型结果。
- `POST /admin/agent/llm-presets`、`PUT /.../{preset_id}`、`DELETE /.../{preset_id}`、`POST /.../{preset_id}/activate`、`POST /.../strategy`、`PUT /.../{preset_id}/capability-overrides`：不仅是文件 CRUD，还同步 active ai 段、校验搜索/上下文能力、持锁配置、全局 provider reasoning continuation 失效；Node main 未找到消费 ai_presets strategy/pool_mode/激活变化的生产模型选择装配。不能只把配置写进未消费文件。
- `POST /.../{preset_id}/test`、`POST /.../{preset_id}/capabilities`、`POST /.../{preset_id}/probe-media`、`POST /.../probe-media-preview`：需要实际 Provider 目的地/协议、探测缓存/快照/完整媒体样本与结果合约；现共享静态快照和模型诊断不等于这些主动探测。真实 LlmPresetEditor/useMultimodalProbe 有调用方，未用固定结果接线。
- `DELETE /data-portability/imports/{job_id}`：先验证任务可删，再删除暂存与快照，物理清理失败 503 保留 DB，最后才 finish_delete；当前已知本地删除原语的父目录 symlink 竞态未解，不绕过它。
- `POST /data-portability/imports/{job_id}/cancel`：只允许 queued，提交 canceled 并清能力，再尽力清 staging；同样不能通过不安全物理删除适配补齐，未仅迁移状态分支宣告完整。
- `POST /admin/services/{name}/restart`：白名单 gateway/worker、真实心跳 host/pid/cmdline 防 PID 复用、SIGTERM/等待、systemd 托管或固定 Python 模块 detached 拉起；Node 只有读取服务状态，没有同等部署生命周期管理，不能仅模拟进程状态或去操作真实进程。

本轮没有修改 Python、旧目录、运行配置或其他会话代码；包导出/组合根接入与撤下由主会话处理。未提交、推送、fetch 或触发 CI。
