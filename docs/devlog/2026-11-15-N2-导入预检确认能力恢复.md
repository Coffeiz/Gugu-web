# N2：导入预检确认能力恢复

## 实际范围

接通 `POST /api/v1/data-portability/imports/{job_id}/resume`。前端实际消费者为 `ProfileDataPortabilityPane.vue:resumeImport` 和 `services/api.ts`。Python 基线为 `data_portability.resume_import`、`api_jobs.resume_preflight_import`。

此接口不是恢复文件导入执行器：它只允许当前 owner 尚有效的 preflight/preview_ready 任务恢复确认能力。需已存在 staging_key、非空 preview 及未过期 expires_at；无任务/越权 404，不满足条件 409。每次产生新的 token_urlsafe(32)，仅持久化 SHA-256 摘要，成功响应带 import_token 和 Cache-Control:no-store，普通读取不带 token。

Core `packages/core/src/data-portability/resume-import.ts` 复用现有 transaction 与任务读取；Host `modules/data-portability/resume-import.ts` 处理认证、UUID、HTTP 与 no-store。主会话注入 Node randomBytes(32)/base64url 和 SHA-256；不引入 envelope 密钥，不读取、解密、重写或删除已有暂存归档。

## TDD 与真实消费者

先新增 `tests/portability/resume-import.test.ts`，在 devserver 实际因目标 Core 模块不存在失败；实现后 Core/Host 同组 2/2 通过。使用真实 DataImportJob/DataExportJob metadata 创建 PostgreSQL 模型表，保护 owner、状态/mode、空 staging、空 preview、缺失/过期时间、UTC 微秒及内部能力字段不外泄。

并发恢复令牌均不同，数据库最终摘要仅对应最后一个有效令牌，与 Python 行锁轮换语义一致；注入数据库失败后验证旧摘要保持。取锁后按实时数据库时钟检查有效期。

同一数据库上实际调用 Python `apply_import_job`：旧 token 返回 403，新 token 通过 hmac 比较后变为 incremental/queued 并清空 import_token_hash。暂存 key 保持不变；没有启动 Worker 或执行文件导入。证明恢复能力能被既有后续消费者使用，而非写入无人消费的新队列。

Python 原 `test_data_portability_api_jobs.py` 串行 3/3，保护 apply token 消费及幂等重试等；新增 `compat/tests/test_data_import_resume.py` 1/1，直接执行原 Python handler，验证令牌轮换、摘要、no-store、owner 和过期语义。未修改 Python 参考后端。
