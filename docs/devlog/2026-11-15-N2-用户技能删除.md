# N2 用户技能删除

## 行为与依赖

`DELETE /api/v1/skills/{skill_id}` 以 `backend/app/api/v1/user_skills.py:delete_skill` 和 `backend/agent/capabilities/skill_registry.py:delete_user_skill` 为基线。只删除当前 owner 对应 skill_id，缺失与跨用户均返回 404，成功提交后发布 skills 变更事件，HTTP 返回 204 空响应。Python 的 `events.publish` 对 Redis 计数和发布故障采用 best-effort；skills 不进入上下文版本及 RAG 索引来源。默认 operation 为 refresh。

Core 新增 `agent/skills/user-delete.ts`，复用 Kysely、可信 owner 校验和统一 CoreError；Host `modules/skills/user-delete.ts` 只负责认证上下文与 HTTP。

## 消费者与限制

生产 RedisEventPublisher 可以发布 resource=skills、operation=refresh；Node Live SSE 同时允许该资源与操作，前端 resourceRefreshEvents 将其转换为 skills-changed，SkillsHome 监听后重载。消费者存在，但 Node GET skills 默认还需要内置工具 metadata 与 MCP 工具发现；当前 Node 未接该列表，不能声称完整技能目录已可用。create/update 同样存在此依赖，不扩展共享领域实现。

初始 PostgreSQL 合同使用精简表。随后生产 `startServer` 集成显式提供独立 Redis 和测试 Python，从 Python 实际 UserSkill metadata 编译 PostgreSQL CREATE TABLE，在随机 schema 建表，验证真实用户认证、删除204空响应、数据库重读、重复404及真实 Redis subscriber 收到 skills/refresh/resource.changed 与递增 revision。该集成 1/1，通过时三个测试环境变量均显式提供；未配置 Redis 时该文件只执行其他 API，不应计为技能通知验收。实际模型 owner_id 为 UUID、skill_id 为 varchar(16)，具有 owner+skill_id 唯一约束。此验证使用实际表定义，但没有执行完整 Alembic 升级历史；正式 SQLite、完整生产部署和完整技能页面仍未验收。
