# N2：管理员兼容封禁开关

## 范围与真实调用链

接通 `PATCH /api/v1/admin/users/{user_id}/ban`，消费者为现有 Admin/Users 页面 toggleBan。Python 基线为 `users_admin.toggle_ban`、`security/account_status.suspend_user/unsuspend_user` 和 `audit_log.write_log`。

Core `packages/core/src/admin/user-ban.ts`：按当前 is_active 决定封禁或解封；封禁为 suspended、固定 30 天、reason=admin_ban_compat；解封清截止时间和原因；每次安全版本加一。事务提交后发布已有 auth.state.changed，再单独提交 user 审计，保留 Python 实际两个提交的顺序。审计失败向上返回错误，但不恢复已提交账户或旧安全版本；状态事务失败则不通知、不审计。

Host `modules/admin/user-ban.ts` 只做 Admin guard、操作者与请求 IP 元数据。主会话接入真实生产组合根、package 导出与既有 Redis auth publisher。检查确认没有同名目标模块，旧 `domains/admin/admin-users.ts` 有其他会话未提交修改，完全未触碰。

## 明确差异和边界

Python 原 toggle 读取无锁，Node 为当前用户行加锁，两个并发 toggle 不丢安全版本，分别完成封禁与解封。这是有意加强的并发语义，不声称 Python 原实现已具备该保证。

Python write_log 对 X-Forwarded-For 首段 strip 后不截断，而正式列是 varchar60；超长头可在封禁提交后导致审计失败。Node 入口与现有其他管理员审计一样将 IP 限为 60 字符，避免此类意外失败，作为明确的稳定性差异记录。真实审计数据库失败的两次提交语义仍按 Python 保留。

已接生产身份消费者与 SSE，不涉及文件、Worker、Docker、付费 Provider；正式 SQLite 和部署未验收。Python 参考后端、用户配置、其他会话修改均保留，没有提交或推送。
