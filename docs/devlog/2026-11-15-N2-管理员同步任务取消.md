# N2：管理员文件同步任务取消

## 范围与基线

接通 `POST /api/v1/admin/filesync/runs/{run_id}/cancel`，由现有 FileSyncAdminPanel 的 cancelRun 调用。Python 基线为 `filesync_admin.cancel_run`、`jobs.request_run_cancel`；后续真实消费者为 `jobs.cancellation_requested`、`finish_run` 及 runner 的取消检测。

Core `packages/core/src/filesync/cancel-run.ts` 与旧 Worker 共享 PostgreSQL 行锁：queued 立即变 cancelled、设置 stage/finished_at 并增加 revision；running 只变 cancelling、设置 cancel_requested 并增加 revision，等待 Worker 收尾。其他状态包括 cancelling 和终态保持不变，重复请求仍按 Python 发布相同修订的失效通知。管理员可合法处理跨 owner 任务，但普通用户不能进入此路由。

事务内复用现有快照 reader 返回同次事务状态；提交成功后才发布 `events:filesync-admin` 的 canonical filesync.run.changed。通知失败不回滚取消请求；事务失败不发布。Host `modules/filesync/admin-run-cancel.ts` 负责 Admin guard、UUID 和 HTTP；同业务读路由的现有 UUID 校验仅做最小导出复用，没有迁移或依赖旧 domains 转发。

## 生产链路

在真实 startServer、Admin 登录、随机 PG schema/隔离 Redis 下，创建 synthetic queued 任务、建立实际 HTTP SSE，再执行取消 API：收到匹配 run_id/binding_id/revision 的失效事件，字段经过现有 Core codec，不泄露路径或 owner。重复取消修订不再增加；running 取消由同库真实 Python 消费者收尾。独立无 Redis Host 真实登录后取消仍持久化成功，符合 Python best-effort 通知语义。

不操作真实文件，不启动扫描 Worker，不声称 Node watcher、全部同步状态/修复领域、正式 SQLite 或部署完成。没有覆盖其他会话修改、没有提交或推送。

最终核对九份关键源码、测试、package 和 app/main/Redis adapter 本地与 devserver SHA-256 一致、无活动构建后串行 Core build 通过。最新 Node 合批 5/5（取消 2、读取回归 2、真实生产 1），原 Python 1/1；生产覆盖真实 Redis/SSE、无 Redis 及 Python 后续消费者。没有使用过期 dist 冒充验证。
