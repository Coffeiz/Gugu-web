# N2 管理员通知广播闭环

新增 `POST /api/v1/admin/notifications/broadcast`。Python 基线为 `notifications_admin.broadcast()`、`BroadcastRequest`、`events.broadcast()/publish()`，消费者为用户通知列表/上线 bubble 查询和生产 `/api/v1/live/stream`。此前广播被记录为缺少发布能力；本次复核确认既有 live 消费器订阅 `events:__broadcast__` 及 owner 频道，并接受 `{notification: ...}`，因此可以通过稳定 Redis 适配接通。

Core `notifications/broadcast.ts` 承载双渠道验证、TTL、持久化和提交后 best-effort 发布；Host `modules/notifications/routes/broadcast.ts` 只处理管理员认证、DTO 和 400/422 映射。稳定 Redis 发布适配由主会话在 `adapters/redis-events.ts` 最小增量集成，不借用 Agent 取消的业务命名或旧 Node 转发。

标题和内容不能同时为空，bubble/persist 至少一个开启；所有通知均先写权威记录（包括只气泡），再发布实时 envelope，投递失败不撤销已提交记录。无 Redis 也保留持久化，用户可通过现有列表/上线补弹读取。TTL 仅在 bubble=true 且小时数非零时生效；原样保留负小时过期语义。响应和实时通知保留 id、title、content、color、bubble、persist。

## 验证

- devserver 先执行 Node 合同，明确缺少目标 Core 模块而失败，随后正式 `tablesSql('postgres').siteNotifications` 创建的隔离表回归转绿，覆盖提交后发布、无效输入无写入、TTL、渠道及投递失败不回滚。
- Python 可复跑 `compat/tests/test_notification_broadcast.py` 直接 handler 对照 1/1，验证持久化、渠道、TTL 和 400 错误。未修改 Python 参考后端。
- 生产集成实际启动两个 Host：隔离 PG+Redis 下真实管理员登录、HTTP SSE 流收到全局和定向通知、用户侧 bubble 权威读取和跨 owner 限定、仅气泡不进列表；另一无 Redis Host 仍成功持久化。初始整体 2/2 通过，正常退出。
- 后续补充 Python DTO 兼容断言：bubble/persist 布尔字符串、TTL 整数浮点字符串 `2.0`；Node 新断言先以 422 而非 200 失败，再修复 Host 解析。Python DTO 对照通过。最终规则合同与完整生产闭环合计 2/2 通过、无跳过、正常退出；曾遇并行配额状态的新导出尚未构建导致入口加载失败，待对应构建完成后复跑通过，未删除或放宽断言。
- 本地与 devserver 的两份实现、两份 Node 测试 SHA-256 一致；构建前确认没有并发 Core build。

## 有意差异与边界

Python 当前 `_channel(user_id)` 直接字符串拼接，没有 UUID 校验。Node 采用明确的安全边界：非 all 目标只有成功解析的 UUID 才投递，并规范化 Redis owner 频道；非法 target 仍按 Python 原请求保存，但不向任意 Redis 频道投递。DB target 不擅自规范化，因此紧凑 UUID 目标的历史上线补弹匹配限制仍保留；不能把该安全差异描述为 Python 已有校验。

PG 通知表使用 Core 正式定义；认证用户/审计表为隔离必要列精简表，不代表完整 Python Alembic schema 已验收。此广播写入路径未验证正式 SQLite；Worker、实际部署和跨进程失效仍未验收。SSE 与广播的实际 Redis 消费已在隔离环境验证，不把仅发布无人消费消息当成完成。未连接真实用户数据、付费 Provider 或 Docker，未提交或推送。
