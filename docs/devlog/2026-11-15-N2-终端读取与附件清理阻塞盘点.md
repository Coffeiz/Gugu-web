# N2 终端读取与附件清理阻塞盘点

本记录为代码和既有pytest的只读依赖盘点，没有把未注册路由、固定403或替身通过计为迁移完成。以下能力继续保留未完成；本会话没有为规避依赖新增空接口。

## 终端读取缺少目标平台与权限运行时

涉及 `GET /api/v1/terminals`、`GET /api/v1/terminals/{terminal_id}`，以及同样依赖VIEW/page_access的metrics、改名和重开。

- Python `app/api/v1/terminals.py:get_terminals` 首先调用 `agent/terminal/access.py:page_access`。权限不是简单owner过滤：必须通过真实sandbox readiness、终端入口模式、管理员Shell开关和用户有效Shell权限。列表成功后还执行过期/孤儿清理和最近5个agent终端保留策略，再提交；最终ptyEnabled由真实pty_access决定。
- 详情通过get_terminal限定owner，随后 `authorize_operation(VIEW)` 校验关联session并调用同一page_access。不能因为表查询简单就省略平台和权限边界。
- 旧page_access直接依赖Docker sandbox_readiness。2.0已明确退出Linux Docker执行后端，不能照搬该实现。现有 `packages/sandbox/src/platform.ts:mxcDiagnostics` 对非Windows明确supported=false；Windows也需真实SDK隔离探测，不能据此推导Linux/NAS已经有可用MXC多用户终端。
- Web Host当前只有终端持久视图删除切片，没有共享终端page_access/PTY可信状态注入；部分workspace/Agent Host装配仍明确禁用Shell readiness。不能用假true放开边界，也不能注册固定403后标已完成。
- 前端terminalApi及终端页确有列表/详情消费者。阻塞是后端目标平台和权限运行时，不是缺前端按钮。终端删除已完成仅代表持久视图清理，不终止PTY，不能替代此项。

需要交接的具体能力：目标平台可信readiness/PTY能力、管理员与用户有效Shell权限、会话授权及终端持久状态组合；同时保留列表清理/保留策略和真实消费者验收。未在本任务中扩展整块终端运行时迁移。

## 附件删除必须与复用共享引用锁和安全物理生命周期

涉及 `DELETE /api/v1/agent/attachment/{attach_id}`、`DELETE /api/v1/agent/attachments` 及依赖同一清理能力的会话删除。

### 单草稿删除

`app/services/chat_attachments.py:delete_draft_attachment` 先owner限定取storage_key，再以owner/attach_id/state=draft条件删除；未命中返回404，已被发送claim返回409。只有DB commit成功后才调用 `chat_attach/records.py:try_delete_storage_if_unreferenced` 清理字节。必须保护发送/清理竞争，不可先删FS再提交DB。

### PostgreSQL复用与物理清理的同一锁协议

`chat_attach/records.py:_lock_storage_key` 在PostgreSQL执行 `pg_advisory_xact_lock(hashtextextended(:lock_key, 0))`，lock_key为 `chat-attachment:<owner>:<storage_key>`。`reuse_attachment` 在锁定源行后取得这把锁、确认物理对象存在，再创建共享引用；`try_delete_storage_if_unreferenced` 也取得同一把锁，检查同owner是否仍有任何存活chat_attachments引用，持锁完成物理清理后提交。

这不是可用一次SELECT count和普通unlink代替的查询：如果复用方不遵守相同锁协议，检查后可出现新引用并被误删。当前Node没有这组附件复用/清理共享锁调用链；Core通用操作收据锁、文件回收站锁使用不同key，不能当成已经兼容此协议。已有Node claim/read适配也不等于共享字节复用和删除已接通。

`packages/fs` 已提供只读打开和部分暂存原语；它们没有补齐附件引用生命周期、崩溃恢复或并发路径替换验收。不能因为只读下载已通过，直接扩大声明为安全删除可用。

### 批量清除还有Redis legacy路径

`chat_attach/records.py:clear_staged` 收集同owner draft记录并对storage_key去重，条件删除draft后提交，再逐个走未引用字节清理。返回数量按成功进入字节清理的不同storage_key及legacy键计，不是DB删除行数。

随后还扫描 `chatfile:<owner>:*` 的旧Redis元数据，读取元数据、处理物理对象并删除legacy键。Node目前只迁移了DB优先/legacy读取的下载路径，没有这组owner限定扫描、清理和失败计数语义。旧Python legacy分支会直接delete元数据storage_key，不能据此绕开Node应有的owner路径和共享引用安全边界。

### 会话删除还包含其他副作用

`conversation_cleanup.py:remove_session_with_attachments` 在DB事务里先关闭关联agent终端、删除消息附件ownership及消息，再删会话；提交后统一清理共享字节，随后清理反思缓冲。只删conversation_sessions或依靠外键级联不等价。

既有回归证据入口包括 `test_chat_attachments_ownership.py` 中draft/attached守卫、owner隔离、共享storage_key、存储失败不回滚DB和DB失败不删物理对象；以及反思缓冲生命周期用例。这些必须随完整清理用例迁移，不能用简化表或仅DB删除测试替代。
