# N2 飞书设备授权连接

## API 与生产边界

- `POST /api/v1/me/feishu/connect`，执行 init/begin，返回扫码地址和随机 poll_id。
- `GET /api/v1/me/feishu/connect/{poll_id}`，轮询设备授权；成功时加密 upsert Bot、绑定 owner open_id、写入 reach 缓存和通知。

Python 基线为 `backend/app/api/v1/feishu_connect.py` 的 start/poll/_post，以及正式 `UserBot` 模型默认值、`scheduled_tasks.save_imreach/get_imreach`。前端通过真实飞书连接服务使用这两个接口。

Core `im/feishu-connect.ts` 承担业务及协议状态；Host `modules/im/feishu-connect.ts` 承担认证、HTTP、安全 transport 与生命周期。生产目标固定 `https://accounts.feishu.cn`，与 Python 一致；没有新增门户环境变量，没有自动放宽本地目标。合成 TLS 门户只通过测试显式依赖注入提供。

## 行为和最小复用

- init 必须支持 client_secret；begin 使用 PersonalAgent/client_secret/request_user_info=open_id。device_code 仅存服务器 Redis 的 `feishuconnect:<poll_id>`，TTL 3600 秒。
- owner 不符 403 且不请求上游；缺挑战/expired_token/invalid_grant 返回 expired，access_denied 返回拒绝，authorization_pending/slow_down 等继续 waiting。轮询 HTTP 400 JSON 是合法设备流响应，不误当连接异常。
- 同 owner/client_id 更新密钥并启用，不重复创建；不同应用可以独立创建，不能套 QQ 单 Bot 限制。
- 保留 Python 两阶段提交：先提交凭据，再提交 owner 平台 ID/绑定时间。第二阶段失败时第一阶段已经提交，挑战仍保留、不发送快照通知，不能宣称全量回滚。
- owner open_id 从 user_info.open_id 或顶层 open_id 读取；正式表中的 owner 字段写入后，按 Python 顺序 best-effort 写 reach，再失效当前 owner IM 快照/通知，最后清挑战。
- reach 内容严格保留 platform/channel_id/chat_id/puid/context_token；按平台键与最近键都使用 90 天 TTL。Python `get_imreach` 实际读取了 Node 写入值，不是孤立队列或无消费者状态。
- 直接泛化已有 QQ 插入默认值为 `insertUserBot`；QQ wrapper 继续保留原 strip/default 行为，既有手动创建和扫码回归均保留。Redis writer 仅追加该 API 直接需要的两键写入，未整理其他共享代码。

主动安全差异：未配置 Redis 时认证后 fail-fast 503；NX 避免挑战碰撞覆盖；owner 行锁序列化 Node upsert；两 reach 键通过一次 Lua 原子写入；拒绝凭据型/非 HTTPS 扫码地址；上游/Redis 异常脱敏、不跟随重定向。原始异常和凭据不回显。
