# Node 公网 IPv4 被映射 IPv6 规则误拒

## 结果和根因

微信固定官方目标的完整隔离生产链已通过。此前错误被归因为 DNS 返回非公网，实际系统解析器和两个显式公共解析器都返回公网 A 记录；误拒发生在共享 Node 出口的地址分类函数，不需要修改系统 DNS 或主机代理配置。

`node:net` 的同一个 BlockList 同时保存 IPv4 和 IPv6 网段时，IPv6 `::ffff:0:0/96` 也会匹配原生 IPv4：只加入这条规则，`check('1.1.1.1','ipv4')` 就为 true。原有分类器因此拒绝所有正常公网 IPv4，导致 CONNECT 隧道和 HTTP 请求都没有发出。

最小修复位于 `packages/core/src/agent/providers/transport/network.ts`：拆分两个地址族的 BlockList，不更改任何网段表。按照既有运行边界和本次明确要求，所有 IPv4-mapped IPv6（含映射公网）继续拒绝；正常原生公网 IPv4 恢复通过，私有/保留地址、混合公私 DNS、URL 凭据、查询密钥、重定向、TLS 和 SNI 检查保留。

## 先失败后通过

只在 devserver 执行测试。`packages/core/tests/agent/providers/transport.test.ts` 先增加行为断言，正常公网 IPv4 三项及纯公网 DNS 固定一项共四项失败；私有与保留映射地址断言通过。实现最小修复后完整传输回归 37/37，覆盖原有超时、连接池、取消、代理 CONNECT、CA、TLS 域名/SNI、重定向、分片与解压等场景；没有放宽既有断言。

构建前网络、微信、导出预览和组合根共 14 项本地/devserver SHA-256 一致，确认无活动构建后串行 Core build 通过。生产合批 2/2：微信固定目标的完整扫码路径，以及其他切片的只读导出预览。微信原完整断言没有改为预期 502，而是修复根因后恢复到正常回归文件 `tests/host/wechat-connect-tls-main.integration.test.ts`，元数据同步登记。

微信测试仅使用临时配置、随机 PostgreSQL schema、隔离 Redis、临时 CA 和合成 TLS 服务。请求保留官方域名、真实安全传输及 Host/SNI 校验，经测试配置的隔离 CONNECT 代理转到合成服务；代理从不连接 CONNECT 原始目标，没有调用官方业务接口。真实 SSE 刷新及 Python gateway 的加密凭据读取已经验证，正式微信授权、消息收发、SQLite 和部署未验收。
