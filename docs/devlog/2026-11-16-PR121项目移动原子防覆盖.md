# PR #121 项目移动原子防覆盖

审查指出：`findAvailableKey()` 和 `move()` 的目标 `lstat` 都只是预检查；在检查后创建同名目标，POSIX `rename()` 仍可能覆盖目标。rollback 复用同一移动实现，也有同样的数据丢失风险。

## 修改与调用链

- Host 的 `project-path-move.ts` 用 `link(source, target)` 原子占用缺失目标，成功并重新核对路径和文件身份后才 `unlink(source)`。目标存在返回带 `EEXIST` 的安全错误；不支持硬链接、跨文件系统等失败明确拒绝，不回退到 rename，也不删除目标来重试。
- 项目回收站、恢复、各自 rollback 和 Undo journal 本地恢复共用该端口；保留既有 owner 根、路径及 symlink/junction 拒绝检查。普通缺源仍保留原兼容行为，Python 参考实现未修改。
- 安全移动错误继承 `ProjectTrashStoragePathError`，穿过 Host 和 Core 的旧 Python 兼容 catch。项目删除/恢复冲突会中止数据库事务；补偿目标已被占时保留两边文件并报告 busy。Undo/redo 同样让错误穿过状态机，业务行与操作终态一起回滚。
- Node 当前没有可用的目录原子不覆盖移动原语。实际存在的目录明确返回 `ENOTSUP`，包括项目改名、反向补偿及 journal 恢复；不发出“已经移动”信号。源目录缺失时仍按原行为返回。错误对象提供诊断代码，现有统一 HTTP 错误层对这类服务错误保留通用 500 脱敏响应；目标文件冲突是 409。
- journal 在移动前记录路径；冲突或源/目标同时存在时，恢复事务回滚并保留日志。link 成功而 unlink 前崩溃可能留下两个硬链接，此时不猜测终态、不自动删除任一边。它保证目标占用不覆盖，并非整次移动、数据库与文件系统组成单一原子事务。

目录拒绝是本次安全要求带来的明确功能限制。原 PG 改名成功用例改为显式内存目录端口，继续保护数据库路径、版本、锁和未知提交恢复的协调合同；不能据此宣称 Local 目录支持或真实文件移动通过。生产组合根用例改为先验证目录改名被拒绝、原文件保留，再验证无路径变化的元数据更新和删除/恢复。未删除相关数据库断言。

## 确定性回归与实际验证

新增回归使用 `beforeMove` 在预检查后以排他写入创建目标，不依赖调度或 sleep。删除和恢复的正向竞态、各自 rollback 目标冲突均验证双方内容；真实临时 SQLite 合同继续验证删除/恢复及 Undo/redo 冲突后项目、文件、版本、操作终态和事件不被提交。journal 用合成 SQL 端口和真实临时文件验证 active/undone 两种恢复方向、双硬链接崩溃状态和目录拒绝，断言回滚及日志保留；该层不算 PG 验收。
