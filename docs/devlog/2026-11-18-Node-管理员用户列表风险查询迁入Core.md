# Node 管理员用户列表与风险查询迁入 Core

## 范围

迁移旧 Python 的两个只读管理员入口：

- `GET /api/v1/admin/users/`
- `GET /api/v1/admin/users/risk`

Fastify 继续负责 Admin guard、查询 DTO 和通用 HTTP 错误映射。HTTP 路由位于 `apps/web-host/src/modules/admin/users.ts`；Core reader 负责 Kysely 查询、搜索/窗口、用量与风险聚合、字段投影。`main.ts` 将 Core PostgreSQL DB 接入 Host。

## Python 行为基线

对照 `backend/app/api/v1/users_admin.py`、`backend/app/services/storage/quota_ledger.py` 与 `backend/tests/platform/admin/test_admin_risk_users.py`：用户列表按创建时间倒序，`q` 对用户名/邮箱不区分大小写；周用量从周一 UTC 零点计算，6 小时窗口按 UTC 的 00/06/12/18 边界重置，并排除 BYOK。文件记录用量包含回收站；Local `file_library` 账本值覆盖文件记录汇总。

风险列表把用户可见窗口与最近五分钟动作策略分开计算，满足 `account_status != active` 的用户即使没有可见事件也保留；计数 `>=10` 为 `suspended`、`>=5` 为 `throttled`，否则为 `logged`。Python User 模型有 `updated_at`，因此按 `updated_at` 倒序。本切片修正旧 Node Host 按 `created_at` 排序的差异。

Python 风险 pytest 源码已阅读；本地 Python 没有 pytest 模块，devserver SSH 在此前探测中超时，因此本轮没有 Python 实跑。旧风险测试只覆盖冻结账户保留、展示窗口事件和策略阈值；没有直接的 Python 用户列表 API 测试。

## TDD 与验证

新增 Core 行为测试先因缺少 `admin/users` reader 导出失败；实现首轮后，SQLite 查询又暴露两个实际问题：聚合表达式被 Kysely 解释成列名、SQLite 不接受 `Date` bind 参数。修正表达式及 UTC 字符串参数后，Core SQLite 行为 **2/2** 通过，覆盖用户搜索/窗口用量/文件账本优先级、BYOK 排除、冻结用户保留、展示与策略窗口以及 `updated_at` 排序。

Host/Admin 和实际入口回归 **38/38** 通过，含认证前不访问 reader、查询错误脱敏、参数上限、随机 PostgreSQL schema reader 测试，以及实际 `startServer` 登录后用户列表与风险列表请求。Core build 和 Web Host `tsconfig.build.json --noEmit` 通过。

Core 默认 Vitest 启动时受到当前共享 `tests/suites.json` 与发现文件不一致的影响；本轮登记了本测试文件，并使用仅选本切片的临时 Vitest config 运行。临时 config 已清理。临时 SQLite 测试使用本切片精简 schema，不代表正式 Core SQLite 用户 schema 已接通。
