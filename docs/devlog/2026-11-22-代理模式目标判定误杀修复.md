# 代理模式下的目标判定误杀修复

## 现象

桌面端在本地代理环境下请求部分模型 API 时，会在 1 毫秒内被本地判定层拒绝（`input_rejected`），请求完全没有出网；同一份配置下另一些域名却正常。表现是"时好时坏"，取决于应答落在哪一段地址。

## 根因

三层叠加：

1. 本地 DNS 被代理接管后只返回合成地址（Fake IP 段）。
2. 桌面端为了拿到"真实"地址，会改用活动物理网卡的 DHCP DNS 二次解析。该 DNS 的应答可能已被污染，返回的不是目标站点的真实地址。
3. 代理模式的判定规则是"任一解析结果不是公网地址即整体拒绝"。污染应答里的 IPv6 地址落在 IPv6 特殊用途段内，被判成非公网，整个目标随之被拒。

第 3 条是真正的错误。代理端才是权威解析方，本地结果只应作尽力而为的私网提示；而污染地址与真实私网地址在语法上无法区分，用"非公网"当拒绝依据，就会把真实公网域名误杀。同一台机器上有的域名恰好拿到未被污染的应答、有的恰好拿到被污染的，所以失败呈间歇性。

## 改动

- `packages/core/src/agent/providers/transport/network.ts`
  - 新增 `isPrivateAddress`：只覆盖明确的私网、回环、链路本地、CGNAT、IPv6 ULA 与组播，**不含**合成地址段，也不含 IPv6 特殊用途段。代理模式改用它作为拒绝依据。
  - 代理模式下本地解析失败保持 fail-closed（见下方"已知限制"）。
  - 主机名守卫补无点单标签主机名，并把后缀集合收窄到真正指向内网的保留名（`localhost`、`.localhost`、`.local`、`.internal`、`.home.arpa`）。
- `packages/core/src/agent/providers/transport/node.ts`
  - 代理模式的本地解析超时收紧到 2 秒，不占用连接级超时预算。

## 一个被实测推翻的方案

起初把 RFC 2606 的 `.test`、`.example`、`.invalid` 一并纳入主机名守卫，结果仓库测试基础设施使用的假域名恰好落在 `.example` 段上，导致一批既有用例全部失败。

除了撞上测试基础设施，这几个后缀本来就没有防护价值：它们解析不到内网，"非公网"理由不成立，而真正可能指向内网的形态（mDNS、云内网、家庭网段、localhost、无点单标签）都已在名单内。因此最终只保留有实际拦截语义的那一组。

## 验证

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 代理 + 本地应答为污染地址（IPv4 第三方段 + IPv6 特殊用途段） | 放行 | 放行，请求到达目标 |
| 代理 + 本地应答为私网地址 | 拒绝 | 拒绝 |
| 代理 + 字面私网、回环、元数据地址 | 拒绝 | 拒绝 |
| 代理 + 本机主机名、无点单标签主机名 | 拒绝 | 拒绝 |
| 代理 + 本地解析失败 | 放行 | 放行 |
| 直连 + 合成地址目标 | 拒绝 | 拒绝 |

端到端用桌面端真实装配加本地代理复验：此前被本地拒绝的目标域名恢复正常响应（上游返回业务错误码而非判定错误），内网类目标仍在 1 毫秒内被拒。

## 已知限制

代理模式下本地解析失败仍会阻断请求。曾考虑改成 fail-open——代理解析才是权威解析方——但 Web Host 侧以代理侧 DoH 作为**唯一**判定来源，那里放行会让这条边界失效，属于安全倒退，因此保持 fail-closed。

代价是"目标域名只能由代理端解析"的场景（split-horizon DNS、企业代理专属域名）暂时连不上。要同时兼顾，需要把"本地解析结果是否权威"显式建模成独立选项，而不是复用代理模式的布尔开关；这属于独立改动，尚未实施。

## 打包版实测：本地 DNS 抖动打掉整条请求

换一个构建版复跑时仍连不上，错误形态与上文不同：`providerErrorCode=network`、`transportHop=dns`，而且同一时刻 QQ、微信、Anthropic 三个互不相关的上游同时失败。这是环境层 DNS 故障，不是某个 provider 的配置问题——本机当时路由器 DNS 出现瞬时无响应。

问题在于代码把"本地解析失败"等同于"目标非法"：桌面端为拿到真实地址会二次查询活动物理网卡的 DHCP DNS，这一次抖动就让模型请求全线失败并重试到耗尽，错误信息也完全看不出真实原因。

修法是把"本地解析结果是否权威"显式建模：

- `resolvePinnedTarget` 增加 `localResolution`（`advisory` / `authoritative`）。走代理默认 `advisory`——代理解析才是权威解析方，本地解析失败没有信息量，不该阻断请求；直连默认 `authoritative`——本地解析是唯一来源，失败必须拒绝。
- 桌面端二次解析失败或仍返回合成地址时回落到系统结果，由上层按当前模式判断，不再把整条请求打掉。
- Web Host 以代理侧 DoH 作唯一私网判定来源，显式声明 `authoritative`，边界保持 fail-closed。

验证：代理模式 + 本地解析抛错时目标域名恢复正常响应；权威模式与直连模式仍然拒绝；内网类目标仍在一毫秒内被拒。

## 残余风险

代理模式下，"公网域名指向私网地址"只能靠本地解析尽力发现；本地解析失败或返回污染地址时会漏过，需要代理侧规则与用户配置兜底。Web Host 侧走代理侧 DoH 解析并固定公网 IP，不受这条影响。

## 与上游的对照

MiniMax Code 开源实现里没有任何 fake-IP 专门处理：主体路径用进程级 CONNECT 隧道把域名交给代理解析，从不本地解析；只有必须本地解析的两条窄路才做公网判定，并把合成地址段当作非公网直接拒绝。我们保留本地解析是为了拦"公网域名指向私网"，因此判据应当是"明确指向私网"，而不是"不是公网"。

## 教训

往主机名守卫这类"名字级"规则里加后缀之前，先确认仓库测试基础设施用的假域名是什么形态；规则既要有实际拦截语义，也不能和仓库内的合成域名冲突。
