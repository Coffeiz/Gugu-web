# 子代理等待期会话被占用：发消息只能排队

## 现象

桌面端让咕咕派子代理做检索后，会话一直显示「运行中」。这段时间里用户再发消息，
不会立刻得到回复，而是进待发队列排队，必须等子代理跑完这一轮才能继续对话。

## 定位过程

先看本机运行记录的时间线，确认不是模型卡住：

- 16:44 父运行派子代理，父运行状态转为等待子代理；
- 16:46 用户以为卡住，手动点了取消（这一步是误操作，不是缺陷本身）；
- 16:46 之后用户发出的新消息，落在待发队列里，直到 16:49 子代理交付才被消费。

再用仓库真实的准入与运行存储写探针复现：

1. 父运行提交为等待状态；
2. 会话表里 `active_run_id` 仍指向父运行，`execution_state` 仍是 running；
3. 等待期间发消息被判为「会话已有运行中的任务」，只能进待发队列；
4. 父运行进入终态后，会话执行位才被清空，新消息这才准入成功。

## 根因

三层叠加，核心是「会话执行位」的语义没对齐：

1. `packages/core/src/agent/run/sqlite-store.ts` 只在运行进入终态时清会话执行位。
   等待子代理不是终态，于是会话一直被父运行独占。
2. `packages/core/src/agent/run/sqlite-admission.ts` 用「是否终态」判断会话是否被占用，
   等待态同样被算作占用，新消息直接被拒。
3. 界面完全看不到等待态：事件协议里没有等待态的展示映射，
   等待中的父运行和真正在跑的运行长得一模一样，用户只能理解为卡死。

对照 `apps/web-host/src/modules/agent/run/lease.ts`，Web 侧的租约语义本来就是
「获取租约即占有会话，释放租约即归还会话执行位」，SQLite 侧是移植缺口。

## 修复

按「会话状态只跟随主 Agent 的运行」的原则，对齐 Web 侧语义：

- **租约端口**：获取租约时占有会话，释放时同事务归还会话执行位。
  接管要求会话严格空闲（归属为空或已属于本运行），否则整体回滚，
  避免抢走刚被准入但还没开始执行的新运行。
- **归还不是一刀切**：仍在执行中的运行保留会话归属。崩溃残留的孤儿运行
  要靠这个归属被恢复流程找到并结算，只有等待态和终态才归还。
- **会话当前运行**：按 Web 侧 `currentRunId` 的回退规则，
  没有在执行的运行时回退到最新的等待态运行，界面仍能读到等待子代理那一轮的输出。
- **恢复索引**：纳入等待态运行，重启后这类运行仍有恢复入口。
- **取消判定**：改为「运行未终态」，等待中的父运行仍可被用户点停。
- **桌面端唤醒**：按父运行自身的准入行定位（会话当前持有者可能已是用户的新消息），
  会话被占用时退避重试而不是一次性尝试后永久搁置。

## 验证

- 新增 `packages/core/tests/agent/run/sqlite-session-ownership.test.ts`：
  等待期可继续发言、执行中的孤儿运行保留归属、租约接管失败整体回滚。
  双向验证：把归还行为改回修复前状态，用例转红；砍掉孤儿保留条件，另一条用例转红。
- `packages/core` 相关套件：27 个文件通过，1 个用例超时。
  该超时用例在 HEAD 基线上同样超时，属存量失败。
- `apps/desktop` 端到端用例：17 条全部通过。
- 桌面端全量：3 个文件 4 条失败，回退到 HEAD 基线后同样失败，属存量失败。
- 两个包 typecheck 均无错误。

## 遗留

- 界面仍把等待态映射成运行中，用户看不出「在等子代理」。
  本轮先修会话占用，界面态需要单独一轮处理。
