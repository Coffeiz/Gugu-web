# 桌面邮件确认与 IPC 帧上限

## 故障与定位

桌面 Agent 调用发送邮件时，曾卡在生成确认提示。重试时，纯文本邮件通过确认后约 4.4 秒完成投递。紧接着确认模板邮件，桌面提示 Core 已停止。该时段日志记录了两次邮件确认和一次成功投递，未发现重复工具调用风暴。

- 确认提示在 SQLite 事务内生成，附件引用查询曾从数据库根实例重新申请连接。事务持有连接并等待查询完成，查询又等待同一连接释放。修复后引用查询复用事务连接，无附件时跳过该查询。
- 模板邮件的两张内置图片原先随请求以 Base64 跨进程传输。合成模板的请求数据约 110 KiB，超过当时的 64 KiB 上限。通用帧编码把超限的宿主请求转成了无对应请求 ID 的错误响应，桌面端将其判为协议失步并关闭 Core 连接。修复后桌面主进程根据主题和配色标识加载内置图片。超过传输预算的邮件在准备阶段返回错误，stdio 层也会直接拒绝超限宿主请求。

## 协议调整

桌面主进程与 Core 通过 stdio 交换逐行 JSON。原单帧上限从 Python Core 迁移时沿用，限制的是 UTF-8 编码后的整帧大小，含末尾换行。

共享帧上限提高到 256 KiB，普通桌面请求也使用这一上限。逐方法参数校验继续生效，已支持分帧的响应合计仍限 4 MiB。模板图片在主进程加载，用户附件继续通过引用读取。

## 验证

- 桌面邮件和 Core 邮件共 14 项测试通过，覆盖事务内附件引用、模板图片和投递回执。测试使用合成账号和模拟投递。
- 独立 Core 回归验证了约 141 KiB 的笔记请求可写入。超过 256 KiB 的请求被拒绝后连接仍可用，合计超过 256 KiB 的笔记列表在重启后可分帧读取。
- 桌面类型检查、Core 构建和桌面构建通过。扩展宿主套件另有 3 项失败，分别涉及项目文件统计、反思恢复和画布便签。修复后的真实 SMTP 投递尚未验证。
