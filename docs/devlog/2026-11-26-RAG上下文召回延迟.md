# RAG 上下文召回延迟

## 运行证据

从同一桌面会话读取 12 条 LoopScope 计时。RAG 中位耗时为 3.75 秒，范围为 1.68–8.98 秒，占样本上下文准备总耗时的 93%。截图中的一轮准备耗时 3,407 毫秒，其中 RAG 3,243.16 毫秒、恢复历史 4.35 毫秒、组装消息 3.84 毫秒。旧桌面 Trace 只暴露了 RAG 总耗时，无法还原该轮具体的向量请求或索引读取耗时。

共享 Core 的旧流程会对有索引文档的查询先请求 embedding，再读取所有向量来源。桌面的 pattern 向量源还可能现场计算行为模式的 embedding。实际的混合排名只重排词法选出的前 50 个候选，没有命中时这些工作全部无效。只剩普通的词法候选时，读取行为模式向量也不会改变结果。

## 改动

共享检索先做词法召回，再按命中候选读取相关向量来源。没有候选或没有版本匹配的候选向量时，直接使用词法结果。其余情况沿用原有向量排序、owner/scope 授权复核和历史水位。LoopScope 的 `assembly.rag_stages_ms` 现在记录索引快照、词法检索、文档向量读取、查询 embedding、排序和授权复核等数值阶段。

## 复现和 A/B

合成语料包含 1,801 条索引文档，查询 embedding 模拟等待 1,600 毫秒，未命中的行为模式向量模拟等待 1,500 毫秒。每组 5 轮，使用同一查询、语料和模拟端口。中位耗时如下，三组召回结果及融合方式的摘要均一致。

| 场景 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 无词法命中 | 3,115 ms | 12 ms |
| 有词法命中、无匹配向量 | 3,117 ms | 9 ms |
| 存在可用候选向量 | 3,119 ms | 1,614 ms |

前两组查询 embedding 调用均从 5 次降到 0 次。第三组保留 5 次查询 embedding。三组的未命中行为模式向量读取均从 5 次降到 0 次。已确认仍有匹配向量时需要等待实际 Provider，真实会话的优化前后耗时需由新 Run 的分项 Trace 测量。

```sh
pnpm --filter @gugu/core build
node packages/core/scripts/bench-rag-retrieval.mjs
pnpm --dir packages/core exec vitest run tests/agent/rag/scoped-search.test.ts tests/agent/rag/context-builder.test.ts
```

对比基线时，用同一脚本运行优化前的 Core 制品，比较输出里的 `medianMs`、请求次数和 `output`。基准和回归使用合成数据，不启动真实数据库或 Provider。

## 第二轮优化：复用 BM25 语料

同一桌面会话后三条 Trace 的索引快照耗时 1.02–4.34 秒、词法阶段耗时 2.45–3.68 秒，均未执行查询 embedding。共享自动召回现在为每个数据库保留最近使用的一个 owner 的 BM25 语料，最多缓存 50,000 条文档。每轮从当前的授权快照核对增删改及消息水位，只重算变化的文档。并发 Run 等待向量时使用各自已经复制的语料统计。

用 22,000 条合成中文文档，在复用前后的同一共享检索路径上对照。各方案使用 1 次冷启动、5 次稳定语料查询和 5 次每轮新增、删除各一条的查询。11 轮的召回结果、顺序、分数和融合方式逐轮一致。

| 场景 | 词法阶段优化前 | 词法阶段优化后 | 合成召回总耗时优化前 | 合成召回总耗时优化后 |
| --- | ---: | ---: | ---: | ---: |
| 稳定语料（中位数） | 1,409 ms | 68 ms | 1,461 ms | 165 ms |
| 每轮增删（中位数） | 1,508 ms | 83 ms | 1,556 ms | 152 ms |

冷启动仍需建立索引。本次 A/B 使用模拟快照，仍保留真实路径每轮从持久索引读取授权快照的行为。真实会话中快照阶段的耗时不计入此次优化收益。

```sh
pnpm --dir apps/web-host exec tsx ../../packages/core/scripts/bench-rag-corpus.mjs
```

## 第三轮优化：SQLite 快照版本与元数据更新

SQLite 迁移 `0051_rag_snapshot_generation` 为每个 owner 记录索引变更代数。触发器与索引写入同事务推进代数，覆盖正文更新、范围改变、逻辑删除和物理删除。热查询用代数验证本机内存快照，开始、结束代数一致才缓存一次重新读取的快照。查询仍按当前权限和消息水位过滤。共享 BM25 使用排序正文判断是否重做分词，展示字段与时间戳继续更新。

临时 SQLite 数据库包含 22,000 条有效文档和 66,000 条删除记录。交替运行全量读取与快照复用各五轮，比较完整快照一致。热快照中位数从 469 ms 降至 121 ms。仅更新所有有效文档的展示时间后，词法索引同步耗时 152 ms，复用路径未再次调用文档分词，且命中结果与从头构建一致。快照首次加载和索引代数变化仍会读取完整正文，跨 PostgreSQL 的快照复用与按游标增量暂未接入。

```sh
pnpm --filter @gugu/core build
node packages/core/scripts/bench-rag-sqlite.mjs
```

## 第四轮优化：跳过完全相同的索引写入

持久写入器在事务中读取现有投影，跳过正文、范围、展示字段、元数据和更新时间均相同的活行。墓碑恢复、范围变更和正文更新仍推进水位，队列租约及任务收据照常校验和提交。

临时 SQLite 的 22,000 条有效行与 66,000 条墓碑夹具上，优化后的等价重建耗时 733 ms，修改 0 行，后续快照耗时 227 ms。此前同规模复现的等价重建修改了 22,000 行，耗时 5,930 ms，后续全量快照 2,657 ms。两次测量分轮执行，真实会话和存在实际索引变更的场景未纳入本轮测速。复现入口仍为 `node packages/core/scripts/bench-rag-sqlite.mjs`。

## 桌面 IM 的召回分项

一次桌面 IM Run 的上下文准备、RAG、范围快照和词法阶段分别耗时 12,851、11,562、8,616 和 2,771 ms。该 Run 早于无变化写入优化的验证构建。同一桌面会话的后续八轮词法耗时为 57–208 ms，范围快照耗时为 364–3,199 ms。桌面聊天与 IM 共用自动 RAG 构建器，IM 仍使用自身的实时授权策略。

在已有聚合计时下补充分项，区分授权等待、读取 SQLite 代数、缓存命中复制、全量查询、行投影、缓存存储复制，以及词法语料同步和实际查询。查询计时包含数据库调用的等待及结果传输。临时 SQLite 回归分别验证缓存命中和失效时的分支，真实 IM 新 Trace 尚未验证。
