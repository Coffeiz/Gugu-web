# QQ 群文件投递 40034128 失败：被动回复额度用尽缺少主动降级

> 排查日期：2026-11-29
> 排查环境：本地桌面预览实例、QQ 群实测、合成协议回归
> 排查对象：桌面端 Agent 的 `send_item` 在 QQ 群里的文件投递
> 排查目的：记录同一轮里群文件连续投递时全部失败的根因，以及文字回复正常、文件全挂的原因

---

## 现象

- 同一轮里连续多次 `send_item`（`attach_id` / `url` / `path` 三种入参）时，前几次成功、其后全部返回「文件未能发送」。
- 换一条新的入站消息又能成功若干次，失败位置总落在同一条入站消息的第 6 次及以后。
- 同一轮里的 `view_image` 不受影响，图片读取始终正常。

## 根因

诊断日志显示文件上传阶段全部成功，失败发生在随后的消息投递步骤：

```
gateway.qq_upload_timing   {"elapsedMs":2008, ...}
gateway.qq_file_message_failed {"httpStatus":400,"upstreamCode":40034128}
gateway.qq_file_delivery_result  {"deliveryOutcome":"rejected"}
```

`40034128` 是 QQ 官方的「被动回复时间或者次数超过限制」。携带 `msg_id` 的请求属于被动回复，群聊被动回复有次数上限；额度用尽后，同一入站消息上的后续被动回复一律被拒。

调用链：

1. `apps/desktop/src/main/im/gateway/delivery/attachments.ts`：桌面出站把当前事件 ID 作为 `qqReplyMessageId` 传给 `sendImMedia`，即把文件投递绑定到这条入站消息的被动回复窗口。
2. `packages/gateway/src/runtime/media-delivery.ts`：`prepareQqMedia` 把它写进 `msg_id`，发往 `/v2/groups/{group_openid}/messages`。
3. `packages/gateway/src/platforms/qq/sender.ts`：`media()` 收到 40034128 后直接判失败。

关键差异在于降级口径不一致：同一文件的文字路径 `text()` 使用 `withPassiveFallback`，被判定为被动失效（40034128 / 40034005 / 40034024 / 40034031）时去掉 `msg_id` 改发主动消息；媒体路径没有这道降级。结果是被动额度用尽后群文件永久失败，而同一轮的普通文字回复仍能送达——与现场「文字正常、文件全挂」完全一致。

投递回执侧也能对上：同一条入站事件的记录呈现「先若干条 accepted、其后全部 rejected」，accepted 的条数正好等于被动回复额度。

## 修复

`packages/gateway/src/platforms/qq/sender.ts` 的 `media()` 改用 `withPassiveFallback`：

- 被动失效时去掉 `msg_id` 以主动消息重发一次，复用已上传的 `file_info`，不重复上传。
- 上游 5xx、超时、缺消息 ID 等未知结果仍然不重发，避免盲目重复投递。

`packages/gateway/dist` 随源码入库，因此同步重建了该目录。

## 回归

`apps/web-host/tests/im/gateway/qq/sender.test.ts` 新增用例「QQ群文件被动额度用尽时改发主动消息，服务端失败不盲目重发」：断言被动额度用尽时第二次请求不带 `msg_id`、按主动消息序号投递并成功，服务端 5xx 时只发一次且结果为 unknown。

移除修复后该用例失败（21 通过 / 1 失败），恢复修复后全部通过。

## 验证

- 修复后同一轮 9 次连续群文件投递全部 accepted；同一窗口在修复前第 6 次起必然 rejected。
- `packages/gateway` 类型检查与产物重建通过。

## 边界

- 主动消息同样受平台额度约束（单关系每分钟、每群每日上限）。额度用尽时会返回平台自己的频控码，该码不在被动失效集合内，因此不会重试，这是预期行为。
- 本记录不把「每条入站消息恰好 5 次被动回复」当作协议常量，而是记为现场实测值：被动额度用尽的位置稳定落在同一入站消息的第 6 次投递。
