# 前端交互同步规则

## 目的

统一处理本地即时反馈、服务端提交、失败回滚和多客户端事件，避免页面各自维护一套乐观更新与刷新抑制逻辑。

统一入口为 `frontend/src/interaction/sync/InteractionSync.ts`。业务模块只提供字段如何应用、如何回滚以及实际请求；mutation 身份、客户端身份和意图生命周期由 `InteractionSync` 管理。

## 接入范围

### 必须接入

- 单值开关、单值选择和高频拖拽移动。
- 用户可立即看到结果，且失败时可以恢复到明确旧值的操作。
- 可能被其他浏览器标签页或客户端同时修改的普通业务状态。

典型例子：邮件订阅、时区、默认页面、日历显示方式、Shell 偏好、咕咕显示偏好、文件移动、画布节点移动和日历事件调整。

### 不接入

- 密码、API Key、SMTP 密码等敏感字段。
- 头像上传、文件上传和其他有上传/解析阶段的操作。
- 多字段编辑表单的草稿状态；这类操作在点击“保存”后整体提交。
- 删除账号、清空数据、停用能力等危险操作。
- 纯本地主题、配色和语言切换，除非该状态同时需要服务端跨客户端同步。

这些操作保留表单局部状态、显式保存、确认弹窗或服务端成功后更新本地状态的语义。

## 标准时序

```text
捕获旧值
  -> InteractionSync.execute
  -> apply：同步更新本地状态
  -> 发起服务端请求
  -> 成功：接受服务端快照
  -> 失败：rollback 恢复旧值
```

连续操作必须使用稳定的 `entityKey`，让同一实体的较新意图不会被较旧请求的失败回滚覆盖。调用方不得在成功后立即无条件全量刷新并覆盖本地新状态，应使用带版本/意图判断的对账。

## Live 事件

服务端事件需要携带来源客户端身份。当前客户端发起的事件不能再次覆盖本地乐观状态；其他客户端或浏览器标签页的事件必须进入正常对账流程。乐观更新本身不等于 Live 同步，必须同时确认事件队列和来源回声抑制已接入。

## 失败处理

- `apply` 和 `rollback` 必须针对同一个状态源。
- 回滚快照要在本次 apply 前捕获。
- 旧意图失败时不得覆盖更新的本地意图。
- 普通设置可以沿用页面已有的轻量错误提示；敏感表单和上传流程必须保留明确错误状态。
- 禁止通过延迟、额外 `nextTick`、重复刷新或 CSS 补丁掩盖状态竞态。

## 代码审查清单

- 是否判断了这是单值即时状态，还是需要显式保存的表单？
- 是否使用了稳定且足够细的 `scope` 与 `entityKey`？
- 是否有 apply 前的旧值快照和对称 rollback？
- 是否会被旧请求或旧 Live 回声覆盖？
- 是否误把密码、凭据、上传或危险操作做成乐观更新？
- 是否在成功后保留服务端规范化结果？
- 是否为连续点击、失败回滚和跨客户端事件补充测试？
