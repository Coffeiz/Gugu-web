## 1. 背景与目标

Admin 当前已有用户、服务、日志、Agent、模型、沙箱和存储等管理页面。管理员需要在多个页面之间查状态、定位故障和执行低频操作，入口分散且上下文不连续。

本能力在 Admin 页面增加一个前台咕咕球风格的浮动入口，让管理员可以用自然语言询问后台数据，并在明确授权后执行受控管理操作。

目标：

- 复用前台咕咕球的品牌识别和聊天体验，降低学习成本。
- 让管理员能够快速回答“系统现在是否健康”“哪个用户/服务异常”“最近有哪些失败任务”等问题。
- 将查询、诊断和操作分层；默认只读，危险操作必须展示对象、影响和确认入口。
- 所有操作都能追溯到 Admin 身份、工具名、目标对象、结果和时间。
- 为后续更新助手预留版本、发布状态和回滚信息，但不让首版直接修改代码或自动发布。

本 PRD 不包含：

- 不把普通用户的咕咕聊天直接提升为 Admin 权限。
- 不允许通过提示词、伪造参数或普通 Agent 工具绕过 Admin 权限。
- 不在首版中自动执行数据库删除、批量用户操作、服务器 Shell、镜像清理或生产发布。
- 不在首版决定产品的自动更新来源、更新包格式、灰度策略或升级进程。

## 2. 功能需求

### FR-ADM-001：Admin 咕咕球入口

登录 Admin 后，在 Admin 全局布局中显示咕咕球入口；未登录或普通用户页面不显示 Admin 助手状态。入口复用前台咕咕球的视觉语言，但使用 Admin 深色暗玻璃主题和清晰的“Admin 助手”身份标识。

打开后使用独立的 Admin 对话窗口或侧边面板，不复用普通用户的会话列表、历史消息和未授权上下文。入口位置、层级和关闭行为不能遮挡 Admin 页面主要操作。

### FR-ADM-002：后台上下文查询

管理员可以询问系统健康、用户状态、服务状态、模型配置、沙箱状态、存储用量、失败任务和审计记录。回答必须标注数据时间范围和来源范围；没有权限或没有数据时明确说明，不用猜测或用前台用户数据补全。

首版只读工具目录：

| 工具 | 用途 | 默认权限 |
|---|---|---|
| `get_system_status` | 服务、数据库、Redis、Worker 和 Gateway 健康状态 | `admin.read` |
| `get_system_overview` | 用户数、活跃度、任务量、存储和错误概览 | `admin.read` |
| `list_users` | 按状态、注册时间、绑定渠道和关键词筛选用户 | `admin.read` |
| `get_user_detail` | 查看单个用户的配置摘要、连接状态、用量和风险状态 | `admin.read` |
| `list_workspaces` | 查看工作区、所有者、容量和沙箱开关 | `admin.read` |
| `list_im_bots` | 查看 IM 机器人、网关连接和最近心跳 | `admin.read` |
| `list_models` | 查看系统模型、用户模型和验证状态 | `admin.read` |
| `list_failed_tasks` | 查看失败任务、服务来源、时间和可重试状态 | `admin.read` |
| `search_audit_logs` | 按操作者、工具、对象和时间检索审计日志 | `admin.audit.read` |
| `get_usage_summary` | 查看 Agent、模型、存储和服务资源用量 | `admin.read` |

### FR-ADM-003：受控管理操作

首版允许接入低风险、可追踪且可恢复的操作。每个操作必须在服务端再次校验 Admin 身份、权限、目标对象所有权边界和当前状态。

建议首批操作：

| 工具 | 用途 | 确认 |
|---|---|---|
| `disable_user` / `enable_user` | 暂停或恢复用户使用权 | 必须确认 |
| `disconnect_im_bot` | 断开指定 IM 机器人 | 必须确认 |
| `retry_failed_task` | 重试明确可重试的失败任务 | 必须确认 |
| `revoke_user_sessions` | 注销指定用户的登录会话 | 必须确认 |
| `reset_user_onboarding` | 重置用户引导状态 | 必须确认 |

暂不开放的高风险工具包括删除用户/工作区、批量停用、永久删除文件、重置生产沙箱、重启关键服务、修改全局模型配置、执行任意 Shell 和生产发布。需要时单独设计更高等级的权限和审批流程。

### FR-ADM-004：确认门与结果反馈

危险操作必须先返回待确认状态，内容至少包括：操作名称、目标对象、将要发生的变化、潜在影响、是否可恢复和有效期。只有用户在 UI 中明确点击确认后，服务端才接受带有一次性确认令牌的执行请求。

取消、过期、目标状态变化和执行失败都必须有明确结果。操作成功后展示结果摘要和审计记录编号；不得只显示“已完成”而隐藏实际失败。

### FR-ADM-005：数据脱敏与审计

工具结果不得返回密码、Token、API Key、Cookie、完整授权参数或聊天正文。用户查询只返回管理所需的最小字段，敏感标识使用脱敏值或稳定指纹。

每次工具调用至少记录：Admin 操作者、会话 ID、工具名、参数摘要、目标对象摘要、结果状态、耗时、错误分类和时间。参数摘要不得包含密钥、聊天正文、附件正文或未经脱敏的用户输入。

### FR-ADM-006：跨页面跳转

对话回答中涉及具体用户、服务、任务或配置时，可以提供跳转到对应 Admin 页面或详情抽屉的入口。跳转链接只能携带内部 ID 或短期签名引用，不把敏感数据放入 URL。

### FR-ADM-007：更新能力预留

首版只展示当前 Admin 服务版本、构建时间、运行环境和是否存在可用更新的摘要，不自动下载、安装或重启。更新相关工具未来应与管理工具分开命名空间，并至少区分“检查更新”“查看变更”“下载更新”“应用更新”和“回滚版本”。

## 3. 技术方案

### 3.1 前端边界

Admin 入口优先复用 `GuguChatFab`、聊天窗口、消息行和工具状态展示等视觉/交互原语，但不得直接复用普通用户的会话 store、用户级工具列表或普通用户上下文注入逻辑。

建议新增 Admin 专属容器和编排层：

- `frontend/src/components/admin-gugu/AdminGuguFab.vue`：Admin 入口和主题外壳。
- `frontend/src/components/admin-gugu/AdminGuguPanel.vue`：Admin 会话面板、确认卡片和结果卡片。
- `frontend/src/components/admin-gugu/composables/useAdminGuguChat.ts`：Admin 会话、工具状态和确认流程。
- `frontend/src/services/adminGugu.ts`：Admin 助手 API 请求封装。

Admin 页面入口只负责挂载和布局，不在 `Admin` 页面 `index.vue` 内堆叠对话、工具和确认业务。视觉上使用 Admin 暗玻璃设计规范；复用前台样式时只复用结构性组件和通用 token，不把前台浅色 surface 直接带入 Admin。

### 3.2 后端权限与会话

新增独立的 Admin Assistant API 命名空间，例如 `/api/v1/admin/assistant/*`。所有请求必须经过现有 Admin token 校验；服务端以 token 中的 Admin 身份作为唯一权限事实源，不信任前端传入的角色、用户 ID 或工具名。

Admin 会话上下文只允许注入：

- 当前 Admin 身份和权限集合；
- 当前问题明确涉及的后台摘要；
- 工具返回的已脱敏结果；
- 必要的时间范围、环境和版本信息。

不得自动注入普通用户的聊天历史、私聊内容、文件正文、API Key 或完整数据库记录。

### 3.3 工具注册与返回契约

Admin 工具使用独立注册表或明确的 `admin` 命名空间，不与普通用户工具列表隐式混合。每个工具声明名称、用途、所需权限、是否 destructive、参数 Schema、确认要求和审计分类。

统一结果建议如下：

```ts
type AdminToolResult<T = unknown> = {
  ok: boolean
  summary: string
  data?: T
  warnings?: string[]
  requires_confirmation?: boolean
  confirmation_token?: string
  audit_id?: string
}
```

`confirmation_token` 只在服务端生成，短期有效、绑定操作者、工具、参数摘要和目标状态；执行时必须重新校验，不能只凭前端传回的布尔值。

### 3.4 失败与并发

查询工具应设置明确的时间范围、分页和结果上限，避免一次请求拉取全量用户或日志。操作工具使用幂等键，重复提交不得重复停用、断开或重试。目标在确认后发生变化时拒绝执行并要求刷新，不使用过期快照强行覆盖。

### 3.5 与更新系统的关系

Admin 咕咕球不是更新器本身。更新检查、版本元数据、下载、校验、切换和回滚应由独立的部署/更新服务负责，助手只负责调用受控接口并解释状态。这样可以避免把发布凭据、Docker 控制权或宿主机 Shell 权限放进聊天 Agent。

## 4. 验证与上线

验收重点：

- 普通用户 Token 访问 Admin Assistant API 必须失败；Admin Token 才能创建 Admin 会话。
- Admin 助手能查询系统状态、用户摘要、服务状态和审计日志，结果带时间范围且不泄露敏感字段。
- 同一危险操作在未确认、确认过期、目标状态变化和重复提交时都不能误执行。
- 操作成功、失败和取消都能在 UI 显示，并能在 Admin 审计日志中定位。
- Admin 咕咕球使用深色暗玻璃样式，不影响现有 Admin 页面布局，也不改变普通用户咕咕球行为。
- 更新相关问题只能看到版本/更新摘要；首版不能下载、安装、重启或发布。

建议测试覆盖：权限隔离、工具 Schema、确认令牌绑定、敏感字段脱敏、幂等执行、审计记录、空结果和超时错误。前端补充 Admin 面板的确认/取消路径测试，后端补充跨角色和跨用户访问测试。

上线采用 Admin 内部灰度：先只开放只读工具，再按 Admin 角色逐步开放低风险操作。出现工具误报、越权或审计缺失时，可关闭 Admin Assistant 开关而不影响普通用户聊天、Admin 页面和业务 API。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 前台聊天组件误带入用户工具或上下文 | 越权读取或误操作 | Admin 独立会话、独立工具命名空间和服务端权限校验。 |
| 工具结果包含敏感字段 | 凭据或个人信息泄露 | 后端最小字段返回，统一脱敏，禁止前端自行拼装原始数据。 |
| 模型误判危险操作 | 用户/服务被误停用 | destructive 工具强制确认令牌和目标状态复核。 |
| 查询范围过大 | 延迟高、数据库压力大 | 默认时间范围、分页、结果上限和聚合接口。 |
| 更新能力与运维权限混在一起 | 可能演变为任意发布或 Shell | 更新服务独立，首版只读，后续单独 PRD。 |

待确认事项：

- Admin 助手是否只向 `superadmin` 开放，还是允许普通 `admin` 使用只读工具。
- Admin 助手是否需要支持多环境（dev/staging/prod）切换；默认环境必须明确且不可由模型猜测。
- 低风险操作是否需要二人审批，还是由单个 Admin 的确认门完成。
- 更新助手未来只服务 Docker Compose 部署，还是同时覆盖桌面/本地部署。
