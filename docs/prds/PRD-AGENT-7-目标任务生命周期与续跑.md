# PRD-AGENT-7：目标任务生命周期与续跑

> 状态：规划，暂不实施。创建：2026-11-14。
> 时机：桌面端完成后再评估与实施，不作为当前 N2/N3 迁移或桌面可运行版本的前置条件。
> 关联：`docs/refactor/Gugu-2.0-架构说明.md`、`docs/refactor/Gugu-2.0-迁移任务清单.md`。

## 1. 背景

现有 Python `/goal` 在会话上下文中保存目标文本、状态和模式；创建目标后立即启动 Agent。Goal 模式在模型没有输出内部完成标记时追加续轮提醒，并在当前 Run 中继续。用户可通过命令查询、暂停、恢复或取消目标。Node Harness 已有完成标记和续轮提醒逻辑，但不代表 Web 或桌面 Host 已完成 Goal 生产接入。

当前方案适合一次运行内的多步任务。长任务需要更明确的停止原因、预算、恢复边界和用户可见状态。仅有目标文本或模型输出完成标记，不能证明任务完成，也不能保证中断后可安全重放。

## 2. 目标与范围

- 保留 `/goal` 交互，为目标提供清晰的状态、完成条件、进度摘要和停止原因。
- 一个 Goal 可由多个有边界的 Run 推进；单个 Run 内仍可进行多轮模型和工具调用。
- 根据运行结果、目标状态、预算和用户操作决定是否续跑，不能持续盲目追加同一提醒。
- 遇到必须由用户处理的缺失信息、授权或外部阻塞时停止自动续跑并说明原因。
- 支持桌面和自部署 Host 装配同一套目标契约；各 Host 保持独立的数据与生命周期。

本 PRD 不要求新增通用工作流引擎，不提前确定独立数据库表，不要求兼容 Codex 的内部协议；不因启用 Goal 自动获得工具、文件、网络或执行权限。SaaS、跨设备转交和多设备同步不在首期范围。

## 3. 产品行为

### 3.1 状态与用户操作

| 状态 | 含义与可用操作 |
| --- | --- |
| `active` | 目标仍在推进，可暂停或取消；是否有运行中的 Run 单独展示。 |
| `paused` | 用户暂停，不再自动启动新的 Run；用户可恢复或取消。 |
| `blocked` | 需要用户输入、授权或外部条件变化；展示原因和下一步，用户可恢复或取消。 |
| `completed` | 目标声明完成并通过定义的收尾检查；保留可查看的结果和验证证据。 |
| `cancelled` | 用户取消，不再自动续跑；保留必要的历史和已发生的副作用记录。 |

预算耗尽作为明确的停止原因，具体表现为独立状态还是 `paused` 的原因由实施设计决定，不得记作完成。状态切换须记录时间和原因；用户界面及 IM 提示不得暴露内部标记、凭据或原始异常。

创建目标后可立即开始；查询展示目标、状态、最近进度、停止原因和预算信息。暂停、恢复、取消需要定义当前 Run 的中断和收尾语义：暂停或取消后禁止启动新 Run；当前 Run 的取消信号、已产生结果与副作用按既有运行和工具契约处理。恢复必须是显式用户动作，并在满足授权、预算、Host 可用和无冲突运行等条件后调度；暂停和恢复不能伪装成已经完成。

### 3.2 完成与阻塞

模型可提出完成声明并提供结果、已执行验证和未完成项；Harness 校验是否仍有未解决的交互、待完成工具、取消或失败等已知障碍。用户指定的测试或查询应报告实际结果；跳过和未运行不能写成通过。检查仍不能证明语义上绝对正确，必须对缺少证据的部分明确说明。

认证、确认、凭据、缺少用户信息等无法自主消除的阻塞进入 `blocked`，提供清晰原因和恢复方式；不得反复请求授权或靠重复提示掩盖失败。自动续跑须有成本/次数或时间预算与明确停止条件；具体默认值、是否允许用户调整及不同端的产品交互待实施前确定，不直接套用旧普通对话守卫。

## 4. 目标与 Run 的关系

Goal 承载用户目标和跨 Run 的状态；Run 承载一次有边界的执行、工具调用、取消、结果及事件。Run 结束后，根据持久化的状态和结果决定完成、阻塞、停用或创建下一次 Run。续跑必须以明确的进度与已有历史为依据；内部完成标记仅可作为迁移期兼容信号，不能单独成为完成证据。

持久化至少表达：目标内容与完成条件、所属用户与会话、状态与停止原因、当前/最近 Run 的关联、进度与验证摘要、时间及预算消耗。实际表结构、版本与存储位置在实施前根据既有 Run/Job、SQLite 和 PostgreSQL 能力决定，避免建立第二套并行状态真源。

同一目标并发续跑须经持久化的条件更新、租约或等效机制协调；过期执行者不能覆盖新状态。崩溃可能发生在副作用已执行但回执未持久化之间：不得假设可以无条件重放，须复用既有幂等键、操作收据或明确标记结果未知并要求核实。非幂等操作不能自动重复。Goal 恢复不绕过 destructive 确认、工具授权和跨用户隔离。

桌面进程退出、Host 重启、断网和用户暂停需各自定义恢复方式。重启后先恢复持久状态并核对既有 Run 与待处理操作；是否自动恢复执行须由产品策略和用户授权明确决定，不能仅凭 `active` 标记重放操作。前端断线本身不等于 Run 失败或目标完成。

## 5. 兼容与实施顺序

0. **桌面端完成后再立项评估**：确认桌面产品基础、普通 Agent 对话和工具、取消、持久化、Run/Job 与 Host 入口具备可验证能力；依赖不满足时继续保留现状。
1. **契约与基线**：盘点现有 `/goal` 命令、会话字段、完成标记和 Python/Node 回归；明确旧状态迁移、失败与恢复语义。迁移旧会话时保留用户目标与状态，避免未授权自动执行。
2. **目标状态与单 Run**：在现有生命周期上接入状态和用户操作，完成状态转换、权限、取消和预算边界，不改变普通对话的运行规则。
3. **有界续跑与恢复**：接入持久化的续跑决策、并发保护、已知/未知副作用处理及重启恢复；复用现有 Run/Job 与操作收据。
4. **多端体验与验收**：桌面、自部署 Web 与 IM 按各自能力展示状态及操作；分别验证桌面 SQLite 和服务端 PostgreSQL 的持久化与隔离。是否支持其他端由后续能力评估决定。

每阶段先验证再替换对应旧路径；旧完成标记和会话字段的退役时间由兼容与恢复验收决定。架构方案与旧 Python 行为冲突时记录有意差异，不以代码存在或接口注册代表完成。

## 6. 验收标准

- 创建、查询、暂停、恢复、取消、完成和阻塞状态在不同入口语义一致，重启后可正确读取，越权用户不可查看或操作。
- 普通多步任务能够跨有界 Run 推进；已有进度和工具回执不丢失、不乱序、不重复提交。
- 等待用户确认或外部条件时不空转；预算耗尽、取消、失败和完成可区分，且不以未验证声明为完成证据。
- 暂停/取消与续跑、Run 完成、用户确认并发时，不会启动不应启动的后续 Run；过期租约持有者不能覆盖新状态。
- 断线、进程退出、重启以及副作用结果未知时有可观察状态；非幂等操作不被盲目重放。
- 覆盖 Python 现有 `/goal` 与 Node Harness 相关回归，新增测试保护状态转换、授权隔离、续跑、预算、故障及恢复；真实依赖隔离测试与跳过项分别报告。
- 不改写普通对话的既有轮次限制和重复调用策略；无真实环境证据时不宣称跨端或生产可用。

## 7. 待决定事项

- 桌面端“完成”的具体产品和验收门槛，由桌面计划确认；本 PRD 不把当前验证壳等同于桌面产品完成。
- 默认预算、用户是否可调整，以及预算耗尽后的恢复交互。
- 恢复时默认询问用户还是在授权范围内自动继续，以及 Web、IM、桌面各自可用的交互方式。
- Goal 状态的最终存储模型、迁移及历史保留策略；是否支持并发多个 Goal。
- 完成验证的证据格式和可由程序可靠判断的最低条件。
