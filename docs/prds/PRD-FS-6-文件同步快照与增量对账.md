## 1. 背景与目标

### 1.1 原始调查与当前实现边界

`FileSyncWatcherManager.run()` 把启动/周期补偿和临时整树回退交给同一 `_project()` 路径。`force=True` 会关闭 stat 缓存、强制内容校验；补偿成功时间只保存在进程内，启动后重新执行一次全量补偿，失败又会在后续循环尝试。

`reconcile_local_directory()` 在数据库查询后递归扫描磁盘，再继续查询数据库。双向绑定的 `_pending_conflicts()` 也会在查询后同步读取文件计算指纹。把其中一处改成线程不足以修复整条链路。

devserver 的只读复测中，一个绑定遍历约八万个目录项、七万余文件耗时接近一分钟，尚不包含后续路径映射、冲突哈希与数据库投影。连接配置的 `idle_in_transaction_session_timeout` 为 60 秒。该结构高度符合扫描期间事务空闲、后续 SQL 遇到连接关闭的故障；尚无数据库端终止日志证明每次断连的具体原因。

最近八小时的对应故障首次记录紧贴零点，但报错时间不等于任务启动时间，不能据此确认每日补偿。现有调度是启动补偿加间隔，不是固定零点调度。

### 1.2 目标

建立“实时事件增量同步 + 按文件活跃度筛选的每日快照差异对账 + 手动完整校验”的单一同步体系；没有有效快照时自动完整校验以建立基线，除此之外不设置周期完整校验。

每用户独立队列与持久进度，由有界 Worker 池分批调度，不为每用户常驻进程。后台遍历与哈希不阻塞聊天、取消和心跳，不持有数据库事务；单次执行预算默认 30 分钟，整轮允许跨多个调度片段完成。正常让出/预算耗尽保存游标后续跑，不从头重扫；失败不破坏最后成功基线。

### 1.3 非目标

- 不将数据库空闲事务时限改为 30 分钟，不关闭该保护。
- 不声称快照可消除每日目录遍历；没有可靠变更事件时仍须枚举目录确认缺失路径。
- 不删除虚拟环境、依赖目录或用户文件，不新增未经确认的目录忽略规则。
- 不替换 TS 文件事件 sidecar、RAG、文件事实源协议或现有冲突处理产品契约。
- 不新建文件正文备份系统；本方案快照只存同步元数据与指纹。
- 不要求固定零点执行，不在首版新增时区化 cron 设置。
- 不设置每周或其他周期自动完整校验；不因用户登录、聊天或浏览认定文件活跃。

## 2. 功能需求

### FR-FS6-001：对账模式与同步方向

| 模式 | 触发 | 工作范围 |
|---|---|---|
| `event_incremental` | 文件事件 | 受影响路径与必要父目录，直接复用 targeted 投影 |
| `snapshot_diff` | 每日到期且用户周期内无文件变更、事件丢失补偿、启动续跑、管理员手动对账 | 本地输入方向分段枚举元数据，仅处理差异项；新增和变化文件重新哈希 |
| `integrity_full` | 首次无有效快照、快照损坏/范围变更需重建、明确手动请求 | 分段枚举并校验所有普通文件的内容，按差异投影；无周期自动触发 |
| `mirror_out` | 文件库变更事件、每日补偿、启动恢复或管理员手动请求 | 文件库→绑定目录，按绑定成功水位与任务固定截止点分页，只复制新增/变化项或补回缺失目标；不扫描本地目录、不反向导入 |

调度原因独立于模式，使用 `bootstrap`、`daily`、`file_event`、`event_fallback`、`restart_recovery`、`manual`、`snapshot_invalid`。`file_event` 表示文件库对象变化直接触发 `mirror_out`；运行中到达的事件以绑定脏水位保留，并在当前固定截止任务成功后立即排入下一任务。同一次任务只记录一个主原因，合并请求可记录其他原因枚举。

默认每日判断周期为 24 小时，周期判断水位与成功扫描水位分别持久化：跳过周期也推进判断水位，不伪造扫描成功时间。手动/初始化完整校验成功可满足已合并的当次对账；没有完整校验周期。无有效快照自动排队建立可信基线，不从旧缓存推断成功；正常重启仅恢复游标，不强制重建。

### FR-FS6-002：成功元数据快照

快照按用户、绑定、绑定范围版本隔离，记录普通文件/目录的规范相对路径、类型、大小、纳秒 mtime、可用的 ctime、内容指纹与数据库投影版本。不存在正文、绝对宿主路径或凭据。

只有扫描完整、投影成功、journal/outbox 已提交且并发水位验证通过，才发布新成功快照。冲突路径不得标记为已同步；单独保留阻塞标记和最后已同步基线，冲突解决后重新对账。

读取失败、目录不可访问、扫描中断、超时或任务失败均不得把未见到的路径解释为删除，不得裁剪旧成功快照。

### FR-FS6-003：差异规则

- 新增、stat 变化、精确文件事件标脏或无可信指纹的文件进入内容校验。
- stat 未变化且基线有效时复用内容指纹，但仍校验数据库投影版本；数据库侧变更不能因磁盘未变化而遗漏。
- 删除必须来自完整扫描结果，且在投影前复查目标仍缺失；扫描缺口不产生删除。
- 移动沿用现有明确的匹配规则；多个相同指纹候选不能武断认定重命名。
- 文件转目录、目录转文件、目录移动和子项变化都进入计划，不只比较文件条目。
- size/mtime 相同不等于内容相同：ctime、文件事件用于提前发现；元数据未变化且事件遗漏的内容修改可能只能由手动完整校验发现，不宣称严格零漏检。

### FR-FS6-004：30 分钟执行预算、续跑与取消

默认一个用户扫描任务单次执行预算上限为 1800 秒，覆盖该次执行的扫描、哈希、计划、投影和发布；排队/暂停时间不计入该次预算，整轮累计时间独立记录。正常调度片段应短于预算，达到目录项数、字节数或时长上限时主动让出。管理员不得通过 HTTP 请求等待整轮结束。

扫描线程使用协作停止标志，在目录项之间与哈希分块之间检查；仅取消 `asyncio.to_thread()` 的等待不能视为线程已终止。截止后禁止新投影批次；当前短事务必须成功提交或回滚后才释放任务租约。

正常片段结束或执行预算耗尽进入 `paused`，保存已确认游标，下一轮继续同一逻辑任务，不计失败、不触发故障退避。用户显式取消进入 `cancelled`，不自动续跑；真实 I/O/数据库错误才进入故障退避。系统停机在安全检查点暂停，异常退出由租约恢复。

已提交批次无需回滚整棵目录；候选快照与进度独立保存，旧成功快照保留。续跑用 journal 幂等和版本校验跳过已应用批次，禁止重复增加 File 版本或重复产生业务事件。

### FR-FS6-005：并发与事件不断流

同一绑定最多一个整树对账任务，事件同步仍可及时消费。所有文件库写入、targeted 投影与整树批次均参与绑定水位或对象版本校验。重叠绑定保留原有作用域与冲突规则，不能只靠绑定锁证明数据隔离。

整树扫描及暂停期间的事件按路径合并并持久保留。发布前处理扫描后的脏路径并复核水位，文件持续变化时暂停待续跑，不强行发布“干净”快照。事件缓冲溢出只能升级为一次整树回退，不能丢失信号后宣称完成。

### FR-FS6-006：故障退避与运行状态

同一绑定失败后按默认 60、300、900、3600 秒退避，附带有界抖动；成功清零。失败不阻塞其他绑定，重启不重置退避。每日/事件/手动请求合并到同一任务，禁止每轮 watcher 都重新全树扫描。

管理员可查看模式、原因、阶段、耗时、上次成功时间、下次执行时间、失败次数与脱敏错误类别。手动 dry-run 不写 File、journal、内容副本、成功快照或 RAG 事件；允许写独立任务状态和计数结果。

### FR-FS6-007：每用户独立任务与分批公平调度

每用户有独立任务队列、租约、周期水位和各绑定游标。同一用户最多一个扫描执行槽，同一绑定最多一个活跃逻辑整树任务；独立指调度/状态隔离，不是无限启动线程或进程。

全局每轮只领取一批用户，运行槽位、目录枚举、内容哈希及 DB 写入分别有资源上限。不把全体用户任务一次 `create_task`；未获槽位的任务保持持久排队，不占扫描线程和数据库连接。

每用户按目录/路径批次、字节数和时间片处理，保存进度后让出，用户间轮转，用户内多个绑定也轮转。手动、异常补偿、首次基线优先于普通每日任务；同用户手动请求在当前片段安全结束后切换，不并发扫描。普通任务通过等待时间提升优先级，持续高优先级任务不能使其永久饥饿。

### FR-FS6-008：周期内文件活跃跳过

定期判断区间为 `(previous_cycle_cutoff, current_cycle_cutoff]`，以服务端观察到的文件新增、修改、删除、移动事件为准，聚合到用户。目录结构变化同样属于文件树变更。登录、聊天、浏览和无变化写入不算；对账自身的投影、journal/outbox 重放不算，不得自我触发活跃。

区间内存在文件变更的用户跳过本周期所有到期的本地目录扫描绑定（`mirror_in` / `bidirectional`），每个绑定均记录 `skipped_file_active`，实时事件同步仍运行。`mirror_out` 的权威方向是文件库→绑定目录，本地输入目录活动不得阻止导出同步，因此它仍按期排队。区间内无文件变更的用户分批进入每日快照差异任务。使用持久周期截止与事件序号水位，迟到事件按实际观察周期计入，避免客户端时间影响判断；跳过只更新判断水位，不更新成功快照。

首次基线、无效快照重建、监听异常/丢失补偿、手动任务和已开始任务的续跑不受跳过规则影响。监听或活动统计状态不可信时不能认定健康活跃而跳过；恢复后合并一次补偿任务。已排队但尚未开始的普通每日任务在领取时重新核对活动水位。

明确边界：用户长期持续产生文件变更可能一直跳过定期扫描，未被监听发现的遗漏可能长期存在；不另加周期完整校验暗中改变规则，通过异常补偿、首次基线与手动校验处理可识别情况。

## 3. 技术方案

### 3.1 架构与抽象边界

```text
TS 文件事件 → watcher 事件合并 → targeted 路径投影 → journal/outbox
                        ↓ 需要整树回退
周期调度 / 启动恢复 / 管理员请求
    → 周期文件活动判断（普通每日任务可跳过）
    → 每用户持久队列 → 有界 Worker 池分批领取 / 公平轮转
    → 分段扫描与哈希（线程、无 DB）↔ 持久游标 / 候选快照
    → 成功基线 + 短事务读取的 DB 水位 → 差异计划（纯逻辑）
    → 事务外内容哈希 / 冲突副本准备
    → 短事务批次投影（归属、配额、冲突、版本、journal/outbox）
    → 并发脏路径复核 → 发布成功快照
    → outbox 异步投递与 RAG 更新
```

`watcher` 只管理事件与入队，不持有跨整树扫描的 ORM session；`scan` 不知道 ORM；`plan` 不执行 I/O；`jobs` 编排任务运行，`job_scan` 管检查点续跑，`job_projection` 负责数据库投影与成功基线发布，`job_mirror_out` 负责文件库到绑定目录的分页导出，`job_lifecycle` 集中写任务状态和租约，`scheduling` 管理用户公平性，`activity` 管理文件活动水位。不得将 AsyncSession/ORM 对象传入扫描线程。

方向必须保持现有绑定模式契约：`mirror_in` 与 `bidirectional` 的目录事件/快照扫描方向是本地目录→文件库；`mirror_out` 的方向是文件库→绑定目录，不注册本地目录 watcher，也不得调用本地路径投影器反向导入。文件库正式写入必须能触发 `mirror_out`，不可要求源文件路径位于输出绑定根内；活动任务期间到达的事件不得被当前固定截止点吞掉。成功元数据基线用于本地目录扫描模式；`mirror_out` 使用文件库对象分页与任务游标，不伪装成目录扫描或 `integrity_full`。分页不是每次无条件重复制：以绑定的上次成功水位和逻辑任务固定的源端截止时间识别新增/变化文件，只复制需要更新的目标；任务片段内用文件 ID 游标续跑，每项在复制成功后才推进，失败重试必须幂等。每轮仍检查目标是否缺失，以修复外部删除的导出副本；源文件在任务截止点之后变更时留给下一轮处理。文件库对象若已位于该绑定输出目录内，视为已在目标位置，不得把它再次嵌套复制到输出目录下。文件库软删除不得静默删除绑定目录中的目标文件，沿用 FS-3 的删除保护契约。

执行器边界：`event_incremental` 继续走现有 watcher → targeted 路径投影 → journal/outbox 链路，保持事件级及时处理；不为单路径事件创建 `FileSyncReconcileRun`，也不让它等待整树任务的用户队列、扫描预算或并发槽位。持久任务、租约、预算、续跑和状态查询用于 `snapshot_diff`、`integrity_full` 及 `mirror_out` 分页导出；事件丢失后的 `event_fallback` 是整树补偿任务，仍进入该执行器。这样复用的是同步协议与幂等/水位边界，而不是把实时事件改造成整树任务。

#### 持久任务代码的职责拆分约束

`jobs.py` 的拆分属于不改变行为的结构重构，不增添新的同步协议或状态语义。任务状态及租约只能由 `job_lifecycle.py` 写入；`job_projection.py`、`job_mirror_out.py` 和 `job_scheduler.py` 通过明确的生命周期操作请求状态变化，不可各自维护状态收尾逻辑。执行上下文使用 `ReconcileJobSpec`（绑定身份/模式/范围版本、固定截止水位、预算与恢复游标等显式字段）替代松散 `dict`；扫描检查点仍由 `checkpoint.py` 持有，不扩建通用 utils 模块。

按低风险顺序拆分：扫描/检查点续跑、本地扫描投影/成功基线发布、`mirror_out` 分页导出、每日调度与任务状态/租约写入分别位于职责模块，并通过本地 filesync 全量回归。执行函数间以显式任务规格及执行 DTO 传递上下文，避免十余个松散参数。`jobs.py` 保留领取任务的编排和兼容门面；2026-10-06 职责收敛后约 446 行，旧整树实现及旧 stat-cache 已按 FS6-018 清理。拆分必须保留已提交批次、取消/预算暂停、租约恢复、幂等 outbox、成功水位 CAS 与失败退避行为。

验收不得以“模块行数下降”代替行为证明：现有对账、调度、活动、PostgreSQL 生命周期及压力测试须继续通过；增加/调整测试必须覆盖跨模块状态序列和可观察结果，不断言函数所在文件或源码结构。实时 `event_incremental` 继续由 watcher → targeted → journal/outbox 直接处理，不进入这里的任务队列。

### 3.3 快照与 journal 的单一职责

`FileSyncJournal` 继续是已应用变更的幂等和冲突基线依据；元数据快照是可重建的扫描加速基线，不成为第二个业务事实源。`snapshots.py` 的正文副本只用于现有冲突恢复，继续独立保留。

整树成功基线和事件 stat 缓存分工：整树任务发布完整成功代次；事件同步只在对应数据库提交成功后更新路径缓存、记录脏水位，不把局部观察覆盖为整树快照。将原 `StatCache.save(prune=True)` 的“已见路径裁剪”改为仅由完整成功发布调用；targeted 的局部更新永不裁剪未扫描路径。

旧裸 `stat-cache.json` 没有成功提交证明，不能导入为可信基线。迁移时将其作为可丢弃缓存失效，首次建立新基线；不长期维护旧格式读取分支。不删除正文 `.bin` 冲突副本。

### 3.4 数据、原子发布与恢复

复用 `FileSyncBinding`，目标字段包含 `scope_revision`、`baseline_generation`、`last_daily_reconciled_at`、`last_integrity_verified_at`（仅观测手动/初始化结果）、`next_reconcile_at`、`consecutive_failures`、`dirty_revision`。现有 `revision` 是文件同步 journal 的写入序号，不能作为绑定配置版本；任务的 `binding_revision` 必须复制 `scope_revision`，绑定根目录或同步方向变化时递增并使旧任务/检查点失效。

`FileSyncReconcileRun` 目标字段：用户/绑定外键、逻辑 run ID、模式、原因、阶段、状态、整轮开始/完成时间、单次执行开始/截止时间、累计执行时长、暂停原因、下一续跑时间、租约 token 与过期时间、绑定/脏水位、候选快照代次、检查点引用、进度计数和脱敏错误代码。状态为 `queued/running/paused/succeeded/failed/cancelled/interrupted`；预算耗尽是 `paused` 而非失败 `timed_out`。活跃逻辑任务唯一约束涵盖排队与暂停状态，兼容测试 SQLite 方言。

拟新增 `FileSyncUserScanState`：用户外键唯一、前后周期截止、活动事件序号水位、最近文件变更时间、周期决策及跳过原因、轮转/公平等待水位、执行租约。活动按用户记录一次，不为每绑定复制账号活动状态；租约过期持有者不得写检查点或发布快照。

快照头包含 schema 版本、绑定范围指纹、代次、创建时间、完整性、条目数量与校验摘要。正文条目采用规范相对路径。先写临时文件、fsync、原子改名为不可变代次文件，再用短事务 CAS 提交绑定的成功代次和任务成功状态。读取只认 DB 成功指针，不依靠“最新文件名”。

数据库提交前崩溃：候选代次孤立，旧基线仍有效；提交后崩溃：DB 指针已发布，重启加载该代次。指针所指文件缺失/摘要不符时明确标记 `snapshot_invalid` 并重建，不执行删除推断。仅清理无引用的元数据候选代次，保留当前与上一成功代次，不清理用户正文/冲突副本。

#### 分段检查点与大文件

检查点包含绑定范围/schema 指纹、逻辑 run、待遍历目录队列、已扫描范围、当前目录分页水位、候选分片 manifest、哈希/投影批次位置、脏事件水位。队列与条目分片持久存储，不能把十万项完整列表嵌入每次任务 DB 更新，也不能保存不可序列化的 Python `rglob` 迭代器或目录句柄。

目录分页不能仅依赖变化中的目录序号；需稳定路径排序/已见集合和目录变更复核，目录变动时局部重扫而非整轮重启。游标恢复先检查绑定范围和目录身份，范围变更时失效相应候选并重建。

大文件按字节块分段，检查点绑定文件身份和读前/读后 stat。不能序列化标准 `hashlib` 运行对象并假定可恢复；使用版本化分块指纹算法，持久分块摘要及偏移，并通过同一算法生成整体指纹。旧整文件指纹与新算法不可直接比较，升级时需首次可信重建。文件在分块期间变化就废弃该文件候选、重新读取，不继续拼接混合版本；冲突副本准备同样支持阶段续跑。

部分扫描范围只产生候选，不推断未扫描区域删除；发布必须以完整范围覆盖、短事务已提交和并发脏事件复核为前提，分片成功不等于整轮成功。

### 3.5 事务、分批资源与执行时间预算

每个扫描/哈希阶段都在短读取事务关闭后执行；投影按最多 200 个候选一批起步，每批目标不超过 5 秒，具体批量依据压力验收调整。配额增量必须事务内检查，不能依据扫描开始时的剩余额度长期推算。

单批失败回滚后丢弃全部 ORM 引用，从 DTO/ID 重查。成功事件和快照发布都不得早于对应提交。outbox 发送失败不会推翻已提交投影，但必须持久重试，避免“快照成功、业务事件丢失”。

预算用 monotonic 截止时钟，持久字段使用 UTC 业务时间。线程不能安全强杀：停止检查粒度目标为目录项/哈希块；文件系统 syscall 长期阻塞的环境须单独评估进程隔离，不声称线程方案提供绝对硬超时。

30 分钟是单次执行安全上限，不是目录必须扫描完成的总期限；整轮累计耗时可超过 30 分钟。默认较短时间片与目录项数上限触发正常让出，下一次恢复游标。扫描、哈希、投影使用独立资源门控，不能让每个用户都开无限子任务；保存检查点时先完成当前提交边界，再释放用户/绑定槽位。

### 3.7 Admin 与 API

保留现有管理员确认与用户 ownership。对账/dry-run 请求改为返回 `202` 和任务 ID，通过状态接口读取结果；不在 Web HTTP 事务内扫描几十分钟。相同绑定的重复请求返回已合并任务；明确冲突的模式请求不得悄悄降级完整校验。

Admin 显示最近运行、用户队列/片段进度、暂停与下次续跑、周期跳过原因及成功快照时间。独立的 `background_reconcile_enabled` 只暂停自动补偿、事件回退及分页后台任务的排队/领取，不关闭总 `filesync.enabled`，因此 targeted 实时路径投影和 outbox 继续工作；明确手动任务仍可执行，运行中的自动任务在当前安全片段结束后等待恢复。完整校验只有独立手动选项，无每周设置；危险操作继续统一确认组件。取消停止未执行批次，不承诺撤销已提交同步；正常 `paused` 显示待续跑而非错误或完成。普通用户绑定对账 API 如存在同步入口，也改接同一执行器，不能保留另一条长事务路径。

### 3.8 可观测与安全

日志只允许 run/绑定 ID、模式、原因、阶段、计数、时长、租约状态和脱敏错误代码。不得记录文件名、相对/绝对路径、文件正文、用户昵称或配置凭据；异常原文仅进入受限诊断日志。

关键指标：枚举/哈希/投影/发布耗时、哈希数量与复用比例、脏路径数量、事务耗时、事件延迟、真实失败/重试次数、片段暂停/续跑次数、整轮累计时长、队列等待与饥饿、活跃跳过次数、基线代次。用户 ID 指纹化；不记录检查点里的路径。日志必须区分周期跳过、正常让出、预算暂停、用户取消、真实故障与每日/临时触发。

## 4. 验证与上线

### 4.1 行为与压力验收

使用合成目录和临时存储，不连接真实用户数据。覆盖首次基线、无变化每日扫描只复用指纹、增改删移、目录类型变更、同 stat 不同内容在完整校验被发现、DB 侧版本变化、冲突阻塞及解除、重叠绑定隔离。

故障注入覆盖：不完整扫描不得删文件；DB 批次回滚不得发布快照；候选文件落盘后/DB CAS 前后崩溃能恢复；事件在扫描、暂停和发布期间到达不会丢失；预算到期保存进度并停止该片段后台工作，续跑不重头扫描；大文件跨片段与中途修改不会混合版本；真实重试不重复加版本、不漏 outbox；dry-run 无业务副作用。

调度验收覆盖跨用户/同用户绑定隔离、有界领取/并发、优先级老化和公平轮转；大用户跨多周期不阻塞小用户。活动验收覆盖周期起止边界、迟到/重复事件、登录聊天不计入、对账投影不计入、多个绑定活动聚合、连续活跃跳过、异常/初始化/手动例外，以及跳过不推进成功快照。`mirror_out` 验收需证明本地活跃不能跳过导出、未变化源文件不会重复复制、复制后重试不产生副作用，且文件库软删除不会静默删除导出目标。

PostgreSQL 集成验收保留 60 秒空闲事务超时，用受控扫描延迟超过 60 秒证明任务仍完成；查询 `pg_stat_activity` 验证扫描阶段无本任务持有的空闲事务。不能用 SQLite 单测替代这项验收。

压力场景至少十万目录项及多用户混合大小任务，记录冷/热缓存遍历、完整哈希与少量差异的实际耗时，不要求一分钟内完成。测试期间 Worker 事件循环延迟 p95 目标低于 200ms，取消/心跳处理目标 1 秒内开始；硬件差异需记录而不是放宽断言冒充通过。用逻辑时钟验证累计超过 1800 秒的整轮经多次片段仍能完成，且每次执行遵守预算；队列用户数增长不能线性增加运行线程数。

定向测试入口包含 `test_filesync_scan.py`（含纯差异计划规则）、`test_filesync_baseline.py`、`test_filesync_jobs.py`、`test_filesync_postgres_lifecycle.py`、`test_filesync_scheduling.py`、`test_filesync_activity.py`，以及现有 filesync 回归；不为已有覆盖的纯计划逻辑另建重复测试文件。前端采用独立任务状态测试和管理员关键路径 E2E，不用源码字符串断言替代行为验证。2026-10-06 当前证据：本地与 devserver filesync 全量均为 115 passed、4 skipped；10 万项扫描压力测试本地通过（71.79 秒）；专用 PostgreSQL 61 秒扫描通过且期间 `idle in transaction` 为 0，并通过 16 用户/48 任务/8 并发 Worker 领取测试。持续扫描压力回归在临时 PostgreSQL schema 与合成存储中通过：4 用户/4 Worker/4,000 文件，冷扫描 16.661 秒、热扫描 0.772 秒且复用 4,000 个指纹、事件循环延迟 p95 1.3ms、哈希期间取消至终态 212.7ms；数值仅描述本机硬件结果，不外推为线上 SLA。管理员预览、确认、取消和解绑路径在 devserver 浏览器使用全拦截合成 API 通过；解绑停用绑定、取消排队任务、请求运行中任务安全停止且不删除已投影文件。devserver 逐绑定灰度和回滚演练仍待完成；测试/代码存在本身不表示整体方案验收。

### 4.2 迁移、灰度与回滚

Alembic 增量增加表/字段，不改用户运行配置，不把旧缓存当作可信快照。先验证迁移可重复运行、已有 journal/冲突副本不损坏，再逐绑定排队首次基线，禁止更新后同步阻塞启动扫描全部用户。

灰度先启用纯扫描/计划 dry-run，对比现有合成环境结果，再启用投影和成功发布。上线记录新增/变化数量、任务原因、预算、数据库事务空闲与 Worker 响应延迟。不得擅自触发 GitHub CI、运行真实数据迁移或修改部署配置。

故障回滚优先暂停新整树调度、保留 targeted 事件同步和 outbox；不自动恢复每日长事务强制哈希。保留新表、journal 与成功代次，避免数据破坏；旧版本不兼容新任务水位时须明确停用后台对账后回滚，不能双执行器并行。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 目录遍历依旧昂贵 | 元数据差异仍非 O(变化数量) | 线程扫描、复用 stat 结果、避免重复 resolve；不取消路径安全校验 |
| stat 未变化但内容变化 | 日增量不能严格检测 | 标脏事件、ctime 提示与手动完整校验；无周期校验兜底 |
| 批次提交而基线未发布 | 下次重复处理 | journal 幂等、File 版本校验与候选代次恢复 |
| 并发事件持续到来 | 快照无法形成稳定水位 | 持久脏路径合并与有界复核；暂停续跑保留旧基线 |
| 线程 syscall 长期阻塞 | 不能保证 1800 秒强杀 | 协作截止并显式报告未退出，必要时评估独立进程 |
| 元数据快照被当成正文备份 | 清理误删冲突恢复文件 | baseline 与正文 snapshots 分离命名、清理只按 manifest 引用 |
| 首次完整基线超过预算 | 从头重扫无法完成 | 持久目录/分块/投影游标；预算暂停是正常续跑，不是重扫 |
| 长期有文件变更的用户持续跳过 | 遗漏事件可能长期未发现 | 显式记录产品边界；异常补偿、初始化和手动不跳过，不暗加周任务 |
| 用户/任务数不断增加 | 线程、内存和 DB 连接膨胀 | 持久排队、有界用户领取、独立 I/O/写入资源门控 |

待确认事项：分批大小、时间片和并发默认值以压力测试调整；分块指纹与存量指纹的算法迁移验证；是否需要固定维护时段（首版沿用持久间隔）；`revision` 是否能可靠覆盖所有 UI/事件写入，不能满足时使用独立 `dirty_revision`。不再把每周周期和整轮 30 分钟限制列为待定方案。
