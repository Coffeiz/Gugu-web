## 1. 背景与目标

### 1.1 现状与问题

当前主要调用链如下：

```text
Files 页面当前目录
  → GET /files?space=...       （当前目录全部 File）
  → GET /folders?...           （当前父目录全部 Folder）
  → store 缓存当前目录快照

跨目录导航 / 非 Workspace 定位 / Markdown 相对路径
  → filesCache.load/refresh
  → GET /files/all + GET /folders/all + GET /files/version
  → 浏览器内存持有全部 File/Folder，随后前端过滤、排序和建立索引
```

因此 `/all` 只是最显眼的入口，不是唯一的无界读取：普通列表、上传时 `all_in_scope`、回收站列表和文件夹内容也会物化完整集合。页面虽有虚拟滚动，但它发生在列表响应抵达之后，无法避免网络传输、JSON 解析、缓存占用和排序成本。规模继续增长时，慢请求、反向代理超时、浏览器内存压力及多个请求并发放大都可能出现。

此外，`/files/version` 每次读取用户文件行的数量和最大时间戳；`/files/tree`、`/files/summary`、`/trash/counts` 也执行精确聚合。它们响应很小，但数据规模大时仍可能扫描大量索引/记录，不能把“小响应”误认为常数成本。

### 1.2 目标

- 所有面向用户、返回 File/Folder/Trash 实体集合的读取都必须有服务端硬上限；没有“返回全部结果”的 API 或前端调用。
- 使用稳定的 keyset/cursor 分页。空目录、首屏、继续加载、刷新和目录切换都保持明确的加载状态；不要求用户先下载整目录。
- 全局缓存改为有界的页面缓存和按 ID 详情缓存；部分缓存绝不伪装成完整缓存。
- 文件名/筛选/排序、选择、上传目录复用、搜索跳转、Markdown 图片和文件链接、项目文件区及回收站均保持语义正确。
- 活动列表页的页面读取和 UI 交互不依赖全库计数/版本扫描；根目录统计采用可扩展的统计投影或等价的有界方案。
- 通过真实 PostgreSQL 查询计划和大规模数据集验证，而不是只验证响应条数或 mock API。

### 1.3 非目标

- 不改变 File/Folder 的事实源、权限归属、软删除、同步投影、配额记账和冲突处理规则。
- 不取消文件同步/管理员对账内部为了正确性而执行的后台完整范围扫描；它们是异步任务，不是文件库用户列表接口。
- 不把全局搜索改造成内容索引；现有每类结果上限保留，确保其内部读取也继续有硬上限。
- 不限制单文件下载、媒体 Range/stream 等按需内容传输；但文件夹打包等集合操作必须有明确资源上限或转为后台任务，不能先把所有元数据/内容装入内存。
- 不在此 PRD 重做通用 SSE、跨模块缓存框架或全部文件操作 API。

## 2. 功能需求

### FR-FS8-001：文件列表默认有界

`GET /files` 接受 `limit` 与不透明 `cursor`，默认页大小为 100，服务端最大页大小为 200。响应统一为 `{items, next_cursor, has_more}`；单页 `items` 数量不得超过请求上限，超过最大值返回明确的 422，不得静默钳制或忽略分页参数。响应不默认包含精确 `total_count`。

原有 `space`、`project_id`、`folder_id`、`workspace_directory_id`、`mind_map_id`、`ext`、`q` 等筛选条件继续由服务端执行，游标只能在相同用户、筛选、排序与 scope 下使用。每次查询仍必须显式附加 `user_id`、活动记录和空间归属约束。

### FR-FS8-002：文件夹列表与全空间查询有界

`GET /folders` 改为分页 envelope；默认/最大页大小与文件列表一致。普通目录浏览只读取指定 `parent_id` 的直属子文件夹，并为本页最多 200 个文件夹返回直属文件数。

移除 `all_in_scope=true` 这种向客户端返回整个空间文件夹树的模式。需要按名称解析上传相对路径时，使用只返回请求路径结果的有界批量路径解析接口；不得以分页客户端循环抓完整个空间树替代旧实现。

### FR-FS8-003：游标顺序稳定且失效行为明确

游标使用 keyset，不以大 `OFFSET` 作为深页方案。每种排序定义确定性的次级唯一键（至少包含实体 ID），相同排序值不得造成静态数据集翻页重漏或重复。服务端校验 cursor 与当前用户、scope、过滤条件、排序键/方向及协议版本一致；篡改、跨 scope 复用或格式不合法的 cursor 返回明确 4xx。

目录发生创建、删除、移动或影响排序字段的更新时，客户端失效相关 scope 的页缓存并从第一页重新取数；在已知实时事件缺口或重连后，不继续拼接旧 cursor。分页不是跨多个 HTTP 请求的数据库长事务快照，不得声称提供该保证。

### FR-FS8-004：排序语义不退化

文件库现有 `name`、`type`、`stage`、`createdAt`、`size`、`id` 排序以及文件夹排序语义迁移到服务端分页排序。排序字段采用白名单和确定性 tie-breaker；前端不得先拿到单页再声称完成全目录排序。根目录/项目状态卡片原有业务顺序保持。

如果某个现有排序不能用可验证的数据库查询计划支持深页，必须在实施前明确给出有界策略（例如仅允许当前目录有限结果排序、后台排序任务或缩减为可索引排序）；不能以全量拉取维持表面兼容。

Phase 1 的迁移 API 使用独立 `/page` 路径，前端迁移后再替换正式列表路径。文件分页必须指定空间，项目空间必须指定项目 ID。`stage` 排序只在项目固定范围、个人空间或 Workspace 空间开放：项目范围内项目名为常量，按 ID 确定顺序；个人/Workspace 按文件阶段名自然序；未提供这些有界 scope 时返回 422。文件夹没有独立的创建时间、大小或阶段排序器，这些字段继续按 ID 排序；文件夹 `type` 排序等价于名称排序。

### FR-FS8-005：回收站实体也分页

`GET /trash`、`GET /trash/folders` 和 `GET /trash/folders/{id}/contents` 对返回的文件/文件夹都实行服务端分页。文件与文件夹可各自使用独立 cursor，但每个响应中每类实体都必须有硬上限；加载、恢复、还原、永久删除等操作仍以确切 ID 和所有权校验为准。

`/trash/counts` 保持轻量摘要语义，不因打开回收站而拉取所有已删实体。清空回收站继续使用现有后台清理任务，不把它改成浏览器端逐条全库下载。

### FR-FS8-006：单实体与目录路径按需解析

保留 `GET /files/{id}` 并增加等价的文件夹按 ID 获取能力。增加 owner-scoped 的位置解析能力，按 File/Folder ID 返回导航所需的项目/空间信息和祖先链，避免用 `filesCache.load()` 还原路径。祖先查询需限制最大深度、检测循环并在归属/路径不一致时失败关闭。

Markdown 同目录、跨目录相对链接与相对图片通过服务端逻辑路径解析；支持一次解析有界数量的引用，返回匹配的文件 ID/元数据。解析只允许在来源文件所属的个人、项目或 Workspace scope 内，`..` 不得逃逸该 scope；不得把逻辑路径解释为宿主机绝对路径，也不得让文件名/路径进入可见日志。

### FR-FS8-007：前端按需加载并保持浏览体验

Files 页面、项目文件区、音频列表和回收站改为首屏加载一页，滚动接近末尾时继续取页；需要总数/加载更多提示时使用摘要数据。现有虚拟滚动继续只负责已加载页的 DOM 窗口化，不承担 API 分页职责。

选择操作明确区分“本页选择”和“全部匹配结果选择”。若保留全筛选选择，服务端需提供带 scope/filter 的选择令牌并在批量动作执行时重新验证；不可通过把所有 ID 下载到浏览器实现。所有批量 ID 接口均有硬项目数上限，超大操作走现有后台任务或另行定义异步作业。

### FR-FS8-008：全局缓存改为有界缓存

`filesCache` 不再提供 `allFiles/allFolders/loaded` 表示“整库已装载”的契约。使用有界 LRU 页面缓存（键至少包含账号边界 epoch、空间、目录、过滤、排序和 cursor）与 File/Folder 按 ID 的详情缓存；设置页面数和总实体数上限。缓存淘汰不能改变服务端事实，也不能把缓存未命中解释为实体不存在。

`ensureFile(id)`、文件/文件夹 ID 卡片、画布引用、项目编辑区按需获取单实体或当前目录页。账号切换时立即清空页面、ID、祖先链和进行中的请求；迟到响应不得写入新账号缓存。

### FR-FS8-009：实时事件只失效相关页面

可从 canonical event 安全判断实体和旧/新 scope 时，更新已缓存 ID 项并失效涉及的目录第一页/后续页；无法判断、批量操作、事件顺序缺口或重连恢复时，只失效当前可见的文件库/项目/回收站 scope 并重取，不触发全库 refresh。

不能仅依赖可能过期或被浏览器缓存的 `/files/version` 响应判断数据新旧。移除为了缓存验证而扫描整个 File 表的热路径；如果需要恢复后的失效水位，使用可靠资源 revision/事件游标或带 TTL 的当前 scope 重新验证，方案必须覆盖 DB commit 与事件发布之间的失败边界。

### FR-FS8-010：统计摘要不退化为全表热扫描

分页响应不查询精确全目录总量。根目录、项目卡片、空间用量和回收站只读取 UI 确实展示的摘要字段。文件/文件夹数量统计必须有可验证的有界成本：优先复用/建立事务一致的按用户、空间/项目和活动/回收站分类的统计投影，采用可重建的后台校准；单页文件夹直属计数仅对当前返回页计算。

统计投影不能在用户读取请求中回退成整库逐行加载；投影短暂落后时返回明确的更新时间/近似状态，或仅在产品确认允许的字段提供近似值。存储字节配额账本与文件数量统计不是同一事实，不得用字节账本冒充文件计数。

### FR-FS8-011：全局搜索和内容读取保持各自边界

现有 `/search` 按 `per_type` 有硬上限，维持该上限及用户归属约束；搜索跳转使用返回的路径/位置元数据或按 ID 查询，不能为了补路径回退到全局文件缓存。文件内容读取、图片缩略图、媒体流仍按单实体 ID 读取。

文件/文件夹搜索跳转必须覆盖个人、项目和 Workspace scope。冷缓存下点击结果时，不得请求 `/files/all` 或 `/folders/all` 来还原路径；应先通过结果携带的位置元数据或 owner-scoped ID 位置解析得到目标路径，再只请求目标目录内容。目标路径/面包屑应先于目录内容显示，并提供明确的目标目录加载状态，不能先展示错误目录或空白区域再延迟跳转。全局搜索结果匹配和结果数量边界不在本需求中改变。

## 3. 技术方案

### 3.1 API 契约与查询

- 建立统一 `PageResponse[T]` envelope（`items`、`next_cursor`、`has_more`），页大小由 API 常量/配置统一限制；客户端不控制最大值。
- Cursor 采用版本化、不可读/不可随意拼接的编码；如签名，密钥只从现有安全配置读取，不能写入日志。即使 cursor 校验通过，SQL 仍按当前用户和 scope 授权，cursor 不是权限凭据。
- 活动 File 默认排序使用稳定 `(created_at, id)`；Folder 使用确定性 `(created_at, id)` 或经查询计划验证的排序。方向与比较运算必须和排序一致，包含空值处理约定。
- 名称、大小、类型、项目阶段等现有排序在 PostgreSQL 上以 `EXPLAIN (ANALYZE, BUFFERS)` 核对。仅在证明缺少索引且收益覆盖写放大后增加复合/部分索引，并提供可在线/低锁风险的 Alembic 迁移策略。
- `q`、扩展名和 scope 筛选均保持在数据库查询内；禁止先取全体再 Python 过滤。模糊 `%term%` 查询的成本单独测量；必要时另立搜索索引方案，不用读取所有 File 的有限切片伪装完整搜索。

### 3.2 导航、上传与相对路径

- 搜索跳转、待打开引用和项目编辑窗口通过 ID 详情/祖先链接口建导航路径。
- 上传目录结构只解析本次上传所需的相对路径节点：批量查询已有路径节点，按需创建缺失节点；目录唯一约束继续作为并发同名保护，不能先取全空间 Folder 清单。
- Markdown 链接/图片以 `source_file_id + bounded relative paths` 为输入，由服务端按 File/Folder 归属、活动状态和逻辑 scope 解析。响应只含本次引用结果，不返回目录索引。
- 文件夹下载/归档如需枚举大量对象，必须流式/分批读取元数据和内容，并有文件数、总字节数或后台作业边界；不属于页面 cursor 的客户端抓页循环。

### 3.3 缓存、虚拟滚动与事件一致性

- Page cache 只缓存已取页，ID cache 只缓存显式加载的实体；`notLoaded`、`loading`、`loadedPage`、`notFound` 分离表达，不能再以全局 boolean 暗示完整性。
- 客户端翻页用请求序号/AbortSignal 防止快速切目录时旧响应覆盖新目录；账号 epoch 继续作为缓存写入的最后一道隔离。
- 排序/筛选/父目录变化产生新 cache key。实时变更只使实体可能所在的旧/新目录失效；因事件缺少完整路径时失效当前 scope 并重新取第一页。
- 本地页缓存总量有硬上限，超过后按 LRU 淘汰；虚拟滚动只作用于当前已缓存/展示数据，滚动加载负责继续取页。

### 3.4 统计投影与版本

- 移除 `/files/version` 以 `count/max(updated_at)/max(deleted_at)` 作为全局刷新水位的用法。
- 目录卡片所需准确计数由可事务维护、可重建的统计投影提供；实施前枚举 ORM 写入、批量 SQL、文件同步 targeted 投影、软删除/还原、迁移和数据导入写入路径，证明每种变化都能更新投影。首选同一数据库事务内的统一写入服务或数据库级机制，不接受依赖 best-effort SSE 增量作为唯一计数来源。
- 对账/重建采用有界后台批次，状态、进度和投影水位可观察；重建期间不能清零或覆盖新写入计数。统计迁移支持从现存 File/Folder 重建，并能在失败后安全重试。
- 如果实现阶段发现需要为所有遗留写入点增加投影维护会扩大到无法验证的范围，先缩减精确计数展示范围并复用现有摘要；不得为了保留 UI 数字重新引入全库列表 API。

### 3.5 迁移和兼容

- 前后端 API 契约、OpenAPI schema、生成类型和全部调用者在同一发布范围内迁移；旧 `/files/all`、`/folders/all` 不得继续返回整库。迁移后可直接移除路由；如需兼容一版旧静态客户端，旧路由只能返回明确的 `410 Gone`/迁移错误，绝不能返回未分页全集。
- `GET /files`、`GET /folders`、Trash 的响应从数组改为 envelope 属于破坏性协议变更；先在仓库全局搜索并迁移 Web、项目弹窗、音频、Mind/画布引用、上传、搜索跳转和回收站的全部消费者，再同时发布前后端。
- `frontend/src/types/api.ts` 是 OpenAPI 生成物，只能在后端 schema 更新后用 `frontend` 的 `npm run gen:types` 生成；不得手改生成文件。生成差异需审阅，避免混入无关 OpenAPI 漂移。

## 4. 验证与上线

### 4.1 行为与安全验收

- API 测试覆盖首/中/末页、空集合、恰好达到页大小、非法/越权/跨筛选 cursor、相同排序值、软删除、多个空间、其他用户 ID、limit 上下界。
- 静态数据集全遍历时，cursor 分页结果与相同 scope 的 DB 预期集合完全一致，无重复、无遗漏；模拟页间插入、移动、删除时，事件失效后从新首屏重载，不继续展示已失效游标链。
- 文件、文件夹、回收站所有列表 API 的任何单次响应均不超过 hard limit；不返回整库数组。全局搜索继续受 per-type 上限限制。
- 上传相对目录查找只返回被请求的路径；跨用户、跨项目、跨 Workspace、软删除目录、重复路径和同名不同父级均验证隔离与正确性。
- Markdown 同级/父级/多级相对链接和图片、路径逃逸、百分号编码、缺失目标、引用数量上限均有行为测试；文件跳转和 Mind 引用在全局 cache 未加载时能按 ID 定位。
- 页面在无 SSE、乱序 SSE、事件缺口、断线重连和账号快速切换时都不会把旧页写入新 scope/账号；请求取消或序号保护通过交互测试验证。
- 根目录统计投影对上传、覆盖、删除、恢复、移动、复制、同步事件、事务回滚和后台重建具有一致性测试；重建与并发写交错不能丢计数。

### 4.2 性能与负载验收

- 在隔离 PostgreSQL 环境至少准备单用户 1,000,000 个活动 File/Folder 混合记录，并覆盖一个超大平面目录、深层目录、多个项目和大量回收站项目；测试数据中不得使用真实用户信息。
- 对每个分页筛选/排序组合保留 `EXPLAIN (ANALYZE, BUFFERS)` 结果。首屏及深页不得发生全量 ORM 物化或随 cursor 增大的 OFFSET；确认索引、行数和 buffer 读取随单页上限受控。
- 目标：每页最多 200 项，响应不含总量时首屏 API 在隔离基准环境 p95 ≤ 500ms；前端网络/缓存保留实体总数有硬上限，连续滚动不会把已淘汰页又累积成整库数组。未达到目标时先修查询/索引，不降低数据正确性或返回上限。
- 统计摘要独立测量；它不能在浏览器打开文件库时触发整表扫描。后台计数重建不得阻塞分页 API，且应有批次/时间预算。
- 对 Markdown 文件中含大量相对图片、项目文件夹内含大量路径、超大回收站及批量上传进行请求数、响应字节、内存和 p95 对比，确保从线性全库下载变成请求目标集合的有界读取。

### 4.3 发布与回滚

- 先完成仓库全调用者迁移、后端 schema/API、生成类型和前端页面的同版本发布；不能先发布只返回 envelope 的后端而让旧前端继续把数组当响应。
- 数据库索引采用经 PostgreSQL 验证的迁移方式；统计表/投影需支持从现存数据重建和重复执行，旧数据不删除、不改 File/Folder 身份。
- 观察分页接口 p50/p95/p99、每页记录数、游标失效率、缓存项数、摘要投影延迟、DB rows/buffers、API 5xx 与客户端加载错误。日志记录 route、页大小、耗时和错误码，不记录文件名、逻辑路径、cursor 原文或聊天正文。
- 若发布后出现分页不完整，先回滚前端到兼容版本并恢复旧列表 API 的临时硬上限实现；不得恢复无限制 `/all`。统计投影异常时可关闭精确计数展示/重建投影，但不能改写 File/Folder 事实数据。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 目录内排序字段未建立合适索引 | 深页仍可能扫描或排序大量行，cursor 不等于自动高效 | 对现有排序逐一跑 PostgreSQL 查询计划；仅添加有实测依据的索引，或明确有界排序策略。 |
| 统计计数维护路径遗漏 | 根目录/项目计数漂移，可能误导删除确认 | 实施前盘点 File/Folder 所有写入路径；投影事务一致、可重建，并以差异对账测试覆盖。 |
| SSE 事件缺少旧/新 scope 或事件丢失 | 页面旧游标继续展示移动前内容 | 对无法精确定位的事件失效当前 scope；重连刷新第一页，不进行全库刷新。 |
| cursor 翻页期间实体变化 | 页面间出现重复或短暂缺项 | 使用稳定排序；变更使 scope cursor 链失效并重取；不宣称跨请求快照。 |
| 客户端一次性“全选”语义改变 | 用户可能误以为只选中当前已加载页或误操作全目录 | UI 明确区分本页/全部匹配；大范围动作采用有界服务端选择 token 或异步任务，并逐项确认危险动作。 |
| 相对路径解析端点被滥用 | 可能越过用户空间或造成高 fan-out 查询 | 按来源实体校验 owner/scope，路径数量硬限制，拒绝 scope 逃逸，严格限制单次查询成本。 |
| 旧静态客户端仍请求旧数组 API | 发布窗口出现 404/响应协议不匹配 | 前后端同版本发布；旧 `/all` 可短期只返回 410，不保留全量兼容行为。 |

待确认事项：实施前由产品确认列表采用“滚动加载更多”作为默认交互；默认页 100、最大页 200 为本 PRD 的初始值，最终可根据 p95 和单项响应体大小调优，但 hard limit 不得移除。`total_count` 是否必须精确实时展示尚未由现有界面语义完全证明；若确认必须精确，应使用事务一致统计投影，而非每次打开页面实时扫表。
