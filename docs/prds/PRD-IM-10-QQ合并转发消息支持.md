# QQ 合并转发消息支持 调查笔记

> 状态：初步调查（代码走查，未放探针、未拿到真实 payload），未评估是否要做
> 创建：2026-08-09
> 关联模块：`backend/agent/gateway/qq.py`、`backend/agent/im/parsers/qq.py`、`backend/agent/im/media_ingress.py`

## 1. 背景

用户反馈：QQ 群里收到一条"合并转发"消息（把多条历史消息打包成一张卡片转发），GuguChat 里没有正常显示图片，只显示一串裸 URL。用户贴出的实际内容形如：

```
[某某的聊天记录]
=== 消息 1 ===
[发送者] 某某
[附件1] 类型:图片 文件名:xxx.jpg 尺寸:691x1540 大小:78.3KB URL:https://multimedia.nt.qq.com.cn/download?...
```

## 2. 排查结论（代码走查，非真实 payload 验证）

这**不是**之前 PRD-IM-9 调查过的"回复引用"（reply-quote）问题——两者是 QQ 完全不同的消息类型：

- **回复引用**：`agent/im/parsers/qq.py` 的 `_extract_quoted`/`_find_quoted_element` 通过 `scene_ext` 里的 `ref_msg_idx` 识别，已有完整处理路径（PRD-IM-9 已验证可行）。
- **合并转发**：全代码库搜索 `转发`/`forward`/`node_id`/`forward_msg` 等关键词**零命中**——没有任何代码识别或解析这类消息。

**推测的根因**（未经真实 payload 验证）：合并转发消息送达网关时，没有被识别成结构化的转发节点列表，upstream（OneBot/NapCat 一类的 QQ 适配器）大概率把整张转发卡片展开成一段描述性纯文本（就是用户贴出的那种 `[发送者]`/`[附件N] 类型:...URL:...` 格式）塞进消息的 `text`/`content` 字段。对咕咕这边来说，这条消息里没有"附件"这个概念，只是一段普通文本——`ingest_qq_media()` 那套下载/暂存逻辑根本不会被触发，因为它不负责从纯文本里挖链接。GuguChat 显示裸 URL，是因为这行内容对系统而言就是纯文本，不是附件引用，符合预期（虽然产品体验很差）。

**这不是一个回归 bug，是合并转发这个 QQ 消息类型从来没被支持过**——是缺功能，不是"引用图片读取失败"。

## 3. 待确认（下一步如果要推进）

同 PRD-IM-9 的做法：先放一个临时探针，在网关收到消息时把疑似合并转发结构的原始 payload（redact 后）落进受限诊断出口（`logs/gugu-diag.log`），拿到真实数据后确认：

1. 合并转发消息在 OneBot/NapCat 原始事件里到底长什么样——是不是真的整体展开成文本，还是有更结构化的字段（比如某个 `message` 数组里的 `forward` 类型消息段）咕咕现在直接忽略掉了。
2. 如果有结构化字段：转发节点里每个图片消息段是否带 QQ 的 `file`/`url` 字段（跟 PRD-IM-9 里"小图"模式类似的可下载链接）。
3. 转发卡片能嵌套多深（转发套转发）——决定要不要处理递归解析，还是只处理一层。

## 4. 非目标（本轮）

- 不在没有真实 payload 验证的情况下直接写解析代码——`_extract_quoted` 当初也是先放探针拿到真实数据才定的方案，合并转发的协议细节现在完全是推测。
- 不跟 PRD-IM-9（引用消息附件复用）合并成一份 PRD——两者触发路径、协议结构都不同，识别逻辑也不会共享代码，值得独立评估、独立决定要不要做。

## 5. 结论

问题成因基本明确（合并转发缺解析），但具体协议细节和实现方案都还没定，需要先放探针拿到真实 payload 才能继续设计。当前只做了代码走查，还没验证。
