## 1. 背景与目标

### 1.1 背景

个人设置中的“显示工具调用信息”开启后，IM Loop 会把工具调用状态发到平台。飞书当前也沿用通用工具状态消息，而助手正文另由 CardKit 流式卡片发送，工具活动与最终回复因此分散在不同消息中。

ZCode 的飞书体验展示了另一种形式：将助手文本和工具活动摘要按运行顺序放入同一张卡片，工具详情可折叠查看，需用户决策的交互仍单独呈现。Gugu 已有统一 Runner 工具事件与飞书流式卡片，可在现有执行链路上增加飞书专属呈现，不需要复制 Agent Loop。

### 1.2 目标

- 用户开启“显示工具调用信息”且使用飞书时，在同一张回复卡片中查看助手回复和工具执行摘要。
- 工具开始和结束事件通过 `tool_call_id` 对应到同一摘要项，并保持与助手文本一致的发生顺序。
- 用户关闭该设置时，飞书严格保持当前回复卡片行为，不增加工具摘要、卡片区块或额外消息。
- QQ、微信及 Web 工具事件行为保持现状。
- 展示失败不影响 Agent Run、工具执行、最终回复持久化和流迭代消费。

### 1.3 非目标

- 不修改 Agent 工具执行、权限、确认门或工具结果语义。
- 不新增第二套 Runner、飞书专用 Agent Loop 或模型请求路径。
- 不修改用户设置的字段、默认值、设置页面或设置持久化协议。
- 不将 `ask_user`、确认请求或其他等待用户输入的交互改造成普通工具摘要；它们继续沿用现有独立交互消息。
- 不改变 QQ、微信的工具状态消息样式，也不改变 Web 的工具事件流。
- 不承诺在飞书卡片更新失败时仍完整展示工具摘要；优先保证 Run 和最终回复不丢失。

## 2. 功能需求

### FR-IM14-1：关闭设置时保持现有飞书行为

当 `show_tool_interactions` 为 `false`（包括用户尚未设置、偏好读取失败并按默认值处理）时：

- 飞书继续使用现有 CardKit 流式助手回复卡片及原有创建、更新、结束和失败回退流程。
- 回复卡片不得出现工具摘要、工具详情容器或因工具事件引起的额外 CardKit 更新。
- 不发送独立工具状态消息。
- Web 仍收到既有工具事件；工具执行、用户确认和最终回复不受该设置影响。

### FR-IM14-2：开启设置时在飞书卡片呈现工具摘要

当 `show_tool_interactions` 为 `true` 且平台为飞书时：

- 每个工具调用以简短摘要显示工具名称和状态；执行中显示运行状态，结束后显示成功、失败或等待确认等已有状态语义。
- 通过 `tool_call_id` 将 `tool_call` 与对应 `tool_done` 合并更新，不能重复追加同一次调用。
- 连续工具事件统一收纳在一个默认折叠的“工具摘要（数量）”外层面板中；外层使用 CardKit 灰色底板和圆角边框形成独立折叠层，面板内每个工具作为轻量条目展示，不再各自嵌套折叠。助手正文打断工具序列时，后续工具活动开启新的摘要组。
- 助手文本和工具摘要按实际事件顺序呈现；多轮工具调用不得被错误合并或重排。
- 工具详情折叠展示，默认卡片内容保持紧凑；展开详情时显示经过脱敏和长度限制的参数/结果摘要。
- 一轮运行中的普通工具活动优先更新同一张飞书卡片，不为每个工具事件单独发送消息。

### FR-IM14-3：保留交互与其他平台边界

- `ask_user`、危险操作确认及其他需要用户输入的交互继续走现有交互消息和恢复流程，不作为普通工具摘要嵌入卡片。
- 用户开启设置时，QQ 与微信继续调用现有 `send_tool_event` 文本呈现，不套用飞书卡片组件。
- 工具事件的 Web 发布不受飞书呈现状态、CardKit 错误或用户设置影响。

### FR-IM14-4：展示内容安全与有界

- 卡片中的工具名称、参数和结果遵循现有出站脱敏规则；不得展示凭据、密钥、令牌或未脱敏异常。
- 工具详情必须限制单项和单卡片总长度/元素数量；超限时截断并给出明确的省略提示，不因大型输出导致卡片更新失败。
- 不在日志中记录工具正文、参数或结果；诊断只记录脱敏后的错误类型、事件类型和卡片操作阶段。

### FR-IM14-5：展示故障不影响业务运行

- 卡片创建或更新失败不得中断 Runner、取消工具、跳过剩余 token 消费或改变已持久化的 Run 结果。
- 最终回复仍按现有飞书流式卡片失败回退契约尽力发送，且不得因“卡片更新失败 + fallback”重复发送最终回复。
- 已开始展示后若卡片不可继续更新，应停止对该卡片的后续写入并完整消费 Run；不得并发创建多张恢复卡片。

## 3. 技术方案

### 3.1 责任边界

复用 `agent/runner.py` 的共享 `run_stream`、`agent/im/loop.py` 的 `on_tool_event` 和现有偏好读取。只在飞书出站呈现层组合回复文本与工具摘要。工具事件仍由 Runner 产生，IM Loop 仍负责按设置和平台选择展示方式，飞书 Gateway 仍负责 CardKit 协议和序列号。

建议每轮飞书回复创建一个短生命周期的卡片呈现状态对象，由 `send_text_stream` 初始化卡片并拥有卡片 ID、元素状态和序列号；同一对象同时接收流式文本与工具事件。工具调用状态按 `tool_call_id` 保存，收到完成事件时更新原项。连续工具活动组成一个外层折叠摘要，容器内部不再嵌套折叠面板；正文出现时结束当前工具组，后续工具调用形成新组，以保持卡片顶层顺序。结构更新与正文流式更新必须串行，并共用同一 CardKit 卡片的单调递增 `sequence`；不得为工具区块另建序列计数器。

仅在“平台为飞书且工具展示开关开启”时创建/连接该呈现状态。关闭开关时不传入工具呈现回调或卡片状态，沿用当前 `send_text_stream` 路径，避免空工具面板、额外更新或视觉变化。其他 IM 平台继续使用 `agent/im/replies.py` 现有文本格式化和发送逻辑。

卡片全量结构更新可能与 CardKit 元素级流式更新竞争。实现需先确定稳定的元素模型和更新策略：正文 token 更新可继续使用现有元素级接口；工具区块变更使用整卡更新或经过验证的元素接口。所有写入必须经过同一串行发送门面和序列号分配器，确保并发事件不会以旧状态覆盖新状态。若 CardKit 当前卡片结构无法安全地增量更新，应选择开启状态下的单一有界更新策略，而不是同时保留互相竞争的两条更新链路。

### 3.2 文件范围

```text

│   │   ├── loop.py                         【修改】依据平台与设置路由工具事件；保留 Web 发布及非飞书发送

│   └── gateway/
│       ├── feishu.py                       【修改】增加可选工具摘要卡片呈现及有序 CardKit 更新
│       └── feishu_tool_summary.py          【新增】维护单轮卡片正文/工具事件顺序、摘要状态和折叠元素
└── tests/
    ├── test_feishu_tool_summary.py          【新增】飞书摘要状态、顺序、序列与安全边界行为测试
    ├── test_streaming_regressions.py        【条件】补充关闭设置时现有卡片/回退行为回归
    └── test_im_replies.py                   【条件】仅当共享工具事件路由需要覆盖时补充非飞书兼容测试
```

用户设置的前后端定义与偏好 API 明确不在本需求修改范围内；Runner、工具执行器、数据库 schema、Alembic 和其他平台 Gateway 均不应因卡片展示而增加专用分支或新数据存储。若实现发现必须修改上述范围，应先更新本 PRD 并说明新增边界。

### 3.3 事件与卡片状态约束

- 工具摘要以 `tool_call_id` 为稳定关联键；缺少关联 ID 的事件不得猜测合并，应按安全、可读的独立摘要处理或省略，并留下不含正文的诊断信息。
- 同一轮运行的文本与工具状态维护确定性顺序；连续工具事件聚合到一个摘要外壳，助手正文隔开不同摘要组；同一工具结束事件重复到达时更新幂等，不重复插入摘要。
- 工具调用详情沿用现有出站脱敏和截断规则；不得为卡片展示直接序列化 Runner 内部对象或异常全文。
- 卡片元素数量、详情字符数和更新频率均需有上限；文本更新继续遵守现有流式节流，结构更新不得形成每个 token 一次的整卡 PUT。
- 卡片展示状态只存于单轮进程内存，不新增持久化表、Redis key 或跨运行恢复协议。

## 4. 验证与上线

### 4.1 自动化验证

- 关闭开关的行为测试必须验证：流式正文、卡片最终化和失败回退与现有实现一致；工具事件不会触发卡片结构更新或独立 IM 工具消息；Web 事件仍发布。
- 开启飞书开关的行为测试必须验证：工具开始/结束按 ID 更新同一摘要、文本和工具事件顺序稳定、重复完成事件不重复展示、卡片更新序列严格递增。
- 安全测试必须验证详情经过脱敏、超长参数/结果和超大事件数受限、原始参数/结果不进入可见日志。
- 边界测试必须验证 QQ/微信仍走既有工具消息、`ask_user` 仍走独立交互、卡片更新失败后 Runner 仍被完整消费且最终回复不重复。
- 在 `backend/` 运行新增测试及相关 IM/流式回归测试；实现后由实施者给出实际命令和结果，不以源码字符串断言代替行为验证。

### 4.2 飞书验收

在测试 Bot 上分别关闭、开启个人设置验证：

1. 关闭时，对比改造前行为：回复仍只有现有流式助手卡片，卡片布局及完成状态不变化；Web 工具调用显示仍正常。
2. 开启时，触发至少两次工具调用并让助手在工具前后输出文字，确认一张卡片内顺序、状态更新和折叠详情正确。
3. 覆盖工具失败、需要确认的操作、CardKit 创建失败和中途更新失败，确认交互及最终回复符合现有契约。
4. QQ/微信开启同一设置后，确认工具状态消息与改造前一致。

仅在自动化测试通过且测试 Bot 验收通过后启用该能力；不新增全局默认开启或未经用户确认的设置迁移。回滚时可恢复飞书现有独立工具消息呈现，用户偏好字段保持不变。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| CardKit 整卡更新和元素级流式更新争用序列或覆盖状态 | 正文丢失、卡片回退或出现序列冲突 | 所有卡片写入由单一状态对象串行调度，共享单调序列；关闭开关路径不触碰新调度器。 |
| 工具事件与文本 token 的到达时序不一致 | 卡片内容顺序与实际运行顺序不符 | 在共享 Run 消费上下文中维护单调事件顺序，并为交错文本/工具事件增加行为测试。 |
| 工具参数或结果包含敏感内容、体积过大 | 凭据泄漏、卡片超限或更新频繁 | 复用现有脱敏格式化，详情折叠、分项和总量限长，限制结构更新频率。 |
| 卡片展示链路失败 | 工具摘要不完整 | 展示故障与 Runner 解耦；完整消费 Run 并按既有最终回复回退契约发送，不并发创建恢复卡片。 |
| 默认关闭行为被实现改动意外影响 | 所有未开启用户的飞书体验发生变化 | 关闭路径保留现有发送调用和卡片结构，并以行为测试锁定无工具事件卡片更新。 |

待确认事项：无。卡片更新接口与序列约束应在实施前通过现有代码和测试 Bot 验证；若发现当前 CardKit 模式不能安全支持交错区块，应先更新技术方案，不得静默改变关闭状态的行为。
