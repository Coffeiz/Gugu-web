# PRD-IM-17 · 群聊注意力算法 v3.0 草案

> **状态：讨论草稿，不是生产实现基线。** 本稿先冻结近期话题相关性算法，作为 v3.0 的 Topic 子算法；Cold/Topic 情景分数、权重、门槛和运行策略仍待回放验证。确认前不据此改写正式 PRD 或生产 scorer。

## 1. 目标与当前问题

v3.0 拟把群聊注意力拆成两个情景：

- **Cold**：咕咕没有有效的近期话题锚点，只根据当前消息的召唤、提问等情景特征计算分数。
- **Topic**：咕咕有有效的近期话题锚点，同时考虑固定的 Topic 相关性分和当前消息的情景分。

当前基础意图分类可能漏掉自然召唤，例如「咕咕看吧」。单纯依赖固定请求词表会把「看」等动词漏在外面；只凭「咕咕」出现也会把长篇转述或第三人称讨论误当成召唤。v3.0 需要结合主体指向、动作、问句结构及其在完整消息中的位置，并通过语料回放校准。

用户提出取消咕咕主动参与的频率限制。草案按此记录为设计方向；上线前仍需明确它指产品侧主动额度/间隔限制，平台自身限流仍然存在。`choose_no_reply` 和明确收件人排除等行为边界继续保留。

## 2. 不变部分：近期 Topic 相关性算法

本节先按此前讨论冻结。它计算「当前消息是否延续咕咕最近参与的话题」，不判断消息是否值得主动回复。

### 2.1 可信锚点和窗口

取当前消息到达前，**同平台、同 Bot、同群**最近一条已被平台接受、对用户可见的咕咕会话最终消息作为锚点 `b*`。工具状态通知不作为会话最终消息。没有可信锚点，或锚点年龄达到 600 秒，Topic 分数为 0。

窗口最多包含锚点之前的 5 条群消息、锚点本身、之后最多 5 条且早于当前待评消息的群消息：

```text
W11(b*) = {b-5, …, b-1, b*, b+1, …, b+5}
```

窗口里的其他群成员消息也参与匹配。按时间排序；数据不足时使用现有可用消息，不跨平台、Bot 或群取数。其他成员的消息不会刷新 Topic TTL；只有咕咕下一条可信、已接受的会话最终消息建立新锚点。

### 2.2 文本相关性

先对文本做 Unicode NFKC、大小写折叠，并移除标点、空白和符号。

对当前消息 `m` 和窗口候选 `x`：

```text
C(m,x) = M(m,x) / |m|
```

`M` 是非重叠匹配块的共同字符数，分母是规范化后的当前消息长度。

```text
P(m,x) = 1 - exp(-max(0, L(m,x) - 3) / 4)
RCP(m,x) = 0.5 * C(m,x) + 0.5 * P(m,x)
```

`L` 是最长公共连续片段长度。

另计算局部编辑相似度：

```text
E(m,x) = max over contiguous a ⊆ m, b ⊆ x, 3 ≤ |a|, |b| ≤ 12:
         1 - levenshtein(a,b) / max(|a|, |b|)
```

没有符合长度的片段时 `E=0`。当前提案不增加 `E` 硬门槛。Topic 相关度取窗口内最高值：

```text
Rtopic(m) = max over x ∈ W11(b*) of max(RCP(m,x), E(m,x))
```

### 2.3 Topic 时间衰减与分数

沿用固定 600 秒硬 TTL、360 秒半衰参数：

```text
g(t) = (2^(-t/360) - 2^(-600/360)) / (1 - 2^(-600/360)),  0 ≤ t < 600
g(t) = 0,                                                       t ≥ 600
```

`t` 是当前消息与锚点 `b*` 的秒数差。已有讨论中的 Topic 分数为：

```text
Stopic(m) = 100 * Rtopic(m) * g(t)^0.25
```

此公式、窗口、相似度和时间参数是本草稿中暂时冻结的 Topic 模块。若之后修改其中任何一项，应单独记录版本差异及回放结果。

## 3. v3.0 情景分数：待设计和校准

Cold 与 Topic 共用同一套情景特征，区别在于是否叠加 Topic 分：

```text
Scold(m)  = Scenario(m)
Stopic_v3(m) = Combine(Stopic(m), Scenario(m))
```

建议将情景特征至少拆成下列可解释信号，而不是由单个问句/动作词决定：

| 信号 | 含义 | 例子 / 边界 |
| --- | --- | --- |
| `subject` | 消息是否把咕咕作为对话对象，包括昵称、原生 @、明确的第二人称呼叫 | 「咕咕看吧」有主体；引用里提到咕咕不自动算主体 |
| `action` | 是否包含对咕咕的召唤、查看、回答、解释、检查等请求动作 | 「看」「出来」「回答一下」应按上下文和作用对象判断 |
| `question` | 是否存在可回答的问题结构或求助意图 | 问号不是必要条件；反问、感叹、转述需降权或排除 |
| `pairing` | 主体、动作、问句是否在同一分句/局部语义范围内形成关系 | 长消息开头点名、末尾出现无关动作不应简单相乘 |
| `length` | 完整当前消息长度对稀疏特征的归一化影响 | 长消息里只提一次咕咕应弱于短而明确的召唤 |
| `negative` | 明确对象是其他人、第三人称/引用、结束语或无实质反应 | 结构化收件对象与用户消息正文应分别处理 |

### 3.1 待比较的长度归一化

用户提出的初始形式是：

```text
Score ≈ [主体特征 + 动词特征 + 问句特征] / 完整对话长度 * 词权重系数
```

它能表达「长消息里只出现一次称呼，注意力应降低」，但直接除以全文长度有明显风险：同一条有效请求只因补充背景或引用变长，就可能被压到门槛以下；不同特征的量纲也不一致。建议 mock 对比以下方案，不在本稿预设权重：

1. **线性密度**：特征命中加权和除以消息长度，严格反映点名密度，但对长文本很敏感。
2. **软长度惩罚**：特征先按局部语义关系加权，再乘一个有上下限的次线性长度因子（如平方根或对数归一化），避免长背景文本无限压低明确请求。
3. **局部分句评分**：逐分句计算主体/动作/问句组合，再以最高分为主、全文长度只做轻微惩罚；可降低「全文任意位置凑齐关键词」的误触发。

建议优先验证第 3 种，另以第 1、2 种作对照。`subject + action` 必须允许在没有问号时形成召唤，因此「咕咕看吧」不能因为 `question=0` 被压成无效分。

### 3.2 冷热组合方式（未定）

Cold 使用情景分本身。Topic 状态要把 Topic 相关性和当前情景共同考虑，但组合公式仍需通过算例决定。候选包括：

```text
加法封顶：  min(100, Stopic + λ * Scenario)
加权和：    wT * Stopic + wS * Scenario
证据取强：  max(Stopic, Scenario)
```

加法直观，但容易让 Topic 与「点名/问句」对同一证据重复加分；乘法会重新造成任一低系数压死另一通道的问题。建议先用代表性场景比较加法封顶和局部分句的「证据取强/有限加成」，再决定是否需要权重。当前不确定 `λ`、`wT`、`wS`，也不沿用旧意图值或旧门槛作为 v3.0 已定参数。

## 4. 结构规则与运行边界

- 原生、可信的 @ 咕咕可继续作为结构性 DIRECT；明确发给其他成员或 Bot 的消息不得被正文相似度救回。
- Topic 相关性是历史话题证据，不等同于召唤；普通陈述是否允许参与由 Cold/Topic 情景分和最终门槛决定。
- 取消产品侧主动回复频率/间隔额度是本版方向。仍保留结构性权限边界、重复消息幂等、平台自身限流处理，以及 Agent 的 `choose_no_reply`。
- 模型是否允许自主不回复、各模式门槛是否继续存在、主动回复失败如何结算，需和评分公式分开决策。
- 可观测性记录分数、特征类别、Topic 分数、情景分及决策结果；不得记录原始聊天正文或可反推出正文的片段。真实消息的词权重和分桶评估只能在获授权的明文调查环境中进行，导出的报告需脱敏。

## 5. v3.0 回放测试集草案

先覆盖边界，不先追求单一准确率：

| 情景 | 需要验证的结果 |
| --- | --- |
| Cold：「咕咕看吧」 | 主体 + 查看动作可构成召唤，不要求问号 |
| Cold：「咕咕看吧？」 | 召唤与问句可叠加，但不能重复计算同一证据 |
| Cold：「咕咕看吧，我等他自己看」 | 第二分句语义可能否定/转向，不能只用全文词项命中 |
| Cold：长消息只在引用/转述中提到咕咕 | 降权或排除，不由长度公式单独决定 |
| Cold：无称呼的明确群体提问 | 问题通道可独立贡献分数 |
| Cold：短反应、纯陈述、反问/打趣 | 不因标点、问句词或单个动作词误升格 |
| Topic：「他哪会翻跟斗」 | 保持现有窗口、C/P、局部编辑距离、时间衰减结果不变，再测试情景组合影响 |
| Topic：同话题后提出新公开问题 | 不让旧 Topic 分数压制独立的新请求 |
| Topic：长篇无关消息只复用一个三字片段 | 测量局部编辑度量误命中和组合后的误触发 |
| 边界：@ 其他成员、可信引用对象为其他人 | 结构排他优先，不能被高 Topic/Scenario 分数覆盖 |
| 边界：同一入站消息重复、并发处理、平台发送失败 | 即使取消频率额度，仍保持幂等和一致出站 |

Mock 阶段需同时列出命中特征、局部分句、长度、Cold 分、Topic 分、最终分和门槛，明确哪些值是人工假设。真实语料回放再建立正负样本标注，报告误触发与漏触发分桶。

## 6. 尚待讨论的决策

1. 召唤、提问及普通对话分别包含哪些特征；请求动词词典如何维护。
2. 主体/动作/问句的权重、同一分句的配对规则、否定和转述的惩罚方式。
3. 完整对话长度指当前单条/批次的规范化字符数，还是有边界的上下文长度；是否用软长度归一化。
4. Topic 与 Scenario 的组合公式、门槛及现有 Quiet/Natural/Active 模式如何映射。
5. 「取消频率限制」的确切范围；本草案暂按取消产品侧主动预算/间隔限制理解，不取消幂等和平台发送保护。
6. 允许无 @ 的明确召唤走 DIRECT，还是走高分情景通道；两者在权限、预算和诊断上的语义需一致。

这些问题确认并完成合成回放后，再将选定规则迁入正式 PRD 并实现；目前生产代码与 v2.5.8 实施基线不因本草案自动改变。
