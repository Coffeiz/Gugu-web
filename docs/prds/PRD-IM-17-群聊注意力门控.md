# PRD-IM-17 注意力门控算法 v3.0.6（延迟 ASK 观察版）

**文档状态：** 当前实现基于 v3.0.5 的评分规则，新增开放 ASK 延迟介入状态。ASK 分数、模式门槛及其他注意力通道不变；本次实现尚未部署，本文不代表真实群聊准确率或生产运行验收。
**日期：** 2026-10-31
**范围：** 群聊消息进入 Agent Run 前的确定性注意力判断，不增加额外 LLM 调用
**设计取向：** 提高自然参与召回；接受适度话题误关联；由 Agent 的 `choose_no_reply` 负责最后的发言判断
**验证边界：** 合成回归验证规则和数值，不证明真实群聊标签准确率；此前回放报告仅作设计依据，不将自动过线数当作真阳性。本文保留通用基础词根，并显式补充短回应拒绝侧规则。

| 显式召唤取消 | 当前 Bot 的结构化 @ 会在所有路由模式下取消旧开放 ASK；已排队的旧唤醒也须识别取消水位并丢弃 | 不能依赖 scored 注意力分支才取消；其他 Bot 的 @ 不取消 |
| 恢复会话 | 待处理项保存原 IM `session_id` 与原消息批次；恢复 Run 显式复用该 session | 延迟任务是新的 Agent Run，但必须延续同一群会话历史，不创建孤立会话 |
| 最终出站回执 | 提交投递时无条件登记 `delivery_id`、`source_attention_kind` 与接收成员；最终正文及摘要为可选字段 | 只有平台接受的合格最终回复才建立成员 180 秒索引；工具过程消息不激活成员 |

等待截止时间（毫秒）：

`due = min(start + 180s, max(start + 60s, latest_ask + 60s, last_non_gugu_activity + 30s))`

到期时，如果 `now - latest_ask < 60s` 或 `now - last_non_gugu_activity < 30s`，且已经达到 `start + 180s`，则取消待处理项；否则按上述等待截止时间继续等。

### PENDING_ASK 生命周期与路由

1. 先执行原有硬路由。DIRECT、可信 CONTINUE、CAP、MEMBER_ACTIVE 等独立准入不等待；被明确排除或纯短回应的消息不登记 ASK。任何路由识别到当前 Bot 的结构化 @ 时，均立即取消已有待处理 ASK，并使已排队的旧唤醒失效。
2. 仅在 QUIET/NATURAL/ACTIVE 等 scored 模式中，当前消息的生产决策为 `PROACTIVE` 且 `scene_type=ASK`、未明确指向咕咕时登记待处理项。此时即使 TOPIC 融合分已过线，也不得提前启动 Run。AUTONOMOUS 完全沿用原行为。
3. 同群等待期间的开放 ASK 合并进已有待处理项，最新 ASK 更新 `latest_ask` 和唤醒主体；`start` 不刷新，因此最多等待 180 秒。普通群消息不会被 C/P 分类器判为“回答”，也不会直接删除待处理项。
4. 每条入站群消息均参与活动观察。仅比较 `platform_user_id` 与当前 `platform_bot_user_id`：相同则是咕咕自身消息、不重置静默；不同则重置静默，包含其他 Bot。身份字段缺失时按非咕咕活动处理，避免误判为静默。
5. 等待中的群消息继续按原被动路径落入会话历史。登记时保存原 IM `session_id` 和来源消息批次；Worker 到期时用稳定唤醒键重新送入原有 IM 入站/注意力 Run 路径，保留原始事件 ID 并复用已落库行；评分以到期重入时的最新上下文、当前群模式重新计算。恢复会启动新的 Agent Run，但必须显式沿用原 session。
6. 到期复评分未过当前门槛则结束待处理项，不强制 Run。进入 Run 后 Agent 可读取观察期完整群聊上下文，并由 `choose_no_reply` 判断问题是否已有人解答或已过时。本版不实现文本相似度回答分类，也不据普通消息自动取消待处理项。
7. Redis 暂存时长覆盖最大等待周期；Worker 重启后继续处理。入队成功与状态清理之间故障时，以稳定唤醒 ID 幂等重试。一个群同一时刻只保留一个合并待处理项。

| 验收情境 | 预期介入时机/结果 |
|---|---|
| 开放 ASK 后群内没有新消息 | 满 60 秒后介入 |
| 20 秒时出现任意非咕咕消息，之后安静 | 最早在该消息后安静 30 秒且 ASK 满 60 秒时介入 |
| 其他 Bot 在群内发言 | 与普通成员消息一样重置 30 秒静默窗口 |
| 咕咕自身消息回流 | 不重置静默窗口 |
| 群聊持续到首个待处理 ASK 的 180 秒上限仍未静默 | 取消待处理项，不补发过期回答 |
| 等待期间有人回答，但群随后安静 | 到期后把完整上下文交给 Agent，由它选择回答或 `choose_no_reply` |
| 未点名咕咕的 ASK 不足当前模式门槛 | 不创建待处理项；保持原评分结论 |
| 显式 @ 咕咕、CAP 或 MEMBER_ACTIVE 命中 | 保持原立即准入路径，不等待 |

## v3.0.5 评分修订（当前评分基线）

| 项目 | v3.0.5 实验决定 | 边界 |
|---|---|---|
| CAP 请求结构 | 动作与能力对象必须处于同一顶层子句中的当前请求结构；请求前缀必须紧邻操作结构。裸动作后接陈述谓语、完成事实、计划、评价与转述不准入 | 不靠长负面短语表补漏；不切下子片段绕开整句的负向证据 |
| CAP 强弱 | 明确请求框架或对象前置操作作为 strong；独立祈使作为 weak。两者均由结构判断决定准入 | 本版不按 CAP 原文位置加权；仅记录 strength、区间与位置权重供后续回放分析 |
| ASK 长文位置权重 | 长度 `L≤200` 时权重为 1；`200<L<800` 平滑启用 U 形权重；`L≥800` 使用完整 U 形权重。每个弱问句独立计算，再取最高加权 ASK | 明确以当前 Bot 为受话对象的问句不降权；代码和引用屏蔽后保留原文偏移 |
| ASK 证据与公式 | 明确疑问算子/请求结构按现有具体性规则给强证据；仅靠问号或疑问语气给 `Q=0.85`；问号不能单独把否定劝告升级为提问；否定劝告以「吧？」收尾且无独立疑问算子时 `Q=0`。`α(L)=clamp((L−200)/600,0,1)`；`w(p,L)=1−α(L)[1−(0.55+0.45|2p−1|)]`；`P(u)=0.65` 仅用于以 `。` 结尾且没有明确发问框架的问句，其余为 1；`A_ask=0.90×max_u(Q(u)w(p_u,L)P(u))` | `p` 使用问句子句中心在可见正文中的相对位置；`L` 为屏蔽代码/引用后的非空白字符数；标点按单个子句判断。弱问句仍按现有分数门槛处理；延迟 ASK 不在本修订范围 |
| 其他通道 | CALL、TOPIC/C/P/E、MEMBER_ACTIVE 180 秒、DIRECT、CONTINUE、融合公式和工具权限保持 v3.0.4 语义 | 不新增频率预算，不把位置权重扩展到其他通道 |
| 诊断 | 沙盒和诊断日志增加 ASK 原始分、位置权重、标点权重、加权分、原文区间，以及 CAP 强弱、区间、位置参考值 | 只记录数值、偏移和规则码；不记录匹配正文 |
| 回放边界 | 覆盖长文中部弱问句、首尾问句、多问句、句号弱问句、明确发问结构、标点相邻子句、明确中部请求及 CAP 陈述/转述/计划反例 | CAP 长文弱请求的准入率先通过位置诊断观察；本版不改变其准入条件 |


## v3.0.5 合成回放验收重点

1. 3600 字量级长文中的中部弱问句：原始 ASK 为 `0.90`，完整位置权重约 `0.55`，不带句号时加权 ASK 约 `0.495`；短消息不受位置影响。
2. 首尾弱问句保留较高分；多问句仍取最高加权证据，诊断区间应落在对应原文位置。
3. `为什么延期。` 的 ASK 为 58.5 分；`为什么延期？`、无标点的 `为什么延期` 与明确发问的 `请问为什么延期。` 保持原分。单靠问号的普通表达为弱问句（`Q=0.85`）；中部句号弱问句同时乘位置与标点权重，约为 32.2 分。
4. `为什么延期？我觉得主要是资源问题。` 中第一句仍按问号计分，不被整条消息末尾的句号降权。
5. `这种天气就不要出来玩了吧` 和 `这种天气就不要出来玩了吧？` 都不构成 ASK；问号不能把否定劝告升级为提问。`天气不错吧？`、`我们明天出去玩？`、`在吗？` 属弱问句；`这是什么游戏？`、`为什么项目延期？`、`要不要出门？` 保留强问句。
6. 中部明确指向咕咕的提问及 CAP 明确操作请求保持高召回。
7. 「创建项目需要注意权限」「用户反馈请问如何创建项目」及完成、计划、评价、转述结构不得被 CAP 放行。
8. 「文档中创建项目需要注意权限」等对象前置的说明句不得因“文档中”误认为操作宾语。
9. CAP 位置参考值目前仅作诊断；待结构修复后的真实回放仍出现弱请求误准入，再单独评估位置准入约束。

## 0. 版本决策与非目标

### 0.1 已确认的决策

1. **两套情景路径：** COLD 只计算当前消息的情景分；TOPIC 计算当前消息的情景分与近期话题分并融合。COLD 指「Bot 当前没有有效话题锚点」，不是群成员都不发言。v3.0.3 在这两条评分路径前另有独立的 MEMBER_ACTIVE 续聊资格。
2. **情景只有两大类：** 召唤（CALL）、提问（ASK）。其他情景（抱怨、主动展示、纯媒体等）先不加入正向评分。
3. **词表只允许通用基础词根、代词和语法标记。** 禁止将「看吧」「帮我看看」「看看这个」「怎么解决」等整句/固定触发短语加入词表。
4. **v3.0.4 长文本基线（历史）：** 情景分只看顶层子句，不按文档内字符距离扣分。v3.0.5 对弱 ASK 引入长文位置权重，按本节开头的实验修订覆盖此条；CALL 仍不做位置衰减。
5. **TOPIC 保留既定主干：** 群级最后一条可信出站消息前后最多各 5 条；`C=M/|m|` 保留非对称定义，E 仅处理有效的真实局部编辑（`1≤d≤2`）；窗口最大值与 600 秒 TTL、时间衰减指数 0.25 不变。对称 C 仅作为 A/B 对照。
6. **融合：** `S = 100 A`（COLD）；`S = 100 (A + T − AT)`（TOPIC）。
7. **取消频率限制：** 不设主动发言次数预算、最短间隔、群忙惩罚、最近出站扣分；保留按消息 ID 幂等、结构性收件人保护、运行时资源保护和 `choose_no_reply`。
8. **实验模式门槛：** QUIET=85、NATURAL=65、ACTIVE=55、AUTONOMOUS=保留无分数门槛的自主模式（仍执行硬路由与安全校验）。在 COLD 的当前离散意图档位下 **NATURAL 与 ACTIVE 完全同效**：任何非零 CALL/ASK 最低 73.6，均过 65/55；不能宣传 ACTIVE 在 COLD 更容易参与。
9. **群级 TOPIC / 成员级 CONTINUE：** TOPIC 允许 A 发起、Bot 回复、B 接话；可信 CONTINUE 仍基于成员/原生回复关系。明确指向其他人的消息优先 EXCLUDED。
10. **不得恢复频率或群忙惩罚：** 保证硬路由、正向证据有效性和消息幂等；并发过载由运行层处理，不得作为注意力分数的暗扣。
11. **纯礼貌/反应单独治理：** 只对精确匹配的独立、无新意图短回应提供明确的 PASSIVE 规则；原生 DIRECT 和确有新请求的 CONTINUE 不被短词子串截断。
12. **数据与性能优先于公式调参：** 评分只依赖可信出站事实；合成回归通过不代表生产 CPU 预算、真实标签准确率或部署状态已通过。

### 0.2 非目标

- 不在门控阶段完整理解反讽、隐喻、复杂省略或对话语义。
- 不重做 RAG、分词、IDF、聚类、话题摘要或训练意图分类器。
- 不对长期历史建立额外的 100 条 Bot 回复兴趣检索；v3.0 的 TOPIC 只使用指定局部窗口。
- 不把「出现 Bot 名称」直接当作召唤，也不把「出现问号」直接当作完整提问。

## 1. 输入数据契约

### 1.1 单条消息 `m`

至少需要：

| 字段 | 含义 | 信任要求 |
|---|---|---|
| `event_id` | 唯一入站事件 ID | 来自可信消息队列 |
| `group_id` | 群 ID | 平台适配层提供 |
| `sender_id` | 发送者 ID | 平台适配层提供 |
| `received_at_ms` | 服务端接收时间 | 可信时钟或流事件 |
| `raw_text` | 完整当前消息 | 用户数据，不可信指令源 |
| `segments` | 文本、代码块、引用、转发、附件等结构片段 | 有平台原生结构时优先采用 |
| `mentions_bot` | 是否原生 @ 当前 Bot | 不得从文本猜测为原生 @ |
| `mentions_others` | 原生 @ 其他成员/Bot 列表 | 同上 |
| `reply_to_id` / `reply_target_sender_id` | 原生引用/回复目标 | 必须可验证归属 |
| `sender_is_bot` | 是否是 Bot 自己发出的消息 | 可信标记 |

### 1.2 话题快照

- `outbound_receipts`：当前 Bot 在该群已被平台确认接受的实际出站消息。生产实现从出站投递账本读取短期接受回执及最终载荷正文；正文须来自实际交付平台的不可变载荷。出站消息级事实字段：`platform, bot_id, group_id, platform_message_id, accepted_at_ms, final_sent_content, run_key, status`；正文来自出站 `_flush` 时实际交付给平台的不可变载荷，每条分段出站各自写一条，不能把助手内部总结、工具日志或未发送草稿误写入。对已发送但正文缺失的旧记录，TOPIC 不得猜测补齐。
- `group_history`：依照可信事件顺序排列的群消息；能够定位出站锚点前后各 5 条。出站锚点必须在同一 Bot、同一群；TOPIC 话题范围是**群级**，候选包含不同普通成员的消息，不要求每位成员曾亲自与 Bot 互动。
- `snapshot_complete`：窗口是否可信、是否存在缺失页或未知引用归属。窗口不完整时允许 COLD，但不使用无法证实的 TOPIC 候选。
- `aliases`：运行配置中的本 Bot 称呼，例如「咕咕」「gugu」，按群配置变化；**不属于固化自然语言词表**。
- 出站回执还提供 `recipient_sender_id` 与 `source_attention_kind`，仅在平台确认接受最终答复后用于 MEMBER_ACTIVE。工具通知的来源类型为 `tool`，不能激活成员窗口。
- `topic_compare_units`：从候选消息提取有效聊天文本片段/分句，附件与大段代码不被当作单独的普通群聊内容；C/P 的当前消息与窗口历史比较必须记录使用的是完整消息还是哪一个比较单元，防止用 300 字或 1000 字文档直接与一句话做双向长度惩罚。

### 1.3 判定结果

内部判定返回：`kind`（DIRECT / CONTINUE / CAPABILITY_ACTION / MEMBER_ACTIVE / PROACTIVE / ALLOW_RUN / PASSIVE / EXCLUDED）、`score`（0—100，可为空）、`state`（COLD/TOPIC/MEMBER_ACTIVE/CAPABILITY_ACTION）、`scene_type`、`scene_score`、`topic_score`、`anchor_event_id`、`topic_match_event_id`、匹配片段长度、`reasons`、`threshold`。匹配明文只在内存计算，不进入常规日志或持久化诊断。

### 1.4 独立能力操作召唤 `CAPABILITY_ACTION`

CAP 仅判断消息是否值得启动 Agent Run，不负责判断受话对象，也不负责选择或授权工具。算法为：

\[
\boxed{CAP(m)=V_{action}(m)\land O_{capability}(m)\land K_{request}(m)}
\]

- `V_action`：命中 CAP 专属通用动作词表；它与 v3.0.2 的 `_ACTION_ROOTS` 分开维护，不能改动 CALL/ASK 评分，也不建立「某能力允许哪些动词」的关联矩阵。
- `O_capability`：命中显式产品能力名词及别名。当前包括项目/任务、定时任务/提醒、日历/日程、笔记/记录、画布、文件/文件夹/文档/附件、技能/Skill、联系人、邮件、终端/命令及网页搜索等。名词按最长项优先，并保留区间，动作词与对象区间不得重叠，例如「定时任务」里的「定」不能同时作为动作词。
- `K_request`：通过顶层子句和操作关系识别当前请求，支持动作在对象前（「那定个定时任务」「帮我创建项目」「整理文件」「给我设置提醒」）及对象前置（「把笔记删掉」「在画布里画一下」「给项目加个任务」）。仅对完整顶层子句判定，不把空白片段重新当作独立祈使句，以免切掉完成、计划、评价或转述等上下文；群聊用空格断句时，由整句规范化与句首承接词识别兼容（「好吧 那记录个日程吧」「那么记录个笔记吧」）。句首可连续剥离「那么」「好吧」「对了」等承接词，不改变 CALL/ASK/TOPIC 的分句规则。排除已完成事实、个人计划、功能评价和转述；否定的创建/修改请求不命中，明确取消/停止请求可命中。
- CAP 不区分「小北帮我整理文件」和对咕咕本人的请求。纯文本受话对象交给 Agent 结合上下文判断；结构化 `@` 他人的硬排除仍优先。群成员之间的操作请求可进入 Run，由 Agent 决定回复或静默。
- CAP 命中返回 `kind=CAPABILITY_ACTION`、`reason=capability_action`、无评分门槛，并独立记录原因。它不改变工具权限；进入 Run 不代表获得执行授权，工具调用仍由代码侧注册、归属、权限及确认门控制。群成员没有操作权限时，Agent 只能理解、回应或选择静默。
- 不确定或未命中的消息继续走既有 `MEMBER_ACTIVE` 或 v3.0.2 CALL/ASK/TOPIC。

能力注册表是显式维护的识别元数据；工具名仅用于与产品能力保持一致，既不从工具描述生成名词，也不代表这些工具对当前群聊可用或已获授权。

| 能力 | 名词/别名 | 对应工具名（维护核对用） |
|---|---|---|
| 项目/任务 | 项目、项目任务、任务项、待办、待办事项、阶段 | `list_projects`、`create_project`、`update_project`、`archive_project`、`delete_project`、阶段管理工具、`get_upcoming` |

## 2. 总执行顺序与数学总式

**先硬路由，再双通道评分。** 不能先计算高相似度、再让它覆盖明确发给其他人的消息。

1. 校验数据结构、去重，排除本 Bot 自己的回声或无效事件。
2. 判断原生 @ 当前 Bot：`DIRECT`，可直接进入 Run（不受情景门槛限制）。
3. 判断明确发给其他成员/Bot 的原生 @ 或可验证原生回复：若未同时原生 @ 当前 Bot，`EXCLUDED`。
4. 判断可信回复当前 Bot 的结构性续聊：若包含新问题、请求或有内容的续聊，`CONTINUE`；仅「收到、谢谢、哈哈」等纯礼貌反应不自动触发。
5. 排除空消息、纯短回应及裸问号；这些消息不进入 TOPIC 搜索，也不命中 MEMBER_ACTIVE。
6. **CAP 检查：** 若同一顶层子句同时含有不重叠的通用动作词、产品能力名词和当前请求结构，返回 `CAPABILITY_ACTION`，直接允许进入 Run，不进入分数比较。
7. **MEMBER_ACTIVE 检查：** 在同一 `(platform, bot_id, group_id)` 范围内，查找目标发送者最近一条已 ACCEPTED 的最终答复；若 `0 < message.received_at_ms − accepted_at_ms < 180000`，返回 `MEMBER_ACTIVE`，直接允许进入 Run。消息必须晚于已接受时间；窗口不因成员单独发言刷新。
8. 对未命中 CAP 和 MEMBER_ACTIVE 的消息计算情景值 `A(m)`。
9. 查找最新的可信、已送达 Bot 出站锚点；有效则计算 `T(m)`，否则 `T=0`。
10. 用双通道公式得到 `S(m)`，对照模式门槛。
11. 评分过线只意味着**允许**进入 Agent Run；Agent 可不回复。CAP/成员准入同样不授予工具权限。取消频率限制不意味着绕过消息幂等或基础安全校验。

MEMBER_ACTIVE 仅依赖成功最终回复回执：工具进度/通知、失败或状态未决的发送、仅调用工具后无最终回复、以及 `choose_no_reply` 不会激活或刷新窗口。窗口过期后立即回落到原 v3.0.2 CALL/ASK/TOPIC 评分，不叠加新的意图分。

设 `A∈[0,1]` 为情景证据，`T∈[0,1]` 为已衰减话题证据：

\[
\boxed{
S(m)=\begin{cases}
100A(m),&\text{COLD / 无有效锚点}\\[3pt]
100\{A(m)+T(m)-A(m)T(m)\},&\text{TOPIC / 有有效锚点}
\end{cases}}
\]

**可等价实现为：** `S = 100 * (1 - (1-A)*(1-T))`，在 COLD 令 `T=0`。数学上仍保留状态区分与日志字段，方便分析。

该融合是启发式“证据并集”，**不是概率模型**；当 A 与 T 相关时可能放大误命中。v3.0 接受该取向，保留回放监测。

## 3. 文本预处理与子句提取 `U(m)`

### 3.1 两种文本视图

- **意图视图（scene view）：** 保留自然语言语气、问号、称呼、否定与词序；执行 Unicode NFKC、换行规范化和空白折叠，不把「吗、呢、吧」丢弃。
- **相似度视图（topic view）：** NFKC + casefold + 移除空白、标点及非语义分隔符，保留中文、拉丁字母、数字；具体规则与已采用的 C/P 版本一致。

不要用 topic view 代替 scene view：删除标点后会损失召唤和疑问语法信息。

### 3.2 顶层发言与嵌入材料分离

从消息中提取 `U(m)={u1,...,un}`，只用 **顶层发言子句**评估 CALL/ASK，排除下列材料的内部文本：

- 原生附件正文、转发消息内容、引用消息正文；
- Markdown fenced code、平台原生代码片段、标准引用块；
- 明确被包裹为引用内容的长文本（如引号内的转述），除非顶层明确在请求对其分析。

未标记为引用的长文，按顶层段落、句号/问号/叹号、换行拆分为子句；允许指令出现在开头、末尾或两段普通文字之间。**评分取子句最大值，不做全文长度归一化。**

**围栏与引号的强制处理规则：**

1. 先做平台原生附件、转发、引用、代码分段；再识别 Markdown fenced code（成对的 ` ``` ` / `~~~` 围栏，可含语言标签）、行内代码和 `>` 引用块；其中的正文作为材料，永远不直接成为 CALL/ASK 子句。若围栏与正文紧贴且语法不规范，成对围栏仍优先识别为内容边界；匹配失败时标记 `segmentation_uncertain`，不要从疑似围栏内部抽取高分子句。
2. 中文/英文引号内的直接引语、转述内容不独立触发 CALL/ASK。例如「我的意思是‘咕咕帮我看看’」为转述，场景分 0；「咕咕，帮我看看‘这个算法’」只由引号外的顶层请求触发。
3. `REPORTING_ROOTS` 同时服务 CALL 的 `K=0` 与 ASK 的 `Q=0` 转述消歧。若顶层语言行为仅为叙述「某人说/问/想/知道……」，不允许被内嵌的命令或疑问重新触发。若顶层明确是「我想知道……」的信息请求，则按 ASK 判断。
4. 无法确定主句/引语边界时记录 `segmentation_uncertain` 并保守地不给不确定子句正向分；可由其他确定子句、DIRECT 或 TOPIC 独立触发。

> 例：一条消息先写「咕咕帮我看看这个算法怎么样？」，然后附上一大段 fenced code，最后写「这是详细设计」。仅开头的请求进入情景评分；所有内容仍可以在实际 Run 中作为任务材料读取。

对于无明确分隔的全文转述，纯规则无法保证完美区分；标记为 `segmentation_uncertain`，纳入测试，而非宣称识别完全正确。

### 3.3 句法合成，不准维护固定表达触发表

- 单字词根可以经语法规则组合，例如 `看+看` 表示动词重叠（VV），`看+吧` 表示动词与句末祈使助词。
- `帮+我+看`、`来+看`、`别+走` 由词性与位置关系识别，**不写成词典条目**。
- 「为什么」「怎么」「怎么样」属于通用疑问结构，识别可由其基本语素组装实现；不是某一问题领域的固定语句模板。
- 不维护「音乐、算法、Redis、报错、文件、视频」等用于决定提问具体性的领域词表。领域实体视为开放内容。

## 4. 情景评分总式

每条有效顶层子句 `u` 分别计算召唤和提问：

\[
\boxed{A(m)=\max_{u\in U(m)}\left(A_{call}(u),A_{ask}(u)\right)}
\]

约定空集合取 0。两类证据**取最大值，不彼此相加**；避免「称呼+问题」重复抬分。

### 4.1 CALL：召唤

\[
\boxed{A_{call}(u)=0.92\,N(u)V(u)K(u)}
\]

| 项 | 定义 | v3.0 判定 |
|---|---|---|
| `N`（受话对象候选） | 当前 Bot 是否可能是直接受话者 | `1`：句首或独立呼语位置出现配置别名，或「请/让」等泛用请求结构把当前 Bot 设为动作执行者；`0`：纯第三人称提及、合并主语、转述、引用材料或没有明确受话对象。句首别名也可能是陈述主语，**须由 K=0 排除**；原生 @ 已由 DIRECT 处理。 |
| `V`（基础动作） | 是否存在有效通用动作词根 | `1`：**已经确认是请求谓语**，且其核心动词属于基础词表（允许 VV、串行动作、补语）；`0`：无匹配词根，或虽命中词根但无法确认请求谓语角色。词根命中不等于 V=1。|
| `K`（请求/祈使结构） | 动作是否在要求对方参与，而非描述对方 | 取 `{0,0.8,0.9,1.0}`，详见下表。 |

`K` 的规则按**优先级从上往下**，不是简单把助词权重相加：

| K | 一般化语法结构 | 示例（例子不是词表） |
|---:|---|---|
| `0` | 状态/事实陈述、第三方转述、引用、句法不可判；有明确主语+陈述性情态/时态，动作非面向受话者；例如 `看+起+来` 是状态结构 | 「咕咕看起来很累」「咕咕走了」「咕咕说累了」「咕咕想起来了」「他说明天咕咕来看」 |
| `1.0` | 受话对象明确，存在祈使标记（请、快、别、吧等）、动词重叠 VV、受益人/动作对象形成的明确请求、趋向邀请 | 「咕咕看吧」「咕咕看看这个」「咕咕帮我看看」「咕咕别走」「咕咕快来」 |
| `0.9` | 明确呼语 + 动词 + 明确任务宾语，但缺少更强祈使证据 | 「咕咕查这个」「咕咕读文档」 |
| `0.8` | **确认为直接呼语 + 能独立作祈使命令的裸动作谓语**，且无时体/状态/转述主句证据；这不是「词根命中后兜底」 | 「咕咕看」「咕咕来」；「咕咕说」若无法确认是命令，则 K=0 |

如果出现互斥证据，优先采用 `K=0` 的陈述/转述排除；**句法分析不确定时 K=0，V 也不因裸词根命中而赋 1**。`想、知、说、看、问` 等多义词不能单独证明祈使；「咕咕想起来了」「咕咕说累了」应得 0。`吗` 不能一律视为陈述：它可能由 ASK 通道处理。

**统一句法次序：** 顶层/引用作用域 → 受话角色 N → 谓语/主语与时体关系 → V 是否为指令谓语 → K 档位 → 提问 Q；`REPORTING_ROOTS` 同时参与 CALL 和 ASK 的排除。

**关键对照：**

| 输入 | N | V | K | CALL 分数 |
|---|---:|---:|---:|---:|
| 咕咕看吧 | 1 | 1 | 1 | 92 |
| 咕咕看看这个 | 1 | 1 | 1 | 92 |
| 咕咕帮我看看这个算法怎么样 | 1 | 1 | 1 | 92 |
| 咕咕别走 | 1 | 1 | 1 | 92 |
| 咕咕查这个 | 1 | 1 | 0.9 | 82.8 |
| 咕咕看 | 1 | 1 | 0.8 | 73.6 |
| 咕咕看起来很累 | 1 | 1 | 0 | 0 |
| 咕咕走了 | 1 | 1 | 0 | 0 |
| 咕咕和小北真的能唠 | 0 | 1 | 0 | 0 |
| 我看咕咕今天没说话 | 0 | 1 | 0 | 0 |

> `N` 的句法角色与 `K` 的请求/陈述消歧，是需实现和测试的解析规则；简单的词根命中**不足以保证表中的结果**。本表为验收目标，不是已运行测试。没有必要把各种示例句加入词表。

### 4.2 ASK：提问

\[
\boxed{A_{ask}(u)=0.90Q(u)}
\]

| Q | 类别 | 可检查的通用结构 |
|---:|---|---|
| `1.00` | 明确提问/明确求助 | 独立疑问词与具体开放内容、正反问 `X+不+X`、带具体内容的 `吗` 问句、含具体对象的完整问号问句；明确请求获取信息（如 `我+想+知` + 疑问内容）。不要求问号。 |
| `0.85` | 模糊疑问/上下文依赖追问 | 「怎么这样啊」「为什么呢」「这/那咋回事」「这/那怎么回事」「你呢」「真的？」等独立疑问行为但对象不充分；允许主动参与，由 Agent 根据上下文决定是否回复。|
| `0` | 非独立提问 | 陈述、感叹、纯问号、转述/嵌入疑问、任务材料中的引用；例如「我不知道为什么会这样」「他说为什么会这样」。|

**问句判定次序：**

1. **先判断是否是当前发送者的顶层言语行为。** 处于引用、转述或嵌入从句中的疑问词不能单独触发；`我想知道...` 视为请求信息，`我不知道...` 视为事实陈述。
2. **识别通用疑问语法。** 包括疑问代词/副词、是否问句、正反问、选择问、问号表示的口语省略问；`?`/`？` 是证据，不是必要条件。
3. **再判断问题是否独立完整。** 去除语法标记和无独立指称的泛指成分后，是否仍有具体对象、动作、状态或询问目标。不要求专门的领域名词列表，也不只按剩余长度判断。
4. **最后区分 1.0 / 0.85 / 0。** 模糊疑问和明确提问使用不同 Q，但不额外按群安静程度改变 Q。

疑问单字不能单独触发 ASK，必须识别其句法位置；`哪+会` 用于「他哪会……」时是反问式否定，不是当前发送者提出的问题。

例如：「为什么汉密尔顿的音乐这么好听」「为什么汉密尔顿的音乐这么好听啊？」必须同为 `Q=1`；「怎么这样」「怎么这样啊」「怎么这样？」必须同为 `Q=0.85`，不因句末助词跨档。

**提问验收目标：**

| 输入 | Q | ASK 分数 |
|---|---:|---:|
| 为什么汉密尔顿的音乐这么好听 | 1 | 90 |
| 为什么汉密尔顿的音乐这么好听啊？ | 1 | 90 |
| 这个算法怎么样 | 1 | 90 |
| Redis 超时怎么解决 | 1 | 90 |
| 这个方法能不能用 | 1 | 90 |
| 怎么这样啊？ | 0.85 | 76.5 |
| 怎么这样？ | 0.85 | 76.5 |
| 为什么呢 | 0.85 | 76.5 |
| 你呢 | 0.85 | 76.5 |
| 这首歌真好听啊 | 0 | 0 |
| 我不知道为什么会这样 | 0 | 0 |
| 他刚才问为什么会这样 | 0 | 0 |
| 单独一个问号「？」 | 0 | 0 |

**非完美性说明：** 「怎么这么离谱」既可能是反问/感叹，也可能是真疑问；纯基础词规则难以保证一致。v3.0 允许在难例上更偏向召回，不新增针对「离谱」等内容词的固定例外短语；以实际误触发率决定下一版取舍。

### 4.3 不用原公式「(主体+动词+问句)/全文长度」的原因

- 长文档会不合理稀释短召唤；
- 「咕咕和小北真能唠」虽然有名称+动词，但不是指令；
- 「怎么这样啊」极短，靠长度比例会被不合理抬高；
- 受话对象、动词、祈使结构具有逻辑依赖，宜用 `N×V×K`；召唤和提问是可替代情景，宜用 `max`。

## 6. TOPIC：保留既定算法，不更改数学形式

### 6.1 可信中心与 `W₁₁`

`b*` 为当前群在当前消息到达前**最后一条有平台成功回执、且正文可信可得的本 Bot 实际出站消息**。锚点作用域为 `(platform, bot_id, group_id)`，不是 `(platform, bot_id, group_id, member_id)`。这意味着成员 A 建立话题后，成员 B 可以通过 TOPIC 相关性主动加入；属于产品明确允许的跨成员续接，可能产生抢答，但不能将它升级为成员级可信 CONTINUE。不以助手内部推理记录、工具执行消息、未送达草稿作为中心。

按平台可信顺序构造最多 11 条候选：中心前 5、中心本身、中心后最多 5，且均早于当前入站消息：

\[
W_{11}(b^*)=\{b_{-5},\ldots,b_{-1},b^*,b_{+1},\ldots,b_{+5}\}
\]

候选包括 Bot 与所有普通群成员的消息；**不是只比 Bot 自己说过的话**。若某部分不存在，则使用现有记录；窗口为空则相关度为 0。

### 6.2 字符覆盖与连续片段：保留非对称 C

对规范化后的当前消息或其有效聊天子句 `m` 与一个窗口候选比较单元 `x`：

\[
\boxed{C(m,x)=\frac{M(m,x)}{|m|}},\qquad
P(m,x)=1-e^{-\max(0,L(m,x)-3)/4}
\]

- `M`：当前文本与候选文本按非重叠块匹配到的字符数；参考实现应固定 `SequenceMatcher(autojunk=False)` 的行为，换实现必须重新回归。
- `|m|`：当前消息**参与该次比较的有效文本单元**的规范化长度；空串时 C=0。注意此处不是历史出站正文长度。
- `L`：最长公共连续字符块长度。
- `C` 是**有意的非对称覆盖率**：衡量「当前发言多少内容在最近话题里出现」，不要求历史消息长度接近当前消息。它并不是对称语义相似度。
- 比较片段来源必须有可解释记录；若历史出站含大量代码/附件/工具转录，不能直接声称整个正文都是一条适合匹配的聊天单元。比较单元的划分规则需在生产实现与回放保持一致。

\[
\boxed{R_{CP}(m,x)=0.5C(m,x)+0.5P(m,x)}
\]

**v3.0.2 明确不采用全量对称 C：**

\[
C_{sym}(m,x)=\frac{2M(m,x)}{|m|+|x|}
\]

`C_sym` 仅保留为**实验对照指标**（日志可选项），不参与 `R_CP`、TOPIC 或最终 S 的计算。原因不是否认短句包含产生假阳的风险，而是 session 2652 回放显示对称归一更严重地伤及正常的短句跟进长文档/教学说明；完整包含也可以是合理复述。**不增加**「短句长度小于 8 就改分母」或「仅纯包含时改对称 C」的条件式补丁。

#### 6.2.1 与精确包含相关的已知局限

在当前消息是历史候选的完整子串时，C 可能为 1；若 L 较长，P 也会上升。例如：

| 当前 `m` | 历史 `x` | 原 C/P | 含义 |
|---|---|---:|---|
| 我也这样觉得 | 嗯我也这样觉得 | 0.764 | 可能是延续，也可能是无意义复述 |
| 这个方案挺好 | 这个方案挺好的就这么定了 | 0.764 | 同上 |
| 确实是这样 | 我觉得确实是这样，太巧了 | 0.697 | 同上 |
| 我也是这样 | 我也是这样吧今天 | 0.697 | 同上 |

**这不是算法已经解决的语义问题**，只是产品阶段决定先容忍，再用真实人工标签区分「合理接话」与「不应接话」；不可在设计文档把上表都定性成假阳。纯礼貌反应由 §5.8 明确阻断，其他无关的完整包含仍可能放行。

### 6.3 局部编辑相似度 E：只识别真实局部改写

E 保留为 TOPIC 的正向证据，但职责明确为**处理有实际编辑的局部短语**，不再用精确匹配生成完美话题相关性。

对 `m` 的有效聊天文本子句 `u` 和历史比较单元 `x`，先生成满足长度 3～12 的有界片段对 `(a,b)`。有效候选必须同时满足：

1. **长度：** `3 ≤ |a|,|b| ≤ 12`，不得跨引用、代码、附件等结构边界。
2. **有效子句覆盖：** `|a|/|u_effective| ≥ 0.5`；`u_effective` 在 E 判定视图中消除**可确认的句末非决定性语气助词**（如「啊、呀、呢、吧」）及末尾标点。保留原文视图供 CALL/ASK 使用；「吗」及有时承载时体的「了」不得无条件消除。对「你呢」等省略式问句，不能剥离「呢」后改变 ASK 的 Q 类别。
3. **真正编辑：** `1 ≤ d(a,b) ≤ 2`，其中 d 是标准 Levenshtein 距离。**`d=0` 一律不参与 E，长度 3、5、12 都一样。** 完全相同的短语只经 C/P 体现。
4. **编辑位置：** 不允许仅通过首尾增删把原本完全相同的片段包装为编辑证据，**不论片段长度**；三/四字内部插入、删除和真正替换允许，避免漏掉「翻跟斗」↔「翻个跟斗」。建议在匹配前后检查首尾纯包含关系，若仅有前/后缀变化则拒绝该片段对。
5. **内容资格：** 共同内容至少有可辨别的非纯语法成分；全是 `GRAMMAR_MARKERS ∪ PRONOUNS_AND_REFERENCE ∪ QUESTION_MORPHEMES` 的公共字符时不单独利用 E 放行。纯回应优先由 §5.8 判定。语法字符过滤是低成本保护，**不声称能识别真实语义**。
6. **候选确定性：** 相同输入及快照必须得到相同候选排序与截断结果；`E=0` 表示未找到有效候选，而不是证明语义无关。

\[
\boxed{
E(m,x)=\max_{u\in U_{topic}(m)}
\max_{\substack{(a,b)\in H(u,x)\\ valid(a,b)}}
\left(1-\frac{d(a,b)}{\max(|a|,|b|)}\right)
}
\]

无有效候选时 E=0；`U_topic` 只包含当前消息的有效顶层聊天片段，与 `U(m)` 情景指令子句共享边界识别，但不强制同一个子句切法。

**自动候选及实现预算：**

- 当前实现按「**共享 2-gram 锚点 + 两侧独立扩展 + 确定性排序 + 每个 `E(u,x)` 最多 256 个候选片段对**」生成编辑候选；原 3-gram 锚点会漏掉单字插入。
- 每条消息最多抽取 4 个 TOPIC 比较单元；单元超过 64 个规范化字符时按连续片段切分，再从全文均匀取样。对 W₁₁ 中每个候选消息，按 2-gram/字符重合排序，只计算前 4 组单元对，因此完整话题窗口最多进行 44 组 C/P/E 单元比较。
- 这些是计算硬上限，不等价于遍历全文全部子串；取样可能漏掉长文本中未选中的证据。该限制保持公式不变，但应在真实语料观察中单独监测召回。
- 暂以 **E CPU P95 ≤4ms；完整评分 CPU P95 ≤10ms、P99 ≤30ms** 为实验目标，排除 DB 与平台 I/O。历史一次短消息 `evaluate` P95≈4.9ms 的报告不能与 E-only 的 4ms 预算直接混淆；长消息初版 E P95≈13.5ms 报告来自优化前，不是最终状态的证据。必须补齐优化后的单项性能回放、消息长度分层与生产硬件条件。

**规范化与 E 的最小必测样本：**

| 当前消息 / 窗口短语 | 有效片段 | E 预期 | 理由 |
|---|---|---:|---|
| 他哪会翻跟斗 ↔ 翻个跟斗 | 翻跟斗 / 翻个跟斗 | 0.75 | 中间插入一个「个」 |
| 他哪会翻跟斗啊 ↔ 翻个跟斗 | 翻跟斗 / 翻个跟斗 | 0.75 | 句末「啊」不使覆盖率跨档 |
| 他哪会翻跟斗吧 ↔ 翻个跟斗 | 翻跟斗 / 翻个跟斗 | 0.75 | 同上 |
| 挺好听 ↔ 真好听 | 挺好听 / 真好听 | 约 0.667 | 真实字符替换，仍允许短时关联 |
| 我也这样觉得 ↔ 嗯我也这样觉得 | 完全相同的六字片段 | **0**（仅对这组纯包含候选） | d=0 不进入 E；首尾补字不得伪装为编辑 |
| 这个方案挺好 ↔ 这个方案挺好的就这么定了 | 完全相同的六字片段 | **0**（仅对这组纯包含候选） | 同上；整体仍由 C/P 计算 |
| 这可能 ↔ 这可能 | 完全相同的三字片段 | 0 | d=0，不能凭 E 给 1 |
| 哈哈哈 ↔ 哈哈哈 | 笑声短反应 | 0 / PASSIVE | 精确短回应拒绝优先 |

> 表中 `E=0` 是对**列出的直接片段对或纯包含路径**的预期，不能保证完整句子所有候选对均为 0。自动 E 候选枚举仍可能找到其他合资格局部改写，应以完整参考实现回归为准。

### 6.5 时间衰减

时间差 `t = (m.received_at - b*.sent_at) / 1000` 秒。

\[
g(t)=\begin{cases}
\displaystyle\frac{2^{-t/360}-2^{-600/360}}{1-2^{-600/360}},&0\le t<600\\
0,&t\ge600
\end{cases}
\]

`t<0` 视为无效输入，TOPIC 不参与；固定 TTL 为 600 秒，其他成员发言**不会**刷新中心 TTL。有效时：

\[
\boxed{T(m)=R_{TOPIC}(m)\,g(t)^{0.25}}
\]

此处无需再乘 `I=0.25` 的陈述权重，也不使用旧版 `0.98`、`0.65+0.35sim` 等关系系数。

### 6.6 已知风险与边界（v3.0.2）

1. 非对称 C 对短消息完整包含的高覆盖率**保留**。这是有意的召回取向，不能声称已消除所有话题误关联。具体反例与计算在 §6.2.1。
2. E 禁止精确片段直接拿满分，但**并不能逻辑保证所有长片段完整包含最终不会通过 E 的其他编辑候选**；候选枚举的全局最大值与日志须接受自动测试，不得把局部 E=0 误当成整句 E=0。
3. E 语气词边界依靠有效子句规范化解决，ASK/CALL 仍依靠保留原始标记的 scene view 判定，不得因删除「呢」误伤「你呢」等省略问句。
4. C/P 对长篇引用的短句续接较有利；比较单元如何分段会影响结果，必须固定生产/回放口径并保留 match source、比较单元边界及原始事件 ID。
5. 不增加频率惩罚、群忙惩罚，也不叠加条件式对称 C；统计无效 Run 与实际误插话来评估成本。
6. `E` 至少记录 `matched_spans、d、coverage、candidate_count、candidate_cap、candidate_capped、E_cpu_ms、match_source`；区分「公式通过」「自动候选确实命中」和「出站行为实际发生」。

## 8. 边界规则：不要因融合而破坏对象归属

1. **DIRECT 优先：** 原生 @ 本 Bot 走强路由；不把用户输入的裸 `@咕咕` 字符串冒充平台原生 @。
2. **其他成员优先：** 原生 @ 其他人、原生回复其他人且未同时 @ 本 Bot，先排除，TOPIC 的 `E=1` 也不得覆盖。
3. **第三人称提及 ≠ 呼语：** 「咕咕走了」「咕咕和小北能唠」等不因别名加动词自动当召唤。
4. **短反应不自动生成新的 CONTINUE 或 TOPIC Run：** 可信续聊需要真实的提问、请求或实质跟进；§5.8 精确独立短回应归 PASSIVE。**但平台原生 @ 当前 Bot 的 DIRECT 优先**，不能被「谢谢」子串拦掉。
5. **群里有多个 Bot：** 中心只使用本 Bot 已成功送达的出站；其他 Bot 的消息可以出现在 W₁₁ 作为上下文文本，但它们不是本 Bot 的 TTL 锚点。
6. **事件竞争：** 接收当前消息前的历史窗口是因果快照，绝不包含当前消息自身或未来消息。排序依赖可信顺序/出站回执，不以内部 assistant 记录替代真实出站。
7. **不靠问号/语气词产生资格跳变：** 明确疑问增删「？、啊、呀、呢」在同一语言行为下应保持分档；省略式「你呢」允许被评为模糊提问。
8. **取消频率限制：** 不对同一成员或全群设置「N 秒只能触发 1 次」的门控规则；负载不足时可由独立执行层实行并发/排队保护，但不可伪装成注意力得分。
9. **MEMBER_ACTIVE 是成员级资格，不是群级话题续期：** 只匹配最终答复回执记录的同一发送者，180 秒内成员消息本身不刷新 TTL；Bot 再次成功发送关联到该成员的最终答复后刷新。该通道不覆盖明确收件人排除和纯短回应规则。

```python
from dataclasses import dataclass

QUIET, NATURAL, ACTIVE = 85.0, 65.0, 55.0


def score_scene(message) -> tuple[float, dict]:
    best = 0.0
    best_reason = {"scene": "none"}
    for clause in extract_top_level_user_clauses(message):
        n = direct_addressee_score(clause, message.bot_aliases)  # 0 or 1
        v = directive_predicate_root_confirmed(clause)            # 0 or 1; bare roots alone => 0
        k = imperative_structure_strength(clause)               # 0/.8/.9/1; uncertain => 0
        call = 0.92 * n * v * k

        q = question_structure_strength(clause)               # 0/.85/1
        ask = 0.90 * q

        if max(call, ask) > best:
            best = max(call, ask)
            best_reason = {"scene": "call" if call >= ask else "ask",
                           "N": n, "V": v, "K": k, "Q": q,
                           "clause": clause}
    return best, best_reason


def topic_evidence(message, snapshot):
    anchor = last_platform_accepted_bot_reply(snapshot, message)
    if anchor is None or not snapshot.complete:
        return 0.0, None
    t = (message.received_at_ms - anchor.sent_at_ms) / 1000
    if not 0 <= t < 600:
        return 0.0, None
    window = get_causal_window(anchor, message, before=5, after=5)
    if not window:
        return 0.0, None
    winner = max(
        ((max(cp_similarity_asymmetric(message, item), edit_local_similarity_valid_edits_only(message, item)), item)
         for item in window),
        key=lambda pair: pair[0],
    )
    r, item = winner
    g = (2 ** (-t / 360) - 2 ** (-600 / 360)) / (1 - 2 ** (-600 / 360))
    return r * (g ** 0.25), {"anchor": anchor.id, "match": item.id,
                             "raw_r": r, "age_seconds": t}


def decide(message, snapshot, mode):
    if duplicate_event(message) or invalid_event(message) or is_bot_echo(message):
        return passive("invalid_or_duplicate")
    if has_native_mention_of_this_bot(message):
        return direct("native_mention")
    if definitively_addressed_to_others(message):
        return excluded("other_recipient")
    if is_verified_substantive_reply_to_this_bot(message, snapshot):
        return continue_run("verified_reply")
    if is_empty_or_pure_question_mark(message):
        return passive("empty_or_bare_mark")
    if is_pure_short_reaction_without_new_intent(message):  # §5.8: 完整匹配，非子串
        return passive("pure_reaction")
    if has_capability_action(message):  # CAP 专属词表；不参与 CALL/ASK 分数
        return capability_run("capability_action")
    if has_accepted_final_reply_for_same_sender_within(message, snapshot, seconds=180):
        return member_active_run("member_active_window")

    a, scene_reason = score_scene(message)
    t, topic_reason = topic_evidence(message, snapshot)
    state = "TOPIC" if topic_reason else "COLD"
    score = 100 * (a + t - a*t) if state == "TOPIC" else 100 * a

    if mode == "autonomous":
        return allow_run(score, state, scene_reason, topic_reason)
    threshold = {"quiet": QUIET, "natural": NATURAL, "active": ACTIVE}[mode]
    if score < threshold:
        return passive("below_threshold", score=score, state=state)
    return allow_run(score, state, scene_reason, topic_reason)
```

## 10. 回归测试与验收门槛

### 10.1 单元测试

- **公式：** A/T 都在 `[0,1]`；融合分不超过 100；A=0 时为 100T；T=0 时为 100A；随 A/T 单调不减。
- **词表边界：** v3.0.2 `_ACTION_ROOTS` 与 CAP 通用动作词表独立；CAP 产品能力名词来自显式元数据；不维护整句黑盒正向触发词或动作/能力关联矩阵。
- **召唤正负对照：** 同根不同语法（「咕咕看吧」与「咕咕看起来很累」；「咕咕别走」与「咕咕走了」）。
- **提问稳定性：** 同义标点/语气变体 `Q` 不变；完整问句 vs 引用/转述。
- **文档长度不变性：** 指令前/后添加 1 万字 fenced code，A 不改变；引用块包含召唤不触发。
- **TOPIC 数值：** R=.75、t=124.3 → S_topic≈68.34；t=600 → T=0；窗口最多 11 条、当前消息不自匹配。
- **多 Bot/接收对象：** 明确@其他 Bot 的消息不得通过 TOPIC；Bot 的内部 assistant 日志不得创建出站锚点。
- **E 精确重合修复：** `d=0` 的三至十二字片段 E=0；首尾增删不得利用 d=1 绕过；「翻跟斗」↔「翻个跟斗」自动 E=.75；「他哪会翻跟斗啊/吧」均维持 E=.75；「挺好听」↔「真好听」约 .667；纯语法片段过滤；全文取样、每个单元对 256 组候选及每条历史消息 4 组单元比较均有上限。
- **C 覆盖实验：** 以原 `C=M/|m|` 为主基线；`C_sym` 与仅纯包含条件版**只做离线 A/B**，不得偷偷写进生产。包括短句包含、长篇出站中的原文引用、俄语/代码/英文短续聊；固定 `autojunk=False`。
- **短回应精确拒绝：** 「谢谢」「收到」「哈哈」独立消息无新意图时 PASSIVE；「谢谢，咕咕帮我查」不得因「谢谢」子串拒绝；DIRECT @ 优先。
- **CAP 独立准入：**「那定个定时任务」「帮我创建项目」「小北帮我整理文件」「请大家整理笔记」「把笔记删掉」「在画布里画一下」「取消提醒」可进入 Run；「我已经创建项目」「我准备写笔记」「创建项目这个功能不错」「他说让我创建项目」「别创建项目了」不命中 CAP；「不要再提醒我」识别为停止提醒请求。匹配不依赖 CALL 的称呼词或 v3.0.2 `_ACTION_ROOTS`，且结构化 @ 他人排除优先。

### 10.2 模拟/真实群聊验收指标

| 指标 | 口径 | 期望 |
|---|---|---|
| CALL 召回率 | 人工标注的真实指向 Bot 的动作请求 | 高于旧版，重点覆盖短召唤 |
| ASK 召回率 | 独立明确问句与模糊口语问句 | 不因无问号丢失 |
| 第三人称误召唤率 | 仅提到 Bot 而非邀请 Bot 的消息 | 尽量低，重点监测 |
| TOPIC 跨成员续接召回 | A 发起、Bot 回复、B 接话 | 「翻跟斗」案例可通过 |
| TOPIC 误关联/误插话 | 相似片段来自不同话题 | 记录但不提前一刀切否决；需接受产品取舍 |
| 无效 Run 率 | 进入 Run 后最终 `choose_no_reply` | 衡量额外 token 成本 |
| 实际误插话率 | Bot 实际发言打断成员定向对话 | 严格区分于仅进入 Run 的误命中 |
| 时延 | P50/P95/P99 + E 子串比较次数 | 特别关注长文档和长 Bot 出站 |

观察期间可对真实入站做离线人工标注，记录脱敏 score/reason、是否进入 Run 和最终是否发言；不得为了比较而让旧 scorer 重新参与生产决策，也不得把命中片段明文写入日志。人工标注应覆盖跨成员接话和 E 单独拉起的案例。

### 10.3 实现状态与仍需观察事项

1. **已实现：可信出站正文链路。** 通过投递账本只读取平台接受的最终载荷；失败、未知、工具通知和缺失正文不作为 TOPIC 锚点。Redis 快照不完整或无法验证时关闭 TOPIC，按 COLD 评分。
2. **已实现：E 自动候选与有效性。** `d=0`、纯首尾变化和纯语法片段不产生 E；2-gram 候选、每消息 4 个 64 字符单元和 W₁₁ 每个候选 4 组单元比较均有硬上限。长文本真实负载下的耗时与抽样召回仍需持续观测。
3. **已实现：确定性 CALL/ASK 规则。** 词根和语法角色共同决定分数；代码、引用、转述、陈述和纯反应有负向规则。当前规则仍是轻量确定性解析，不承诺完整中文句法理解。
4. **已实现：结构归属与群级锚点。** 不同成员可参与同一 TOPIC；明确指向其他成员/ Bot 优先排除；窗口按事件时间构造且不含当前或未来事件。
5. **已实现：短回应硬路由。** 精确整句纯反应在 TOPIC 计算前拦截；DIRECT、可信且有实质内容的 CONTINUE 先于该规则。
6. **待观察：性能与长文本。** 候选生成设有每一对消息比较最多 256 个候选对的上限；本次验证未建立生产负载 P95/P99 数据，因此不宣称达标。
7. **待观察：真实语料与人工标签。** 需要按 `应参与 / 可参与 / 不应参与` 标注并分析 C/P、E 单独拉起、跨成员续接及实际发言结果。自动过线数不等于真阳性。
8. **验证范围：** 本次实现以注意力模块和 IM 回归测试为验证重点；全仓 CI、生产部署和 devserver 实际运行状态需以单独执行记录为准。
9. **已实现：模式与运行可靠性。** COLD 下 NATURAL/ACTIVE 当前离散分档完全等效；不加频率惩罚，保留消息幂等、并发/队列保护、Run 与实际发言区分及 `choose_no_reply`。
10. **v3.0.3 成员激活续聊：** 仅用平台 ACCEPTED 的最终出站回执，按平台、Bot、群和接收成员隔离；`0 ≤ 入站事件时间 − accepted_at_ms < 180s` 时放行非纯反应消息。同成员再次收到成功最终答复才刷新；工具通知、未决/失败出站、其他成员消息、以及激活窗口内单独发言均不刷新。

### 10.4 2026-10-30 真实语料 A/B（引用执行报告，非本稿独立实测）

**报告范围：** 2026-10-29 某次历史回放报告中的 490 条群消息 + 281 条 Bot 出站；TOPIC 以本 Bot 最后可信出站的前后各五条构成。比较口径中的**461 条候选**与 490 条群消息不是同一个集合，不能混成分母。报告的是 `S≥65` 的次数，**不是人工标注的正确次数**。

| 版本 | S≥65 次数 | 相对原 C | 解释限制 |
|---|---:|---|---|
| 原始 `C=M/|m|` | 35 | 基准 | 保持短句对长回复的高召回 |
| 全局替换 `C_sym` | 13 | 减少 23、新增 1，净 -22 | 疑似漏掉俄语语法多轮跟进；尚无完整人工标签 |
| `0.5C+0.5C_sym` 混合覆盖实验 | 26 | 净 -9 | 弱化长度不对称，损失仍较大 |
| 仅当 `|x|≤2|m|` 使用对称 C | 32 | 净 -3 | 仅是变体，不构成正式规则 |
| 仅在完整包含时使用对称 C | 34 | 净 -1 | 额外减少的俄语 42 字练习可能是真阳，不证明收益 |

另据报告，**461 条候选里仅 9 条出现「当前消息被历史窗口整段包含」**。这显示针对包含关系改分母可能收益有限；但不能据此断定其他群、其他语言和长文本分布同样稀少。

**解释纪律：** 由机器直接数过线不能证明「原 C 更准确」或「对称 C 的 23 条全是真阳」。这轮选择保留原 C 是**在召回优先的产品取向下，当前证据不足以支持破坏性替换**，仍需人工标签与实际发言结果确认。

### 10.5 当前实现验证记录

- 生产评分器版本为 `attention-v3.0.6`；开放 ASK 的延迟状态由 IM 入站运行时和 Worker 实现，不改变评分器公式；开发沙盒复用同一评分函数，不模拟 Redis 等待状态；CAP 原因码独立于评分原因记录。

- 用户配置和真实消息正文不写入测试或普通日志；测试均使用虚构群成员和合成消息。

## 11. 算法公式冻结摘要

\[
\boxed{A_{call}=0.92\max_{u\in U(m)}[N(u)V(u)K(u)]}
\]

\[
\boxed{A_{ask}=0.90\max_{u\in U(m)}Q(u),\qquad A=\max(A_{call},A_{ask})}
\]

\[
\boxed{R=\max_{x\in W_{11}}\left[0.5C(m,x)+0.5P(m,x),\ E(m,x)\right]}
\]

\[
\boxed{T=R\,g(t)^{0.25},\qquad
S=\begin{cases}100A,&\mathrm{COLD}\\100(A+T-AT),&\mathrm{TOPIC}\end{cases}}
\]

**一句话：** CAP 以独立通用动作词、产品能力名词和请求结构直接准入；其余消息沿用 v3.0.2 双通道公式及 v3.0.3 成员激活 TTL。CAP 不做纯文本受话对象消歧，也不改变工具权限；其余评分仍不按全文长度打折、不用固定口语短语正向词典、不做频率门控，并尊重结构化收件人和真实出站事实。
