## 1. 背景与目标

用户在桌面「个人设置 → 接入咕咕」连接自己的机器人。桌面独立运行连接、存储和 Agent，用户可以从平台私聊发送文本并收到回复，整个过程无需 Web Host、PostgreSQL 或 Redis。现有 Web Host 入口继续使用原有存储与任务运行方式。

首版以四平台私聊文本、原会话回复和通用确认回调为目标。群聊、附件、原生流式回复等能力按平台验收后开放，既有 Web 功能继续受回归测试保护。

## 2. 功能需求

### FR-IM-01：本地连接管理

设置区显示四个平台的真实能力及运行状态，支持开始连接、查看进度、启停和重新绑定。飞书、QQ、微信使用各平台授权流程，Telegram 使用 Bot Token 验证与私聊身份绑定。启用的连接在桌面运行时重启后恢复。预览环境使用自己的运行时和凭据边界。

### FR-IM-02：本地私聊与 Agent 收发

只有已绑定且获准的私人会话能触发本地 Agent。私聊会话由连接、平台与会话身份确定。收到回复时按原会话和平台回执发送。账号、机器人和聊天范围之间保持隔离。撤销授权后，后续运行和投递都重新检查当前权限。

### FR-IM-03：重复投递与恢复

平台重复投递同一事件时只产生一条入站记录和一个逻辑运行。接收后尚未调度的记录可以恢复。上游发送结果不明时显示结果未知，并保留诊断依据，避免盲目重复发送。确认回调须校验目标、触发者和一次性动作状态。

## 3. 技术方案

以 `packages/gateway` 为 IM 接入的统一开发入口，目标目录如下。

```text
packages/gateway/
├── README.md             接入、调试、测试和新增平台指南
├── src/
│   ├── platforms/
│   │   ├── feishu/       授权、绑定、连接、事件转换和收发
│   │   ├── qq/
│   │   ├── wechat/
│   │   └── telegram/
│   ├── ir/              统一事件契约及运行时校验
│   └── runtime/         IM 授权、去重、会话路由和回复投递
└── tests/               平台及双端共用的契约测试
```

| 模块 | 目标职责 |
|---|---|
| `packages/gateway/src/platforms/` | 集中维护各平台的授权协议、身份绑定交互、连接、事件映射及回复适配。 |
| `packages/gateway/src/ir/` 与 `runtime/` | 定义事件契约，执行 IM 权限校验、去重、会话路由与运行投递。 |
| `packages/core/` | 提供通用 Agent、用户身份、工具权限及运行接口。 |
| `apps/desktop/src/main/im/` | 装配本地连接和桌面 IPC，提供加密凭据、SQLite 入站及投递记录、本地 Agent 调度。 |
| `apps/web-host/src/modules/im/` | 继续装配服务器端的可信账号、配置、持久化和调度，逐步接入相同契约。 |
| `ImConnectPane.vue` | 共用平台列表、连接状态和表单交互。通过运行时适配层获取能力及执行操作。 |

迁移先梳理 `core/src/im` 的复用点。把 IM 专属流程逐步迁到 Gateway，把 Core 侧现有调用收敛为通用事件、运行接口或由宿主注入的工具端口。保持 `gateway → core` 单向依赖。Desktop 和 Web Host 继续各自装配存储、凭据和调度。

### Desktop、WebUI 和 Web Host 的 IM 目录

Desktop 与 WebUI 的界面入口使用相同的 `im/` 相对结构。Desktop 主进程与 Web Host 使用相同的宿主 IM 相对结构。以下为迁移目标，新增子目录随实际实现落地。

| 层 | Desktop 根目录 | Web 根目录 | 两端共用的相对路径 |
|---|---|---|---|
| 设置与连接界面 | `apps/ui/src/desktop/im/` | `apps/ui/src/shared/im/` | 共享入口位于 `connect/`；桌面专属连接适配器位于 `apps/ui/src/desktop/im/connect/platforms/<platform>/` |
| 宿主接入 | `apps/desktop/src/main/im/` | `apps/web-host/src/modules/im/` | `connect/` 为连接配置和绑定装配，`gateway/platforms/<platform>/` 为平台装配，`gateway/{inbound,interactions,delivery}/` 为消息、回调和回复入口 |

**UI 源码归属**：共享面板、平台列表、通用交互、状态展示及样式统一维护在 `apps/ui/src/shared/im/`，以 WebUI 的行为和界面为准；桌面只在 `apps/ui/src/desktop/im/` 放置桌面专属桥接与适配器。WebUI 直接使用共享 `ImConnectPane.vue`，Desktop 通过类型化适配器接入同一面板。两个 UI 目录采用一致的 `im/connect/platforms/<platform>/` 组织方式。该约定仅适用于 UI；Desktop 仍在本机完成绑定、收发和 Agent 调度。

**所有 IM 的双端一致性**：QQ、飞书和 Telegram 的群聊设置行与交互统一由 `GroupChatSettings.vue` 定义，WebUI 和 Desktop 不复制模板或自行排列字段。两端按同一顺序显示群聊开关、回应方式、适用平台的参与度/消息格式、记忆开关和群工具；平台不支持的能力整项隐藏，不用占位选项凑齐布局。回应方式与参与度枚举位于 Core 的平台无关 IM 领域类型，群消息候选选择规则由 Core `selectAttentionCandidate` 提供；群工具分组投影和更新由 Core `userBotGroupToolFlags` / `updateUserBotGroupTools` 提供，桌面飞书、Telegram 与 WebUI 对部分开启的旧工具配置也采用相同显示规则。桌面 IPC patch 直接复用同一设置契约；各宿主只负责将设置保存到自己的数据层并装配运行端口。Core 的 `defaultUserBotGroupSettings` 是 Web Host 与 Desktop 首次配置的默认值来源，群工具授权集合与 Web 新建机器人保持一致；旧配置中显式保存的关闭状态继续保留。QQ 提供私聊/群聊消息格式和私聊流式传输；飞书、Telegram 提供 Web 已有的参与度选项，Telegram 保留平台操作指引；三个群聊平台均提供群主/群/成员记忆和群工具选项。微信 iLink 是私聊平台，不展示群聊控制；平台原生消息格式和流式能力按 Gateway 实际支持情况开放，不为界面一致而虚构设置。桌面飞书和 Telegram 的短期群上下文及已接受机器人回复事实现通过 SQLite 收件/投递记录和共享 Gateway 注意力算法处理，回执保存平台消息 ID、接收成员和触发注意力类型；超出持久化覆盖范围会关闭完整上下文判定。群参与度 ASK 的评分与等待时序由 Gateway 共用，Web Host 和 Desktop 各自注入 pending 状态存储、授权复核与派发端口；桌面延迟唤醒复用同一条被动历史消息，不复制消息记录。

本次核对确认 Desktop QQ、飞书和 Telegram 的设置展示均引用上述共享组件，设置读取与写回分别由类型化桌面适配器接入各自凭据存储；Web 端同样使用该组件并由 Web Host API 持久化。`gugu-web` 全量 UI 类型检查通过。实际页面的热更新/视觉验收仍需在运行中的 Desktop 与 WebUI 分别确认。

查某个平台时，从 `packages/gateway/src/platforms/<platform>/` 查授权协议、绑定交互和收发规则，再按上表相同的相对路径查对应宿主的装配或界面。两个宿主复用 Gateway IR 和运行策略，并各自接入凭据、数据库和调度端口。

IM IR 首版包含 `message.received`、`interaction.received`、`reply.requested`。记录版本、可信连接标识、平台、会话类型与会话标识、平台发送者、源事件标识、动作或内容，以及回复所需的引用或受控句柄。客户端收到的事件字段不能自定 owner，owner 由运行时从已验证连接绑定。IR 携带决策事实，Gateway 运行时在执行时读取最新绑定，并结合 Core 的通用权限能力作出决定。

入站去重键以可信 owner、平台、连接、事件类型及平台定义的事件唯一范围组合。平台缺少稳定事件 ID 时，适配器提供可验证的稳定去重依据。接收登记与待调度状态在同一事务提交，调用方按同一逻辑标识恢复调度。回复独立记录发送状态和回执，平台不确定结果按平台支持的查询能力核实。

凭据、会话令牌与连接回执由可信运行时管理。普通日志仅保留平台、阶段、安全错误码和可关联的内部标识，不记录 Token、群聊文本或私聊正文。扫码完成后向界面返回状态与可展示的机器人信息。

## 4. 验证与上线

用四个平台的合成事件验证 IR 转换、重复投递、跨连接隔离和权限撤销。用独立 SQLite 数据目录验证接收后重启、入队恢复与投递结果未知。Web Host 使用现有路由、平台回归和隔离 PostgreSQL 测试验证兼容性。

用各平台测试账号逐项确认扫码或 Token 验证、绑定、私聊收发和桌面重启恢复。以微信验收开发入口。新合作者应能从 Gateway README 进入微信平台目录，定位授权和绑定、事件转换、收发以及对应测试。每个平台独立开放，验收结论区分合成测试和真实机器人。回滚时停用对应桌面连接，保留本机连接配置和消息历史。观察连接成功率、入站重复数、调度失败和结果未知的投递数量。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 同一机器人同时在两端轮询 | 事件分流或连接互相踢下线 | 连接前提示停用旧端，明确展示冲突并支持重新连接。 |
| 网络失败发生在平台接受发送之后 | 重发可能造成重复回复 | 独立保存投递结果，按平台能力查询或保留待核对状态。 |
| 平台身份和事件唯一范围不同 | 串聊、误授权或误去重 | 由平台适配器明确语义，Gateway 运行时校验并通过双端测试验证隔离。 |
| 桌面退出或休眠 | 收发暂停、游标落后 | 恢复后使用已提交游标继续，界面显示连接状态。 |

待确认事项包括桌面休眠及退出期间是否需要独立后台常驻，以及各平台群聊、附件和流式回复的后续开放顺序。
