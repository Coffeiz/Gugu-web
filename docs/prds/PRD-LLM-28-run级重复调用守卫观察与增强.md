## 1. 背景与目标

### 事故复盘（2026-09-18 run-f3438e041ff44620）

MCP 搜图任务中 `MAX_TOOL_CALLS` 预算耗尽 → 用户拒绝解除 → 工具被整体摘除，MiniMax-M3 仍每轮输出 tool_call（幻影调用，只拿 skipped 占位结果），~75 轮空转（106 次 LLM 调用、约 3.5 分钟）直到 100 轮绝对上限强停；叠加「取消/上限不落库」导致整个 run 从所有端消失。

### 已上线的基础守卫

1. **统一重试**：LLM 瞬时错误（429/529/超时/网络/5xx）按 `app/core/retry.py` 固定 5s×5、墙钟 90s 重试，两 SDK 内建重试收零；`OverloadedError` 显式进两链路的瞬时名单。
2. **跨轮重复守卫**（unlimited 生效，与预算弹窗解耦）：`round_tool_signature()` 对一轮全部工具调用（含幻影）计算形态签名（名字+归一化参数，同轮去重）；连续 3 轮一致 → 注入一次提醒；连续 5 轮一致 → 流式收束文案并终结 run。verify/goal 模式不适用。
3. **预算止损**：拒绝解除后模型仍调工具，第 2 轮强制收束。
4. **熔断按轮计数**：`RepeatCallBreaker` 同轮多相同调用只记 1 次（单轮多相同调用合法），跨轮重复第 4 轮拦，仅 repeat_safe 白名单。
5. **取消/失败部分落库**：已产生的 display_timeline 照常持久化。

### 目标

观察上述基础守卫在生产中的真实表现（命中率、误伤率、漏网形态），再决定两项增强是否值得做。**不追求覆盖所有理论形态**——奇异形态仍由 100 轮绝对上限兜底，接受其存在。

### 明确不做

- 语义级「进展判断」（LLM 评估每轮是否产生新信息）：成本高、误判率不可控。
- 提高 `MAX_TOOL_CALLS`：用户主力 unlimited 模式，预算线感知度低。

## 2. 功能需求（待评估项的目标行为，实施前不生效）

### FR-LLM28-1：失败轮守卫

连续 N 轮（建议值 3）内**所有**工具调用均以失败告终（无论参数是否变化）→ 第 N 轮注入提醒；连续 M 轮（建议值 5）仍全失败 → 强制收束。与跨轮签名守卫互补：签名守卫抓同参重试，失败轮守卫抓换词乱撞（参数微调绕过签名时的兜底）。

### FR-LLM28-2：收束前升级交互弹窗

跨轮重复守卫达到强制收束阈值时，不直接静默收束，优先复用 budget/goal 弹窗机制询问用户「检测到重复调用卡住：继续试 / 就此打住」；用户选继续 → 注入「换一种做法」指令并给有限轮数；交互不可用（IM/后台无通道）或过期 → 落回现有静默收束。

## 3. 技术方案（待评估项的思路，未实现）

- 失败轮守卫：machine 的 dispatch 结果聚合处统计每轮成败；成败形状经 `enrich_tool_error`/`_TOOL_BUDGET_EXHAUSTED` 等占位结果归一，需确认占位结果是否计入「失败」（建议：计入——占位轮本身即无进展）。
- 弹窗升级：复用 `create_goal_mode_prompt`/`wait_for_resolution` 同款管线；`session_id=None` 或过期时返回 None 落回静默收束，保证 IM/定时任务路径行为不变。

## 4. 观察方法（本 PRD 的核心章节）

- **观察信号**：`[core] 连续 3 轮重复相同的工具调用，注入提醒`（WARNING）与 `[core] 连续 5 轮…强制收束`（WARNING）两类日志的出现频次与分布。
- **误伤判定**：守卫触发后用户回复「你怎么停了/我还在等结果」类反馈，或触发场景为合法轮询（同一查询等待长任务完成）→ 记为误伤，考虑放宽阈值或加白名单。
- **漏网判定**：再次出现「100 轮上限强停」或用户反馈长时间无响应后自行恢复 → 记为漏网（大概率是参数微调绕过签名），触发 LLM28-001 实施。
- **观察窗口**：至下次 MiniMax 高峰时段事故复现，或累计 2 周二者取先。窗口结束输出结论：维持现状 / 实施 LLM28-001 / 实施 LLM28-002 / 两者都做。
- **回滚**：守卫均为 machine 内纯逻辑，无迁移无配置；回滚 = revert 对应提交。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|------|------|------|
| 跨轮签名守卫误伤合法轮询（同参轮询长任务） | 用户任务被提前收束 | 观察 3/5 阈值误伤率；确认误伤后考虑对显式轮询类工具（repeat_safe + 轮询语义）放宽 |
| 幻影调用参数不可考，事故真实形态可能不是同参重复 | 签名守卫可能对该形态无效 | 即 LLM28-001 的立论依据，观察期内以「漏网判定」验证 |
| 提醒注入对 MiniMax 无效（已有先例：budget stop prompt 被无视） | 提醒层形同虚设 | 无碍——收束层不依赖提醒生效；提醒只降低误伤时的突兀感 |
| 守卫与预算止损/熔断叠加触发顺序 | 收束文案可能互相覆盖 | 三者收敛点相同（流式收束文案 + return），先到先得，无状态冲突 |

待确认：失败轮守卫的「失败」口径是否应包含空结果（tool 成功但返回空 content）——倾向不含，避免把合法的空查询结果误判为失败。
