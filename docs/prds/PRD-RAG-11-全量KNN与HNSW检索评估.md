## 1. 背景与目标

当前混合检索先由 BM25 生成有限候选，再对这些候选做精确余弦排序。该路径开销受候选数限制，但语义相关内容若未进入 BM25 候选，就没有机会被向量排序召回。讨论 HNSW 前，需要先测量全语料精确 KNN 的质量和成本，作为近似检索的质量基线。

本评估比较三条路径：

1. **A：当前路径**——BM25 候选 + 候选集精确余弦排序，代表当前生产基线。
2. **B：全量精确 KNN**——在同一授权语料上计算精确 top-K，再与 BM25 结果融合，作为语义召回质量基准。
3. **C：HNSW ANN**——用 HNSW 取近似向量 top-K，再与同一份 BM25 结果按同一融合规则合并。

目标是回答：全量精确 KNN 是否已足够快；若不足，HNSW 能否在可接受的召回质量损失下，显著降低查询延迟或资源成本；以及选型、构建、增量更新和恢复成本是否适合当前 worker 生命周期。

本评估不实现生产切换、不决定最终向量库、不改变 embedding 模型或召回评分策略，也不把 ANN 近邻距离直接当作 RAG 置信度。

## 2. 功能需求

### FR-RAG11-01：使用一致的语料与请求进行对照

A、B、C 必须使用同一时点的向量、BM25 索引、查询集合、过滤条件、top-K、融合算法和 embedding 配置。分开记录查询 embedding、向量检索、BM25、融合/重排和端到端耗时，避免把模型调用波动误记为索引差异。

### FR-RAG11-02：以全量精确 KNN 建立 ANN 质量基线

B 对目标授权语料中的全部有效向量做精确相似度计算。C 的 ANN 结果对照 B 计算 `Recall@K` 和排名差异，同时使用人工相关性标注评估 A/B/C 的 `MRR`、`nDCG@K`、`Precision@K`，并检查最终回答引用的证据是否命中相关材料。

### FR-RAG11-03：验证租户、范围和来源过滤

所有路径必须在相同授权边界内检索。至少覆盖用户隔离、知识来源、项目/文件夹等范围过滤、来源类型、时间边界和对话 `before_message_id`。评估必须验证未授权向量不会进入候选或结果，不能只在最终展示层过滤。

### FR-RAG11-04：覆盖索引完整生命周期

记录冷启动构建或加载、热查询、批量重建、单条 upsert、删除、索引与来源数据不一致、worker 重启、用户断联后卸载和重新连接后的恢复表现。比较索引增量维护与全量重建成本，并验证删除和权限变更不会留下可检索的旧向量。

### FR-RAG11-05：验证 embedding 空间隔离

测试不同 provider、模型、模型版本和维度。索引分区或过滤键必须能阻止不同 embedding 空间混算；维度或模型标记变化后，应明确触发新索引、重建或跳过该空间，不能静默把不兼容向量加入既有图。

### FR-RAG11-06：记录资源、质量和回退行为

每条路径记录查询延迟分位数、索引构建/加载时长、峰值 RSS、常驻内存、持久化索引体积、增量写入/删除时延、空结果率、重复率、误召回率和索引陈旧程度。向量索引不可用、损坏、版本不兼容或查询失败时，验证系统能否安全退回 BM25 路径，并留下脱敏诊断信息。

## 3. 技术方案

### 3.1 对照方法

- 固定一份脱敏快照，明确向量数、维度、模型标签、用户/来源分布和更新时间；每轮比较使用同一快照。
- 先用 A 与 B 判断“全量语义召回”相对现状的质量收益和成本，再用 B 与 C 判断 HNSW 的近似损失与性能收益。
- 对每个请求分别计时 embedding 生成、BM25 查询、KNN/ANN 查询、融合重排和端到端链路。模型耗时和索引耗时分开报告。
- 冷测覆盖空 worker 初次构建/加载和进程重启；热测在索引加载完成后运行。更新测量包含新增、修改、删除和重建，不以单次热查询代替生命周期评估。
- 查询集需覆盖精确词、同义/改写、拼音或错别字（若该语料支持）、跨来源查询、无答案查询、时间过滤和不同权限范围。保留人工相关性标签及代表性 RAG 回答证据检查。
- 使用多轮运行给出样本量、硬件/运行环境代称、语料规模及 p50/p95（必要时 p99），报告中不得包含原始聊天正文、真实昵称、凭据或可识别内容。

### 3.2 候选实现边界

实现选型留待评估数据之后决定。候选可包括：

- **全量精确 KNN**：先在 worker 中对已授权、同模型空间的全部向量做精确计算，作为无近似误差基准；测量其 CPU、内存和查询耗时增长曲线。
- **pgvector HNSW**：评估与现有 PostgreSQL 的运维整合、扩展可用性、索引构建/内存成本、维度约束以及过滤条件下的召回率和查询计划。
- **进程内 HNSW 库（如 USearch）**：评估 TS worker 可用性、索引文件保存/加载、外部元数据过滤、增量删除、崩溃恢复和 worker 级内存占用。

候选方案不得绕过现有 Python 所有权校验、TS Data Runtime 的数据读取边界或 RAG 最终 scope 校验。向量索引属于可重建的派生数据；权威来源和当前向量缓存继续按现有数据流维护，直到后续独立方案明确批准数据模型变更。

### 3.3 评估产物边界

本 PRD 阶段只新增评估文档。实际执行评估时，报告、可重复基准脚本和任何隔离索引存储应作为单独评估改动提出；不得在本阶段修改生产检索、数据库迁移、依赖锁文件或用户运行配置。若需要 devserver 真实用户数据，必须先使用经批准的只读、隔离快照，不把正文或可识别字段写入仓库报告。

## 4. 验证与上线

这是评估计划，不包含生产上线。执行时需按以下验收标准形成可复核报告：

- A/B/C 使用同一语料快照、query set、模型空间、过滤条件和融合设置；报告明确列出不可比因素。
- ANN `Recall@K` 以 B 的精确 top-K 为基准，同时报告人工标注下的 `MRR`、`nDCG@K`、`Precision@K` 和 RAG 证据命中结果。
- 冷启动、热查询、upsert、delete、重建、重启恢复、峰值 RSS 和索引磁盘占用都有独立结果；不能只给平均查询时延。
- 多用户和多 scope 的隔离用例均无越权候选、结果或缓存复用；模型/维度变化用例无跨空间混算。
- 预先登记评估样本规模、目标语料规模和可接受的质量/资源阈值，再运行最终对照，避免看到结果后调整门槛。
- 只有当 B 的实测成本不满足预先登记的目标，且 C 满足 ANN 质量门槛并显著改善目标成本时，才提出 HNSW 生产方案。若 B 已满足目标，优先保留更简单的精确路径；若 C 质量不达标，则不以延迟收益抵消证据质量退化。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 只测热查询 | 会漏掉索引构建、加载和 worker 恢复成本 | 独立记录冷启动、热查询和生命周期变更。 |
| 用 ANN 自身结果当质量真值 | 无法测出近似召回损失 | 以同语料全量精确 KNN 的 B 组作为近邻真值，再用人工标签衡量实际相关性。 |
| 过滤后候选不足或近似召回偏差 | 可能造成特定用户/scope 召回明显下降 | 对不同数据规模和过滤选择性分层报告，验证过滤执行位置与候选扩展行为。 |
| 用户使用不同模型或向量维度 | 混用索引会造成检索错误或数据污染 | 按 provider/model/version/dimension 隔离索引空间，并覆盖模型升级后的重建路径。 |
| 向量索引与源数据短暂不一致 | 删除或撤权后的内容仍可能被检索 | 测量同步延迟；要求最终 scope/ownership 校验阻止过期或越权结果，并验证删除恢复。 |
| 小语料下 HNSW 收益不明显 | 增加依赖、部署和运维复杂度却无实际收益 | 同时测当前和目标规模，按实测门槛决定是否继续，不预设必须采用 ANN。 |

待定事项：评估语料规模和目标规模、标注 query 数、资源预算、质量阈值，以及是否可以使用隔离的真实用户数据。这些参数应在正式执行前登记；本文件不预填未经测量的数值。
