## 1. 背景与目标

### 1.1 背景

Agent 执行任务时可能需要新增系统包或运行时工具。当前 Shell 容器使用固定、临时的运行环境，权限和只读根文件系统会阻止 `apt` 等系统级安装。临时容器结束后，容器内安装结果也无法保留。若每次增加工具都要求重新构建、发布并更新整个 sandboxd/runtime 镜像，自部署用户难以管理；若直接开放宿主 Docker 或让运行任务容器长期可写，则会扩大宿主和用户数据风险，并使更新、回收和环境状态难以预测。

本需求为管理员提供部署级共享权限开关，并允许咕咕在专门隔离的环境修改流程中更新沙盒运行镜像。修改后的镜像作为持久化、有版本记录的自定义镜像，供后续新建的执行容器使用。它不是持久运行的可写容器：执行任务仍按既有策略创建临时容器，环境变更通过受控镜像版本提交保存。

### 1.2 目标

- 让自部署一体化镜像用户可选择让咕咕安装和保留完成任务所需的系统工具，不必每次手工重建 sandboxd 镜像。
- 由 Admin 单一开关控制是否允许修改，开关范围是当前整套部署中的所有用户与 Agent 会话。
- 默认业务部署（`external` 分体部署）关闭；自部署一体化镜像（`embedded`）默认开启。
- 自定义镜像和活动版本指针持久保存于 Rootless Docker 的专用持久数据目录；sandboxd/app 容器升级或重建不得静默删除、覆盖或重置它们。
- 管理员能够查看当前环境、基镜像版本和变更状态，并在确认后回滚到先前版本或恢复当前内置基镜像。
- 保留普通命令执行现有的逐次隔离、工作区授权、网络策略和资源限制；镜像修改操作不得获得宿主 root、宿主 Docker Socket 或用户工作区内容。

### 1.3 明确不做

- 不向 Agent、执行容器或 Web API 暴露通用 Docker CLI、Docker Socket、任意镜像引用、宿主路径、任意挂载参数或 privileged 容器能力。
- 不允许普通 Shell/PTY 命令直接以 root 运行，也不允许把任务容器改为长期可写并依赖其存活保存工具。
- 不为每个用户维护一套沙盒镜像；这是部署级共享环境，开启后安装会影响此部署中后续新建的所有执行容器。
- 不自动把既有自定义镜像重放到新版基镜像，也不在升级时擅自清理历史镜像或回滚用户修改。
- 不改变业务部署的数据隔离、沙盒管理器拓扑或默认权限来规避当前固定镜像限制。

## 2. 功能需求

### FR-SHELL5-001：Admin 部署级权限开关

Admin 沙盒管理界面提供“允许 Agent 修改共享沙盒环境”开关，显示当前有效值和部署模式。开关仅由管理员配置，作用于当前部署的所有用户与 Agent 会话，不提供普通用户级别的二次覆盖。界面必须说明开启后 Agent 可通过受控流程变更后续任务使用的共享运行环境。

关闭开关后，系统拒绝新发起的环境变更请求，并明确返回权限关闭状态；已开始的变更按取消/安全收尾流程终止。关闭开关不删除当前活动自定义镜像，也不切回基镜像；恢复默认环境需由管理员单独执行并确认。

### FR-SHELL5-002：按部署模式初始化默认值

首次初始化且没有管理员持久化选择时，按受信部署模式设置初始值：

| 部署模式 | 默认值 | 面向场景 |
|---|---:|---|
| `embedded` | 开启 | 自部署一体化镜像；管理员可在 Admin 中关闭。 |
| `external` | 关闭 | 业务分体部署；管理员必须显式开启后才允许修改共享镜像。 |
| 未知、缺失或无法确认 | 关闭 | 安全失败关闭，不根据 IP、域名、用户身份或 socket 探测猜测部署类型。 |

管理员保存的值优先于默认值。升级、重启、模式状态探测和配置热加载不得把管理员已保存的值重置为部署默认值。改变部署拓扑不会静默开启此前关闭的权限。

### FR-SHELL5-003：受控修改共享运行环境

权限开启时，Agent 可通过专用环境修改操作安装所需工具并生成新的自定义镜像版本。该操作使用独立的临时修改容器和受控写层；它与普通 Shell/PTY 执行容器分离，不更改正在运行的任务容器。

环境修改操作必须遵循现有用户确认和命令安全策略；展示将执行的安装/修改摘要及网络需求，等待所需确认后才执行。网络访问继续受沙盒 egress/代理策略约束，不允许以安装为由绕过现有网络边界。权限关闭、sandboxd 未就绪、Rootless 存储不可写、配额不足或镜像校验失败时必须拒绝或失败关闭，不得退回到宿主或普通应用容器执行。

### FR-SHELL5-004：环境修改隔离边界

环境修改容器可以在其临时根文件系统内使用满足包管理需要的管理员权限，但该权限只存在于 Rootless Docker 管理的隔离子容器内，不代表宿主 root，也不提升 Web、Worker、sandboxd 或普通 Shell 进程权限。

修改容器不得挂载任何用户工作区、个人目录、项目目录、`/data/users`、`/config`、应用凭据目录、Docker Socket 或宿主路径；不得接收模型提供的任意挂载、UID、capability、privileged 或 Docker 参数。镜像提交内容只来源于该容器的系统环境变更，不包含用户文件、对话内容、密钥或运行配置。

普通任务执行继续使用当前低权限策略：执行用户保持非 root；根文件系统只读；清除 capabilities；启用 `no-new-privileges`；仅挂载经授权的工作区；沿用原有网络、超时、并发、输出、取消和清理限制。共享镜像变更不得改变这些策略。

### FR-SHELL5-005：原子发布、活动版本和回滚

环境变更先产生新的不可变镜像版本，在验证镜像可启动且基础工具检查通过后才切换活动版本。切换必须原子完成；构建、中断、空间不足、校验或健康检查失败时，活动版本保持不变，部分产物可安全回收且不得删除仍被引用的镜像。

保存有限数量的历史版本，记录版本 ID、创建时间、基镜像版本、变更结果摘要、大小和状态；不得保存或展示密钥、对话正文、工作区文件内容或未经脱敏的命令输出。Admin 可以查看版本、将活动指针回滚到保留版本，或确认恢复到当前随应用发布的内置基镜像。回滚只影响之后创建的任务容器；正在运行的任务继续使用创建时绑定的镜像版本。

### FR-SHELL5-006：跨 sandboxd/app 更新持久化

自定义镜像存放在 Rootless Docker 专用持久 data-root 下，与临时容器、构建上下文和内置 bundle 导入临时区分离。自定义镜像不得复用会被 bundle 装载流程覆盖的固定基镜像 tag；活动版本指针与版本元数据存放在专用、持久且可校验的状态位置。

sandboxd 容器/app 镜像更新、服务重启和容器重建后，系统应恢复同一活动自定义镜像及历史版本，不要求用户重新安装工具。更新流程不得对承载这些镜像的 data-root 执行 prune、清空或格式化。若持久数据缺失或损坏，系统显示明确状态并停止修改/切换，不得静默回退为看似成功的空白自定义环境。

更新 sandboxd 程序与更新内置执行基镜像是不同操作。sandboxd 程序更新必须保留自定义镜像；内置基镜像更新不得静默重建、覆盖或删除自定义版本。Admin 应能识别自定义环境所基于的旧基镜像，并可显式选择恢复当前基镜像。自动 rebase/合并任意系统包改动不在本期范围内。

### FR-SHELL5-007：部署范围与状态可见性

Admin 状态应区分：部署模式、修改权限、当前活动镜像（内置/自定义）、基镜像版本、最近成功变更、镜像存储占用、历史版本数量以及失败/不可用原因。显示状态不得泄露其他用户数据或敏感安装参数。

状态中明确指出自定义镜像是整套部署共享的，变更会影响后续新任务中的所有用户；已运行任务不切换镜像。业务分体部署只有在 Admin 显式开启权限后才允许变更，开启前的默认关闭行为必须可从 API、管理界面和自动化测试观察到。

## 3. 技术方案

### 3.1 权限配置与部署默认值

复用现有 `SandboxSettings`、Admin 沙盒管理 API 与已验证的管理员设置持久化路径，不新增另一套权限存储或按用户权限表。增加明确的部署级布尔设置及其来源语义：部署默认值只用于首次初始化；管理员持久化值优先且升级保留。

`embedded` / `external` 必须来自受信部署配置，不接受 Agent、用户请求或运行时网络信息覆盖。若当前设置持久化格式需要字段迁移，先复用既有 override/config schema 兼容流程；若必须新增数据库结构，单独提供 Alembic 迁移并覆盖旧版本数据默认行为。不得直接重写 `backend/config.override.json` 或 `.env`，也不得让升级脚本覆盖用户配置。

### 3.2 镜像修改与发布事务

在 sandboxd 内实现窄化的环境变更生命周期；Agent 只能提交产品定义的变更请求，不能传入 Docker 命令行或自由指定 image/mount/network/UID 参数。sandboxd 在内部校验全局开关、调用者身份、确认结果、资源和并发锁后创建隔离修改容器。

完成变更后生成唯一版本 tag/ID，执行镜像结构和启动 smoke 检查；校验通过后将镜像元数据写入持久版本目录，并原子更新活动版本指针。执行器只在创建后续任务容器时读取活动版本；每个容器固定记录创建时的 image ID，避免正在运行任务因指针变化中途切换。

固定 bundle 的 tag 和导入流程继续代表随版本发布的基镜像；用户自定义镜像使用独立命名空间/tag。bundle 重载只能校验或更新基镜像，不得移动自定义活动指针。版本回滚只切换指针，不重放命令；恢复默认只切换到当前 bundle 基镜像，删除旧版本需经保留策略和引用检查。

### 3.3 持久化、容量和并发

镜像层、版本清单和活动指针分别位于 Rootless Docker 专用 data-root/专用状态子目录中；实现原子写入、校验和、互斥锁、并发变更拒绝或排队、最大镜像占用和历史版本上限。所有清理依据显式版本引用、保留数量和空间策略执行，不调用无范围 `docker system prune`，不影响正在运行或可回滚版本。

环境修改具有时限、磁盘预算和取消语义。取消/崩溃只清理未提交的临时容器与构建产物；若镜像已校验但活动指针未切换，应可安全恢复或回收，不产生指针与镜像不一致状态。异常信息对用户脱敏，内部诊断不得记录密钥、对话或完整工作区内容。

### 3.4 目标文件树

```text
backend/app/core/config.py                         【修改】部署级权限设置、模式默认值与持久配置优先级
backend/app/api/v1/sandbox_admin.py                【修改】开关、状态、版本列表、回滚/恢复默认管理 API
backend/agent/sandbox/                             【修改】隔离修改生命周期、活动镜像解析、版本事务和互斥
backend/agent/sandbox/bundle_runtime.py             【修改】区分 bundle 基镜像与自定义镜像，禁止导入覆盖
backend/updater/                                   【条件】仅在现有升级链会清理 Rootless data-root 时修正保留边界
frontend/src/views/Admin/Sandbox/                  【修改】部署级权限、镜像状态和确认式版本操作；遵循组件/composable 拆分约定
frontend/tests/admin/sandbox/                      【新增】开关、默认值说明、共享影响范围和回滚交互测试
backend/tests/                                      【修改】补充部署默认、隔离边界、事务失败、持久化、升级保留和回滚测试
scripts/release/                                    【条件】升级回归确保不 prune 自定义镜像数据根
docs/prds/PRD-SHELL-5-自部署共享沙盒镜像环境管理.md 【新增】本产品需求与唯一实施清单
```

镜像修改核心逻辑归 `backend/agent/sandbox/` 和 sandboxd，不放入通用 Shell 工具层；Admin API 只负责管理员授权、状态和版本操作，不直接执行 Docker 命令。前端新增组件应落在 `components/`，状态流程放 `composables/`，API 请求复用/扩展对应 service。升级脚本只在确认会触及 Rootless data-root 时修改，并补充保留测试。

明确不改：普通 Shell 的宿主执行 fallback、现有用户工作区授权策略、Docker Socket 挂载、业务分体部署的 Rootless 管理器边界、固定 bundle 作为基镜像的发布来源。除非实现调查证明现有配置无法表达，不新增配置数据库或全局权限子系统。

## 4. 验证与上线

- 部署模式测试：新建配置且无管理员选择时，`embedded` 默认开启、`external` 默认关闭、未知模式默认关闭；管理员保存后重启、热加载和应用/sandboxd 升级均保留该选择。
- 隔离测试：修改容器不能读取或挂载工作区、其他用户目录、应用配置/密钥、Docker Socket 和宿主路径；普通 Shell 继续以非 root、只读根文件系统、无 capabilities 和既有网络策略执行。
- 持久化测试：安装一个可验证工具并发布自定义版本；重启 Rootless daemon、重建 sandboxd/app 容器后，后续执行仍可使用该工具，活动版本 ID 不变。
- 事务测试：模拟安装失败、健康检查失败、取消、磁盘满、活动指针写入失败及并发变更；验证活动版本不损坏、失败产物可控清理、历史版本仍可回滚。
- 生命周期测试：升级内置 bundle 和 sandboxd 程序后自定义镜像保持；确认升级脚本不对自定义 data-root 执行 prune/重置；管理员显式恢复默认后新任务才使用当前基镜像。
- 权限测试：关闭开关后 API 和 Agent 变更入口均拒绝新变更；Admin 回滚/恢复默认必须二次确认；确认取消不会修改活动指针。
- UI 验证：业务部署新装显示关闭，自部署一体化新装显示开启；说明文本清楚表达“部署级共享”和“只影响后续新任务”；状态、失败原因和占用量与后端一致。
- 首次发布默认只启用 `embedded` 新安装；已有安装按兼容迁移策略初始化一次并持久化确定值，不在升级时根据模式反复重算。`external` 既有安装默认关闭，管理员可主动开启。
- 回滚路径为 Admin 将活动指针切回已保留的旧版本或当前内置基镜像；若镜像存储/元数据损坏，关闭变更能力并显示错误，不删除原始数据尝试自动修复。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 共享环境变更影响部署内所有用户 | 某用户请求安装的软件可能改变其他用户后续任务的工具行为或兼容性 | 明确这是部署级开关；Admin 展示影响范围；变更前确认、版本化、可回滚；不做隐式 per-user 行为。 |
| 安装脚本或包来源不可信 | 可能在自定义镜像中植入恶意程序或影响后续任务 | 沿用网络代理/egress 策略；保留变更摘要和来源信息；使用隔离修改容器；管理员可关闭；镜像发布前做 smoke/基础检查。 |
| 自定义镜像持续占用磁盘 | Rootless data-root 增长，挤占应用数据空间 | 设体积/版本上限，展示占用；删除前检查活动/运行引用；绝不无范围 prune。 |
| 基镜像安全更新与用户改动冲突 | 自定义环境可能继续基于较旧系统层，或重置会丢用户安装 | 显示基镜像版本与新版本提示；不自动 rebase/重置；管理员显式恢复新基镜像。 |
| 升级流程清理 Rootless Docker 存储 | 用户自定义工具丢失 | 将持久 data-root 视为用户数据；升级测试验证重建后镜像和指针不变；禁止 prune/初始化覆盖。 |
