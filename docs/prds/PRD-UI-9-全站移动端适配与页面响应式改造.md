## 1. 背景与目标

### 1.1 背景

当前前端是 Vue 3 单应用，Vue Router 按路由加载公开页面、主应用和 Admin。代码调查确认：

- `frontend/src/layouts/DefaultLayout.vue` 使用全视口固定高度和横向 flex，挂载 `AppSidebar`；普通页面内容区固定预留顶部栏空间。该布局还统一挂载 Chat、通知、上传、个人资料、预览等全局交互。
- `frontend/src/layouts/AdminLayout.vue` 使用全视口布局，左侧后台导航固定宽度 220px，`.admin-main` 是后台页面的主滚动容器。
- 主应用包含项目、日历、文件、MCP、技能、终端、Mind 笔记/画布、定时任务等路由；公开页面包含登录、注册、密码找回/重置、邮箱验证、隐私和 404；开发环境还会注册开发工具页。
- Admin 路由覆盖配置、Agent、数据统计、用户与配额、沙盒、反馈、审计、日志、服务、更新、存储、通知和邮件等页面。
- `frontend/src/views` 与 `frontend/src/components` 下约 40 个文件已有 `max-width` 媒体查询，断点包括约 460、560、600、620、640、680、700、720、760、900、960、1100px 等值。局部规则不等于整页移动端任务已可完成。
- 现有断点扫描只用于定位规则，不代表这些页面已通过手机验收；需要逐路由检查滚动、遮挡、交互和长文案。

### 1.2 目标

- 所有正式用户可访问页面在手机和平板尺寸下可读、可滚动、可完成核心任务。
- 主应用与 Admin 导航、顶栏、全局弹层能够适配窄屏；桌面布局保持现有能力。
- 每个页面在自身 view/component 目录内负责内容区适配；全局样式只维护真正跨页面的规则。
- 页面业务状态、请求、权限和动作保持一份；只有展示结构明显不兼容时，才拆分桌面/移动展示组件。
- Mind 笔记桌面端使用正式三栏布局；UI9-009 响应式阶段按可用内容宽度切换为按日期横向浏览的笔记流，不按 UA 判断。切换时共享笔记数据、选中状态和业务行为。当前 UI9 前窄屏暂时保持三栏原样式，接受布局拥挤；DEV 时间轴仅作为临时对照入口。
- 通过逐路由、逐视口、逐核心任务的验收清单，避免用“页面可打开”或“已有 media query”代替完成标准。

### 1.3 非目标

- 不构建独立 Mobile SPA、移动端部署包或基于 UA 的页面分流。
- 不创建平行的 `views-mobile/` 与 `views-desktop/` 页面树。
- 不把所有页面移动规则汇总到单个全局 CSS 文件。
- 不重做主题/品牌系统、路由结构、服务端 API 或桌面端产品信息架构。
- 不要求移动端与桌面端视觉一致；允许针对窄屏改变展示密度和局部操作结构。

## 2. 功能需求

### FR-MOB-01：单一业务页面与逐页适配

- 每个路由继续使用现有页面入口和业务状态；常规差异使用 CSS Grid/Flex、换行、收缩、局部滚动和媒体查询适配。
- 页面特有的响应式规则放在对应 view 或功能组件内，不由全局布局代替页面内容适配。
- 若桌面与移动的展示 DOM 确实差异显著（例如数据表格与卡片列表），允许在该功能域 `components/` 中分别实现展示组件；两者必须共用同一份数据、业务动作、权限判断和请求状态。
- 纯布局切换优先使用 CSS。仅当输入行为、触控能力或交互流程确实不同，才允许使用 JS 视口/设备能力判断；禁止用 JS 代替普通 CSS 媒体查询。

### FR-MOB-02：主应用与 Admin 壳层响应式导航

- 主应用桌面侧栏、普通页顶栏和 fullBleed 工作区均需在窄屏可用；用户可以从任意主应用路由访问主导航。
- Admin 全部正式路由需可从窄屏后台导航访问；当前页面、导航开关和返回/关闭路径应明确。
- 移动导航形态由实现阶段沿用现有 `AppSidebar`/Admin 导航结构评估，优先通过壳层适配，避免复制一套路由与权限定义。
- 导航抽屉打开时应遵循键盘焦点、Escape 关闭、背景滚动和触屏点击行为；导航变化后抽屉关闭且路由行为不变。
- 顶栏的搜索、上传、新建等动作在窄屏不能相互挤压或被裁掉；低频动作可以收进菜单，但不能丢失。

### FR-MOB-03：公开页与普通内容页面

- 登录、注册、验证、找回/重置密码页面适配窄屏表单、长错误提示、软键盘和提交按钮。
- 隐私与 404 页面保证正文可读、标题自然换行、主要导航可触达。
- Projects、Calendar、Files、MCP、Skills、Schedules 等页面逐页检查核心任务；允许在页面内调整布局或拆分展示组件，不改变原有操作语义。
- 每个正式路由都必须有独立的适配结论和核心任务验收记录；不可因共享布局已适配而略过页面验收。

### FR-MOB-04：全屏与交互密集型页面

- Chat、个人资料、上传、预览、通知等布局级挂载组件在手机下适配窄屏、软键盘、安全区、内部滚动和关闭/返回操作。
- Mind 笔记/画布、终端等长生命周期视图适配触控和可视区域变化时，不能意外重置会话、播放状态、选区、对象状态或画布坐标。
- Mind 笔记在宽屏且三栏内容宽度满足可读性时使用桌面三栏布局（笔记列表、阅读/编辑区、信息区）；移动端及不足以容纳三栏的视口继续使用现有日期卡片/横向时间流布局。视口变化只切换展示，不得丢失当前笔记、筛选或编辑状态。
- 画布、终端及其他工具区要区分页面滚动、内部滚动和手势操作，避免触控事件互相抢占。
- 桌面 hover 才能发现的操作，移动端必须有常驻或明确的菜单入口；拖放必须存在等价触屏操作路径。

### FR-MOB-05：密集信息与触控可用性

- 表格、看板、日历、日志和图表按各自任务决定卡片化、字段折叠、详情抽屉或局部横向滚动，不强制统一成单一表现。
- 页面不应出现无意的整体横向溢出；设计允许的局部横向滚动须边界明确、可触控且不隐藏完成核心任务所需的信息。
- 触控目标以至少 44 CSS px 为设计目标；紧凑排列保留足够间距，并提供按下/焦点状态。
- 标题、字段、按钮、菜单、长中英文与数字串、成功/错误信息在窄屏不重叠、不被裁切；省略文本时仍须能查看完整内容。

### FR-MOB-06：全站一致性与功能边界

- 适配不得改变登录态、路由守卫、权限、破坏性操作确认、数据持久化和 API 行为。
- 继续支持现有主题与中文、英文、日文；长文案必须纳入代表性验收。
- 固定/浮动控件适配动态视口与 `safe-area-inset`，不得长期遮挡输入框、确认/取消操作或页面主体。
- 明确每层滚动容器的 owner，避免 html、layout、page、modal 多层互相抢滚动。

## 3. 技术方案

### 3.1 文件与责任边界

```text
frontend/src/
├── layouts/
│   ├── DefaultLayout.vue              【修改】主应用壳层、顶栏与全局挂载组件编排
│   └── AdminLayout.vue                【修改】Admin 壳层和后台导航布局
├── components/common/layout/
│   ├── AppSidebar.vue                 【修改】主导航保持单一数据/权限来源并适配窄屏
│   └── <移动导航容器>.vue              【条件】现有导航组件无法承担抽屉容器时新增，不预先建立
├── assets/styles/
│   ├── responsive/                    【条件】仅当存在跨页面共享规则时新增
│   │   ├── index.css                  【条件】响应式基础规则唯一入口
│   │   └── shell.css                  【条件】主应用/Admin 壳层共用规则
│   └── STYLE-OWNERS.md                【修改】新增全局规则 owner 时同步维护
├── views/<Feature>/
│   ├── index.vue                      【修改】页面布局组合及流程调度
│   ├── components/                    【修改】页面特有 UI；显著不同的移动呈现只在此处分离
│   └── composables/                   【条件】仅在抽取/复用状态或异步流程时修改
└── <既有 api、stores、services、router>
                                      【不改】无响应式需求时不改变 API、权限、路由和业务数据流
```

责任约束：

- `DefaultLayout.vue` / `AdminLayout.vue` 只拥有壳层、导航、顶栏和全局挂载 UI 的响应式编排，不接管每个页面的内容布局。
- 每个页面由对应 view 与功能组件负责自身移动适配；入口组件只做布局组合和流程调度。
- 只有跨页面且规则稳定的基础样式才进入全局响应式样式；新增文件必须从 `variables.css` 唯一入口引入，并更新 `STYLE-OWNERS.md`。
- 不预先创建 `ResponsivePage`、`MobilePage` 等通用抽象；复用需求经过两个以上明确消费者验证后再提取。
- Admin 大型入口遵守既有 Admin 拆分约定，避免移动适配继续把多个区块和状态堆进 `index.vue`。

### 3.2 断点与布局策略

- 以内容拥挤和交互失效点确定断点，不根据设备 UA 或产品设备名称切换。
- 初始验证区间：窄屏 `<=640 CSS px`、中间屏 `641–1023 CSS px`、宽屏 `>=1024 CSS px`。这些是调查和验收起点；组件可有基于内容的局部例外，不能机械替换现有所有媒体查询。
- 项目现有 CSS 自定义属性不能用作原生 CSS `@media` 条件；本次不为统一断点引入不必要的预处理依赖。断点约定在样式 owner 文档中记录。
- 视口高度优先评估 `100dvh` 并保留兼容 fallback；底部固定区和浮层使用安全区 inset。逐层定义滚动 owner。

### 3.3 页面族与改造关注点

| 页面族/路由 | 重点适配与文件 owner |
|---|---|
| 主应用壳、全局 Chat/上传/预览/资料 | `DefaultLayout.vue`、`components/common/layout/`、对应全局组件：导航、标题/操作区、全屏浮层、键盘与安全区 |
| 项目 `/projects` | `views/Projects/`：看板列、卡片操作、筛选和编辑弹窗；局部滚动不能变成页面无提示溢出 |
| 日历 `/calendar` | `views/Calendar/`：视图密度、日期导航、事件编辑与窄屏表单 |
| 文件 `/files` | `views/Files/`、`components/common/file-browser/`：工具栏/面包屑、文件列表、批量操作、上传、预览 |
| MCP/技能 `/mcp`、`/skills` | `views/Mcp/`、`views/Skills/`：卡片、筛选、授权/编辑表单、长描述和操作菜单 |
| 终端 `/terminals` | `views/Terminals/`：会话切换、PTY 可视区、软键盘和触控工具栏 |
| Mind `/mind/notes`、`/mind/canvases` | `views/Mind/`：笔记宽屏三栏与窄屏原笔记流的视口切换、共享选择/编辑状态、画布触控、工具栏和面板位置；保留共享便签事实源 |
| 定时任务 `/schedules` | `views/Schedules/`：任务卡片、操作和编辑/确认弹层 |

### 3.4 页面具体落地模式

1. 先在原组件上做 CSS 响应式，适用于相同信息和动作仅需要换行、重排、折叠或尺寸调整的情况。
2. 对明显不同的展示结构，例如桌面表格与手机卡片列表，在 feature `components/` 内拆展示组件；页面入口/已有 composable 持有单份选择状态、加载状态、权限与动作。
3. 不把页面全量拆为 Desktop/Mobile 两个入口；不复制 API 请求或绕开原确认门。
4. 特殊手势/输入行为只在对应功能域处理，不在全局注入设备判断逻辑。

## 4. 验证与上线

### 4.1 视口矩阵

| 设备类别 | 视口尺寸 |
|---|---|
| 小手机 | 360 × 800 |
| 常见手机 | 390 × 844、430 × 932 |
| 平板 | 768 × 1024、1024 × 768 |
| 桌面回归 | 1280 × 800 或项目现有基准 |

覆盖窄屏竖屏、横屏、长文案、主题变化和浏览器缩放。至少使用桌面 Chromium 自动化；发布前对 iOS Safari 与 Android Chrome 的软键盘、安全区、固定操作区、文件选择和全屏工作区做真实设备抽样。

### 4.2 路由和任务验收

- 主应用、公开页面和 Admin 每个正式路由至少有一个移动端验收用例，记录视口、核心任务、结果和已知局部横向滚动区域。
- 测试不止断言页面加载；需验证主要动作，例如创建/编辑、筛选/选择、保存、导航、文件操作或查看详情。
- 所有页面验证无意页面级横向溢出、文案/控件裁切、操作区遮挡、键盘遮挡和 hover-only 操作不可达。
- Mind 笔记在宽屏验收三栏布局，在手机/窄屏验收原日期卡片时间流；调整视口或旋转设备后，当前笔记、筛选与编辑状态保持一致。长内容滚动和横向日期浏览都纳入移动端验收，不能只以首屏可见的少量日期卡片作为性能结论。
- Files/Projects/Calendar/Chat/Mind/Admin 导航等高频复杂页面优先加入 Playwright E2E；其他页面使用通用溢出与可见性检查，并补充页面主任务用例。
- 桌面基准行为、权限、确认门、持久状态和长生命周期视图状态不回归。
- 至少在代表性路由覆盖中文、英文、日文长文案及浅/深主题。

### 4.3 工程检查

按改动范围运行前端 `typecheck`、相关 Vitest、Playwright E2E 和生产 `build`；最终全站适配完成时运行全量前端检查。变更全局样式 owner 时检查导入链和样式回归。真实设备抽样的结果须记录在实施 TODO 对应项或 PR 验收记录中。

本 PRD 不规定部署或灰度开关；适配随前端构建发布，异常时可通过回退对应前端提交恢复。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 断点历史值冲突 | 某宽度段出现规则覆盖或页面跳变 | 按页面真实失效点适配；仅清理目标组件冲突规则；有内容依据的局部断点保留并记录 |
| 壳层和页面各自滚动 | 触控滚动失效、内容被裁切或背景错位 | 每个布局/全屏页/弹层明确滚动 owner；普通页、fullBleed、Mind 和弹层单独验收 |
| hover 操作触屏不可用 | 用户无法访问悬停才显示的操作 | 逐页盘点 hover-only 行为，为触屏增加显式按钮或菜单入口 |
| 页面全量复制 | 桌面和移动业务、权限、请求长期分叉 | 共享入口和 composable；只在展示 DOM 不兼容时分离展示组件 |
| 密集表格在手机可读性下降 | 用户无法比较数据或误触 | 按页面任务选择卡片、核心字段、详情抽屉或局部滚动，并保留字段标签 |
| iOS/Android 动态视口差异 | 软键盘或安全区遮挡输入与底部动作 | 动态视口、安全区和焦点滚动检查；真机对关键交互抽样 |
