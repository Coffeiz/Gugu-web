# PRD 撰写规范

本目录存放咕咕的产品需求文档（PRD）。为保证 AI/人协作时格式一致、便于检索和跨文档比对，新增 PRD 请遵循本规范。参考范例：[【已完成】PRD-IM-1-im接入稳定性与qq自建websocket.md](./【已完成】PRD-IM-1-im接入稳定性与qq自建websocket.md)。

## 文件命名

`PRD-<编号>-<简短主题>.md`

- 编号按模块/领域分组自增（如 IM 相关用 `IM-1`、`IM-2`），不用全局流水号，方便看出同一领域的文档演进关系。
- 主题用中文短语，不用英文缩写堆砌，一眼看出是什么。

## 文档头部

```markdown
# <PRD 标题>

> 状态：<Phase 1 已实现 / Phase 2 待评估 / ...>
> 创建：<YYYY-MM-DD>
> 最近更新：<YYYY-MM-DD>
> 关联模块：`path/to/file.py`、`path/to/other.vue`
> 背景参考：<如有参考实现/外部文档，注明来源>
```

`状态` 行是全文档最重要的一行——任何人（包括未来的 AI）打开文档，第一眼要知道现在做到哪一步了。每次阶段性进展都要回来更新这一行和 `最近更新` 日期。

## 章节结构

按以下顺序编号（不是所有 PRD 都需要每一节，简单的改动可以跳过 2/3，缺的节直接跳过编号或注明"不适用"）：

0. **实施状态** — 表格：`阶段 | 状态 | 说明`。状态用 ✅ 已完成 / 🔲 待评估 / 🚧 进行中。这是只读执行摘要，必须放在最前面、随实施进度实时更新。
   每份 PRD 只能有一处可执行的“实施 TODO”清单，已完成项改为 `[x]`，未完成项保留为 `[ ]`。实施状态表、功能需求标题和技术章节不得再复制同一批 TODO；如果摘要与 TODO 不一致，以 TODO 为准并立即修正摘要。
1. **背景与目标** — 为什么做这件事、现状痛点、想达到什么效果。顺带写清楚不做什么（如果范围容易被误解的话，一两句话带过即可，不必单独成节）。
2. **功能需求** — 每条需求用 `FR-<模块缩写>-<序号>：<需求名>` 作为三级标题，缩写取模块英文/拼音首字母（如飞书用 FS、QQ 用 QQ）。正文写清楚触发条件、预期行为、边界情况。不要在需求标题里重复实施状态；实现进度只写入实施状态摘要和唯一 TODO。
3. **技术方案** — 按子系统分节说明实现思路，包含新增依赖（包、外部服务、环境变量）和需要注意的数据/日志事项（尤其隐私相关：哪些字段不能打印原文）。
4. **验证与上线** — 一节写完「怎么测、怎么灰度、上线后看什么」：单元测试覆盖情况、待人工端到端验证的点、发布方式（按 Phase 的话分小节，每个写范围+风险等级+回滚方式）、上线后要盯的具体指标/日志关键字（不要写"观察运行情况"这种空话）。
5. **风险与待确认问题** — 表格 `风险 | 影响 | 对策` 之后，接一个 ✅/🔲 列表列出还没有定论的问题；有结论的要写清楚结论本身和依据（比如"实测日志显示…"），不能只打个勾就完事。

## 状态标记约定

- ✅ 已完成 — 代码已合并/已验证。
- 🔲 待评估 / 待确认 — 还没做，或做了但没有真实环境验证。
- 🚧 进行中 — 正在做。
- 如果某项结论后来被推翻或补充（比如"待确认问题"里的猜测被证伪），直接在原条目上更新，不要另起一条，保持单一事实来源。

## 语言与风格

- 全文中文，代码/字段名/环境变量用反引号包裹保持英文原名。
- 描述功能需求和风险时避免空泛表述（"提升稳定性"），优先给可验证的具体行为（"丢弃 `app_id` 不匹配的错投事件"）。
- 需求名之外的正文可以用列表/表格，不必大段散文。

## 何时创建新 PRD vs 更新旧 PRD

- 同一领域的延续性工作（比如 IM 稳定性专题下新增一个阶段）→ 更新现有 PRD，编号不变。
- 全新独立特性/模块 → 新建 PRD，走新编号。
- 判断不明确时，倾向于更新现有文档——PRD 太碎会增加以后检索和比对的成本。
