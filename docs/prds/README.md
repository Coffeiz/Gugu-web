# PRD 撰写规范

本目录存放咕咕的产品需求文档（PRD）。为保证 AI/人协作时格式一致、便于检索和跨文档比对，新增 PRD 请遵循本规范。参考范例：[【已完成】PRD-IM-1-IM接入稳定性与QQ自建WEBSOCKET.md](./【已完成】PRD-IM-1-IM接入稳定性与QQ自建WEBSOCKET.md)。

## 当前产品基线

产品文档以当前运行代码和可复现验收结果为准，当前生产边界如下：

- Web、Admin、文件/项目/日历/画布等公开 API 由 Python 3.12 + FastAPI 提供；Agent Loop、IM worker、网关和 scheduler 仍由 Python 负责。
- TypeScript 只保留前端构建和独立 RAG worker，不作为公开 API、Agent、IM 或 scheduler 的替代后端；数据库 schema 迁移继续由 Alembic 负责。
- 业务实时更新由 Python 业务写入侧发布 canonical event，经 Redis event bus 由 FastAPI SSE 提供给前端；聊天生成流、Admin 日志流、文件下载流和终端 PTY WebSocket 保持独立生命周期。
- 群级反思只维护群本身；被动群消息累计 50 条后，由一次 member-batch 使用完整群上下文批量维护多个群友的 `profile`、`pattern`、`summary` 和长期 `memory`。私聊继续使用 `private_reflection`，不与群友批反思混用。

`docs/agent/` 记录实现架构和运行链路，`docs/prds/` 记录产品目标、功能边界和验收状态；两者出现冲突时，先核对代码和测试，再在对应文档中修正，不在 PRD 内保留第二套实现说明。

## 文件命名

`PRD-<编号>-<简短主题>.md`

- 编号按模块/领域分组自增（如 IM 相关用 `IM-1`、`IM-2`），不用全局流水号，方便看出同一领域的文档演进关系。
- 主题用中文短语，不用英文缩写堆砌，一眼看出是什么。

## 文档头部

```markdown
# <PRD 标题>

> 状态：<当前能力状态，例如“部分完成，安全事件总览待实施”>
> 创建：<YYYY-MM-DD>
> 最近更新：<YYYY-MM-DD>
> 关联模块：`path/to/file.py`、`path/to/other.vue`
> 背景参考：<如有参考实现/外部文档，注明来源>
```

`状态` 行是全文档最重要的一行——任何人（包括未来的 AI）打开文档，第一眼要知道当前能力做到什么程度。它描述实际结果，不写 Phase；每次能力状态变化都要回来更新这一行和 `最近更新` 日期。

## 章节结构

按以下顺序编号（不是所有 PRD 都需要每一节，简单的改动可以跳过不适用章节，但不能因此创建第二份 TODO）：

0. **实际状态** — 只读摘要表：`能力/结果 | 状态 | 说明`。状态用 ✅ 已完成 / 🟡 部分完成 / 🔲 待评估 / 🚧 进行中。这里只说明当前能力和结果，不按 Phase 展开、不列实施任务、不写复选框。
1. **背景与目标** — 为什么做、现状痛点、目标和明确不做什么。
2. **功能需求** — 每条需求用 `FR-<模块缩写>-<序号>：<需求名>` 作为三级标题。只写目标行为、触发条件和边界，不写“已完成/待实施”等进度信息。
3. **技术方案** — 按子系统说明实现思路、依赖、环境变量、数据和日志隐私边界。只写方案和约束，不创建任务列表。
4. **验证与上线** — 只写验收方法、测试命令、灰度开关、观测指标、发布范围和回滚方式。可以引用唯一 TODO 的编号，但不得重新列出 TODO、Phase 清单或同义任务。
5. **风险与待确认问题** — 先写 `风险 | 影响 | 对策`，再写待确认事项。待确认事项只记录尚未定案的问题，不得替代实施 TODO。
6. **唯一实施 TODO** — 全文唯一可执行任务清单，也是唯一事实来源。任务可以按 Phase 分组，但每个可验收动作必须单独一条，并包含稳定编号、责任边界和验收标准。

### 唯一实施清单规则

- 每份 PRD 只能有一个标题为 `唯一实施 TODO` 的清单；不得在其他章节出现第二份任务清单。
- 每个交付结果只出现一次。一个任务可以包含多个文件，但不能按“后端实现 / 前端接入 / 测试验收”拆成语义重复的三项；需要拆分时必须是独立可验收的结果。
- 任务使用稳定编号，例如 `SEC2-001`，后续章节只引用编号，不复制任务文字。
- 每项至少包含：`编号`、`状态`、`任务`、`验收标准`。推荐按 Phase 分组，并使用独立复选项：

  ```markdown
  ### Phase 1：安全事件持久化

  - [x] `SEC2-001` 接入安全事件事实表；验收：迁移通过，跨用户测试通过，敏感字段不落明文。
  ```

- 每一条任务必须使用独立的 `[x]` 或 `[ ]`；不要把多个可独立验收的动作合并成一条。
- 已完成项保留为 `[x]`，未完成项使用 `[ ]`，进行中在任务文字中标注 `🚧`，部分完成在任务文字中标注 `🟡`；不要删除历史项或另起一份“剩余 TODO”。
- Phase 只能出现在唯一 TODO 内，用于组织实施顺序；实际状态摘要不得按 Phase 展开。
- “实际完成项”“剩余工作”“后续计划”“Phase X TODO”“验收清单”都不能成为第二个任务源；它们必须合并为结果摘要、验收说明或唯一 TODO 的行。
- 需求、技术方案和风险章节不得使用 `[ ]` / `[x]` 表示实施进度。只有唯一 TODO 使用可执行复选状态。
- 文档头部状态、实际状态表和唯一 TODO 不一致时，以唯一 TODO 为准；修改时必须同步修正摘要，不得保留互相矛盾的历史说法。

## 状态标记约定

- ✅ 已完成 — 代码已合并/已验证。
- 🟡 部分完成 — 已有可运行实现，但仍有明确的功能、配置或验收缺口。
- 🔲 待评估 / 待确认 — 还没做，或做了但没有真实环境验证。
- 🚧 进行中 — 正在做。
- 如果某项结论后来被推翻或补充（比如"待确认问题"里的猜测被证伪），直接在原条目上更新，不要另起一条，保持单一事实来源。

## 语言与风格

- 全文中文，代码/字段名/环境变量用反引号包裹保持英文原名。
- 描述功能需求和风险时避免空泛表述（"提升稳定性"），优先给可验证的具体行为（"丢弃 `app_id` 不匹配的错投事件"）。
- 需求名之外的正文可以用列表/表格，不必大段散文。

## 何时创建新 PRD vs 更新旧 PRD

- 同一领域的延续性工作（比如 IM 稳定性专题下新增一个阶段）→ 更新现有 PRD，编号不变。
- 全新独立特性/模块 → 新建 PRD，走新编号。
- 判断不明确时，倾向于更新现有文档——PRD 太碎会增加以后检索和比对的成本。
