## 1. 背景与目标

### 1.1 背景

当前咕咕 QQ 回复需要等待 Agent 完整生成后再发送。模型调用、工具调用或上下文较长时，用户只能看到等待，难以判断咕咕是否仍在工作。

QQ 官方提供 C2C `stream_messages` 接口，可以在客户端中持续更新同一条回复消息。目标是让 QQ 私聊具备和网页/飞书相近的“边生成边显示”体验，同时不破坏现有 Agent、消息落库、失败回退和群聊行为。

### 1.2 目标

- QQ C2C 私聊回复能够逐步显示，用户只看到一条不断更新的消息。
- 流式发送失败时，仍能可靠得到一次普通回复。
- 不改变 Agent 的工具循环、上下文组装、缓存策略和最终回复内容。
- 群聊继续使用普通消息，避免超出 QQ 流式接口适用范围。
- 不在日志中输出聊天正文，只记录流会话、帧序号、状态和错误摘要。

### 1.3 不做什么

- 不为 QQ 群聊接入 `stream_messages`。
- 不把每个 token 作为一条普通 QQ 消息发送。
- 不修改 Runtime、Agent 上下文架构或模型供应商适配协议。
- 不以“发送处理中”可见消息和流式回复同时占位，避免重复回复。

## 2. 功能需求

### FR-QQ-1：C2C 私聊流式回复（✅）

当收到 QQ C2C 私聊并且 `private_streaming_enabled=true` 时，Agent 使用现有 `run_stream()` 产生文本增量，并交给 QQ 流式发送适配器。

用户侧表现：

- 首次内容出现后创建一条 QQ 回复消息；
- 后续内容替换同一条消息，而不是新增消息；
- 生成结束后保留最终完整文本；
- 空回复沿用现有空回复错误处理，不创建空流。

### FR-QQ-2：累计全文与节流（✅）

适配器必须将文本增量累计为 `fullText`，以 `replace` 模式发送当前完整文本。默认约 500ms 刷新一次，允许在 300–500ms 范围内调整；结束时立即发送最终内容，不因节流定时器延迟完成。

同一帧不能重复发送未变化的全文。节流任务不能阻塞 Agent 生成，也不能为每个 token 创建 HTTP 请求。

### FR-QQ-3：流式协议生命周期（✅）

每个流式会话必须满足：

- 每个新流生成新的 `msg_seq`；同一流的所有帧共用该序列；
- `index` 从 `0` 开始递增且不重复、不跳号；
- 首帧使用 `input_state=1`；
- 后续帧携带首帧响应返回的 `stream_msg_id`；
- 结束帧使用 `input_state=10`，继续携带最后完整文本和 `stream_msg_id`；
- 所有请求通过一个串行 Promise 队列发送。

请求体使用 `input_mode=replace`、`content_type` 和 `content_raw`。队列任务执行时才读取最新 `stream_msg_id`，不能在入队时提前构造后续请求体。

### FR-QQ-4：失败降级与去重（✅）

发送器记录是否成功发送过流式帧：

| 状态 | 行为 |
|---|---|
| 首帧前失败 | 使用现有普通 C2C 发送与主动发送回退，完整回复只发送一次 |
| 已发送部分帧后失败 | 不再发送完整普通消息，记录错误并保留已显示内容 |
| 结束帧失败 | 不重复发送全文，记录流结束失败 |
| 限流/临时错误 | 按有限次数退避重试，超过上限按上述规则处理 |

流式接口失败不能触发第二次 Agent 生成。

### FR-QQ-5：开关与群聊隔离（✅）

新增 `private_streaming_enabled` 作为 QQ Bot 的私聊流式开关：

- 开启：C2C 私聊使用流式；
- 关闭：C2C 私聊使用现有普通发送；
- 群聊：无论开关状态都不调用 `stream_messages`，继续普通发送。

设置说明需要明确：部分 QQ 客户端可能不展示流式过程，关闭后会恢复一次性发送。

### FR-QQ-6：消息落库与审计（✅）

Agent 完成后仍只落库一条最终 assistant 消息，不为中间帧写多条业务消息。日志只记录 `sessionId`/目标类型、流状态、`msg_seq`、`index`、是否已有 `stream_msg_id`、重试次数和脱敏错误摘要，不记录完整回复正文。

## 3. 技术方案

### 3.1 组件边界

```text
QQ gateway
  -> IM worker
  -> Agent run_stream()
  -> QQTextStream.push(delta)
  -> 累计全文 / throttle / 串行队列
  -> QQ /v2/users/{openid}/stream_messages
```

建议在 QQ gateway 或独立的 QQ 发送模块中提供 `QQTextStream`，对上层暴露：

```ts
interface QQTextStream {
  push(delta: string): void
  finish(finalText: string): Promise<void>
  hasSent(): boolean
}
```

`run_stream()` 只负责产生 Agent 事件；QQ 适配器负责平台帧、节流、重试和降级，不把 QQ 协议字段泄漏到 Agent 层。

### 3.2 与现有 IM 路径的接入

当前 QQ 主要路径是 `run_collect()` 后调用普通 C2C/群聊发送。接入后按以下条件选择：

```text
message.chat_type == c2c && private_streaming_enabled
  -> run_stream() + QQTextStream
else
  -> 现有 run_collect() + 普通发送
```

如果当前网关存在可见的快速 ACK，流式路径不能同时发送该 ACK；内部队列确认可以保留，但不能制造第二条用户可见回复。

### 3.3 并发与串行

同一流内部必须串行发送，避免首帧响应尚未返回时后续请求缺少 `stream_msg_id`。不同用户的流可以并行，但同一 QQ 会话仍应沿用现有 Agent 串行约束，防止两条回复互相覆盖。

流结束、异常和进程退出时必须清理定时器、队列引用和流状态，不能遗留后台定时器或继续发送旧流内容。

### 3.4 内容格式

第一阶段优先使用纯文本 `content_type=text`，沿用普通发送的 Markdown/纯文本判断和回退策略。若真实 QQ 客户端确认流式 Markdown 稳定，再单独评估 `content_type=markdown`；不能因为普通消息支持 Markdown 就默认假设流式接口同样支持。

## 4. 验证与上线

### 4.1 自动化测试

至少覆盖：

- 短回复：首帧、结束帧、全文一致；
- 多个 delta：累计全文单调增长，不发送独立分片；
- 快速连续 delta：请求串行，后续帧带首帧 `stream_msg_id`；
- 不同流：`msg_seq` 不重复；
- `index` 连续递增；
- 首帧失败：普通发送只调用一次；
- 中途失败：不重复发送完整回复；
- 限流重试有上限；
- 空回复不创建流；
- 关闭私聊开关：不调用流式接口；
- 群聊：不调用流式接口；
- Agent 最终只落库一条 assistant 消息。

### 4.2 灰度与真实验证

先在 QQ sandbox 或单个测试 Bot 开启，分别用手机 QQ 和桌面 QQ 验证：

1. 短回复；
2. 持续生成回复；
3. 含工具调用的长回复；
4. 生成中断/网络失败；
5. 连续发送多轮私聊；
6. 群聊保持普通消息且不受开关影响。

观察关键日志：流创建、首帧成功、更新帧数量、结束帧、降级原因和 QQ HTTP 错误码。日志不得包含正文、附件名或用户输入。

### 4.3 回滚

关闭 `private_streaming_enabled` 即可回到现有普通发送路径；不需要回滚 Agent 或数据库结构。若发现流式客户端兼容性问题，默认关闭开关并保留协议测试。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 不同 QQ 客户端不展示流式更新 | 用户仍看到延迟或最终消息 | 手机/桌面分别验证；必要时默认关闭 |
| QQ 流式接口限流 | 流中断或结束失败 | 300–500ms 节流、串行队列、有限退避 |
| 首帧成功后后续失败 | 用户看到半截回复 | 禁止普通全文重复发送，记录失败并保留已有内容 |
| Agent 结束与节流刷新竞态 | 最终内容丢失或重复帧 | `finish()` 取消定时器，等待队列后发送最终帧 |
| Markdown 在流式接口不兼容 | 请求失败或显示异常 | 第一阶段优先纯文本，单独验证 Markdown |
| 群聊误走 C2C 流式接口 | 回复失败或路由错误 | 路由条件强制要求 `chat_type=c2c`，补测试 |

待确认：

- 🔲 真实 QQ 账号和桌面端是否都能看到中间替换帧。
- 🔲 QQ 流式接口对 Markdown、内容长度和限流的真实限制。
- 🔲 是否需要产品层默认开启，还是先默认关闭进行灰度。
