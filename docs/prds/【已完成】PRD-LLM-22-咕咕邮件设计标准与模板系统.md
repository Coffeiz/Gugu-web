## 1. 背景

咕咕已经支持 Agent 邮件、用户 SMTP、Admin SMTP、密码重置、反馈通知和安全告警，但目前邮件样式主要由调用方或模型临时拼接 HTML，存在以下问题：

- 同类邮件的标题、间距、按钮和颜色不一致；
- 模型生成的 HTML 难以保证邮件客户端兼容性；
- 前端设计令牌与邮件颜色可能逐渐漂移；
- 纯文本 fallback、HTML 清洗和发送状态虽然已有，但没有统一模板入口；
- 用户说“发一封好看的邮件”时，Skill 没有明确的标准输出方式。

本 PRD 建立咕咕邮件的视觉、结构、安全和工具调用标准。

## 2. 目标

1. 建立一套与咕咕前端视觉一致的邮件语义令牌。
2. 统一系统邮件、Agent 邮件和定时任务邮件的基础布局。
3. 让模型只提供邮件内容和语义字段，不直接负责 HTML 排版。
4. 所有 HTML 邮件保留纯文本 fallback，并兼容主流邮件客户端。
5. 统一发送成功、SMTP 已接受、发送失败和超时的结果语义。
6. 保持个人 SMTP、服务器默认 SMTP 和收件人解析逻辑不变。
7. 定时任务邮件失败可区分原因，但不在发送层自动重试非幂等 SMTP 操作。

## 3. 非目标

- 本期不实现邮件营销、群发、订阅退订和发送队列。
- 本期不允许邮件模板加载远程 CSS、脚本、追踪像素或外部图片。
- 本期不把前端 CSS 变量直接注入邮件；邮件必须使用编译后的静态值。
- 本期不改变 SMTP 配置、确认门、定时任务授权和收件人权限规则。

## 4. 产品标准

### 4.1 邮件类型

规划统一以下模板，Phase 1～2 已实现：

| 模板 | 用途 | 默认结构 |
|---|---|---|
| `notification` | ✅ 已完成 | Agent 普通通知、结果说明 |
| `reminder` | ✅ 已完成 | 日历和定时任务提醒 |
| `report` | ✅ 已完成 | 汇总、进度和结果报告 |
| `test` | ✅ 已完成 | SMTP 测试邮件 |
| `security` | ✅ 已完成 | 密码重置和安全告警 |

所有模板都必须支持纯文本和 HTML 两种输出；纯文本是主内容的降级版本，不从 HTML 反向解析。

### 4.2 邮件令牌

邮件只使用语义令牌，不直接依赖前端 CSS 变量。令牌值以当前咕咕主题为基准，邮件侧编译成静态 CSS：

| 语义令牌 | 用途 | 规则 |
|---|---|---|
| `brand` | 品牌标识、主按钮 | 使用咕咕主紫色，不使用高饱和纯色 |
| `surface` | 邮件卡片背景 | 浅色背景下与页面底色有明确层次 |
| `canvas` | 邮件整体背景 | 不使用复杂渐变 |
| `text` | 标题和正文 | 保证浅色/深色客户端可读性 |
| `muted` | 辅助说明、时间、页脚 | 对比度不能低到无法阅读 |
| `border` | 分割线和卡片描边 | 使用低对比度中性色，不使用纯白线 |
| `success` / `warning` / `danger` | 状态提示 | 颜色只表达状态，不依赖 Emoji |
| `radius` / `space` / `font` | 几何与排版 | 使用固定兼容值，不能依赖 CSS 变量 |

标准要求：

- 邮件正文最大宽度 600px；
- 主体内容使用表格布局或邮件客户端兼容的块级布局；
- 样式尽量内联，禁止依赖外部样式表；
- 按钮使用明确的文字和完整 URL fallback；
- 不使用纯白分割线、不可读的浅灰文字和仅靠颜色表达的关键信息；
- 不强制使用深色模式，邮件在客户端深色模式下仍需可读。

### 4.3 Agent 工具字段

模型面向的 `send_email` 使用语义字段：

```json
{
  "subject": "项目进度更新",
  "body": "纯文本正文，始终必填",
  "template": "notification",
  "title": "项目进度更新",
  "preheader": "咕咕为你整理了最新进展",
  "sections": [
    {"heading": "当前状态", "text": "项目已经进入执行阶段。"}
  ],
  "actions": [
    {"label": "打开项目", "url": "https://example.com/projects/1"}
  ]
}
```

字段规则：

- `subject`、`body` 继续必填；
- `body` 是所有客户端的可靠 fallback；
- `template` 使用固定枚举，省略时默认为 `notification`；
- `title` 省略时使用 `subject`；
- `preheader`、`sections`、`actions` 可选，均有数量和长度上限；
- `actions.url` 必须通过现有 URL 安全校验；
- 模型不再直接传任意 HTML 作为默认排版入口；模板 HTML 由服务端生成并清洗；
- 收件人、确认凭证、自动任务授权和 SMTP 选择逻辑保持现有规则。

如果后续确实需要特殊 HTML，应新增经过审核的模板，而不是让模型绕过模板层。

### 4.4 Skill 标准

邮件 Skill 必须明确：

- 什么时候使用 `notification`、`reminder`、`report` 和 `test`；
- 默认收件人是当前用户注册邮箱，不得因为看不到邮箱而索要地址；
- 普通交互式邮件发送前需要确认；用户在页面创建并授权的定时邮件不重复确认；
- 正文先写清事实，HTML 只负责结构和视觉，不添加正文没有表达的信息；
- 工具返回 SMTP 已接受后才能说“已提交发送”，不能承诺最终送达；
- 必须根据工具返回的结构化失败状态如实反馈超时、未配置、认证失败或 TLS 错误。

Skill 不应包含具体 CSS、颜色值或大段 HTML；视觉标准只在邮件模板层维护。

## 5. 技术方案

```text
Agent / 系统通知
        ↓ 语义邮件模型
email_templates.py
        ↓ 选择模板 + 编译静态令牌 + 生成纯文本/HTML
email.py
        ↓ 收件人解析 + SMTP 选择 + 发送超时 + 脱敏投递指标
        SMTP provider

定时任务 `email` 渠道
        ↓ 注册邮箱 + 用户主题/配色
        ↓ `reminder` 模板
        ↓ 单次 SMTP 投递（失败保留任务/等待下一次计划）
```

### 5.1 模板层

新增模板渲染器，负责：

- 校验模板枚举和结构化字段；
- 生成 HTML 和对应纯文本；
- 转义所有用户内容；
- 应用静态邮件令牌；
- 统一品牌头、内容容器、按钮和页脚；
- 对模板输出执行最终 HTML 清洗。

### 5.2 发送层

公共发送服务继续负责：

- 个人 SMTP 优先，未启用时回退服务器 SMTP；
- SMTP 单步 socket timeout 和整次发送总超时；
- 返回 `sent / failed`、`smtp_accepted`、`smtp_timeout` 等结构化状态；
- 日志只记录脱敏错误类型，不记录正文、邮箱密码、Token 或完整地址。

### 5.3 令牌同步

邮件令牌不是运行时读取前端 CSS，而是一个经过评审的静态映射。修改前端品牌令牌时，必须同步检查邮件令牌，并通过快照测试防止邮件颜色、边框和间距漂移。

## 8. 安全与兼容性

- 所有用户内容必须 HTML escape；URL 只允许现有安全协议和校验后的地址；
- 禁止脚本、事件属性、iframe、外部追踪资源、远程 CSS 和未审核图片；
- 邮件密码、API Key、确认 Token 不进入正文、日志或模板字段；
- HTML 邮件始终附带纯文本版本；
- 模板生成失败时返回明确错误，不静默发送格式损坏的邮件；
- 邮件客户端不支持现代 CSS 时，仍能阅读标题、正文、按钮文字和 URL；
- 不改变 SMTP 凭据加密、个人配置启用开关和收件人归属校验。

## 9. 验收标准

- Agent 不传 `html` 也能生成统一风格的 HTML + 纯文本邮件；
- 不同模板的品牌色、按钮、边框、间距和页脚符合令牌标准；
- 用户正文中的 HTML、脚本、事件属性和危险链接不会原样进入邮件；
- Gmail、Outlook、Apple Mail 的基础结构可读，纯文本版本内容完整；
- SMTP 未响应时，工具在总超时内返回结构化失败，不让 Agent 永久等待；
- 发送前确认只出现一次，用户已授权的定时任务不重复确认；
- 个人 SMTP、服务器 SMTP fallback、测试邮件和密码重置均有回归测试；
- 前端 typecheck/build、后端定向测试和邮件模板快照检查通过；
- 文档、Skill、工具简介和 PR 描述说明模板字段与发送状态语义。

## 10. 决策记录

本方案选择“语义字段 + 服务端模板”，不选择“模型直接生成任意 HTML”，原因是：模板更容易保证安全、兼容性、品牌一致性和后续主题升级；模型仍然可以决定标题、正文分组和是否提供操作按钮，但不负责实现邮件客户端细节。
