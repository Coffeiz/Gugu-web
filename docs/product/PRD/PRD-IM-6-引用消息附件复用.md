# 引用消息附件复用 PRD

> 状态：讨论稿，可行性已验证，未开始设计实施细节
> 创建：2026-08-09
> 关联模块：`backend/agent/im/parsers/qq.py`、`backend/agent/im/media_ingress_wechat.py`、`backend/agent/im/media_ingress.py`、`backend/app/core/chat_attach.py`
> 依赖：PRD-STORAGE-1（`chat_attachments` 状态机落地后才有稳定的"按平台消息 ID 反查附件"的查询对象）
> 不是：PRD-IM-5（QQ 表情本地缓存）的升级版——两者复用键的性质不同，故意保持独立，见第 5 节。

## 1. 背景

排查 PRD-STORAGE-1 的 `quoted` 字段语义时发现：用户在 QQ/微信里引用回复一条带媒体的历史消息时，网关会把被引用消息的媒体**重新下载、重新 `stage()` 成一条全新附件**（`agent/im/media_ingress.py:178`、`agent/gateway/qq.py:247`），即使这份内容咕咕在处理原始消息时已经下载过一次。

这是否值得优化，取决于 QQ/微信有没有给"这次引用指向的是哪条历史消息/哪份媒体内容"提供一个稳定、可复用的标识。本 PRD 记录这次可行性调查的过程和结论。

## 2. 调查方法

在 `agent/im/parsers/qq.py` 的 `_extract_quoted` 和 `agent/im/media_ingress_wechat.py` 的 `extract_quoted` 里临时加了探针（已删除），把带媒体的引用元素原始结构落进受限诊断出口（`logs/gugu-diag.log`，只有直登服务器能看，不进任何用户可见/后台可见出口）。在 devserver 上实测：

1. 发送一张普通图片（QQ "小图"上传模式）、引用它 4 次（跨约 4.5 分钟、4 个独立 webhook 事件）。
2. 发送一个文件（QQ "文件"上传模式，图片以文件形式发送）、同样引用 4 次。
3. 引用一条本身是"引用消息"的消息（验证没有直接媒体的引用不会误触发）。

## 3. 调查结论

### 3.1 QQ："小图"模式和"文件"模式返回结构不同，但都有一个稳定字段

- **`fileid`**（出现在"小图"模式的下载 URL query string 里）：同一条消息被反复引用时完全一致；"文件"模式的下载 URL（`ftn_handler/...`）里**没有这个字段**，两种模式结构不统一，不能作为通用方案。
- **`rkey`**（"小图"模式）/ 文件模式的整个 `ftn_handler` token：**每次引用都不同**，是带时效的签名下载凭证，不代表内容身份，不能当缓存键。
- **`msg_idx`**（`elem.msg_idx`，形如 `REFIDX_...`，来自 `scene_ext` 的 `ref_msg_idx`）：**两种上传模式下都稳定**，同一条消息 4 次独立引用（跨 4.5 分钟）值完全一致。这是 QQ 对"被引用的这条消息"本身给出的持久引用标识，跟走哪种媒体上传通道无关。

**结论**：不需要靠 QQ 的文件级标识（`fileid`，覆盖不全）或者下载后计算内容 hash（会失去"避免重新下载"这个优化本身的意义）。应该用 `msg_idx`（或其代表的"被引用消息"身份）去匹配咕咕自己是否已经处理过这条历史消息的附件，命中就直接复用已有的 `attach_id`/`storage_key`。

### 3.2 微信：未验证

只对 QQ 做了实测。微信 `image_item.media` 里的 `encrypt_query_param`/`full_url`/`aeskey`（`media_ingress_wechat.py:23-30`）是否有等价的"消息级稳定标识"，需要单独探针验证，不能直接套用 QQ 的结论——微信的引用消息结构（`ref_msg.message_item`）跟 QQ 的 `msg_elements`/`scene_ext` 完全是两套协议，字段命名和稳定性都要重新确认。

## 4. 可行性结论

**可行**，但匹配依据是"咕咕自己是否已经处理过被引用的这条消息"，不是"QQ/微信给的文件是否同一份"：

```
引用事件到达
  ↓
提取被引用消息的平台标识（QQ: msg_idx；微信: 待验证）
  ↓
查询：咕咕此前是否已经为这条平台消息暂存过附件？
  ├─ 命中且附件仍然可用（依赖 PRD-STORAGE-1 的所有权状态，附件所属消息/会话没被删）
  │     → 跳过下载，为当前引用消息新建一条 chat_attachments 行，storage_key 指向已有的
  │       物理字节（不重新写一份，只是复用同一个 storage_key）
  └─ 未命中/已被清理
        → 走现有逻辑：重新下载、重新 stage()
```

**重要修正（写初稿时想岔了一步）**：这里"复用"指的是**新消息获得自己独立的 `attach_id`/`chat_attachments` 行，只是这行的 `storage_key` 恰好和原消息那行相同**——不是把原消息那条附件记录的 `message_id` 改指到新消息、或者让两条消息共享同一条 `chat_attachments` 行。原因：PRD-STORAGE-1 已经决定 `chat_attachments.message_id` 用简单外键、不做多对多关系表（因为排查时没找到"一个 attach_id 被多条消息共同引用"的场景）——如果这里让两条消息真的共享同一条附件记录，就是重新把那个场景造出来了，会推翻那个决定。用"两条独立记录、同一个 storage_key"的方式可以拿到复用下载的好处，同时不需要动 `chat_attachments` 的数据模型。

**代价**：存储层清理（Storage-1 的安全网扫描、`delete_session` 级联删除）不能再只看"这一条 `chat_attachments` 行对应的消息/会话是否还在"就直接删 `storage_key` 的物理字节——必须先确认**没有任何其他存活的 `chat_attachments` 行还指着同一个 `storage_key`**（按 `storage_key` 做引用计数，而不是按单条记录的所属消息判断）。这是本 PRD 给 PRD-STORAGE-1 的清理逻辑新增的一个约束，需要同步过去。

这不是一套新的缓存机制，而是给 PRD-STORAGE-1 即将落地的 `chat_attachments` 表加一个"按平台消息标识反查"的索引——原始消息第一次到达时，除了记录 `attach_id`/`storage_key`，多记一个 `platform_message_id`（QQ 场景下就是 `msg_idx` 或其对应的稳定字段）。所以本 PRD 依赖 PRD-STORAGE-1 先落地，不能独立于它实施。

## 5. 为什么不并入 PRD-IM-5（QQ 表情本地缓存）

两者表面相似（都是"IM 场景下避免重复下载"），但结构不同，故意不合并：

| | IM-5（表情缓存） | 本 PRD（引用附件复用） |
|---|---|---|
| 复用键 | 协议给的 `face_id`（小集合、跨消息跨用户复用） | 平台消息标识（`msg_idx`，只在"同一条消息被再次引用"时命中） |
| 存储位置 | 刻意独立的本地缓存目录，脱离 `StorageBackend`/`chat_staging`（PRD-IM-5 §5.3），不进用户可见的存储体系 | 直接复用 `.chat_staging` 里已经存在的附件字节，是 Storage-1 所有权模型的自然延伸，不是新缓存层 |
| 命中范围 | 任意两条消息，只要表情 ID 相同 | 只有"引用回复"这一个触发路径 |
| 前置依赖 | 无 | 依赖 PRD-STORAGE-1 的 `chat_attachments` 状态机先落地 |

把两者塞进同一个 PRD 会把两套不相关的基础设施耦合在一起，保持独立更清晰。

## 6. 非目标

- 不通过下载内容再算 hash 来判断是否同一份内容——`msg_idx` 已经足够，做 hash 校验只是徒增一次下载，违背优化本身的目的。
- 不缓存"被引用消息之外"的任意历史附件——只在真实发生"引用回复"这个动作时才查找复用，不做预取/预缓存。
- 本 PRD 只覆盖 QQ；微信要不要做，等第 3.2 节的验证结果出来再决定，不在这个版本里下结论。

## 7. 待确认问题

- 微信是否有等价的稳定标识，需要单独探针验证。
- `msg_idx` 的稳定性只验证了约 4.5 分钟、4 次独立事件，长期稳定性（比如几天后再引用同一条消息）未验证。
- 一条消息带多个附件时，`msg_idx` 定位到的是"消息"还是"消息里第几个附件"，需要构造多附件消息验证顺序/对应关系（同类风险 PRD-IM-5 §8 也提到过）。
- 被引用消息的原始附件如果已经因为 Storage-1 的生命周期规则被清理（消息/会话已删除），复用应该优雅回退到重新下载，不能报错。
- **（必须解决，实施前置条件）复用创建共享引用时，必须保证源附件行在此期间不会被并发删除**：Storage-1 的 `try_delete_storage_if_unreferenced()` 是"先检查还有没有其他引用、再删物理字节"，检查和删除本身不是原子操作。如果本 PRD 的"复用"逻辑是"读到一条历史附件 → 用它的 `storage_key` 建一条新行 → commit"，那么存在这样的时序：Storage-1 那边删除源附件时，检查阶段还没有新引用（判定"可以删"），但检查完、真正 `storage.delete()` 之前，本 PRD 的复用逻辑刚好插入了一条指向同一个 `storage_key` 的新行——物理字节被删掉后，新行立刻变成指向不存在文件的坏引用。这是 Storage-1 § FR-STORAGE-1-1 第 4 条不变量明确点名、但要求本 PRD 负责解决的一半：**复用逻辑必须在读取源附件到新行 commit 成功期间，锁住源附件行**（`SELECT ... FOR UPDATE`、advisory lock，或其他等价机制均可，具体选型留到设计阶段），确保这段时间内源行不会被删除路径拿到并删除；如果加锁时发现源附件已经被删除（说明删除赢得了竞态），复用直接判定未命中、走回退重新下载，不强行复用一个可能已经不存在的对象。
