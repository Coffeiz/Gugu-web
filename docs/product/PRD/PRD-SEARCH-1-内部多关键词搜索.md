## 1. 背景与目标

当前内部搜索工具把输入作为一个完整字符串进行 `ILIKE '%关键词%'` 匹配。输入多个候选词时，只有这些词以完全相同的连续文本出现才会命中；如果某一个词未命中，整个查询可能返回空结果。Agent 为了提高召回率只能重复调用搜索工具，增加延迟和工具调用次数。

本 PRD 为内部搜索增加一次调用搜索多个关键词的能力：

1. 一次工具调用支持多个候选关键词。
2. 默认使用 OR 语义，任意关键词命中即可返回，解决单个词未命中的问题。
3. 支持 AND 语义，要求所有关键词都至少命中一个可搜索字段。
4. 对结果按命中数量和字段重要性排序，减少 OR 查询带来的噪声。
5. 统一供站内搜索工具复用，不改变外部网页搜索的查询语义。

本 PRD 不实现 BM25、向量检索或通用 RAG；这些能力保留给记忆召回和未来 RAG 模块。

## 2. 功能需求

### FR-SEARCH-1：多关键词输入（已实现）

搜索工具支持：

```json
{
  "queries": ["项目", "部署", "上线"],
  "mode": "OR"
}
```

约束：

- `queries` 至少包含一个非空词，最多 8 个。
- 单个关键词最多 64 个字符，服务端负责裁剪或拒绝超限输入。
- 自动 trim、去空、去重；不把数组拼接成一个带空格的字符串。
- 现有 `q` 或 `keyword` 单字符串输入在内部转换为一个元素的 `queries`，保持现有调用方可用。

### FR-SEARCH-2：OR/AND 匹配模式（已实现）

- `OR`：任意关键词在任意可搜索字段命中即可返回，默认模式。
- `AND`：每个关键词都必须至少在一个可搜索字段中命中。
- 大小写沿用数据库当前不区分大小写的行为。
- 中文、英文、数字按子串匹配，不依赖空格分词。
- 未来需要短语精确匹配时另行增加 quoted phrase 语法，不在首版混入普通关键词。

### FR-SEARCH-3：统一接入站内搜索工具（已实现）

首批接入：

- `global_search`
- 项目、文件、文件夹、日程、客户、思维便签搜索
- `search_conversations`
- `group_context_search`

各工具保留原有数据范围、用户隔离、群隔离和返回格式。没有搜索语义的列表、读取、删除等工具不接入多关键词接口。

### FR-SEARCH-4：相关性排序（已实现）

结果按以下因素组合排序：

1. 命中的关键词数量越多，排名越高。
2. 标题、名称等短字段命中优先于摘要和正文。
3. 同分时沿用各工具原有的更新时间或创建时间排序。

首版只需要可解释的字段权重，不引入 BM25 或向量模型。

### FR-SEARCH-5：空结果与降级（已实现）

- OR 模式无结果时，返回空结果并保留实际解析后的关键词，方便 Agent 改写查询。
- AND 模式无结果时，不自动偷偷降级为 OR；由调用方决定是否重试 OR，避免语义不透明。
- 查询参数异常、超限时返回明确参数错误，不通过宽泛兜底掩盖问题。

### FR-SEARCH-6：前端全局搜索的多关键词输入（已实现）

前端全局搜索框只提供 OR 语义，不增加复杂筛选控件：

- 用户输入以空格分隔多个关键词，例如 `项目 部署 上线`。
- 前端按连续空白拆分、去空、去重后发送 `queries`。
- 请求固定使用 `mode: "OR"`，任意关键词命中即可返回。
- 单个连续短语仍作为一个关键词传递，不在前端强制拆分引号或标点内部内容。
- AND 模式只保留给后端内部工具和未来 API 调用方，网页搜索不暴露该选项。
- 输入继续使用 debounce，并取消尚未完成的上一请求，避免快速输入造成请求堆积。

### FR-SEARCH-7：Agent 工具与 skills 迁移（已实现）

代码接口完成后，必须同步更新咕咕的工具定义和使用说明：

- 工具 schema 明确 `queries` 数组和默认 `mode: "OR"`。
- skill 文档和工具描述引导咕咕一次传入多个候选关键词，而不是逐个重复调用。
- 对用户明确范围的查询，仍优先调用对应专用工具，不因多关键词能力而扩大搜索范围。
- 旧 `q` / `keyword` 入口只作为迁移兼容，不再作为 prompt 推荐格式。
- 更新相关工具测试样例，确认模型调用格式、返回结果说明和无结果提示一致。

## 3. 技术方案

### 3.1 统一查询模块

新增共享模块，例如 `backend/app/search/query.py`，提供：

- `parse_search_queries(args)`：解析单字符串和数组输入。
- `build_keyword_predicate(fields, queries, mode)`：生成 SQLAlchemy 条件。
- `build_match_score(fields, queries)`：生成可解释的命中评分表达式。

`app` 层不反向依赖 `agent` 层；Agent 工具只负责把工具参数传给共享搜索服务。

### 3.2 字段映射

每种对象显式声明可搜索字段，禁止搜索工具随意扩大字段范围：

| 类型 | 字段 |
|---|---|
| project | `name`、`client`、`current_stage` |
| file | `display_name`、`ext` |
| folder | `name` |
| event | `title`、`description`、`client` |
| client | `name`、`contact`、`email`、`phone`、`notes` |
| note | `title`、`content_plain` |
| conversation | 消息正文、session 标题、摘要 |

### 3.3 性能边界

- 首版继续使用现有数据库查询和限制，不新增外部服务或依赖。
- 多关键词条件使用参数化 SQL，不能拼接原始 SQL 字符串。
- 继续保留每类结果数量上限，避免 OR 查询扩大返回集。
- 记录查询耗时和关键词数量，不记录完整聊天正文或敏感字段。
- 后续如果数据量增长，再单独评估数据库全文索引或 BM25，不在本 PRD 中提前引入。

## 4. 验证与上线

### 4.1 自动化测试

- 单字符串输入与当前结果兼容。
- OR 模式下任意关键词命中即可返回。
- AND 模式下缺少任一关键词时不返回。
- 关键词去空、去重、长度和数量限制。
- 标题命中优先于正文命中，命中数量排序正确。
- 会话和群上下文仍保持用户、bot、群隔离。
- 空结果、非法模式和超限输入返回稳定错误。

### 4.2 手测

- 用多个中文候选词搜索项目、文件和历史消息。
- 验证一个词不存在时 OR 仍能命中其他词。
- 对比 OR 与 AND 的结果差异。
- 在群聊中确认不会搜索到其他群或其他用户的消息。
- 检查全局搜索一次调用覆盖多种对象类型，工具调用次数没有增加。
- 在前端输入以空格分隔的多个关键词，确认按 OR 语义返回结果；连续输入单个短语时保持原有行为。
- 检查工具 schema、skill 文档和 prompt 已从单关键词示例更新为多关键词 OR 示例。

### 4.3 上线与回滚

先只改工具输入解析和站内查询层，保持原有单关键词调用；通过测试后再切换 Agent 提示词使用 `queries`。若出现结果膨胀或耗时回归，可关闭多关键词入口并继续使用单关键词路径，不影响数据写入。

## 5. 风险与待确认问题

| 风险 | 影响 | 对策 |
|---|---|---|
| OR 结果过多 | Agent 获得较多低相关候选 | 命中数、字段权重排序并保留结果上限 |
| `ILIKE '%词%'` 扫描大表 | 查询耗时增加 | 限制关键词数和结果数，后续评估全文索引 |
| 中文词边界不明确 | 拆词可能产生歧义 | 首版不强行分词，关键词由调用方显式提供 |
| 旧调用方仍传字符串 | 接口迁移不完整 | 入口统一转换为单元素关键词数组 |

待确认：

- 🔲 是否需要在首版开放精确短语搜索。
- 🔲 是否需要增加 `NOT` 排除词；首版不支持，避免扩大查询语法。
- 🔲 全局搜索是否允许调用方显式指定 `OR`/`AND`，还是只由 Agent 内部决定。
