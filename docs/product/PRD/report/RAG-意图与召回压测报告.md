# RAG 意图与召回压测报告

## 1. 测试目的

验证“LLM 意图判断 + 词法/向量召回 + 上下文注入”这条链路的耗时和初步质量，重点确认一次召回 20 条和 100 条信息时，主要瓶颈是否在召回层。

本报告记录的是开发环境压测结果，不代表生产数据规模下的最终容量上限。

## 2. 测试脚本与复现方式

脚本位置：

```text
backend/scripts/bench_rag_virtual.py
```

脚本从 `backend/` 目录运行，读取当前环境的 AI 和 Embedding 配置。它支持 BM25、Embedding、LLM 意图判断、真实文档向量缓存和质量指标输出。

生成 30 条真实文档向量并保存缓存：

```bash
cd /home/coffeiz/文档/Workspace/Gugu-web/backend
PYTHONPATH=. .venv/bin/python scripts/bench_rag_virtual.py \
  --docs 30 \
  --embed-docs 30 \
  --top-k 20 \
  --relevant-every 10 \
  --relevant-per-window 3
```

缓存默认保存为：

```text
backend/scripts/.bench_rag_embeddings.json
```

复用已有缓存进行测试：

```bash
PYTHONPATH=. .venv/bin/python scripts/bench_rag_virtual.py \
  --docs 30 \
  --embed-docs 0 \
  --top-k 20 \
  --relevant-every 10 \
  --relevant-per-window 3
```

`index-ready` 输出中的 `quality_valid=true` 表示当前测试文档全部使用真实向量；如果仍有随机向量，质量指标只能用于观察流程，不能用于判断 Embedding 准确率。缓存按模型标识和向量维度失效，缓存文件不纳入 Git。

主要参数：`--docs` 控制文档数量，`--embed-docs` 控制本次真实生成数量，`--top-k` 控制候选数，`--cache` 指定缓存路径，`--query` 指定查询，`--embed-delay` 控制请求间隔。

测试 LLM 重排：

```bash
PYTHONPATH=. .venv/bin/python scripts/bench_rag_virtual.py \
  --docs 1000 \
  --embed-docs 0 \
  --top-k 100 \
  --rerank-models deepseek,minimax
```

该命令固定同一批 BM25 候选，分别使用匹配到的 DeepSeek 和 MiniMax-M3 预设重排，不会切换后台当前激活模型。

## 3. 测试流程

```text
用户输入
  ↓
LLM 结构化意图判断
  ↓
按 sources / scope 过滤候选
  ↓
BM25 召回
  ↓
去重与上下文拼装
  ↓
注入主模型上下文
```

意图输出结构：

```json
{
  "intent": "search_context",
  "sources": ["project", "note", "memory"],
  "keywords": ["文件系统重构", "拖拽动画"],
  "need_current": true,
  "scope": "user"
}
```

测试使用 10,000 条虚拟混合数据，包含项目、笔记、记忆、文件和日程；不读取真实用户聊天、记忆或文件内容。

## 4. 单次召回 100 条

测试查询：

```text
找一下文件系统重构项目和拖拽动画相关的项目、笔记、记忆，看看目前做到哪一步了
```

每个模型只调用一次意图判断，然后由 BM25 一次返回 100 条候选。

| 模型 | 意图判断 | BM25 召回 100 条 | 上下文拼装 | 上下文字符数 | 总耗时 |
|---|---:|---:|---:|---:|---:|
| MiniMax-M3 | 2958ms | 84ms | <1ms | 7388 | 3042ms |
| DeepSeek-v4-flash | 1508ms | 89ms | <1ms | 7388 | 1596ms |

两种模型均成功返回结构化 JSON，并成功召回 100 条信息。

## 5. 多场景本地 BM25 对比

以下测试同样使用 10,000 条虚拟数据，`hits` 是去重后的召回结果数，`ctx_chars` 是最终拼装的上下文字符数。

| 场景 | 查询 | BM25 耗时 | 召回数 | 上下文字符数 |
|---|---|---:|---:|---:|
| 简单项目查询 | 文件系统重构项目 | 19.1ms | 80 | 4084 |
| 跨来源查询 | 文件系统重构 | 14.3ms | 80 | 4728 |
| 明确笔记范围 | 拖拽动画 | 2.0ms | 80 | 3079 |
| 无命中 | 火星基地量子烹饪 | 6.3ms | 0 | 0 |
| 长上下文查询 | 知识系统 项目 方案 | 19.0ms | 80 | 4715 |

索引构建耗时约 73ms。召回量从 20 条增加到 100 条时，BM25 仍处于几十毫秒级，未成为主要瓶颈。

## 6. LLM 意图判断对比

为了测量模型自身的意图判断速度，分别进行了 100 次虚拟查询测试，关闭深度思考，输出结构化 JSON。

| 模型 | 调用次数 | 成功 | 有效 JSON | 中位数 | P95 | 最大耗时 | 总耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|
| MiniMax-M3 | 100 | 100 | 100 | 1453ms | 2978ms | 10243ms | 177.5s |
| DeepSeek-v4-flash | 100 | 100 | 100 | 871ms | 1079ms | 1998ms | 89.3s |

该部分是 100 次调用测试，不是一次召回 100 条；用于单独观察 LLM 意图判断的稳定性。

## 7. 真实 Embedding 缓存与召回质量

使用百炼 `tongyi-embedding-vision-flash` 为 30 条虚拟项目、笔记、记忆、文件和日程生成真实 768 维向量，并保存到：

```text
backend/scripts/.bench_rag_embeddings.json
```

缓存包含模型标识、向量维度、文档文本指纹和向量内容。模型或维度变化时缓存自动失效；缓存文件只用于本地压测，不纳入 Git。

测试查询：

```text
找一下文件系统重构项目和拖拽动画相关的记录
```

测试数据中有 9 条人工标记为相关内容：

| 方式 | @10 Precision | @20 Precision | @20 Recall | 说明 |
|---|---:|---:|---:|---|
| BM25，不经 LLM | 66.7%（按实际返回 6 条） | 66.7%（按实际返回 6 条） | 44.4% | 返回数量较少，但前几条更集中 |
| Embedding，不经 LLM | 40% | 35% | 77.8% | 召回更广，前 20 条覆盖更多相关内容 |
| Embedding + LLM 意图 | 40% | 25% | 55.6% | LLM 重写关键词后召回率下降 |

Embedding 的耗时：

| 阶段 | 首次生成缓存 | 复用缓存 |
|---|---:|---:|
| 查询向量 | 约 200ms | 约 200ms |
| 本地 cosine 排序 | 约 6～16ms | 约 6～16ms |
| Embedding 召回总计 | 约 210ms | 约 220ms |
| LLM 意图 + Embedding | 约 1.8s | 约 2.3s |

具体命中情况表明：BM25 前 6 条命中 4 条相关内容；Embedding 前 20 条命中 7 条相关内容；加入 LLM 意图重写后只命中 5 条。当前测试不支持让 LLM 默认重写 Embedding 查询，保留用户原句更稳。

注意：这是虚拟文本和人工标签的初步质量测试，不等同于真实用户数据上的准确率。正式评估仍需建立真实查询与相关文档标注集。

## 8. 结论

1. BM25 召回 20 条和 100 条的耗时差距不大，当前数据规模下通常仍是几十毫秒。
2. 上下文拼装本身几乎不耗时，100 条测试数据约 7,400 字符。
3. 整体延迟主要来自 LLM 意图判断，而不是 BM25。
4. DeepSeek-v4-flash 在本次测试中比 MiniMax-M3 更快、更稳定。
5. 关闭深度思考后，短 JSON 意图判断不应继承主对话的深度思考设置。
6. 当前没有必要为了 100 条召回引入 LLM 重排；向量召回可以作为 BM25 的并行补充。

## 9. LLM 重排测试

测试流程：

```text
BM25 召回 100 条
  ↓
LLM 输出候选 key 顺序
  ↓
校验 key，缺失项按 BM25 顺序补回
  ↓
上下文注入
```

| 模型 | BM25 候选数 | 重排耗时 | 注入耗时 | 有效排序 key | @20 Precision | @20 Recall |
|---|---:|---:|---:|---:|---:|---:|
| DeepSeek-v4-flash | 100 | 2.34s | <1ms | 15/100 | 100% | 80% |
| MiniMax-M3 | 100 | 2.82s | <1ms | 100/100 | 100% | 80% |

同一批候选的 BM25 基线：

- BM25 排序约 12ms；
- 前 20 条 Precision 为 100%；
- 前 50 条 Precision 为 50%；
- 前 100 条 Precision 为 25%。

测试结论：

1. 重排耗时主要来自 LLM，约 2～3 秒；上下文注入几乎没有成本。
2. 本轮重排没有改善前 20 条质量。
3. DeepSeek 只返回 15 个有效 key，剩余结果由脚本回填，不能视为完整完成了 100 条排序；MiniMax 返回了全部 100 个 key。
4. 当前不建议默认开启 LLM 重排。BM25 已经足够快，质量也足够；重排只适合复杂查询、候选噪声较多或用户明确要求精排的场景。
5. 后续正式评估需要真实查询—文档标注集，不能只依据本次虚拟数据结果。

## 10. 建议方案

首版可以采用：

```text
简单明确的查询
  → 规则/关键词判断
  → BM25

跨来源、范围不明确或行动型请求
  → DeepSeek 无思考模式意图判断
  → 权限与范围过滤
  → BM25 召回
  → 去重
  → token 上限截断
  → 注入上下文
```

建议初始参数：

- 每个来源最多召回 20 条。
- 全部来源去重后最多注入 50～100 条。
- 最终按上下文 token 上限截断，而不是单纯按条数截断。
- 无命中时保留用户原始关键词搜索结果，不让 LLM 直接断言“没有”。
- 低置信度或复杂跨来源请求才调用 LLM 意图判断。

## 11. 测试边界

- 本次 BM25 使用虚拟索引，未连接真实用户数据库。
- 未测真实文件正文解析、分词索引构建和数据库查询耗时。
- 上下文拼装耗时不包含主模型最终回答耗时和 token 计费。
- 生产环境仍需补充真实数据量、权限过滤、并发查询和索引更新测试。
