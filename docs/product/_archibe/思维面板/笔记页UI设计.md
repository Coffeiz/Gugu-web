## 一句话基调

**对齐全站玻璃语言**（v2.1 定）：每日一块轻玻璃底板（同定时任务面板），便签卡与定时任务卡/项目卡同款质感——笔记页不再另起"纸"的视觉体系。曾试过"哑光纸片流"（借右键菜单的薄、近实底无投影），实际效果与全站语言割裂、观感单薄，一轮就废弃了。设计草案"纸条 vs 玻璃"的双语言留给 P2 画布再议（画布上的对比语义与时间流里不同）。

## 为什么横置（v2 改版记录）

第一版是纵向双列 grid + 右侧日期索引。真实数据一进来就露馅：便签多为短句，横跨半屏的宽卡片装一行字，又空又扁；右上角的小日期索引悬在大片空白旁边很尴尬。改为**一天一列、时间横向流动**后：短便签在窄列里天然紧凑；"单日单条右格空着"的问题直接消失（每天独占一列，没有格子要配对）；横置画面跟 P2 画布的"工作台"气质连续。参考形态：周视图日历（列=天、列内竖排条目）。

## 整体骨架（full-bleed，纵向四层）

`/mind` 走 full-bleed（路由 `meta.fullBleed`，DefaultLayout 据此隐藏 topbar、去掉顶部渐变遮罩、`page-content` 收窄留白且不滚动，滚动交给页面自管）。topbar 的 GlobalSearch 由胶囊条右侧的便签筛选补位。

| 层 | 规格 | 玻璃？ |
|---|---|---|
| 胶囊条 | 椭圆（全圆角 999px，内层胶囊高 36px/外层含 2px 内边距共 40px）、**水平居中**（grid 三列布局保证真居中）；右侧同排放**日历快速定位**图标（40×40px 圆按钮）+ 筛选框（同 40px 高） | 可以（背后静态） |
| 日期滑杆 | 拖动式 filmstrip：逻辑日期坐标定位刻度（不依赖会变的 DOM 像素测量），中心疏、两侧密的**变量间距**（`BASE_PITCH`+`CENTER_EXTRA` 平滑过渡），只渲染中心前后各 10 个刻度（窗口化）；拖动带**橡皮筋边缘阻尼**+**吸附检测曲线**，松手走弹簧物理回正（spring/damping），无固定中线标记（早期版本有一根竖线 playhead，实测多余已去掉） | 否——裸刻度 |
| 便签流 | 横向滚动，**每日一块轻玻璃底板**（`--glass-bg` 0.25、hover 不提亮）**400px** 列、`corner-shape: squircle` 圆角 40px，**左旧右新**（今天最右）；无便签的日期**不出列**（时间轴压缩）；列头大日期数字 26px（今天主色）+ 小字月份/星期竖排；列**不随选中日改变大小**——只跟"谁现在正卡在屏幕物理中心"绑定，叠加**视觉深度效果**（见下节） | 底板玻璃（背后静态安全）；卡片见下 |
| 捕捉条 | 视口底部停靠、**水平居中**（与胶囊呼应，max 480px）；收起 50px 单行（与咕咕悬浮球同高）、圆角 25px（=半高，纯圆药丸）、聚焦展开为同圆角矩形，收展全程用 `corner-shape: round`（不用超椭圆——过渡瞬间切换会有跳变，见"踩坑记录"）；z-index 120，盖过景深效果给居中列写的最高 100 | 玻璃面板，内部交互克制 |

**玻璃红线适用**（design.md「弹窗动画规范」+ devlog 07-01/07-06）：捕捉条浮在滚动内容之上，内部交互元素 hover 一律走 opacity 叠层，不动 background/box-shadow（白带）；任何玻璃元素的祖先链不挂 opacity/filter/mask 动画（隔离组）。

## 滚动模型（横竖两轴分工）

- **横轴 = 翻历史**：纵滚轮在列外/无溢出列上时转为横滚（`wheel` 事件 `scrollLeft += deltaY`）；触控板横扫、Shift+滚轮走浏览器原生；日期条点击直达。横向滚动条隐藏（导航靠滚轮/日期条，露在捕捉条底下很脏）。
- **竖轴 = 翻当天**：列内溢出时列内自己竖滚（细滚动条）；滚轮悬在有溢出的列上优先列内竖滚。
- **滑杆语义**：聚焦哪天、那天的列停在**屏幕正中**（轮播/剪辑时间轴语义）——「当前」=中心离容器中心最近的列，`.timeline-cols` 两端留半屏 padding 让首末列也能居中；首载今天直接定正中（不播动画），提交后今天列居中+高亮，刻度杆点击/联动同此。判定用 **rAF 节流的 scroll 手算**（几十列一次遍历微不足道）：IntersectionObserver 只适用于"进出边界"型判定，"最近者易主"需随每个滚动像素连续变化，是 IO 的能力边界。日期滑杆是**双向控制器**：列滚动 → active 变 → 滑杆刻度带平移回中（非拖动态才动，避免和手指打架）；拖滑杆 → 松手吸附 → emit scrub/snap → 列带阻尼跟随滚到该日居中。
- **快速定位入口**：顶部胶囊行的日历图标复用补录用的 `DatePicker`（改成纯图标外观），选中日期写入 `store.jumpTarget`（Pinia，跨 `index.vue`/`NotesView.vue` 传递跳转意图，避免用 provide/inject 或 RouterView ref 绕一圈）；弹层自带"今天"快捷按钮，不需要再单独摆一个今天按钮。选中的日期没有便签时（该日不出列）退化到最近的有记录日期并 toast 提示，不静默跳偏；如果目标正好是"今天"且没记录，顺手展开捕捉条邀请写一条。

## 视觉深度效果（v2.2 新增）

真实列坐标（DOM 位置/宽度）完全不变——只在渲染层用 `transform`/`filter` 压缩视觉呈现，日期滑杆的定位几何、`offsetLeft` 测量都不受影响：

- **缩放 + 压缩间距**：`NoteTimeline.vue` 的 `columnStyle(index)` 按"离屏幕物理中心的连续距离"算 `scale()` 缩小 + `translateX()` 压缩间距，越远缩得越多、挤得越紧（分段函数，越往边缘每一步挤得比原生列距更紧，不是匀速压缩），`z-index` 同步降低让远处列沉到近处列后面。
- **必须严格绑定屏幕物理中心，不做平滑滞后**：这个距离直接吃 `centerFrac`（每帧滚动实算的连续分数位置），**不经过任何低通滤波/阻尼**——曾经加过一层 JS 低通滤波防止快速拖动时数值跳变过猛，结果反而导致"最大的那张卡"和"实际卡在屏幕中间的那张"对不上（平滑值追不上真实滚动位置）。教训：这类"谁在正中间就该长什么样"的效果，正确性优先于顺滑，宁可接受快速拖动时数值跳变大，也不能让视觉中心和物理中心脱节。
- **景深模糊**：同一个距离值再驱动一层 `filter: blur()`（系数偏轻，`capped * 0.35`），中心列清晰、越远越糊，和缩放/压缩共用一套输入，不需要额外状态；`capped===0`（真正居中的那一列）时直接给 `filter: none` 而不是 `blur(0px)`——后者仍会让浏览器为这一层维持一个 filter effect layer，白白多一份合成开销。
- **运动模糊试过又去掉了**：曾加过一个所有列共享的 SVG `feGaussianBlur`（只做水平分量），配一个常驻轮询的 rAF 循环按滚动速度写 `stdDeviation`。实测效果不明显、观感上加不加差别不大，而且是这次新功能里最贵的一块（每帧都要重新栅格化 SVG 滤镜，还叠在 `.glass-card` 本来就有的 `backdrop-filter` 之上），性价比太低，直接去掉了。

**性能note**：`.tl-col` 本身有 `.glass-card` 的 `backdrop-filter`，叠加上面这层 `filter: blur()` 是两套独立的滤镜机制，都不便宜；`content-visibility: auto`（列内 `.tl-col-body`）在祖先有 `filter` 时优化会打折扣（filter 需要子树的真实像素）。目前只对"离中心的距离"做了保守的强度设计（轻系数 + 静止时 filter:none），如果之后还嫌卡，下一步可以考虑只对视口内+少量缓冲的列计算这层效果、远处冻结不逐帧碰。

## 便签卡片（主角，定时任务卡同款）

- **质感 = task-card / 项目卡同款**：白 56% 底 + `1px rgba(255,255,255,0.72)` 白描边 + `--radius-md` 圆角 + 轻投影，`::after` 顶部高光层，hover 加深阴影 + 高光提亮。卡自身**不用 backdrop-filter**（底板已经是玻璃）；卡内 hover/让位动画发生在底板内容层、不碰底板 backdrop，两条玻璃红线都不踩，TransitionGroup move 可放心用 transform。
- **顶部显示标题，不是时间戳**（v2.2 改）：原设计时间戳常驻左上，实测发现"这条是什么"比"这条几点写的"更值得放在最显眼位置，时间信息本来就由所在的日期列承载，不需要卡片再重复一遍。
- **只有真标题（`#` 打头）才单独摘出来当头部**：不是"随便拿首行当标题"——首行只有真的匹配 `#{1,6}\s+` 才算标题、用粗体展示；纯正文/待办/列表开头的便签整段原样进正文渲染，不会凭空多出一条"标题"把第一行跟其余内容分割开。空便签在只读态给"（空便签）"占位。
- **标题/正文有分割线，但只在正文存在时才画**（`:has(+ .nc-body)` 选择器判定）：纯标题（无正文）的便签不会挂一条悬空的分割线。
- **卡片固定最小高度**（`min-height: 140px`，不止是 `.nc-body`）：早期只在正文区块给了 `min-height`，纯标题/一行正文的便签因为没有渲染 `.nc-body` 就完全绕开了这个下限，卡片变得又扁又寒酸；现在整张卡兜住方形比例的下限，跟内容多少无关。
- **卡内结构**：正文 13px/1.6；长内容 line-clamp 6 行 + 「展开」（阅读态展开，不进编辑）；待办渲染成可勾 checkbox **卡上点击即完成**（直接 PATCH 走乐观锁，不进编辑）；对象引用小 chip；**咕咕代记微标**加工档才标（`record_note` 的 origin 字段，直录不标）。
- **可选颜色**：整卡低饱和 tint（紫灰/粉灰/青灰/暖黄），不做左侧色条。
- **编辑 = 列内就地展开，按区域分标题区/正文区**（跟只读态结构对齐，而不是靠"标题"这个段落文字样式）：编辑态是一个纯文本标题 `<input>`（占位"标题（可选）"，回车跳到正文）+ 下面的富文本正文编辑器，固定分割线常驻（不看内容有没有）。工具栏因此从"正文/标题/待办/列表"四个减到"待办/列表"两个——标题不再是段落样式选项，写在哪个区域就是哪个角色。存的时候标题+正文拼回 `# 标题\n正文` 这套跟只读态解析约定一致的单串 markdown（没标题就只存正文，不产生假的 `#` 行）。**自动保存**：停顿 900ms 落一次盘，没有取消/保存按钮，点卡外面/切到别的便签才退出编辑态（先补一次保存）。工具栏藏掉 `@` 提示文字（放不下，捕捉条那份还在）；同列其余卡由 TransitionGroup move 让位。
- **编辑态和只读态是两套独立渲染实现，排版数值靠共享 CSS 文件维持一致**：只读态特意不用 TipTap 渲染每张卡（一天一列摆几十张卡，每张卡都起一个编辑器实例太重，这条权衡是故意的），而是走 `mdToPreviewHtml()` 生成纯 HTML；编辑态是真正的 TipTap/ProseMirror。两边 DOM 结构不同（比如 TipTap 的待办项内容会多包一层 `<p>`，只读预览是裸 `<span>`），但字号/行高/段落间距必须看着一样，不然编辑时一个样、保存后一读又变了间距。这类数值现在全部收进 `mind-content.css`（同目录下的共享样式文件），用组合选择器同时覆盖 `.md-preview` 和 `.ne-body .ProseMirror` 两边写在一起——只有一处要改，不会再出现"改了编辑器忘了改预览"。真要把两边**渲染引擎**也合成一个（只读态也用只读 TipTap 实例）技术上可行，但会把"一天一列几十个 TipTap 实例"这个已经被规避掉的性能坑重新引入，目前判断不值得，先靠共享 CSS 文件这条路维持一致。

## 捕捉条（底部停靠、居中）

- 收起态：单行 50px（与咕咕悬浮球同高）「记点什么…」+「随手记」角标；**收起不丢草稿**（单行里露草稿开头提醒"还有没记完的"）。
- 聚焦展开：编辑器 + 工具栏（正文/单级标题/待办/列表 + `@` 引用）从条内长出来，不弹浮层；补录日期选择器同排。收起/展开圆角同值 25px、`corner-shape` 全程固定 `round`（收展两态如果分别用 round/squircle，切换瞬间会跳变——`corner-shape` 不可过渡，且 squircle 不像 round 那样按盒子尺寸自动收窄半径，两者在高度动画途中切换会看着"先缩小再放大"）。
- 编辑器行为遵循设计草案：无 Markdown 输入规则、格式只走工具栏、`@` 引用（行首/空白前触发、连续无结果自动关）、`/` 预留咕咕。

## 提交行为

- **常规提交**：若已横滚进历史 → 先平滑滚回最右（今天列）→ 新卡插列顶 + 紫灰 12% 高亮 ~1.8s 淡出。
- **补录**（`captured_at` 是过去）：**不滚动**，toast「已记到 7 月 3 日」。不做这条反馈就是 bug——补录落进左边很远的列，眼前没有任何动静，用户会以为没保存。

## 空态

**未来融合进新手引导**（onboarding 系统）：P1 先放最简占位（"还没有记录，在下面记一条试试～"指向捕捉条），完整引导（这页是干嘛的 + "或者在 QQ 上对咕咕说『记一下』"）挂进新手引导流程时一并做。

## 未来方向：产品设想取舍（2026-07-11 讨论）

另一个视角（gpt）review 了这版 UI，整体认可"时间流"定位（不该往 Notion/Obsidian 那种知识库语言收），提了几条更长远的设想，讨论后按能不能做、该不该做分了三档：

**可以做、优先级较高（2026-07-11 已实现）：**
- **自动保存，去掉"取消/保存"**：`NoteCard.vue` 编辑态停顿 900ms 自动 PATCH，点卡外面/切到别的便签才退出编辑态（先补一次保存）。取消按钮语义上不存在了——`emit('cancel')` 改名 `emit('close')`，因为已经没有「可丢弃的东西」。踩了一个坑：`finishEditing()` 主动 flush 一次后 `emit('close')` 会让 `editing` prop 变 false，反过来触发监听 `editing` 的 watch 又 flush 一次——这时候保存请求可能还没落地、`props.note.contentMd` 还是旧值，两次 flush 会拿同一份 draft、同一个旧 version 连发两次 PATCH，自己把自己撞出 409 冲突。用一个 `closedByFinish` 标记位挡掉了这个重复 flush。
- **时间轴自适应标签**：没有另起一个标签元素——直接改了 `DateIndex.vue` 的 `fmtLabel()`，滑杆自带的刻度提示（离焦点越近越大越显眼那个）在"今天/昨天/前天/周X（7 天内）/具体日期（更早）"之间切换，比原来干巴巴的日期数字更有时间感。

**记方向、暂不动工（等 P2 画布/媒体支持真正开工时用）：**
- **笔记页作为思维面板入口**：写完一段内容后，AI 判断"这段值得展开成思维"，底部轻浮出提示 chip；点击才让咕咕介入（进画布发散，或直接在原地展开）——不是主动插评论，是留一个安静的钩子，用户自己拉不拉这根线。跟"不做操作型 UI"不冲突，因为这是邀请而非操作。这条其实可以泛化成一套通用机制：任何咕咕觉得有必要介入的时刻（总结、发现关联、提醒推进）都用同一种"提示 chip + 点击才介入"模式，不要为每种场景另起一套浮层。核心难点在后端"什么时候该出现提示"的判断逻辑，是需要认真设计的部分。
- **多媒体自然流**：图片/语音/语音条已经有独立的 IM 侧实现，Mind 笔记页目前完全没有媒体支持；等做的时候应该让它们长在时间流里（跟文字一样是一条便签），而不是做成"附件"语言。

**明确不采纳（附理由，免得以后被重新提起）：**
- **卡片自然生长成"每天一个无限长页面"**：跟现在这套横向翻页 + 景深压缩 + 固定方形卡片的交互模型互斥——一个是"翻卡片"、一个是"刷长页面"，两者不能都要。而且"卡片固定最小高度、方形比例"才刚定下来（NoteCard.vue 的 `min-height:140px`），跟"内容多就自然撑高"直接冲突。继续押横向翻页这条已经打磨很久的路。
- **AI 主动在时间流里插评论/总结（未经点击、自动出现）**：这个仓库明确定过"不做操作型 UI，保持纯对话"（咕咕人设是陪伴不是操作面板）。AI 主动冒泡评论容易把"安静的笔记本"变成"又一个会打扰你的助手"，跟"留白舒服"这个已经做对的东西有张力。改成点击式提示（见上一档）之后这条顾虑解除，所以拆分成了两条。
- **"今天只有一个页面、一切追加"（多条便签合并成单一长文档）**：这是要不要推倒重来的根本性问题，不是 UI 层面的取舍——现在的数据模型是"离散的便签列表"，改成这样要动数据模型本身。不建议现在拍板，等横向列这套跑出真实用户反馈再判断值不值得换。

## 格式扩展（2026-07-11 讨论）

现状：`useMindEditor.ts` 的窄口径（正文/单级标题/待办/无序列表/对象引用）目前是 `content_md` 唯一的产出源——P1 咕咕还没有写便签的工具（`record_note` 是 P3 计划），所以现在不存在"某种格式咕咕写得出、编辑器却渲染/编辑不了"的活跃 bug。但这是个提前该想的问题：等咕咕拿到写便签的工具，LLM 默认会写得比较全（加粗、代码块这些），如果编辑器接不住，用户会看到自己改不了的格式，甚至（因为 `mdInlineToNodes`/`inlineToHtml` 目前不解析这些语法）直接看到裸露的 `**`/`` ` ``/`>` 等字符。方向定为**扩大窄口径能接住的格式集合**，而不是等咕咕接入时再把 AI 输出硬拍平到什么都没有。按成本分三档：

- **优先做（低成本，✅ 2026-07-11 已实现）**：加粗/斜体/删除线/行内代码/链接。都是 TipTap `StarterKit` 原生的行内标记（inline mark），配置项翻开即可；解析走简化版 Markdown（`**`/`*`/`~~`/`` ` ``/`[text](url)`，不认 `_..._` 下划线写法——笔记里下划线常见于 snake_case，会被误判成斜体），支持两两/三个叠加（`***x***`/`~~**x**~~` 等固定几种组合字面量，按 ProseMirror 的 schema 顺序排，与点击先后次序无关）。UI 装进一个"样式"二级菜单（`Aa` 按钮展开），待办/列表留在外层主工具栏。
- **其次做（中等成本，✅ 2026-07-11 已实现）**：代码块、引用块、有序列表、分割线。都是 TipTap 原生块级节点；有序列表数字不锁宽度，交给 CSS counter 算，不手动记„第几项"；有序列表项因为不能跟无序列表共用同一个渲染（圆点 vs 数字），单独起了 `orderedListItem` 节点名。UI 装进一个新的"插入"二级菜单（`+` 按钮展开，竖排文字菜单，跟"样式"横排图标条区分开），因为都是一次性插入动作、不像样式需要连续切换。**多级标题仍未做**：NoteCard 的标题/正文分区假设"正文里只有开头一行真 `#` 才算标题"，如果正文里也允许 `##`/`###`，需要先定语义（算分段符？只是加粗的替代品？）——是设计问题，不是单纯的编辑器能力开关，做之前要先拍板。
- **暂缓（另一个坑，不跟这次捆一起）**：图片/表格。图片要有上传存储链路，表格要有网格数据模型，都不是加个解析规则能解决的，跟"多媒体自然流"（见上一节）是同一个坑，留给做媒体支持时一起处理。
