# 思维面板数据模型草案

> 状态：schema 讨论稿，未实现
> 配套：[设计草案.md](设计草案.md)（产品侧）
> 最后更新：2026-07-10

先钉死数据边界，再动前端。本文只定"全局图层 / 画布视图 / 关系边"三层的存储结构，不涉及 API 与 UI。

## 一条核心原则

**节点是全局的，画布只是视图，关系挂在节点之间。**

- 一条便签（节点）可以出现在多张画布上，画布只保存"它摆在哪、多大、第几层"。
- 关系连接的是节点与节点，跨画布、跨项目天然成立。
- 项目 / 文件 / 活动这些既有业务对象，通过一个轻量的"引用节点"进入这张图——这样画布项和关系永远只需要指向 `mind_nodes.id` 一种外键，不用做 `(type, id)` 多态外键（既能保 FK 完整性，又给"业务对象被删了还能留墓碑"留了空间）。

三张新表：`mind_nodes`（全局节点层）、`mind_canvas_items`（画布视图层）、`mind_relations`（全局关系层）。既有 `mind_maps` 复用为"画布容器"。

---

## mind_nodes —— 全局节点层

节点分三种 `kind`，用同一张表承载，让画布项 / 关系统一 FK 到 `id`：

| kind | 含义 | 内容来源 | 启用阶段 |
|------|------|----------|----------|
| `note` | 用户的 Markdown 便签 | 正文存在本行 | P1 |
| `ref` | 指向业务对象（项目/文件/活动…）的引用代理 | `ref_type` + `ref_id` 指过去，本行只存快照标签 | P2 |
| `suggestion` | 咕咕的归纳/待确认结论 | 与 note 同材质，带待确认状态 | P3/P4 |

> **suggestion 需要自身状态（P4）**：关系有 `suggested`/`confirmed`，但一条独立的咕咕建议便签本身还有"待确认 / 已采纳 / 已忽略"的生命周期，光靠 `origin='gugu'` 表达不全。P4 引入 suggestion 时，加一列节点级 `status`（`pending` | `accepted` | `dismissed`），或把它做成所有 kind 通用的节点状态列——本期先不加列，但把这个位置留出来，别到 P4 才发现只有 origin 不够用。

```python
class MindNode(Base):
    __tablename__ = "mind_nodes"

    id:         Mapped[int]           = mapped_column(Integer, primary_key=True, autoincrement=True)
    user_id:    Mapped[UUID]          = mapped_column(Uuid, ForeignKey("users.id", ondelete="CASCADE"), index=True)
    kind:       Mapped[str]           = mapped_column(String(20), default="note")   # note | ref | suggestion

    # ── note / suggestion 的内容 ──
    title:        Mapped[Optional[str]] = mapped_column(String(300), nullable=True)   # 可选：便签标题 / ref 快照名 / 墓碑显示名
    content_md:   Mapped[str]           = mapped_column(Text, default="")             # 块编辑器序列化出的 Markdown 源（可移植存储格式）
    content_plain:Mapped[str]           = mapped_column(Text, default="")             # 去格式纯文本，供 global_search 匹配 + 将来 embedding
    color:        Mapped[Optional[str]] = mapped_column(String(30), nullable=True)    # 便签低饱和底色，可空

    # ── ref 节点：指向既有业务对象 ──
    ref_type:   Mapped[Optional[str]] = mapped_column(String(20), nullable=True)      # project | file | event | client | folder（对齐 search.ALL_TYPES，单数）
    ref_id:     Mapped[Optional[int]] = mapped_column(Integer, nullable=True)         # 业务对象主键（这些表都是 int PK，单列够用）
    # 注意：ref_id 故意不做真实 FK——业务对象删除时不连带删节点，而是让节点降级成墓碑（见删除规则）

    # ── 咕咕相关 ──
    origin:      Mapped[str]           = mapped_column(String(10), default="user")     # user | gugu
    indexed_at:  Mapped[Optional[datetime]] = mapped_column(DateTime, nullable=True, default=None)  # 索引水位：null=待索引；P3 embedding 后写入
    indexed_hash:Mapped[Optional[str]] = mapped_column(String(64), nullable=True, default=None)     # content_plain 的哈希：索引管线据此判"内容真变过才重索引"

    version:     Mapped[int]           = mapped_column(Integer, default=1)             # 乐观锁：API 层 compare-and-swap（同 Project.version，见下"乐观锁"节）
    captured_at: Mapped[datetime]      = mapped_column(DateTime, default=datetime.utcnow, index=True)  # 面向用户的"发生/记录时间"，可编辑；记录页按它排时间流
    created_at:  Mapped[datetime]      = mapped_column(DateTime, default=datetime.utcnow)              # DB 落行时间，只作审计，不用来排时间流
    updated_at:  Mapped[datetime]      = mapped_column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)
    deleted_at:  Mapped[Optional[datetime]] = mapped_column(DateTime, nullable=True, default=None, index=True)  # 软删=墓碑（同 File.deleted_at）

    owner: Mapped["User"] = relationship()

    __table_args__ = (
        # ref 节点去重：同一用户对同一业务对象只保留一个引用代理，关系才不会散在多个 ref 上
        UniqueConstraint("user_id", "ref_type", "ref_id", name="uq_mind_node_ref"),
        # 便宜的底线约束，不只靠 API 校验：ref 节点必须两列都有值，非 ref 必须两列都空
        CheckConstraint(
            "(kind = 'ref' AND ref_type IS NOT NULL AND ref_id IS NOT NULL) "
            "OR (kind <> 'ref' AND ref_type IS NULL AND ref_id IS NULL)",
            name="ck_mind_node_ref_shape",
        ),
    )
```

要点：

- **`captured_at` 与 `created_at` 分开**：记录页的时间流按 `captured_at` 排——它是"这条想法发生/被记下的时间"，可编辑。补录昨天的想法、导入外部内容、迁移旧数据时，`created_at`（落库时间）会全挤在导入当天、把时间流排乱；`captured_at` 默认取当前时间，但允许写成过去。`created_at` 只留作审计。
- `ref` 节点存 `title` 快照（创建/刷新时抄一份业务对象名）——这样即便业务对象后来被删，墓碑仍能显示"[已删除] 某项目"，图谱不静默断裂。
- `content_plain` 从 P1 就写（保存便签时同步去格式），P3 的 embedding 直接吃这一列，不用回头改表。
- **`indexed_at` 在内容变更时必须清回 null**：保存节点、`content_md`/`content_plain` 有变化时，**同一事务内**把 `indexed_at` 置 null——否则首次向量化后用户再改正文，会被误当"已索引"漏掉。`indexed_hash`（`content_plain` 的哈希）给索引管线二次确认"内容真变过才重索引"，避免仅 `updated_at` 变（如只挪了画布位置）就白重算。
- **`content_md` 与 `content_plain` 必须成对、`indexed_hash` 跟着重算**：清 `indexed_at` 的同时，`indexed_hash` 一定要按新 `content_plain` 刷新，否则水位清了、哈希却停在旧值——P3 索引管线拿旧哈希会误判"内容没变"而漏掉重索引。`update_node_atomic` 里做了兜底：调用方只给 `content_md` 时服务层推导出 `content_plain` 再算哈希，二者不会脱钩（见 `app/core/mind.py`）。

## mind_canvas_items —— 画布视图层

只存"某节点摆在某画布上的展示状态"，删它不碰节点。

```python
class MindCanvasItem(Base):
    __tablename__ = "mind_canvas_items"

    id:         Mapped[int]      = mapped_column(Integer, primary_key=True, autoincrement=True)
    user_id:    Mapped[UUID]     = mapped_column(Uuid, ForeignKey("users.id", ondelete="CASCADE"), index=True)  # 冗余存一份，省掉查归属时的 join
    canvas_id:  Mapped[int]      = mapped_column(ForeignKey("mind_maps.id",  ondelete="CASCADE"), index=True)
    node_id:    Mapped[int]      = mapped_column(ForeignKey("mind_nodes.id", ondelete="CASCADE"), index=True)

    x:          Mapped[float]           = mapped_column(default=0)   # 画布坐标
    y:          Mapped[float]           = mapped_column(default=0)
    w:          Mapped[Optional[float]] = mapped_column(nullable=True)   # 空=用节点默认尺寸
    h:          Mapped[Optional[float]] = mapped_column(nullable=True)
    z:          Mapped[int]             = mapped_column(Integer, default=0)   # 层级
    collapsed:  Mapped[bool]            = mapped_column(Boolean, default=False)
    data_json:  Mapped[str]             = mapped_column(Text, default="{}")   # 预留：折叠状态外的展示扩展

    created_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow)
    updated_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)

    __table_args__ = (
        UniqueConstraint("canvas_id", "node_id", name="uq_canvas_node"),  # 同一节点在一张画布上最多一份
    )
```

- 一节点跨多画布 = 多条 canvas_item（不同 `canvas_id`）；跨项目关系不受画布归属影响。
- `ondelete=CASCADE` 到 `mind_maps` 和 `mind_nodes`：删画布或硬清节点时，对应画布项自动清掉。

## mind_relations —— 全局关系层

有向边，P1/P2 只存默认 `related`，P4 才开放语义类型。

```python
class MindRelation(Base):
    __tablename__ = "mind_relations"

    id:          Mapped[int]      = mapped_column(Integer, primary_key=True, autoincrement=True)
    user_id:     Mapped[UUID]     = mapped_column(Uuid, ForeignKey("users.id", ondelete="CASCADE"), index=True)
    src_node_id: Mapped[int]      = mapped_column(ForeignKey("mind_nodes.id", ondelete="CASCADE"), index=True)
    dst_node_id: Mapped[int]      = mapped_column(ForeignKey("mind_nodes.id", ondelete="CASCADE"), index=True)

    rel_type:    Mapped[str]      = mapped_column(String(20), default="related")
    # P1/P2: 只有 related；P4 开放 belongs | derived_from | supports | refutes | verifies | causes | follow_up
    origin:      Mapped[str]      = mapped_column(String(10), default="user")     # user | gugu
    status:      Mapped[str]      = mapped_column(String(10), default="confirmed")# confirmed | suggested（咕咕推断默认 suggested）
    note:        Mapped[Optional[str]] = mapped_column(Text, nullable=True)       # 详情栏补充语义的自由说明

    created_at:  Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow)
    updated_at:  Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)

    __table_args__ = (
        # 幂等 + 并发保护：一对节点在同一 rel_type 下只存一条边。related 无向，服务层先归一
        # （见下"related 归一"），归一后 (src, dst) 唯一即可挡住重复；有向类型天然按方向唯一。
        UniqueConstraint("user_id", "src_node_id", "dst_node_id", "rel_type", name="uq_mind_relation"),
        # 底线约束：禁止节点连向自己
        CheckConstraint("src_node_id <> dst_node_id", name="ck_mind_relation_no_self"),
    )
```

- 用字符串存 `rel_type`/`origin`/`status` 而非 enum——跟代码库既有 status/type 一致，P4 加类型不用改表结构。
- 有向：`supports`/`causes`/`follow_up` 本就不对称，按 src→dst 存。
- **`related` 归一 + 幂等**：`related` 是无向的，`A→B` 和 `B→A` 必须在服务层归一成同一条边——约定**存的时候永远让 `src_node_id < dst_node_id`**（按 id 排小的在前）。归一后配合上面的唯一约束，用户重复点连线、咕咕重复建议都命中同一行：服务层用 upsert（存在即返回已有边，只在需要时升级 `status`/`origin`），而不是堆重复线；唯一约束同时兜住并发下两个请求同时插入的竞态（一方触发约束冲突→捕获→返回已有边）。有向类型不做 id 归一（方向有意义），靠 `(src, dst, rel_type)` 唯一即可。

## mind_maps —— 复用为画布容器

既有表保留，语义调整：

- `project_id` 从"归属"降级为**可选关联 / 初始筛选**，不再限制节点归属。
- `data_json` 存画布级视图状态（平移、缩放）即可，不再塞节点数据（节点去了 `mind_nodes`）。
- **`files.mind_map_id` 是历史字段，新模型里不再用它判断"文件在哪张画布"**：文件出现在画布上，一律由"`ref` 节点（`ref_type='file'`）+ `mind_canvas_items`"表达。这个字段只保留给旧的"思维空间文件存储"归档用途，本期不迁移、代码里也不得再拿它推断画布归属——注释和文档都要写明，免得后人误用。
- 后续可补 `deleted_at` 与其他表对齐，本期非必需。

## 跨用户不变量（冗余 user_id 不自动等于安全）

`mind_canvas_items`/`mind_relations` 上那个冗余 `user_id` 只是省 join、方便按人查，**它本身挡不住跨用户拼接**（谁写请求谁就能填任意 user_id）。真正的隔离必须在 API 写入路径上强制，用既有的 `get_owned(db, Model, id, current_user.id)` 校验（同 projects/events 的写法）：

- 建/改 **canvas_item**：`canvas_id` 和 `node_id` 都要各过一次 `get_owned`，且二者的 `user_id` 必须都等于当前用户；`MindCanvasItem.user_id` 只能由服务端从当前用户填，不接受请求体传入。
- 建/改 **relation**：`src_node_id`、`dst_node_id` 两端都过 `get_owned`，且都属于当前用户——杜绝把别人的节点接进自己的图，或反之。
- 一句话：**凡是外键引用另一行的地方，服务层都要独立验一次那行的归属**，不能因为"我这行 user_id 对"就假设被引用的行也归我。

## 乐观锁（用原子 UPDATE，别复制 Project 的竞态）

`version` 是真锁，不是装饰列。但**不要照搬 `Project.version` 的"先读→比较→再写"实现**（[projects.py:122](../../backend/app/api/v1/projects.py:122)）——那是应用层 compare-and-swap，读和写之间有窗口，两个并发请求可以同时通过版本比较、再互相覆盖，锁形同虚设。

`mind_nodes` 用**一条原子 UPDATE 把比较和写入合成一步**：

```sql
UPDATE mind_nodes
   SET <字段...>, version = version + 1, updated_at = now()
 WHERE id = :id AND user_id = :user_id AND version = :client_version
   AND deleted_at IS NULL
```

- 再看受影响行数（SQLAlchemy `result.rowcount`）：为 `0` 就是版本已变（或不归属）→ 返回 `409`；为 `1` 才算更新成功。比较条件在 `WHERE` 里、由数据库在行锁下判定，没有 read-compare-write 的窗口。
- `user_id = :user_id` 同时兜住归属（`get_owned` 之外再加一道），跨用户改不动别人的节点。
- `deleted_at IS NULL` 兜住软删的 TOCTOU：路由先读到 live 便签、原子 UPDATE 之前它被并发软删时，这道 WHERE 让写落空（rowcount=0）而不是把编辑静默写进墓碑。命中即返 `409`（语义上是"已被改动/删除"，可接受）。
- 本期决定**接入**（便签会多端/咕咕并发改），`mind_nodes` 保留 `version` 且更新 API 必须走这条原子 UPDATE。
- `mind_canvas_items`（纯位置）和 `mind_relations` 冲突面小、最后写赢可接受，本期不加 version。

## 删除规则（写进设计，避免图谱静默断裂）

1. **删画布贴纸**：只删对应的 `mind_canvas_items` 行。节点和它参与的关系全不动。
2. **删原始便签**：软删（写 `mind_nodes.deleted_at`）。节点行、它的 canvas_items、它的 relations **全部保留** → 在画布上渲染成"已删除记录"墓碑节点，关系仍在。
3. **用户明确清理**：真正 `DELETE` 该 `mind_nodes` 行 → 靠 `ondelete=CASCADE` 连带清掉它的 canvas_items 和 relations。
4. **业务对象被删**（如项目删除）：不连带删对应 `ref` 节点（`ref_id` 故意非真实 FK）；`ref` 节点降级成墓碑，用之前抄下的 `title` 快照显示"[已删除]"，等用户清理。

## 检索预留（P3 才接，P1 先占位）

- `content_plain`：P1 保存便签时就写，是 global_search 匹配和 embedding 的共同输入。
- `indexed_at`：待索引状态（null=待索引），P3 的向量管线按它捞增量，不急着首期就上向量库。**保存内容时同一事务清回 null**（见 MindNode 要点），否则改了正文会被漏索引。
- `indexed_hash`：`content_plain` 的哈希，索引管线据此判"内容真变过才重索引"，避免只挪位置（`updated_at` 变而正文没变）也触发重算。
- **P1 的搜索接触点**：`search.ALL_TYPES` 加 `"note"`，让 `global_search` 至少能按 `content_plain` 召回便签正文（便签短，匹配正文可行，不像文件那样只能匹配名）。

## 按阶段激活哪些列 / 取值

| 阶段 | 用到的表 / 列 | 关系取值 | 节点 kind |
|------|--------------|----------|-----------|
| P0 建地基 | 三表 + mind_maps 全部建好 | — | — |
| P1 记录可用 | mind_nodes（note）、captured_at 时间流、content_plain、version 乐观锁、global_search | 只写 `related`（服务层归一+幂等）| `note` |
| P2 画布可用 | + mind_canvas_items、mind_nodes（ref）| 仍只 `related` | `note` `ref` |
| P3 检索+咕咕 | + indexed_at/embedding、relations.origin=gugu/status=suggested | 关系可由咕咕建议、用户确认 | + 只读分析 |
| P4 丰富 | 版本接口、图片块、节点级 suggestion `status` | 开放 supports/derived_from/verifies 等少量高价值类型 | `suggestion`（沿用纸条材质 + 待确认角标）|

> 落地提示：`CheckConstraint` 需加进 `app/models/__init__.py` 的 sqlalchemy import（现有那行只有 `UniqueConstraint`）。P0 迁移里两个 CheckConstraint（`ck_mind_node_ref_shape`、`ck_mind_relation_no_self`）和唯一约束一起建。
