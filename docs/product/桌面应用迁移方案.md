# 咕咕桌面应用迁移方案

> 状态：讨论稿
> 更新时间：2026-07-13
> 策略：云版桌面客户端先行；本地文件、BYO Key 与离线数据按价值逐步演进，不与首发绑定。

---

## 1. 结论与边界

桌面版首发目标是给现有云服务提供一个更适合常驻使用的原生入口，而不是先重建一套本地后端。用户登录现有账户后，继续使用服务器上的项目、文件、日历、思维面板、咕咕、IM 与定时任务；桌面端优先带来独立窗口、系统通知、文件拖放、下载保存和自动更新。

首版推荐采用 **Electron + Vue 前端**。Vue 渲染进程沿用当前前端，通过可配置 API 基址连接现有 Gugu-web 服务；Electron 主进程只负责原生能力与窗口生命周期。这样能尽快验证桌面端的真实使用价值，避免在首发前陷入 SQLite 兼容、Python sidecar、数据迁移与云同步冲突。

```text
Electron 主进程
  ├─ Vue 渲染进程（现有前端）
  ├─ 受控 preload IPC（原生文件、通知、更新）
  └─ 现有云端 Gugu-web API
       ├─ FastAPI / Agent / Worker / IM 网关
       ├─ PostgreSQL / Redis / 对象或服务器存储
       └─ 已有账号、权限与数据
```

### 云版首期必须达成

1. 使用现有账号登录，完整访问现有云端数据与咕咕能力。
2. 现有 Vue 页面在 Electron 中稳定运行，API 地址不写死在页面代码中。
3. 支持系统通知、独立窗口、文件拖放、原生下载保存和后续自动更新。
4. 启用 `contextIsolation`，渲染进程仅通过最小化 preload API 使用原生能力。

### 云版首期明确不做

- 离线创建/编辑项目、笔记、画布等业务数据。
- 本地数据库、Python/FastAPI sidecar、SQLite 迁移。
- 用户选择目录作为云端文件库的实际存储后端。
- 未登录的持久化本地用户。
- 本地独占的 BYO LLM Key。

这些能力不是被放弃，而是进入后续阶段，并且必须先明确各自的数据、隐私和同步语义。

---

## 2. 云版账户、数据与认证

云版桌面客户端直接复用现有登录、Token、用户数据和服务端所有权校验。桌面端不引入另一套身份模型，也不需要把 Web API 的认证边界放松。

首期数据原则：

- 服务器是业务数据唯一真源；桌面端只保留会话、窗口状态和可清理缓存。
- 用户退出登录时清理本机 Token 与私有缓存。
- 多设备数据一致性由现有服务端负责；桌面端不自行做离线队列或冲突合并。
- IM、定时任务和 Agent worker 继续在服务器运行，桌面应用退出不影响它们。

---

## 3. Electron 责任划分

### 主进程

- 创建窗口、系统托盘、深链、系统通知与自动更新。
- 提供文件选择、文件拖放后的受控路径处理、下载保存对话框等原生能力。
- 管理桌面端的 API 环境配置和安全会话边界。
- 只向渲染进程暴露最小 preload API，不开放 Node.js 全量能力。

### Vue 渲染进程

- 继续复用当前路由、Pinia、项目卡片、文件库、思维面板和咕咕聊天。
- 通过 `VITE_API_URL` 或启动时注入的 API 基址请求云端服务。
- 需要原生能力时调用 preload API，不自行读取任意本机路径。

### 云端服务

- 保持现有 FastAPI、PostgreSQL、Redis、Agent、Worker 和 IM 网关部署。
- 继续承担认证、业务写入、文件归属校验、定时任务、模型调用与跨设备一致性。
- 桌面端只是新增一个受支持的客户端，不是新的一套后端模式。

---

## 4. 本地文件目录的演进

“让用户选择本地目录作为文件库”会改变文件真源位置和多端访问语义，不能作为云版首期的一个简单设置项。

推荐分为两步：

1. **云版增强**：支持把云端文件下载、另存、拖入上传和“在 Finder/Explorer 中显示”做得更顺手；桌面应用可保留可清理缓存，但服务器仍是文件真源。
2. **工作目录镜像或本地优先文件库**：用户选择目录后，先明确它是只读镜像、双向同步工作区，还是唯一真源。只有确定冲突、离线编辑、删除回收站与其他设备访问规则后，才接入 storage 抽象。

无论进入哪一步，前端都不能直接拼任意本机路径；文件读写必须经过 Electron IPC 或后续的本地 storage 服务，并处理目录失联、权限变化、移动硬盘断开和卸载应用不误删用户文件等情形。

---

## 5. BYO LLM Key 的演进

云版和本地优先版的 BYO Key 是两种不同承诺，不能混为一个“设置输入框”。

### 云版阶段

若首期开放 BYO Key，模型调用仍发生在服务器，密钥必须通过服务端的加密存储、脱敏日志和访问控制方案管理。桌面端不能把 Key 长期放在 `localStorage`，也不能每次聊天把裸 Key 附在请求里。

若这套服务端密钥托管还未准备好，云版首期应继续使用现有服务端模型配置，不仓促开放 BYO Key。

### 本地优先阶段

用户要求“密钥只留在本机”时，需要本地 Agent sidecar：Key 存 macOS Keychain / Windows Credential Manager，本地模型调用由 sidecar 完成；Vue 前端不直接持有长期密钥。普通配置可以在本地数据库保存，导出数据默认不包含密钥。

---

## 6. 本地优先与未登录用户

未登录也能完整使用，意味着需要本地业务数据、文件存储、任务执行与模型调用，不是云版桌面客户端自然附带的能力。该阶段应单独立项。

建议设计：首次启动创建持久化本地用户 UUID，所有项目、文件、便签、画布、关系与对话仍带 `user_id`，继续复用既有的所有权模型；不为本地模式制造无身份的数据旁路。用户未来登录云端时，必须显式选择导入、备份或同步，不能静默上传本地内容。

本地运行时大致为：

```text
Electron 主进程
  ├─ Vue 渲染进程
  ├─ Python/FastAPI sidecar（仅监听 127.0.0.1）
  ├─ SQLite 与本地任务/缓存实现
  ├─ 系统钥匙串（BYO Key）
  └─ 用户选择的本地文件目录
```

现有 PostgreSQL、Redis、迁移脚本与 worker 假设需要先做依赖审计和 SQLite 兼容改造；不能把这一步当作改一个连接字符串。

---

## 7. 推荐分期

### 阶段 A：云版桌面客户端

- 引入 Electron，打包当前 Vue 构建产物。
- 注入可配置的云端 API 地址，复用现有登录与业务 API。
- 完成窗口、托盘、通知、下载保存、文件拖放和自动更新基础。
- 先以 macOS 为开发与验收目标，再建立 Windows 打包链路。

### 阶段 B：桌面文件体验

- 本地下载缓存、打开文件、另存与上传体验。
- 定义工作目录镜像需求与云端文件的冲突语义。
- 不在此阶段承诺离线业务编辑。

### 阶段 C：受控的 BYO 模型能力

- 先决定密钥托管在云端还是仅留本机。
- 云端托管时完善加密与权限边界；本机独占时引入最小 sidecar 原型。
- 验证模型连通性、流式聊天与错误脱敏。

### 阶段 D：本地优先 MVP

- SQLite 兼容层、迁移、备份和恢复。
- 本地用户、离线项目/文件/日历/笔记/画布。
- 本地目录 storage、系统钥匙串与本地 Agent。
- 网络恢复后的同步策略只在明确协议后接入。

### 阶段 E：同步与协作

- 账户绑定、显式导入/导出。
- 双向同步、版本、冲突解决与审计。
- 多设备协作只在同步协议稳定后开放。

---

## 8. 云版首期验收标准

1. 登录后，项目、文件、日历、思维面板与咕咕聊天和 Web 端使用同一份云端数据。
2. 桌面端关闭、重启或升级后，云端定时任务与 IM 机器人持续按服务器规则运行。
3. 文件下载、另存、上传和拖放不绕过服务器的归属、大小限制与存储校验。
4. Token、密钥和个人数据不写入日志、URL 或不受控的渲染进程存储。
5. 断网时明确显示服务不可达，不伪装成已离线保存成功。
6. Web 部署模式的认证、所有权校验和服务端行为不因新增桌面客户端而放松。

---

## 9. 主要风险

| 风险 | 处理原则 |
| --- | --- |
| 云版和 Web 行为分叉 | 云版首期尽量复用现有 API 与 Vue 页面，桌面特性只放主进程/preload。 |
| Electron 渲染进程权限过大 | 开启 `contextIsolation`，最小 IPC 白名单，禁止任意 Node.js/文件系统访问。 |
| 本地缓存被误解为离线数据 | 产品文案明确“缓存不是离线编辑”；网络失败不假装保存成功。 |
| BYO Key 泄露 | 未完成密钥托管或本地 sidecar 设计前，不开放相关输入。 |
| 后续本地化被云版写死 | API 基址、认证、文件入口和模型配置都留可替换边界。 |
| SQLite 迁移成本被低估 | 本地优先另立项目，先做依赖清单和兼容测试。 |

## 10. 待决问题

1. 云版桌面首发是否只支持 macOS，还是需要同时覆盖 Windows？
2. 系统托盘关闭窗口后，是否保留通知与快速打开入口？
3. 文件工作目录后续定位为缓存、镜像，还是本地唯一真源？
4. BYO Key 是否接受云端加密托管，还是必须从第一天保证仅留本机？
5. 本地优先未来的同步目标是备份、单设备迁移，还是多设备双向协作？
