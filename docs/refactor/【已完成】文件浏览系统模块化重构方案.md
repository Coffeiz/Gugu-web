## 1. 背景与目标

- 后端已完成响应、浏览查询、上传准备/确认、预览、批量选择、文件删除和回收站动作的 service 边界整理；`FileService` 继续作为文件夹和文件写语义入口。

- devserver 浏览器已完成文末手动验收，覆盖拖拽克隆、缓存回滚、上传 ghost、项目范围、回收站、覆盖上传和网页粘贴冲突处理。

`frontend/src/views/Projects/components/ProjectModal.vue` 当前仍承担项目基础信息、阶段、待办和项目文件管理；`frontend/src/views/Files/index.vue` 已拆分至约 1330 行，主要保留文件库页面状态、生命周期、页面级动作协调和样式。

两个页面已经共享部分 Store、API 和 composable，但仍分别维护大量文件网格、列表、选择、排序、上传、拖拽和右键菜单模板与交互编排。因此本次重构范围不再只是 ProjectModal，而是建立两边共同使用的文件浏览层。

本次重构目标：

- 降低 `ProjectModal.vue` 和 `Files/index.vue` 的职责和代码量。
- 让项目文件区与文件库共享文件浏览、选择、排序、上传和操作逻辑。
- 保留项目文件区与文件库之间的产品差异，不强行复用回收站和全局导航。
- 保证重构期间行为可逐阶段验证，避免一次性替换导致文件操作回归。

## 2. 目标架构

目标架构按三层收口：共享展示组件、文件浏览 composable、页面场景扩展。完整的当前结构与目标结构目录主图统一放在 **2.2 整理前后目录对比**，本节不再重复维护目录树。

- 共享展示组件放在 `frontend/src/components/common/`。
- 文件浏览状态与动作放在 `frontend/src/composables/files/`。
- 项目文件区和文件库页面只保留场景配置与专属扩展。
- 项目基础信息、阶段和待办继续属于项目域，不并入通用文件浏览层。

### 2.1 后端配合整理

前端通用文件浏览层需要后端提供稳定、按能力边界组织的文件 API。后端配合遵循三条原则：

- API 路由只负责认证、参数解析、HTTP 异常映射、事务提交和事件触发。
- 文件和文件夹写操作继续统一经过现有 `FileService`，不在路由中重复实现文件语义。
- 目录查询、上传、预览、批量操作和回收站分别下沉到对应 service，项目文件区只通过 `projectId` 配置范围，不依赖前端限制权限。

后端目标能力对应关系：

```text
前端 FileBrowserPanel
├── 目录查询       -> FileBrowserService
├── 文件操作       -> FileService / FileActions
├── 上传           -> FileUploadService
├── 预览           -> FilePreviewService
└── 回收站扩展     -> TrashService
```

详细的后端目录、执行顺序和约束见本文“后端实施细节”章节。

## 3. 职责边界

### 3.1 ProjectModal

只负责弹窗生命周期、整体布局和模块协调：

- 打开、关闭和当前项目切换。
- 传递 `projectId` 和项目配置。
- 接收项目删除、保存和关闭事件。
- 不再直接实现文件卡片、文件夹导航和文件操作。

### 3.2 ProjectFilesPanel

负责项目文件场景的配置：

- 固定当前 `projectId`。
- 默认打开项目根目录。
- 禁止回收站入口。
- 限制文件移动在当前项目范围内。
- 复用通用文件浏览组件和 composable。

### 3.3 FileBrowserPanel

负责普通文件浏览的布局和公共工具栏编排：

- 工具栏。
- 面包屑。
- 排序、视图切换、新建文件夹和粘贴入口。
- 网格/列表视图。
- 文件和文件夹渲染。
- 批量选择栏。
- 右键菜单。

面板通过受控 props / emits 接入状态：

- `viewMode` / `update:view-mode`：网格和列表切换。
- `selectionMode` / `toggle-selection`：多选模式。
- `canPaste` / `paste`：剪贴板粘贴入口。
- `showNewFolder`、`newFolderName`、`create-folder`：新建文件夹编辑态。
- `sortOptions`、`sortKey`、`sortDir` / `sort-select`：排序入口。

面包屑、回收站按钮、存储统计和项目阶段切换分别通过 `breadcrumb`、`toolbar-extra`、`trailing` 和自定义 `toolbar` 插槽传入；面板不判断具体业务场景，也不复制 API 副作用。

### 3.4 右键菜单复用

文件库和项目文件区的右键菜单统一使用 `FileBrowserContextMenu.vue` 和 `useFileContextMenu.ts`，不再分别维护菜单模板。

通用菜单根据当前目标类型和页面能力配置显示菜单项：

- 文件目标：信息、下载、重命名、复制、剪切、删除。
- 文件夹目标：下载 ZIP、重命名、复制、剪切、删除。
- 空白区域：粘贴、新建文件夹等当前页面允许的操作。

项目文件区通过能力配置隐藏跨项目、回收站和永久删除等不适用动作；文件库通过配置增加回收站相关动作。菜单的展示结构、定位、关闭和键盘行为由组件统一负责，具体动作由 `useFileContextMenu.ts` 调用 `useFileActions.ts`。

这里的差异通过能力配置表达，不为文件库和项目文件区各写一份菜单模板。

### 3.5 复用边界

通用文件浏览层只复用两边都需要的文件能力：

- 文件和文件夹卡片。
- 网格/列表视图。
- 排序。
- 单选、多选、Shift 选择和框选。
- 文件夹进入、面包屑和目录移动。
- 文件/文件夹重命名、下载、删除。
- 文件上传、冲突处理和上传进度。
- 右键菜单和批量操作栏。

以下能力不强行放进通用 `FileBrowserPanel`，由文件库页面单独扩展：

- 回收站入口。
- 回收站文件和文件夹恢复。
- 文件和文件夹永久删除。
- 个人文件、项目列表、年份/月度等全局导航。
- 跨项目空间切换。
- 存储空间统计和文件库专属筛选。

项目文件区同样有自己的边界：

- 固定在当前 `projectId` 下，不提供个人文件和其他项目的全局导航。
- 第一阶段不显示回收站，不提供恢复和永久删除入口。
- 文件和文件夹移动只能发生在当前项目范围内。
- 项目颜色、项目权限和项目弹窗布局由 `ProjectFilesPanel` 负责，不下沉到通用文件浏览组件。

这样做不是减少复用，而是避免通用组件变成包含大量场景分支的“全能文件页面”。通用层提供稳定的文件操作能力，回收站、全局导航和存储统计作为页面级扩展存在。

### 3.6 通用 composable

`useFileSelection` 处理选择状态，`useFolderNavigation` 处理目录路径，`useFileActions` 处理 API 操作，`useFileUploadController` 处理上传流程。composable 不直接依赖具体页面 DOM，页面只提供当前空间、目标目录和刷新/投影回调。

## 4. 统一数据模型

网格和列表使用同一份展示模型，避免两套模板分别判断文件和文件夹状态：

```ts
type BrowserItem =
  | {
      type: 'folder'
      id: number | string
      folderId: number
      name: string
      count?: number
    }
  | {
      type: 'file'
      id: number
      name: string
      ext: string
      folderId: number | null
    }
```

数据层保留后端原始模型，`BrowserItem` 只作为浏览器 UI 的投影模型。排序、选择、右键菜单和拖拽均基于该模型工作。

## 5. 执行计划

> **实施路线修订（2026-07-15）**
>
> 目标架构保持不变，但不按“完整 FileBrowserPanel 一次性落地”的方式执行。文件浏览系统的风险主要在拖拽、缓存同步、文件归属和回收站语义，而不是类型检查能否通过。因此采用渐进式迁移，每一阶段都保持可运行、可验证、可回滚。
>
> 重构分为四条风险递增的主线：
>
> 1. **展示层**：Grid/List 和面包屑展示。
> 2. **状态层**：选择、排序、目录导航和数据投影。
> 3. **操作层**：上传、移动、复制、删除和批量操作。
> 4. **边界层**：右键菜单、后端 service、权限和回收站扩展。
>
> 第一阶段不得顺手改变拖拽行为、缓存策略、API、数据模型或卡片 DOM 层级。尤其要保留现有拖拽克隆、落地动画、连接点、缩略图和卡片外壳结构；这些属于已经反复修复过的高风险交互。

## 6. 后端实施细节

### 6.1 当前后端职责

当前 `backend/app/api/v1/files.py` 约 620 行，主要负责路由鉴权、事务提交、事件发布和 HTTP 响应映射；目录查询、上传校验、媒体预览、下载和响应组装已分别下沉到 `services/files/`。`folders.py` 负责文件夹路由，`trash.py` 负责回收站业务；现有 `FileService` 已经是文件和文件夹写操作的统一语义入口。

后端重构不与前端组件一一对应，而是遵循“路由变薄、写操作统一、查询和媒体能力分离”的边界。

### 6.2 目标后端结构

```text
backend/app/api/v1/
├── files.py              # 路由协调
├── folders.py            # 文件夹路由协调
└── trash.py              # 回收站路由协调

backend/app/services/files/
├── browser.py            # 当前目录、项目根目录、文件夹内容查询
├── actions.py            # 重命名、移动、复制、删除、下载
├── selection.py          # 批量下载、批量删除
├── upload.py             # 预签名、确认、冲突和上传编排
├── previews.py           # 缩略图、PDF 和流式预览
├── trash.py              # 回收站业务编排
└── response.py           # FileResponse、FolderResponse 组装

backend/app/services/storage/
├── file_service/         # 文件和文件夹写操作门面及底层实现
├── folder_tree.py        # 文件夹树和归属解析
└── trash.py              # 存储层回收站移动、恢复和清理
```

### 6.3 前后端对应关系

```text
前端 FileBrowserPanel
├── 目录查询       -> FileBrowserService
├── 文件操作       -> FileService / FileActions
├── 上传           -> FileUploadService
├── 预览           -> FilePreviewService
└── 回收站扩展     -> TrashService
```

前端的项目文件区通过 `projectId` 使用同一套 API，但项目范围、父子目录、跨项目移动和归属校验必须由后端最终确认，不能只依赖前端能力配置。

## 7. 风险与控制

### 文件范围风险

项目文件区只能访问当前项目范围，不能因为复用文件库逻辑而出现跨项目移动或读取。所有移动操作必须继续传递正确的 `projectId` 和 `folderId`。

### 缓存一致性风险

文件操作仍使用现有 `filesCacheStore` 的乐观更新和回滚约定。抽 composable 时不得在组件层再维护一套项目文件缓存。

### 回收站差异

项目文件区第一阶段不实现回收站恢复和永久删除。文件库的回收站逻辑通过扩展能力保留，不能塞进通用文件操作的默认路径。

### 拖拽风险

文件拖拽同时涉及指针事件、落点判定、层级和缓存更新。展示组件迁移后必须优先验证拖拽克隆、文件夹落点和项目抽屉交互。

文件库/项目文件区当前已通过 Interaction Runtime 的 Vue API 接入单卡与多卡拖拽；文件业务层只保留 Runtime Action 到文件移动 API 的适配。旧的 `usePhysicsDrag`/`flipCoordinator.ts` 仍服务于画布、抽屉和其他尚未迁移的物理拖拽场景，不应重新接入文件浏览组件。

### 本轮保留的结构决策

- **通用 `FolderCard` 已落地**：卡片外壳、选中态、预选态和拖入态统一，具体图标、操作按钮和拖拽入口继续由场景插槽提供。
- **`FileBrowserPanel` 采用能力配置 + 插槽扩展**：面板统一承载普通工具栏编排和布局边界，Grid/List、数据投影、API 副作用及回收站特殊列表仍由页面和 composable 提供，避免把场景分支堆叠进“大总组件”。
- **ProjectModal 的信息、阶段、待办面板列入阶段 6 后续主线**：开发阶段允许完整拆分，但必须先建立草稿、阶段和待办的统一状态边界，再逐块迁移，不能通过组件之间互相复制响应式逻辑完成拆分。
- **存储统计暂不抽成共享组件**：它只服务文件库顶部空间提示，且样式依赖 `Files/index.vue` 的 scoped CSS；在没有明确第二个使用场景前保留页面内实现，避免为了结构名义上的复用改变现有布局。

以上结构决策已纳入 Phase 6 验收；最终报告需分别记录项目文件区、文件库普通目录和回收站的自动检查与手动验收结果。

### 迁移策略

每个阶段保持页面可运行，先让新组件与旧逻辑并行对照，再删除旧实现。不要在同一个提交中同时改变 API、Store 数据模型和 UI 组件边界。

## 9. 拖拽引擎迁移与性能（关联但独立的任务线）

> 这一节记录文件库/项目文件区拖拽的现状、性能问题的实测根因和后续迁移方向，
> 不属于第 5 节的展示/状态/操作/边界四条主线，也不改变阶段 0-8 的执行顺序或
> 验收范围。按阶段 6 的"拖拽动画红线"，本文档的展示层重构不得顺手修改拖拽
> 物理、克隆层或落地动画——这一节只是把"接下来该往哪个方向动拖拽"记录下来，
> 具体实现留到独立提交，不在文件浏览重构的阶段内完成。

### 9.1 现状

文件库和项目文件区的拖拽已经迁移到 `gugu-interaction-runtime`，通过
`frontend/src/interaction/runtime/vue` 的 `useObject`、`useSurface`、Runtime Target
和 `useRuntimeAction` 接入；多选使用 Runtime Group Session，文件业务层通过
`useFileRuntimeMove` 执行移动、乐观更新和回滚。`usePhysicsDrag.ts` 与
`flipCoordinator.ts` 仍保留给画布、抽屉等旧物理拖拽场景，不能再作为文件浏览区的接入入口。

`拖拽系统模块化拆分方案.md` 规划的自研 `CardProxy`/`DragSession` 架构已标记废弃，
不再作为文件/文件夹拖拽的迁移目标；文件浏览区后续新增卡片应继续复用 Runtime Vue API
与共享文件适配层，不重新引入页面级 pointer、命中、landing 或多选生命周期。

### 9.2 性能实测（2026-08-02 trace 分析）

针对"图片文件多时，抓起卡片掉帧明显"录了一份 Chrome Performance trace，覆盖两次
完整的抓起→落地。结论：

- 每次抓起后 40-60ms 左右出现一个约 20-25ms 的单帧主线程任务，是可感知卡顿的直接来源。
- 拆开这个任务：真正执行 JS 的时间只占约 15%（~15-20ms/150ms 窗口），集中在
  `flipCoordinator.ts` 的 `measureWithoutTransform` —— 抓起时连续调用
  `getBoundingClientRect`/`elementFromPoint`，中间穿插 `cloneNode`/
  `copyInheritedTextStyle` 建拖拽克隆节点、写样式。
- 剩下约 85% 是浏览器原生渲染管线（`Layerize`/`UpdateLayoutTree`/`Layout`/`Paint`/
  `HitTest`），根因是上面这批读写没有批处理，形成经典的布局抖动
  （layout thrashing）：每次 `getBoundingClientRect` 夹在两次 DOM 写操作中间，
  逼浏览器在同一个任务里插入多次同步布局，叠加克隆节点刚建就要升合成层。

这类"读写交替、逐次 `getBoundingClientRect`"的问题，正是 `gugu-interaction-runtime`
已经用 `LayoutMeasurement` 批量测量、单一 overlay proxy 代替临时克隆节点、运动只走
`transform`/`opacity` 解决掉的问题类型——项目看板迁移到 Runtime 后已经验证过这条路径
可行。据此判断：文件/文件夹拖拽的抓取掉帧，大概率会随着迁移到 Runtime 基本消失，
不需要现在单独为 `flipCoordinator.ts` 做局部性能修补。

另有一处**不在拖拽引擎范围内、且已确认与掉帧无关**的独立问题：文件卡 `:hover`
直接改 `background`/`box-shadow`（`FileCard.vue`），触发主线程重绘，纯鼠标移动/
滚动扫过密集网格时会闪烁。trace 里也观察到不在拖拽窗口内的 `mousemove` 同样伴随
明显的 `Layerize`/`HitTest` 开销，与上述抓取问题相互独立。曾尝试用 `::after`/
`::before` + `opacity` 复合层修复，实测会让拖拽抓取掉帧更严重（具体机制未查明，
已撤销该改动），需要更谨慎的方案，暂不重新尝试。
