# 拖拽系统模块化拆分方案

## 1. 背景与目标

当前 `frontend/src/composables/usePhysicsDrag.ts` 约 1876 行，同时承担单卡物理拖拽、多卡拖拽、落地动画、FLIP 重排、clone/clone2 生命周期、hover/reveal、z-index、自动滚动和点击/拖拽阈值。

它已经不是普通 Vue composable，而是前端交互基础设施。文件库、项目页、思维画布和项目抽屉都依赖它，但各场景的业务目标不同，继续把业务判断和物理动画放在一起会增加时序、层级和清理问题。

目标：

- 建立 `DragSession` 作为一次拖拽的唯一状态和生命周期中心。
- 将物理运动、动画、视觉克隆、层级和交互拆成单向依赖的模块。
- 用文件、项目、画布、抽屉 adapter 隔离场景业务。
- 保持现有拖拽手感、clone/clone2、层级、连接线和缓存行为。
- 分阶段迁移，任何阶段都能独立验证和回滚。

### 3.1 FLIP 协调器（渐进式补充）

当前 `animation/flip.ts` 提供的是无状态的 `invertPlay()`，拖拽主流程仍分别负责元素收集、前后位置测量、动画启动和清理；页面组件的 `TransitionGroup` 也各自维护一套 FLIP。这会让拖拽让位、月份文件夹高度变化和 Vue 的 move 动画互相叠加。

新增 `animation/flipCoordinator.ts`，在 `invertPlay()` 之上提供一次 FLIP 事务的生命周期：

```text
capture(elements)       记录变化前的位置
更新业务状态 / DOM
measure(elements)       记录变化后的位置
play()                  统一 inverse transform 和过渡
cancel()                清理 transform、transition 和定时器
```

协调器只负责几何和动画，不负责拖拽状态、落点判定、Vue Store、clone 或业务 adapter。后续状态机可以调用协调器，但不需要把业务判断塞进动画模块。

实施顺序：

1. 保留 `animation/flip.ts` 作为底层无状态播放函数，新增协调器并补充取消/超时清理。
2. 先替换 `interaction/single.ts` 中源卡收合、原位归还/落点展开的两处 FLIP 调用，业务分支和 clone 生命周期保持不变。
3. 再由 `useDragEngine.ts` 统一提供 FLIP 事务，接管拖拽兄弟卡片让位和落地重定目标。
4. 最后再评估完成列多层 `TransitionGroup` 是否关闭 move 动画并交给协调器；进入/离场的 opacity/scale 过渡仍可留在组件侧。

第一阶段不接管 `KanbanColumn.vue`、`DoneColumn.vue`、`ProjectCard.vue` 和 `ProjectModal.vue` 的全部 `TransitionGroup`，避免把已经稳定的组件动画与拖拽重构同时改动。该协调器与后续状态机、单代理卡片架构兼容：状态机决定“发生什么”，协调器只负责“如何平滑移动”。

#### FLIP 协调器实现约束

协调器不是对 `invertPlay()` 的简单包装，必须先满足以下基础设施约束：

1. **样式所有权**：每个事务记录元素被写入前的 inline 值、事务实际写入的值和当前 transaction token。`cancel()`、`transitionend` 和 fallback timeout 只在 token 仍属于本事务且当前值仍是本事务写入值时恢复，禁止直接清空 `transform`/`transition`，避免旧 session 覆盖新动画。
2. **稳定元素标识**：事务接收 `{ key, element }`，前后位置使用 `Map<FlipKey, DOMRect>` 对齐，不依赖数组索引；元素卸载、增删或跨月份移动时，只播放前后都存在且 key 匹配的元素。
3. **第一阶段只处理位移**：默认只写 `translate(dx, dy)`；`scaleX/scaleY`、月份文件夹真实高度、卡片尺寸变化和文字重排暂不归协调器，继续由容器动画、clone 或 morph 负责。
4. **读写分批**：`capture` 批量读取旧 rect，业务更新后 `measure` 批量读取新 rect，随后批量写 inverse transform；下一帧再批量写 transition 和 identity transform，禁止在读写循环中交替触发布局。
5. **明确完成结果**：`play()` 返回 `Promise<FlipResult>`，结果至少包括 `finished`、`cancelled`、`stale`、`skipped`；完成判断同时支持 transitionend、fallback timeout、session cancel 和元素卸载检测。
6. **执行门禁**：`isCurrent()` 在 `measure` 前、写 inverse 前、下一帧播放前、transitionend 清理前和 fallback timeout 清理前都必须检查；旧事务不得向新动画写入哪怕一帧样式。

建议接口：

```ts
interface FlipItem {
  key: string | number
  element: HTMLElement
}

interface FlipTransaction {
  capture(items: FlipItem[]): void
  measure(items?: FlipItem[]): void
  play(): Promise<FlipResult>
  cancel(): void
}
```

## 4. DragSession 状态模型

`DragSession` 只负责一次拖拽的生命周期，不承载物理、clone、落点或业务数据。卡片视觉状态由独立的 `VisualController` 持有，运行时由 `useDragEngine` 统一编排。

`DragSession` 至少包含：

```ts
type DragPhase = 'pressed' | 'dragging' | 'landing' | 'handoff' | 'finished' | 'cancelled'

interface DragSession {
  id: string
  phase: DragPhase
  startedAt: number
  cleanup: Set<() => void>
  isCurrent(): boolean
}

interface PhysicsState { /* 速度、弹簧和坐标 */ }
interface CloneState { /* clone/clone2 的引用和显示状态 */ }
interface LandingState { /* 落地目标和动画进度 */ }
```

规则：

- 每次拖拽拥有唯一 `id`。
- 所有 `requestAnimationFrame`、`setTimeout`、`transitionend` 回调必须验证 session 仍有效。
- `DragSession` 不持有 `source`、`clone`、`clone2`、`target` 等业务或视觉引用；这些状态必须放在对应模块。
- clone/clone2 的底层 DOM 创建由 `visual/clone.ts` 提供，完整生命周期和清理由 `visualController.ts` 统一持有。
- 本体、clone、hover shell、按钮 overlay、connectionDotManager 和 reveal 必须通过同一个 `VisualController` 同步状态。
- 新 session 只能取消同一张卡片的旧 session，不能误清理其他卡片。
- 组件卸载、取消、失败、超时和再次抓取都必须走统一清理流程。

## 5. 前端场景联合方案

模块不按平级文件互相 import。由 `useDragEngine` 统一编排，模块通过 `DragSession`、`PhysicsState`、`LandingState` 和 `VisualController` 协作，避免 `animation`、`visual` 与 `session` 之间形成循环依赖。业务 adapter 只调用运行时提供的能力，不直接依赖底层动画和视觉实现。

### 5.1 文件库与项目文件区

```text
Files/index.vue
└── useFileDrag / fileDrag adapter
    └── useDragEngine

Projects/components/ProjectModal.vue
└── useFileDrag / fileDrag adapter
    └── useDragEngine
```

文件 adapter 只负责：

- 文件和文件夹目标解析。
- 面包屑、文件夹和根目录落点。
- 当前项目范围和跨项目限制。
- 调用文件移动 API、缓存更新和错误提示。

它不负责弹簧、clone、FLIP、z-index 或视觉揭示。

### 5.2 思维画布

```text
ProjectRefCard
FileRefCard
NoteSticker
EntitySticker
└── useCanvasDrag / canvasDrag adapter
    └── useDragEngine
```

画布 adapter 负责：

- 屏幕坐标到世界坐标转换。
- 卡片尺寸和落点计算。
- `landing`、`landingDone`、`onDragMove` 回调。
- 关系线的临时位置同步。
- 画布节点位置和 z-index 数据保存。

### 5.3 项目看板

```text
ProjectCard
└── useProjectDrag / projectDrag adapter
    └── useDragEngine
```

项目 adapter 负责项目列、阶段和文件拖入项目卡的业务判断，不直接处理物理运动。

### 5.4 项目抽屉

```text
ProjectDrawerCard
└── useDrawerDrag / drawerDrag adapter
    └── useDragEngine
```

抽屉 adapter 负责：

- 抽屉命中判定。
- 拖出后创建画布项目节点。
- 拖回抽屉的吸附目标。
- `physics-landing-regrab` 等接力语义迁移到统一 handoff 模块。

抽屉通用壳第一阶段已落地：

```text
DrawerShell
├── DrawerViewport
│   └── DrawerTrack
│       └── ProjectGroups / CanvasList
```

`DrawerShell` 只负责外框、展开高度和 header；`DrawerViewport` 已接管可视区域、滚动与滚动条；`DrawerTrack` 只负责内容布局和后续 placeholder/布局事务接入。项目与画布业务仍保留在 `CanvasSidebar`，文件抽屉后续复用这三个组件。旧的抽屉本体锚点补偿和状态组额外位移逻辑已移除。

## 8. 风险与控制

### 状态所有权风险

- clone/clone2 只能由 `VisualController` 持有生命周期；`visual/clone.ts` 只提供底层创建工具。
- session 按卡片记录，`DragRegistry` 不用单一全局 active 覆盖落地生命周期；当前主入口仍保留 `_active` 作为兼容性的物理 listener 调度锁，因此暂不支持两套物理拖拽同时进行，不能将其误认为并发 session 状态。
- 旧 session 的回调、timeout 和 transitionend 必须失效。

### 时序风险

- FLIP、落地飞行和再次抓取可能同时发生，重定目标前必须冻结并重新测量。
- 抽屉/画布接力不能重复创建 clone，也不能提前清理原 clone。
- reveal、hover、overlay 和 connectionDotManager 不再各自维护生命周期；由 `VisualController` 统一协调，底层工具保持无状态。

### 层级风险

- z-index 必须基于真实层叠上下文动态计算。
- 拖拽卡片只能在拖拽期间高于抽屉，未命中后必须回到 UI 下方。
- 顶部胶囊、底部工具栏、抽屉和浮窗必须分别验收。

### 坐标风险

- 文件库/项目页使用容器或视口坐标，画布使用世界坐标。
- 画布缩放、平移、页面滚动和浮窗定位不能共享未经换算的落点。
- 关系线必须跟随真实卡片或克隆体位置。

### 业务边界风险

- 文件 adapter 不能绕过后端项目归属、版本和文件夹循环校验。
- 画布卡片拖入抽屉与文件拖入文件夹不是同一业务目标。
- 未命中目标时不得误触发删除、移动或项目创建。

### 性能风险

- 多模块不能在同一帧重复 `getBoundingClientRect()`。
- 静止卡片使用数据坐标，只有拖拽/悬浮卡片做高频真实测量。
- 多卡拖拽只能注册一套全局 pointer listener。

## 10. 状态重构计划

当前 `DragSession` 已经完成第一层状态划分，负责一次拖拽会话的生命周期：

```text
pressed → dragging → landing / handoff → finished / cancelled
```

这层状态不再扩张业务含义。后续在其内部补充视觉和落地状态，用于描述 clone、本体、目标布局和动画阶段，避免继续在 `single.ts` 中堆叠布尔条件。

### 10.1 目标状态层次

```text
DragSession（会话生命周期）
└── DragVisualState（视觉与落地阶段）
    ├── dragging
    ├── resolving-target
    ├── absorbing
    ├── returning
    ├── morphing
    ├── revealing
    ├── completed
    └── cancelled
```

`DragSession` 负责 token、有效性和 cleanup；`DragVisualState` 负责当前动画阶段和落点目标；`VisualController` 负责本体、clone、hover shell、按钮 overlay、connectionDotManager 和 reveal 的同步。业务 adapter 只提供目标判定和状态更新，不直接切换视觉状态。

`VisualController` 是卡片视觉状态的唯一来源：

```ts
type CardVisualState = 'idle' | 'hover' | 'dragging' | 'landing' | 'landing-hover' | 'revealing' | 'cancelled'

interface VisualController {
  setState(state: CardVisualState): void
  setPointerPosition(point: { x: number; y: number }): void
  cleanup(): void
}
```

本体和所有视觉代理消费同一个状态，不再分别依赖 DOM `:hover` 或各自的临时 class。

### 10.2 渐进实施阶段

1. **盘点现有隐式状态**：整理 `single.ts`、`LandingState`、clone 生命周期和各 adapter 中的布尔条件、early return 与 cleanup，建立现有状态转移表；不改行为。
2. **引入阶段类型**：新增内部 `LandingPhase`/`DragVisualState`，先由现有分支写入和读取，保留旧分支作为兼容逻辑，确保可随时回退。
3. **收拢落地编排**：把吸入、原位归还、跨列落位、目标等待和再次抓取分别变成阶段处理函数；每个阶段只负责进入、推进和退出清理。
4. **接入 FLIP 协调器**：状态转换只触发 capture/measure/play，几何动画和状态判断分离；禁止同一元素同时被两套 FLIP 控制。
5. **统一取消与接力**：所有阶段都支持 `cancelled`、超时和 `handoff`，中途再次抓取从当前视觉盒继续，不重新猜测起点。
6. **删除旧分支**：回归测试和桌面端手测覆盖文件、项目、画布、抽屉、多卡后，删除已被状态处理函数替代的嵌套分支和兼容兜底。

### 10.3 约束

- 状态机不拥有 DOM clone；底层创建由 `visual/clone.ts` 提供，clone 生命周期和本体/代理同步归 `VisualController`。
- 状态机不计算世界坐标；坐标换算仍由 `coordinates.ts`/adapter 提供。
- 状态转换不能隐式触发业务 Store 更新，业务更新由 adapter 明确调用。
- 每次状态进入都必须有对应的退出清理，且退出后不得再执行旧 session 的异步回调。
- 先完成状态转移表和 FLIP 协调器，再实现 `VisualController`；单代理卡片作为其后续落地形态，不再另起一套 clone 架构。

## 12. 单代理卡片（CardProxy）方案

### 12.1 背景

已完成列拖入卡片重叠的排查（见第 7 节完成列部分）暴露出一个更根本的问题：当前一次拖拽的视觉表现由四套独立状态机拼接而成，彼此只靠时序衔接，不共享同一份真相：

```text
drag clone 状态机（拾起时跟手的克隆体，clone.ts 的 cloneForDrag）
landing clone 状态机（落地形变克隆体，clone.ts 的 createLandingClone，即“clone2”）
reveal hover 状态机（reveal.ts 的 phys-reveal-hover / phys-reveal-controls）
真实卡片 hover 状态机（组件自身的 :hover 样式）
```

四者各自维护位置、透明度和 hover 状态，任何一次 reveal、pointer 变化或 session 切换发生在中途，都会出现某一套状态机的动画播到一半就被另一套覆盖——项目看板的 hover 撞色 bug、历史上相机缩放不跟随、抽屉分组跳一下，本质都是同一类"多个状态源互相覆盖"问题的不同表现。

这次重构的目标不是"让两个 hover 动画同步"，而是：**整个拖拽过程中始终只有一个视觉主体、一个 hover 真相来源、一个当前 session。**

### 12.2 CardProxy 的职责边界

新增 `CardProxy`，取代 `clone.ts` 的 `cloneForDrag` + `createLandingClone` 两次独立创建。代理节点只创建一次，全程通过 phase 切换驱动同一个 DOM 节点，不再销毁重建。

```ts
type CardProxyPhase = 'idle' | 'dragging' | 'landing' | 'revealing' | 'disposed'
type AnimationResult = 'completed' | 'cancelled'

interface CardProxy {
  readonly cardKey: string
  readonly sessionId: string
  readonly phase: CardProxyPhase
  readonly element: HTMLElement

  beginDragging(): void
  setHovered(hovered: boolean): void
  updateDragPosition(position: DragPosition): void
  moveTo(rect: DOMRect, options?: MoveOptions): Promise<AnimationResult>
  revealTo(target: HTMLElement, options?: RevealOptions): Promise<AnimationResult>
  cancel(): void
  dispose(): void
}
```

**不暴露通用 `setPhase(phase)`。** 调用方若能直接从 `dragging` 跳到 `disposed`、或从 `revealing` 跳回 `landing`，状态机约束就只停留在文档里——历史上不止一次出现"为了修一个场景直接改内部状态"，又重新制造隐式时序。改成每个动作方法（`beginDragging`/`moveTo`/`revealTo`/`cancel`/`dispose`）内部各自校验并完成合法转换：

```text
idle → dragging
dragging → landing
landing → revealing
revealing → disposed
任意未结束状态 → cancelled/disposed
```

**`cancel()` 和 `dispose()` 语义必须彻底分开，不能合并成一个"清理"动作：**

```text
cancel()
→ 停止当前动画，把当前 Promise resolve 为 'cancelled'
→ 清除监听、rAF、timeout
→ 代理本身仍然存在，等待编排层决定后续处理（可能被复用、可能接着 dispose）

dispose()
→ 永久销毁代理、移除 DOM、退订 CardInteractionState
→ 禁止任何后续方法调用
```

如果 `cancel()` 顺便删除了 DOM，二次抓取或 session 接管时会出现视觉空窗——这正是历史上"落地动画中途再次抓取"这类场景最容易出问题的地方。可以再提供一个 `cancelAndDispose()` 便捷方法，但底层这两个语义必须保持分离。

`moveTo`/`revealTo` 返回的 `Promise<AnimationResult>` 必须在取消时也正常 `resolve('cancelled')`，不能悬空不 resolve——历史上"取消旧 session 却让新一轮动画卡住"的问题，根子多半就是这类遗留 Promise 没人 resolve。调用方（`morphLifecycle.ts`）据此判断是否继续往下执行，仍应叠加 `session.isCurrent()` 兜底，双重保险。

`dragging → landing → revealing → disposed` 中间保留独立的 `revealing`：真实卡片已经显示、代理仍在淡出的这段时间不能与"代理已销毁"合并，否则 `revealed` 会同时表示"reveal 已开始""真实卡已可见""代理动画已结束""代理可销毁"四件事，语义过载后又会在后续实现里长出新的时序分支。

CardProxy **只负责**：

- 代理 DOM 的创建和销毁
- 几何状态（位置、尺寸、缩放）
- phase 切换
- hover 视觉状态的呈现（不判定）
- 代理自身动画
- session 校验和动画取消

CardProxy **不负责**（仍留在 engine 和 adapter/lifecycle 编排层）：

- 判断项目该落在哪一列
- 修改业务数据
- 计算拖拽目标
- 控制真实卡片何时挂载
- adapter 之间的差异逻辑

### 12.3 hover 状态只有一个来源

现在的 bug 根子在于 `hoverShell` 自己监听/推断 hover，跟真实卡片各判各的。改为单一状态源，双方都只读、不自己判定。这是交互语义（谁在拖、谁被 hover），不是视觉实现细节，放在 `core/CardInteractionState.ts`，不放 `visual/`：

```ts
interface CardInteractionSnapshot {
  sessionId: string | null
  hoveredCardKey: string | null
  draggedCardKey: string | null
}

interface CardInteractionState {
  getHoveredCardKey(): string | null
  getDraggedCardKey(): string | null
  setHoveredCardKey(sessionId: string, key: string | null): void
  setDraggedCardKey(sessionId: string, key: string | null): void
  subscribe(listener: (snapshot: CardInteractionSnapshot) => void): () => void
  reset(sessionId: string): void
}
```

**单一状态源不代表安全——写入和清理都必须校验 session 归属，只有当前 owner 才能生效。** 若旧 session 延迟调用 `reset(oldSessionId)`（比如落地动画的 timeout 兜底在新 session 已经开始后才触发），必须保证它不会清掉新 session 已经写入的状态；`setHoveredCardKey`/`setDraggedCardKey` 同理，非当前 owner 的写入应静默忽略。这跟 `DragRegistry` 现在"按卡片记录 session、避免互相误清理"是同一个模式，直接复用即可，不需要另起一套校验逻辑。

代理和真实卡片都从这里派生：`const hovered = getHoveredCardKey() === cardKey`。CardProxy 不监听 `mouseenter`/`mouseleave`——拖拽期间代理通常带 `pointer-events: none`，本来就无法可靠拥有自己的 hover 语义，让它自己判定只会长出第二套判定系统。

它应该由 `DragRegistry` 持有，而不是模块级全局单例：

```text
DragRegistry
└── CardInteractionState
```

理由：一旦出现主页面拖拽和画布内部拖拽共存、多选拖拽需要独立状态、测试并行运行等场景，全局单例会成为新的隐式耦合点——跟这次重构"消灭隐式状态源"的初衷矛盾。由 Registry 持有能让状态生命周期跟 session 生命周期天然对齐。

### 12.4 代理 DOM 分层，隔离 transform 写入者

现在 `hoverShell` 用 `translateY` 表达 hover，而拖拽、landing、morph 也都要控制 transform——这是"谁最后写 transform 谁赢"这类冲突的技术根源（历史上相机缩放、抽屉分组跳动都是这个模式的变体）。代理 DOM 应分三层，各自只写自己的 transform：

```text
<div class="card-proxy-position">      拖拽位置、landing、morph transform
  <div class="card-proxy-hover">       hover translateY / 阴影
    <div class="card-proxy-content">   contentScale、文字样式、圆角、内容形变
```

真实卡片保持同样的层级划分，交接时两边结构对应，不需要临时换算。

三层各自的职责要卡死，不能三层都控制同类几何：`position` 只处理屏幕空间位移和外层 scale；`hover` 只处理局部 Y 偏移和阴影；`content` 只处理内部内容比例，不承担世界坐标位置。

**`contentScale` 尤其要在 12.6 核对时拆成两个不同名字，不能笼统都叫 scale：**

```ts
worldScale    // 补偿画布 zoom 的逆缩放——是坐标系转换的一部分，不是普通内容动画
contentScale  // 卡片自身的视觉内容缩放，跟画布 zoom 无关
hoverOffsetY  // hover 层的局部位移，不是几何位置
```

这条直接对应本次会话已经踩过的坑：相机缩放不跟随克隆体那次 bug，根子就是"画布 zoom 补偿"和"卡片内容缩放"混用同一个 `contentScale` 变量，命名拆开能从源头避免同类问题复发。

### 12.5 morphLifecycle.ts 退化为纯编排器

重构后 `morphLifecycle.ts`（当前 331 行）只做阶段编排，不再实现视觉细节：

```ts
await proxy.moveTo(targetRect)
assertSession()

prepareRealCard(targetEl)
proxy.setHovered(sharedHoveredState)

await proxy.revealTo(targetEl)
assertSession()

showRealCard(targetEl)
proxy.dispose()
```

它不再创建 clone2、复制 hover 状态、自己拼 transform/transition、同时管理多个 `HTMLElement`，也不再猜测哪个节点是当前视觉主体。若这次拆分做对了边界，行数预期能从 331 降到约 120–180；降不到这个量级，说明职责还没拆干净。

`CardVisualController.ts` 不能只是把存储的 `HTMLElement` 换成 `CardProxy`——要趁这次把职责也收紧成"管理 session 与 CardProxy 的对应关系"：

```ts
interface CardVisualController {
  createProxy(options: CreateCardProxyOptions): CardProxy
  getProxy(sessionId: string): CardProxy | null
  cancelProxy(sessionId: string): void
  disposeProxy(sessionId: string): void
}
```

不能继续暴露 `setCloneElement()`/`setLandingClone()`/`setRevealElement()` 这类接口——那只是把存储对象换了个名字，旧的"双 clone"心智模型还会残留在接口形状里。改造完成后，`CardVisualController` 应该完全不知道 `clone2` 这个概念。

### 12.6 clone2 隐藏职责清单（迁移前必须先盘点）

`clone2`（`createLandingClone`）目前不只是"第二个克隆"，还在暗中承担尺寸归一化节点、样式快照节点、hover 退出动画节点、真实卡 reveal 遮罩四种角色。迁移到 CardProxy 前必须先逐项列出、逐项迁移，不能只迁移创建逻辑：

- **几何**：初始 rect 来自谁；landing rect 是否包含滚动补偿；`contentScale` 是否独立于 outer scale；是否修正 border/padding/zoom。
- **视觉**：border-radius、box-shadow、backdrop-filter、opacity、hover translateY、controls 的显隐、selected/active 状态。
- **内容**：`copyInheritedTextStyle`、图片或图标尺寸、文本裁剪、line-height、CSS variables、伪元素是否丢失。
- **时序**：clone2 在什么时候插入 DOM；revealEl 在什么时候显示；旧 clone 在什么时候删除；transitionend 是否有超时兜底；cancel 时谁清理内联样式。
- **交互**：pointer-events、cursor、data 属性、adapter 特有 class。

### 12.7 渐进迁移：显式 feature gate，抽象成 visual strategy 对象

不靠"这是项目卡所以走新路径"这类隐式判断，在 adapter 上显式声明视觉模式：

```ts
type DragVisualMode = 'legacy' | 'proxy'

interface DragAdapter {
  visualMode: DragVisualMode
}
```

**关键约束：不能在 `single.ts`/`morphLifecycle.ts` 里到处写 `if (visualMode === 'proxy') ...`。** 那样迁移期间会形成交错路径，最后很难判断哪些分支还依赖 legacy、哪些可以安全删除。应该在一次拖拽开始时就确定策略对象，后续统一调用同一组方法名：

```ts
interface DragVisualStrategy {
  begin(context: DragVisualContext): DragVisualHandle
}

interface DragVisualHandle {
  update(position: DragPosition): void
  land(target: LandingTarget): Promise<AnimationResult>
  reveal(target: HTMLElement): Promise<AnimationResult>
  cancel(): void
  dispose(): void
}
```

**每次拖拽创建一个 handle，而不是让 strategy 自身保存当前代理。** `strategy` 只是无状态的工厂，`handle` 才持有这次拖拽的具体状态。这样新 session 启动、同一卡片二次抓取、并行测试、legacy 与 proxy 生命周期隔离都天然成立，不需要额外加锁去防止两次拖拽共用同一个 strategy 实例导致状态串号。调用方在拖拽开始时拿到 handle：

```ts
const handle = createVisualStrategy(adapter.visualMode).begin(context)

handle.update(position)
await handle.land(target)
await handle.reveal(target.element)
handle.cancel()
handle.dispose()
```

`legacy` 和 `proxy` 两个策略实现短期并存，但内部互不感知，不会互相渗透。等全部 adapter 切到 `proxy`，删除 legacy 策略实现即可，不需要再逐处排查 `single.ts` 里散落的分支判断。

第一步不直接取代 `clone.ts`，而是先实现 `CardProxy`，让项目看板 adapter 通过 `proxy` 策略调用它，`cloneForDrag`/`createLandingClone` 暂不删除。项目看板稳定后再迁移文件卡/画布卡/抽屉卡，最后删除旧 clone API——每一步都能独立验证和回滚，不需要一次性重写整个拖拽引擎。

在此之前，`single.ts` 暂不拆分文件结构——它已经 1068 行，但现在立刻拆会把"视觉代理迁移"和"拖拽流程模块化"两类变化混在一起，出问题时无法判断是哪一类改动引入的。当前只改调用点，并加一条临时约束：**`proxy` 策略路径下，`single.ts` 禁止直接读写 `proxy.element.style`，只能调用 `CardProxy` 暴露的方法**（`updateDragPosition`/`moveTo`/`revealTo`/`cancel`/`dispose`），否则 `single.ts` 会很快重新长出一份视觉实现。等所有 adapter 切换完成，再评估是否把 `single.ts` 拆成 `single/beginSingleDrag.ts`、`updateSingleDrag.ts`、`completeSingleDrag.ts`、`cancelSingleDrag.ts`，但不属于这次范围。

三个文件的编排权限也需要一条明确规则，防止互相越权：

```text
single.ts        → 决定什么时候开始落地（拖拽业务阶段编排）
morphLifecycle.ts → 决定 landing/reveal 的先后（跨阶段事务编排）
CardProxy.ts      → 决定动画具体怎么播放（单个视觉阶段实现）
```

### 12.7a reveal.ts 的取舍：不整体搬迁，按职责拆两半

`reveal.ts` 里的逻辑分两类，不能整体判给 `CardProxy` 或整体保留：

**应迁入 `CardProxy`**（代理自身的视觉状态）：`phys-reveal-hover`、`phys-reveal-controls`、hover translate、代理节点的 reveal 动画、代理视觉 class 切换。

**应继续保留**（真实卡片的长期归属，不该被代理接管）：真实卡片 reveal 前后的准备、恢复真实卡片 opacity、控件显隐的真实 DOM 清理、无代理场景的通用 reveal 工具、legacy 策略的兼容路径。

理由：代理不应该长期控制真实卡片的显示状态——那是真实卡片自己的职责，`CardProxy` 只负责"交接前"的那一小段。迁移期间 `reveal.ts` 可以逐步收缩成 `prepareRevealTarget()`/`completeRevealTarget()`/`cancelRevealTarget()` 三个函数，等 legacy 策略全部删除后再决定是保留为真实节点工具，还是并入 `morphLifecycle.ts`。不要为了目录整洁提前把这部分塞进 `CardProxy`。

### 12.8 五步迁移顺序

每一步都必须先满足对应的完成标准，才能进入下一步——不满足就停在当前步骤补齐，不允许"先往下做，回头再补"。

1. **定义 CardProxy 的职责边界**（本节 12.2–12.4），先落地类型和分层 DOM，不接入任何 adapter。
   完成标准：`CardProxy` 可以独立创建、移动、取消和销毁，但没有任何业务 adapter 使用它。
2. **hover 状态源整合**：新增 `CardInteractionState`，CardProxy 和真实卡片都改为读取它，暂不改动 clone/morph 流程本身。
   完成标准：真实卡片与代理能够读取同一份 `CardInteractionState`，旧 clone 流程行为完全不变。
3. **clone2 职责清单核对+CardProxy 落地**：按 12.6 的清单逐项确认现有实现覆盖了哪些职责，缺项在 CardProxy 里补齐。
   完成标准：清单每一项都有明确去向——迁入 `CardProxy`、保留在 `reveal.ts`、保留在 adapter、或确认已无必要，四选一；不允许存在"可能不需要"但未验证的项目。
4. **morphLifecycle.ts 收敛为编排器**：按 12.5 的形态重写，只调用 `proxy.moveTo/revealTo/dispose`。
   完成标准：`morphLifecycle.ts` 不再直接创建视觉 DOM、写 `style.transform`、写 `style.transition`、操作 clone2、推断 hover，也不再持有多个视觉主体。
5. **项目看板 feature gate 接入，验证后再推广**：先接项目看板，人工验收 + 自动化测试通过后，依次推广文件卡、画布卡、抽屉卡，最后删除 `cloneForDrag`/`createLandingClone`。
   完成标准：只有 `projectDrag` 进入 `proxy` 路径，其他 adapter（`fileDrag`/`canvasDrag`/`drawerDrag`，仍是 `legacy`）的行为 diff 为零。

#### clone.ts 删除门槛

不能只看四个 adapter 的 `visualMode` 是否都已改成 `'proxy'`，还要确认没有其他隐式调用者。删除 `cloneForDrag`/`createLandingClone` 前必须逐项确认：

- [ ] 所有 adapter 的 `visualMode` 均为 `'proxy'`。
- [ ] `cloneForDrag` 无调用方。
- [ ] `createLandingClone` 无调用方。
- [ ] `clone2` 相关类型和字段无残留引用。
- [ ] `legacy` visual strategy 实现已删除。
- [ ] 旧 hover/reveal class（`phys-reveal-hover`、`phys-reveal-controls` 等）无调用。
- [ ] 相关测试全部迁移到新路径，没有仍断言 legacy 行为的用例。
- [ ] 全局搜索以下关键词，确认无 clone2 语义残留：`clone2`、`landingClone`、`revealEl`、`phys-reveal-hover`、`phys-reveal-controls`、`copyInheritedTextStyle`、`contentScale`。这些隐藏职责有些不是从 `clone.ts` 直接调用的（比如画布相机缩放的 `contentScale` 传递链路），全局搜索比只看调用方列表更可靠。

### 12.9 必须覆盖的自动化测试

1. **hover 中开始拖拽，落地时 pointer 已离开** —— 最终真实卡不能残留 hover 位移。
2. **landing 动画中再次开始新的拖拽 session（优先级最高，历史 bug 复现率最高的场景）** —— 旧代理的 `transitionend` 和清理回调不能修改新代理或真实卡。相机缩放不跟随、抽屉分组跳一下两个历史 bug 根子都在"上一段动画收尾时机"与"下一段起始状态"没对齐，比 hover 场景更容易在真实使用中触发，应最先锁死。
3. **目标真实卡延迟一帧或多帧挂载** —— 代理必须继续维持最终视觉，不能闪空或提前销毁。

手测高风险场景（自动化测试之外必须跑一遍）：快速连续拖动同一张卡 → 落地动画未结束再次抓起 → 跨列 → 鼠标在动画期间反复进出真实卡区域。这个场景跑稳，说明状态机基本收住了。

### 12.10 最终链路

```text
真实卡片提供视觉快照
        ↓
拖拽开始创建唯一 CardProxy
        ↓
dragging / landing / revealing 只切换状态
        ↓
真实卡片接管同一份交互状态
        ↓
CardProxy 销毁
```

### 12.12 三条全局规则

这次重构真正建立的是三条规则，不是一堆局部修补：

```text
一个 session 只有一个视觉主体
一个交互语义只有一个状态来源
一个视觉属性只有一个写入者
```

只要实现阶段严格守住这三条，历史上反复出现的 hover 残留、缩放不同步、抽屉跳动、旧动画污染新 session，才有可能被一次性从根上收掉，而不是每次单独修一个症状。
