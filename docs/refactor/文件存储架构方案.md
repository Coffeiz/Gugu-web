# 存储 / 工作空间架构方案（设计版 v2 · 2026-07-11）

> 状态：**设计稿，未动代码**。供评审。定稿后再拆可执行任务、分阶段实施。
> v2 变化：定位从「Web→OSS→Desktop 迁移」升级为 **Local-first + Cloud-optional 的 AI 工作空间运行时**。
> 真相源改「按运行域」、FolderTree 升为核心领域接口、file_id 身份坐实 opaque、软删定为三重身份、
> 预留（不建）operation log。
> 关联：[[gugu-p2-refactor-plan]]、[[gugu-agent-reliability]]、`app/services/storage/`。

## 0. 定位

咕咕的核心不是「网盘」，是 **AI 工作空间**：`项目 + 文件 + 记录 + Memory + Agent 操作历史`。
存储层的真正职责是——**给 Agent 一个稳定、可靠、可解释的「现实映射层」，让它能安全操作真实世界**
（与 ADR「让 AI 在稳定的世界里可靠工作」同源）。

产品形态：**本地可独立运行（未登录/离线），云可选叠加（登录同步）**。这条把下面所有设计的目的点透了。

## 1. 三运行域 · 按模式定真相源

「DB 唯一真相源」只对**云侧**成立；完整产品是**每个运行域各有自己的元数据真相源**，同步模式下靠同步协议达成最终一致：

| 运行域 | 真相源 | 元数据 | 字节 |
|---|---|---|---|
| 未登录（本地） | **本地** | 本地 SQLite | 本地文件系统 |
| 登录·仅本地 | **本地** | 本地 SQLite | 本地文件系统 |
| 登录·云+本地双向 | **云为权威副本，本地可发起变更 → 两副本收敛** | Cloud DB ↔ Local SQLite | OSS ↔ 本地镜像 |

```
              Sync Engine（后续大件）
             ↙                 ↘
     Local SQLite            Cloud DB
         |                       |
     Local Files               OSS
```

双向同步**不是** `Cloud → Local` 的 CRUD，而是**两个都能写的副本要收敛**（飞机上改名、回家联网、两端同时改）——这是分布式系统问题，靠 file_id + version + tombstone（+ 后续 op-log）解决，见 §3/§4。

## 2. 领域模型：FolderTree 核心接口 + StorageBackend + KeyStrategy

**分层（漂亮的三层，别合并）**：

```
   领域操作（建/移/删/树遍历/软删）
              ↓
   FolderTree 接口（逻辑/元数据树）      ← 核心领域接口
              ↓
   StorageBackend 接口（字节：put/get/delete/rename/list/presign）
```

- **`FolderTree`（核心领域接口）**：`getFolder / getChildren / createFolder / moveFolder / deleteFolder / resolvePath`。三实现：
  - `CloudFolderTree` → SQLAlchemy（服务端）
  - `LocalFolderTree` → 本地 SQLite（桌面端 / 离线）
  - `SyncFolderTree` → merge 层（**后续同步阶段**）
- **`StorageBackend`**：只管字节，Local / OSS 两实现。**与 FolderTree 正交**（逻辑树 ≠ 字节存储）。
- **`KeyStrategy`**：物理 key 怎么生成 + 文件夹移动语义。见 §3。

## 3. 身份是 file_id，不是 path → 坐实 opaque

**路径会变（`images → assets → design`），文件身份不变。** 所以：
- **身份 = `file_id`**（永不变）；路径 = `folder_id` 链，是**可变的逻辑属性，只活在元数据**。
- **物理 key 从 file_id/uuid 派生（opaque）**：`{uid}/blobs/{uuid}.{ext}`。path-mirror 把「会变的路径」焊进「不该变的身份」，与此直接矛盾 → **淘汰**。

两个 KeyStrategy：
| | path-mirror（旧/Local 过渡） | **opaque（目标）** |
|---|---|---|
| key | `{uid}/个人文件/.../file` | `{uid}/blobs/{uuid}.{ext}` |
| 文件夹移动/改名 | 逐对象搬（OSS 上 2N 次请求，昂贵） | **改 `folder_id`，O(1)，零搬运** |
| 孤儿目录 | 会留（Local） | **不存在** |
| 同步友好 | 差（身份含路径） | **好（身份稳定）** |

> 结论：**opaque 是终态**。它同时解决 OSS 移动成本、Local 孤儿、以及双向同步的身份稳定性——一石三鸟。

## 4. 要现在埋好的字段（同步/软删/审计的地基）

`files` / `folders` 现在就加（迁移 nullable，安全）：

```
files:  id  folder_id  storage_key  storage_backend(local|oss)  version  updated_at  deleted_at
folders: id parent_id project_id name  version  updated_at  deleted_at
```

- **`storage_backend`**：支撑 §7 的 lazy 双后端迁移（每文件知道自己在 local 还是 oss）。
- **`version` / `updated_at`**：双向同步的冲突裁决基线。
- **`deleted_at`（tombstone）**：见 §5。

**operation log —— 预留、不建（划入 context 因果层）**：
- 双向同步里 last-write-win 会丢**意图**（A 10:00 移动 / B 10:01 删除，只看 version 不知用户想干嘛）。op-log 能做冲突提示 / undo / audit / **AI 解释**，对 Agent 产品尤其值钱。
- **但现在不建机制本身**（每变更写 op + 重放 + 因果时钟 + 压缩 = event-sourcing 级承诺，同步引擎还不存在，建了没消费者）。
- **现在只做「可发射成 op」**：所有变更收敛到 FolderTree 的少数操作口（create/move/rename/delete）+ 上面的字段。将来从这些口发射 op 即可，不返工。
- **与 agent 决策轨迹（agent.traj）合流,别建两套日志**。它的定性不是「同步管道」，而是**工作空间的因果历史**（这个文件为什么在 / 谁移的 / 关联哪个任务）——正是咕咕「Agent 解释真实世界」的品牌。**同步阶段再建实体。**

## 5. 软删：三重身份（应尽早做）

`deleted_at` 软删 + 整体恢复，同时服务三个系统：
1. **回收站**：用户「恢复昨天删的项目」。
2. **Agent 执行安全层**：咕咕删目录 = `deleted_at=now()` 可撤销，是它「安全操作真实世界」的信任底座（与 P2-b 错误处理、confirm-gate 同一条可靠性主线，见 [[gugu-agent-reliability]]）。
3. **同步删除墓碑**：无 tombstone 无法区分「文件不存在」vs「文件被删除」，双向同步传播删除必须靠它。

> 一份软删，三处受益 → 优先级高，和迁移并行甚至更前。

## 6. 模块切分（按「能否搬进桌面端」）+ 依赖方向

```
app/services/storage/
  base.py              # StorageBackend 抽象 + KeyStrategy 协议 + FolderTree 接口
  factory.py           # 按配置选后端 + 选策略

  local/               # ★本地策略 —— 桌面客户端可复用
    backend.py         # LocalStorageBackend（真实文件系统）
    tree.py            # ★可移植核心：文件夹树 ↔ 真实目录 物化/改名/移动/删除/对账
    keys_pathmirror.py # path-mirror（Local 过渡期浏览用；opaque 落地后可退役）

  oss/                 # OSS 策略 —— 纯服务端
    backend.py         # OSSStorageBackend（SDK / presign / 直传）
    keys_opaque.py     # opaque/uuid key
    migrate.py         # Local→OSS lazy 迁移

  bindings.py          # 服务端胶水：CloudFolderTree（把 tree 接口接到 DB/SQLAlchemy）
```

**可移植铁律**：`local/tree.py`、`keys_pathmirror.py` **绝不 import `app.*` / SQLAlchemy / FastAPI**。只依赖文件系统抽象 + `FolderTree` 接口。
**依赖方向（定死）**：`oss/` 永不被 `local/*` import（桌面端不拖 OSS SDK）；`local/tree.py` 永不 import `app.*`；`bindings.py`/`oss/`/`factory.py` server-only。
**桌面端语言无关**：桌面端更可能 Electron+TS / Tauri+Rust / Swift，**不追代码复用、追领域规则一致**——见 §9。

## 7. 现状诊断（root cause）+ opaque 如何溶解它

`Folder` 现为纯 DB 行（无 storage_key/物理路径，`app/models/__init__.py:156`），物理只靠文件 key 内嵌路径：
- **DB→盘缺失**：建空文件夹从不 `mkdir`（`storage/__init__.py:113` 只在写文件时隐式建）→ 空文件夹不上盘。
- **盘→DB 幽灵**：`rename_file`（`:130`）只建新父、**不删空旧目录**；`delete`（`:119`）只清一层 → 移动/改名后旧目录成幽灵（如两个 `adr`）。（已停 WIP `relocate_folder_tree_files` 逐文件 rename，正是幽灵制造机。）
- **回收站无文件夹**：`delete_folder` 硬删文件夹行（`db.delete`）。

**关键判断：这些是 path-mirror 的病，opaque 迁移会直接溶解整类**——opaque 下文件夹是 DB 行 + App/桌面端浏览（没人翻原始桶）、key 不含路径（移动=改 DB、无孤儿）。所以**别在 Local 目录生命周期上重投入**（那是修一个正要抛弃的模型）；只做**过渡期最小稳定** + **一次性清幽灵**（对账器当**一次性工具**，非常驻小时级扫描）。

## 8. OSS opaque + Lazy 双后端迁移

**不搞一次性大作业 + 冻结**，走 **lazy 双后端并存**：
- `LocalStorageBackend` 与 `OSSStorageBackend` 并存，每文件 `storage_backend` 标记所在。
- **新上传直接 OSS opaque**；**老文件读时顺带迁 + 后台低频冷扫**，逐个搬完、可随时中断、无冻结窗口。
- **per-file 不变式（保留原六红线里仍适用的）**：幂等、迁后 checksum 校验、**迁完校验通过前不删源**（可回滚）。dry-run 大报告 / 全局冻结这些一次性作业的包袱可扔。
- 访问路由：`if storage_backend==local: 读 Local（顺带迁 OSS、改 storage_key/backend）else: 读 OSS`。

## 9. 桌面端：三模式 + 双向同步（后续）+ 语言无关规格

- **未登录 / 登录·仅本地**：桌面端**离线跑完整模型**——`LocalFolderTree`(本地 SQLite) + `local/tree.py`(物化真实目录) + `LocalStorageBackend`。无云。
- **登录·云+本地双向**：`SyncFolderTree` merge 层 + 同步引擎（**后续大件，现在不建**）；靠 §3/§4 的 file_id/version/tombstone(/op-log) 收敛。
- **领域规则一致（不追代码复用）**：写一份**语言无关的《Folder/File 行为规格》**：
  ```
  create: 建元数据 + 建物理目录
  delete: 打 tombstone + 移 trash（可撤销）
  move:   改 parent_id，保持 file_id 不变，物理不搬（opaque）
  rename: 改 name，保持 file_id
  ```
  Python(服务端) / TS / Rust(桌面端) **各自实现 + 各自跑同一套平行测试向量**——比共享代码可靠（咕咕验证过：projectStages、agent 工具）。

## 11. 生产安全红线

1. 存量 `storage_key` 不主动重写（lazy 迁移逐个搬、迁完校验前不删源、可回滚）。
2. 新列（`storage_backend/version/updated_at/deleted_at`）走 Alembic nullable、不回填即安全。
3. 对账器只补目录 / 报告孤儿，**非空目录先报告人工确认**，绝不自动删。
4. 全程 `get_owned` 授权 + 30 天可还原（P2④ 红线）。
5. 先 staging 全量 dry-run → 灰度内部账号 → 放量。
