# ADR：文件存储抽象与生命周期一致性（Web 后端 · 2026-07-11）

> **状态**：设计稿，未动代码。供评审，定稿后拆任务实施。
> **一句话工单**：把 Web 文件系统从「**路径直拼**」升级成「**领域模型 + 可换存储后端**」——
> 业务代码只经 `File Service` / `StorageBackend`，不再直接拼 `/upload/.../file`。
> **近期真实风险不是迁移成本，是数据完整性**：丢文件 / Agent 删不可恢复 / DB 与盘不一致。
> **前提**：生产未来**几个月仍用本地 `upload/` 目录**；OSS 是几个月后的事。所以现在做「演进层」，不做完整 OSS 迁移。
> 关联：[[gugu-p2-refactor-plan]]、[[gugu-agent-reliability]]、`app/services/storage/`。

## 0. 范围（写死，防越界）

**现在做（Web 1.0，Local 还要用几个月）**：
- `StorageBackend` 抽象——**把 `upload/` 当成一种后端实现，而不是整个文件系统**。
- `KeyStrategy` 接口——**现在保留 `PathMirrorStrategy`（存量数据零迁移）**，opaque 留作未来可换实现。
- 文件夹**生命周期一致性**（DB 状态 ↔ 磁盘状态）：修当前的丢失/幽灵/不可恢复。
- `File Service`——**REST 与 Agent 共用同一套文件语义**。
- 文件夹**软删 + 整体恢复**；埋 `version / updated_at / deleted_at` 字段。

**OSS 到来时才做**（几个月后，非现在）：
- `OSSStorageBackend`；lazy 双后端（新文件→OSS、旧文件留本地慢慢迁）。

**更以后再决定**（现在连是不是要都没定）：
- opaque key（是否切、还是 path-mirror 长期留）；桌面端 / 双向同步 / 冲突 / operation log。

> 原则：**现在把「文件操作入口」收紧就够了；不为未来把生产文件系统提前重写。**
> **别为未来桌面端把后端写成同步系统；但今天的后端不能挡住未来。**

## 1. 现状诊断（当前要修的 root cause）

`Folder` 是纯 DB 行（无 storage_key/物理路径，`app/models/__init__.py:156`）；物理存在只靠文件 key 内嵌路径 + 业务代码直拼 `/upload`。当前**生产在跑**的三个数据完整性问题：
- **空文件夹不上盘**：建文件夹从不 `mkdir`，只在写文件时隐式建（`storage/__init__.py:113`）。
- **rename 留幽灵目录**：`rename_file`（`:130`）建新父但**不删空旧目录**；`delete`（`:119`）只清一层 → 移动/改名后残留（如两个 `adr`）。
- **删文件夹无法恢复**：`delete_folder` 硬删文件夹行（`db.delete`）。

**根因**：文件夹缺物理生命周期 + 业务层直接拼路径、无统一入口。**这三个是当前线上真实风险**，与 OSS 无关，先修。

## 2. 目标抽象（现在就落）

```
                REST API        Agent 工具
                    \             /
                     File Service          ← 唯一文件语义入口（REST 与 Agent 共用）
                    /            \
             FolderTree      StorageBackend
             (领域层)          (字节层)
                 |                |
             SQLAlchemy    LocalStorageBackend → /upload   （未来加 OSSStorageBackend）
                                  |
                             KeyStrategy = PathMirror（现在）  （未来可换 Opaque）
```

- **`File Service`**：建/移/删/改名/软删/列举的**唯一实现**，REST 与 Agent 都调它 → 天然一致。
- **`FolderTree`**：文件夹树的 Web 后端领域层（`getFolder/getChildren/createFolder/moveFolder/deleteFolder/resolvePath`），当前实现 = SQLAlchemy。**保持为接口**（未来桌面端可另给实现，白捡；非当前目标）。
- **`StorageBackend`**：只管字节。现在只有 `LocalStorageBackend`（包 `upload/`）。**未来 OSS 是加一个实现,不动业务层。**
- **`KeyStrategy`**：现在 `PathMirrorStrategy`（`{uid}/项目文件/.../file`，存量数据不变、可挂盘浏览）。opaque 是未来接口后面的可换项，**现在不切**。

> **YAGNI**：现在只实现 `Local` + `PathMirror` 一条。OSS/Opaque 只留接口、不写实现，等真需要。

## 3. 文件夹生命周期一致性（当前主线）

**要求**：`Folder DB 状态` 与 `磁盘状态`始终一致。因为 Local 还要用几个月，这是**当前主要交付、不是过渡投入**：
- 建文件夹 → `mkdir` 真目录（修「空文件夹不上盘」）。（Local 空目录用真 `mkdir`，不用 `.keep`，避免污染用户可见文件。）
- 纯改名 → `rename_dir`（整目录 `mv`，原子、不留孤儿）。
- 移动 → 目录/文件同步，**逐级清空的旧祖先目录**。
- 删文件夹 → 物理搬子树进 trash 前缀（配合 §5 软删）。
- 修 `rename_file`/`delete`：清空后**逐级 rmdir** 旧祖先。
- **一次性清幽灵**：对账工具 diff DB 树 vs 磁盘，补缺失目录、报告孤儿（非空目录人工确认后清），治现存 `adr`/123。**用户手动触发 + 低频兜底，不做小时级常驻扫描。**

> 未来若切 opaque（文件夹变纯 DB 行、无物理目录），这套生命周期会大幅简化甚至消失——但那是未来；**现在就是要把 Local 修对**。

## 4. Agent / REST 一致（当前价值最高之一）

Agent 的 `_create_folder`/`_delete_folder`/移动等，**全走同一个 `File Service`**（现在各写一套：REST 走 `folders.py`，Agent 走 `tools/files.py`，语义容易漂）。一致靠共用实现 + 对称测试（沿用 projectStages / agent 工具模式，不合并成单一代码源）。

## 5. 软删：回收站 + Agent 执行安全

`deleted_at` 软删 + 整体恢复：
- **回收站**：文件夹可整体恢复（修 §1 第三个 bug）。
- **Agent 执行安全层**：咕咕删目录 = 可撤销 tombstone，是「安全操作真实世界」的信任底座（与 P2-b、confirm-gate 同一条可靠性主线，见 [[gugu-agent-reliability]]）。
> （将来还能当同步删除墓碑——白捡的未来价值，现在不为它设计。）

## 6. 现在埋的字段（低成本，不实现未来系统）

Alembic 加列、nullable、不回填即安全：
```
File:   version  updated_at  deleted_at   （未来加 storage_backend）
Folder: version  updated_at  deleted_at
```
- `version`/`updated_at`：当前用于乐观并发（延伸现有 409 并发锁）；未来同步冲突裁决白捡。
- `deleted_at`：软删（§5）。
> **只加字段，不建** SyncEngine / ConflictResolver / OperationLog。`storage_backend` 列等 OSS 到来再加。

## 7. 分阶段路线（Web 后端，按数据完整性优先）

**现在做**：
| 阶段 | 内容 | 驱动 |
|---|---|---|
| **P0** | `StorageBackend`/`KeyStrategy(PathMirror)`/`FolderTree` 接口 + `File Service` + `factory`（**零行为变化**，把入口收紧） | 可换后端地基 |
| **P1** | 文件夹**生命周期一致性**修复（mkdir / rename 清孤儿 / 一次性清幽灵） | **数据完整性（线上风险）** |
| **P2** | 文件夹**软删 + 回收站整体恢复** + 埋 `version/updated_at/deleted_at` | Agent 安全 + 数据可恢复 |
| **P3** | **Agent / REST 统一到 `File Service`** + 对称测试 | 咕咕一致 |

**OSS 到来时**（几个月后）：
| P4 | `OSSStorageBackend` + lazy 双后端（`storage_backend` 列、新传→OSS、旧文件留本地慢慢迁） |

**更以后**（现在不做、只留接口）：opaque key 决策；桌面端；双向同步 / op-log。

> 纪律：每阶段独立提交；先补对称/单元测试再改；生产相关先 dry-run + staging + 灰度。

## 8. 生产安全红线

1. **存量 `storage_key` 不动**（现在保留 path-mirror，不迁移；OSS 到来再逐个 lazy 迁）。
2. 新列走 Alembic nullable、不回填即安全。
3. 对账器只补目录 / 报告孤儿，非空目录先报告人工确认，绝不自动删。
4. 全程 `get_owned` 授权 + 删除 30 天可还原（P2④ 红线）。
5. Local 生命周期修复也先 staging 验证再上生产（涉及真实文件的 mkdir/rmdir/搬迁）。

## 9. 待拍板

- Local 生命周期修复的对账工具：一次性脚本 vs 加个后台管理入口——P1 起手时定。
- `FolderTree` / `File Service` 接口最终签名——P0 起手时定。
- （未来）opaque 是否切、OSS 厂商——OSS 临近再定，现在不锁。

## 附：与未来的关系（仅「不阻碍」约束，非本 ADR 目标）

- `StorageBackend` 接口 → 未来 OSS 是加实现、换 factory，业务层不动。
- `KeyStrategy` 接口 → 未来若切 opaque 是换策略，不重写业务。
- `FolderTree` 接口 → 未来桌面端可给 `LocalFolderTree`(SQLite) 实现；领域规则靠《行为规格》+ 对称测试一致（不追代码复用）。
- storage 模块把 Local 逻辑与（未来）OSS SDK 分目录，避免桌面端打包拖依赖。
> 这些是**结构上顺手留的口子**，本 ADR **不实现**任何 OSS / 桌面 / 同步逻辑。
