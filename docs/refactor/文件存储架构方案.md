# 文件夹 / 存储架构重构方案（设计版 · 2026-07-11）

> 状态：**设计稿，未动代码**。供评审。定稿后再拆可执行任务、分阶段实施。
> 背景：现有「文件夹 = 纯 DB 行 + 文件 key 内嵌路径」的模型导致 DB 与磁盘双向不同步；
> 未来后端换 OSS、且要做桌面客户端做本地文件管理。本方案统一这几件事。
> 关联：[[gugu-p2-refactor-plan]]、`app/services/storage/`、（已停的 WIP：`storage/folders.py`）。

## 1. 目标与约束

**三个「浏览面」**（同一份逻辑树，三处呈现）：
- **SMB / 服务端磁盘（now）**：当前用户直接挂盘翻目录，必须与网页一致。
- **App（网页）**：文件库视图，读 DB 树。
- **桌面客户端（future）**：本地目录做文件管理，双向同步。

**唯一真相源**：**DB 的 `folders` 表 = 文件夹树的权威来源**。物理存储是它的投影/镜像，不反过来。

**要同时解决的历史问题**（用户反馈）：
1. 删文件夹后回收站没有文件夹、无法整体恢复。
2. 网页建的（空）文件夹，服务端磁盘看不到。
3. 磁盘上有 DB 里没有的幽灵文件夹（如两个 `adr`），数据不同步。
4. 咕咕（Agent）的文件工具行为必须与 REST 一致。
5. 生产用户不受影响。

## 2. 现状诊断（根因）

`Folder` 是纯 DB 行（`id/user_id/project_id/parent_id/name`，**无 storage_key、无物理路径**，见 `app/models/__init__.py:156`）。物理存在只靠「文件 key 内嵌文件夹路径」。由此：

- **DB→磁盘缺失（问题 2）**：建空文件夹从不 `mkdir`，只有写文件时 `put` 隐式建目录（`storage/__init__.py:113`）。空文件夹永不上盘。
- **磁盘→DB 多余（问题 3，幽灵目录）**：`rename_file`（`:130`）只建新父目录 + `old.rename(new)`，**从不删空的旧目录**；`delete`（`:119`）只 `rmdir` 一层。移动/改名文件夹后旧目录名留盘成幽灵。（已停的 WIP `relocate_folder_tree_files` 逐文件 `rename_file`，正是幽灵制造机。）
- **回收站无文件夹（问题 1）**：`delete_folder`（`folders.py`）软删文件、**硬删文件夹行**（`db.delete`）。文件夹本身消失，只有文件逐个进回收站，无法整体恢复。

**结论**：不是单点 bug，是**「文件夹缺物理目录生命周期」的系统性缺陷**——建不物化、移不清旧、删不清目录、空文件夹无实体。

## 3. 领域模型与核心接口

**DB 树是真相源；物理布局是可插拔策略。** 关键事实：**每个文件的 `storage_key` 已存在 DB**，逻辑层只认 `folder_id` + `storage_key`，不关心 key 形态 → 物理策略天然可换。

```
StorageBackend（接口）：put/get/delete/rename_file/rename_dir/exists/list_prefix/presign/delete_prefix
KeyStrategy（协议）：
    build_key(file, folder_tree) -> key          # 物理 key 怎么生成
    move_semantics: 'relocate' | 'db-only'       # 文件夹移动=搬对象 还是 纯改 DB
    empty_folder: 'sentinel' | 'logical'         # 空文件夹=占位对象 还是 仅 DB 行
```

两个策略实现：
- **path-mirror（Local now）**：key = `{uid}/个人文件/.../file`；`empty_folder=sentinel`（`.keep` 或真 `mkdir`）；`move=relocate`。**可挂盘/客户端本地浏览**。
- **opaque（OSS future）**：key = `{uid}/blobs/{uuid}.{ext}`；`empty_folder=logical`；`move=db-only`（移动=1 次 DB 更新，**零搬运、无孤儿、OSS 友好**）。

> 为什么不 path-mirror 一统：OSS 无 `mv`，path-mirror 下移动文件夹 = 逐对象 copy+delete（2N 次请求，昂贵）。opaque 把逻辑路径留在 DB、物理 key 不含路径，移动 O(1)。

## 4. 模块切分与依赖方向（硬约束：local 可移植进桌面端）

```
app/services/storage/
  base.py              # StorageBackend 抽象 + KeyStrategy 协议
  factory.py           # get_storage()：按配置选后端 + 选策略

  local/               # ★本地策略 —— 桌面客户端可直接复用
    backend.py         # LocalStorageBackend（真实文件系统）
    tree.py            # ★可移植核心：文件夹树 ↔ 真实目录 物化/改名/移动/删除/对账/清孤儿
    keys_pathmirror.py # path-mirror key 策略

  oss/                 # OSS 策略 —— 纯服务端
    backend.py         # OSSStorageBackend（SDK / presign / 直传）
    keys_opaque.py     # opaque/uuid key 策略
    migrate.py         # Local→OSS 受控迁移作业

  bindings.py          # 服务端胶水：把 local/tree 的抽象 FolderTree 接到 DB（SQLAlchemy）
```

**可移植铁律**：`local/tree.py`、`keys_pathmirror.py` **绝不 import `app.*` / SQLAlchemy / FastAPI**。只依赖：
- 文件系统抽象（pathlib 或薄 FS 接口）；
- 抽象 `FolderTree` 接口（列文件夹、拿 parent/name/path）——谁提供树它不管。

于是同一份 `tree.py`：**服务端**用 `bindings.py` 提供的 DB 支持树；**桌面端**用本地 SQLite / API 同步数据提供的树。核心算法一处写、两处跑。

**依赖方向（定死）**：
- `oss/` 永不被 `local/*` import（桌面端打包不拖 OSS SDK）。
- `local/tree.py` 永不 import `app.*`（叶子，两边都依赖它、它不依赖任何一边）。
- `bindings.py` / `oss/` / `factory.py` / `oss/migrate.py` 均 server-only，可依赖 `app.models`。

**重构切口**：已停 WIP 的 `storage/folders.py`（`resolve_folder_path`/`relocate_folder_tree_files`）是 DB 耦合的——**纯目录算法**抽进 `local/tree.py`（可移植），**读 DB 拿树**留 `bindings.py`。

## 5. `local/tree.py` 目录生命周期 + 对账器（治 today）

**目录生命周期**（Local 策略下，DB 变更后同步物理）：
- 建文件夹 → 物化目录（`mkdir` / 写 `.keep`）。（治问题 2）
- 纯改名 → `rename_dir`（整目录 `mv`，原子、不留孤儿）。
- 结构性移动（跨空间/项目，key 结构变）→ 逐文件 relocate + **逐级清空的旧祖先目录**。
- 删文件夹 → 物理搬子树进 trash 前缀（配合 §6 软删）。
- 修 `rename_file`/`delete`：清空后**逐级 rmdir** 旧祖先（现在只清一层/不清）。

**对账器（folder doctor）**——治问题 3、补问题 2 的存量：
- diff「DB 树」vs「磁盘实际目录」，产出**差异报告**：缺失目录（DB 有盘无）、孤儿目录（盘有 DB 无，如 `adr`）。
- **只自动补建缺失目录**；**孤儿目录先报告、人工确认**再清（尤其非空的），绝不自动删有内容目录。
- 一次性迁移跑一遍 + 定期兜底。可移植 → 桌面端将来也用它对账本地镜像。

## 6. `oss/` opaque 策略 + 迁移作业

**opaque 策略**：key = `{uid}/blobs/{uuid}.{ext}`；文件夹移动/改名 = 纯 DB；空文件夹 = DB 行；无孤儿。

**Local(path-mirror) → OSS(opaque) 迁移作业**（「迁移 OSS」按钮挂在它上面，按钮只是触发 UI）。**六条红线**：
1. **幂等**：重复跑不重复迁、不损坏。
2. **可断点续**：中断后从进度点续，不从头。
3. **先 dry-run 出报告**：列将迁对象数/大小/新旧 key，人工确认再执行。
4. **逐对象校验**：迁后 checksum 比对，不一致停并报警。
5. **迁完验证通过前保留源**：不删 Local，直到 OSS 全量校验通过（可回滚）。
6. **处理迁移期新写入**：双写窗口或短冻结，避免漏迁/迁到一半的新文件。

## 7. 问题 1 / 4 / 5 收口

- **#1 文件夹进回收站可整体恢复**：`Folder` 加 `deleted_at`（Alembic nullable）；`delete_folder` 改**软删文件夹**（不再硬删）+ 递归软删文件；回收站列 `deleted_at` 非空的**顶层文件夹**为可恢复单元；恢复 = 子树 + 文件复原 + 物理搬回（Local 走 `tree.py`）；`cleanup_expired` 30 天后物理清子树。
- **#4 咕咕一致**：Agent 的 `_create_folder`/`_delete_folder`/移动全走同一套 `bindings` + `tree`/策略；对称测试保证与 REST 语义一致（不合并代码——沿用前端 projectStages 教训）。
- **#5 生产不受影响**：存量 `storage_key` 不主动重写（不动不破）；`deleted_at` 加列 nullable 不回填即安全；对账器只补目录 / 报告孤儿；迁移作业守六红线；全程 `get_owned` 授权 + 30 天可还原（P2④ 红线）；先 staging 全量 dry-run → 灰度内部账号 → 放量。

## 8. 分阶段路线

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P0 止血 + 地基** | 修 Local 目录生命周期（建/删/移清孤儿）；把 key 生成 + 移动逻辑抽到 `base.py` 策略接口（零行为变化） | today 的 Local 自洽；策略缝就位 |
| **P1 对账器** | `local/tree.py` 对账，出差异报告，补 123、清 adr（人工确认） | 双向同步修复 |
| **P2 文件夹回收站** | `Folder.deleted_at` + 软删 + 整体恢复（#1） | 文件夹可恢复 |
| **P3 咕咕一致** | Agent 工具全走共享 service + 对称测试（#4） | 两侧语义一致 |
| **P4 OSS 策略 + 迁移** | `oss/` opaque + 迁移作业（六红线）+ 按钮 | 可切 OSS |
| **P5 桌面端复用** | 拎走 `storage/local/` + 客户端自实现 FolderTree/FS + API 同步 | 本地客户端地基 |
| **P6 收敛** | 客户端成浏览面后，Local 也可切 opaque，path-mirror 退役 | 单模型终态 |

**纪律**：每阶段独立提交；先补对称/单元测试再改；生产相关先 dry-run + staging + 灰度；`local/tree` 保持零 `app.*` 依赖（每次 CI 校验 import 边界）。
