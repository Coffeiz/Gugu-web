# ADR：文件存储抽象与生命周期一致性（Web 后端 · 2026-07-11）

> **状态**：设计稿，未动代码。供评审，定稿后拆任务实施。
> **一句话工单**：把 Web 文件系统从「**路径驱动**」升级成「**领域模型驱动**」——文件身份是
> `file_id` + `folder_id`，`storage_key` 降为不透明实现细节。
> **背景**：生产环境马上从本地存储切 OSS；同时修当前文件夹与磁盘的不同步；并为未来桌面端**留接口不留实现**。
> 关联：[[gugu-p2-refactor-plan]]、[[gugu-agent-reliability]]、`app/services/storage/`。

## 0. 范围（写死，防越界）

**In scope（现在做）**：
- Local → OSS 存储迁移；`StorageBackend` 抽象；`KeyStrategy`（opaque）。
- 文件夹**生命周期一致性**（DB 状态 ↔ 存储状态）。
- **Agent / REST 共用同一套文件语义**（咕咕工具与网页行为一致）。
- 软删（回收站 + Agent 安全）；为未来**低成本预留字段**。

**Future（非目标，现在只保证「不阻碍」，绝不实现）**：
- 桌面端 / local-first；双向同步引擎；冲突解决；operation log / event history。
> 原则：**别为未来桌面端把后端写成一个同步系统；但今天的后端不能挡住未来桌面端。**

## 1. 现状诊断（root cause）

`Folder` 是纯 DB 行（无 storage_key/物理路径，`app/models/__init__.py:156`）；物理存在只靠文件 key 内嵌文件夹路径 = **路径驱动**。由此三个 bug：
- **空文件夹不上盘**：建文件夹从不 `mkdir`，只在写文件时隐式建目录（`storage/__init__.py:113`）。
- **rename 留幽灵目录**：`rename_file`（`:130`）建新父但**不删空旧目录**；`delete`（`:119`）只清一层 → 移动/改名后旧目录残留（如两个 `adr`）。
- **删文件夹无法恢复**：`delete_folder` 硬删文件夹行（`db.delete`），只有文件逐个进回收站。

**根因**：文件夹缺物理生命周期 + 身份焊在路径上。**领域模型驱动**（file_id/folder_id 是身份、storage_key 不含路径）从根上消除这类问题。

## 2. 目标抽象

```
                REST API        Agent 工具
                    \             /
                     File Service          ← 唯一文件语义入口（REST 与 Agent 共用）
                    /            \
             FolderTree      StorageBackend
             (领域层)          (字节层)
                 |                |
             SQLAlchemy       Local / OSS
```

- **File Service**：建/移/删/改名/软删/列举的**唯一实现**，REST 与 Agent 都调它 → 天然一致（#Agent 一致）。
- **FolderTree**：文件夹树的**Web 后端领域层**（`getFolder/getChildren/createFolder/moveFolder/deleteFolder/resolvePath`），当前实现 = SQLAlchemy。**保持为接口**，未来桌面端可另给实现（复用思想，不一定复用代码）——这是「留接口不留实现」。
- **StorageBackend**：只管字节（put/get/delete/rename/list/presign），Local / OSS 两实现。**与 FolderTree 正交**。
- **KeyStrategy**：见 §3。

## 3. KeyStrategy：opaque（file_id ≠ storage path）

**当前只需一条**：**别让 `folder/name` 决定 storage key**。

```
DB:  file_id=abc123  name=design.png  folder_id=456  storage_key=users/1/blobs/abc123.png
```

- key 从 file_id/uuid 派生（**opaque**），不含路径。
- **文件夹移动/改名 = 改 `folder_id`/`name`，storage_key 不动**（O(1)，无物理搬运，无孤儿）。
- **path-mirror 淘汰**（它把会变的路径焊进不该变的身份；OSS 上移动还要逐对象 copy+delete，昂贵）。

> opaque 的当前价值：① OSS 移动零成本；② 文件身份稳定（改名/移动不动 key）。
> 「支持未来同步」是白捡的第三点，**不是当前需求**——现在不为它做任何额外设计。

## 4. 文件夹生命周期一致性

**要求**：`Folder DB 状态` 与 `存储状态` 始终一致。实现随后端不同：
- **opaque（OSS，目标态）**：文件夹是纯 DB 行、无物理目录 → 一致性**天然成立**（建=写行、移=改行、删=软删行、空文件夹=DB 行）。这也是为什么 opaque 迁移**直接消除** §1 的整类 bug。
- **Local 过渡期**：切 OSS 前仍是路径驱动，需最小修复保证盘面自洽：建文件夹 `mkdir`、`rename_file`/`delete` 清空的旧祖先目录、一次性清现存幽灵（`adr`）。**这块是过渡投入，opaque 落地后退役——不为它建常驻基建**（对账当一次性工具，非小时级扫描）。

## 5. Agent / REST 一致（#4）

Agent 的 `_create_folder`/`_delete_folder`/移动等，**全走同一个 File Service**（现在各写一套：REST 走 folders.py，Agent 走 tools/files.py）。语义一致靠共用实现 + 对称测试保证（沿用 projectStages / agent 工具的既有模式）。

## 6. 软删（当前价值：回收站 + Agent 安全）

`deleted_at` 软删 + 整体恢复：
- **回收站**：文件夹可整体恢复（修 §1 的第三个 bug）。
- **Agent 执行安全层**：咕咕删目录 = 可撤销 tombstone，是「安全操作真实世界」的信任底座（与 P2-b、confirm-gate 同一条可靠性主线）。
- OSS 下天然适合：trash prefix + 30 天 lifecycle。
> （它将来还能当同步删除墓碑——白捡的未来价值，现在不为它设计。）

## 7. 现在埋的字段（低成本前向兼容，不实现未来系统）

Alembic 加列、nullable、不回填即安全：
```
File:   storage_backend(local|oss)  version  updated_at  deleted_at
Folder: deleted_at  version
```
- `storage_backend`：支撑 §8 lazy 迁移。
- `version`/`updated_at`：当前用于乐观并发（已有 409 并发锁的延伸）；未来同步冲突裁决白捡。
- `deleted_at`：软删（§6）。
> **只加字段，不建** SyncEngine / ConflictResolver / OperationLog / WorkspaceEvent —— 那些是桌面/同步阶段。

## 8. Local → OSS：lazy 双后端迁移

不搞一次性大作业 + 冻结：
- `LocalStorageBackend` 与 `OSSStorageBackend` 并存，每文件 `storage_backend` 标记所在。
- **新上传直接 OSS opaque**；**老文件读时顺带迁 + 后台低频冷扫**，逐个搬完、可随时中断、无冻结窗口。
- per-file 不变式：幂等、迁后 checksum 校验、**迁完校验通过前不删源**（可回滚）。
- 路由：`if storage_backend==local: 读 Local（顺带迁 OSS、改 storage_key/backend）else: 读 OSS`。

## 9. 分阶段路线（Web 后端）

| 阶段 | 内容 |
|---|---|
| **P0** | `StorageBackend`/`KeyStrategy`/`FolderTree` 抽象 + `File Service` + `factory`（迁移入口，零行为变化） |
| **P1** | OSS `opaque` backend + **lazy 双后端迁移**（`storage_backend` 列、新传直 OSS、读时迁+冷扫） |
| **P2** | 文件夹**软删 + 回收站整体恢复** + 埋 `version/updated_at/deleted_at`（#6/#7） |
| **P3** | **Agent / REST 统一到 File Service** + 对称测试（#5） |
| **P4** | 一次性清幽灵 + Local 过渡期最小稳定（对账当工具，非常驻） |

> 纪律：每阶段独立提交；先补对称/单元测试再改；生产相关先 dry-run + staging + 灰度。

## 10. 生产安全红线

1. 存量 `storage_key` 不主动重写（lazy 逐个迁、迁完校验前不删源、可回滚）。
2. 新列走 Alembic nullable、不回填即安全。
3. 对账器只补目录 / 报告孤儿，非空目录先报告人工确认，绝不自动删。
4. 全程 `get_owned` 授权 + 删除 30 天可还原（P2④ 红线）。
5. 先 staging 全量 dry-run → 灰度内部账号 → 放量。

## 11. 待拍板

- 生产 OSS 厂商（阿里云 OSS？）→ 定 `oss/backend.py` SDK/presign。
- Local 过渡期空文件夹：真 `mkdir`（推荐，无污染）vs `.keep`（**已否**）。
- `FolderTree` / `File Service` 的接口边界最终签名（P0 起手时定）。

## 附：与未来桌面端的关系（仅「不阻碍」约束，非本 ADR 目标）

- `FolderTree` 保持为接口 → 未来桌面端可给 `LocalFolderTree`(SQLite) 实现。
- storage 模块把 Local 逻辑与 OSS SDK 分目录放，避免未来桌面端打包拖 OSS 依赖。
- 领域规则未来靠**语言无关《行为规格》+ 各端对称测试**一致（不追代码复用）。
> 这些是**结构上顺手留的口子**，本 ADR **不实现**任何桌面/同步逻辑。
