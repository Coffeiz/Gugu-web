# 文件浏览系统模块化重构方案

## 1. 背景与目标

`frontend/src/views/Projects/components/ProjectModal.vue` 当前约 2900 行，`frontend/src/views/Files/index.vue` 当前约 2660 行。前者同时承担项目基础信息、阶段、待办和项目文件管理，后者同时承担文件库导航、普通文件操作、回收站和存储统计。

两个页面已经共享部分 Store、API 和 composable，但仍分别维护大量文件网格、列表、选择、排序、上传、拖拽和右键菜单模板与交互编排。因此本次重构范围不再只是 ProjectModal，而是建立两边共同使用的文件浏览层。

本次重构目标：

- 降低 `ProjectModal.vue` 和 `Files/index.vue` 的职责和代码量。
- 让项目文件区与文件库共享文件浏览、选择、排序、上传和操作逻辑。
- 保留项目文件区与文件库之间的产品差异，不强行复用回收站和全局导航。
- 保证重构期间行为可逐阶段验证，避免一次性替换导致文件操作回归。

### 2.1 后端配合整理

前端通用文件浏览层需要后端提供稳定、按能力边界组织的文件 API。后端配合遵循三条原则：

- API 路由只负责认证、参数解析、HTTP 异常映射、事务提交和事件触发。
- 文件和文件夹写操作继续统一经过现有 `FileService`，不在路由中重复实现文件语义。
- 目录查询、上传、预览、批量操作和回收站分别下沉到对应 service，项目文件区只通过 `projectId` 配置范围，不依赖前端限制权限。

后端目标能力对应关系：

```text
前端 FileBrowserPanel
├── 目录查询       -> FileBrowserService
├── 文件操作       -> FileService / FileActions
├── 上传           -> FileUploadService
├── 预览           -> FilePreviewService
└── 回收站扩展     -> TrashService
```

详细的后端目录、执行顺序和约束见本文“后端实施细节”章节。

## 3. 职责边界

### 3.1 ProjectModal

只负责弹窗生命周期、整体布局和模块协调：

- 打开、关闭和当前项目切换。
- 传递 `projectId` 和项目配置。
- 接收项目删除、保存和关闭事件。
- 不再直接实现文件卡片、文件夹导航和文件操作。

### 3.2 ProjectFilesPanel

负责项目文件场景的配置：

- 固定当前 `projectId`。
- 默认打开项目根目录。
- 禁止回收站入口。
- 限制文件移动在当前项目范围内。
- 复用通用文件浏览组件和 composable。

### 3.3 FileBrowserPanel

负责通用文件浏览布局：

- 工具栏。
- 面包屑。
- 排序、视图切换、新建文件夹和粘贴入口。
- 网格/列表视图。
- 文件和文件夹渲染。
- 批量选择栏。
- 右键菜单。

页面差异通过配置或扩展插槽传入，不通过大量 `if (isProject)` 分支实现。

### 3.4 右键菜单复用

文件库和项目文件区的右键菜单统一使用 `FileBrowserContextMenu.vue` 和 `useFileContextMenu.ts`，不再分别维护菜单模板。

通用菜单根据当前目标类型和页面能力配置显示菜单项：

- 文件目标：信息、下载、重命名、复制、剪切、删除。
- 文件夹目标：下载 ZIP、重命名、复制、剪切、删除。
- 空白区域：粘贴、新建文件夹等当前页面允许的操作。

项目文件区通过能力配置隐藏跨项目、回收站和永久删除等不适用动作；文件库通过配置增加回收站相关动作。菜单的展示结构、定位、关闭和键盘行为由组件统一负责，具体动作由 `useFileContextMenu.ts` 调用 `useFileActions.ts`。

这里的差异通过能力配置表达，不为文件库和项目文件区各写一份菜单模板。

### 3.5 复用边界

通用文件浏览层只复用两边都需要的文件能力：

- 文件和文件夹卡片。
- 网格/列表视图。
- 排序。
- 单选、多选、Shift 选择和框选。
- 文件夹进入、面包屑和目录移动。
- 文件/文件夹重命名、下载、删除。
- 文件上传、冲突处理和上传进度。
- 右键菜单和批量操作栏。

以下能力不强行放进通用 `FileBrowserPanel`，由文件库页面单独扩展：

- 回收站入口。
- 回收站文件和文件夹恢复。
- 文件和文件夹永久删除。
- 个人文件、项目列表、年份/月度等全局导航。
- 跨项目空间切换。
- 存储空间统计和文件库专属筛选。

项目文件区同样有自己的边界：

- 固定在当前 `projectId` 下，不提供个人文件和其他项目的全局导航。
- 第一阶段不显示回收站，不提供恢复和永久删除入口。
- 文件和文件夹移动只能发生在当前项目范围内。
- 项目颜色、项目权限和项目弹窗布局由 `ProjectFilesPanel` 负责，不下沉到通用文件浏览组件。

这样做不是减少复用，而是避免通用组件变成包含大量场景分支的“全能文件页面”。通用层提供稳定的文件操作能力，回收站、全局导航和存储统计作为页面级扩展存在。

### 3.6 通用 composable

`useFileSelection` 处理选择状态，`useFolderNavigation` 处理目录路径，`useFileActions` 处理 API 操作，`useFileUploadController` 处理上传流程。composable 不直接依赖具体页面 DOM，页面只提供当前空间、目标目录和刷新/投影回调。

## 4. 统一数据模型

网格和列表使用同一份展示模型，避免两套模板分别判断文件和文件夹状态：

```ts
type BrowserItem =
  | {
      type: 'folder'
      id: number | string
      folderId: number
      name: string
      count?: number
    }
  | {
      type: 'file'
      id: number
      name: string
      ext: string
      folderId: number | null
    }
```

数据层保留后端原始模型，`BrowserItem` 只作为浏览器 UI 的投影模型。排序、选择、右键菜单和拖拽均基于该模型工作。

## 5. 执行计划

> **实施路线修订（2026-07-15）**
>
> 目标架构保持不变，但不按“完整 FileBrowserPanel 一次性落地”的方式执行。文件浏览系统的风险主要在拖拽、缓存同步、文件归属和回收站语义，而不是类型检查能否通过。因此采用渐进式迁移，每一阶段都保持可运行、可验证、可回滚。
>
> 重构分为四条风险递增的主线：
>
> 1. **展示层**：Grid/List 和面包屑展示。
> 2. **状态层**：选择、排序、目录导航和数据投影。
> 3. **操作层**：上传、移动、复制、删除和批量操作。
> 4. **边界层**：右键菜单、后端 service、权限和回收站扩展。
>
> 第一阶段不得顺手改变拖拽行为、缓存策略、API、数据模型或卡片 DOM 层级。尤其要保留现有拖拽克隆、落地动画、连接点、缩略图和卡片外壳结构；这些属于已经反复修复过的高风险交互。

## 6. 后端实施细节

### 6.1 当前后端职责

当前 `backend/app/api/v1/files.py` 约 1069 行，除了路由协调，还包含目录查询、冲突检测、上传确认、文件操作、缩略图生成、PDF 转换和流式预览。`folders.py` 负责文件夹路由，`trash.py` 负责回收站业务；现有 `FileService` 已经是文件和文件夹写操作的统一语义入口。

后端重构不与前端组件一一对应，而是遵循“路由变薄、写操作统一、查询和媒体能力分离”的边界。

### 6.2 目标后端结构

```text
backend/app/api/v1/
├── files.py              # 路由协调
├── folders.py            # 文件夹路由协调
└── trash.py              # 回收站路由协调

backend/app/services/files/
├── browser.py            # 当前目录、项目根目录、文件夹内容查询
├── actions.py            # 重命名、移动、复制、删除、下载
├── selection.py          # 批量下载、批量删除
├── upload.py             # 预签名、确认、冲突和上传编排
├── previews.py           # 缩略图、PDF 和流式预览
├── trash.py              # 回收站业务编排
└── response.py           # FileResponse、FolderResponse 组装

backend/app/services/storage/
├── file_service/         # 文件和文件夹写操作门面及底层实现
├── folder_tree.py        # 文件夹树和归属解析
└── trash.py              # 存储层回收站移动、恢复和清理
```

### 6.3 前后端对应关系

```text
前端 FileBrowserPanel
├── 目录查询       -> FileBrowserService
├── 文件操作       -> FileService / FileActions
├── 上传           -> FileUploadService
├── 预览           -> FilePreviewService
└── 回收站扩展     -> TrashService
```

前端的项目文件区通过 `projectId` 使用同一套 API，但项目范围、父子目录、跨项目移动和归属校验必须由后端最终确认，不能只依赖前端能力配置。

## 7. 风险与控制

### 文件范围风险

项目文件区只能访问当前项目范围，不能因为复用文件库逻辑而出现跨项目移动或读取。所有移动操作必须继续传递正确的 `projectId` 和 `folderId`。

### 缓存一致性风险

文件操作仍使用现有 `filesCacheStore` 的乐观更新和回滚约定。抽 composable 时不得在组件层再维护一套项目文件缓存。

### 回收站差异

项目文件区第一阶段不实现回收站恢复和永久删除。文件库的回收站逻辑通过扩展能力保留，不能塞进通用文件操作的默认路径。

### 拖拽风险

文件拖拽同时涉及指针事件、落点判定、层级和缓存更新。展示组件迁移后必须优先验证拖拽克隆、文件夹落点和项目抽屉交互。

### 迁移策略

每个阶段保持页面可运行，先让新组件与旧逻辑并行对照，再删除旧实现。不要在同一个提交中同时改变 API、Store 数据模型和 UI 组件边界。
