# 日历模块化重构方案

## 1. 背景与目标

当前 `frontend/src/views/Calendar/index.vue` 约 2540 行（模板约 430 行、script 约 1670 行、style 约 440 行），同时承担月视图网格、周视图时间轴、拖拽/缩放指针状态机、布局分行算法、颜色/展示工具、事件 CRUD、本地添加/编辑事件弹窗和三处独立的右键菜单。

它已经不是一个普通页面组件，而是一个自成一体的日历子系统，只是还没有被识别成模块。继续在一个文件里维护会让"周视图改坏了会不会牵连月视图""这条颜色规则改了会不会漏改另一处判断"这类问题越来越难回答。

目标：

- 建立 `CalendarItem` 作为日历世界里事件和项目时间线的统一数据形状，业务规则（能否拖拽/缩放、展示色）集中到 `domain/`，不再让组件里出现 `if (type === 'project')` 式的散落判断。
- 把布局算法（月/周分行）拆成纯函数，输入输出明确、可直接单测。
- 把月视图、周视图、拖拽/缩放指针状态机拆成独立模块，`index.vue` 收缩为数据获取 + composable 组合 + 组件组装的协调层。
- 三处独立右键菜单（月格/周列/全天行）合并成一个通用 `ContextMenu.vue`，按 `CalendarContext`（类型 + 目标对象）出菜单项。
- 本地手写的添加/编辑事件弹窗，统一到 `DefaultLayout.vue` 已经在用的全局 `EventEditModal.vue` + `stores/eventModal.ts`，消掉两套并行实现。
- 保持现有拖拽手感、吸附、resize 判定和月/周视图行为不变；拖拽状态机第一阶段只做原样搬家，不顺手优化。
- 分阶段迁移，任何阶段都能独立验证和回滚。

## 2. 当前结构与问题

```text
frontend/src/views/Calendar/
├── index.vue                   # 约 2540 行：数据、状态、布局算法、拖拽状态机、CRUD、
│                                #   弹窗、三处右键菜单全部混在一起
└── components/
    ├── EventEditFields.vue      # 约 89 行：事件表单字段（已抽出）
    └── EventEditModal.vue       # 约 108 行：全局事件弹窗外壳（已抽出，但只有
                                 #   DefaultLayout.vue 在用，Calendar/index.vue 自己
                                 #   另外手写了一套 showEditForm/editingEvent）
```

当前最主要的问题不是行数，而是三类东西没有明确边界：

- **数据形状没有统一**：`CalItem` 接口本身承认"同一数组里既有 `isProject` 也有 `isUserEvent` 的对象"，靠调用方各自判断字段是否存在，规则（能不能拖、显示什么颜色）散落在月视图、周视图、拖拽状态机三处各自的 `if` 分支里。
- **布局算法和组件状态耦合**：`weekBars`/`dayLayout`/`timedLayoutFor` 这类分行算法读写的是组件内的 `ref`/`reactive`，理论上是纯函数却没有纯函数的可测性。
- **拖拽状态机横跨月/周两个视图**：`startDrag`/`_evDragMove`/`onEvResize`/`_wvDrag` 等十几个函数共用同一套指针状态，是全文件里改动风险最高、最容易顺手改坏手感的部分。

│   ├── EventEditModal.vue      # 已有；阶段 3 起 Calendar/index.vue 也复用它

│   │                            #   接收 CalendarContext（type + target）
│   ├── MonthGrid.vue           # 新增（阶段 5）：月视图网格 + chip 渲染 + 拖框选

```text
frontend/src/utils/
├── calendarColors.ts    # extractAccent/capBg/hexAlpha/darkenHex（纯色值计算，不含规则判断）
└── calendarLayout.ts    # weekBars/weekBarsCached/weekBarsCapped/dayLayout/timedLayoutFor/maxSlots
                          #   纯函数：input CalendarItem[] → output 带位置信息的条目

frontend/src/composables/
├── useHolidays.ts           # 已有，不动
├── useEventEditForm.ts      # 已有，不动；阶段 3 起被 Calendar/index.vue 更彻底地复用
├── useCalendarNav.ts        # 新增：prev/next/goToday/setView/selectYearMonth/togglePicker，
│                             #   视图/月年/activeRange/todayIso 等导航态
├── useCalendarUpcoming.ts   # 新增：buildUpcomingList，读 domain/calendarNormalizer
└── useCalendarDrag.ts       # 新增（阶段 5，最后做）：startDrag/startEventDrag/startBarDrag/
                              #   startBarResize/_evDragMove/_evDragUp/onEvResize/_wvDrag/_wvUp
                              #   等——月/周视图共用的指针状态机，第一遍只搬家不重构
```

依赖方向单向收口，不允许反向 import：

```text
components → composables → domain/utils
```

`domain/`、`utils/` 不 import 组件或 composable；`composables/` 不 import 组件。

## 4. 统一数据模型

```ts
interface CalendarItem {
  id: string | number
  type: 'event' | 'project'
  title: string
  start: string
  end?: string
  color: string
  draggable: boolean
  resizable: boolean
  // 其余字段（description/status/currentStage/progress 等）按 type 收在各自的可选块里，
  // 不强行拍平成一个大而全的联合形状
}
```

`domain/calendarNormalizer.ts` 负责把后端 `EventResponse` 和项目时间线数据都转成 `CalendarItem`；`domain/calendarRules.ts` 提供 `canDrag(item)`/`canResize(item)`/`getDisplayColor(item)` 等函数，月视图、周视图、拖拽状态机、右键菜单统一调用这几个函数判断，不在各自内部重复写 `item.type === 'project'`。

`utils/calendarLayout.ts` 的分行算法只认 `CalendarItem[]`，不认组件的 `ref`/`reactive`，也不感知 Vue：

```text
input:  CalendarItem[]
output: 带 colStart/colEnd/row 等位置信息的条目
```

## 6. 风险与控制

### 数据模型风险

- `CalendarItem` 归一化必须覆盖现有 `CalItem` 承载的所有字段场景（月视图 chip、周视图条目、侧栏、"更多"弹窗、拖拽 item），归一化时确认没有静默丢字段。
- 规则收口到 `domain/calendarRules.ts` 后，必须删除组件和 composable 里原有的重复判断，不能两处并存导致以后改一处漏一处。

### 拖拽风险

- 月视图和周视图共用同一套指针状态机，阶段 5 搬家时不得拆散状态归属，也不得为了"看起来更干净"合并/拆分状态字段。
- resize 边缘判定（`_evEdge`）、拖拽阈值、吸附（`_snapMin`）都是隐含产品需求，迁移前后必须逐条对照。

### 依赖方向风险

- `domain/`、`utils/` 不得 import 组件或 composable；一旦出现反向依赖，视为架构违规，需要在评审时拦下。

### 弹窗统一风险

- 全局 `EventEditModal.vue` 目前只服务 `DefaultLayout.vue` 的场景，接入日历页前需要确认参数/事件契约是否够用，不够则先扩展全局组件，不在日历页另建分支绕过去。
