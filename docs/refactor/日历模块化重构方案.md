# 日历模块化重构方案

## 1. 背景与目标

重构前 `frontend/src/views/Calendar/index.vue` 约 2540 行；当前已收缩到 1575 行，月视图网格与周视图时间轴分别归位到 `MonthGrid.vue`、`WeekTimeline.vue`，页面仍承担事件 CRUD、新建表单和部分周视图交互编排。

它已经不是一个普通页面组件，而是一个自成一体的日历子系统，只是还没有被识别成模块。继续在一个文件里维护会让"周视图改坏了会不会牵连月视图""这条颜色规则改了会不会漏改另一处判断"这类问题越来越难回答。

目标：

- 建立 `CalendarItem` 作为日历世界里事件和项目时间线的统一数据形状，业务规则（能否拖拽/缩放、展示色）集中到 `domain/`，不再让组件里出现 `if (type === 'project')` 式的散落判断。
- 把布局算法（月/周分行）拆成纯函数，输入输出明确、可直接单测。
- 把月视图、周视图、拖拽/缩放指针状态机拆成独立模块，`index.vue` 收缩为数据获取 + composable 组合 + 组件组装的协调层。
- 三处独立右键菜单（月格/周列/全天行）合并成一个通用 `CalendarContextMenu.vue`，按 `CalendarContext`（类型 + 目标对象）出菜单项。
- 本地手写的添加/编辑事件弹窗，统一到跨页面共享的 `EventEditModal.vue` + `stores/eventModal.ts`，消掉两套并行实现，并修正组件归属。
- 保持现有拖拽手感、吸附、resize 判定和月/周视图行为不变；拖拽状态机第一阶段只做原样搬家，不顺手优化。
- 分阶段迁移，任何阶段都能独立验证和回滚。

## 2. 当前结构与问题

```text
frontend/src/views/Calendar/
├── index.vue                   # 1575 行：页面状态、拖拽提交、CRUD、
│                                #   新建表单和页面级交互编排
└── components/
    ├── CalendarToolbar.vue      # 日历导航与视图切换
    ├── CalendarSidebar.vue      # 侧栏事件与近期节点
    ├── CalendarMorePopup.vue    # 更多事件弹层
    ├── CalendarContextMenu.vue  # 统一右键菜单
    ├── MonthGrid.vue            # 月视图
    └── WeekTimeline.vue         # 周视图

frontend/src/components/events/
├── EventEditFields.vue          # 共享事件字段
└── EventEditModal.vue            # 全局事件编辑弹窗
```

当前最主要的问题不是行数，而是三类东西没有明确边界：

- **数据形状没有统一**：`CalItem` 接口本身承认"同一数组里既有 `isProject` 也有 `isUserEvent` 的对象"，靠调用方各自判断字段是否存在，规则（能不能拖、显示什么颜色）散落在月视图、周视图、拖拽状态机三处各自的 `if` 分支里。
- **布局算法和组件状态耦合**：`weekBars`/`dayLayout`/`timedLayoutFor` 这类分行算法读写的是组件内的 `ref`/`reactive`，理论上是纯函数却没有纯函数的可测性。
- **拖拽状态机横跨月/周两个视图**：`startDrag`/`_evDragMove`/`onEvResize`/`_wvDrag` 等十几个函数共用同一套指针状态，是全文件里改动风险最高、最容易顺手改坏手感的部分。


依赖方向单向收口，不允许反向 import：

```text
components → composables → domain/utils
```

`domain/`、`utils/` 不 import 组件或 composable；`composables/` 不 import 组件。

组件之间默认使用 `props`/`emits` 传递数据和动作。只有跨层级、稳定且明确属于 Calendar subsystem 的能力才允许通过 `provide/inject` 传递；不得建立包含 items、导航、拖拽、弹窗和侧栏等全部状态的“大 CalendarContext” service locator。

Calendar 专用的 domain、utils、composables 默认留在 `views/Calendar/` 内；只有出现第二个稳定消费者后，才提升到全局 `src/utils/` 或 `src/composables/`。已有的 `useHolidays`、`useEventEditForm` 是否继续留在全局，按现有真实消费者决定。

`EventEditFields.vue` 和 `EventEditModal.vue` 已归入 `src/components/events/`：由于 `DefaultLayout.vue` 和 Calendar 都会使用它们，避免形成 `layout → views/Calendar` 的反向依赖。后续只统一弹窗状态与调用协议，不重复实现字段逻辑。

## 4. 统一数据模型

`CalendarItem` 不直接做成一个所有字段都可选的扁平大对象，而是使用 `type` 判别的联合，保留事件和项目时间线各自的字段边界：

```ts
interface CalendarItemBase {
  id: string | number
  title: string
  allDay: boolean
  color?: string
}

interface EventCalendarItem extends CalendarItemBase {
  type: 'event'
  date: string
  startTime?: string
  endTime?: string
  description?: string
}

interface ProjectCalendarItem extends CalendarItemBase {
  type: 'project'
  startDate?: string | null
  endDate?: string | null
  status: string
  currentStage?: string
  progress?: number
}

type CalendarItem = EventCalendarItem | ProjectCalendarItem
```

`color` 如果是用户保存的事件配置，可以作为原始配置字段保留；它不表示最终渲染色。`canDrag(item)`、`canResize(item)`、`getDisplayColor(item)` 是规则的唯一真相，不能再同时保留 `item.draggable`、`item.resizable` 作为并行判断来源。

`calendarNormalizer.ts` 不使用一个同时处理所有来源的 `normalizeEvent`：应拆成 `normalizeEvent(event): EventCalendarItem` 和 `normalizeProjectTimeline(project): ProjectCalendarItem`。如果调用方需要统一入口，再由 `normalizeCalendarItems()` 组合两者。

具体字段以现有 `CalItem`、后端响应和模板实际访问为准，不要求一次性补齐所有业务字段。新增字段应放入对应的判别分支，避免重新形成“大而全”的可选属性集合。

`domain/calendarNormalizer.ts` 分别把后端 `EventResponse` 和项目时间线数据转成对应的 `EventCalendarItem` / `ProjectCalendarItem`；`domain/calendarRules.ts` 提供 `canDrag(item)`/`canResize(item)`/`getDisplayColor(item)` 等函数，月视图、周视图、拖拽状态机、右键菜单统一调用这几个函数判断，不在各自内部重复写 `item.type === 'project'`。

`utils/calendarLayout.ts` 的分行算法只认 `CalendarItem[]`，不认组件的 `ref`/`reactive`，也不感知 Vue：

```text
input:  CalendarItem[]
output: 带 colStart/colEnd/row 等位置信息的条目
```

## 6. 风险与控制

### 数据模型风险

- `CalendarItem` 采用 `event`/`project` 判别联合；归一化必须覆盖现有 `CalItem` 承载的所有字段场景（月视图 chip、周视图条目、侧栏、"更多"弹窗、拖拽 item），确认没有静默丢字段。
- 不允许通过大量可选字段重新制造一个扁平大对象；新增业务字段应归入对应的 `type` 分支。
- 规则收口到 `domain/calendarRules.ts` 后，必须删除组件和 composable 里原有的重复判断，不能两处并存导致以后改一处漏一处。

### 布局算法风险

- `calendarLayout.ts` 必须保持纯函数，不得读取 Vue 的 `ref`/`reactive` 或组件 DOM。
- 阶段 1 的目标是等价迁移，不是重新设计布局；跨天、重叠、全天和最大行数规则必须由回归测试固定。
- 回归测试应覆盖月视图和周视图共同使用的边界，避免只验证其中一个视图导致另一侧行为漂移。

### 拖拽风险

- 月视图和周视图共用同一套指针状态机，阶段 5 搬家时不得拆散状态归属，也不得为了"看起来更干净"合并/拆分状态字段。
- resize 边缘判定（`_evEdge`）、拖拽阈值、吸附（`_snapMin`）都是隐含产品需求，迁移前后必须逐条对照。

### 依赖方向风险

- `domain/`、`utils/` 不得 import 组件或 composable；一旦出现反向依赖，视为架构违规，需要在评审时拦下。

### DOM/CSS 拓扑风险

- 阶段 5 的第一轮组件抽取不得改变原有 DOM 拓扑；不得为了组件语义增加无必要 wrapper。
- 原有 class、节点层级、`position` containing block、scroll container、`overflow` clipping、stacking context、`z-index` 和 pointer hit-test 必须保持一致。
- `getBoundingClientRect()`、pointer capture、`querySelector` 范围和弹层定位参照物都要在迁移前后逐项对照。
- 父组件的 scoped CSS 不会自动作用于新组件内部 DOM；相关样式随组件一起迁移，第一轮不顺手整理 CSS。
- 5A 只搬状态机，5B/5C 才搬 DOM；每次只改变一个边界，出现拖拽或定位回归时可以明确归因。

### 弹窗统一风险

- 共享 `EventEditModal.vue` 接入日历页前需要确认参数/事件契约是否够用，不够则先扩展共享弹窗，不在日历页另建分支绕过去。
