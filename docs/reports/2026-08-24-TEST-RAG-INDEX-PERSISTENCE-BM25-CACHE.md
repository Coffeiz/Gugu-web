# RAG 索引持久化与 BM25 缓存测试报告

> 日期：2026-08-24
> 环境：devserver
> 数据：单个测试账号的聚合索引数据；本文不记录账号标识、正文、文件名或查询原文。

## 1. 测试目的

验证统一知识索引的以下链路：

- 数据库 chunk 是否已经持久化；
- ILIKE 与 BM25 的公平性能差异；
- BM25 首次加载、构建和热查询成本；
- 进程内缓存是否按用户和来源隔离；
- 索引版本变化后缓存是否失效；
- 增量 upsert 和 stale chunk 清理是否正常。

## 3. ILIKE 与 BM25 对照

测试条件：同一 owner、同一数据库、同一来源集合、同一查询集合，重复查询 10 次；ILIKE 统计数据库查询，BM25 统计已构建索引后的热查询。

| 查询类别 | ILIKE 中位数 | ILIKE P95 | BM25 热查询中位数 | BM25 热查询 P95 | Top 10 重叠率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 查询 A | 34.85ms | 40.09ms | 2.83ms | 3.87ms | 100% |
| 查询 B | 36.16ms | 47.56ms | 3.12ms | 7.05ms | 100% |
| 查询 C | 34.80ms | 37.10ms | 2.14ms | 2.32ms | 100% |

结论：

- BM25 热查询约比 ILIKE 快一个数量级；
- 三组测试的 BM25 Top 10 都落在 ILIKE 命中集合内；
- 不能把冷加载和首次构建时间混入热查询结论；
- Global Search 仍默认保留 ILIKE，BM25 只作为实验路径。

## 5. 进程内缓存验证

在同一进程中连续执行 3 次 Project RAG：

| 指标 | 结果 |
| --- | ---: |
| 第一次查询 | 205.08ms |
| 后续热查询 | 13.87ms |
| 缓存条目 | 1 |
| 缓存 owner 数 | 1 |
| 估算缓存占用 | 0.50MB |

缓存键包含 owner、词法后端和索引 revision；查询时再应用 source/scope 过滤。Rust 与 Python 使用同一套 30 分钟 TTL、LRU 和单 owner 32MB 预算，不同用户或不同后端不会复用同一索引对象。

## 7. 当前限制

- Memory 的群组/群友 scope 仍使用统一索引查询时的过滤路径；
- 文件当前索引的是元数据，不代表已经完成文件正文抽取；
- Project 等业务数据的自动增量重建事件仍需继续接入；
- 当前测试是单进程、单账号基线，不代表多 worker 高并发最终结果；每个 worker 各自维护 owner 级缓存，并通过 revision 重新构建；
- 索引路径仍需回查业务表补齐展示字段，数据库回查成本会抵消一部分 BM25 热查询收益。

## 8. Phase 4：Global Search 真实数据验收

### 8.1 测试方法

- 环境：devserver 当前数据库和当前代码；
- 数据：索引 chunk 最多的单个 owner，索引覆盖 `memory/project/file/note/canvas/calendar/scheduled_task/conversation`；
- 查询集：5 个固定中文通用查询词，仅用于测试，不写入报告；
- 每个查询先执行一次索引查询预热，再分别重复 ILIKE 和索引路径 5 次；
- 全量对照使用 Global Search 的全部来源；独立对照只使用已经接入 Phase 4 的 `project/file/note`；

### 8.5 权限与结论

- 对索引路径返回的 71 条项目、文件和便签结果进行 owner 回查，越权结果 `0`；
- 索引路径当前没有达到“比 ILIKE 更快且结果等价”的默认切换门槛；
- 当前结果数量偏多且集合重叠率低于 95% 质量目标，说明 BM25 与 ILIKE 的排序/分词语义还需要继续校准；
- Admin 开关保留索引灰度能力，但默认值回到 ILIKE，避免真实数据质量未达标时影响全局搜索。

## 9. 结论与下一步

当前方案已经证明持久化 chunk、进程内 BM25 复用和 Global Search 后端切换链路可用；但在当前真实数据和回查结构下，BM25 尚未取得整体延迟优势，召回集合也还未达到默认替换标准。

下一步：

1. 保持 Global Search 默认 ILIKE；
2. 优先分析 BM25 多返回结果与 ILIKE 的排序差异，补充稳定的 Recall@K/Precision@K 标注集；
3. 评估索引结果直接携带展示字段、减少业务表回查的方案；
4. Rust/Python 均按单用户 32MB、全局 512MB 和 30 分钟空闲 TTL 运行；后端切换会命中不同缓存键，不会沿用另一后端的索引对象；
5. 达到质量门槛后再逐步扩大来源灰度，并继续评估 PostgreSQL 原生检索或 Rust/Tantivy 的端到端收益。

## 10. Rust/Python 统一缓存回归

本轮补充了统一缓存层的回归测试：

- Python BM25 transient 索引在同一 owner、同一文档 fingerprint 下会复用同一个对象；
- 切换 Rust/Python 后缓存键隔离，旧后端对象不会被错误复用；
- 两种后端均通过同一 `_store`、TTL、LRU 和 owner 预算回收路径；
- Rust sidecar 的生命周期由缓存淘汰、过期和失效统一关闭，Python 索引不再走单独的临时重建路径。
