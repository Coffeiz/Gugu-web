# TEST：LLM-16 5 工具多模型 Schema 模式复测

> 测试日期：2026-09-02
> 测试环境：devserver `192.168.110.51`，代码版本 `6b125361`
> 测试对象：MiniMax、GLM、DeepSeek、Qwen；简介/全量两种 Schema 注入模式
> 测试目的：按照 2026-09-01 复测方法，重新验证连续会话、缓存、Token 和工具调用表现

## 1. 测试范围

本次沿用 [`2026-09-01-TEST-LLM-16-5TOOLS-MULTI-MODEL-RETEST.md`](2026-09-01-TEST-LLM-16-5TOOLS-MULTI-MODEL-RETEST.md) 的测试口径。测试目标工具固定为：

1. `list_folders`
2. `read_file`
3. `list_events`
4. `create_project`
5. `note_create`

每个模型、每种模式分别建立一个连续 session，先执行 1 次预热，再执行 20 个测量轮。20 个测量轮按 5 个目标工具循环 4 次。工具 dispatch 被诊断脚本拦截为 `not_executed`，不写入真实项目、文件、日历或笔记数据。

本次不是“只注入 5 个工具”的实验。简介模式仍注入全部已授权工具的能力目录和固定 Adapter Schema；全量模式仍注入完整工具 Schema。5 个工具只表示本轮实际要求模型调用的目标工具数量。

## 2. 统计口径

- `provider input` 为 20 个测量轮中所有 provider 子请求 input 的累计值；预热请求不计入该列。
- `cache rate = cache_read / provider_input`。
- `context input` 取每个测量轮最后一次 provider 请求的上下文长度，不等于该轮所有子请求 input 的累计值。
- `provider requests` 为 20 个测量轮的 provider 请求数，并在表中额外计入 1 次预热请求。
- Schema token 和目录 token 是当前模型 tokenizer 的运行时估算，只适合比较同一模型的模式差异，不用于比较不同模型的绝对 Token 化效率。
- 准确率要求：目标工具被调用，且参数结构满足诊断脚本预期；额外的合理核实工具调用不单独判错。

## 4. 简介与全量对比

| 模型 | 简介总 Token | 全量总 Token | 简介节省 input | 简介节省总 Token | 固定注入节省 | 准确率变化 |

| glm-4.5-air | 716,472 | 1,309,433 | 45.47% | 45.28% | 54.13% | -20 个百分点 |
| deepseek-v4-flash-vision-exp | 860,350 | 1,230,111 | 30.25% | 30.06% | 54.13% | 无变化 |
| qwen3.8-flash | 1,020,887 | 1,468,316 | 30.66% | 30.47% | 54.13% | -5 个百分点 |

四个模型合计：简介模式累计 provider input 为 `3,930,360`，全量模式为 `5,291,227`，简介模式总体节省 **25.72%**；总 Token 分别为 `3,953,333` 和 `5,307,430`，总体节省 **25.51%**。

简介模式的固定注入为 `Schema + 目录`，各模型每个 provider 请求约为 `6,432` 或 `6,461` Token；全量模式固定注入为完整 Schema，约为 `13,361` 或 `14,086` Token。因此固定部分减少约 **51.86%–54.13%**。实际累计 input 还会受到模型工具选择和续轮次数影响。

MiniMax 是本轮的例外：简介模式准确率为 19/20，但发生了更多工具续轮，累计 provider input 比全量模式高 3.98%。这说明固定 Schema 成本下降不一定能抵消模型额外核实或重试产生的续轮成本。

## 6. 失败分类

- **MiniMax 简介：1 项**：第 1 轮没有选中 `list_folders`，未发生工具调用；全量模式 20/20。
- **GLM 简介：4 项**：第 5、10、15、20 轮的 `note_create` 块结构与诊断预期不一致，均为 `blocks` 字段内部结构差异；全量模式 20/20。
- **DeepSeek 简介和全量：0 项**：两种模式均完成 20/20。
- **Qwen 简介：1 项**：第 5 轮 `note_create` 的块结构与诊断预期不一致；全量模式 20/20。

本轮 `schema_errors` 是诊断准确率层面的结构/工具轨迹统计，不代表真实工具 handler 已执行失败。所有工具 dispatch 都被 no-op 拦截，因此没有真实业务数据副作用。

## 7. 结论

1. **上下文连续性保持稳定。** 8 组测试都完成 20 轮，未记录 history compaction；说明当前 batch/history 组装没有在本轮测试中出现断裂。
2. **简介模式平均仍能节省 Token。** 四模型合计 provider input 节省 25.72%，总 Token 节省 25.51%；但节省幅度取决于模型是否额外触发工具核实和续轮。
3. **MiniMax 需要单独关注。** 其简介模式固定注入成本更低，但因多次额外续轮，实际 input 比全量高 3.98%；不能只根据 Schema token 判断最终成本。
4. **全量模式准确率更稳定。** 本轮四个模型全量模式均为 20/20；简介模式为 MiniMax 19/20、GLM 16/20、DeepSeek 20/20、Qwen 19/20，剩余问题集中在工具路由和 `note_create` 块结构。
5. **缓存率应结合上下文体积判断。** 简介模式合计缓存率为 98.73%，全量模式为 99.39%；全量模式略高，但总 provider input 更大，不能仅以缓存率决定模式优劣。
6. **默认建议仍为简介模式，但需要保留全量模式。** 日常任务优先使用简介模式；对 MiniMax 或复杂参数任务，应观察续轮和准确率，必要时切换全量模式。
