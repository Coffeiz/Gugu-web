# INVEST：RAG 冷构建超时事故的基准测试与两级 O(n²) 修复验证

> 排查日期：2026-09-13
> 排查环境：本地 Mac（worker 以 tsx 直跑 src / 构建后 bundle 两种方式各测一轮）+ devserver 部署验证
> 排查对象：`backend/ts/workers/rag` 的 `patchInMemory` 全量补丁路径
> 排查目的：事故根因（冷重建 68s > 30s 构建预算）修复后，用事故同规模数据验证真实耗时

---

## 1. 背景

2026-09-13 下午起 devserver 对话 RAG 查询全部超时。根因：20237 条文档的冷重建耗时约 68–70s（sync 1.4s + install 68s + persist 0.7s），超过 `BUILD_TIMEOUT_SECONDS = 30` 的构建预算 → 操作被取消 → persist 永不执行 → 索引快照永不落盘 → 每次查询都从头全量冷重建 → 必然超时。

第一轮修复（标记-清扫重写 `patchInMemory`）提交后，用事故同规模数据做基准验证，**发现修复只完成了一半**——本报告记录两级修复的完整测试数据。

## 2. 基准方法

脚本通过 JSONL 协议直连 worker 进程，模拟真实事故路径：

1. **建状态**：21 × 1000 条 `patch` op 分批灌入 20237 条文档（对应 sync 后的首次安装）；
2. **全量重灌**：单条 `patch` op 携带全部 20237 条同 id 重灌（对应 daily sync 的全表 upsert，事故时的 68s 热点就在这一步）；
3. **搜索验证**：`search` op 确认候选数与结果正常（排除账目错乱）;
4. **全量删除**：20237 条 deletes 验证清扫路径。

文档为合成中文文本，每条含全局共享词项 + 按 id 变化的区分词项，贴近真实语料的词项分布形态（共享热词 + 大量长尾词项）。

## 3. 测试数据

### 3.1 事故版本（逐条 removeDocument/addDocument）

事故时 worker 探针实测（devserver，20237 条）：

| 阶段 | 耗时 |
|---|---|
| sync_index_from_database（读库） | 1.4s |
| index_install_build（install） | **68s** |
| persist（落盘） | 0.7s |
| **合计** | **~70s vs 30s 预算 → 超时取消，永不落盘** |

### 3.2 第一版修复（标记-清扫，commit bf2808a1b）

| 操作 | 耗时 | 结论 |
|---|---|---|
| 冷构建（21 批 patch 建状态） | 1.6s | ✅ |
| **全量重灌 patch（事故热点）** | **71.6s** | ❌ 仍然超时 |
| search 验证 | 36ms，candidates=20237 | ✅ 账目正确 |
| 全量删除 | 320ms | ✅ |

**关键发现**：标记-清扫只对小补丁有效。全量重灌场景下，清扫阶段每个脏词项都线性扫一遍 `added` 全表找贡献者，复杂度 O(脏词项数 × 文档数)——全量重灌时几乎所有词项都脏，2 万 × 2 万 ≈ 4 亿次扫描，退化回与事故同级。

### 3.3 最终修复（新增侧按词项倒排预聚合，commit ca54a6908）

| 操作 | src (tsx) | 构建后 bundle | 对比事故 |
|---|---|---|---|
| 冷构建（21 批 patch） | 777ms | 731ms | ~70s → **<1s** |
| 全量重灌 patch | 1358ms | **782ms** | 68s → **<1s**（约 87×） |
| search（candidates=20237） | 31ms，结果 5 条 | 29ms，结果 5 条 | 正常 |
| 全量删除 | 463ms | 327ms | — |

bundle 与 src 两轮结果一致，排除了「bundle 未包含修复」的可能。minify 会改写变量名（`addsByTerm` 等标识符 grep 不到），bundle 验证必须以行为基准为准，不能以标识符 grep 为准。

### 3.4 正确性验证

- worker 协议测试套件 **62/62 全绿**，含新增回归：「大批量 patch 重灌后打分与整表 replace 一致（标记-清扫不重复计词）」——重灌同 id 同内容后 d1 打分与基线完全相等，删除后零结果。
- 重灌后 search 的候选数精确等于文档总数，账目（docFreq / lengths / documentsById）无重复计数、无遗漏。

## 4. 结论与余留

1. 复杂度从 O(n²) 降到 O(总变更词项出现数)，全量重灌 68s → 0.78s；且该路径不再对文档规模敏感（4 万条 ≈ 2 倍耗时而非 4 倍）。
2. 120s 构建预算（`ts_sidecar.py` BUILD_TIMEOUT_SECONDS，commit d86e8c52）保留作兜底，正常情况已用不到 1/10。
3. devserver 已部署新 bundle 并重启 sidecar（2026-09-14 00:27），待自然流量验收落盘缓存命中。
4. **生产 v1.2.0 镜像仍是 30s 预算 + O(n²) 旧代码**，生产后端重启导致索引失效时会复现同样的超时循环，v1.2.1 应携带本修复。
