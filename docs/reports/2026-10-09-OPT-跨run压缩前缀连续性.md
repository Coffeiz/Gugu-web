# 跨 run 压缩前缀连续性 A/B

> 日期：2026-10-09
> 环境：devserver 代码副本；真实 provider + 合成消息
> 对象：跨 run 压缩后的请求历史前缀
> 目的：验证把上一 run 的保留历史边界传给压缩器，是否修复下一 run 的前缀断裂及后续缓存命中

## 结论

根因是当前 run 的压缩路径没有使用 `MessageArea.protected_history_start`。压缩器因此可能把上一 run 的保留轮次并入摘要；持久化历史重建却继续从数据库恢复这些轮次原文。压缩后下一 run 的请求历史与上一 run 的最终前缀不一致。

修复是在 `backend/agent/loop/machine.py` 调用压缩器时传入 `protected_previous_from=messages.protected_history_start`。合成 MiniMax A/B 中，旧路径第二轮 cache_ratio 为 0.87%，修复路径为 99.84%；provider 返回的输入用量同时显示旧路径第二轮有 14,578 fresh input tokens，修复路径为 24。该结果支持“持久历史重建与压缩边界对齐后，后续轮次复用前缀”的判断。

## A/B 设计与结果

两组请求使用相同的模型配置、合成历史（摘要、25 条上一 run 历史、锚点和当前轮次）及追加轮次逻辑。A 组按旧压缩行为只保留摘要、锚点和当前轮；B 组额外保护上一 run 的历史尾部，并在下一轮按持久历史视图回放。两组使用不同的合成 system 前缀，避免彼此污染 provider 前缀缓存。只比较 provider 返回的 usage，不以本地估算作为结果。

| 组别 | 轮次 | Fresh input | Cache read | Total input | cache_ratio |
|---|---:|---:|---:|---:|---:|
| A：旧边界 | Round 1 | 9,746 | 188 | 9,934 | 1.89% |
| A：旧边界 | Round 2 | 14,578 | 128 | 14,706 | 0.87% |
| B：修复边界 | Round 1 | 14,495 | 188 | 14,683 | 1.28% |
| B：修复边界 | Round 2 | 24 | 14,683 | 14,707 | 99.84% |

旧边界 Round 2 将历史重新拼接，新增约 14.6k fresh input；修复组 Round 2 复用了 Round 1 已缓存前缀，只有新增轮次内容需要 fresh input。两组总输入量相差 1 token，说明差异来自前缀复用，而不是上下文规模明显减少。

同日还运行了仓库通用压缩缓存对比脚本（36 条合成消息）：`warm_main` cache_ratio 0.32%，`replay` 0.48%，`append` 100%。这组结果用于确认 provider 缓存对完整追加前缀的行为；跨 run 修复的定量判断以上表的定向 A/B 为准。

## 验证范围与限制

- provider：配置中的 MiniMax M3.1 Flash Preview；真实 provider 请求，正文全部为合成内容。
- 没有写入 Gugu 用量账本、业务数据库或用户会话；A/B 仅通过 provider usage 读取输入统计。
- 在 devserver 代码副本上运行 `tests/agent/context/test_compaction.py`：60 项通过。该套现有行为用例覆盖 `protected_previous_from` 保留上一 run 历史的契约。
- 文件已同步到 devserver 代码副本，但没有重启应用服务。因此没有验证正在运行的应用进程，也没有新的 LoopScope trace；需在服务加载修复后再观察真实运行的 `cache_ratio`。
- A/B 只隔离验证前缀连续性和 provider 缓存结果，不代表并发、不同模型或长时间运行下的性能结论。
