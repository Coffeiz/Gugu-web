# OPT：文件库 grep 性能实验

> 测试/排查日期：2026-10-14
> 测试/排查环境：devserver 串行后端测试；隔离 PostgreSQL Compose；进程内合成扫描器
> 测试/排查对象：文件库 grep 的元数据候选、路径解析、正文读取和逐行匹配
> 测试/排查目的：保持 Python 字面子串与 casefold 语义及用户隔离，降低常见查询延迟和峰值内存

---

## 1. 结论

当前 HEAD 已包含 SQL 路径候选下推、CJK 原始 UTF-8 字节预筛和大文件增量流式扫描；扫描并发实际为 64。独立合成扫描基准只覆盖并发 1/4/8/16，其中 16 相对 8 有小幅改善，不能据此证明 16 以上继续加线程有收益。本轮更有希望的算法方向是“DB 内 per-file Bloom n-gram 候选筛选 + 原逐行精确复核”：48,000 行合成 DB 基准中它将正文传输量减少 98.7%；另有一次真实 owner 数据的进程内预热验证，热查询为 3.96 秒。索引尚未接入产品代码，所以当前服务请求和冷查询仍未达标。

路径下推在隔离 PostgreSQL 的 4,096 文件语料中，将路径候选元数据从 4,096 行缩到 16 行，端到端 p50 从 339.47 ms 降到 15.59 ms、p95 从 499.00 ms 降到 22.79 ms。两种方案都只读取目标目录的 16 个文件、384 字节，命中和无命中语义相同。

并发 16 在 128 文件全空间无命中扫描中，相对并发 8 将 p50/p95 从 35.83/44.96 ms 降到 26.14/38.09 ms；小文件峰值 Python 分配增加约 4.8%。对超过 1 MiB 的文件，流式读取将峰值 Python 分配从 5.80 MiB 降到 0.43 MiB，但 p50 从 56.80 ms 增到 87.95 ms。因此小文件保留整文件读取，大文件才流式处理。

PostgreSQL trigram 对两字中文无收益，直接 ILIKE 也会漏掉 Python casefold 能命中的 Unicode 扩展。DB 内 Bloom 合成基准在 48,000 行上将 p50/p95 从 4.17/4.70 秒降到 2.45/2.58 秒，正文候选率 1.3%、传给应用的数据减少 98.7%；真实 owner 数据的一次性预热热查询为 3.96 秒。前者不含真实对象存储，后者预热约 20 分钟且 Bloom 只存在临时进程内。生命周期审查也发现多条内容写入和 filesync 路径；本轮没有在真实数据库建表、建索引或回填，当前服务请求尚未接入索引。

## 2. 核实的当前实现与真实数据基线

### 实现现状

- list_grep_candidates() 先按 user_id、未删除状态和文件空间加载文件元数据，按更新时间倒序；没有正文列、正文表或正文索引。逻辑路径由项目、Workspace 和 Folder 元数据批量解析，然后原实现在 Python 中按路径前缀过滤。
- 候选文件正文通过 storage.get() 整体读取，UTF-8 解码后调用 splitlines()；默认逐行 casefold()，再用 needle in line 做字面子串匹配。单文件元数据大小上限为 4 MiB，读取并发原为 8。
- 文件库不在自动 RAG 来源列表中；旧文件事件也不会建立正文 RAG 索引。仓库已有的 pg_trgm 索引覆盖拼音/元数据等字段，不覆盖文件正文。

#### 当前分支 Bloom 热查询只读验证

将当前 worktree 的 `grep.py`、`corpus.py` 临时导入一次性只读进程，连接真实 devserver 数据库和 storage；没有同步或重启服务。以同次全量正文读取计算 Bloom 过滤器及精确基线结果，再重新查询 owner 元数据和路径，使用进程内过滤器筛选并调用当前分支 `_scan_candidates` 精确复核。只在内存保留位图和结果用于等价比较，进程退出即释放，不写真实数据库、服务配置或磁盘索引。只输出聚合值：

|---|---:|
| 元数据行 / 正文候选 | 87,676 / 48,115 |
| 全量预热读取 | 48,115 文件 / 344,266,029 B |
| 预热 + 同次精确基线计算 | 1,202,149.89 ms |
| Bloom 位图内存 / 进程峰值 RSS | 98,535,424 B / 473,372 KiB |
| 热查询（元数据、路径、筛选、候选精确扫描） | 3,957.52 ms |

| 全量与候选结果 | 均为 1 个文件、10 条匹配；结构与正文逐项相同 |

这在真实 owner 数据和当前 worktree 扫描器上复现了热查询低于 10 秒，但**不代表产品当前请求已达标**：Bloom 是本次实验进程内预建的临时状态，预热约 20 分钟，约需 75 次查询才能按此前 19.97 秒冷扫描估算摊平；服务重启后该缓存不存在。它证明候选过滤算法可以达到目标延迟，仍需持久化索引、后台回填与完整写路径失效协议才能成为产品方案。由于真实库 schema/data/config 禁止改动，本轮没有把索引接入 devserver。该单次样本不报告 p50/p95；真实正文、名称、路径、搜索词和用户标识均未输出或保存。

全库长词无命中与早先单次基线的 24,212.1 ms 相比，本次为 24,820.9 ms（+2.5%）；读取量由 343,503,477 B 变为 344,274,221 B（+0.22%），扫描文件数由 48,017 变为 48,115。数据规模基本相当，但每组只有一个样本，运行时缓存、负载和文件集合有变化，不能据此声称稳定回退或改善。单字符和短中文不做同词 A/B：为满足不保留搜索词的要求，原词未保存，本次使用了不同的临时查询。

另做一次 owner 范围内的原生固定字符串批量扫描对照：路径列表仍由 owner 过滤后的文件元数据生成，候选结果再由应用现有精确扫描器核验。元数据 4,310 ms、路径/预处理 1,215 ms、原生正文扫描 11,601 ms、候选精确复核 1.3 ms；扫描 48,115 个正文候选，总计 26,333 ms，峰值 RSS 431,444 KiB，最终命中 1 个文件、10 行，与已知结果一致。原生扫描阶段比此前应用正文阶段的 17,629 ms 快约 34%，但仍读取全部 344,274,221 B，且本次端到端耗时没有优于 19,973 ms 的应用基线；不将外部 `grep` 子进程选为产品方案。

路径样本从本人命中文本的路径元数据中动态选择，路径值只在进程内使用并丢弃；SQL 返回 8 条候选，读取 8 个文本文件。没有对该真实路径另跑未优化的全量元数据方案，因此它的真实数据 A/B 仍以隔离合成路径基准为准。实际复测未记录峰值内存；大文件内存收益来自合成扫描器的 tracemalloc 数据。真实 devserver 复测期间没有修改服务、配置、数据库 schema 或数据，也没有输出正文、文件名、路径、搜索词或用户标识；临时远端/本地脚本及源码副本已按准确目录核验并清理。

## 3. 合成语料与候选方案数据

合成正文、标签和路径均为脚本生成值。进程内扫描语料为 128 个文件、3,075,992 B、每文件 32 行、最大 24,032 B；数据库路径语料为 4,096 个文件，其中目标目录 16 个文件。大文件扫描语料为 8 个文件、共 12,287,603 B、最大 1,535,952 B。PostgreSQL trigram 语料为 512 行、3,751,221 B。计时分别重复 21 次、21 次、11 次；p95 使用最近秩法，受远端调度影响，作为此语料上的比较值而非生产 SLA。

### 路径候选下推

| 方案 | 元数据候选行 | 扫描/读取 | p50 | p95 | 峰值 Python 分配 | 正确性 |
|---|---:|---:|---:|---:|---:|---|
| 先加载元数据、解析路径后过滤 | 4,096 | 16 文件 / 384 B | 339.47 ms | 499.00 ms | 8,445,444 B | 基线 |
| SQL 按用户、空间和逻辑路径预筛 | 16 | 16 文件 / 384 B | 15.59 ms | 22.79 ms | 301,965 B | 无命中与路径内命中一致 |

SQL 仍按 owner 条件筛选 Project、Workspace、Folder 和 File；随后保留原路径解析和 Python 前缀检查作为最终校验。读取字节不变，收益来自避免加载和解析无关文件的元数据。

| 整文件 | 1 | 185.82 ms | 245.77 ms | 106,755 B | 128 / 3,075,992 B | 基线 |
| 整文件 | 4 | 58.91 ms | 78.83 ms | 100,380 B | 同上 | 等价 |
| 整文件 | 8 | 35.83 ms | 44.96 ms | 100,414 B | 同上 | 等价 |
| 整文件 | 16 | 26.14 ms | 38.09 ms | 105,184 B | 同上 | 等价 |

并发 16 对全扫描最有利；小文件语料内额外 Python 分配约 4.8%，大文件通过 1 MiB 分界进入流式路径，避免同时把多个大正文完整驻留在内存。并发 1/4 远慢于 8/16。指定目录的短中文命中中，并发 8 与 16 的 p50 分别为 4.51 ms 和 3.17 ms，收益小于全空间无命中场景。

### PostgreSQL trigram 候选

在隔离 PostgreSQL 临时表上创建 gin_trgm_ops 正文索引：构建 386.00 ms，占用 1,269,760 B。查询计划没有选择该索引；小语料下的计时不支持把约 0.7 ms 的单次 p50 差异当作稳定索引收益。

| 查询类别 | 无索引命中行 | trigram 命中行 | 无索引 p50/p95 | trigram p50/p95 |
|---|---:|---:|---:|---:|
| 三字符无命中 | 0 | 0 | 5.143 / 6.140 ms | 0.712 / 5.621 ms |
| 单字符 | 512 | 512 | 1.239 / 1.585 ms | 1.633 / 1.855 ms |
| 双中文字符 | 512 | 512 | 未单独计时 | 未单独计时 |

16 行写入操作的 p50（无索引 → trigram）：新增 0.628 → 0.766 ms，正文编辑 1.600 → 13.635 ms，路径移动 0.733 → 12.898 ms，删除 0.708 → 0.645 ms。p95 对应为 1.529 → 1.954、2.722 → 22.536、1.250 → 19.021、1.292 → 0.960 ms；移动和删除量级很小且时延波动较大，不据此推断稳定差异。正文索引不需要因移动改变正文索引项，但实际文件移动链路未在此表模拟。

Python casefold 中，strasse 能匹配 Straße；PostgreSQL ILIKE 对相同合成值返回零候选，直接用它做前置过滤会漏结果。普通全文检索、ILIKE 或 RAG 语义召回都不能直接替代当前字面匹配契约。要用正文索引，至少需要与 Python casefold 一致的索引表示、短词回退、文件增删改同步机制和迁移；本轮收益证据不足以覆盖这些成本。

### DB 内 Bloom n-gram 候选过滤

在两次独立 PostgreSQL 18 Compose 中用 SQL `get_bit(bytea, …)` 检查每文件 2 KiB 位图，应用只取候选 ID 和候选正文，再沿用逐行精确匹配。语料由 6,000 份固定种子的合成中文正文复制扩展成 48,000 行，逻辑正文 274,464,000 B；复制扩展的行分布适合规模查询，不代表 48,000 份独立文档。每次运行重复 7 次：

| 方案 | 第 1 次 p50/p95 | 第 2 次 p50/p95 | 候选文件 | 应用接收正文 | 命中数 | 语义一致 |
|---|---:|---:|---:|---:|---:|---|
| 全量扫描 | 4,171.81/4,699.38 ms | 7,185.12/9,510.69 ms | 48,000 | 274,464,000 B | 8 | 基线 |
| DB 内 Bloom + 精确复核 | 2,444.87/2,579.48 ms | 3,189.15/6,448.28 ms | 624 | 3,568,032 B | 8 | 是 |

位图总计 98,304,000 B，DB Bloom 表占 137,371,648 B；候选率 1.3%，应用正文传输减少 98.7%。两次隔离运行的 Bloom p95 均低于 10 秒，但尾延迟从 2.58 秒波动至 6.45 秒；均验证了 48,000 行语义相同。9 个性质样例覆盖中文、大小写敏感复核、casefold 扩展、跨行、无正规化、单字符/无效编码回退。语料包含第二 owner、deleted、索引缺失和 DIRTY 样本；缺失/dirty 作为全扫候选，owner/deleted 条件保留。

另将候选筛选接到产品现有 `_scan_candidates` 和 `LocalStorageBackend`，在临时目录创建 48,000 个合成路径（6,000 份随机正文以硬链接扩容），各路径重复 7 次。此分段测量预先计算 Bloom 候选 ID，不计 SQL 过滤时间：全扫描 p50/p95 为 12,505/13,056 ms，读 48,000 个文件和 274,464,000 B；候选扫描为 173.64/210.19 ms，读 616 个文件和 3,522,288 B；扫描结果等价。DB 实验的 624 个候选还包含索引缺失/DIRTY 安全回退样本，因此该存储分段的 616 个候选数字不能替代前表的 DB 候选数。该本地硬链接语料只衡量应用正文读取/扫描段，不模拟 OSS 延迟，也不能外推成真实请求总延迟。

6,000 份位图构建 42.54/42.07 秒，初始 DB 装载 1.88/3.32 秒；扩展到 48,000 行用时 22.98/14.55 秒（复制合成数据和位图）。按构建耗时线性外推，48,115 个独立文件初次回填约 5.7 分钟，仅为估算。16 文件新增/编辑（含位图构建及 DB 写入）的 p50/p95 分别为：新增 58.44/88.82 ms 与 100.40/4,812 ms，编辑 51.99/56.80 ms 与 78.62/2,295.50 ms；移动不重建位图为 2.31/7.38 ms 与 3.53/48.01 ms；删除并级联清理为 3.46/3.82 ms 与 3.82/7.47 ms。维护尾延迟有显著环境波动。

数据库 p50 中位收益明确，但测试尾延迟波动明显；本地存储分段也只验证正文候选裁剪收益，不包含真实 DB 元数据路径处理、OSS 往返、filesync 竞态和产品表锁争用，因此不能将其结果当作真实请求 p95。原型还必须提供独立内容 revision/失效状态、初次后台回填、编辑中失效和写后发布、活动 filesync 根绕过，以及索引缺失/损坏回退。当前 `File.version` 不足以独立作为内容版本，不能只加 SQL 过滤后就上线。
