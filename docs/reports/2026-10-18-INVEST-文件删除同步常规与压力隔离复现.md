# 文件删除同步：常规与压力隔离复现

## 结论

已在临时目录复现“磁盘删除完成，监听仍活跃，但部分删除事件永久缺失”。直接触发条件是大量删除期间监听进程无法及时读取内核事件；不能仅凭 CPU 使用率高判定必然丢失。

当前 `node:fs.watch` 路径未把本次内核队列溢出转换为 `needs_reconcile`。Python 队列、TS 输出队列已有的溢出保护覆盖不到这个更早的丢失点。与此同时，自动补偿明确使用 `allow_delete=False`，即使发现缺失记录也会保留为冲突，不能自动恢复删除事实。

这提供了与真实故障一致的可复现机制，但没有当时的内核事件记录，不能证明历史事故必然由同一触发条件造成。

## 隔离与方法

- 实验在 devserver 临时目录创建合成文件；不使用真实工作区、真实用户 ID 或文件正文。
- 运行独立 `FileSyncSidecar` 子进程，使用当前已构建的实际 TS watcher 制品。
- 文件先创建，等待 watcher `ready`，再以独立 Shell 命令批量删除；测量磁盘剩余文件、唯一删除事件数量和缺口通知。
- 压力分为：突发批量删除、业务消费暂停 8 秒、仅暂停探针自己的 watcher 子进程直到删除完成、测试 watcher 与一个有 15 秒上限的 CPU 忙循环绑定到同一核。
- 对初次未收齐的 CPU 场景延长观测，避免把处理延迟当成丢失。最终删除观测窗口为 45 秒，再写入哨兵，最多观察 20 秒。
- 原生 inotify 对照使用独立文件描述符及相同删除量，直接读取内核事件掩码。
- 数据库行为使用已有 pytest 临时 SQLite fixture；未执行真实数据库修复、配置写入或服务重启。
- 临时目录与探针子进程由脚本收尾清理；单核竞争只约束实验子进程，不修改应用进程亲和性或系统内核参数。

入口：`backend/scripts/diagnostics/filesync_delete_pressure.py`。

```bash
cd backend
PYTHONPATH=. .venv/bin/python scripts/diagnostics/filesync_delete_pressure.py --repeats 1
```

脚本仅支持 Linux。全矩阵串行运行，不接入默认 CI。

## 测量结果

| 场景 | 预期删除 | 收到删除 | 结果 |
| --- | ---: | ---: | --- |
| 常规，重复两轮 | 100 | 100 / 100 | 全部到达 |
| 批量，重复两轮 | 5000 | 5000 / 5000 | 全部到达 |
| 大批量，持续消费 | 24000 | 24000 | 一轮全部到达，约 14.54 秒 |
| 单核竞争，延长观测 | 24000 | 24000 | 约 22.41 秒全部到达，哨兵正常 |
| 监听停顿，延长观测 | 24000 | 16384 | 永久缺失 7616；约 46.17 秒后哨兵正常 |
| 消费暂停 8 秒，初次两轮 | 24000 | 21259 / 22696 | 未收齐；初次不含哨兵，因此不单独作为永久丢失证据 |
| 消费暂停 8 秒，追加哨兵 | 24000 | 22776 | 未收齐，哨兵正常；缺口通知为 0，随后追加延长观测复核 |
| 消费暂停 8 秒，延长观测复核 | 24000 | 24000 | 约 14.06 秒全部到达，哨兵正常 |
| 原生 inotify 对照 | 24000 | 16384 | 另收到 1 个 `IN_Q_OVERFLOW` |

监听停顿、追加哨兵的消费积压实验均未收到 `needs_reconcile` 或 `error`。探针结束前 sidecar 仍在运行。消费暂停的重复结果随事件产生与调度时序变化，延长观测复核可以全部到达，因此不将“消费者暂停 8 秒”认定为稳定丢失条件；稳定证据以暂停监听进程与原生内核队列对照为准。

早期单核竞争只观察约 17 秒时收到 8772 个，哨兵未到；延长观测后全部收齐，故不把早期数字计为丢失。

## 已有行为回归

- Python：真实 Shell 创建/等长更新/删除到 watcher、数据库、journal 的链路；sidecar 队列溢出；周期补偿；绑定健康标记：9 项通过。
- Python：禁止删除时持久化缺失冲突；明确允许删除的完整修复（两种账本状态）：3 项通过。
- TS watcher 与协议输出队列：9 项通过。

合计 21 项已有测试通过；这些普通用例不代表高压路径正确。压力探针揭示了既有回归未覆盖的内核队列溢出边界。

## 代码链路

1. `backend/ts/packages/filesync-watcher/src/watcher.ts`：`watchDirectory()` 使用 `node:fs.watch`；回调仅处理文件名事件，缺失名字等情况会报告缺口，但本次内核溢出没有进入该协议。
2. 同文件 `processPath()`：删除每一路径时遍历全部已追踪路径寻找子项；大批量删除存在同步扫描开销，是可能放大消费停顿的因素。本次没有独立性能剖析，不将它单独认定为事故根因。
3. `backend/ts/packages/filesync-watcher/src/protocol-output.ts`、`backend/app/services/filesync/ts_sidecar.py`：TS/Python 缓冲溢出有恢复信号，但只保护已经到达各自队列的事件。
4. `backend/app/services/filesync/watcher.py`、`periodic.py`：自动缺口修复均明确禁止删除。
5. `backend/app/services/filesync/runner.py`：缺失对象在禁止删除的修复中转为可处理冲突，数据库记录保持活动。

## 后续修复建议

- 优先让 Linux 监听源可靠暴露内核溢出；溢出后持久化缺口、进入可核对状态，不能继续只显示 ready 使调用方误认为完整同步。
- 对检测到缺口后的删除恢复制定明确契约：验证根身份、扫描完整性和对象版本后，选择受控修复或明确要求确认；不能简单全局打开删除或只增加队列大小。
- 改善大量文件删除的事件处理复杂度，并保留“精确事件遗漏时仍可恢复”的机制。
- 增加可持久查询的缺口原因及发生时间；ready 不应覆盖最近缺口的诊断依据。
- 把内核溢出、服务暂停期间删除、大目录删除、补偿后的最终数据库收敛纳入后续回归。

本轮仅调查、隔离测试和记录，不修改生产同步策略，不清理真实残留记录。
