# 记忆反思缓存率与群分支资料顺序调查

日期：2026-10-18。范围：用户所报当天 7 次记忆反思，及 devserver 上隔离的真实模型复现。本文只保存统计与结构事实，不保存真实聊天、记忆正文、用户标识、环境地址或凭据。

## 结论

71.1% 是准确的 token 加权结果，不是 UI 算错。5 次 owner 反思合计命中率为 90.06%；另 2 次群组/成员反思分别为 0% 和 65.34%，拉低总值。

低值有两个不同原因：

1. 群消息是被动接收，闲置窗口到期后由 worker 创建反思；没有同时发生的新主 run，也就没有本进程可复用的主请求快照。后台走持久历史重建，不能把它当作刚完成主请求后的热缓存分支。
2. 群反思与成员反思虽然共享相同历史、system 和约 5.7 万字符的已有记忆资料，但任务增量先放不同的专用指令，再放共同资料。两种请求在共同资料之前已经分叉，后续约 3.4 万 tokens 的资料不能跨任务共享前缀缓存。

真实模型重复复现了第二项，单纯调整共同资料和专用指令的先后顺序后，成员反思由约 65% 提升到约 98%。首次冷请求仍为 0%～0.13%；此实验不能保证包括冷请求的总缓存率达到 80%，也不代表已完成记忆提取质量验收。

初始调查阶段仅在诊断进程的请求副本中调整顺序。用户随后授权落地缓存优化和冷请求统计，实施结果见文末与对应 devlog。

## 运行事实与代码位置

- 群两次反思来自同一会话、同一批被动消息；任务 reason 为 `idle`，重试次数为 0，均成功完成，不是失败重试造成统计失真。
- 最后几条被动用户消息约在 06:30，worker 约在 06:35 创建任务，符合共享的 4 分 30 秒闲置窗口。
- 可用 trace 中，该群最近的真实主请求在 10 月 15 日；当时为 Anthropic 路由。本次后台反思为 MiniMax-M3.1-Flash-Preview 的 Responses 路由。不能宣称复用了同一次请求的缓存身份。
- 群与成员观测的 prefix digest 相同，history count 为 357，tool count 为 0，origin 为 idle 重建；并非 owner 快照链路普遍损坏。
- `agent/memory/reflection_jobs.py:settle_idle_scopes` 创建闲置任务；`im_reflection.py:_execute_job_locked` 找不到运行时快照后调用 `_rebuild_session_snapshot`。
- `_rebuild_session_snapshot` 重建静态 system 和持久历史，不带冻结 session snapshot 及主请求工具声明。这个既有路径明确不保证缓存命中；本次群数据也没有可供热复用的新主 run。
- `im_reflection.py:_build_append_branch_input` 当前布局为：专用规则 → 已有记忆 → 本批范围。group/member 的规则开头不同，所以共同资料无法命中前一个任务的后半段缓存。
- 当前读取的共同资料包含 profile、summary、daily、memory，排除了 members。实验时共同资料序列化后为 56,964 字符，没有裁剪、删除或改写资料。

## 真实模型复现

初始调查进行了 11 次真实模型请求：3 次现行路径检查、第一组 4 次 A/B、脚本复跑 4 次 A/B。后续落地再进行了 4 次 A/B，以及仓库规定的 3 次合成缓存策略对照，总计 18 次。均没有执行返回的工具，没有调用生产反思结果写回，也未设置业务 usage context，因此不向 AgentUsage 写入诊断记录。Provider 侧仍发生真实计费用量。

### 现行路径检查

以同一已有群反思任务重建当前输入，使用生产 `provider_runner.complete_messages` 调用，保持模型、协议、完整历史与任务内容：

| 请求 | 完整输入 | 缓存读取 | 命中率 |
| --- | ---: | ---: | ---: |
| group | 102,220 | 128 | 0.125% |
| member，紧跟 group | 103,154 | 67,840 | 65.766% |
| group 原样重发 | 102,220 | 102,144 | 99.926% |

最后一次 SDK 请求体 digest 与第一次完全一致。这说明 provider 能缓存这份长输入，65% 不是此模型对长上下文的固定缓存上限。

### A/B 方法

- A：现行专用规则在前。
- B：将完全相同的已有记忆资料移到专用规则前，其余内容完整保留。
- 每臂都先 group，再 member；两臂分别使用不同的实验 system 标记，避免互相预热。
- 两臂使用同一份模型配置、同一历史和同一记忆快照；没有切模型、删字段、换任务、缩短历史或增发预热请求。
- 独立标记的 tokenizer 差异可造成两臂完整输入相差少量 tokens，不是业务正文有变化。

| 实验 | 现行 member | 资料置前 member | 首次 group |
| --- | ---: | ---: | ---: |
| 第一次 A/B | 65.752%（67,840 / 103,176） | 98.380%（101,504 / 103,176） | 两臂均约 0.125% |
| 仓库脚本复跑 | 65.504%（67,584 / 103,176） | 98.005%（101,120 / 103,178） | 两臂均为 0% |

脚本复跑中 member 未命中输入由 35,592 降至 2,058 tokens，下降约 94.2%。

限制：历史反思 trace 只保留结构与 usage，没有完整的历史反思 SDK payload；本次复现用当前配置与当前记忆重建。历史与布局匹配，system digest 与 06:35 的旧样本不同，所以这是同路径结构复现，不是历史请求逐字节回放。较小输出预算只为测量缓存，不评价完整 JSON 产物或提取质量。

## 建议与验收边界

优先把 group/member 共同资料放在专用任务指令前，可保留完整语义并减少后一个任务的重复输入。本次仅验证了缓存收益；正式落地仍应验证成员归属、scope 隔离、旧记忆冲突处理和模型提取质量，不能用缓存率代替质量。

对被动群聊的首次闲置反思，应单独统计冷重建，避免和有主 run 快照的热分支混用一个 80% 目标。若进一步降低冷请求成本，可以评估本批消息与必要指代上下文的范围，但这属于语义范围调整，需要另做质量对照，不能直接删历史或记忆来刷高指标。

初始调查未修改生产逻辑。用户随后授权优化与统计展示，现已实现共同资料置前及场景统计的新指标，详见 [群反思资料前缀复用与冷请求统计](../devlog/2026-10-18-群反思资料前缀复用与冷请求统计.md)。没有植入运行时探针，未修改用户配置，未提交或推送本轮文件。
