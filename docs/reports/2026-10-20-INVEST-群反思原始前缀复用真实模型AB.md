# 群反思原始前缀复用真实模型 A/B

> 日期：2026-10-20
> 环境：devserver 隔离诊断
> Provider：DeepSeek `deepseek-flash` / OpenAI Chat Completions；MiniMax `MiniMax-M3.1-Flash-Preview` / Anthropic Messages
> 范围：主 run 后的群反思追加请求；只记录 usage 与安全结构字段，不记录提示词正文。

## 结论

使用真实 Provider 请求对比持久历史重建与进程内原始前缀复用。DeepSeek 两次对照中，A 的反思缓存读取均为 0，B 缓存率为 90.59% 和 91.09%。随后使用 MiniMax M3.1 Flash Preview 做三组隔离合成对照，A 缓存率为 2.25%、2.05%、2.14%，B 为 99.59%、99.57%、99.65%。DeepSeek 第二次通过正式 `ContextBranch` 生成 LoopScope 反思观测，来源标记正确记录为 `in_memory_extended`。

结果支持这次改动能让群反思复用主 run 的 Provider 缓存前缀。它不代表所有真实群消息都能通过严格的数据库尾部对齐，也不保证不同 Provider 或更长间隔下达到相同缓存率。

## A/B 方法

- 两轮实验分别使用独立合成标记，防止 A、B 两臂互相预热；每臂先发一次真实主请求，再立即发群反思请求。
- A 使用持久历史重建视图，经生产分支历史投影，并保留旧路径的空工具声明。
- B 使用主请求的 `ProviderConversation` 和工具声明，通过生产 `_extend_snapshot_with_persisted_tail` 严格匹配原前缀，再追加一条合成被动消息。
- 两臂使用相同的模型、协议、群反思构造器、任务内容结构和生成预算。正文为合成项目记录，不读取真实 QQ 消息；工具未执行，不调用业务记忆写回。
- 第二轮使用生产 `run_reflection_branch` / `ContextBranch`，并把脱敏 usage 发入隔离 LoopScope trace。完整提示词不写入 trace 或报告。

该实验验证真实 Provider 对两种群反思输入形态的缓存表现。它没有向真实 QQ 群发送消息，也没有读取或改写生产会话、记忆文件、用户配置或数据库，因此不等同于线上调度端到端回放。MiniMax 对照直接使用生产 Anthropic client 发起隔离请求，未经过正式 `ContextBranch` 或 LoopScope 记录；它补充验证 Provider 缓存行为，不替代 DeepSeek 的正式分支验证。

## 限制与后续观察

- 严格尾部对齐用合成持久化序列验证；真实群里历史重建可能因旧消息形态、thinking/tool 记录或基线边界不同而无法匹配。无法匹配时仍按设计回退到 `persisted_history`。
- 实验是立即连续调用，不能外推 Provider 缓存 TTL，也不能保证线上闲置窗口、运行排队和负载下的同等结果。
- MiniMax 对照验证的是 Anthropic API 对这两种合成输入形态的缓存行为；由于未运行完整 `ContextBranch` / LoopScope 链路，不能据此推断 MiniMax 线上反思的 `snapshot_source` 与调度行为。
- 上线后应观察 QQ 群反思的 `snapshot_source` 分布及 cache ratio：若仍以 `persisted_history` 为主，应继续调查真实历史对齐失败的结构原因；若来源为 `in_memory_extended` 但缓存低，再检查 Provider 前缀与时间间隔。
- 本轮真实 Provider 调用可能产生费用；只保存聚合 token 数、来源标签和隔离 trace ID。
