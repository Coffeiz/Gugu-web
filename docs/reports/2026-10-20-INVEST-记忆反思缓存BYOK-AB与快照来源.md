# INVEST：记忆反思缓存 BYOK A/B 与快照来源调查

> 测试/排查日期：2026-10-20
> 测试/排查环境：devserver 诊断记录；用户 BYOK 的 MiniMax 直连验证
> 测试/排查对象：MiniMax-M3.1-Flash（Anthropic API 格式）记忆反思请求缓存
> 测试/排查目的：确认同一前缀能否复用缓存，调查低缓存读取是否由前缀变化造成，并补齐反思快照来源观测

---

## 结论

1. 通过用户已配置的 BYOK 对 MiniMax 做合成请求 A/B 后，同一前缀的紧邻重复请求缓存读取率约为 **99.97%**；改变静态 system 内容并移除工具定义后，首轮请求只读取约 184 个缓存 tokens。这证明该 BYOK 路径可以命中缓存，也说明前缀变化会让大部分输入重新成为冷请求。
2. 这次 A/B 同时改变了 system 内容和工具集合，不能据此区分哪一项单独造成失配。它也没有等待超过 5 分钟后重放同一前缀，因此不能证明或排除 TTL 到期。
3. 两条线上反思 trace 的缓存读取都只有 184 tokens。第一条与前次主请求相隔约 329 秒；第二条与最近主请求相隔约 285 秒，但其反思请求与主请求的 system 摘要和工具数量不同。现有证据更支持“缓存前缀不一致和请求间隔共同影响”的解释，尚不能把低命中单独归因于 TTL。
4. 排查同时发现 idle drain 从持久历史重建快照时，LoopScope 上下文可能保留初始的空来源，漏记重建快照的来源信息。此次代码修复补记 `persisted_history` / `in_memory` / `unavailable`，并保留 `idle` 触发类型；它改善后续诊断，不会直接改变 Provider 缓存行为。

## 用户 BYOK 合成 A/B

测试顺序为串行，每组先发一次冷种子请求，再立即以相同前缀重复请求。正文由合成随机内容组成，不使用真实对话或记忆内容。

| 组别 | 前缀设置 | 阶段 | 输入 tokens | 缓存读取 tokens | 缓存写入 tokens | 缓存读取比例 |
|---|---|---|---:|---:|---:|---:|
| A | 合成 system、历史及 4 个合成工具 | 种子请求 | 59,887 | 184 | 0 | 0.31% |
| A | 与 A 种子请求完全相同 | 紧邻重复 | 17 | 60,054 | 0 | 99.97% |
| B | 改变合成静态 system，省略工具定义 | 种子请求 | 59,476 | 184 | 0 | 0.31% |
| B | 与 B 种子请求完全相同 | 紧邻重复 | 17 | 59,643 | 0 | 99.97% |

种子与重复请求的 usage 分别来自 Provider 返回值。种子请求只读取 184 个缓存 tokens；紧邻重复请求则读取约 60k 个缓存 tokens。A 到 B 的变化同时修改 system 与 tools，实验设计没有隔离这两个变量。

MiniMax 文档说明提示缓存按请求前缀工作，并提到工具、system、历史内容的排列会影响前缀；该文档未给出可用于本次判断的明确 TTL 数值：[MiniMax 提示词缓存文档](https://platform.minimax.cn/docs/api-reference/text-prompt-caching)。

## 代码与观测修复

- idle drain 先以无快照上下文启动时，若反思随后成功从持久历史重建快照，现会在保留 `trigger_source=idle` 的同时更新 `origin_run_id`、间隔及快照来源。
- LoopScope 反思缓存观测和聚合样本增加固定枚举 `snapshot_source`，仅允许 `in_memory`、`persisted_history`、`unavailable` 等安全标签，不记录历史正文。
- 本修复不改 system/tool 组装、前缀排序、Provider 请求策略或缓存 TTL。

## 验证与限制

- `test_reflection_append_reuse.py`：17 项通过。
- `test_cache_drop_probe.py` 中针对缓存观测的 3 项：通过。
- 一次扩大范围的组合运行中，另有 2 个 active-trace 断言失败（未找到预期 span，run spans 为空）；目前没有基线对照，不能判断是否由本次改动导致，需单独确认运行上下文。
- BYOK A/B 调用了真实 MiniMax Provider，但只发送合成正文；BYOK 配置为只读解析，未输出或保存密钥，未写入数据库或运行配置。A/B 使用临时进程内调用，没有提交测试脚本或原始请求正文；上表仅保留结构化 usage 统计。
- A/B 是立即重复请求，未覆盖跨 5 分钟 TTL 场景；也没有将 system 变化与工具集合变化拆开测试。当前结论不应被解读为 TTL 已确认。

## 后续建议

1. 收集带 `snapshot_source` 的新反思 trace，核实低命中样本具体使用的是数据库重建还是内存快照。
2. 用同一 BYOK、同一 wire 前缀分别做即时重放和超过 5 分钟后的重放；固定 system、tools、历史及协议，只改变等待时间，才能验证 TTL。
3. 再单独改变 tools 或 system 做前缀敏感性对照。在获得这两类证据前，维持现有 TTL 与缓存策略。
