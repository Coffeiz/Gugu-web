# MiniMax 完整视频首响应超时隔离复现

日期：2026-10-22。范围：devserver 的一次真实 QQ 故障调查及隔离 Provider 请求；未修改业务代码、运行配置、原始文件或正式会话。

## 已确认结论

完整视频请求可被 MiniMax-M3.1-Flash 正常处理并返回非空正文，但一次隔离请求直到 **128.793 秒**才收到首个事件，134.299 秒完成；工具结果结构的隔离请求则在 131.423 秒收到首个事件，133.632 秒完成。主对话 Anthropic 驱动固定使用 120 秒读取超时，因此会在此类慢视频请求返回前断开；相同超时边界的反复重试会放大用户等待。

这不是本次成功复现中的输出 token 耗尽：所有隔离请求使用 25600 输出预算，完整视频成功请求实际只输出 388 token，停止原因为 `end_turn`。这也不证明任意视频、任意历史长度都不会超过上下文窗口。

## 真实故障证据

- Run：`run-921a1389c5a6-9b707d`，第 1 轮成功，第 2 轮读取视频工具返回后失败。
- 工具耗时 15.401 秒，结果已包含 MiniMax Files 引用；后续模型轮次耗时 746.113 秒。
- 诊断编号：`D3EB0EAC1C809CD5`。异常链包含 `RetryableError → APITimeoutError → ReadTimeout`，未收到 HTTP 状态或 Provider 错误码。
- 失败请求的序列化正文为 321349 字节、123 条消息；正文使用文件引用，并不内嵌完整视频。
- 第 1 轮 Provider 实际输入 82345 token、输出 256 token。这是成功轮次用量，不是失败视频请求的实际用量；失败请求没有返回 usage。
- 触发消息已持久化失败状态，正文未被覆盖。

现有策略由 `backend/agent/loop_drivers.py` 的 Anthropic 驱动设定读取超时；`backend/agent/loop/provider.py` 在尚未输出正文时重试，`backend/app/core/retry.py` 允许最多重试 5 次，间隔 5 秒。六次 120 秒等待加五次间隔约为 745 秒，与故障轮次耗时吻合。

## 输入与隔离边界

原视频：58820613 字节，631.531 秒，1920×1080，30 fps，AV1 视频、AAC 音频。报告使用通用名称，不记录真实文件名和路径。

使用现有配置的同型号 MiniMax 预设，仅在测试进程内把输出预算设为 25600；配置文件保持只读。复用现有 Provider client、认证和思考参数，每次测试仅发起一个请求，关闭 SDK 重试，不执行模型返回的工具，不落正式会话。

完整视频直接复用故障 Run 的 Files 引用。编码对照取原视频开头约 8 秒，去除音轨；AV1 片段只裁切封装，H.264 片段仅用于隔离测试。该对照没有改变产品的原文件直传策略。

视频块取自工具 span 的完整结果。LLM span 中更深层的媒体字段可能已记录为 `<max-depth>`，不能直接当作有效 Provider 请求回放；初次因此被拒绝的预检不计入下面的有效对照。

另有一次把完整视频采样参数改为 `fps=0.1` 的探针，120.313 秒后收到 HTTP 400；未取得足以分类的错误正文，不能解释为 token 超限，也不作为降低采样率的改动依据。

## 结论边界与建议

已排除“AV1 一概无法理解”“Files 引用一概不可用”“必须嵌入工具结果才出错”和“必须携带长历史才出错”：短片段四组对照均成功，精简为单条用户输入的完整视频仍能触发超时。

延长单次等待后两种结构均成功，证明当前 120 秒读取超时可以直接阻止这份视频完成。成功标准是返回非空正文且以 `end_turn` 正常结束，并非对视频理解准确度的评测。测试没有测量 MiniMax 内部解码、排队和推理各自耗时，也没有按原正式 Run 的完整 123 条消息精确重放，不能声称所有原始上下文因素都已逐项排除。

建议下一步：复用 Provider 能力配置，为实际携带视频的请求提供更长的单次读取等待，并保留明确的总等待边界；重试策略与较长单次等待共同设计，避免连续重启同一慢请求。界面应区分“视频已上传”和“模型分析中”，并将超时原因准确显示给用户。第一版不需要强制转码、降低视频规格或提高输出 token 上限。

本轮只完成调查与复现，未应用上述改动。临时本地媒体由临时目录退出时清理，两个新上传的短片段均收到删除接口成功回执，再次列举确认剩余测试上传为 0；原视频及其已有 Provider 文件引用保留。
