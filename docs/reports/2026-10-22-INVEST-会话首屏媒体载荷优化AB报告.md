# 会话首屏媒体载荷优化与 A/B 报告

## 结论

首屏 `messages` 响应膨胀的直接原因，是聊天展示时间线重复保存并回传了 `read_file` 读取视频时产生的多模态帧数据。真实会话的同数据 A/B 中，响应从 **185,334,883 字节**降到 **708,181 字节**，减少 **99.62%**（约 **262 倍**）。

## 问题证据

- 首屏请求实际返回 28 条正文消息和 216 条时间线事件；虽然正文窗口上限为 50 条，但每条助手消息可能附带多个工具/展示事件。
- 优化前 JSON 响应为 185,334,883 字节，与浏览器记录的约 185 MB、8.23 秒加载相符。
- 结构探查显示，大载荷来自 `read_file` 时间线里的视频块及其 Base64 帧数据。探查只统计结构、字节数和耗时，没有输出或保存聊天正文及媒体内容。
- 前端工具气泡原本会截断较长结果，但截断发生在响应下载和 JSON 解析之后，因此没有降低传输量。

## 修改

1. Run 收尾写入展示时间线前，复用媒体域的历史清理函数，将图片、视频、音频块改成简短占位文本。模型本轮仍可使用原始多模态数据；只清理供历史气泡展示的副本。
2. 消息接口也清理 `timelineEvents` 和兼容 `toolEvents`。这样既覆盖新数据，也避免旧记录在读取时继续向浏览器回传 Base64。
3. 增加接口与持久化回归测试，确保视频载荷在展示历史中被替换，同时保留工具名称及事件结构。

## A/B 方法与结果

在 devserver 的同一真实会话、同一数据库快照上直接调用消息接口两次：A 组将清理函数替换为原样返回，B 组使用优化后的清理函数。两组使用相同分页、消息与事件；只记录序列化字节数和耗时，不记录正文内容。

| 指标 | A：原样回传 | B：媒体占位 | 变化 |
|---|---:|---:|---:|
| JSON 响应体 | 185,334,883 字节 | 708,181 字节 | -99.62% |
| 接口处理耗时 | 2,334 ms | 2,280 ms | -54 ms |
| JSON 序列化耗时 | 3,258 ms | 24 ms | -99.28% |
| 正文消息 / 时间线事件 | 28 / 216 | 28 / 216 | 不变 |

这次 A/B 直接测量了真实接口投影和 JSON 序列化；没有模拟浏览器网络，也没有把结果解释为完整端到端时延。主要收益是响应体缩小约 185 MB、序列化耗时明显下降。接口处理耗时仍约 2.3 秒，主要因为旧记录在数据库中仍保存着完整媒体数据，读取时需要先加载再清理；网络传输后的最终浏览器耗时还取决于网络与客户端环境。

### 运行时 500 补充

首次同步后，devserver 的常驻后端仍返回 500。日志表明，当前 `agent.media` 包只导出子模块，`strip_image_for_history` 实际定义在 `agent.media.images`；接口和 Run 收尾按不存在的包级导出导入该函数。现已统一改为从 `agent.media.images` 导入，并将 canonical history 写入点改为经 `media.images` 调用。定向测试随后仍为 **63 项通过**。

修复同步后重启后台服务，健康检查返回 200；对同一真实会话再次调用消息接口成功，响应 **708,181 字节**，包含 28 条正文消息和 216 条时间线事件。服务日志中该接口最近的 500 均早于最终重启时间。

## 后续空间

新产生的会话展示时间线不会再累积媒体帧副本。历史记录的响应已即时压缩，但旧媒体数据仍占用数据库空间并增加服务端读取/解码成本。若后续需要继续降低约 2.3 秒的服务端处理时间和历史数据库占用，可单独评估分批清理既有展示时间线；这需要独立的数据变更方案和可回滚验证，不包含在本次改动中。
