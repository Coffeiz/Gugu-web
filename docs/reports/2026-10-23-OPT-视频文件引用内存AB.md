# OPT：视频文件引用内存 A/B

> 日期：2026-10-23。环境：devserver 隔离子进程。未调用真实模型、数据库或用户文件；未修改运行配置。

## 方法

运行 `backend/scripts/diagnostics/compare_video_transport_memory.py --rounds 3`，每组采用全新 Python 子进程，交替执行旧内联与新文件引用路径。样本是 ffmpeg 生成的一秒红色视频，通过合法 MP4 free box 扩充至 40 / 44 MiB，并经 ffprobe 验证。每轮自动清理临时目录。父进程监控 RSS，超过 768 MiB 或 60 秒终止子进程；本轮最终对照均未触发。

旧路径使用生产 `prepare_video_media`、原 45 MiB 内联阈值，保留全部媒体后执行 canonical digest 和 JSON 编码。新路径使用生产 `prepare_video_path`、真实 HTTPX multipart 编码，通过合成 `AsyncBaseTransport` 消费上传流并返回合成 file_id，再执行相同摘要及 JSON 编码。三组分别保留 1 / 2 / 4 项媒体，新路径以 gather 发起并行准备；旧路径沿用同步编码、顺序准备。

不使用 HTTPX MockTransport：其实现会预先聚合请求体，测出的整包内存和大块读取属于测试替身，而非真实网络传输。最终对照的合成接收器逐块消费，最大上传块均为 65,536 字节。

## 结果

下表为三轮子进程峰值 RSS 的中位数；包含解释器与依赖基线，不是整台服务器或 Worker 的峰值。

| 场景 | 旧内联 MiB | 文件引用 MiB | 降幅 | 模型/trace JSON 字节：旧 → 新 |
| --- | ---: | ---: | ---: | --- |
| 单个 40 MiB | 209.66 | 50.59 | 75.9% | 55,924,170 → 133 |
| 40 + 44 MiB | 385.67 | 50.88 | 86.8% | 117,440,699 → 221 |
| 四段，共 168 MiB | 721.63 | 50.98 | 92.9% | 234,881,353 → 397 |

上传字节仍约等于原文件体积加 multipart 开销，不是“视频没有发送”。相同原件不转码、不降分辨率。独立传输测试验证文件正文完整、最大 64 KiB 数据块，以及源文件未被修改；摘要回归验证 Unicode、转义和媒体引用的 canonical JSON 摘要不变。

单项新路径约 0.12–0.23 秒，两段约 0.16–0.22 秒，四段约 0.19–0.39 秒。这是本地合成接收器与编码耗时，不含网络、上传服务排队和视频理解，不能作为真实用户响应速度的承诺。旧路径还验证了 Base64 解码后原件哈希，故不拿两侧耗时差异作为纯序列化性能结论。

## 边界与未完成项

- 已验证大视频文件引用对本地内存和载荷体积的改善，未做真实 Provider 视频理解 A/B；不声称模型总结质量或缓存率改善。
- 不复现 OOM 或主动压垮在线 Worker；不能据此断言历史 OOM 的唯一分配位置。
- 内存预算仅覆盖媒体准备阶段，不限制整个 run 的所有 retained context、SDK 或 trace 对象。
- 引用缓存按用户、模型配置身份和内容哈希隔离，六小时固定有效期，命中不续期；源文件变化时拒绝并不缓存。未新增远端文件主动回收，Provider 留存行为沿用既有 Files API；需要单独评估生命周期管理。
- LoopScope 本轮保留完整正文，只将快照编码移出事件循环。文件引用避免了此次大视频 Base64 膨胀，但尚未实现通用 artifact 存储及 span 增量协议，其他来源的大快照仍可能超过 Collector 上限。

## 契约变更

MiniMax M3 的内联阈值从 45 MiB 调为 4 MiB，是传输策略变化，512 MB 源文件与 1800 秒时长能力不变。此前优先内联以避免远端留存的取舍，现因长视频内存故障调整；源文件将上传到既有 Files API，缓存仅减少重复上传，不改变 Provider 侧的文件留存政策。
