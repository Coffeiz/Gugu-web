# IM-17 v3.0.5 注意力算法本地合成压力测试

**日期：** 2026-10-31
**范围：** ASK/CAP/TOPIC 评分及开发评分 API 的本地计算耗时与并发行为。
**结论边界：** 仅为合成输入、本地回环 HTTP 测量；不代表 devserver、真实群聊消息体分布或完整 IM/Agent 请求链路。

## 测量方法

- 使用隔离的 FastAPI 应用，只挂载 `/dev/attention` 路由；当前用户依赖使用合成对象，不连接数据库、Redis、IM 平台、模型或外部服务。
- 端到端样本通过本地 HTTP 请求评分 API，计时包括 HTTP、请求校验、合成快照构建、生产注意力决策器和响应序列化。
- 单场景每项 8 次预热、80 次计时；并发负载每种配置发送 240 个请求。并发混合负载在六种输入间均匀抽样：短问句、句号弱问句、CAP 请求、约 3600 字 ASK、约 12000 字多子句正文、11 候选 TOPIC。
- 并发矩阵为 1/2/4 个 Uvicorn worker，客户端并发 1/8/32/64。关闭访问日志。所有正文均为合成内容。
- 使用 cProfile 对 20k 文本和 11 候选长 TOPIC 各重复 120 次，仅用于定位函数占比；剖析器会显著放大绝对耗时，因此不与 HTTP 延迟表直接比较。

## 热点剖析

### 20k 正文

在受剖析的 120 次评分中，累计耗时约 61.3 秒：

- `_capability_action_evidence` 累计约 45.7 秒（约 75%）。
- 其中 `_capability_request_unit` 累计约 43.4 秒；`_lexicon_spans` 累计约 37.7 秒。
- `_scene_score_details` 累计约 15.3 秒。

输入包含约 4000 个短子句。当前 CAP 路径逐子句匹配动作词与能力名词，重复运行词项正则，是长文性能的首要热点。

### 长 TOPIC 窗口

在受剖析的 120 次评分中，累计耗时约 19.5 秒：

- `_topic_evidence` 累计约 8.6 秒（约 44%）。
- `_capability_action_evidence` 累计约 8.0 秒（约 41%）。
- `_edit_similarity` 累计约 6.1 秒；其中 `_levenshtein` 累计约 5.4 秒。

TOPIC 的编辑相似度有候选数和片段长度上限，但在较长文本及 11 个候选窗口下仍是主要计算项之一。

## 容量判断

- 常见短消息评分在本地端到端 P95 约 3 毫秒；常规短请求开销很低。
- 长消息成本随正文长度和子句数增长明显。20k 字 API 上限正文的中位数约 161 毫秒，单 worker 下长请求会阻塞同一事件循环中的其他评分请求。
- 对本次等比例混合负载，1 worker 在并发 8 到 64 时吞吐约 50–57 req/s，但 P95 从约 285 毫秒上升到约 1.39 秒。4 workers 在并发 8/32 达到约 189–191 req/s；并发 64 时降至约 135 req/s，P95 约 682 毫秒。
- 本次 64 并发没有 HTTP 错误，但延迟已明显排队；这不是系统最大并发上限测试，也不能据此给生产容量承诺。

## 下一步建议

先优化 CAP 长文扫描：按子句预检是否含有任一能力对象/动作词，或改为一次性扫描后按字符区间归属到子句，避免每个子句遍历整个词典。再用同一 20k/12k HTTP 场景复测。

然后单独评估 TOPIC 编辑相似度：当前窗口规模固定为 11，进一步优化应针对 `_edit_similarity` 的锚点对和 Levenshtein 调用数，不能放宽既有匹配语义。优化前后复用本报告的场景、输入和并发矩阵，并重新跑注意力回归测试。
