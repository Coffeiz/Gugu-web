# LLM-29 历史工具签名恢复：真实缓存 A/B 验证

## 结论

LLM-29 的数据库历史恢复路径遗漏了工具调用 ID，导致加密续接状态中的历史 thinking/signature 被过滤。下一 run 的实际 Anthropic 请求缺少这些块，历史缓存前缀发生变化。修复工具 ID 的读取路径后，两次真实调用 A/B 均保留上一请求的完整缓存读取量。

缓存比例下降本身不是断点证据：下一请求新增上一轮最终回复、思考和用户问题，分母增大时，即使缓存读取 token 数不变，比例也会下降。

## 原始 trace 调查

来源为用户提供的 2026-10-01T18-41-40-015Z 导出，四个 run 均使用 MiniMax 的 Anthropic 接口。以下比较上一 run 最后 round 与下一 run round1：

| 相邻 run | 上轮 input / cache_read | 下轮 input / cache_read | 上轮比例 → 下轮比例 |
| --- | --- | --- | --- |
| 1 → 2 | 33,418 / 32,960 | 33,665 / 31,337 | 98.63% → 93.08% |
| 2 → 3 | 33,665 / 31,337 | 33,919 / 33,663 | 93.08% → 99.25% |
| 3 → 4 | 51,224 / 38,243 | 52,353 / 33,881 | 74.66% → 64.72% |

system 文本相同；逻辑消息面板中的历史前缀相同，但 `assembly.cache.actual_request` 的 SDK 请求结构显示历史签名块减少。第一个边界丢失索引 5 的 assistant 签名工具轮；第三个边界丢失索引 19、26 的历史工具轮，仅保留新增的末尾思考块。本文请求索引均从 0 开始。

devserver 只读检查中，历史数据有 5 个工具调用 ID，旧读取器识别为 0，修复后的实际投影识别为 5。当前持久续接状态已经只剩末尾思考块，无法从该状态恢复已经丢失的旧签名。

## 根因与修复边界

`_anthropic_history_tool_use_ids` 直接扫描 Area entry 的 `content`。实时 entry 的内容位于该字段，但数据库恢复的 row envelope 将工具块放在 `content_json`；读取器因此返回空集合。随后 `restore_provider_state` 将全部历史工具签名过滤掉，且这一结果会再次持久化。

修复改为扫描 `render_provider_history(messages, adapter)` 的实际请求投影，统一实时和恢复路径，也避免恢复已裁剪的孤立工具调用。签名仍只存在于加密续接状态和出站请求，不写回 canonical Area 或普通消息数据库。

## 真实 A/B 方法

在 devserver 使用该会话的 BYOK 配置，临时限制输出预算，不更改运行配置。使用导出中的原始 system、快照和初始上下文，生成一个真实签名工具轮，执行只读 `get_tool_schema`，随后模拟中性消息的 SQLite 持久化与恢复，再发送下一轮问题。

每个实验组使用独立、等长的 system 标识隔离供应商缓存；新旧组共用同一真实工具轮。先重复上一请求使其充分命中，再比较下一 round1。旧组只在探针进程内复现原 content 扫描逻辑，新组调用修复后的驱动。后续请求禁止调用业务工具，无生产消息或项目写入。

| 试验 | 恢复路径 | 上轮 cache_read / fresh | 下轮 cache_read / fresh | 下轮比例 | 历史前缀首个差异 |
| --- | --- | --- | --- | --- | --- |
| 1 | 旧代码 | 33,189 / 2 | 31,464 / 3,304 | 90.50% | 索引 5 |
| 1 | 修复后 | 33,189 / 2 | 33,189 / 1,679 | 95.18% | 无 |
| 2 | 旧代码 | 33,188 / 2 | 31,463 / 2,719 | 92.05% | 索引 5 |
| 2 | 修复后 | 33,191 / 2 | 33,191 / 1,396 | 95.96% | 无 |

修复组恢复 1 个历史签名工具轮，旧组为 0。最终回复由供应商生成，长度可能不同，因此不把总输入和 fresh 的组间差异单独归因于修复；确定性证据是历史请求块一致性、签名保留和 cache_read 保持。

原始导出不包含全部原始签名字节，当前数据库续接状态也已被覆盖。因此这不是历史故障请求的逐字节重放，而是复用真实上下文、真实供应商和真实签名工具轮的路径复现。自适应思考未产出签名工具轮的种子尝试被排除，不用于结论。

## 回归验证与清理

新增数据库持久化 → Area 恢复 → 驱动 prepare → SDK 请求回归测试，检查两个历史签名工具轮完整保留、孤立状态被排除、canonical 消息不被修改。旧读取器下测试失败，修复后通过。

devserver 上 10 个相关测试文件共 203 项通过；语法、ownership 和 destructive confirm 守卫通过。临时真实调用探针验证后删除，不保留原始聊天、签名、凭据或生产配置副本。
