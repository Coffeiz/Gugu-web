# 连续历史 baseline 与缓存对照

## 背景与修改

真实 QQ 群会话的历史 baseline 为 0，原共享加载器仍按最近 100 条读取；有 baseline 时也会按最近 500 条截取。窗口向前滚动后，历史开头变化，后续消息不能继续复用同一缓存前缀。Web、IM 和反思调用同一加载器，默认统一读取有效 baseline 之后的全部连续历史，压缩仍由现有流程推进水位。显式条数上限保留给诊断脚本构造受限样本。

跨平台物理保留目标仍为 2000 条；超过目标时只删除摘要已覆盖的旧消息，并保留摘要、未覆盖消息与待处理消息。尚未摘要时会暂时超过保留目标。

## 合成输入的真实模型对照

在 devserver 使用 `scripts/diagnostics/compare_cache_strategies.py --allow-real-llm --compaction-ab --session-id <测试会话>`，通过测试会话选择 MiniMax-M3.1-Flash 模型配置。脚本使用 36 条合成消息，不读取会话正文；请求未写业务消息。

| 请求 | 总输入 token | cache read | 缓存读取率 |
| --- | ---: | ---: | ---: |
| 原始历史预热 | 58,133 | 184 | 0.32% |
| 删除历史开头后重放 | 38,825 | 184 | 0.47% |
| 保留原始历史重放 | 58,133 | 58,131 | 100% |

此实验比较截去历史开头和保留同一历史，并非真实会话修改前后的 A/B，不能据此保证线上命中率；用量来自 provider 返回。脚本的 `usage_recorded=false`，结果没有写入 LoopScope。

## 验证和限制

- devserver 串行运行历史加载、摘要水位、反思、IM 提前落库、消息保留和 run 收尾回归，共 70 项通过。
- 一次只读检查中真实群会话有约 1,290 条未压缩历史，正文约 18.5 万 token 是本地估算，模型配置上下文上限为 25.6 万 token。完整请求还包含系统提示、工具和其他上下文；实际大小以 provider usage 为准，可能触发现有压缩或超窗恢复。
- 修改已同步到 devserver 文件，调查时运行中的进程仍显示旧的 100 条历史。需要进程加载新代码后的真实 run 才能通过 LoopScope 验证实际历史条数和缓存率；本次不将合成对照当作线上验证。

## 同日完整历史隔离复测

服务加载新代码后，使用真实群会话的持久化历史和系统提示，在独立追加分支中连续请求两次 MiniMax-M3.1-Flash；不执行业务工具，不写入会话消息。加载器读取 1,322 条历史，baseline 为 0，投影后为 1,800 条消息。两次请求的工具声明为 4 个，与真实主 run 的工具集合不完全一致。

| 请求 | 总输入 token | cache read | 缓存读取率 | 模型调用耗时 |
| --- | ---: | ---: | ---: | ---: |
| 首次请求 | 195,207 | 184 | 0.09% | 8.98 秒 |
| 尾部追加后请求 | 195,224 | 195,207 | 99.99% | 1.68 秒 |

移除缓存标记后，两次实际请求的消息共同前缀为第一轮全部 1,801 条消息。另一次只读本地测量中，历史加载 0.31 秒、canonical 恢复 0.09 秒、provider 投影 0.91 秒、角色转换 0.04 秒，总计包含配置读取为 1.83 秒；这些数字是单次测量，不代表线上延迟分布。

第一次回放曾直接把内部 `time-context` 块传给 provider，返回 400；改用正式 Area 投影后两次请求成功。隔离回放没有产生真实聊天 run，LoopScope 中仍缺少更新后的群聊主链路记录，因此这些结果不证明真实群聊的缓存率已经达到同一水平。
