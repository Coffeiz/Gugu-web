# docs/reports

一次性排查/测试报告的存放目录：验证某个第三方能力的边界（如 `TEST`）、定位某个线上问题的根因（如 `OPS`）。跟 `docs/devlog` 的区别是——devlog 记的是"改了什么、为什么改"，这里记的是"测/查出了什么结论"，本身不一定对应一次代码改动。

## 命名

`<YYYY-MM-DD>-<TYPE>-<NAME>.md`，日期置于最前，报告类型居中，主题名称置于最后；`<NAME>` 使用简短的英文或中文均可，单词之间使用连字符。

已用过的 `TYPE`：

| TYPE | 用途 |
|---|---|
| `TEST` | 某个模型/API 能力边界的验证测试（如传输模式、参数限制） |
| `OPS` | 线上环境（服务/中间件/第三方依赖）问题的排查报告 |
| `OPT` | 性能、缓存或实现策略优化记录 |
| `INVEST` | 问题调查与根因分析 |
| `AUDIT` | 代码、架构或文案审计 |
| `VERIFY` | 阶段验收或迁移验证 |
| `TRACK` | 阶段执行台账或迁移清单 |

新增分类时如果已有的都不贴切，直接起一个新的大写单词即可，并补充这张表。

## 文件头格式

参考现有文件，开头统一是标题 + 一段引用块的元信息，字段按报告类型选取（不是所有字段都必填）：

```markdown
# <TYPE>：<标题>

> 测试/排查日期：YYYY-MM-DD
> 测试/排查环境：...
> 测试/排查对象：...
> 测试/排查目的：...

---

## 1. ...
```

正文结构不强制统一模板，但建议至少包含「现象/过程」和「结论」两块——报告的价值主要在结论，过程是为了让结论可信、可复现。

## 测试脚本可追溯性

凡是由脚本生成或复现的测试报告，必须包含独立的「测试脚本」小节，并明确写出：

- 使用脚本的仓库相对路径，并用 Markdown 链接指向脚本文件，例如 [`test_full_schema_compact_ab.py`](../../backend/scripts/diagnostics/test_full_schema_compact_ab.py)；
- 实际运行命令，以及必要的危险开关（如 `--allow-real-llm`）；
- 原始脱敏结果的保存位置；结果在 devserver 临时目录时，同时写明临时路径和是否已清理；
- 测试是否连接真实 provider、真实数据库或真实用户数据，以及数据写入是否被拦截。

脚本路径、命令和结果位置必须与报告对应的提交版本一致。报告不得写入密钥、Token、用户正文、附件名或真实用户标识；只能引用脱敏统计和结构化错误摘要。
