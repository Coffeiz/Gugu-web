# DeepSeek 与 MiniMax-M3 20 轮上下文缓存测试报告

## 1. 测试结论

本次使用 devserver 的真实预设和真实 session，分别连续运行 20 个 run，每个 run 只执行 1 次模型调用。两组测试均完成 20/20，没有 provider 请求失败。

| 模型 | 平均缓存率 | 最低 | 最高 | 输入 Token | 缓存命中 Token | 新鲜输入 Token | 输出 Token | 总耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| MiniMax-M3 | 93.25% | 0.00% | 98.67% | 303,048 | 283,136 | 19,912 | 479 | 53.73s |
| DeepSeek-v4-flash-vision-exp | 67.08% | 0.00% | 78.04% | 328,373 | 221,184 | 107,189 | 3,388 | 43.44s |

首轮出现 `0%` 是缓存建立阶段，不能直接视为异常。MiniMax 从第 2 轮开始稳定在 97% 以上；DeepSeek 从第 3 轮开始固定命中 12,032 Token，但随着工具历史增长，缓存率逐步下降。

## 2. 测试条件

- 测试环境：devserver
- 测试 session：真实 session，脱敏诊断模式
- 测试 run 数：每个模型 20 个 run
- 每个 run：1 个 provider round
- 工具：`call_tool`、`use_skill`、`ask_user` 的脱敏 schema
- 工具执行：关闭真实 dispatch，仅记录模型是否产生 tool call，并追加脱敏 tool result
- 历史：最多读取 20 条历史消息
- 记录字段：输入 Token、缓存命中 Token、新鲜输入 Token、输出 Token、缓存率、耗时、工具调用名称和首次差异位置
- 未记录：提示词正文、用户消息、工具参数、附件名、密钥

缓存率计算方式：

```text
cache_ratio = cache_read_tokens / input_tokens * 100
```

### DeepSeek 观察

- Run 1 是首次建立缓存。
- Run 2 只命中 4,608 Token，说明首个跨 run 的缓存边界仍然受到工具历史/请求结构影响。
- Run 3 开始固定命中 12,032 Token，但这个断点没有继续向后移动。
- 随着输入从 15,417 增长到 17,667，缓存保持 12,032 不变，因此缓存率从 78.04% 降到 68.10%。
- 20 轮中有 7 轮产生工具调用，主要为 `call_tool` 和 `use_skill`；工具历史增长与固定断点高度相关。

## 5. 对比分析

### 5.1 MiniMax-M3

MiniMax 的缓存边界可以随稳定历史增长。当前策略对它的行为是：

```text
system / snapshot
    -> 稳定历史
        -> 最新历史缓存锚点
            -> 当前动态尾部
```

因此新鲜输入基本控制在每轮新增内容和少量请求开销，20 轮平均缓存率达到 93.25%。排除首轮建立缓存后，Run 2-20 平均约为 97.97%。

### 5.2 DeepSeek

DeepSeek 当前仍使用多历史锚点策略。测试显示它能够命中早期锚点，但没有把缓存断点推进到最新工具历史之后：

```text
Run 2: 4,608
Run 3-20: 12,032（固定）
```

这说明 DeepSeek 的 provider 缓存并非不可用，而是当前多锚点策略在出现工具调用后只稳定复用了较早的前缀。后续新增工具调用全部落在新鲜输入区，所以输入越长，百分比越低。

## 6. 当前结论

1. MiniMax-M3 的跨 run 缓存已经达到稳定可用水平，20 轮平均 93.25%，非首轮平均约 97.97%。
2. DeepSeek 的首个稳定缓存前缀已经建立，但工具历史之后的缓存锚点没有持续向后移动，20 轮平均 67.08%。
3. 两个模型均完成 20/20，没有 BadRequest、超时或工具历史格式错误。
4. 本轮数据不能说明 DeepSeek 的模型缓存能力不足，更像是 provider 对多显式锚点/工具历史边界的处理差异。
5. MiniMax 的单锚点策略不应直接复制到 DeepSeek；需要单独做 DeepSeek 的锚点 A/B 测试，比较“保留历史锚点”和“仅保留最新锚点”。

## 7. 后续建议

### P0：DeepSeek 单独做缓存锚点 A/B

使用同一个真实 session，分别测试：

- 当前多锚点策略；
- 只保留最新稳定历史锚点；
- 只保留历史尾锚点，不设置 system 前锚点。

每种策略至少 5 个 run，并记录首个断点、工具历史数量和缓存命中量。

### P1：把缓存断点诊断提升为结构字段

LoopScope 只记录脱敏字段：

- `provider`
- `anchor_count`
- `anchor_indices`
- `stable_prefix_message_count`
- `volatile_image_first_index`
- `tool_history_count`
- `first_diff_index`

不要记录消息正文、工具参数或附件内容。

### P2：报告统计区分建立阶段与稳定阶段

后续报告同时给出：

- 全部 run 平均缓存率；
- 排除首轮后的稳定平均缓存率；
- 固定缓存 Token 数；
- 随历史增长的缓存增量。

这样不会把首轮缓存建立阶段的 `0%` 与后续 provider 行为混在一起。
