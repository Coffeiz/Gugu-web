## 结论与后续

1. 这次 A/B 使用了真实完整对话上下文，不是仅由 memory 字段拼出的合成 payload；两侧每个配对 round 的候选字符数完全一致。
2. `ContextBranch` 没有改变真实候选的消息顺序或内容边界；输出更完整，但 provider 调用时延尚需单独做多次重复基准。
3. 本报告不能宣称新旧单次调用 cache 命中率相同或不同。要比较 cache，下一步应让 branch runner 返回并记录同一 provider response 的 `usage.cache_read_input_tokens`，同时固定请求前缀并重复多轮。
4. 旧策略并非接收完整最终 provider input，而是接收可压缩 history 候选；本次已按这一真实边界重放，避免把 system、动态尾部和工具 schema误当作压缩正文。

## Cache A/B 补测（2026-08-28）

为补齐上项，使用同一真实 trace `eb8246189476` 的连续 3 个 round，在 devserver 上分别按旧路径和 `ContextBranch` 路径发起 provider 请求，并直接读取 Anthropic usage。两侧请求的 system、历史消息和 provider 参数完全一致；每组均在同一测试进程中连续运行，避免把首次冷启动误判为缓存差异。

| 分支 | round 数 | fresh input | cache_read | 总输入 | 综合命中率 |
|---|---:|---:|---:|---:|---:|
| 旧路径 | 3 | 3 | 35,520 | 35,523 | 99.99% |
| ContextBranch | 3 | 3 | 35,520 | 35,523 | 99.99% |

逐轮结果（两侧完全相同）：r1 `1 + 7,545`、r2 `1 + 10,912`、r3 `1 + 17,063`（fresh + cache_read）。`cache_write` 均为 0。

结论：在这组真实 provider 重放中，ContextBranch 没有造成前缀断裂，cache_read 与旧路径一致。该结果只证明请求边界的缓存等价，不代表所有动态注入场景都稳定命中；仍需在真实线上连续 run 中观察不同 session、provider 和动态尾部变化。
