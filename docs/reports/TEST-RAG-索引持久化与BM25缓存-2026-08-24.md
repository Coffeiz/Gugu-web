# RAG 索引持久化与 BM25 缓存测试报告

> 日期：2026-08-24
> 环境：devserver
> 数据：单个测试账号的聚合索引数据；本文不记录账号标识、正文、文件名或查询原文。

## 1. 测试目的

验证统一知识索引的以下链路：

- 数据库 chunk 是否已经持久化；
- ILIKE 与 BM25 的公平性能差异；
- BM25 首次加载、构建和热查询成本；
- 进程内缓存是否按用户和来源隔离；
- 索引版本变化后缓存是否失效；
- 增量 upsert 和 stale chunk 清理是否正常。

## 2. 索引规模

全量重建结果：

| 来源 | chunk 数 |
| --- | ---: |
| memory | 870 |
| project | 58 |
| file | 209 |
| note | 59 |
| canvas | 118 |
| calendar | 15 |
| scheduled_task | 4 |
| conversation | 2,730 |
| **合计** | **4,063** |

公平 ILIKE/BM25 对照使用共同支持的四类来源：`project`、`file`、`note`、`conversation`，共 3,056 个 chunk。

## 3. ILIKE 与 BM25 对照

测试条件：同一 owner、同一数据库、同一来源集合、同一查询集合，重复查询 10 次；ILIKE 统计数据库查询，BM25 统计已构建索引后的热查询。

| 查询类别 | ILIKE 中位数 | ILIKE P95 | BM25 热查询中位数 | BM25 热查询 P95 | Top 10 重叠率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 查询 A | 34.85ms | 40.09ms | 2.83ms | 3.87ms | 100% |
| 查询 B | 36.16ms | 47.56ms | 3.12ms | 7.05ms | 100% |
| 查询 C | 34.80ms | 37.10ms | 2.14ms | 2.32ms | 100% |

结论：

- BM25 热查询约比 ILIKE 快一个数量级；
- 三组测试的 BM25 Top 10 都落在 ILIKE 命中集合内；
- 不能把冷加载和首次构建时间混入热查询结论；
- Global Search 仍默认保留 ILIKE，BM25 只作为实验路径。

## 4. 冷启动与内存

### 4.1 无 tracemalloc 的运行时测量

| 阶段 | 结果 |
| --- | ---: |
| 加载 3,056 个 chunk | 312.67ms |
| 构建 BM25 | 189.31ms |
| 热查询中位数 | 3.16ms |
| 热查询 P95 | 5.64ms |
| 加载阶段 RSS 增量 | 20.30MB |
| BM25 构建额外 RSS 增量 | 29.12MB |

### 4.2 tracemalloc 辅助测量

| 指标 | 结果 |
| --- | ---: |
| BM25 构建额外 RSS 增量 | 71.85MB |
| Python 堆增量 | 约 30.09MB |
| Python 堆峰值 | 约 44.63MB |

`tracemalloc` 会改变运行时开销，因此 RSS 结果只作为辅助观察；缓存上限按无 tracemalloc 的实际进程测量制定，并保留安全余量。

## 5. 进程内缓存验证

在同一进程中连续执行 3 次 Project RAG：

| 指标 | 结果 |
| --- | ---: |
| 第一次查询 | 205.08ms |
| 后续热查询 | 13.87ms |
| 缓存条目 | 1 |
| 缓存 owner 数 | 1 |
| 估算缓存占用 | 0.50MB |

缓存键包含 owner、source 和 scope。不同用户不会复用同一 BM25 对象。

## 7. 当前限制

- Memory 的群组/群友 scope 仍使用原有 JSON 索引路径；
- 文件当前索引的是元数据，不代表已经完成文件正文抽取；
- Project 等业务数据的自动增量重建事件仍需继续接入；
- Global Search 尚未切换 BM25；
- 当前测试是单进程、单账号基线，不代表多 worker 高并发最终结果。

## 8. 结论与下一步

当前方案已经证明：持久化 chunk + 进程内 BM25 复用可以显著降低热查询延迟，但内存必须受控。

下一步：

1. 保持 Global Search 默认 ILIKE；
2. 继续完善来源更新事件和缓存失效；
3. 按 32MB 单用户、512MB 全局和 30 分钟空闲 TTL 运行；
4. Admin 增加实验性 BM25 切换后再做灰度质量对照；
5. 达到数据规模阈值后再评估 PostgreSQL 原生检索或 Rust/Tantivy。
