## 0. 一句话结论

**应用层的授权逻辑与数据处理是本项目的强项**——归属校验(`get_owned`)、错误脱敏、凭据加密、邀请注册、防枚举登录、JWT 算法固定,逐项核实均正确。

关于默认凭据(默认 admin 口令 / 默认 `secret_key`):经用户确认,**本仓库为本地开发环境,生产端 `ADMIN_PASSWORD` 与 `SECRET_KEY` 均已另行设置强值**——故原 C1/H1 在真实生产**不成立**,已降级为「运维守卫建议」(唯一残留价值=加个启动 fail-closed 守卫,防将来某次部署漏设)。

据此,**真正需要代码处理的高危集中在**:SSRF 重定向绕过(H3)、全站无限流(H2)、邀请码注册竞态(H4);其余为封禁 token/日志/头部卫生等纵深问题。

## 2. 已排除:默认凭据(C1/H1)

原审计报了两条 Critical/High——默认 admin 口令 `admin`/`admin123`(`config.py:159-160`)、默认 JWT `secret_key="change-me-in-production"`(`config.py:157`),因本地 `.env` 未设 `ADMIN_PASSWORD`(`SECRET_KEY` 则已设 64 字符自定义值)。

**经用户确认:本仓库为本地开发环境,生产端 `ADMIN_PASSWORD`、`SECRET_KEY` 均已另设强值。** 故二者在真实生产**不成立**,予以排除。

**唯一残留建议(低优先,可选)**:代码默认值为可预测弱值,且**无启动 fail-closed 守卫**——若将来某次新部署/迁移漏设,后果严重(默认 `secret_key` 可离线伪造 superadmin token,并经 HKDF 派生 IM 凭据加密密钥使静态加密失效,见 M5)。可考虑启动时检测默认/低熵值即拒绝启动,作为防呆网。非当前风险。

## 3. High

### H2 · 全站无任何限流
- **位置**:`app/main.py`(仅 CORS 中间件,无 slowapi/limiter);受影响端点:`admin_auth.py:67`(admin 登录)、`auth.py:67`(用户登录)、`auth.py:23`(注册/邀请码)、`auth.py:125`(重置)、feedback/track。
- **核实**:✅ 全仓无限流组件。admin 登录失败虽写审计日志但不阻断。
- **利用**:对 admin 登录在线爆破(叠加 C1 场景基本不需要);对用户登录撞库;对邀请码/重置 token 无限尝试(键空间大使猜解不现实,但尝试次数无界=资源滥用面)。
- **修复方向**:认证类端点上 per-IP + per-account 节流/锁定。允许放在 nginx/WAF 层,但需在部署文档中列为**必需项**。

### H3 · SSRF:重定向绕过 + DNS rebinding
- **位置**:`backend/agent/tools/files.py:983-995`(`_send_file_from_url`,`follow_redirects=True`)、`_url_is_safe`(`:925`);`backend/agent/tools/web.py:24-55`(`_host_allowed`+`_http_get`,`follow_redirects=False`)
- **核实**:✅ 两下载器的私网/回环/链路本地/云元数据(169.254.169.254)基础名单**完整**;但 `send_file` 图片下载 `follow_redirects=True` 而 `_url_is_safe` **只校验初始 URL**——公网可控页返回 `302 Location: http://169.254.169.254/…` 即绕过。`http_get` 已正确 `follow_redirects=False`,**两处不一致本身即坐实这是遗漏**。此外两者都是"先 getaddrinfo 校验→再交 httpx 用原 hostname 重新解析连接"(TOCTOU),存在 DNS rebinding 面。
- **利用**:agent 被 prompt 注入或用户诱导调用 `send_file(url=…)`,经一层 302 打云元数据 / 内网 Redis·DB。
- **修复方向**:图片下载同样关闭自动重定向(或每跳都过 `_url_is_safe`);解析一次拿 IP,校验通过后 **pin 该 IP 直连**、Host/SNI 保留域名;对解析到的所有 IP 一致校验。三处(含 C1 误报涉及的存储层)可共用一个集中式安全取数封装。

### H4 · 邀请码注册竞态(TOCTOU)
- **位置**:`backend/app/api/v1/auth.py:26-54`
- **核实**:✅ 先 `select InviteCode` 查 `used_at is None`(:32),后置 `used_at=now`(:52)、`commit`(:54),中间**无 `SELECT … FOR UPDATE`、无带 `WHERE used_at IS NULL` 的原子 UPDATE**。`used_by` 每次为新 user.id 也不触发唯一约束冲突。
- **利用**:拿到一个有效邀请码,并发多发 `POST /auth/register`(不同用户名/邮箱、同 `invite_code`)→ 一码注册多号,绕过邀请码稀缺性。
- **修复方向**:查码时行锁;或"标记已用"改为原子 `UPDATE … WHERE used_at IS NULL RETURNING`,受影响行数为 0 则拒绝。

## 4. Medium

### M1 · 被封禁/已删用户的 JWT 在 SSE/流式端点仍有效
- **位置**:`app/core/security.py:56`(`get_current_user_id`,**不查 DB**)vs `:70/:86`(`get_current_user` 校验 `is_active`);token 有效期 7 天(`config.py:158`,`access_token_expire_minutes=10080`)
- **核实**:✅ `get_current_user` 每次校验 `is_active`,封号后 DB 型路由立即失效;但 `/live/stream`(`live.py`)与 `/agent/*` 流式用的是 JWT-only 的 `get_current_user_id`,不查 DB;全系统无 jti/blocklist/token_version。故封号或删号后,对方旧 token 在 SSE 上最长再用 7 天。
- **影响**:有限——仍只能拿自己 user_id 的数据,不越权到他人。
- **修复方向**:引入 token 版本号或 Redis 撤销表,`get_current_user_id` 至少校验一次撤销;或缩短 access token 有效期 + 上刷新 token。

### M2 · admin JWT 以 URL query 传给 Debug 日志 SSE
- **位置**:`backend/app/api/v1/admin_debug.py:105-112`(`token` 作 query 参数;前端 `EventSource('…?token=${admin_token}')`)
- **核实**:✅ 完整 admin JWT 落 nginx access log、浏览器历史、Referer;该端点还流式吐原始 `gugu.log`(含路径/UUID 的完整 traceback)。且端点内 `if token: _verify_admin_token(token)` 是**冗余/半死代码**——该 router 已由 `require_admin`(HTTPBearer `auto_error=True`)在 header 层强制鉴权,`if token` 不构成绕过,但也暴露设计矛盾:SSE 拿不到 header 却又被 header 网关强拦,**能否连通取决于 nginx/前端实际行为,值得实测一次**。
- **修复方向**:改用 fetch 流式 + Authorization 头(用户 live stream `stores/live.ts:8` 已是此做法,照抄),或发短时效一次性流票;去掉 query token 与半死的 `if token` 分支。

### M3 · 无安全响应头,参考部署为纯 HTTP
- **位置**:全仓无 CSP/HSTS/X-Frame-Options/X-Content-Type-Options(grep 为空);参考 nginx `docs/ops/DEPLOY.md:277` 仅 `listen 80`。
- **核实**:✅ 认证为 localStorage 里的纯 Bearer(无 cookie→CSRF 免疫),但 XSS 可窃取 token 且无 CSP 兜底;纯 HTTP 下 token 明文传输。
- **修复方向**:nginx/app 加安全头;强制 HTTPS+HSTS;考虑 CSP。

### M4 · 上传无大小上限、无类型白名单
- **位置**:`backend/app/api/v1/files.py:405`(`data = await file.read()` 一次性进内存);唯一限制是存储配额,而 `quota.default_storage_limit_bytes` 默认可能为 `None`=无限(`:409`)。
- **核实**:✅ 无 MIME/扩展名白名单,任意类型可传;大文件或并发大上传可打爆内存。
- **修复方向**:流式落盘 + 读取前查 `Content-Length` 并累计截断的硬字节上限;可读/可转码类型加白名单。

### M5 · `secret_key` 同时派生 IM 凭据加密密钥且可运行时覆盖
- **位置**:`config.py:157` + `backend/app/core/crypto.py:27`(AES 密钥经 HKDF 从 `secret_key` 派生);`config.py:269-273`(`secret_key` 作顶层可 override 字段)
- **核实**:✅ 为 JWT 卫生轮换 `secret_key` 会**静默作废所有已存 app_secret**(`decrypt_secret` fail-open 返回密文,`crypto.py:57`);知道 `secret_key` 的 DB 读取方可解密全部 bot 凭据。
- **修复方向**:加密密钥与 JWT 密钥解耦;把 `secret_key` 移出运行时 override 面;版本化密钥 + 重加密。

- **I1** · `docker-compose.yml` PG 口令 `pm123` + Redis 无密码,端口发布到宿主——仅开发用,若照搬上线有风险。
- **I2** · 依赖用浮动 `>=` 无 lockfile,部署时解析不可复现(现装 fastapi 0.138 / Python-jose 3.5.0 / Pillow 12.2 / cryptography 49 均当前干净)。
- **I3(M6)** · `files.py:566` confirm_upload 的 `storage_key` 仅前缀校验不挡 `..`——当前受 OSS 后端限制(字面前缀,无真实 FS 穿越),仅硬化项;若后端切本地复用此模式则升级为 High。
- **I4** · `GET /auth/avatar/{user_id}` 无归属校验服务任意头像——经核实为**有意的公开资料图**,路径取自 DB 非请求,非漏洞。
- **I5** · `docs/ops/DEPLOY.md:235` 记 SearXNG `0.0.0.0 + limiter:false = 内网无认证可用`——需防火墙限制仅后端主机可达。

## 3. High

### H2 · 全站无任何限流
- **位置**:`app/main.py`(仅 CORS 中间件,无 slowapi/limiter);受影响端点:`admin_auth.py:67`(admin 登录)、`auth.py:67`(用户登录)、`auth.py:23`(注册/邀请码)、`auth.py:125`(重置)、feedback/track。
- **核实**:✅ 全仓无限流组件。admin 登录失败虽写审计日志但不阻断。
- **利用**:对 admin 登录在线爆破(叠加 C1 场景基本不需要);对用户登录撞库;对邀请码/重置 token 无限尝试(键空间大使猜解不现实,但尝试次数无界=资源滥用面)。
- **修复方向**:认证类端点上 per-IP + per-account 节流/锁定。允许放在 nginx/WAF 层,但需在部署文档中列为**必需项**。

### H3 · SSRF:重定向绕过 + DNS rebinding
- **位置**:`backend/agent/tools/files.py:983-995`(`_send_file_from_url`,`follow_redirects=True`)、`_url_is_safe`(`:925`);`backend/agent/tools/web.py:24-55`(`_host_allowed`+`_http_get`,`follow_redirects=False`)
- **核实**:✅ 两下载器的私网/回环/链路本地/云元数据(169.254.169.254)基础名单**完整**;但 `send_file` 图片下载 `follow_redirects=True` 而 `_url_is_safe` **只校验初始 URL**——公网可控页返回 `302 Location: http://169.254.169.254/…` 即绕过。`http_get` 已正确 `follow_redirects=False`,**两处不一致本身即坐实这是遗漏**。此外两者都是"先 getaddrinfo 校验→再交 httpx 用原 hostname 重新解析连接"(TOCTOU),存在 DNS rebinding 面。
- **利用**:agent 被 prompt 注入或用户诱导调用 `send_file(url=…)`,经一层 302 打云元数据 / 内网 Redis·DB。
- **修复方向**:图片下载同样关闭自动重定向(或每跳都过 `_url_is_safe`);解析一次拿 IP,校验通过后 **pin 该 IP 直连**、Host/SNI 保留域名;对解析到的所有 IP 一致校验。三处(含 C1 误报涉及的存储层)可共用一个集中式安全取数封装。

### H4 · 邀请码注册竞态(TOCTOU)
- **位置**:`backend/app/api/v1/auth.py:26-54`
- **核实**:✅ 先 `select InviteCode` 查 `used_at is None`(:32),后置 `used_at=now`(:52)、`commit`(:54),中间**无 `SELECT … FOR UPDATE`、无带 `WHERE used_at IS NULL` 的原子 UPDATE**。`used_by` 每次为新 user.id 也不触发唯一约束冲突。
- **利用**:拿到一个有效邀请码,并发多发 `POST /auth/register`(不同用户名/邮箱、同 `invite_code`)→ 一码注册多号,绕过邀请码稀缺性。
- **修复方向**:查码时行锁;或"标记已用"改为原子 `UPDATE … WHERE used_at IS NULL RETURNING`,受影响行数为 0 则拒绝。

## 4. Medium

### M1 · 被封禁/已删用户的 JWT 在 SSE/流式端点仍有效
- **位置**:`app/core/security.py:56`(`get_current_user_id`,**不查 DB**)vs `:70/:86`(`get_current_user` 校验 `is_active`);token 有效期 7 天(`config.py:158`,`access_token_expire_minutes=10080`)
- **核实**:✅ `get_current_user` 每次校验 `is_active`,封号后 DB 型路由立即失效;但 `/live/stream`(`live.py`)与 `/agent/*` 流式用的是 JWT-only 的 `get_current_user_id`,不查 DB;全系统无 jti/blocklist/token_version。故封号或删号后,对方旧 token 在 SSE 上最长再用 7 天。
- **影响**:有限——仍只能拿自己 user_id 的数据,不越权到他人。
- **修复方向**:引入 token 版本号或 Redis 撤销表,`get_current_user_id` 至少校验一次撤销;或缩短 access token 有效期 + 上刷新 token。

### M2 · admin JWT 以 URL query 传给 Debug 日志 SSE
- **位置**:`backend/app/api/v1/admin_debug.py:105-112`(`token` 作 query 参数;前端 `EventSource('…?token=${admin_token}')`)
- **核实**:✅ 完整 admin JWT 落 nginx access log、浏览器历史、Referer;该端点还流式吐原始 `gugu.log`(含路径/UUID 的完整 traceback)。且端点内 `if token: _verify_admin_token(token)` 是**冗余/半死代码**——该 router 已由 `require_admin`(HTTPBearer `auto_error=True`)在 header 层强制鉴权,`if token` 不构成绕过,但也暴露设计矛盾:SSE 拿不到 header 却又被 header 网关强拦,**能否连通取决于 nginx/前端实际行为,值得实测一次**。
- **修复方向**:改用 fetch 流式 + Authorization 头(用户 live stream `stores/live.ts:8` 已是此做法,照抄),或发短时效一次性流票;去掉 query token 与半死的 `if token` 分支。

### M3 · 无安全响应头,参考部署为纯 HTTP
- **位置**:全仓无 CSP/HSTS/X-Frame-Options/X-Content-Type-Options(grep 为空);参考 nginx `docs/ops/DEPLOY.md:277` 仅 `listen 80`。
- **核实**:✅ 认证为 localStorage 里的纯 Bearer(无 cookie→CSRF 免疫),但 XSS 可窃取 token 且无 CSP 兜底;纯 HTTP 下 token 明文传输。
- **修复方向**:nginx/app 加安全头;强制 HTTPS+HSTS;考虑 CSP。

### M4 · 上传无大小上限、无类型白名单
- **位置**:`backend/app/api/v1/files.py:405`(`data = await file.read()` 一次性进内存);唯一限制是存储配额,而 `quota.default_storage_limit_bytes` 默认可能为 `None`=无限(`:409`)。
- **核实**:✅ 无 MIME/扩展名白名单,任意类型可传;大文件或并发大上传可打爆内存。
- **修复方向**:流式落盘 + 读取前查 `Content-Length` 并累计截断的硬字节上限;可读/可转码类型加白名单。

### M5 · `secret_key` 同时派生 IM 凭据加密密钥且可运行时覆盖
- **位置**:`config.py:157` + `backend/app/core/crypto.py:27`(AES 密钥经 HKDF 从 `secret_key` 派生);`config.py:269-273`(`secret_key` 作顶层可 override 字段)
- **核实**:✅ 为 JWT 卫生轮换 `secret_key` 会**静默作废所有已存 app_secret**(`decrypt_secret` fail-open 返回密文,`crypto.py:57`);知道 `secret_key` 的 DB 读取方可解密全部 bot 凭据。
- **修复方向**:加密密钥与 JWT 密钥解耦;把 `secret_key` 移出运行时 override 面;版本化密钥 + 重加密。

## 7. 经核实确认到位的防御(本项目强项)

- **多租户越权:全覆盖**。`projects/files/folders/clients/events/trash/scheduled_tasks/user_bots/agent(会话)` 每个按 id 取资源处都走 `get_owned()`(强制 user_id 比对、不符记 `ownership.denied`)或显式 `.where(user_id==)`;批量端点亦带 `user_id==`;无漏网裸 `db.get`(agent 工具层 `search.py:130` 唯一裸 get 已标 `# ownership-exempt`);有 `scripts/check_ownership.py` 静态守卫。
- **文件 token 下载/流:归属正确**。`/files/{fid}/stream` 校验 `token_fid==fid` + `get_owned`,stream token 绑 `sub=user_id`+`role=stream` 强校验。
- **JWT alg 绕过不可行**:全部 `algorithms=["HS256"]`,jose 拒 `alg=none`,仅对称无混淆面;所有 token 强校验 `role`(user/stream/superadmin 不可互换)。
- **IM 身份解析不串号**:`worker._resolve_user` 只信 `owner_user_id`,该值由 gateway 从 bot 的 DB 归属注入 env,不来自入站消息。
- **IM 凭据 AES-256-GCM 加密存储**(随机 IV、HKDF 派生密钥、purpose label,`crypto.py`),迁移 `20260702000002` 回填历史明文,API 响应打码。
- **IM 凭据经 env 注入子进程**(非 argv,无 `ps aux` 泄露,`gateway.py:73-95`);OAuth 绑定 poll token 绑发起者 UID + 校验 `uid==current_user.id`,防劫持。
- **SQL 全参数化**:`admin_analytics.py`/`agent_perception.py`/`temperature.py` 的 `text()` 里 f-string 只插内部常量(`_DEV_NOT_IN`/`tz_expr` 等),用户值全走 `:param` 绑定或 `Query(ge/le)` 边界。**无 SQL 注入**。
- **命令注入无面**:LibreOffice/pdftotext/ffmpeg/ffprobe/pilk 全走参数数组(无 `shell=True`),临时文件名硬编码,转码参数来自 `_CONVERT_SPEC`/`_DOC_MIME` 白名单。
- **无危险反序列化/模板**:全仓无 `eval/exec/pickle/yaml.load(非safe)/os.system`,无 Jinja `from_string`。
- **destructive 工具确认门**:`scripts/check_confirm_gate.py`(AST 强制)+ `base.py:280` dispatch 运行时绊线(无 confirm 返回成功→CRITICAL 日志 + `record_security`),prompt 注入无法绕过物理删除门;删除多为软删(回收站 30 天可还原)。
- **工具错误脱敏真挂上**:`base.py` 在唯一 chokepoint `registry.dispatch` 抹连接串/密钥/路径/UUID/traceback(顶层 `error` 字段);`agent.traj` 所有字符串参数打 `***`;感知遥测导出仅结构化枚举字段 + 8 字符用户前缀,writer 强制白名单。(L2 是其未覆盖的嵌套盲区。)
- **登录防枚举**:bcrypt+salt;登录/忘记密码恒定响应 + 60s 冷却;重置 token `secrets.token_urlsafe(32)` 一次性+TTL;注册邀请码门控。
- **密钥不进 git**:`.env`/`config.override.json`/`uploads/`/`backend.zip` 均 gitignore 且历史干净;`.env.example` 全占位;后端/前端/docs 无硬编码密钥。
- **CORS 组合安全**:`allow_origins` 是显式白名单(**非 `*`**)+ `allow_credentials=True`,是安全组合;无凭据泄露面。
- **uploads 不被静态直出**:`StaticFiles` 只 import 未 `.mount()`(全仓 `.mount(` 为空);文件下载走 `/files/{fid}/download` 经 `get_owned` 归属校验、fid 为 int、storage_key 取自 DB——无目录列表、无路径穿越、无跨用户读。

### 暂缓项(需更大改动或跨端,建议单独排期)
- **H3 剩余(DNS rebinding TOCTOU)**:彻底堵需在连接层 pin 已校验 IP,而 HTTPS 下 pin IP 会破坏 SNI/证书校验——收益/风险不划算。已修的是**被证实可利用的重定向路径**;rebinding 需攻击者控权威 DNS 且抢毫秒级双解析竞态,门槛高,列为可接受残留。
- **M1 token 撤销**:封禁/删号后 JWT 在 SSE 最长再用 7 天——需引入 token 版本号或 Redis 撤销表并改 `get_current_user_id`,影响面窄(只能拿自己数据)。
- **M2 admin SSE token 走 URL**:`EventSource` 不能设 header,改 header 认证需前端换 fetch 流式——跨端改动,单独做。
- **M5 加密密钥与 JWT 密钥解耦**:需迁移 + 重加密现存 app_secret,盲改有作废风险,单独排期。
- **L5 XFF 可伪造**:当前部署固定经 nginx(会覆写 XFF),改动反而会破坏真实 IP 记录;需配「可信代理」白名单再动。
