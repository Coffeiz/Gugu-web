## 2. P0 — Markdown 未消毒直出 `v-html`(XSS)✅ 实测确认 · 🛠️ 已修复(2026-07-10)

> **修复记录(2026-07-10)**:按下方方案落地并实测通过。
> - 引 `dompurify@^3.4.11`(唯一新增依赖);`markdown.ts` 建全站唯一安全出口 `sanitizeHtml`(marked → DOMPurify),`renderMarkdown` 经它;link renderer 加**协议白名单**(`http(s)/mailto/tel/#/相对`)+ `href`/`title` **属性转义**。
> - 所有 v-html sink 接入:`MarkdownView`(text **与** html 预渲染 prop 都消毒,覆盖通知 + GuguChat 聊天)、`TextViewer.mdHtml`、`Privacy`;`Admin/Notifications` 走 `renderMarkdown` 自动覆盖;Mind `NoteCard`(本就转义)未动。
> - 实测(jsdom + DOMPurify):`<img onerror>` / `<script>` / `<svg onload>` / `javascript:` 链接**全部中和**;hljs 高亮 span、代码块复制按钮+内联 SVG、`target=_blank rel=noopener` 链接**渲染无损**。vue-tsc 通过。
> - **回归已固化**(2026-07-11):Vitest 落地(见 §3),`src/utils/markdown.test.ts` 13 条断言钉死"危险载荷中和 + 正常渲染无损 + title 属性逃逸不产生真实元素"。跨用户升级路径(§9 待证实项)仍建议核实。

### 现状(核实)

- **全站无 HTML 消毒**:`dompurify` / `sanitize-html` 在依赖与源码里都搜不到。
- **marked v18 默认不消毒**:`sanitize` 选项自 marked v5 起已移除。本地事实:`<img src=x onerror=alert(1)>` 原样保留。
- **裸 `v-html` sink**:
  - [`MarkdownView.vue:2`](../../frontend/src/components/common/MarkdownView.vue:2) — `v-html="rendered"`,`rendered = renderMarkdown(text)`(裸 marked)或预渲染 `html`;喂入方:`AppSidebar.vue:131`(通知)、`NotificationBubble.vue:19`(通知)、`GuguChat.vue:203`(咕咕回复 `msg.html`/流式)。
  - [`TextViewer.vue:40`](../../frontend/src/components/common/viewers/TextViewer.vue:40) — `v-html="mdHtml"`,其独立 `new Marked()` **只对代码块 `escHtml`**,正文/内联 HTML 直出;喂入方:用户上传的 `.md/.txt` 文件正文。
  - `Privacy.vue:16`(静态隐私政策,低危)、`Admin/Notifications/index.vue:61`(管理员预览自己草稿,低危)。
- **`markdown.ts` link renderer 有额外注入面(GPT 未点出)**:[`markdown.ts`](../../frontend/src/utils/markdown.ts) 自定义 link 把 `href` **与** `title` 直接字符串插值、都不转义 —— 不仅 `javascript:` 协议能过,`title` 里 `"><img onerror=…>` 还能**属性逃逸**。
- **Mind 便签预览是安全的(GPT 说法属实)**:`NoteCard.vue:36` 走 `mdToPreviewHtml`,该函数用 `_ESC`(`& < > "` → 实体)**先转义再拼**,不受影响。

### 严重度校准(主审补充)

技术上确凿。本轮追到的**已证实**利用面是 **self-XSS**:用户把 `<img onerror>` 存进项目名/便签/文件正文,诱导咕咕回显(聊天 MarkdownView)或自己打开该 `.md`(TextViewer)→ 在**自己**浏览器执行。**跨用户/跨权限升级**(后台管理员用同一 marked 渲染用户内容而被弹、IM 群聊互相渲染、通知里嵌用户可控串)**本轮未证实**,是待查项而非已确认。**结论:优先级维持"先修",但影响面标注为"已证实 self-XSS + 跨用户待证实",不夸大为已确认的跨租户 Critical。**

### 修复方案

1. **引依赖**:`npm i dompurify` + `npm i -D @types/dompurify`(纯前端、无外部请求,符合仓库无新增外链原则)。
2. **收敛成单一安全出口**:在 [`markdown.ts`](../../frontend/src/utils/markdown.ts) 内把 `renderMarkdown` 改为 `marked.parse(...)` → `DOMPurify.sanitize(html, CONFIG)`,**所有** v-html 都必须经它。
   - `MarkdownView` 的 **`html` 预渲染 prop 也要 sanitize**——它来自服务端/流式,同样不可信,不能因为"已是 HTML"就跳过。
   - `TextViewer` 的 `mdHtml`、`Privacy` 的 `html`、`Admin/Notifications` 预览、`GuguChat` 的 `renderMdStream`/`msg.html` 全部改走同一 sanitizer。
   - Mind 的 `mdToPreviewHtml` 已安全,统一后可让它也复用同一出口(去掉手写 `_ESC` 的维护面),非必须。
3. **DOMPurify 配置**(建议):默认即禁 `on*` 事件属性与 `<script>`;额外 `FORBID_TAGS: ['style','iframe','object','embed','form']`;`ALLOWED_URI_REGEXP` 限 `href`/`src` 协议为 `http/https/mailto/tel/#/相对路径`;`ADD_ATTR:['target']` 保留新标签打开;确认 `class` 在白名单内(hljs 代码高亮产物依赖 `class` span,别被吃掉)。
4. **修 link renderer**:要么删掉自定义 renderer、让 DOMPurify 统一处理后用 `afterSanitizeAttributes` hook 给 `<a>` 补 `target=_blank rel=noopener`;要么保留但对 `href` 做协议白名单校验、`title` 走属性转义。**二选一,别再裸插值**。
5. **图片外链决策**:`<img>` 允许外链 src 会带来 SSRF 追踪像素/隐私泄露面,结合产品需要决定是否 `FORBID_TAGS` 含 `img` 或限制 `src` 协议(至少禁 `javascript:`/`data:` 非图片)。
6. **回归验收**(依赖 P1-a 的 Vitest 落地):断言 `<img src=x onerror=alert(1)>`、`<script>`、`[x](javascript:alert(1))`、`title="\"><img onerror=…>"` 经安全出口后**均被中和**;并确认正常 md(加粗/表格/代码高亮/链接新标签打开)不被误伤。

## 5. P1-c — 时间语义混用 naive UTC ✅ 实测确认

**现状**:后端 `datetime.utcnow()` **55 处**(GPT~54),业务路由直调(如 [`mind.py:74`](../../backend/app/api/v1/mind.py:74) `captured_at = body.captured_at or datetime.utcnow()`)。运行环境 **Python 3.14**(GPT 写的 3.12 有误,但弃用告警点成立——测试输出里持续刷 `utcnow() is deprecated`)。naive UTC 会持续制造"今天/未来日期"边界问题。

**修复方案**(策略,不是逐处替换的蛮力):
1. 立**统一时钟**:一个 `now_utc()` 工具返回 aware UTC(`datetime.now(timezone.utc)`),业务路由一律走它、不再直调 `utcnow()`。
2. 定**存储/展示分层**:存储一律 aware UTC;"展示"与"**日期归属**"(今天/本周/截止日属于哪天)按**用户时区**换算——这正是"今天/未来日期"边界 bug 的根因。
3. 先治**日期归属敏感点**(日历、思维记录 `captured_at`、提醒、留存统计窗口),再清扫其余 `utcnow()`。存量可分批,但**新代码即刻走统一时钟**,先止血。

## 7. P2-b — 异常处理过宽 ✅ 实测确认

**现状**:`except Exception`/裸 except **287 处**(与 GPT 的~287 分毫不差),在 Agent、适配器、文件、配置链路尤其密集。多数是合理的外部 I/O 防护,但缺统一约束,易把编程错误(AttributeError/KeyError)误报成普通失败、抬高排障成本。

**修复方案**:定一条**约束**而非逐处重写——
- **外部调用**(网络/文件/第三方 SDK/DB):可宽捕获,但**必须带结构化日志 + 错误类别**(便于运维分类,不吞编程错误);
- **领域逻辑**:只捕获**预期异常**类型,别裸 `except Exception`。
先把约束写进 CONTRIBUTING/agent 文档,新代码强制;存量按链路(先 Agent/适配器)分批收敛。可加一条轻量 lint/静态守卫抓"裸 except + 无日志"。
