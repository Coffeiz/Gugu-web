# 安全隐患：工具错误信息泄露 → 错误脱敏

> **性质**：信息泄露（information disclosure）类安全隐患 + 代码卫生问题。核心兜底机制**已实现并上线**（见第 6 节状态）。
> **以后写工具 / 改错误处理时务必注意**：别把原始异常串（含路径/UUID/连接串/密钥/traceback）透传给模型或用户。
> 相关：[[privacy.md]]、[[可靠性.md]]、[[gugu-privacy-redaction]]。

---

## 易读概述（面向不懂代码的读者）

**这个安全措施保护什么**：咕咕在执行工具（查文件、发消息、搜索等 60 多个功能）时，如果失败了，错误信息可能会不小心带出咕咕服务器内部的敏感细节——比如你的账户内部编号（UUID）、服务器上的文件存储路径、数据库连接地址、密钥等。这些细节本不该被用户看到，也不该被"喂"给正在回复你的 AI 模型（AI 可能会换种说法把它转述出来，导致同样的泄露）。

**大致怎么做到的**：咕咕给所有工具的"出错通道"装了一道统一的过滤网——不管是哪个工具、以什么方式出错，错误信息在被展示给你或喂给 AI 模型**之前**，都会先过一遍"消毒"处理：把里面看起来像文件路径、账户编号、数据库地址、密钥的片段自动替换成"‹已隐藏›"这样的占位符，同时把完整、未删减的原始错误记录到服务器自己的日志里（供开发者排查问题用，你和 AI 模型都看不到这份原始记录）。

**这层过滤网覆盖范围**：因为它挂在"所有工具执行"这个必经的统一出口上（而不是要求每个工具自己记得做一遍），所以新加的工具（比如这次会话新增的"查最近暂存的附件" `list_recent_attachments`、"发送文件" `send_file`）天然就享受同一套保护，不需要额外开发者手动接入。

**目前的局限**：这套过滤是"关键词/格式匹配"式的兜底网，不是从源头上让每个工具都说"干净"的业务话术（比如"移动失败，可能是权限问题"而不是甩出一整段系统错误）。这个更彻底的根治工作目前还在推进中（见第 6 节「状态」）。

## 专业细节

## 1. 触发与现象（2026-06-29）

咕咕在用户授权下移动文件到「咕咕开发参考」文件夹失败，把**原始 OS 异常**原样转述给了用户：

```
移动失败（物理文件可能已丢失）：
[Errno 13] Permission denied: 'uploads/019efd7c-0150-7671-9f3b-852ba1488bf1/个人文件'
```

这条里泄露了：① 内部存储布局（本地 `uploads/<user_uuid>/<空间>/…`）；② 用户 UUID；③ 内部 id / 空间名 / 工具名 / 错误码。

> 注：那个移动失败本身是**运维问题**——OS 层 `EACCES`，进程对 `uploads/<uuid>/个人文件` 目录无写权限（多半目录属主/mode 不对），**不是鉴权模型漏洞**。咕咕当时还自信推测「token 只有 read 权限」，**是错的**，会误导排查。本文档只谈"泄露"这一面，权限 bug 另修。

## 2. 根因：工具把原始异常串透传

`agent/tools/files.py` 多处 `return {"error": f"...{str(e)[:80]}"}`，个别甚至 `return {"error": str(e)}`（不截断）。原始 `str(e)` 含内部文件系统路径，经 `registry.dispatch` → tool_result → 模型 → 用户，一路原样传。

## 3. 风险评估

**直接危害：低**（这一例）。原因：
- `/uploads` **没有被静态托管**（全后端无 `.mount()`，`public_url()→/uploads/{key}` 无人消费）；
- 文件访问**全走鉴权 API**（`files.py` 每端点 `get_current_user` + 逐用户归属校验）；
- ∴ 访问控制靠"鉴权"而非"路径保密"，泄露路径/UUID **不能直接换来文件访问**；且这一例是给**文件主人本人**看。

**但这个"原始透传"模式本身不安全**，要修：
- **跨用户泄露隐患**：这次路径正好是本人的；若异常引用到的**不是当前用户**的路径/UUID（共享资源、错链、bug），原始透传会漏**别人**的 UUID/路径；
- **污染模型上下文 + 决策轨迹**：原始串进了模型上下文，模型可能换种说法再漏；决策轨迹本已脱敏，错误串得同源处理；
- **进日志/工单/用户外发**：带 UUID/路径的串会扩散到这些地方（提醒：把咕咕生成的报告外发前先抹 UUID/路径）；
- **若将来连接串/密钥/token 出现在异常里**（DB 连接失败、LLM 鉴权失败回显 key），同样会被原样透传——**这才是真正高危的那类**。

## 4. 设计：错误脱敏器（两层 + 出口兜底）

GPT 提过一个 `sanitize_error()`（抹 path/UUID/连接串/token/key/traceback）——方向对，但只是"网"。完整设计是**药 + 网 + 出口**三层：

**① 药（根治）**：工具按"自己在做什么"造**业务层**错误消息，原始异常**只 `log`/`print` 到服务端**（保留路径/traceback 供排查）。
- 用户看到的应是「移动到『咕咕开发参考』失败，可能是文件夹权限问题，要不要换种方式 / 去网页端」——**一个文件系统路径都不该露**（GPT 示例里还写着 `uploads/<user>/`，那仍在漏）。

**② 网（兜底）**：`sanitize_error()` 挂在 **`registry.dispatch`（所有工具执行的唯一咽喉）**，在 **tool_result 回给模型之前**统一脱敏——一处覆盖全部工具（核实于 2026-07-02：当前仓库共 60 个 `Tool` 实例，含本轮会话新增的 `list_recent_attachments`/`send_file`，二者错误分支同样经 `dispatch` 统一脱敏，未单独开洞），且保护模型上下文/轨迹。抹（正则见 `agent/tools/base.py` `_CONN_RE`/`_KEY_RE`/`_PATH_RE`/`_UUID_RE`/`_TB_RE`）：
- 绝对路径 **和相对 `uploads/…`**（不止 `/` 开头；同款覆盖 `.agent/`、`.thumbs/`、`.chat_staging/` 前缀）
- UUID（`[0-9a-f-]{32,36}` 形，标准 8-4-4-4-12 分段）
- DB 连接串（`postgresql://…` / `redis://…` / `mysql://…` / `mongodb://…`）
- token / api_key（`sk-` 前缀形 或 `api_key`/`token`/`secret`/`bearer` 等关键词跟随的长串；注意各家 key 格式不一，正则会漏，故只当兜底）
- traceback / 文件行号

**③ 出口（第三道）**：复用已有的 `agent/outbound.py` `sanitize_outbound` / `StreamSanitizer`（本就"拦系统提示词泄露"），最终发用户前再过一遍。

> 关键：**脱敏边界在 `dispatch`（给模型之前），不是 UI 层**——否则原始串已进模型上下文/轨迹。regex 是兜底网，真正的修是"工具造干净消息 + 原始只进日志"，两者都要。

## 5. 通用红线（以后写工具/错误处理记住）

- **绝不**把 `str(e)` / `repr(e)` / traceback 直接放进给用户或模型的字段；
- 用户/模型看到的错误 = **业务层描述**（在做什么、失败了、建议）；原始细节 → `print`/log；
- 异常里可能藏：**路径、UUID、连接串、API key、token、内部 id、host/port**——任一出现即按泄露处理；
- 新工具的 except 分支默认走统一脱敏（dispatch 级），别各自手拼 `f"...{e}"`。
