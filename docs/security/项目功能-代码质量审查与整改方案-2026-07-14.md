## 易读概述

项目功能的主要风险不在看板界面，而在保存链路。当前前端会在用户编辑项目时连续、并发地发出多个保存请求；后端虽然有版本号，却不是数据库原子比较更新，因此两个请求可能同时通过检查，造成字段互相覆盖。请求失败后，前端又可能继续展示没有成功保存的本地状态。阶段推进和待办自动完成又分散在 Store、项目弹窗、项目卡三处，咕咕项目工具还维护了另一套后端写入逻辑，后续很容易越改越不一致。

当前整改应先把保存并发与失败恢复做稳，收敛阶段状态机和网页/咕咕两套写模型，最后补齐数据校验、统计口径与实时刷新。项目文件路径、目录树恢复与存储迁移属于后续文件系统后端重构的边界，不在此文提出实现要求。

## [x] P1：版本锁不是原子更新

**状态：已完成。** 已新增 `app/core/projects.py`，网页 PATCH 与咕咕工具的既有更新操作均通过 `UPDATE ... WHERE id AND user_id AND version` 执行；版本不匹配返回冲突，不会覆盖已落库的新内容。

### 发现

`PATCH /projects/{pid}` 先读取 `Project.version`，在 Python 中比较后再修改 ORM 对象并提交。两个请求可以先后读到同一个版本、都通过检查，最终后提交的请求覆盖先提交的字段；返回成功却丢掉另一笔修改。

这与前端交互直接叠加：客户名、日期、名称、颜色、阶段和待办都可能在很短时间内触发保存。多标签页、IM 修改和网络乱序时尤为明显。

### 修复方案

1. 将项目更新改为单条原子 `UPDATE`：`WHERE id=:id AND user_id=:uid AND version=:client_version`，同时 `version = version + 1`、刷新 `updated_at`。
2. `rowcount == 0` 时重新按归属读取：不存在/无归属返回 404，存在但版本不同返回 409。
3. 所有项目字段写入均使用同一个客户端版本，并返回完整更新后的项目对象。
4. 为前端返回完整更新后的项目对象，Store 以服务端响应替换本地对象，不只手动更新 `version` 与 `doneAt`。

### 验收测试

- 两个并发 PATCH 携带相同 version：恰好一个 200，另一个 409。
- 不同字段的并发编辑不会双双成功后静默丢字段。
- 404、409、成功三种分支均保持用户隔离与正确版本递增。

## [~] P1：前端乐观更新缺少失败恢复与请求编排

**状态：部分完成。** Store 已按项目串行提交 PATCH，并维护服务端最后确认快照，在网络错误或 409 时回滚；409 会刷新项目列表。输入防抖、组件统一错误提示，以及移除所有组件的预修改仍是下一步。

### 发现

Store 会先直接修改项目对象，再发 PATCH。它只在 409 时全量重拉；网络失败、500 或超时会使页面持续显示未成功保存的内容。项目弹窗中不少 `updateProject`、`updateStages`、`moveProject` 调用没有 `await` 或 `catch`，失败会形成未处理 Promise rejection。

客户输入还会按每个字符触发保存；多个请求会复用尚未更新的 version，既浪费请求，又放大上一节的并发覆盖风险。

### 修复方案

1. 在 Store 建立每项目一条保存队列：同一项目的 PATCH 串行执行；文本字段做 300–500ms 防抖，结构性操作立即提交。
2. 每次乐观修改保留深拷贝快照。任何非成功响应都回滚快照；409 额外拉取最新版本并展示“已刷新”的提示。
3. 组件不直接 fire-and-forget Store Promise。统一由 Store 暴露可等待方法，组件对错误给出一次可见反馈；watch 触发的保存则在 Store 内部消化并维护错误状态。
4. 删除重复的组件级 `p.xxx = value` 预修改，让 Store 成为唯一的乐观更新入口。

### 验收测试

- 模拟 500/断网后，名称、日期、阶段、待办、状态均恢复为服务端确认值。
- 快速输入客户名时，请求数量受防抖限制；乱序响应不会使旧值覆盖新值。
- 连续修改日期、颜色、阶段后，不出现未捕获 Promise rejection。

## [~] P1：阶段与待办状态机重复实现

**状态：第一轮完成。** `projectStages.ts` 已提供项目状态切换、阶段切换、待办完成判定和阶段 clone 的纯函数；Store 与项目弹窗都经由这些转换生成一次 PATCH。项目卡仍有少量拖拽/编辑时的 props 预修改，待下一轮收口。

### 发现

项目阶段推进、自动勾选、撤回自动勾选、完成项目与回退进行中，没有收敛到一处：Store 的 `moveProject()` / `setStage()` 负责项目状态、阶段和待办快照；`ProjectModal.vue` 再实现一份阶段前进/后退、进度计算、待办完成后自动变更项目状态；`ProjectCard.vue` 则直接原地修改 props 中的待办，再决定保存或推进阶段。

三处的输入、拷贝方式和提交顺序不同：Store 以项目对象为源，弹窗以 `localStages` 为源，卡片直接改 props。现在已经有弹窗先 `updateProject(stages)` 再 `moveProject(done)` 的两次写入，而 Store 的 move 本身也会改 stages 的路径。规则一旦调整，很容易只修到其中一处。

### 修复方案

1. 在 `utils/projectStages.ts` 扩展纯状态转换函数，例如 `transitionStage`、`transitionProjectStatus`、`toggleTodo`：输入完整项目快照与用户意图，输出新的 `stages/currentStage/progress/status/doneAt`，不做 Vue 或网络操作。
2. Store 作为唯一写入口：调用纯函数生成下一状态，再通过保存队列提交一次 PATCH；组件只发意图，不直接改 props 或自行拼多次 API 写入。
3. 弹窗的 `localStages` 仅用于编辑草稿；提交时通过同一个转换函数生成 payload。项目卡的待办弹层同样调用 Store 意图方法。
4. 用结构化 clone 或不可变转换替代散落的 `JSON.parse(JSON.stringify(...))`，避免后续字段加入 Date、undefined 或非 JSON 值时静默变形。

### 验收测试

- 同一组项目数据从卡片、弹窗、Store 三个入口执行“前进阶段 / 完成项目 / 回退 / 勾选待办”，得到完全相同的 payload。
- 一次用户动作最多发送一条项目 PATCH。
- 自动完成待办的 `_savedDone` / `autoCompleted` 往返后恢复准确。

## [~] P1：网页 API 与咕咕项目工具存在两套写模型

**状态：部分完成。** 网页和咕咕的更新已共用原子写入底座；咕咕的颜色、归档、阶段、待办等操作按意图生成字段后条件更新，冲突时返回可解释错误而不自动覆盖。创建和阶段状态转换的完整领域服务尚未收敛。

### 发现

`agent/tools/projects.py` 直接读写 `Project`，自行实现创建、更新、阶段、归档和删除；它没有复用 `app/api/v1/projects.py` 的版本锁、schema 校验和统一响应语义，且其写入不递增 `Project.version`，会令网页端下一次带 version 的保存得到过期视图或产生覆盖。

这不是“路由和工具分别有薄适配层”，而是两份独立业务规则。它们已经在默认日期、阶段构造、优先级校验、完成状态和文件统计等方面存在差异。

### 修复方案

1. 提取不依赖 FastAPI 的 `app/services/projects.py`：负责 schema 规范化、原子更新、阶段状态转换和响应投影。
2. REST 路由只负责鉴权、请求/响应转换；咕咕工具只负责参数适配、确认门和面向模型的回执，二者都调用服务层。
3. 服务层提供意图级原子操作，例如“切阶段”“改颜色”“归档”：服务端基于当前行完成小粒度更新，不要求咕咕读后全文回写。只有替换完整 stages 结构这类覆盖型操作才要求明确 version，并在冲突时返回可解释结果；咕咕不得自动重试覆盖用户刚修改的内容。
4. 统一时间出口为 `now_utc()`，默认展示日期再按用户时区转换，移除工具内直接 `datetime.now()` 的业务时间。

### 验收测试

- 网页与咕咕分别执行创建、改名、改日期、完成、归档，数据库字段与 version 结果相同。
- 网页与咕咕并发编辑时，小粒度意图按服务端规则安全合并，覆盖型 stages 更新明确返回冲突而不自动重试。

## [~] P1：项目领域数据未在 API 边界收口

**状态：部分完成。** `status`、`priority`、`progress`、`version` 已在 Pydantic/API 与领域写入底座收紧。日期先后关系、结构化 stages/current_stage 校验，以及前端 API mapper 仍待完成。

### 发现

`ProjectCreate` / `ProjectUpdate` 对 status、priority、progress、日期字符串、阶段 JSON 与 current_stage 的约束过宽。任意 status 会被存储；前端只展示三种列，非法值会让项目从看板消失。progress 可以越界，current_stage 也可指向不存在的阶段。

前端通过 `unknown as Project` 将后端宽松 JSON 断言成严格类型，无法在数据异常时提供明确错误，运行时逻辑反而更脆弱。

### 修复方案

1. 后端定义 status/priority 的 Literal 或 Enum，progress 使用 `Field(ge=0, le=100)`。
2. 日期使用 `date` 或严格 `YYYY-MM-DD` 校验，并校验开始日期不晚于截止日期。
3. 为 stages 定义嵌套 Pydantic schema：唯一非空 key、非空 label、todo 的稳定 id/text/done 类型；有 stages 时 current_stage 必须属于其中。
4. 在兼容旧数据时，读路径可以进行受控规范化；写路径必须拒绝无效数据。前端移除不安全断言，改为依赖生成的 API 类型或显式 mapper。

### 验收测试

- 非法状态、越界进度、坏日期、重复阶段 key、未知 current_stage 全部返回 422。
- 合法旧项目能读取；保存后被规范化为新结构。
- API 返回与 `Project` 前端领域模型可无断言转换。

## [-] P2：文件数量口径与实时刷新不一致

**状态：暂缓。** 文件计数口径与项目列表实时刷新将随文件系统后端重构统一处理，本轮不修改。

### 发现

项目列表统计“根目录且未删除”的文件；单项目读取统计“所有文件且包含已删除文件”；更新响应统计“所有未删除文件”。同一字段 `file_count` 因入口不同含义不同。

此外，项目 SSE 刷新仅在当前列表非空或正在加载时执行。用户项目列表为空时，其他端新建项目不会自动显示。

### 修复方案

1. 明确产品口径：建议 API `file_count` 统一为“项目内全部未删除文件”，需要根目录数时另加 `root_file_count`。
2. 抽成共享 SQL 子查询，list/get/update 均复用；避免三处各写一份 count。
3. Store 增加 `loaded` 标识。收到 projects revision 后，只要已加载过就刷新，即使项目数组为空。
4. 归档列表也维护独立 loaded/refresh 语义，避免注释与实际行为脱节。

### 验收测试

- 根目录文件、子目录文件、回收站文件混合时，三个项目接口返回一致计数。
- 已加载的空项目列表收到 SSE 新建事件后自动出现新项目。
