## 未闭合边界

- **定时任务列表清理存在潜在活跃任务误判风险。** 原 Node Host 列表读取会自动删除未运行过的过期一次任务，并对其他候选依靠 Redis 租约判失败或删除。旧 Python `execute_task` 先获取 Redis 锁再读取任务，续租异常仅记录并继续执行，因此锁过期不证明执行者停止；无锁删除也可能与已获锁但尚未登记启动的执行者交错。并行负责会话已暂停 Node 列表自动清理和崩溃判定，过期和疑似崩溃任务暂时保留；其隔离 PostgreSQL/Redis 回归 7 项、Python 基线 4 项通过。该止损不改变 Python 自身清理，不代表执行者已经停止，也不解决网络分区后的外部副作用。Node runner 尚未生产装配；尚无生产事故证据。完整方案需两端共享持久运行身份和 fencing、覆盖数据库及外部副作用边界，或停写并确认旧运行结束后单执行者切换，再验证网络分区与竞争。
- **现有缺陷及 Node Agent 生产切换阻塞：孤儿恢复与租约代际未统一。** Node 消息历史恢复入口只探测旧版 Redis 状态，未检查 Node PostgreSQL fenced lease。当前 Node 历史读取与 Python writer 并行时也存在风险：Python 会在 PG 行锁事务中写入 `active_run_id`，提交后才取得生成租约；Node 若在此之前完成旧 Redis 探测、之后取得行锁，可能把新运行标为 idle。旧 Redis 多命令探测不是原子快照，探测到回收之间还存在新 Run 竞态，当前 `reap` 无条件删除多个 key，且删除失败被吞掉后仍可能更新 PG。隔离 PostgreSQL/Redis 探针使用真实 Node recovery 和 Redis adapter，在探测后以合成 SQL/Redis 操作模拟 Python 新 Run 启动，复现新 Run 的数据库状态被清空及四个新 Redis key 被删除；未运行真实 Python 协程或完整 HTTP，也无线上事故证据。未来接入 Node Run 时，旧 key 缺失还可能使有效的 Node 租约被忽略。单加 PG 租约检查或 Redis 条件删除不足以与现有 Python writer 互斥；切换前须统一两端启动与恢复的运行身份、锁序和条件清理协议，并完成真实两端隔离交错回归。Node chat 默认生产装配仍未接入。
- 高风险：文件夹创建、重命名和移动在数据库 `COMMIT` 成功但响应丢失时，外层会误判为未提交并回滚物理路径。隔离 PostgreSQL 真实提交后注入断连、配合临时文件和真实 Local PathMirror 已复现：数据库指向新路径，而文件被移回旧路径，新路径读取失败。文件元数据改名/移动也在同样的真实提交后故障注入下复现；`tests/files/folder-commit-unknown.test.ts` 与 `tests/files/file-update-postgres.test.ts` 包含红灯回归。文件夹测试的路径规划 SQL 由替身提供，不代表完整 Host 故障验收。现有 Undo 记录在没有 context 时不会写入，不能充当通用提交收据；需要持久操作标识、同事务收据与文件操作日志及恢复，不能仅跳过回滚。
- `packages/fs/src/node.ts` 逐段检查符号链接和真实路径，末级使用 `O_NOFOLLOW`；检查与打开之间祖先目录可能被替换，现有静态符号链接测试不证明并发替换安全。当前工作树新增的暂存函数同样存在该窗口；它的业务调用在项目过期清理原型，尚未从生产 Host 启用。需要平台安全打开能力和隔离并发验证。
- 删除和恢复的硬链接在提交期间共享 inode；合成数据库适配器与临时文件故障探针确认，另一个进程原地写源会改变目标正文。已接入的 Web 正文/上传/复制路径使用数据库行锁并以临时文件替换，未发现其原地写入；外部进程或已打开句柄不受该锁约束。Python rename 后从旧路径新打开会得到新文件，但已打开的旧句柄仍可修改移动后的 inode；Node 保留源路径到提交因而增加了前一种窗口。完整隔离、跨入口协调与持久恢复仍未验收。
- Node 认证链尚未接入 Python 的用户风险限流和数据替换期间写锁。两项是尚未接入能力，不能按通过计数。
- 文件 `stream-url` 当前返回需要 Cookie 或 Authorization 的普通路径，旧 Python 返回短期签名 URL；仅 Bearer 客户端交给原生媒体元素时无法附带该头。文件读取定向 Node 10 项通过，但未验收此播放路径；禁止把凭据放进 URL，需另行设计兼容方案。
- 上传 multipart 顺序：Node 要求文件字段位于其他字段之后，以便暂存前确定目标与配额；Python 接受文件字段在前。当前 Web 客户端遵循 Node 顺序，旧客户端可能收到 422，尚无完整兼容方案。
- 全局搜索去重仍有 Unicode 差异：Python 使用 `casefold()`，Node 使用 `toLowerCase()`；例如 `Straße` 与 `STRASSE` 在 Python 合并、Node 保留两项，可能改变 AND 查询结果。完整 Unicode case folding 尚未接入，不以局部替换或不等价的区域比较冒充修复。
