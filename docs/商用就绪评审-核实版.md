### P0-2 · 多用户数据隔离

四条原判断**全部核实属实**：

1. **隔离靠工具各自手写 `user_id` 校验，非强制机制**——`agent/tools/base.py::SkillRegistry.dispatch()`（第 209-292 行）是纯分发框架，不含任何 user_id 校验逻辑，直接把 `(db, user_id, args)` 转交给各 handler。全仓搜 `Repository|BaseRepository|scoped_query|RLS` 零命中，没有共享的 scoped-query 抽象。工具目录实际注册了 **60 个 Tool 实例**（不是文件数）。查询模式两种：直接 `.where(X.user_id==user_id)`，或 `db.get(Model, id)` 裸主键查询 + 事后 Python 校验（如 `trash.py:36-37`、`clients.py:43-44`）——后者更脆弱，少一行 `if` 就是越权漏洞。抽查 8 个工具未发现现存漏洞，但模式本身无类型系统兜底。
2. **没有系统性越权测试覆盖**——✅准确，而且**比原评审说的更严重**：全仓库（排除 `.venv`）**没有任何 `test_*.py`/`conftest.py`/`pytest.ini`**，没有 CI/lint 配置（无 `.github/workflows`、无 `pyproject.toml`/`ruff.toml`）。`backend/scripts/` 下 5 个 `smoke_*.py` 是人工冒烟脚本，不是自动化测试。**后端目前是零自动化测试覆盖**，不止越权测试缺失。
3. **隔离没有下沉到查询层/DB 层**——✅准确。无 SQLAlchemy 事件监听器/session 层默认过滤，无 Postgres RLS（`ENABLE ROW LEVEL SECURITY`/`CREATE POLICY` 零命中）。`get_current_user`（`app/core/security.py:56,70`）只做**认证**（你是谁），不做**授权**（这资源是不是你的）——两层是互补但不重叠的机制，认证层覆盖全部路由，授权判断完全下沉到每个 handler。
4. **没有运行时越权检测告警**——基本准确。有 `AuditLog` 表 + `write_log()`，但只覆盖管理员操作（邀请码/config变更/用户管理），不覆盖普通用户的越权访问尝试；`_log_traj` 记工具调用成功/失败但不区分"越权被拦"和"资源不存在"，两者返回同一句错误、日志里也无越权语义标记。

**结论**：三层防线（自动化测试 / DB 层强制 / 运行时检测）**全部缺失**，隔离完全依赖"人肉自觉"——这是本次核实里风险最高、最没有争议的一条。

### P0-3 · 删除安全全链路

| 子项 | 原判断 | 核实结论 |
|---|---|---|
| 确认依赖模型自觉 | 是 | ❌ **对 `delete_project`/`permanent_delete` 说错了**。`agent/confirm.py::needs_confirmation(args, summary)` 是真实代码级拦截：`agent/tools/projects.py:255-257`（`_delete_project`）与 `agent/tools/trash.py:56-58,80-82`（`_permanent_delete`）在执行删除前调用它，`confirm` 非真值时直接 `return blocked`（一段 JSON），**函数在 `db.delete()` 之前就返回，物理上不会执行删除**。对 `delete_file`/`delete_folder`（`agent/tools/files.py:790-800,851-868`）倒是真的没有 confirm gate，但这是**有意为之**——代码注释明写"软删进回收站，30 天可还原——非不可逆，无需二次确认"，设计上就不需要。 |
| 展示影响依赖模型转达 | 是 | ⚠️ **部分对**。受影响文件数是真实 DB 查询算出来的（`projects.py:247-254`：`file_cnt = ...`），不是模型编的，summary 文案是代码生成后交给模型的确定性字符串。但确实没有代码保证"模型把这句话原样展示给用户、且用户真的表达了同意"——理论上模型可以在同一轮自己判断该继续、直接传 `confirm=true`，这条缝隙评审说对了。 |

| 无单测覆盖 | 是 | ✅ 准确（因为整个后端没有任何自动化测试，不止这一条逻辑没测）。 |

**本轮新发现（原评审没提到）**：`Tool.destructive` 是一个存在的元数据标记字段（`agent/tools/base.py:121`），标在 `delete_project`/`permanent_delete` 等工具上，但 `dispatch()`（第 209-292 行）**从不读取它去强制任何行为**——确认门完全是每个 handler 手动 opt-in 调用 `confirm.needs_confirmation()`。现有工具都做对了，但**没有框架级兜底**：以后新加一个危险工具，作者忘了手动加确认调用，不会有任何机制拦住。建议把这条补进 P0-3。

## 三、本轮核实新增发现（原评审完全没有覆盖）

这些是交叉验证过程中挖出来的、原评审五条清单里都没提到的问题，建议补进整改优先级：

1. **后端零自动化测试基础设施**（比"越权测试缺失"更严重）。没有 `tests/` 目录、没有 pytest 配置、没有 CI/lint。任何一条正确性（不止越权）目前都只能靠人工代码审查兜底。

2. **账户注销的文档承诺与代码实现有落差**。`docs/privacy.md` 承诺"注销后，你的所有数据将从数据库和存储中永久删除"，但：
   - 没有用户自助注销入口，`privacy.md` 自己写的也是"如需注销，请通过站内反馈联系我们"（人工处理）；
   - 管理员侧删除用户的实现（`app/api/v1/users_admin.py:128-138`）只做了 `db.delete(user)`，靠 SQLAlchemy `cascade="all, delete-orphan"` 关系清掉数据库表里的行；
   - **`.agent/` 目录下的记忆文件（facts.json 等）和用户上传文件的对象存储实体都不在数据库表里**，是存储层对象，`delete_user` 里**没有调用 `storage.delete(...)` 清理它们**（对比 `clear_memory` 端点明确遍历删除的写法）——大概率会留下孤儿数据，与隐私政策的"永久删除"承诺不完全一致。
   - 也没有找到配套的运维清理脚本，即便管理员想手动清也没有现成工具。

3. **`/memory` `/forget` 目前只在网页聊天生效**。`agent/commands.py:6` 注释"IM 侧待接"，`commands.handle` 全仓只在 `agent/adapters/web.py:200` 一处被调用。飞书/QQ/微信用户暂时无法通过聊天指令查看/删除记忆（仍可用网页端"个人设置"页面清空）。

4. **飞书/QQ 没有类似微信的"封号风险"合规记录**。`docs/agent-im接入架构.md:102`（现编号，微信小节）明确写了"须守《微信 ClawBot 功能使用条款》……个人号自动化风险自负"，但飞书/QQ 的接入文档（`agent-im接入架构.md` 其余小节、`feishu接入指南.md`）通篇未提及条款遵从/风控/封号字样。隐私政策里三家的隐私链接都有，但"平台自身 ToS 合规确认"只做了微信这一家。
