# 咕咕 · 并发与性能优化方案

> 起因：飞书回复偶发很慢。排查后定位为 **LLM 接口延迟抖动**（非飞书/服务器/代码 bug），并顺带盘清了全系统的并发现状。本文记录诊断、现状、分档优化方案。
>
> 相关：[`agent-决策环.md`](agent-决策环.md)、[`agent-im接入架构.md`](agent-im接入架构.md)、[`deploy.md`](deploy.md)、[`devlog.md`](devlog.md)。

---

## 一、诊断：慢在哪

实测（2026-06-23，MiniMax-M3 经 `api.minimaxi.com/anthropic`）：

| 测试 | 结果 |
|------|------|
| 一条 IM `run_collect`（14 字回复） | **17.9s** |
| 其中 `_generate_title`（标题生成） | 1.3s |
| 裸调 LLM，无工具，回一个字 ×6 | **11.9 / 2.3 / 4.0 / 1.9 / 2.4 / 1.7s** |
| 裸调 + 44 工具 | 2.5 ~ 15.6s（不稳定） |
| 工具加 `cache_control` 重复调 | `cache_read=5888` 命中，但延迟仍 8~12s |

**结论**：
- **根因是 MiniMax-M3 接口又慢又抖**（同一请求 1.7s ~ 17s），不是飞书、不是服务器、不是工具数、不是我们的代码。
- 「44 工具慢 5 倍」是**采样偏差**（拿一个慢样本比一个快样本），实测工具数不是主因，**接口抖动才是**。
- **prompt 缓存救不了延迟**：工具命中缓存（省 token 钱）但模型每次仍 attend 全部工具定义，时间不省。
- 网页「等好一会儿才刷新」是因为**实时事件在 `run_collect` 跑完才 publish**，底层一卡，网页跟着等。

> 治本是**换稳的快的 provider**（DeepSeek-V3 / Claude）；但即便如此，下面的并发结构问题在多用户下也会暴露，需一并优化。

## 二、现状：并发结构（基于代码核实）

| 组件 | 现状 | 并发能力 / 瓶颈 |
|------|------|------|
| **Web (uvicorn)** | `WORKERS=1`（`start.sh`），单事件循环，全异步 | I/O 密集能在一个 loop 扛很多并发连接；但**没多核**，CPU/阻塞活卡 loop；SSE 长连接累积在这一个进程 |
| **IM worker** | **单进程，严格串行**：`run_once` 里 `for msg in msgs: await handle()`（`worker.py:118`） | ⚠️ **最弱环**。N 个用户同时发 → 排队，尾延迟 = N × 单条 |
| **IM 网关** | 每 bot 一个 WS 进程，收消息→`produce` 入队（毫秒） | 收+入队不是瓶颈；BYO 每用户一进程，进程数随用户线性涨 |
| **Redis Streams** | 队列 + 消费组 `agent-workers` + `claim_stale` | ✅ 削峰、不丢、**消费组天生支持多 worker 分担 + 崩溃接管**（consumer=`hostname-pid`） |
| **DB (asyncpg)** | `create_async_engine` 无显式 `pool_size` → 默认 ~5+10，`pool_pre_ping=True` | 高并发工具调用可能**耗尽连接池** |
| **LLM 接口** | MiniMax，慢且抖 | **真正的吞吐天花板**（延迟 + 限流） |
| **实时 SSE** | 每浏览器一条长连 + 一个 pubsub 订阅，挂在单 uvicorn loop | 上千并发时连接数是限制 |

**谁先崩（按顺序）**：① IM 串行 worker → ② LLM 限流/延迟 → ③ 单 uvicorn（多核闲置、SSE 累积）→ ④ DB 池。

**已经埋好的扩展性**：worker 无状态（session_id 存 Redis、历史存 DB）、消费组可多开、全异步、pubsub 按用户隔离频道。**现在就能直接多开 worker，不改代码。**

## 三、优化方案（分档）

### Tier 1 · 立刻做，几乎免费，杠杆最大

**① worker：串行 → 有界并发 + 按用户串行** `worker.py`

worker 基本在等 LLM（I/O 密集），串行白白浪费事件循环。改为并发执行：
```
现在： [m1 ██████][m2 ██████][m3 …]        串行，N×单条
改后： [m1 ██████]
       [m2 ██████]   不同用户并行，墙钟≈最慢一条
       [m3 ██████]
```
实现：`asyncio.create_task` + **全局信号量**（并发上限 6~8）+ **每用户一把 `asyncio.Lock`**；ack 改为各自完成时 ack；保留 `claim_stale` 与优雅退出（追踪 inflight 任务）。

⚠️ **两个必须带的正确性保障**（否则引 bug）：
- **按 `owner_user_id` 串行**：同一用户连发的消息不能并行 → 否则乱序 / 抢同一 `session_id` / 历史错乱。不同用户才并行。
- **并发上限**：信号量护住 LLM 限流 + DB 连接池，别无限并发。

收益：单 worker 从「1 条/时刻」→「6~8 条并行」，**0 新进程、0 新内存**，多用户场景上一个量级。

**② 标题生成 + 反思移出关键路径** `runner.py`

现在新会话回复要**等 `_generate_title`（LLM，1~17s 抖动）跑完才发**。改 fire-and-forget：回复立刻发，标题/反思后台补、补完再 publish 更新网页。新会话省 1~10s。（反思已是 fire-and-forget，标题不是 → 一起收口。）

### Tier 2 · 横向扩展 + 运维

**③ 多开 worker 进程**：消费组天生支持，多开即自动分担 + 崩溃接管。与①正交（①吃满单 worker，③叠多核/多机+冗余）。落地：`make restart-im` 起 N 个 + systemd 多实例模板（顺带根治「漏重启 worker」脆弱点，见 devlog）。

**④ uvicorn `--workers N`**：现在用不上多核；SSE/实时无状态（Redis 撑着），多 worker 安全。

**⑤ DB 连接池调大**：显式 `pool_size`/`max_overflow`，匹配「总并发 × 每请求峰值连接」，否则①③④一上并发就耗尽。

### Tier 3 · 治单条延迟（治本，需选型）

**⑥ 换稳的快的 provider**：多 worker 治排队、治不了单条抖动。换 **DeepSeek-V3 / Claude**。DeepSeek 是 OpenAI 兼容，走现有 `_run_openai` 路、改配置不改码（注意用 `deepseek-chat` 而非 `deepseek-reasoner`，后者工具调用会崩）。

**⑦ 慢尾兜底：超时 + 重试**：给 LLM 调用设硬超时（如 25s），撞慢尖峰就取消重试一次，别让离群值占着并发槽。

### Tier 4 · 体验（更后，工作量大）

**⑧ IM 流式**：飞书流式卡片（边生成边更新）或先发「咕咕思考中…」占位。不解决底层慢，但让慢时有反馈、不像死了。

**⑨ 队列水位监控**：已有 worker 心跳；加队列积压（pending/lag）告警，超阈值即知该加 worker。

---

## 四、推进顺序

1. **Tier 1（①②）** —— 改 `worker.py` + `runner.py`，0 新依赖，**性价比之王**，先做。
2. **Tier 2（③④⑤）** —— 横向扩展 + 运维做稳。
3. **Tier 3（⑥⑦）** —— 跟换 DeepSeek 一起。
4. **Tier 4** —— 看产品需要。

**正交关系记牢**：**多 worker / 并发 → 治排队；换 provider → 治单条延迟。** 两件事都要，缺一不可。
