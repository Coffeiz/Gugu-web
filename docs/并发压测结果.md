# 咕咕 · 并发压测结果

> 验证 P1-①（worker 串行→有界并发）的实测数据。
> 相关：[并发优化ROADMAP](并发优化ROADMAP.md)。

## 测试方法

- **环境**：devserver（`192.168.110.51`），provider = MiniMax-M3（`api.minimaxi.com/anthropic`），单 key。
- **被测**：`run_ephemeral`（完整 agent，只读 DB、不发 IM、不落库），用 `asyncio.Semaphore` 模拟有界并发。
- **两类负载**：无工具（prompt 明确「不要调用工具」，单轮 1 次 LLM）/ 带工具（强制 `list_trash`，2 轮）。
- 并发逻辑（保序/去重/限流）另用假 `handle` 单测验证。

## 一、单条延迟（2026-06-25）

| 测试 | 结果 |
|------|------|
| 裸调 LLM，无工具，回一字 ×6 | 1.5 / 1.4 / 2.4 / 5.3 / 1.2 / 1.8s（中位 ~1.6s，偶发 5s） |
| 裸调 + 47 工具 schema ×3 | 2.1 / 2.5 / 2.0s（工具 schema 开销小） |
| `run_ephemeral` 完整单条 ×4 | 3.6 / 4.3 / 4.6 / 4.7s（均 ~4.3s） |

> **对比 2026-06-23 旧数据**：当时 `run_collect` 一条 17.9s、裸调 1.7~17s 剧烈抖动。**版本更新后 provider 明显改善**（现稳定在 1~5s），旧的「换 provider 治延迟」紧迫性大降。

## 二、串行 vs 并发吞吐

| 模式 | 吞吐 | 说明 |
|------|------|------|
| 串行基线 | ~21 条/分 | 一次一条，2.9s/条 |
| 并发 sem=8（无工具） | ~246 条/分 | **≈6× 提速**，0 报错，延迟几乎不涨 |

## 三、升压找限流拐点

**无工具**（单轮）：

| 并发 | 吞吐 | 成功 |
|------|------|------|
| sem=8 | 246 条/分 | 24/24 ✅ |
| sem=16 | 347 条/分 | 24/24 ✅ |
| sem=24 | — | 2/24 ❌ 全 429 |

**带工具**（2 轮，更接近真实）：

| 并发 | 吞吐 | 成功 |
|------|------|------|
| sem=8 | 105~136 条/分 | 12/12 ✅ |
| sem=16 | 189~221 条/分 | 12/12 ✅ |
| sem=20 | — | 0/12 ❌ 全 429 |
| sem=24 | — | 0/12 ❌ 全 429 |

> 带工具拐点（~16-20）比无工具（~24）低：每条 handle 连发多轮 LLM，单位时间调用率翻倍，更早撞限流。429 是**全或无**——过线整批失败。

### ⑦ 退避重试的效果（同 sem=20 带工具）

加了 `_stream_round` 的瞬时错误退避重试（出 token 前，1/2/4s ×3）后复测 sem=20：

| | 成功 | 报错 | 延迟（中位/max） |
|---|------|------|------|
| 加 ⑦ 前 | 0/12 ❌ | 12× 429 | — |
| 加 ⑦ 后 | **12/12 ✅** | 0 | 4.7 / 8.8s（含退避等待） |

> 超限流的 429 被「等 1/2/4s 再发」吸收 → 从「整批硬失败」变成「慢几秒但全成功」。代价是延迟升高（退避等待）。意味着偶发突发冲过 16 上限时优雅降速、不丢消息。

### 端到端验证（真实队列 → worker → ack，2026-06-25）

worker 重启加载新代码后，往真实 `im:inbound` 灌 6 条（不同假 puid → 走不同 user_gate 锁触发并发；假地址 → 回复静默失败、不发真 IM），量「灌入 → 全部 ack」墙钟：

| 模式 | 6 条墙钟 | 判定 |
|------|---------|------|
| 实测（新代码 worker） | **8.1s** | ✅ 并发生效 |
| 串行参照 | ~24s（6×4s） | — |

> 走的是完整链路：队列 → `run_once` 按空闲槽消费 → 并发 `_dispatch`（per-user 锁 + 去重）→ `handle`（run_collect 全脑）→ ack。8.1s ≈ 一条 handle 时间 + 消费/落库开销，远低于串行 24s。同用户保序另由逻辑单测验证（见上「并发逻辑」隐含）。

## 四、结论

1. **并发提速 ~6×**，与理论（IO 密集 + sem）吻合。
2. **单 key 安全并发 ≈ 16**：带工具实测 sem=16 干净（~190 条/分）、sem=20 全 429。建议 `_MAX_CONCURRENCY = 16`（要更大 margin 可设 12）。
3. **瓶颈是 LLM provider 的 key 额度，不是机器**：DB 池（40）/ CPU / 内存都没到瓶颈——handle 在等 LLM 的数秒里不占 DB 连接。
4. **⑦ 慢尾兜底（429 退避重试）✅ 已实现并验证**：sem=20 带工具从 0/12 → 12/12（见上）；拐点近且 429 全或无，重试把硬失败变成短延迟。
5. **要再扩吞吐 = 多备 provider key**（每 key 一份限流额度，总并发 ≈ 16 × key 数），不是调大信号量数字。

## 五、1000 用户容量模型

- 单 key sem=16 ≈ 190 条/分 ≈ 1.1 万条/小时。
- 1000 用户每人每天 5~20 条 → 摊到活跃时段 ~0.5k~2k 条/小时，**平均负载单 key 即够**。
- 风险是**同步突发**（定时提醒齐发 / 午休齐聊）→ 靠 Redis 队列缓冲 + worker 排空，几分钟消化。
- 稳扛 1000 + 突发：配 **2~3 个 key**，`_MAX_CONCURRENCY` 设 32~48（每 key ~16）+ ⑦ 重试。
- worker 单进程足够（IO 密集）；多 worker（P3）等单进程 CPU 真撑不住再上，由埋点数据触发。

> 精确容量需真实流量埋点（队列深度 / lag）才能定，以上为实测外推。
